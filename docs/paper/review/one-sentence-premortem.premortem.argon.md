10. **Single-Vendor, Single-Harness Scope Invalidates Generalizations to "Coding Agents" Broadly (Title, Abstract, Sections 4.3, 5.2, 6, 7; `PROTOCOL.md`, `run.py`):** Although the title, abstract, and Section 6 frame the result as a property of "coding agents" and "LLM-based coding agents," all 240 trials in `study-2026-11b` (and all 90 trials in `study-2026-11`) were executed in a single vendor's CLI harness (`claude` v2.1.112) on two models from the same vendor and generation (`claude-opus-5-5` and `claude-sonnet-5-5`). 11. **Single-Call Multi-Item Judging Permits Halo Effects, Order Effects, and Many-to-One Row Matching (Sections 4.5, 5.3, 5.4; `judge.py`, `prompts/judge.txt`, `judge/gemini/`, `judge/relevance/`):** In `judge.py:trial_prompt` (lines 204–215), each judge call presents all $K \in [6, 10]$ reference items and all up to 10 candidate table rows simultaneously in a fixed order and asks only for a list of covered reference item IDs (`{"covered": [...]}`), rather than evaluating each `(reference item, candidate row)` pair independently or randomizing order. This joint prompt allows a single broad table row to be credited with covering multiple distinct reference items (many-to-one matching) and allows halo effects across items within a trial, while the separate relevance check (`judge.py:do_relevance`, Section 5.4) only asks whether each row is a "concrete, plausible risk" given the request text alone—without inspecting the repository to check whether the claimed risk is actually true or hallucinated. Because `judge/gemini/*.json` and `judge/grok/*.json` record only covered item numbers and not row-to-item mappings, ruling out many-to-one row matching, order bias, and hallucinated "plausible" risks requires re-prompting the judge for bipartite `(row, item)` alignments and repository-grounded factuality on the existing answers in `repo/benchmark/study-2026-11b/runs/answers/*.md`.

15. **Prompt-Order Mechanism in Section 6 Is Conflated with Dual-Prompting Emphasis Because No Post-Plan Control Was Run (Sections 1, 3, 6; `PROTOCOL.md`, `run.py`):** Section 6 ("A possible reading," line 273) attributes the coverage gain to prompt *order*—arguing that in `RED-plain` the plan is written first and the risk table second, whereas in `RED-risk` failure modes are listed before planning—and connects this to Inverse Constitutional AI / InvThink (Kim et al., 2026).
