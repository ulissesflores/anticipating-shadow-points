Three reviewers independently listed ways a software change could go wrong.

Change request: Replace the integer IDs that the API exposes with UUIDs, while keeping existing API clients working.

Items (the letter is the reviewer):
A1. In app/api/summaries.py, the path parameters on readsummary, updatesummary, and deletesummary currently enforce id: int = Path(..., gt=0). Replacing this parameter type with a UUID will cause existing clients sending integer IDs to fail with 422 Unprocessable Entity responses, while retaining gt=0 will reject valid UUIDs.
A2. In app/models/pydantic.py and app/models/tortoise.py, SummaryResponseSchema explicitly declares id: int, and SummarySchema is auto-generated from TextSummary. Replacing id directly with a UUID in responses will break existing client applications whose JSON deserializers expect an integer identifier.
A3. In app/models/tortoise.py, TextSummary relies on Tortoise's default auto-incrementing serial integer primary key (SERIAL NOT NULL PRIMARY KEY in the initial migration). Altering or dropping the primary key column in Tortoise ORM frequently breaks Aerich migration autogeneration, risking failed deployments or corrupted table state in PostgreSQL.
A4. If a new UUID column is added to TextSummary to support both identifier types, any existing database records will have NULL values unless an explicit migration backfill is executed. Existing rows would then be inaccessible to clients attempting to retrieve them via the new UUID-based lookups.
A5. The database operations in app/api/crud.py (get, put, delete) query directly via TextSummary.filter(id=id). If an endpoint accepts both integers and UUIDs but forwards them without branching or type casting, PostgreSQL will raise type mismatch exceptions when comparing UUID strings against integer columns or vice versa.
A6. In app/api/summaries.py, createsummary invokes backgroundtasks.addtask(generatesummary, summaryid, ...), which app/summarizer.py types as summaryid: int and uses in TextSummary.filter(id=summaryid).update(...). If crud.post returns a UUID instead of an integer ID, background article summarization will fail silently without updating the database record.
A7. If a secondary UUID column is introduced to preserve integer primary keys for backward compatibility, omitting a unique=True or indexed constraint on the new field will cause UUID lookups in app/api/crud.py to trigger full table scans as the dataset grows. Furthermore, lack of a uniqueness constraint risks duplicate UUID assignments if not enforced at the database level.
A8. In app/api/crud.py, get, getall, and put return database records as raw dictionaries using .values(). If a Tortoise UUIDField is added, .values() returns Python uuid.UUID objects that can cause serialization failures or unexpected types when returned directly through FastAPI routes.
A9. The readallsummaries endpoint relies on crud.getall() via TextSummary.all().values(), which depends on PostgreSQL's natural ordering by the sequential serial integer id. Exposing randomly generated UUIDs (such as UUIDv4) without adding an explicit .orderby('createdat') clause will lead to non-deterministic listing order for existing clients.
A10. The test suite in tests/testsummaries.py and tests/testsummariesunit.py relies heavily on hardcoded integer IDs in mocked responses, assertions, and validation tests (such as expecting 422 errors with ctx: {'gt': 0} for id=0). Modifying endpoint validation or response schemas without maintaining dual-type testing will cause widespread test failures and hide regressions in backward compatibility.
B1. Database schema mismatch – Changing primary key columns from INTEGER to UUID may break existing migrations, raw SQL scripts, and the SQLite/PostgreSQL schema defined in project/db/create.sql and migration files, causing migration failures or data loss.
B2. ORM model incompatibility – Tortoise‑ORM models in project/app/models/tortoise.py expect integer fields for IDs; switching to UUIDField requires updates to model definitions, default value generation, and possibly the pydantic schemas that serialize these IDs.
B3. CRUD endpoint expectations – API routes in project/app/api/crud.py and summaries.py parse request/response bodies assuming integer IDs; converting to UUID strings will break request validation, URL routing (/items/{id}), and downstream client code that expects numeric IDs.
B4. Serialization / validation errors – Pydantic models (project/app/models/pydantic.py) may still type IDs as int, leading to validation errors when UUID strings are returned or accepted, and causing mismatched OpenAPI docs.
B5. Foreign‑key relationships – Any relationships that reference the primary key (e.g., foreign key columns in other tables or models) must also be migrated to UUID; otherwise referential integrity constraints will fail and queries will raise errors.
B6. Existing test suite – Tests in project/tests/ (e.g., testsummaries.py, testping.py) use hard‑coded integer IDs; after the change they will fail or pass incorrectly, masking real bugs.
B7. Data migration strategy – Introducing UUIDs on a live database requires a data migration path; without a proper migration script, existing rows with integer IDs will become orphaned or duplicated.
B8. Performance considerations – UUID primary keys can impact index size and query performance; the codebase may not account for this, leading to slower API responses and higher storage usage.
B9. Client compatibility layer – To keep existing API clients working, a compatibility shim must translate between integer and UUID representations; lacking this will cause backward‑compatibility breakage for external consumers.
B10. Environment configuration – Deployment scripts (docker-compose.yml, Dockerfile, release.sh) may include commands that assume integer auto‑increment behavior (e.g., seeding data with numeric IDs); these need to be updated to generate UUIDs.
B11. Logging and monitoring – Log statements and metrics that format IDs as integers will break or produce unreadable output when IDs become UUID strings.
B12. Security and validation – UUIDs can be supplied in various formats (with/without hyphens); insufficient validation may allow malformed IDs to reach the database, causing errors or potential injection vectors.
C1. GET, PUT, and DELETE type the path as id: int = Path(..., gt=0), so a UUID is rejected with 422 before crud runs, and the single /{id}/ route cannot also be registered as a UUID. Switching that annotation so only UUIDs parse turns /summaries/999/ from 404 "Summary not found" and /summaries/0/ from the greaterthan / gt: 0 422 (the bodies locked in testsummaries.py and testsummariesunit.py) into a UUID-parse 422.
C2. POST and DELETE serialize id with the hand-written SummaryResponseSchema (id: int and url only), while GET, PUT, and the list use SummarySchema from pydanticmodelcreator(TextSummary), whose id follows Tortoise’s implicit integer primary key. Changing only one of those two types makes that set of routes fail response validation with 500 while the others still emit integers.
C3. crud.post inserts the row before SummaryResponseSchema checks the response, and deletesummary calls crud.delete before returning the pre-delete dict through that same schema. A UUID that still has to satisfy id: int becomes a 500 after the insert or delete has committed, and because url is not unique a retry of the failed create writes a second textsummary row.
C4. createsummary feeds crud.post’s return value to generatesummary, which does TextSummary.filter(id=summaryid).update(...). A zero-row update is success, so passing the public UUID while id is still the serial key (or the serial key while the column is already uuid) leaves summary as "" after the 201, and that error is raised inside the background task, outside addexceptionhandlers=True.
C5. TextSummary never declares id; Tortoise adds an autoincrement integer primary key, and crud.get, put, delete, and generatesummary all filter that field. An extra non-primary-key UUID column is never looked up, and a UUIDField primary key with no stored default leaves summary.id as None after save(), so the 201 body and the background update both miss the row.
C6. The applied column is "id" SERIAL in migrations/models/020250421234125init.py. PostgreSQL will not cast that serial to uuid, downgrade is empty, and CREATE TABLE IF NOT EXISTS means editing this file does not change databases that already ran it. That migration also creates aerich.id as SERIAL, and with no /v2 prefix the integers clients already stored from POST /summaries/ stay valid only if a unique legacy column is backfilled before the serial key is dropped.
C7. The running app uses registertortoise(..., generateschemas=False), the tests use generateschemas=True on DATABASETESTURL, and db.generateschema() imports models.tortoise rather than app.models.tortoise. entrypoint.sh only waits for Postgres, and Dockerfile.prod starts gunicorn with no aerich upgrade (release.sh only swaps the Heroku image), so an empty webtest can get a UUID primary key from the model while webdev and production stay on the serial column and fail with an asyncpg type error.
C8. Both suites call PUT /summaries/1/ with an invalid URL and expect the 422 detail to be the URL-scheme message, which happens only because 1 passes Path(gt=0) and the body fails afterward. Once 1 is an invalid UUID, a client that still sends a stored integer together with a bad body gets a path uuidparsing error in place of the body error it handles today.
C9. On this unversioned /summaries API the JSON id is a number: POST returns {"id": summaryid, "url": ...}, DELETE echoes that pair, and GET/PUT/list return id from .values() under SummarySchema. Replacing that field with a UUID string breaks clients generated from the current OpenAPI integer (and testcreatesummary’s exact {"id": 1, ...} body) even if the path still accepts the old integer, and a GET schema that drops or renames id no longer matches the id the client just received from POST.
