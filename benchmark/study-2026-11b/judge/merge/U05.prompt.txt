Three reviewers independently listed ways a software change could go wrong.

Change request: Make sessions roll by default, so that every request extends the session's expiry.

Items (the letter is the reviewer):
A1. In shouldSetCookie, enabling rolling sets the cookie on every request even when req.session.cookie.expires is null. For applications relying on browser-session cookies without a configured maxAge, this needlessly emits a Set-Cookie header on every response despite having no expiration timestamp to extend.
A2. If a custom or third-party session store does not implement store.touch() and resave is false, res.end will never persist the updated expiration to the backend store. This causes the server-side session to expire and be deleted while the client browser's cookie continues to roll, resulting in unexpected mid-session logouts.
A3. Touching or saving sessions on every single request converts read-only HTTP traffic into continuous write operations against the session store. For network-backed stores such as Redis, Memcached, or MongoDB, this introduces severe write amplification, elevated latency, and connection pool exhaustion under high concurrency.
A4. In index.js, the monkey-patched res.end defers final response completion (writeend()) until the asynchronous store.touch() callback resolves. If the session store encounters network delays or hangs, every HTTP response across the application is delayed waiting for the touch operation.
A5. Emitting a Set-Cookie header on every response via onHeaders breaks downstream HTTP caching by proxies, CDNs, and browsers for otherwise cacheable GET responses. In poorly configured shared caches, this also risks caching and leaking user session identifiers to other clients.
A6. Defaulting to a sliding expiration prevents applications from enforcing absolute session timeouts required by security compliance standards (e.g., PCI-DSS). Background browser requests, polling loops, or periodic asset pings will keep sessions alive indefinitely without requiring user re-authentication.
A7. Parallel requests from the same client will independently touch the session in memory and fire concurrent store.touch() or store.set() calls. These overlapping operations introduce race conditions in the store and result in out-of-order responses delivering conflicting Set-Cookie expiration headers.
A8. If store.touch() produces an error, res.end delegates the error to defer(next, err) after response writing may have already begun via writetop(). Invoking Express's next(err) after headers or partial bodies are sent triggers "Cannot set headers after they are sent" runtime errors instead of cleanly aborting.
A9. A careless implementation that unconditionally forces cookie setting risks overriding the saveUninitialized: false guard for newly generated sessions (cookieId !== req.sessionID). This would set cookies and allocate store entries for anonymous visitors on every request, violating privacy requirements and filling the store with empty sessions.
A10. Flipping the default value of rolling is a breaking change that fails existing assertions across test/session.js, which expect shouldNotHaveHeader('Set-Cookie') on subsequent unmodified requests. Altering this behavior without a formal deprecation period (similar to resave and saveUninitialized) disrupts downstream applications that depend on stable cookie headers.
B1. touch may not be invoked automatically – if request handlers or middleware don’t call req.session.touch(), merely extending the expiry in the code won’t actually roll sessions on each request.
B2. Race conditions with concurrent requests – resetting cookie.maxAge without persisting the new value to the store could cause stale expiration times when multiple requests modify the same session simultaneously.
B3. Inconsistent behavior across session stores – some stores (e.g., Redis, MongoDB) may ignore the maxAge change unless save() is called; blindly resetting maxAge could leave the underlying store unchanged, resulting in premature expiration.
B4. Performance impact – invoking touch on every request adds an extra write to the session store, which can degrade throughput for high‑traffic services if the store isn’t optimized for frequent updates.
B5. Cookie size limits – continuously resetting cookie.maxAge without clearing other cookie attributes may eventually push the serialized cookie beyond browser limits, causing request failures.
B6. Security‑related side effects – extending the session lifetime by default may violate security policies (e.g., short‑lived auth tokens) and increase exposure to session fixation or hijacking attacks.
B7. Potential loss of original maxAge semantics – the current resetMaxAge restores originalMaxAge; making sessions roll by default could unintentionally hide configuration errors where originalMaxAge is set incorrectly.
B8. Compatibility with express-session options – the library supports rolling: true in its config; duplicating that logic here could create conflicting behaviors or double‑increment expiration, leading to erratic session lifetimes.
B9. Testing suites may break – existing unit tests (e.g., in test/session.js) assume non‑rolling behavior; changing the default will cause assertions about expiration timestamps to fail.
B10. Memory leak risk in in‑memory stores – constantly resetting expiration without a corresponding cleanup may keep idle sessions alive indefinitely, exhausting memory in development or low‑capacity environments.
B11. Unexpected side effects for API clients – clients that rely on a fixed session timeout (e.g., mobile apps) may experience prolonged sessions, affecting token refresh logic and potentially causing stale authentication data to persist.
B12. Misaligned documentation – the README and code comments describe “resetMaxAge” as an explicit operation; making it automatic would render those docs inaccurate, leading to confusion for future maintainers.
C1. rolling is Boolean(opts.rolling), so the default is false, and the tests should default to false, should only set-cookie when modified, and should Set-Cookie only once for browser-session cookies require an unmodified later response to send no Set-Cookie. A silent flip in 1.19.x skips the deprecation path already used for an omitted resave or saveUninitialized, and an explicit rolling: false has to keep the absolute cookie deadline.
C2. The default cookie is { maxAge: null } (no Expires). Session.resetMaxAge writes originalMaxAge back, which stays null, so a roll only repeats Set-Cookie and does not extend a lifetime. Inventing a maxAge would turn those browser-session cookies into persistent ones; should not reset cookie covers the case where the handler sets expires to null.
C3. shouldSetCookie honors rolling only when cookieId === req.sessionID. With saveUninitialized: false, a new unmodified session must not be stored and must not get a cookie (should not force cookie on uninitialized session…, should prevent uninitialized session from being touched). Rolling inside generate() would set connect.sid before any session data exists.
C4. rolling only forces Set-Cookie. Store expiry is a separate res.end path: session.touch(), then save if shouldSave, or store.touch when the store has that method. A store without touch and with resave: false keeps its own TTL (the README already says those stores need resave: true), so the browser cookie slides while MemoryStore.getSession still drops the record at the old cookie.expires and the next get calls generate() with a new id.
C5. MemoryStore.touch reloads through getSession, which deletes the record when expires <= Date.now() and then does nothing. A request still in flight when that deadline passes loses the session, while onHeaders still setcookies the same id. set would have written it back; the recommended resave: false path does not.
C6. hash() skips cookie, so a rolled expiry is not a modification and resave: false must not set the whole session. Treating the new Expires as a change makes every request save and brings back the parallel-request overwrite the resave option exists to avoid.
C7. An overlapping request that still holds the old id will Set-Cookie that id if rolling is on, and regenerate()'s new id loses if that response is applied last. Today that unmodified response sends no Set-Cookie, so it cannot put the old id back. This is separate from the resave data race described in the README.
C8. onHeaders calls touch() and then setcookie on the first write, and the touched flag stops res.end from touching again. A res.write before regenerate(), a maxAge change, or res.end (the slow-write case) commits the rolled cookie early; stamping expiry only at res.end after that flush leaves the browser on the pre-touch Expires.
C9. For cookie.secure on a non-secure request, onHeaders returns before setcookie (should not set-cookie when insecure) while res.end still updates the store. Rolling that HTTP response either sends connect.sid in cleartext or extends the store while the HTTPS cookie's Expires stays put. secure: 'auto' and sameSite: 'auto' run only in store.generate, so a rolled Set-Cookie repeats cookie.data from the store, not a new result of a cookie function.
C10. The expires setter sets originalMaxAge from the maxAge getter (expires - Date.now()). resetMaxAge assigns that back through maxAge, which builds a new Date and can store a smaller value (the tests allow 1999 versus 2000). createSession restores originalMaxAge after new Cookie because that setter clobbers it; the touch/save path persists the clobber, so every rolled request ratchets the window down.
C11. Nothing sets Cache-Control or Vary, and setcookie appends Set-Cookie. Rolling puts the signed id on responses that currently omit it, including matches under cookie.path (rfcPathMatch, so /admin matches /admin/users and not /administrator). A shared cache can replay one client's connect.sid, and subresource requests keep sliding maxAge so it never elapses while the page loads. Requests that fail the path check must not extend the session.
