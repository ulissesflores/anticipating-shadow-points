Three reviewers independently listed ways a software change could go wrong.

Change request: Let pet owners book visits online, without two visits being booked for the same vet at the same time.

Items (the letter is the reviewer):
A1. The Visit entity and database tables currently link only to petid with no relationship to Vet, so failing to add a vetid foreign key across H2, MySQL, and PostgreSQL schemas will cause persistence and data integrity failures.
A2. The Visit class and database column visitdate store only a LocalDate (DATE) without time information, which would either restrict vets to a single visit per day or fail to prevent overlapping bookings at specific times.
A3. Because visits are persisted only through cascading updates on the Owner aggregate root (OwnerRepository.save(owner)), concurrent bookings by different owners will bypass entity-level locking and cause double-booking race conditions unless protected by a database unique constraint or explicit locking.
A4. VisitController configures dataBinder.setDisallowedFields("id", ".id"), which will silently discard incoming form parameters like vet.id or vetId, leaving the assigned vet null upon submission.
A5. The application relies on separate DDL scripts (schema.sql under h2, mysql, and postgres) without automated migration tooling, meaning schema updates applied only to H2 will cause CI and containerized tests like MySqlIntegrationTests and PostgresIntegrationTests to fail.
A6. The codebase lacks a VisitRepository and loads visits via eager relationships on Pet, so checking vet schedule conflicts by traversing Owner collections in memory will trigger severe N+1 query and memory issues.
A7. Relying solely on a database unique constraint to prevent double-booking will trigger an unhandled DataIntegrityViolationException that crashes to error.html rather than displaying validation feedback on pets/createOrUpdateVisitForm.html.
A8. The application has no authentication or authorization layer, leaving routes like /owners/{ownerId}/pets/{petId}/visits/new publicly accessible so that any user could book or modify appointments for another owner's pet by altering URL parameters.
A9. VetRepository.findAll() is cached with @Cacheable("vets"), which will lead to stale appointment availability if booking or schedule data is improperly attached to the cached Vet domain model without an eviction policy.
A10. Existing tests in VisitControllerTests post visit payloads containing only date and description, so making a vet selection and time mandatory without updating the test fixtures will break the current test suite.
B1. Missing vet‑appointment model – the current code only stores Visit linked to a Pet; adding a vet booking requires new entities (e.g., Appointment, VetSchedule) and database migrations, which are absent and would break compilation or runtime persistence.
B2. No validation for overlapping slots – there is no service or constraint that checks whether a vet already has an appointment at the requested time, so concurrent requests could easily create double‑bookings.
B3. Concurrency race conditions – the processNewVisitForm method saves the Owner (which cascades Visit) in a single transaction without any locking; simultaneous requests could read the same schedule, both think the slot is free, and both insert, violating the “no double‑book” rule.
B4. Time‑zone and date handling – Visit stores only a LocalDate (no time), while vet appointments need a precise timestamp; without explicit time‑zone handling, bookings could be ambiguous or incorrectly compared across regions.
B5. UI and controller mismatches – existing VisitController URLs (/owners/{ownerId}/pets/{petId}/visits/new) are pet‑centric; introducing vet‑specific booking would require new endpoints and form fields, otherwise users cannot select a vet or a time slot, leading to broken navigation.
B6. Repository queries not optimized for slot checks – VetRepository only provides findAll(Pageable); a new query to fetch existing appointments for a given vet and time range must be added, otherwise the overlap check will be inefficient or impossible.
B7. Missing transactional boundaries – the current save operation (owners.save(owner)) does not encompass the creation of a vet appointment; without a proper @Transactional method that writes both the pet visit and the vet schedule atomically, partial failures could leave orphaned records.
B8. No API for external clients – “book visits online” implies a REST/JSON endpoint, yet the application only returns HTML views; exposing a proper @RestController with DTOs and validation is necessary, otherwise external integrations will fail.
B9. Potential data integrity issues – without foreign‑key constraints linking an appointment to both Vet and Pet, malformed or stray records could be inserted, breaking referential integrity and causing cascade delete problems.
B10. Lack of unit/integration tests for the new flow – the test suite currently covers VisitController and VetController separately; adding concurrent booking logic will require new concurrency and scheduling tests, otherwise regressions will go unnoticed.
B11. Security/authorization gaps – the existing controllers do not enforce any role‑based access; allowing owners to book directly could expose endpoints to unauthenticated users unless proper security rules are added.
B12. Performance impact on existing pagination – the VetController paginates vets but does not account for potentially large appointment collections; naïve loading of all appointments per vet could degrade response times when the booking feature is activated.
C1. Visit has no veterinarian, and visitdate is a DATE mapped as LocalDate, duplicated in db/h2/schema.sql, db/mysql/schema.sql, and db/postgres/schema.sql. spring.jpa.hibernate.ddl-auto=none and the MySQL and Postgres scripts use CREATE TABLE IF NOT EXISTS, so a column added only on the entity, or only in the H2 script that drops tables, never reaches the docker-compose database or the k8s Postgres profile; a NOT NULL vet breaks the four seeded visits, and a nullable unique (vetid, slot) still accepts every null vet because MySQL and Postgres treat those nulls as distinct.
C2. Bookings are written with owners.save(owner), cascading one owner's pets and visits, so a check of that owner's eager collection cannot see another owner's visit with the same vet. The pet-name race was closed with a real unique index and a DataIntegrityViolationException catch in PetController after saveAndFlush that looks for the text uniqueownerpetname; VisitController has no such catch, MySQL's unnamed UNIQUE will not contain that text, and PetClinicConcurrencyTests only races two pet creates on owner 1.
C3. VisitController.setAllowedFields disallows id and .id, so a posted vet.id is stripped and the visit is stored with no vet, which never trips a uniqueness rule. fragments/selectField.html submits each option's toString, which works for pet type only because PetTypeFormatter parses the name; Vet has no formatter, and VetRepository has no findById.
C4. There is no Spring Security on the classpath, and POST /owners/{ownerId}/pets/{petId}/visits/new identifies the pet only by ids, while Owner has no login, only a ten-digit telephone. Anyone who can guess those ids can book another person's pet or fill a vet's calendar, and k8s/petclinic.yml already publishes the app as a NodePort running the image dsyer/petclinic, which would not contain this change.
C5. visitdate is a calendar day, the form control is a date input, and both Visit() and VisitController use LocalDate.now() in the JVM zone, which is UTC in the k8s container while the seeded owners are in Madison. A unique key on that column allows one visit per vet per day and cannot separate 09:00 from 15:00, there is no duration so overlapping times both insert, and the current check rejects any date that is not after today, so a same-day opening can never be booked.
C6. The only visit route is .../visits/new, so a booked slot stays occupied: Pet.visits has no status and there is no cancel or reschedule. The same pet can also be booked with two vets at once, and owner 6's Samantha and Max can be submitted together, because a constraint on the vet does not constrain the pet.
C7. VetRepository.findAll and findAll(Pageable) are @Cacheable("vets") with no expiry and no @CacheEvict, and the vet page uses a page size of 5 while six vets are seeded, so a dropdown or free/busy view built from that cache is stale or omits a vet. The cache is the local JCache manager in CacheConfiguration, so it is not shared if k8s/petclinic.yml is scaled past replicas: 1.
C8. Pet.visits is a LinkedHashSet and BaseEntity defines neither equals nor hashCode, so two Visit instances for the same vet and slot are both kept. loadPetWithVisit attaches the new Visit before validation, ownerDetails.html and createOrUpdateVisitForm.html show only date and description, and I18nPropertiesSyncTest fails the build if a new label is hardcoded or missing from any locale file other than messagesen.properties.
C9. VisitControllerTests, ClinicServiceTests, and src/test/jmeter/petclinictestplan.jmx create visits with only date and description, and the JMeter POST sends date=2013-02-22, which processNewVisitForm already rejects as typeMismatch.visitDate. Making the vet required breaks those callers; leaving it optional leaves a write path that never hits the conflict rule.
