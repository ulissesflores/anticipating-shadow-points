Three reviewers independently listed ways a software change could go wrong.

Change request: Make the session middleware's cookie Secure and SameSite=Strict by default.

Items (the letter is the reviewer):
A1. In starlette/middleware/sessions.py, the parameter controlling the Secure attribute is named httpsonly: bool = False, not secure; introducing a new secure parameter or renaming httpsonly would break backward compatibility for existing callers or introduce conflicting configuration flags.
A2. In starlette/testclient.py, TestClient defaults baseurl to http://testserver, so enabling Secure by default will cause the client's cookie jar to drop the session cookie on subsequent HTTP requests, breaking the majority of test suites in tests/middleware/testsession.py.
A3. Starlette applications frequently run in local development over plain HTTP (http://localhost:8000 or http://127.0.0.1:8000), where browsers will reject or refuse to transmit Secure cookies, silently breaking session persistence out of the box for developers.
A4. Changing samesite from "lax" to "strict" by default will prevent browsers from sending the session cookie on top-level cross-site GET navigations, breaking common workflows such as third-party OAuth/OIDC callbacks, magic links, and incoming external links.
A5. In tests/middleware/testsession.py, testsecuresession specifically checks that an unsecure client fails to persist session state when httpsonly=True is explicitly passed; changing the default makes this test redundant and leaves no test coverage verifying that httpsonly=False properly allows session persistence over HTTP.
A6. In starlette/responses.py, Response.setcookie defaults to secure=False and samesite="lax" (using parameter names secure and samesite), so changing SessionMiddleware's defaults creates confusing inconsistencies in cookie handling and naming conventions across Starlette's public API.
A7. Applications pairing SessionMiddleware with CORSMiddleware(allowcredentials=True) across separate frontend and backend origins or subdomains will have session cookies blocked on all cross-origin requests under SameSite=Strict.
A8. Documentation and examples in docs/middleware.md and docs/config.md explicitly describe httpsonly defaulting to False and samesite defaulting to 'lax'; failing to update these will leave users with inaccurate documentation and broken copy-paste code examples.
A9. If an implementer attempts to set the Secure flag dynamically based on scope["scheme"] == "https" rather than an explicit configuration setting, the cookie will fail to be marked Secure behind TLS-terminating reverse proxies that forward requests to Starlette over plain HTTP.
A10. In starlette/middleware/sessions.py, self.securityflags is shared between persisting session data and clearing sessions via an expired Set-Cookie header; any discrepancy in how attributes are formatted or applied could prevent browsers from properly matching and evicting stored session cookies.
B1. Local development over HTTP will lose the session cookie – the default httpsonly=False currently allows plain‑HTTP; switching Secure on by default will prevent browsers on http://localhost (used by the test client and most dev servers) from receiving the cookie, causing authentication failures in development and CI.
B2. Existing tests assume SameSite=lax – the test suite (tests/middleware/testsession.py) validates the default Set‑Cookie header; changing the default to SameSite=Strict will break those assertions and require updates to the expected header string.
B3. Positional argument compatibility – some code may instantiate SessionMiddleware(app, secretkey, "mycookie") without naming the samesite or httpsonly arguments; changing the default order or adding a new required flag could unintentionally shift the meaning of the third argument (formerly sessioncookie) to samesite.
B4. Clients that rely on cross‑site requests (e.g., OAuth redirects) will be blocked – SameSite=Strict prevents the cookie from being sent on any cross‑origin navigation, potentially breaking authentication flows that redirect users to external providers and back.
B5. Browser compatibility for SameSite=None is unaffected – the code still allows samesite="none" but the Secure flag will always be added when httpsonly is true; however, some browsers reject cookies that specify SameSite=None without Secure, so if a caller explicitly requests samesite="none" they must also ensure httpsonly=True, otherwise the cookie will be silently dropped.
B6. securityflags string construction may produce duplicate flags – the existing logic appends ; secure when httpsonly is true; after making Secure the default, callers that also set httpsonly=True will get ; secure; secure in the header, which is harmless but unnecessary and could confuse debugging.
B7. Domain‑scoped cookies may be unintentionally omitted – the domain flag is appended after SameSite and Secure; if the order of flags changes or duplicate flags are added, some browsers may ignore the Domain attribute, leading to cookies not being sent for subdomains.
B8. Potential regression for API consumers that explicitly set samesite="lax" – existing applications that rely on the default lax behavior will need to update their middleware initialization; forgetting to do so could silently tighten site security and cause unexpected user‑session loss.
B9. Cookie max‑age handling remains unchanged – when maxage is None the Max-Age attribute is omitted, but the added Secure flag could affect caching proxies that treat secure cookies differently, potentially leading to stale sessions in edge caches.
B10. Documentation (docs/middleware.md) will become inaccurate – the current docs describe the default behavior; failing to update them will mislead developers and could cause deployment‑time surprises.
B11. Static type checkers may flag the new defaults – the samesite parameter type is Literal["lax", "strict", "none"]; changing the default value to "strict" is fine, but any code that uses SessionMiddleware(..., samesite=None) (e.g., to defer setting) will now raise a type error.
B12. Potential impact on third‑party libraries that wrap SessionMiddleware – libraries that subclass or monkey‑patch the middleware may assume the original defaults; altering them without a deprecation period could cause subtle incompatibilities in downstream packages.
C1. SessionMiddleware appends ; secure only when httpsonly is true, and TestClient defaults to baseurl="http://testserver". testsecuresession already shows an HTTP client returning the new session in the POST body and an empty session on the next GET, because the cookie jar drops Secure cookies on http://; making that the default breaks testsession, testsessionpersistsmutations, testsetcookieonlyonmodification, testvarycookieonaccess, and the docs/config.md app that builds SessionMiddleware with only secretkey.
C2. The flag is fixed in init (securityflags += "; secure") and the send path never reads scope["scheme"]. A write served over plain HTTP, including uvicorn's default and any request that reaches the middleware before an optional HTTPSRedirectMiddleware, still emits Set-Cookie with Secure, which browsers discard while the endpoint returns 200 and the in-request session.
C3. Deriving Secure from scope["scheme"] == "https" instead of httpsonly misses the proxy layout this repo documents: TLS usually stops in front of the app, and scheme stays http until Uvicorn's optional ProxyHeadersMiddleware applies X-Forwarded-Proto. Those deployments would keep issuing a non-Secure session cookie.
C4. samesite defaults to "lax", which is still sent on a cross-site top-level GET. SameSite=Strict is not, so a login, OAuth/OIDC state, or next URL stored in request.session is missing when the browser returns from an identity provider, a payment page, or an emailed link. AuthenticationMiddleware does not fill that in; it only inspects Authorization.
C5. docs/middleware.md says partitioned=True needs httpsonly=True and, for a cross-site embed, samesite="none". Browsers reject Partitioned without Secure (docs/responses.md) and reject it unless SameSite=None, so a default of Strict plus Secure makes partitioned=True alone a cookie that is dropped both on write and on clear, since both headers are built from the same securityflags string. testpartitionedsession only stays green because it passes samesite="none" and baseurl="https://testserver" itself.
C6. Logout writes session=null; expires=Thu, 01 Jan 1970 00:00:00 GMT plus those same flags, and does not go through Response.deletecookie (Max-Age=0, and defaults secure=False, samesite="lax"). A Secure/SameSite=Strict expiry does not remove the non-Secure SameSite=Lax cookie already stored, and cookieparser keeps whichever session= value appears last, so a stale valid signature still loads. Reads do not reissue the cookie either: testsetcookieonlyonmodification asserts Set-Cookie is omitted unless session.modified, so existing cookies keep the old attributes for the default 14-day maxage.
C7. The middleware loads scope["session"] for websocket connections, but sendwrapper only rewrites http.response.start, so a socket can never update the cookie. A Secure cookie is not sent on a ws:// handshake; TestClient with the default http://testserver base opens ws://, and HTTPSRedirectMiddleware rewrites ws to wss only when it is installed outside.
C8. The attributes are one concatenated string (httponly; samesite= plus optional ; secure, ; domain=, and ; partitioned), and unlike Response.setcookie there is no runtime check of samesite. Hardcoding samesite=strict; secure and still appending the constructor value emits two SameSite attributes, so an explicit samesite="none" can lose. Rebuilding the header with Response.setcookie raises ValueError for partitioned=True on Python before 3.14 (this middleware writes the token raw, and testpartitionedsession does not skip versions) and SimpleCookie can quote the TimestampSigner value (= from b64encode, . separators) so unsign fails.
C9. domain is appended to that same string (testdomaincookie expects domain=.example.com). With Secure set, only HTTPS hosts in that parent domain store or clear the shared cookie; an HTTP host in the Domain keeps the old one. Callers and tests that pass httpsonly=False or samesite="lax"/"none" rely on those parameters overriding the default; docs/middleware.md still documents the defaults as lax and httpsonly=False, with httpsonly=True only as a production choice.
