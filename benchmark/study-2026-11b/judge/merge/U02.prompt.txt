Three reviewers independently listed ways a software change could go wrong.

Change request: Let authors change an article's title, and its URL slug with it, without breaking links that were already shared.

Items (the letter is the reviewer):
A1. If historical slug resolution is only added to ArticleRetrieve (GET /api/articles/:slug), nested sub-resource endpoints like ArticleCommentCreate, ArticleCommentList, and ArticleFavorite will still look up articles by the URL parameter using FindOneArticle and return 404 for shared links.
A2. In ArticleDelete, authorization checks the fetched model but the subsequent deletion executes DeleteArticleModel(&ArticleModel{Slug: slug}) using the raw path parameter; if invoked with a historical slug, the query matches zero rows and returns 204 No Content without deleting the article.
A3. makeUniqueSlug in articles/models.go only checks the slug column of ArticleModel; without checking historical slugs, a newly created or retitled article could claim an old slug, causing database constraint collisions or hijacking existing shared links.
A4. If preserving shared links is implemented using HTTP redirects (such as 301 or 302) instead of internal alias resolution, clients sending authenticated requests to sub-resource endpoints (e.g., POST /api/articles/:slug/comments) will drop Authorization headers or downgrade POST to GET, dropping the request body.
A5. In ArticleUpdate (articles/routers.go), updating the article model occurs without an enclosing database transaction; if saving the historical slug alias fails after updating ArticleModel.Slug, the slug is changed without preserving the alias, permanently breaking existing links.
A6. Reverting an article's title to a previous title (e.g., A -> B -> A) can trigger unique constraint collisions against the article's own history records, cause an infinite redirect loop, or force makeUniqueSlug to append an unnecessary suffix instead of reclaiming the original slug.
A7. Because ArticleModel relies on GORM soft deletes and makeUniqueSlug uses db.Unscoped(), failing to soft-delete or scope historical slug records will leave old links resolving to deleted articles or permanently block slug reuse.
A8. The project uses declarative db.AutoMigrate calls rather than migration files, and calls them explicitly in hello.go as well as multiple times in articles/unittest.go; adding a new history model without updating every test setup site will cause migrations and tests to fail.
A9. Without restricting who can claim historical slugs, another author could update an article to a vacated slug belonging to someone else, effectively hijacking traffic and inbound links from the original author.
A10. The retry logic in ArticleUpdate specifically handles gorm.ErrDuplicatedKey on articleModel.Update, but it does not account for collision handling or race conditions when inserting into a separate slug history table under concurrent requests.
B1. Broken inbound links – After a slug change the old URL (/api/articles/:old‑slug) will no longer resolve, resulting in 404 errors for any previously shared links unless a redirect or slug‑history table is added.
B2. Missing redirect handling – The current code does not create a permanent redirect (301) from the old slug to the new one, so browsers, search engines, and social platforms will not automatically update cached URLs.
B3. Race conditions on slug uniqueness – makeUniqueSlug is retried only a few times; concurrent updates to different articles with the same title could still cause a duplicated‑key error that bubbles up as a 422 response.
B4. In‑place slug update without transaction – The update of the article row and the subsequent ReplaceTags call are performed in separate DB calls; a failure after the slug is saved (e.g., tag replacement error) leaves the article in an inconsistent state.
B5. Cache‑stale references – Any in‑memory caches (e.g., article lists, feed pagination) that index by slug will retain the old slug, causing duplicate entries or missing articles until the cache is explicitly refreshed.
B6. Foreign‑key lookups that rely on slug – Although comments and favorites use the article ID, some helper queries (e.g., favorited‑by‑user) may still filter by slug; after the change those queries will miss the article.
B7. SEO impact without canonical handling – Changing the slug without updating the canonical link or providing a rel="alternate" header can dilute search‑engine ranking for the original URL.
B8. Client‑side URL generation – Front‑end code that builds article URLs from a cached title may generate mismatched URLs if the title is updated but the client has not refreshed its state.
B9. Potential loss of slug‑based uniqueness constraints – If the new title yields a slug identical to another article’s existing slug, the unique index will reject the update, but the error message (database error) may be confusing to the user.
B10. Absence of audit trail – Changing the slug silently overwrites the previous identifier; without logging or an audit table it is impossible to trace which URL was originally used.
B11. Incorrect slug regeneration logic – The code checks if base := makeSlug(title.(string)); base != articleModel.Slug which compares the new base slug to the current slug, not the old one; if the title changes but results in the same base slug (e.g., punctuation differences) the slug will not be updated, leading to inconsistent title/slug pairs.
B12. Missing validation for title‑to‑slug mapping – No constraints ensure the generated slug conforms to URL‑safe characters; a malicious title could produce an invalid or unsafe slug, breaking routing or opening injection vectors.
C1. All eight slug routes (GET/PUT/DELETE /:slug, favorite, comments) resolve the article with FindOneArticle(&ArticleModel{Slug: slug}) on the live uniqueIndex column only, so an alias wired solely into ArticleRetrieve still 404s comments, favorites, and the editor’s PUT/DELETE on a URL that was already shared.
C2. ArticleDelete looks the row up, then calls DeleteArticleModel(&ArticleModel{Slug: slug}) with the path parameter; after a retitle the live row’s Slug is the new value, so a delete (or any other later write) that still filters on the old slug updates zero rows and leaves the article in place.
C3. makeUniqueSlug counts only articlemodels.slug (including soft-deleted rows via Unscoped()), while duplicate titles are allowed; if a vacated slug is not reserved in the same uniqueness domain as live slugs, a later ArticleCreate/ArticleUpdate reclaims it and the original shared URL serves a different article.
C4. makeUniqueSlug does not exclude the article being saved, and ArticleUpdate regenerates whenever slug.Make(title) differs from the current Slug; a suffixed row such as foo-2 that receives its own title again (the editor PUT includes title) is counted as a collision and rotates to foo-3, churning permalinks on no-op saves.
C5. hello.go already sets RedirectTrailingSlash = false because Gin redirects drop POST/PUT bodies, and RealWorld clients plus /#/article/:slug expect 200 with {"article": ...} and a slug field; implementing “keep old links” as 301/302 on /api/articles/:slug breaks those writes and the spec suite in scripts/run-spec-tests.sh.
C6. A single previousslug column cannot cover a rename chain: the sequential tests already go test-article → updated-title, and a third title would drop the originally shared slug unless every historical slug is stored.
C7. Schema setup is copy-pasted in Migrate() (hello.go), TestMain, and resetDBWithMock; a new alias table or unique index omitted from any of the three means production SQLite or the table-driven router tests run without the mapping that is supposed to preserve links.
C8. The ErrDuplicatedKey retry in ArticleUpdate assumes the conflict is the article’s own Slug; a unique-index error while inserting an alias is handled as another slug collision and rewrites finalSlug again, so the JSON response’s slug no longer matches what was persisted for redirects.
C9. DeleteArticleModel is a GORM soft delete and FindOneArticle hides DeletedAt rows; alias lookup that loads by id without that scope resurrects a deleted article, while GET /api/articles/updated-title after delete is required to stay 404.
C10. Static GET /api/articles/feed is registered beside GET /:slug, and gosimple/slug will emit feed for a title like “Feed”; retitling into that slug makes the new canonical GET serve the auth feed instead of the article.
C11. title only has min=4, so values that slug.Make turns into "" still pass ArticleUpdateValidator; FindOneArticle with a zero Slug ignores the condition in GORM struct-Where and can return an arbitrary first row instead of a stable permalink.
