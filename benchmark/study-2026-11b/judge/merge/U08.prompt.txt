Three reviewers independently listed ways a software change could go wrong.

Change request: Change the default signing digest from SHA-1 to SHA-256.

Items (the letter is the reviewer):
A1. Existing tokens signed with default settings by earlier versions of itsdangerous will immediately fail validation with BadSignature upon upgrading, causing widespread session invalidation in downstream consumers like Flask. This exact issue caused the yanked 1.0.0 release when the default was previously switched to SHA-512 without a transition mechanism.
A2. If SHA-1 is added to Serializer.defaultfallbacksigners by eagerly referencing hashlib.sha1 rather than maintaining lazy loading (analogous to lazysha1), imports will crash on FIPS-compliant systems where SHA-1 is disabled.
A3. Updating Signer.defaultdigestmethod without also updating HMACAlgorithm.defaultdigestmethod will desynchronize the defaults, causing Signer(algorithm=HMACAlgorithm()) to silently default to SHA-1 while Signer() defaults to SHA-256.
A4. While Serializer supports fallbacksigners to verify older tokens, Signer itself has no fallback mechanism, leaving direct Signer callers without an out-of-the-box way to validate legacy SHA-1 signatures.
A5. In Signer.derivekey(), the "concat", "django-concat", and "hmac" key derivation schemes use self.digestmethod, meaning switching to SHA-256 alters the derived key value and expands its length from 20 to 32 bytes, breaking any interoperability expecting SHA-1 key derivation.
A6. The test suite contains explicit assertions in testdigests and testiterunsigners (tests/testitsdangerous/testserializer.py) expecting default outputs to match SHA-1 signatures ("[42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM") and the initial unsigner to use lazysha1.
A7. Hardcoded test vectors like testmalformedfuturetimestamp in tests/testitsdangerous/testtimed.py rely on precomputed SHA-1 signatures and will fail TimestampSigner.unsign() signature verification before the malformed timestamp logic is exercised.
A8. Switching to SHA-256 increases the Base64-encoded signature length from 27 to 43 characters, adding 16 bytes per token and potentially overflowing fixed-size database columns, URL length constraints, or HTTP cookie size limits.
A9. Documentation examples and doctests in docs/concepts.rst, docs/serializer.rst, and docs/signer.rst contain hardcoded SHA-1 signature outputs and explanations stating SHA-1 is the default, which will become inaccurate and break doctest verification.
A10. Removing or renaming lazysha1 in src/itsdangerous/signer.py rather than maintaining it for backward compatibility will raise ImportError in tests and external projects relying on it for FIPS workarounds.
B1. Existing signed values generated with SHA‑1 will become invalid, causing immediate breakage of any data or cookies relying on the previous default.
B2. The defaultdigestmethod attribute is defined twice (in HMACAlgorithm and Signer); changing only one may lead to inconsistent behavior between custom algorithm instances and the default signer.
B3. Tests that assert specific signatures or lengths (e.g., in tests/testsigner.py) will fail because the expected SHA‑1‑based signatures will no longer match the new SHA‑256 output.
B4. Documentation strings and examples refer to hashlib.sha1 as the default; they will become misleading unless updated, increasing the risk of future misuse.
B5. The lazy import helper lazysha1 is hard‑coded; replacing the default without providing a comparable lazysha256 could re‑introduce import‑time failures on platforms lacking SHA‑256 (unlikely but a regression risk).
B6. Users explicitly passing digestmethod=None rely on the class‑level default; changing it silently may break backward‑compatible APIs that expected SHA‑1, especially in libraries that pin the default for interoperability.
B7. The derivekey method builds the HMAC key using self.digestmethod(self.salt + …).digest(). Switching to SHA‑256 changes the key length, which could affect downstream callers that assume a 20‑byte SHA‑1 digest (e.g., custom key‑derivation implementations).
B8. The Signer constructor allows overriding digestmethod; if the default is changed but older code still passes digestmethod=hashlib.sha1, inconsistent digests may appear within the same application, leading to hard‑to‑debug signature mismatches.
C1. Tokens already signed with the implicit SHA-1 default will fail to verify. Release 1.0.0 was yanked for the same kind of default change, Serializer.defaultfallbacksigners has been empty since 2.0, and Signer.unsign / TimestampSigner.unsign never try fallbacks, so only Serializer.loads and TimedSerializer.loads can still accept old tokens.
C2. digestmethod is also the key-derivation hash. The default django-concat path, plus concat and hmac, hashes salt + b"signer" + secretkey in derivekey, so the derived key changes from 20 bytes to 32 bytes along with the MAC. keyderivation="none" is the only mode that leaves the secret unhashed.
C3. Signer.defaultdigestmethod and HMACAlgorithm.defaultdigestmethod are separate copies of lazysha1. Signer passes its digest into HMACAlgorithm only when algorithm is omitted, so algorithm=HMACAlgorithm() (see testalgorithm) can MAC a SHA-256-derived key with SHA-1 if only one attribute is updated.
C4. A custom SigningAlgorithm still receives its key from derivekey(). ReverseAlgorithm and any other algorithm that ignores digestmethod still emits different signatures once the default digest changes.
C5. In iterunsigners, a dict fallback replaces signerkwargs instead of merging. A default fallback of {"digestmethod": sha1} drops a caller's sep, keyderivation, or algorithm, and a bare Signer entry uses the new SHA-256 default, so neither form actually verifies those old tokens.
C6. Restoring SHA-1 on defaultfallbacksigners makes every serializer that omitted fallbacksigners accept SHA-1 again, including callers who already passed signerkwargs={"digestmethod": hashlib.sha256} and relied on the empty list from 2.0 (issue 155).
C7. lazysha1 exists so FIPS builds that lack SHA-1 do not touch hashlib.sha1 at import (2.2.0, issue 375). A SHA-1 fallback that calls hashlib.sha1() during unsign raises an exception loads does not catch (BadSignature only; TimedSerializer also aborts the loop on SignatureExpired), so a missing SHA-1 becomes a crash instead of a rejected token.
C8. Both call sites need a constructor: derivekey calls digestmethod(data).digest(), and HMACAlgorithm.getsignature passes that same object as hmac.new(..., digestmod=). It must stay a staticmethod. A plain function on the class is bound to the instance, and a hash name string satisfies only one of the two call sites.
C9. The signature grows from a 20-byte SHA-1 digest (27 url-safe base64 characters, padding stripped) to 32 bytes (43 characters), the cookie and URL growth docs/concepts.rst already warns about. That also invalidates the pinned strings in README.md (6YP6T0BaO67XP--9UzTrmurXSmg), docs/signer.rst (wh6tMHxLgJqB6oY1uT73iMlyrOA), and testdigests ([42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM), and testiterunsigners asserts the first signer's digest is lazysha1. Sphinx is not configured with doctest, so the docs can go stale without a CI failure.
