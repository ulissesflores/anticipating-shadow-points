Three reviewers independently listed ways a software change could go wrong.

Change request: Require new users to verify their email address before they can log in.

Items (the letter is the reviewer):
A1. In app/routes/join.tsx, the action currently calls createUserSession immediately after createUser, which would automatically log new users in upon registration and bypass email verification unless sign-up is explicitly decoupled from session creation.
A2. Adding a non-nullable emailVerified boolean defaulting to false in prisma/schema.prisma would cause npx prisma migrate deploy to treat all existing users as unverified, locking them out of production contrary to the requirement that this only applies to new users.
A3. In server.ts, the multi-region Fly.io replay middleware only replays non-GET requests to PRIMARYREGION; if email verification links are handled via a GET request in a route loader that updates PostgreSQL, users routed to read-only replica regions will encounter database write errors.
A4. The smoke test in cypress/e2e/smoke.cy.ts submits the registration form in join.tsx and immediately asserts access to authenticated routes (/notes), which will break once registration stops creating an active session.
A5. In cypress/support/create-user.ts, test user creation directly calls createUser and createUserSession for cy.login(); if verifyLogin or session checks enforce verification without updating this script, authenticated Cypress tests will fail across the suite.
A6. The database seed in prisma/seed.ts provisions rachel@remix.run via prisma.user.create without verification metadata, which would prevent developers from logging in with the default test credentials after running npm run setup.
A7. If a new Prisma model is added to store verification tokens without onDelete: Cascade referencing User, calling prisma.user.delete in cypress/support/delete-user.ts and app/models/user.server.ts will throw foreign key constraint errors during cleanup.
A8. Because app/routes/join.tsx rejects existing emails with "A user already exists with this email", creating an unverified user record on signup allows abandoned or malicious unverified accounts to permanently squat on email addresses without an account-reclaiming or token-resend mechanism.
A9. In app/routes/login.tsx, authentication failures currently return a generic "Invalid email or password" error, so returning null from verifyLogin for unverified users will mislead them into thinking their credentials are wrong instead of directing them to verify their email.
A10. If verification emails are dispatched synchronously within the join.tsx action without transactional error handling, external email API failures or timeouts will leave orphaned unverified users in PostgreSQL who cannot log in or re-register.
A11. The application has no email service dependencies in package.json, no email environment variables in .env.example, and no mock handlers in mocks/index.js, which will cause local development and offline CI runs (npm run test:e2e:run with MSW) to fail unless mail transport is properly mocked.
B1. Missing isVerified flag in the User model – without adding a boolean column and updating Prisma migrations, the code cannot reliably determine whether a user’s email is verified, leading to runtime errors when the flag is accessed.
B2. Login flow still calls verifyLogin unchanged – the existing verifyLogin function returns a user object regardless of verification status, so users could still obtain a session cookie unless every login endpoint is updated to check the new flag.
B3. Email‑verification token storage & expiration – if a token is stored in‑memory or in an insecure table without expiry, stolen tokens could be reused to validate any account, bypassing the intended verification step.
B4. Race condition between account creation and verification – a user could submit a login request before the verification email is processed, and the server might create a session for an unverified account if the verification check is not atomic.
B5. Database migration impact on existing data – adding a non‑nullable isVerified column without a default or back‑filling existing rows will cause the Prisma client to fail on startup, breaking all endpoints that query User.
B6. Email enumeration vulnerability – the sign‑up API may now return different error messages for “email already exists” vs. “verification pending”, allowing attackers to probe which addresses are registered.
B7. Broken test suites – the Cypress utility cy.login() assumes that a newly created user can log in immediately; after introducing verification, all existing end‑to‑end and unit tests that create a user and log in will fail unless they are updated to handle the verification step.
B8. Forgot‑password / password‑reset flow – password reset emails typically rely on the user’s verified email address; if verification status isn’t checked, reset links could be sent to unverified accounts, exposing a vector for account takeover.
C1. app/routes/join.tsx calls createUserSession right after createUser, so signup already sets the session cookie and never reaches /login; a check only inside verifyLogin still leaves every new account authenticated.
C2. requireUserId in app/session.server.ts only reads the userId cookie, and notes.tsx, notes.new.tsx, and notes.$noteId.tsx all authorize through that helper, so an unverified session can still list, create, and delete notes.
C3. User in prisma/schema.prisma has no verification field, and prisma/seed.ts plus the README account rachel@remix.run are created without one; adding emailVerified with a false default will fail or lock those rows on Fly’s releasecommand (npx prisma migrate deploy).
C4. User.email is unique and join.tsx returns “A user already exists with this email” for any second signup, so an unverified (or attacker-held) row permanently occupies that address with no expiry or reclaim path.
C5. There is no mailer library, .env.example only defines DATABASEURL and SESSIONSECRET, and README Fly secrets only set SESSIONSECRET, so production and npm run start:mocks (MSW with onUnhandledRequest: "bypass") have no configured, mocked, or secret-backed way to send a verification message.
C6. cypress/e2e/smoke.cy.ts expects Create Account to land on Notes/Logout immediately, and cypress/support/create-user.ts mints a cookie via createUser + createUserSession, so CI Cypress will fail or skip the new gate.
C7. server.ts fly-replays only non-GET/HEAD/OPTIONS to PRIMARYREGION, and db.server.ts points other Fly regions at Postgres port 5433; a GET /verify?token= loader that writes emailVerified will error on replica machines.
C8. login.tsx and join.tsx loaders redirect any existing userId cookie to /, and index.tsx shows “View Notes for {email}” from getUser/useOptionalUser with no verified check, so an unverified session is stuck on the home page with a notes link that either bounces or still works.
C9. verifyLogin already returns null for both unknown emails and bad passwords with the single message “Invalid email or password”; treating unverified the same way hides the “check your inbox” step, while a distinct error on /login enumerates which addresses are registered.
C10. morgan("tiny") in server.ts logs the full request URL, so a verification token in the query string is written to Fly access logs on every click of the email link.
