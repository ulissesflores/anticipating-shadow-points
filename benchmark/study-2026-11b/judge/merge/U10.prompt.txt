Three reviewers independently listed ways a software change could go wrong.

Change request: Make every to-do list and item belong to a tenant, so that each company only sees its own data.

Items (the letter is the reviewer):
A1. CreateTodoListCommandValidator and UpdateTodoListCommandValidator enforce unique titles using global queries across context.TodoLists. Without scoping these validation queries to the current tenant, different companies will be blocked from creating lists with common names (such as "Tasks"), and users could probe other companies' list titles through validation errors.
A2. CreateTodoItemCommandHandler assigns request.ListId and UpdateTodoItemDetailCommandHandler updates entity.ListId without validating that the target TodoList belongs to the caller's tenant. Without explicit tenant checks on list associations, users could inject or move to-do items into another company's lists by supplying foreign list IDs.
A3. Item command handlers (UpdateTodoItemCommandHandler, DeleteTodoItemCommandHandler, and UpdateTodoItemDetailCommandHandler) look up entities directly by primary key using context.TodoItems.FindAsync([request.Id]). If TodoItem lacks a tenant identifier or relies solely on parent-list navigation for scoping without global query filters, a user could manipulate or delete any company's items simply by guessing integer IDs.
A4. If TenantId is denormalized and added to both TodoList and TodoItem without database-level composite foreign keys, an item's tenant could diverge from its parent list during updates or moving items. This would cause data integrity violations where an item appears in one tenant's list while belonging to another tenant.
A5. ApplicationDbContextInitialiser.TrySeedAsync inserts default TodoList and TodoItem records on application startup without any tenant association. If a required, non-nullable tenant property or foreign key is introduced, application startup in Program.cs will crash during initialization or create orphaned entities that are invisible to all tenants.
A6. IUser and CurrentUser only expose Id and Roles from ClaimsPrincipal, and Users.MapIdentityApi<ApplicationUser>() uses standard ASP.NET Core Identity endpoints that do not capture, store, or issue tenant claims. Without establishing a clear tenant resolution mechanism (such as subdomain, tenant header, or JWT claim), handlers cannot securely identify which company the authenticated user belongs to.
A7. ApplicationDbContext inherits IdentityDbContext<ApplicationUser>, which enforces global unique constraints on NormalizedEmail and NormalizedUserName. In a multi-tenant environment where multiple companies might share the database, users with identical email addresses across distinct companies will collide and fail registration.
A8. If tenant assignment is handled implicitly within AuditableEntityInterceptor alongside CreatedBy, modifying entities outside an active HTTP request context (such as background jobs, database seeders, or integration tests) will fail or overwrite tenant values with null.
A9. WebApiFactory and TestApp in the functional test suite mock IUser with only a user ID and roles, and helper methods like TestApp.AddAsync persist entities directly to ApplicationDbContext without tenant context. Introducing mandatory tenant constraints or query filters will silently hide data from assertions or break existing functional tests across the suite.
A10. If the tenant identifier is introduced into API route templates or command contracts rather than resolved transparently on the server, existing OpenAPI specifications and generated NSwag clients in both ClientApp (Angular) and ClientApp-React will break and require coordinated client-side refactoring.
B1. Adding a TenantId property to TodoList and TodoItem entities will require updating EF Core configurations and migrations; forgetting to create the migration or apply it will cause runtime database errors.
B2. Existing queries (e.g., in GetTodos.cs) do not filter by tenant, so without explicit tenant scoping every company could retrieve all other tenants’ data.
B3. The AuthorizationBehaviour and AuthorizeAttribute currently enforce role‑based checks but not tenant isolation; omitting tenant validation could allow privileged users to bypass tenant boundaries.
B4. Seed data in ApplicationDbContextInitialiser creates default TodoList/TodoItem records without a tenant reference, leading to null TenantId values and potential constraint violations after the schema change.
B5. Unit and functional tests (e.g., CreateTodoListTests.cs, GetTodosTests.cs) assume a single‑tenant context; they will fail or pass incorrectly if tenant filtering is not mocked or injected.
B6. The CurrentUser service in src/Web/Services/CurrentUser.cs only provides user identity; extending it to expose the tenant ID may require additional DI registration and could break existing consumers.
B7. Caching layers (if any) or in‑memory collections that store TodoItem objects may not consider tenant segregation, causing stale cross‑tenant data to be returned after the change.
B8. Soft‑delete or audit interceptors (AuditableEntityInterceptor.cs) currently log only user ID; they must be enhanced to capture tenant context, otherwise audit trails become ambiguous.
B9. Multi‑tenant support may introduce N+1 query performance issues when loading related TodoItems for each TodoList; failing to add appropriate indexes on TenantId could degrade query performance dramatically.
C1. ApplicationUser, IUser, and CurrentUser only expose the identity user id and role claims, and Users calls MapIdentityApi<ApplicationUser>(), so a newly registered account has no company. A TenantId accepted from the command body can be set to another company, and storing the caller's user id instead means two people in the same company never see the same lists.
C2. UpdateTodoList, UpdateTodoItem, DeleteTodoItem, and UpdateTodoItemDetail load the row with FindAsync on the shared integer id. EF Core ignores a global query filter inside Find/FindAsync, so a filter in OnModelCreating still lets another company's user update or delete that row. DeleteTodoList uses LINQ Where, so the same filter would hide the list there and the handlers would disagree.
C3. CreateTodoItem writes ListId from the command without loading the list, and UpdateTodoItemDetail sets entity.ListId = request.ListId with no ownership check. The Angular and React detail editors already move an item by posting a new listId, so an item can be attached to or moved onto another company's list, and a TenantId stored on both entities can diverge. TodoItemConfiguration does not set delete behavior, so the required ListId foreign key cascades item deletes with the list and never checks the item's tenant.
C4. CreateTodoListCommandValidator and UpdateTodoListCommandValidator reject a title when any TodoList already has it, and the seeder inserts "Tasks". Two companies then cannot use the same title, and the "'Title' must be unique" error reveals that some other company already has it. A unique index on Title alone collides across companies, and scoping only the LINQ check still lets two concurrent creates in one company both pass unless the index is (TenantId, Title).
C5. The only MediatR [Authorize] is on GetTodosQuery. Create, update, and delete commands skip AuthorizationBehaviour, and the endpoint groups only call RequireAuthorization(), which checks that some user is signed in. GetTodos then runs ProjectTo<TodoListDto> over every TodoLists row, so filtering that query alone still leaves every mutation keyed by the global BaseEntity.Id, which the create endpoints return in the Location URL.
C6. InitialiseDatabaseAsync runs only in Development and calls EnsureDeletedAsync then EnsureCreatedAsync. There is no migration, PendingModelChangesWarning is ignored, and Aspire picks one shared SQLite, SQL Server, or PostgreSQL database. A required TenantId will not alter an existing non-development database, and the seeded "Tasks" list and its four items have no company. A nullable column puts that seed, plus every self-registered user with a null tenant, in one shared bucket. Seed runs with no HttpContext, and AuditableEntityInterceptor already stores a null CreatedBy in that case, so the same hook would store a null tenant.
C7. WebApiFactory replaces IUser with a mock of Id and Roles only, and TestApp.AddAsync, FindAsync, and CountAsync use ApplicationDbContext directly. GetTodosTests.ShouldReturnAllListsAndItems expects the signed-in user to see every inserted list. Those tests stay green when the mock's tenant is null and every row shares that null, and TestApp.FindAsync uses DbContext.FindAsync, which also skips query filters.
C8. The only role is the global Roles.Administrator, given to administrator@localhost by the seeder and checked in AuthorizationBehaviour with no company. Bypassing the tenant filter for that role shows every company's lists to that account. Applying the filter leaves the seeded admin in no tenant, so the seeded "Tasks" list is invisible to every user who does have a company.
C9. ClientApp/src/app/todo/todo.component.ts, ClientApp-React/src/components/Todo.jsx, and their NSwag clients load one catalog from getTodoLists() and address every row by numeric id. The OpenAPI summary for that route still says it retrieves all todo lists. Putting the tenant id on the command body leaves it under the caller's control, and leaving the clients unchanged makes them render and move any row an unfiltered query still returns.
