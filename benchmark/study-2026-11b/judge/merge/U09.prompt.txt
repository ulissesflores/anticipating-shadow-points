Three reviewers independently listed ways a software change could go wrong.

Change request: Store passwords with a stronger hashing scheme without forcing existing users to reset their passwords.

Items (the letter is the reviewer):
A1. In PasswordHasher.cs, verification currently branches between 64-byte legacy HMAC-SHA512 hashes and ASP.NET Core Identity PBKDF2 hashes. If the new verifier replaces existing logic without supporting both historical formats or lacks an algorithm discriminator, users with legacy HMAC hashes or intermediate PBKDF2 hashes will fail authentication and be locked out.
A2. In Login.cs, password migration relies on passwordHasher.Verify returning PasswordVerificationResult.SuccessRehashNeeded to trigger updating person.Hash and saving changes to the database. If the new implementation returns PasswordVerificationResult.Success for valid older hashes, users will authenticate successfully but their stored hashes will never be upgraded to the stronger scheme.
A3. PasswordHasher.cs currently converts password hashes to and from Base64 strings using Convert.FromBase64String and Convert.ToBase64String. If the stronger scheme uses standard text formats like PHC or modular crypt strings containing non-Base64 characters (such as Argon2 or bcrypt formats with $), runtime FormatException crashes will occur during verification instead of returning PasswordVerificationResult.Failed.
A4. The Person.Salt column is configured as a non-nullable BLOB in SQLite and varbinary(max) in SQL Server, populated with an empty byte array [] when using self-salting schemes. If the new implementation attempts to set Salt to null when rehashing or creating users, SaveChangesAsync will throw database constraint violations.
A5. If storing the new hash format requires modifying Person (such as changing column data types, nullability, or adding an algorithm discriminator column), migrations must be created for both SqliteConduitContext and SqlServerConduitContext. Omitting migrations for either provider will break MigrationTests because HasPendingModelChanges() is asserted against both database contexts.
A6. While Login.cs handles opportunistic rehashing, Edit.cs also updates passwords using passwordHasher.Hash(message.User.Password, []) when a user updates their profile. If the hashing scheme upgrade is not consistently applied across both Create.cs and Edit.cs, or if existing salt clearing is mishandled during profile updates, users could store mismatched hash formats that fail subsequent logins.
A7. Because opportunistic rehashing converts POST /api/users/login from a read into a database write via context.SaveChangesAsync, concurrent login requests for the same unmigrated user could cause race conditions. Under SQLite, where transactions run at IsolationLevel.Serializable via DBContextTransactionPipelineBehavior, simultaneous hash calculations and writes risk database locking failures.
A8. In Login.cs, requests for non-existent users immediately abort with a 401 before any cryptographic work is performed. With a computationally heavier hashing scheme, the significant latency discrepancy between non-existent emails (~1ms) and valid accounts (~hundreds of ms) enables user enumeration and exposes the unauthenticated login endpoint to denial-of-service attacks.
A9. Although IPasswordHasher.Hash returns a Task<byte[]>, PasswordHasher.cs executes hashing synchronously via Task.FromResult, and Verify is entirely synchronous. Introducing a compute- or memory-heavy algorithm (such as Argon2id or bcrypt) synchronously on Kestrel request threads could exhaust the .NET ThreadPool under concurrent login or registration traffic.
A10. The test suite in tests/Conduit.IntegrationTests contains numerous integration tests (such as CreateTests, LoginTests, and ApiTests) that repeatedly create and authenticate users. If the work factor for the stronger hashing scheme is hardcoded high without an environment-specific or configurable work factor for tests, build and test execution via dotnet run --project build/build.csproj -- test will suffer severe performance degradation or time out in CI.
A11. PasswordHashingTests.cs contains explicit integration tests that construct legacy HMAC-SHA512 hashes using the hardcoded "realworld" key, verify lazy rehashing on login, and assert hash and salt states. Altering the IPasswordHasher contract or changing how legacy HMAC hashes and upgraded hashes are verified will break these tests unless the migration path preserves backward-compatible verification.
B1. Login failures for existing users – the new hasher will produce a different hash format, but PasswordHasher.Verify still expects the legacy HMAC‑SHA512 or the current Identity format; without a migration path, verification will always return Failed.
B2. Database column size mismatch – Person.Hash and Person.Salt are stored as byte[]; a stronger algorithm (e.g., Argon2id) can generate longer byte arrays, potentially exceeding the current column length and causing truncation or runtime exceptions.
B3. Empty‑salt handling – the current Create command stores Salt = [] and the hasher ignores the supplied salt; a scheme that requires an external salt will break because the empty array is persisted and later used for verification.
B4. Re‑hash‑needed flag not acted on – PasswordVerificationResult.SuccessRehashNeeded is returned for legacy hashes, but no code updates the stored hash after a successful login, leaving users stuck with the weaker hash indefinitely.
B5. DI registration incompatibility – replacing PasswordHasher with a custom implementation may break the existing service registration (e.g., lifetime, interface expectations), causing runtime resolution errors for IPasswordHasher.
B6. Unit‑test breakage – tests such as PasswordHashingTests.cs assert specific hash lengths or verification outcomes; a new algorithm will invalidate those expectations, leading to failing CI pipelines.
B7. Performance regressions – increasing the iteration count or switching to a memory‑hard algorithm may introduce noticeable latency in user registration and login, potentially triggering request timeouts in the API.
B8. Incorrect disposal of cryptographic resources – the current Dispose method is empty; a stronger hasher may allocate unmanaged memory that must be cleared, otherwise sensitive material could linger in memory.
B9. Legacy verification path becomes dead code – if the new scheme no longer supports the 64‑byte HMAC hashes, the conditional block in Verify becomes unreachable; removing it without thorough testing could expose hidden bugs for any remaining legacy accounts.
B10. Migration ordering issues – applying a schema migration that enlarges the hash column before migrating existing records could cause temporary data inconsistency, especially if the migration runs concurrently with live traffic.
B11. Incorrect handling of Hash return type – the current Hash method converts the Identity hash string back to a byte array; a new hasher that already returns raw bytes will cause Convert.FromBase64String to throw, breaking user creation.
B12. Missing backward‑compatibility flag – without a way to indicate which hashing algorithm was used per user, future code may misinterpret newer hashes as legacy, leading to incorrect verification results.
C1. PasswordHasher.Verify treats a 64-byte Hash plus a 16-byte Salt as HMAC-SHA512 under the UTF-8 key realworld, and every other length as an ASP.NET Identity payload. A new digest that is 64 bytes, or that leaves the existing 16-byte salt in place, is checked with that HMAC and then either rejects the real password or accepts a password that happens to match the old construction.
C2. Rows already exist in two forms: legacy HMAC (UTF-8(password) concatenated with the salt) and Identity PBKDF2-HMAC-SHA512 at 210,000 iterations, stored as the decoded v3 payload with Salt empty. Replacing the Identity hasher and special-casing only HMAC locks out every account that registered or already logged in under the current code, and no migration can rebuild those hashes because the plaintext is gone.
C3. Login rewrites Hash and clears Salt only when verification returns SuccessRehashNeeded. Identity already returns that whenever the embedded iteration count is below IterationCount, so a new hasher that always reports rehash needed rewrites the hash on every login, while one that returns Success for old rows never upgrades them. CreateTests expects a freshly stored hash to verify as Success. Rewriting on Failed, or clearing Salt before the new hash is saved, makes the only remaining verifier unusable.
C4. Hash stores Convert.FromBase64String of Identity's string, and Verify turns those bytes back with Convert.ToBase64String. Passing an Argon2 PHC string through FromBase64String throws FormatException, which ErrorHandlingMiddleware turns into HTTP 500. The transaction then rolls back, so every later login by a not-yet-upgraded user fails the same way. Storing the base64 text itself in the Hash blob double-encodes current Identity rows, and VerifyHashedPassword returns Failed.
C5. Login.Command is not IReadOnlyRequest, so DBContextTransactionPipelineBehavior opens the transaction before Verify: Serializable on SQLite and ReadCommitted on SQL Server. The KDF runs synchronously inside Task.FromResult and ignores CancellationToken. A heavier function holds that transaction for a failed password too, and for a second hash when an upgrade is written. On deploy, every first login is a write. SQLite lock failures become HTTP 500 even when the password was correct. Unknown emails return 401 before any hash, so the slower function widens the timing gap on POST /api/users/login.
C6. Login only rejects an empty password. Create and Edit also require length 8. Adding that minimum to login stops shorter existing passwords from reaching Verify, so those accounts can never take the upgrade path.
C7. Salt is a required BLOB / varbinary(max) on two independent migration chains, and startup applies migrations by default. Dropping or nulling it makes salt.Length throw, or pushes 64-byte HMAC rows into the Identity verifier, which rejects them. docs/database-migrations.md leaves these columns unchanged because Salt is what legacy verification uses. Databases created with EnsureCreated() are not adopted automatically, so a new required column is missing there and login throws.
C8. Hash ignores its salt argument, and HashPassword is invoked with the scoped PasswordHasher instance as the user, which Identity's hasher ignores. Keying the new digest with that salt argument breaks Create, the login upgrade, and Edit, which all pass an empty salt. Mixing the user argument into the hash binds it to a per-request object, so the next request fails verification. LoginTests saves a 16-byte Guid salt beside an Identity hash. Treating "salt length is 16" as legacy rejects that row and any upgrade that did not assign Salt = [].
C9. Dormant HMAC accounts stay recoverable from a database copy because the key is the literal UTF-8 bytes of realworld in source, until that user logs in successfully. A SQL backfill cannot rehash them. After this change, the process that is running today also cannot verify the new format. The readme already warns that a rollback rejects upgraded hashes, so a rolling deploy or a rollback returns 401 for anyone who has logged in once since the release.
