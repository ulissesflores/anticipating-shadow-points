Three reviewers independently listed ways a software change could go wrong.

Change request: Lock users out by username and IP address together instead of by IP address alone, as the new default.

Items (the letter is the reviewer):
A1. In axes/handlers/cache.py, AxesCacheHandler.resetattempts hashes AccessAttempt(username=username, ipaddress=ipaddress), but commands like axesresetip supply username=None. This produces an IP-only hash that fails to match the combined (username + ip) key in cache, leaving locked-out users unable to be unlocked via IP-based reset commands.
A2. In tests/base.py, AxesTestCase.login(isvalidusername=False) generates a random username on each attempt to test IP lockout. Under a combined default, attempts are split across unique usernames and never accumulate toward AXESFAILURELIMIT, causing self.lockout() and dozens of dependent tests across testlogin.py and testhandlers.py to fail.
A3. In axes/utils.py, resetrequest inspects combined lockout parameters and sets usernamerequired=True, reading the username strictly from request.GET.get("username"). This hardcodes the query parameter name and ignores AXESUSERNAMEFORMFIELD or custom user model fields, breaking reset workflows for applications using non-standard username fields or POST requests.
A4. Defaulting to [["username", "ipaddress"]] fundamentally changes the security model by allowing an attacker at a single IP address to spray passwords across unlimited distinct usernames without triggering an IP lockout. This removes the repository's default protection against horizontal credential stuffing and user enumeration attacks.
A5. In axes/handlers/database.py, userloginfailed contains a guard for lockoutparameters == ["username"] when username is None, but has no corresponding handling for combined parameters. Requests without a username (such as malformed payloads or views decorated with @axesdispatch) will record rows with username=None, which fail to lock out named accounts or aggregate properly with credentialed attempts.
A6. Because AccessAttempt.objects.filter and AxesCacheHandler key generation perform exact, case-sensitive matching, projects with case-insensitive authentication (e.g. email logins) will become vulnerable to lockout bypasses. Attackers from the same IP can evade the failure limit simply by alternating the letter casing of the submitted username unless AXESUSERNAMECALLABLE is explicitly configured.
A7. In axes/conf.py, deprecated flags like AXESONLYUSERFAILURES and AXESLOCKOUTBYUSERORIP are checked only if settings.AXESLOCKOUTPARAMETERS is None. Setting the new default directly on line 39 instead of in the fallback block will silently bypass and break backward compatibility for existing deployments relying on those legacy settings.
A8. In axes/admin.py, AccessAttemptAdmin.status and IsLockedOutFilter evaluate lockout thresholds on single AccessAttempt records rather than aggregating across records sharing the same (username, ipaddress). Because different user agents generate distinct rows under the model's uniquetogether constraint, the admin panel will report users as unlocked even when their aggregated attempts exceed the failure limit.
A9. In axes/models.py, AccessAttempt has single-column indexes on ipaddress and username, but lacks a composite index on (username, ipaddress). Shifting the default query in AxesDatabaseHandler.filteruserattempts to always filter by both fields simultaneously will cause database query degradation on large tables without an accompanying migration.
A10. In axes/apps.py and axes/helpers.py, changing the default alters startup log messages in AppConfig.initialize() and changes formatted client strings in getclientstr() when AXESVERBOSE=False. This will directly break existing tests such as testaxesconfiglogiponly and testnonverboseiponlyclientdetails, and may break downstream log-monitoring systems that parse Axes output.
B1. Database schema mismatch – axes/migrations/0007alteraccessattemptuniquetogether.py creates a unique constraint on (username, ipaddress, useragent). Switching the default to lock out by both username and IP will make the existing constraint too strict for cases where only one of the fields is set (e.g., anonymous login attempts with no username), causing IntegrityError on record insertion.
B2. Missing username handling – axes/handlers/database.py and axes/handlers/cache.py contain a guard that aborts record creation when lockoutparameters == ["username"] and username is None. After the change, the code will still hit this guard for attempts that lack a username, resulting in no lockout record being stored for IP‑only attacks.
B3. Cache key divergence – helpers.getclientparameters() builds filter kwargs based on settings.AXESLOCKOUTPARAMETERS. Changing the default to a combined [["username", "ipaddress"]] will generate a different cache‑key list (makecachekeylist) than the current IP‑only key, causing cache misses and allowing attackers to bypass lockout until the cache is repopulated.
B4. Management commands out of sync – The axesresetipusername command (and its help text) assumes a lockout by both parameters, but the other reset commands (axesresetip, axesresetusername) still operate on single fields. If the default changes without updating those commands, administrators may inadvertently reset only one dimension, leaving the other still locked out.
B5. Query‑filter logic breakage – helpers.getclientparameters() creates a list of dicts for each lockout parameter. When a combined parameter list is used, the resulting filterkwargs become a single dict with both fields, which some downstream code (e.g., AccessAttempt.objects.filter(filterkwargs)) may not expect, potentially raising FieldError or generating incorrect SQL.
B6. Existing tests will fail – The test suite (tests/test) contains fixtures that lock out by IP only (e.g., testlogin.py). Without adjusting the test data to include usernames, those tests will either raise exceptions or incorrectly assert lockout behavior, leading to widespread test failures.
B7. Deduplication migration may delete needed rows – 0007alteraccessattemptuniquetogether.py deduplicates attempts by grouping on (username, useragent, ipaddress). If many records have username=None, the new combined lockout will treat them as different lockouts, but the deduplication still removes duplicates, potentially deleting legitimate attempt records that should remain distinct for IP‑only tracking.
B8. Performance regression – Adding username to the lockout key expands the cardinality of the unique‑together index. In high‑traffic environments this can slow down lookups and insertions in the AccessAttempt table, especially when usernames are long or not indexed, increasing query time for every authentication attempt.
B9. Backward‑compatibility of settings – settings.AXESLOCKOUTPARAMETERS can be a list or callable. Existing projects may still configure it as ["ipaddress"]. Changing the default without a migration step will cause a silent mismatch where the code uses the old list while docs and defaults assume the new combined lockout, leading to inconsistent lockout behavior across deployments.
B10. Signal handling may double‑lock – The axes/signals.py module emits lockout signals based on the result of getlockoutparameters. When both username and IP are considered, a single failed attempt could trigger two separate lockout signals (one for each field) if the signal listeners are not updated, potentially causing duplicate log entries or race conditions in custom lockout callables.
B11. User‑agent edge case – The unique‑together constraint includes useragent. If a user logs in from the same IP with different browsers, the combined lockout will treat them as distinct, defeating the intended stricter lockout by username + IP. This nuance must be addressed in the migration or documentation to avoid unexpected security gaps.
B12. Admin UI confusion – The Django admin (axes/admin.py) displays lockout entries grouped by IP. After the change, administrators may misinterpret the UI, thinking a user is only locked out by IP when in fact the username factor is also part of the lockout, leading to incorrect manual unlock attempts.
C1. ["username", "ipaddress"] is OR lockout (getfailures takes the max of the two counters, the old AXESLOCKOUTBYUSERORIP path). "Together" is the nested [["username", "ipaddress"]]. The flat list locks that username from every other IP after failures from one address, which testlockoutbyuserandipallowswhensameuserdiffipwithoutcache treats as allowed.
C2. A nested pair gives each username its own counter, so one IP can try AXESFAILURELIMIT (default 3) passwords on every account and never trip. axes.W006 only checks that ipaddress appears somewhere, so this stays silent, and the default tests testlockoutbyipblockswhendiffusersameip currently require the other user on that IP to be blocked.
C3. In axes/conf.py, a missing AXESLOCKOUTPARAMETERS still runs the deprecated-flag block, and AXESUSEUSERAGENT appends onto element 0. Turning the implicit default into a nested list changes a user-agent-only project from [["ipaddress", "useragent"]] to [["username", "ipaddress", "useragent"]]. Replacing that whole block also drops AXESONLYUSERFAILURES, AXESLOCKOUTBYUSERORIP, and AXESLOCKOUTBYCOMBINATIONUSERANDIP.
C4. makecachekeylist concatenates values with no separator and skips falsy ones, so root at 10.0.0.1 hashes the same as root1 at 0.0.0.1. An empty username collapses to the old IP-only digest, so omitted-username attempts share one bucket and can hit leftover IP keys. The database handler stores real columns; the cache handler would be wrong for every default install.
C5. AxesCacheHandler.resetattempts hashes a single synthetic AccessAttempt. axesresetip and axesresetusername pass only one field, so they delete a different key than the pair that was incremented, and iporusername=True already raises NotImplementedError. The database handler still filters by whichever column is set, so the same command clears every username on that IP in the database and clears nothing in cache.
C6. The "do not record" guard in both handlers matches only lockoutparameters == ["username"] when the username is None. A combination still inserts username NULL, and filter(username=None) is IS NULL, distinct from "", so a missing field and a blank field are two extra counters that do not add to the real account. getclientusername does not casefold, and it truncates to 255 characters, so Admin/admin and long emails that share a prefix become separate or merged buckets.
C7. Rows already store the username, but today's count is the sum of every username on that IP. After the filter change, a shared address that is over the limit unlocks per pair with no migration. Cache entries move from sha256(ip) to sha256(username + ip), so existing cache lockouts stop matching. Any project that never set the flag picks this up on upgrade, while docs/4configuration.rst and docs/2installation.rst still say the default is ["ipaddress"].
C8. Non-verbose getclientstr logs exactly the lockout parameters, then cleanseparameters masks AXESSENSITIVEPARAMETERS, whose default is ["username", "ipaddress"]. The lockout warning no longer shows either half of the new key.
C9. AccessAttempt is unique on (username, ipaddress, useragent), and getfailures sums every user-agent row for the pair, but AccessAttemptAdmin marks a row locked only when that row's own failuressincestart reaches the limit. A lock spread across browsers never shows as locked in the admin.
