## Assumptions
- I read the repo. It's a small FastAPI + Tortoise ORM + Postgres service (`project/app`) with aerich migrations. There is one model, `TextSummary`, with an `id SERIAL` primary key.
- The integer ID is exposed in four places:
  - Path params `/summaries/{id}/` on GET, PUT and DELETE, declared as `id: int = Path(..., gt=0)` in `app/api/summaries.py`.
  - The `id` in the POST response, from `SummaryResponseSchema.id: int` in `app/models/pydantic.py`.
  - The `id` in `SummarySchema`, which `pydantic_model_creator` generates, so it appears in GET, list, PUT and DELETE responses.
  - `generate_summary(summary_id, url)`, the background task. I haven't read `summarizer.py`, so this is the one place I'm unsure of. It presumably looks the row up by integer ID.
- Existing clients store and send integer IDs and parse `id` as an int. Some may have saved IDs or URLs.
- Postgres is version 13 or later, so `gen_random_uuid()` is built in. If it isn't, enable `pgcrypto`.
- There's no auth, and no other table has a foreign key to `textsummary`.

## Approach: add a UUID alongside the integer key, then deprecate the integer
Keep the integer PK as the internal key. It's cheap for joins and the background task. Add a public `uuid` column and make the API accept and return it. Don't make the UUID the PK, because that would force a rewrite of every FK and lookup and wouldn't help compatibility.

**Phase 1: additive, no client breaks**
1. **Model:** add `uuid = fields.UUIDField(unique=True, default=uuid.uuid4)` to `TextSummary` in `app/models/tortoise.py`.
2. **Migration:** add an aerich migration in three steps:
   - Add the column as nullable.
   - Backfill with `UPDATE textsummary SET uuid = gen_random_uuid() WHERE uuid IS NULL`, in batches if the table is large.
   - Set `NOT NULL`, with a default of `gen_random_uuid()` at the DB level, then create the unique index (`CREATE UNIQUE INDEX CONCURRENTLY` where possible).
   - Write a real `downgrade`. The init migration's downgrade is empty.
3. **Responses:** keep `id` as an int and add `uuid` to `SummarySchema` and `SummaryResponseSchema`. Old clients see no change, and new clients can adopt `uuid`.
4. **Path params:** replace `id: int` with one shared dependency, for example `resolve_summary_ref(ref: str)`:
   - If the value parses as a UUID, look up by `uuid`.
   - If it's all digits, look up by `id` and add `Deprecation: true` and `Link: <…>; rel="successor-version"` headers.
   - Otherwise return 422. Don't use `Union[int, UUID]`, because its parsing can be ambiguous.
5. **CRUD:** in `app/api/crud.py`, make `get/put/delete` take the resolved row or a `(field, value)` pair. Keep the internal calls such as `generate_summary` on the integer PK.
6. **Logging:** count legacy integer-ID hits so there's data for the sunset decision.

**Phase 2: cutover, after the sunset window**
- Release a v2 (`/v2/summaries/`, or a version header) where `id` is the UUID string and the integer is never exposed.
- Keep v1 frozen on the integer `id` plus `uuid`, so old clients keep working. Remove v1 only after the legacy-hit counter reaches roughly zero and the announced sunset date has passed.
- Don't silently change the type of `id` on v1. That is exactly the break you want to avoid.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Changing `id` to a UUID on v1 breaks clients | Clients parse `id` as an int and have it in saved URLs | Keep `id` as int and add `uuid` in Phase 1. Make the UUID `id` a v2 only |
| 2 | Backfill locks or slows a large table | `UPDATE` plus `NOT NULL` and a unique index take locks on `textsummary` | Add nullable, backfill in batches, build the index concurrently, then set `NOT NULL` |
| 3 | Ambiguous path parsing | A `Union[int, UUID]` could mis-route or give confusing 422s | One explicit resolver: UUID regex first, then digits, else 422 |
| 4 | The integer ID leaks through other paths | The background task, logs and error messages still use the integer | Audit `summarizer.py` and logs. Keep the integer internal and never return it in v2 |
| 5 | Existing aerich migration state | The init migration has an empty downgrade, so a rollback is unsafe | Write a real downgrade and test upgrade then downgrade on a copy |
| 6 | IDOR stays as it is | There's no auth. Sequential integers on v1 remain enumerable | Disable integer lookups in v2. Note that UUIDs don't replace authorization |
| 7 | Tests and mocks drift | Unit tests mock `crud` with `int` signatures | Update the mocks and fixtures, and add dual-ref tests |
| 8 | Sunset never happens | Legacy int support lingers forever without a measured cutoff | Add the legacy-hit counter, `Deprecation` and `Sunset` headers, and a dated plan |
| 9 | Missing DB default for new rows | The ORM default doesn't cover raw inserts or other writers | Add the DB-level `DEFAULT gen_random_uuid()` and a unique constraint |
| 10 | Cache or CDN keyed on old URLs | Both forms address the same resource | Pick UUID as canonical and add `Link: rel=canonical`. Keep both forms valid in v1 |

Riskiest: #1. Changing the type of `id` on the existing API version breaks every client that still parses it as an int.
