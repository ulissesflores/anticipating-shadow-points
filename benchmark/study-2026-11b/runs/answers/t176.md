**Assumptions:** I made no edits (as instructed) and I'm not using the plan file. I read `PasswordHasher.cs` and `Users/Login.cs`.

**What exists today.**
- New hashes use ASP.NET Identity's `PasswordHasher<object>`. That is PBKDF2-HMAC-SHA512 at 210,000 iterations, with a versioned payload that carries its own salt.
- Legacy rows (a 64-byte HMAC-SHA512 hash plus a 16-byte salt) are still verified. They return `SuccessRehashNeeded`, and `Login.cs` rehashes them on the next successful login.
- So a lazy upgrade that needs no password reset is already in place. I take "stronger" to mean moving to something like Argon2id, or to a higher PBKDF2 cost. I assume it must stay compatible with both the legacy rows and the current Identity-format rows.

**Ways this could go wrong, before planning:**
- **Format detection:** the legacy check is a length heuristic (`hash.Length == 64 && salt.Length == 16`). A new format whose output is 64 bytes, or any ambiguous blob, could be misrouted to the wrong verifier. That would lock users out.
- **Lazy migration leaves a tail:** dormant accounts keep the weakest hashes (legacy HMAC) indefinitely. A DB leak exposes them, and the weak scheme can't be removed until they are migrated or expired.
- **Wrapping instead of rehashing:** re-hashing the stored legacy hash (hash-of-hash) would upgrade every row at once, but it needs a new format marker and a verify path that chains both schemes.
- **Schema limits:** `Hash` and `Salt` are `byte[]` columns, with `Salt` now empty for new rows. A longer, self-describing encoded hash may exceed column limits. Changing the shape needs migrations for both SQLite and SQL Server, plus snapshots.
- **Downgrade and rollback:** once rows are upgraded, an older build can't verify them. Rolling back the deploy would lock out everyone who has logged in since.
- **Argon2 dependency and platform risk:** Argon2 isn't in the BCL, so it needs a new package. That means a lock-file and `Directory.Packages.props` change, native or managed-implementation concerns, and a supply-chain review.
- **Cost and DoS:** higher memory or iteration cost raises login latency and CPU or RAM per request. Unauthenticated login becomes a cheaper DoS vector, and tests slow down.
- **Timing and user enumeration:** `Login.cs` returns early for an unknown email without hashing. That leaks which emails exist through response time. Making the hash costlier widens the gap.
- **Concurrent rehash race:** two simultaneous logins both rehash and save. With no concurrency token, the last write wins, which is harmless only if both hashes are valid.
- **Silent persistence failures:** if `SaveChangesAsync` fails after a successful verify, the login still succeeds and the user is never upgraded. Without logging or metrics, nobody notices.
- **Password change path:** `Users/Edit.cs` and `Create.cs` call `Hash` separately. If they diverge from the new scheme, the system ends up with mixed formats.
- **Test and spec drift:** the integration tests and the RealWorld Hurl/Bruno suites may seed legacy hashes. Fixtures can mask a broken legacy path, so a real legacy-row test is needed.
- **Secrets and logging:** the legacy scheme uses the constant key `"realworld"`. Keep it only for verification, and never log passwords or hashes during debugging.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Hash format misdetected | Legacy detection is a length heuristic (64/16 bytes) | Add an explicit version prefix or marker, and test that every format routes correctly |
| 2 | Lockout after rollback | Upgraded rows are unreadable by the old build | Ship verify support for the new format first, then enable issuing it later |
| 3 | Dormant weak hashes remain | Lazy rehash only runs on login | Set a sunset date, then expire or force a reset for the remaining legacy rows |
| 4 | Column or schema mismatch | `Hash` and `Salt` are `byte[]`, with separate SQLite and SQL Server models | Check length limits and add migrations for both providers if the shape changes |
| 5 | New Argon2 dependency | Needs a package, a lock file update and a supply-chain review | Prefer Identity-based PBKDF2 at higher cost, or vet and pin the package |
| 6 | Login CPU/DoS and latency | Higher cost hits an unauthenticated endpoint | Benchmark, add rate limiting, and cap the cost parameters |
| 7 | Timing / user enumeration | Unknown email returns before any hashing | Run a dummy hash on the not-found path |
| 8 | Rehash fails silently | The save after a successful login can fail or race | Log and meter failures, use a concurrency token, and make the update idempotent |
| 9 | Inconsistent hashing paths | `Create`, `Edit` and `Login` each call `Hash` | Route all of them through one `IPasswordHasher` and test each path |
| 10 | Tests mask a broken legacy path | Fixtures may only seed new-format hashes | Add integration tests that seed real legacy rows and assert the login and rehash flow |

Riskiest: #2, because a rollback after rows are upgraded locks users out, with no reset flow to recover them.
