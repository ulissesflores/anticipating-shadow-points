## Assumptions
- This repo is `express-session` 1.19.0. "Roll by default" means changing the default of the existing `rolling` option from `false` to `true`. Passing `rolling: false` must still turn it off.
- No new option name and no change to how the store expires sessions. Only the cookie default changes.
- Because this changes what existing apps see on the wire, it is a breaking change. It should go in a major release. If it has to ship in 1.x, use the deprecation pattern described below instead.

## What I found
- The option is read at `index.js:109` as `var rollingSessions = Boolean(opts.rolling)`.
- It is used only in `shouldSetCookie` at `index.js:491`. For a returning session it sets the cookie when `rollingSessions || (cookie.expires != null && isModified(session))`.
- The server-side expiry refresh (`store.touch`, `index.js:362-375`) does not depend on `rolling`. It already runs on every unmodified request when the store has a `touch` method. So this change only affects the browser cookie: a `Set-Cookie` header on every response, with the expiry reset to now + `maxAge`.
- `rolling` only extends anything when `cookie.maxAge`/`expires` is set. With the default browser-session cookie (no expiry), rolling just adds a `Set-Cookie` header to every response for no benefit.
- `test/session.js` has the test "rolling option › should default to false" (line 1159), and 26 assertions of `shouldNotHaveHeader('Set-Cookie')`. Some of those check returning requests and will flip.
- `README.md` around line 295 says "The default value is `false`." `HISTORY.md` has an `unreleased` section.

## Ways this could go wrong (before planning)
1. Shared caches: every response now carries `Set-Cookie`. A CDN or reverse proxy that caches responses with `Set-Cookie` could hand one user's session ID to others. Caches that don't do that will stop caching those pages.
2. Static files, health checks and other endpoints mounted after the session middleware start sending session cookies.
3. Apps that rely on "no `Set-Cookie` unless the session changed" (ETag/304 logic, cache keys, tests) break silently on a minor upgrade.
4. With no `maxAge`, rolling adds header noise and nothing else. Users think sessions now extend, but they don't.
5. The cookie gets extended but the store record doesn't. With a store that has no `touch` method and `resave: false`, the browser keeps a valid cookie for a session the store has already expired, so users get logged out unexpectedly. This was already possible with `rolling: true`, but now it would hit by default.
6. Security: sessions now only end after a period of inactivity, with no maximum lifetime. That conflicts with OWASP/compliance guidance on absolute timeouts and keeps a stolen or fixated session ID usable for longer.
7. Option parsing: `rolling: undefined` has to mean `true`, while `false`, `0` and `null` must still mean off. A naive `opts.rolling !== false` would treat `0` and `null` as on.
8. Tests, README, HISTORY, and the third-party `@types/express-session` docs all state the old default.

## Plan
1. **`index.js:108-109`**: make the default explicit.
   ```js
   var rollingSessions = opts.rolling === undefined ? true : Boolean(opts.rolling)
   ```
   - Alternative if this must ship in 1.x: follow the existing `resave` pattern at `index.js:121-124`. Call `deprecate('undefined rolling option; provide rolling option')` and keep `false` for now, then flip the default in the next major.
   - Optional, and I'd recommend it: only add the forced `Set-Cookie` when `req.session.cookie.expires != null`. That avoids risk 4. The guard would only apply to the implicit default, so an explicit `rolling: true` keeps its current behaviour.
2. **`index.js:78` JSDoc**: document the new default.
3. **`test/session.js`**:
   - Change "should default to false" into "should default to true": the second request must have `Set-Cookie`.
   - Add a test that `rolling: false` suppresses the cookie on an unmodified session.
   - Add tests that `0` and `null` count as false.
   - Add a test that the expiry advances between two requests when `maxAge` is set.
   - For the 26 `shouldNotHaveHeader('Set-Cookie')` checks: pass `rolling: false` where the test is about something other than rolling, and keep each test's intent.
4. **`README.md` (around line 295)**: change "default value is `false`". Add notes on caching/CDN and on the need for a store with `touch` support, or `resave: true`, so the store expiry matches the cookie.
5. **`HISTORY.md`**: add an entry under `unreleased`, marked as breaking (or as a deprecation if you take the 1.x route).
6. **Verify**:
   - Run `npm test`.
   - Run a manual two-request check with `maxAge: 60000`: the `Expires` on the second response should be later than on the first.
   - Confirm `rolling: false` gives no `Set-Cookie` on an unmodified request.
   - Confirm the cookie is still not sent over plain HTTP when `secure: true` (the `issecure` early return).

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|------------------|------------|
| 1 | Session ID leaks through shared caches | `Set-Cookie` now on every response, including cacheable GETs | README warning; recommend `Cache-Control: private`; release as major |
| 2 | Silent breaking change for 1.x users | Code and tests assume no `Set-Cookie` on unmodified sessions | Major bump, or deprecation warning first (`resave` pattern) |
| 3 | Cookie outlives the store record | `store.touch` only runs if the store has it; `resave: false` is common | Document; warn when store lacks `touch` and `resave` is false |
| 4 | No benefit without `maxAge` | Default cookie has `expires == null` | Only force the cookie by default when `expires != null` |
| 5 | Sessions never hit a hard limit | Rolling gives an idle timeout only, no maximum lifetime | Document; suggest the app enforce an absolute timeout |
| 6 | Explicit "off" values mis-parsed | `!== false` treats `0`/`null` as on | Use `=== undefined ? true : Boolean(...)`; add tests |
| 7 | Static/health routes get cookies | Middleware is often mounted before `express.static` | README note: mount session after static routes |
| 8 | Large test churn hides regressions | 26 no-`Set-Cookie` assertions | Add `rolling: false` per test instead of deleting assertions |
| 9 | Stale docs and types | README, JSDoc, `@types/express-session` say `false` | Update README, JSDoc, HISTORY; flag the types package |

Riskiest: #1. A `Set-Cookie` header on every response, combined with a shared cache, can hand one user's session ID to other users.
