**Assumptions.** This is a non-interactive run, so I've read the code and edited nothing, including the plan file. "By default" means changing the `SessionMiddleware.__init__` defaults in `starlette/middleware/sessions.py` from `same_site="lax"` and `https_only=False` to `same_site="strict"` and `https_only=True`. Opt-outs stay available through the existing arguments. I'd treat it as a breaking change that needs a release note and updates to `docs/middleware.md`, `docs/config.md` and the tests.

## Ways this could go wrong (before planning)

1. **Plain-HTTP breakage.** Browsers drop `Secure` cookies over `http://`, so sessions silently stop persisting in local dev, in `TestClient` (its base URL is `http://testserver`) and behind TLS-terminating proxies. Login loops and empty sessions would show up with no error.
2. **Strict breaks inbound navigation.** A user who follows a link from email, Slack or another site arrives without the cookie and looks logged out on the first page load. OAuth/OIDC redirect callbacks (the Authlib flow in `docs/config.md`) and payment-provider returns carry the session `state`, so Strict can fail them.
3. **Silent behavior change on upgrade.** Apps that never passed these arguments get different cookies with no code change, and the failure mode is "sessions don't stick" rather than an exception.
4. **Tests and docs encode the old defaults.** `tests/middleware/test_session.py` and `test_middleware.py` assert on the old cookie string, and `docs/middleware.md` says `lax` and `False`.
5. **Inconsistent validation.** `partitioned` and cross-site embeds already require `https_only=True` and `same_site="none"`. Defaults of `strict` and `https_only=True` make a bare `partitioned=True` contradictory, because Partitioned needs `none`.
6. **The "clear" cookie must match.** The deletion `Set-Cookie` reuses `security_flags`. If the flags change between versions, an old cookie set with Lax/non-Secure may not be overwritten or cleared in some browsers.
7. **WebSocket and subdomain paths.** The cookie is read on websocket scopes. Strict plus a custom `domain` can behave unexpectedly for cross-subdomain apps.
8. **Downstream and ecosystem impact.** Subclasses and wrappers that inspect `security_flags`, and frameworks built on Starlette (FastAPI tutorials and the like), would all change behavior at once.
9. **Scope creep.** Other cookie-setting code, such as CSRF or auth backends, would still use the old defaults and become inconsistent with the sessions cookie.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Secure cookie dropped over HTTP | `https_only` default flips to `True`. `TestClient` uses `http://testserver`, and dev servers use HTTP | Use an `https://` base URL in tests. Document `https_only=False` for dev |
| 2 | Strict drops cookie on cross-site navigation | Users arrive via email or external links and look logged out | Document `same_site="lax"` for login-style apps. Call it out in the release notes |
| 3 | OAuth/OIDC callback fails | `docs/config.md` stores `state` in the session, and the IdP redirect is cross-site | Update the docs example to set `same_site="lax"` |
| 4 | Silent upgrade regression | No exception is raised. Sessions just stop persisting | Make it a major or minor bump with a prominent note. Consider a one-release deprecation warning |
| 5 | Old tests and docs go stale | Existing tests assert `samesite=lax` and no `secure` | Update the tests, add default-flag tests, and fix `docs/middleware.md` |
| 6 | `partitioned` contradicts the defaults | It needs `same_site="none"`, but the new default is `strict` | Validate or document the combination. Add a test |
| 7 | Old cookies not cleared | The clearing cookie's flags differ from those the original was set with | Test the set and clear flows with matching flags |
| 8 | Subclass/ecosystem breakage | Downstream frameworks rely on the current defaults | Search known dependents. Keep the argument names unchanged |
| 9 | Inconsistent cookie policy | Other cookie-setting code keeps the old defaults | State that the scope is sessions only |

Riskiest: #1 (and #4), because the `Secure` default makes sessions silently stop persisting over plain HTTP, in tests and dev, with no error.
