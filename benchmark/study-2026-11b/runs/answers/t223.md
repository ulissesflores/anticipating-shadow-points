## Plan: rename an article's title and slug without breaking shared links

### What the code does today
- `ArticleUpdate` in `articles/routers.go:114` already regenerates the slug when the title changes. It calls `makeSlug`, then `makeUniqueSlug`, then updates the `slug` column.
- Nothing remembers the old slug. `FindOneArticle(&ArticleModel{Slug: slug})` matches only the current slug, so every old URL returns 404. That is the gap to close.
- Two existing quirks make it worse:
  - The check `base != articleModel.Slug` compares the bare base slug with the stored slug. An article stored as `foo-2` that is re-saved with the same title "Foo" gets a new slug, `foo-3`, because `makeUniqueSlug("foo")` finds `foo` and `foo-2` taken. Links break even though nothing changed.
  - `makeUniqueSlug` counts soft-deleted rows, so an old slug can be blocked by a deleted article. That is fine today, but it matters once old slugs are reserved.

### Assumptions
- The API shape stays RealWorld-compliant. `PUT /api/articles/:slug` returns the article with its new slug, and the client uses the returned slug.
- Old slugs should keep working on read endpoints. Redirecting is optional, because RealWorld clients expect JSON.
- SQLite with GORM `AutoMigrate`, as the repo already uses. I haven't confirmed where migration is called, so check that first.
- An old slug stays reserved for good, so no later article can take it.

### Approach: a slug-alias table
1. **Model** (`articles/models.go`): add `ArticleSlugModel` with `Slug` (unique index), `ArticleID` (indexed) and `gorm.Model`. Add it to the AutoMigrate list wherever the repo migrates `ArticleModel`.
2. **Record the old slug on rename.** In `ArticleUpdate`, when the slug changes, do these in one transaction:
   - update the article,
   - insert `{Slug: oldSlug, ArticleID}` into the alias table.

   The transaction matters because the existing retry loop on `gorm.ErrDuplicatedKey` re-runs `Update`.
3. **Resolve by alias.** Add one helper, `FindArticleBySlug(slug)`. It tries the current slug first, then falls back to the alias table and loads the article by `ArticleID`. Switch the handlers that call `FindOneArticle(&ArticleModel{Slug: slug})` to the helper:
   - retrieve
   - favorite and unfavorite
   - comment create, list and delete
   - update

   Delete may also use it. Before the switch, check how `FindOneArticle` handles preloads and the "my user" favorited flag, so the helper keeps that behaviour.
4. **Reserve aliases.** Change `makeUniqueSlug` to treat alias slugs as taken, so a new article never claims a retired slug. Do the same check when creating articles. Also make the create path reject a collision with an alias.
5. **Cycles.** If an article returns to an earlier title, its own alias row is a candidate. The new `makeUniqueSlug` would reject it and add a suffix. Instead, allow reuse when the alias belongs to the same article, and delete that alias row in the same transaction.
6. **Fix the needless re-slugging.** Skip the rename when the new title's base equals the current slug's base. Equivalently, strip the numeric suffix before comparing. This stops re-saves from churning slugs.
7. **Optional canonical signal.** When a request resolves through an alias, add a `Link: <…>; rel="canonical"` header or a 301 for GET. Default: no redirect, and the response body carries the current slug.
8. **Cleanup on delete.** When an article is deleted, delete or soft-delete its aliases. Decide whether a deleted article's old URLs should return 404. Default: 404, with the aliases still reserved so a slug can't be reused for a different article.

### Tests (`articles/unit_test.go`, using `common.TestDBInit()` and `common.TestDBFree()`)
- Rename, then GET by the old slug returns the article with the new slug.
- Rename twice, and both old slugs resolve.
- Favorite and comment through an old slug act on the same article.
- A new article whose title matches a retired slug gets a suffixed slug.
- Renaming back to an earlier title reuses the slug without error.
- Re-saving an unchanged title keeps the slug even when it has a `-N` suffix.
- Delete an article, then its old slugs return 404.
- Two authors: one cannot update through the other's alias (the 403 check stays).

### Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Handler misses the alias lookup | About 8 handlers call `FindOneArticle` by slug, so one missed handler leaves a 404 | Use one helper, and add a test per endpoint |
| 2 | Old slug stolen by a new article | `makeUniqueSlug` checks only `articles`, so a retired slug looks free | Make slug generation check aliases too |
| 3 | Rename and alias insert not atomic | The retry loop on `ErrDuplicatedKey` re-runs the update | Wrap both in one transaction |
| 4 | Needless slug churn on re-save | `base != Slug` is true for `foo-2`, so the slug becomes `foo-3` | Compare slug bases, and test it |
| 5 | Rename back hits own alias | The unique index on the alias table collides with the article's own old slug | Reuse the slug and drop the alias in the same transaction |
| 6 | Alias table grows without limit | Every rename adds a row, and there are no rate limits | Cap aliases per article, or add rate limiting |
| 7 | Schema migration on existing DBs | The new table needs AutoMigrate, and I haven't confirmed where it runs | Check the migration path, and test on a copy of an existing DB |
| 8 | Info leak after delete | A deleted article's alias could still resolve to a soft-deleted row | Resolve through scoped queries, and test for 404 |
| 9 | Race on concurrent renames | The existing slug race on create also applies to renames | Keep the unique indexes on both tables, and retry on duplicate |
| 10 | Clients cache the old slug | The SPA may keep using it after a rename | Return the new slug in the PUT response, and send a canonical header |

Riskiest: #2, an old slug being claimed by another article. That would silently send shared links to the wrong content.
