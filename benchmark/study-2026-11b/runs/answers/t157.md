## What the code does today

The cookie settings are built once, in `SessionMiddleware.__init__` (`starlette/middleware/sessions.py:24-36`):

- `same_site` defaults to `"lax"`.
- `https_only` defaults to `False`. `Secure` is only added when it is `True`.
- The same settings string is used both when writing the cookie and when clearing it.

The docs (`docs/middleware.md:235,237`) state both defaults and tell users to "set `https_only=True` in production".

## Ways this could go wrong

1. **Sessions stop working on plain-HTTP local development.** A browser won't send a `Secure` cookie back over `http://`. Chrome and Firefox make an exception for `localhost`, but not for `127.0.0.1` in every case, LAN IPs, `http://myapp.test`, or Docker hostnames. Sessions would silently stay empty, which looks like being logged out after every request.
2. **The existing test suite breaks.** `TestClient` uses `http://testserver` by default, and httpx won't send `Secure` cookies over http. That is exactly what `test_secure_session` (`tests/middleware/test_session.py:130-163`) checks. Every session test that writes and then reads using the default URL would fail, and so would the `path` test, which uses `base_url="http://testserver/second_app"`.
3. **Users' own test suites break**, for the same reason, in every project that tests sessions with Starlette's `TestClient`. This is probably the biggest visible break for users.
4. **Apps behind a TLS-terminating proxy.** The browser sees HTTPS, so `Secure` itself works. But anything that inspects the cookie on the internal hop, or runs plain-HTTP health checks or tests, is affected.
5. **`SameSite=Strict` breaks arriving from other sites.** When a user follows a link from email, Slack or a search result, the first request carries no session cookie, so they look logged out until they navigate again.
6. **OAuth/OIDC/SAML callbacks.** These sign-in flows store a state value in the session and then come back via a redirect or POST from the identity provider's site. With Strict, that cookie isn't sent on the way back, so the state check fails. Authlib's Starlette integration relies on `request.session` for this. This would break a lot of real sign-in setups.
7. **Payment and other cross-site redirect returns** (Stripe Checkout, 3-D Secure) fail in the same way.
8. **Silent failure.** Nothing raises an error. The cookie is set, the browser just never sends it back. That makes the problem hard to diagnose.
9. **The boolean flag can't express "not Secure".** Changing `https_only: bool = False` to `True` works, but the parameter name now reads oddly as a default. Changing it to `bool | None` with environment detection would add magic. Both choices affect the public API.
10. **Mismatch with `partitioned` and `same_site="none"` guidance.** The `partitioned` docs say "set `https_only=True`". That becomes redundant, but it must stay correct.
11. **Older cookies already in browsers.** These keep their old attributes until they are rewritten. Clearing a cookie with different attributes still works because browsers match on name, domain and path, so this is low risk. It should still be tested.
12. **Semver and release process.** This is a breaking change to defaults in a widely used framework. It needs a release note, and probably a major or minor version bump under the project's policy. `AI_POLICY.md` also requires checking for existing PRs, issues and discussions before opening a duplicate.

## Assumptions (non-interactive run)

- "By default" means only the constructor defaults change: `https_only=True` and `same_site="strict"`. Both stay configurable, so `https_only=False` and `same_site="lax"` still opt out.
- No automatic detection of the environment or scheme.
- This targets Starlette upstream, so docs, tests and release notes are in scope.
