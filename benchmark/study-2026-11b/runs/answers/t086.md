**What the code does today**
- A visit is only a pet, a date and a description (`owner/Visit.java`). It has no vet and no time of day, so "same vet at the same time" can't be expressed yet.
- Booking already exists at `/owners/{ownerId}/pets/{petId}/visits/new` (`owner/VisitController.java`), and there is no login.
- The database tables are created by `db/*/schema.sql` scripts that run on every startup. For MySQL and Postgres they use `CREATE TABLE IF NOT EXISTS`, so a column added to the table definition never reaches a database that already exists.
- There is a precedent for this kind of race: duplicate pet names are blocked by a unique index plus `PetClinicConcurrencyTests`. That index exists on H2 and Postgres but is missing on MySQL.

**Assumptions**
- "Online" means the existing web form, with no login added.
- Bookings use fixed 30-minute slots during clinic hours, so two visits clash only if they have the same vet, date and start time.
- Historical visits keep no vet and no time.
- Any vet can see any pet.

**Plan**
1. **Database:** add a vet and a start time to `visits`, plus a unique index on (vet, date, start time). Old rows have neither value, so they don't count as clashes on H2, Postgres or MySQL. Write the migrations so they can run on every startup: Postgres has `ADD COLUMN IF NOT EXISTS`; MySQL needs a guarded check because it lacks that. Rewrite H2's `data.sql`, whose inserts depend on column order.
2. **Model and lookups:** add the vet and start time to `Visit`, and a new `VisitRepository` to check whether a slot is taken and to list a vet's booked slots for a day.
3. **Controller:** on submit, check the vet exists, the time is on the 30-minute grid and inside opening hours, and the slot is free, with friendly error messages. If two bookings still race past those checks, the unique index rejects the second one; catch that error and show "slot taken" instead of an HTTP 500.
4. **Pages:** add a vet picker and a free-slot picker to the booking form, and show the vet and time in visit history. Old visits without them must still display.
5. **Translations:** add the new labels to every `messages*.properties` file, because `I18nPropertiesSyncTest` fails if any language is missing a key.
6. **Tests:** controller tests for each rejection case; a concurrency test where many threads book the same vet and slot and exactly one succeeds; and the MySQL and Postgres integration tests run against a database with the old schema.

**Main risks**

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Two simultaneous bookings both succeed | A check-then-insert in the controller isn't atomic | Unique index on (vet, date, start time); catch the duplicate error |
| 2 | Overlap slips past the unique key | 09:00 and 09:10 are different keys but overlap | Require times on the 30-minute grid, checked on the server |
| 3 | Existing MySQL/Postgres databases never get the new columns | The table scripts only create missing tables | Guarded `ALTER TABLE` statements that are safe to re-run |
| 4 | Sample data in H2 breaks | `data.sql` inserts values by column position | Name the columns in each insert |
| 5 | Old visits break pages or the unique index | Historical rows have no vet or time | Nullable columns, NULL-safe page code, required only for new bookings |
| 6 | Duplicate booking shows HTTP 500 | The database error isn't caught today | Turn it into a form error on the time field |
| 7 | Database engines behave differently | MySQL already lacks the pet-name unique index | Integration tests against all three engines |
| 8 | Translation test fails | It checks every language for the same keys | Add new keys to all translation files |
| 9 | Anyone can book for any owner | There's no login; the owner id is in the URL | Out of scope here; flag it as a follow-up |
| 10 | Wrong-day or past bookings | `LocalDate.now()` uses the server's time zone | Set the clinic time zone in configuration and use it everywhere |

Riskiest: #3: existing MySQL/Postgres databases never get the new columns or index, so the double-booking guard silently doesn't exist in production even though tests on a fresh H2 database pass.
