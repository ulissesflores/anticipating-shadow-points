**Assumptions**
- This is django-axes, where the default comes from `axes/conf.py`. Today it is `AXES_LOCKOUT_PARAMETERS = ["ip_address"]`.
- "Username and IP together" means the combined key `[["username", "ip_address"]]`, which is an AND. It does not mean `["username", "ip_address"]`, which is an OR.
- The change only affects the default, which applies when `AXES_LOCKOUT_PARAMETERS` and the legacy flags are all unset. Explicit settings keep working.
- I haven't edited any file, and I haven't written the plan file, because you said not to edit files. I only read `axes/conf.py`. I haven't run anything or checked the handlers, the tests or the docs.

**What could go wrong**
- The default gets weaker. A lockout counter per (user, IP) pair lets an attacker rotate IPs against one account without being locked. A single IP can also try many usernames, and each pair gets its own full attempt limit.
- Upgraders get a silent change. The 9.0.0 release is already prepared, and existing deployments would see different lockout behavior without changing any setting.
- The legacy-flag branch in `conf.py` is fragile. It uses `AXES_ONLY_USER_FAILURES`, `AXES_LOCK_OUT_BY_USER_OR_IP`, `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP` and `AXES_USE_USER_AGENT`. The `[0]` indexing logic assumes a particular list shape, and it could mishandle a nested default.
- A missing or odd username could break the lockout. Examples are API or token logins, credentials without a username field, and a custom `AXES_USERNAME_CALLABLE`. The key could then be built with `None`, which would either lock everyone sharing that blank value or skip the lockout.
- Username variants could bypass it. If `AXES_USERNAME_CASE_SENSITIVE` is on, `Admin` and `admin` become separate counters.
- Stored state could be inconsistent after deploy. Cache keys and `AccessAttempt` rows were built per IP, so counters reset or old rows stop matching. Existing lockouts could end early or never clear.
- Cache and database handlers might differ on how they count or filter combined keys. Reset-on-success and the signals could also behave differently.
- Many existing tests and docs assume an IP-only default. The test suite will break in many places, and the documentation will be wrong until it is updated.
- Proxy and IP-detection misconfiguration shows up differently. Today it locks out everyone behind one proxy IP. After the change, a wrong IP would make the per-user lockout inconsistent.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Weaker brute-force protection | A per-(user, IP) counter lets an attacker rotate IPs against one account without being locked | Keep an IP or username OR rule as well, or document it as opt-in |
| 2 | Silent breaking default | 9.0.0 is already prepared, and users who never set the option get new behavior | Changelog and upgrade note; consider shipping it in a major release with a warning |
| 3 | Legacy-flag and `USE_USER_AGENT` logic breaks | The `conf.py` branch and its `[0]` indexing assume a list shape | Add tests for each legacy flag combined with the new default |
| 4 | Empty or `None` username | The combined key can't be built, so there is a mass lockout or a skipped lockout | Define the fallback (IP only) and test non-form logins |
| 5 | Case or normalization bypass | Username variants create separate counters | Normalize the username before keying |
| 6 | Old counters and DB rows | Existing cache keys and `AccessAttempt` rows were keyed by IP | Note the reset in the release notes; check the cleanup command |
| 7 | Handler divergence | Cache and database handlers build and filter keys separately | Run the handler tests across all backends |
| 8 | Tests and docs drift | The IP-only default is assumed widely | Update the docs, and update or parametrize the tests |
| 9 | Proxy or IP misconfiguration | A wrong client IP now interacts with the username key | Document `AXES_PROXY_COUNT` and `AXES_META_PRECEDENCE_ORDER` |

Riskiest: #1, the weaker brute-force protection, because the new default makes attacks easier for every user who relies on it.
