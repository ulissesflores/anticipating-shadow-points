# Plan: default signing digest SHA-1 → SHA-256 (itsdangerous 2.3.0.dev)

**Assumptions**
- This is the `itsdangerous` library, currently at `2.3.0.dev` with an unreleased changelog section.
- The change is breaking, so it goes into 2.3.0 with no deprecation cycle. I'm assuming you accept that.
- I'm not adding automatic SHA-1 fallback. Callers opt in through the existing `fallback_signers`.
- No files were edited, as you asked. I'm also not writing a plan file.

## Findings
- `src/itsdangerous/signer.py:40` defines `_lazy_sha1`. It is wired in as `default_digest_method` on both `HMACAlgorithm` (line 54) and `Signer` (line 120). It is lazy so FIPS builds can still import the module.
- `Signer.derive_key` (around lines 201–207) uses `digest_method` to derive the key, not only to sign. The default change therefore alters the derived key as well as the MAC.
- The `Signer` and `HMACAlgorithm` docstrings (lines 52 and 94–100, 115) and `docs/concepts.rst:140–153` say the default is SHA-1. `docs/serializer.rst:97–103` shows a SHA-512 example with a SHA-1 fallback.
- `tests/test_itsdangerous/test_serializer.py` has two tests that depend on the default. `test_iter_unsigners` asserts `== _lazy_sha1` (line 180). `test_digests` asserts the default equals the SHA-1 output and pins `"[42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM"` (lines 189–192).

## Steps
1. **`signer.py`**
   - Replace `_lazy_sha1` with `_lazy_sha256`, which calls `hashlib.sha256(string)` at call time and keeps the FIPS rationale in its docstring.
   - Point both `default_digest_method` attributes at it.
   - Keep a `_lazy_sha1` alias, or leave it in place, only if it is used elsewhere. I'd drop it because it is private.
   - Update the docstrings and add `.. versionchanged:: 2.3` notes.
2. **Docs**
   - In `concepts.rst`, say the default is SHA-256. Keep the point that SHA-1 is safe inside HMAC, and recast the section as a rationale for modernizing.
   - Add a migration recipe: `Serializer(..., fallback_signers=[{"digest_method": hashlib.sha1}])`.
   - Mention the longer signature in cookies and URLs: 43 vs 27 base64 characters.
   - Adjust the `serializer.rst` example so it is not SHA-512-only.
3. **`CHANGES.rst`**: add a breaking-change entry under 2.3.0. Say that existing signatures and tokens become invalid unless SHA-1 is configured as a fallback or explicit digest.
4. **Tests**
   - Update `test_iter_unsigners` to use the new default.
   - Change `test_digests` so the default equals the SHA-256 output. Pin a new SHA-256 vector and keep the explicit SHA-1 and SHA-512 vectors.
   - Add a test that a SHA-1-signed token loads via a SHA-1 fallback and fails without one.
   - Add a test that `URLSafe` and `Timed` variants still round-trip.
5. **Verify**
   - Run `uv run pytest`, then mypy and ruff through pre-commit.
   - Run a FIPS-style check by monkeypatching `hashlib.sha1` to raise. Import and default use must still work.
   - Sign a token with 2.2.0 and load it with the new code, with and without a fallback.
   - Check downstream users such as Flask, which passes `digest_method=hashlib.sha1` explicitly and so should be unaffected.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing tokens, sessions and cookies stop validating | Both the signature and the derived key change, so every outstanding SHA-1 signature fails | Document the SHA-1 `fallback_signers` recipe, add a changelog entry, and ship in a minor version with a loud note |
| 2 | Users who rely on the default can't roll back or deploy gradually | Old and new app versions in a rolling deploy reject each other's tokens | Recommend deploying a fallback-enabled version first, then switching |
| 3 | Longer signatures break size limits | SHA-256 adds 16 base64 characters per token, which matters for cookies and URLs | Document the size delta and test URL-safe and timed tokens |
| 4 | Hidden dependence on the default digest | Code that calls `Signer` or `HMACAlgorithm` directly, or subclasses and overrides `default_digest_method`, may break | Grep downstream projects and note the change in the API docs |
| 5 | Third-party verifiers mismatch | Another service that verifies these signatures, for example in another language, assumes SHA-1 | List this under compatibility in the changelog and tell users to pin the digest explicitly |
| 6 | FIPS regression | An eager `hashlib` access at import would break FIPS builds, which `_lazy_sha1` was written to prevent | Keep the lazy wrapper and add a test that import works without SHA-1 |
| 7 | Stale tests and docs | Pinned SHA-1 vectors and the "default is sha1" docs would contradict the code | Update them in the same change and grep for `sha1` and `SHA-1` |
| 8 | Key-derivation side effect goes unnoticed | `django-concat` hashes the salt and secret with the default digest, so the key changes, not only the MAC | Call it out in the docs and test a fallback-signed round trip |

Riskiest: #1. Every outstanding token or session signed with the SHA-1 default is invalidated on upgrade, because both the signature and the derived key change.
