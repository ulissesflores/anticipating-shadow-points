## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Sessions silently stop working on plain HTTP | Browsers and httpx drop `Secure` cookies over `http://`, so local dev and HTTP-only deployments lose their sessions with no error | Release-note it, document `https_only=False`, and test over HTTPS |
| 2 | Cross-site logins and flows break | `SameSite=Strict` omits the cookie on cross-site navigations, which breaks OAuth/OIDC callbacks and links from email | Document `same_site="lax"` for those flows |
| 3 | Behind a TLS-terminating proxy, `Secure` still works but test and dev setups differ | Browsers see HTTPS, while internal checks and health probes over HTTP get no cookie | Document the proxy case and keep the override |
| 4 | Many existing tests fail | The default `TestClient` uses `http://testserver`, so default-config tests lose cookies | Switch the base URL to HTTPS and keep the override tests |
| 5 | Downstream breakage for users upgrading | Users on the old defaults see sessions vanish after a minor upgrade | Highlight it in the release notes and ship it in a major or clearly marked release |
| 6 | Embedded or iframe use breaks | `Strict` cookies are not sent in third-party frames, and `none` needs `Secure` | Keep `same_site="none"` with `https_only=True` as the documented path |
| 7 | Docs example becomes misleading | `docs/config.md` examples assume defaults that no longer hold | Review and update the examples |

Riskiest: #1, because sessions silently stop persisting on plain HTTP with no error.
