## Assumptions
- "Username and IP together" means the existing combination mode, `AXES_LOCKOUT_PARAMETERS = [["username", "ip_address"]]`. Lockout applies only to a given user from a given IP. It does not mean "user OR IP".
- This is a breaking default change, so it should ship as a major or minor release with a loud changelog entry. It should not be a silent patch.
- Explicit settings keep winning. That covers `AXES_LOCKOUT_PARAMETERS` and the deprecated flags `AXES_ONLY_USER_FAILURES`, `AXES_LOCK_OUT_BY_USER_OR_IP`, `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP` and `AXES_USE_USER_AGENT`.

## Findings
- `axes/conf.py:42-60` computes the default. When no flag is set, the `else` branch at line 51 yields `["ip_address"]`.
- The `AXES_USE_USER_AGENT` block already handles a nested first entry by appending `user_agent` to it. It works unchanged with the new default.
- `axes/checks.py:183-203` only warns when no `ip_address` is present, so it still passes. The default is read in `axes/helpers.py:317-329` and logged in `axes/apps.py:40-60`, and neither needs changes.
- The documented default is stale in `docs/4_configuration.rst:93`. `docs/5_customization.rst:181+`, `docs/2_installation.rst:150-168` (the migration table) and `docs/3_usage.rst:128` also describe it.
- Many tests assume IP-only lockout: `tests/base.py`, `test_login.py`, `test_attempts.py`, `test_handlers.py`, `test_helpers.py`, `test_failures.py`, `test_checks.py`, `test_logging.py` and `test_management.py`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Credential stuffing and username spraying are no longer throttled | One IP can try unlimited distinct usernames, because each username+IP pair gets its own counter | Document it. Suggest `["ip_address", ["username", "ip_address"]]` for a per-IP cap plus a per-pair cap |
| 2 | Attackers rotating IPs against one account | Lockout is per pair, so a botnet can guess one user's password indefinitely | Recommend a per-username parameter, or CAPTCHA or MFA alongside |
| 3 | Silent behavior change on upgrade | Deployments relying on the implicit IP-only default get weaker protection without any config change | Changelog breaking note, a release note, and a one-time startup log or system check |
| 4 | Real lockout for a user is easy to dodge | A legitimate user's lockout only affects that IP, so they can retry from mobile data, which weakens the lock's purpose | Document the intended semantics and offer the user-only mode |
| 5 | Wrong client IP behind proxies | If ipware or proxy headers are misconfigured, every user shares one IP, or IPs are spoofable via `X-Forwarded-For` | Keep `AXES_PROXY_COUNT` and trusted-header docs prominent |
| 6 | Existing lockout records and counters | Existing `AccessAttempt` rows were keyed by IP only, and they are matched differently after the change | Note that old rows age out or are reset, and tell users to run `axes_reset` |
| 7 | Test suite churn | Many tests assume IP-only, so mass edits could mask real regressions | Pin old tests via `override_settings`, and add new default tests |
| 8 | Interaction with `AXES_LOCKOUT_TIERS`, whitelists and `AXES_NEVER_LOCKOUT_*` | These features assume the IP is the key, so checks may behave differently | Add combination-mode tests for each, and review `helpers.py` for IP-only assumptions |
| 9 | Username normalization and truncation (9.0.0) | Case or truncation differences split or merge counters, and attackers can vary case to dodge them | Verify the lookups normalize usernames, and test case variants |
| 10 | Docs and defaults drift | Docs still state `["ip_address"]` in several places | Update all four doc spots in the same change and grep for stale mentions |

Riskiest: #1. The combination default removes any per-IP cap, so one host can spray unlimited usernames without being locked out.
