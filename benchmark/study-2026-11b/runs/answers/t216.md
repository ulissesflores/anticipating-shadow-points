## Plan

**Assumptions**
- "Online" means the existing public form at `/owners/{ownerId}/pets/{petId}/visits/new`. The app has no login, and adding one is out of scope.
- Bookings use fixed 30-minute slots during configurable clinic hours. That turns "no overlap" into a simple uniqueness rule.
- New bookings must name a vet. Existing visits keep an empty vet and time.
- Cancelling and rescheduling are not part of this change.

**Approach**
1. **Database changes.** Add `vet_id` and `visit_time` to the visits table, plus a unique rule on (vet, date, time), in the H2, Postgres and MySQL scripts. Old visits keep an empty vet and time, and empty values never clash under that rule, so they're unaffected.
   - The Postgres and MySQL scripts run on every startup. On an existing database the `CREATE TABLE IF NOT EXISTS` is skipped, so separate upgrade statements that can safely run again are needed.
   - Postgres has `ADD COLUMN IF NOT EXISTS`. MySQL doesn't, so its upgrade needs a guarded statement or a documented one-off migration.
   - The sample-data inserts list values by position, so they must name their columns once the table gains new ones.
2. **Model.** `Visit` gets a vet and a time.
   - Add a new `VisitRepository` that answers "is this slot taken?" and "which times are booked for this vet and day?".
   - Add a lookup of a single vet by id to `VetRepository` (not cached).
   - Add a `VetFormatter`, modelled on `PetTypeFormatter`, so the form can pick a vet by id.
   - Add a small helper that builds the slot list and removes booked times.
3. **`VisitController`.**
   - Add a vet list to the form, and an endpoint that returns the free slots for a vet and date.
   - When a booking is submitted:
     - Check that the vet and time are set, and that the time is a real slot within clinic hours.
     - Check whether the slot is already taken, to show a friendly message in the normal case.
     - Save with `saveAndFlush`. If the database rejects it under the unique rule, show "slot taken" on the form instead of an error page. `PetController` already handles duplicate pet names this way.
   - **The database rule is what actually prevents double-booking; the earlier check only gives a nicer message.**
4. **Pages and translations.**
   - Add vet and time pickers to the visit form, and vet and time columns there and on the owner page.
   - Add the new message keys to every `messages*.properties` file, or `I18nPropertiesSyncTest` fails.

**How to test it**
- **Controller tests:** the valid and invalid cases, including a database rejection turning into a form error rather than a 500.
- **Concurrency test**, modelled on `PetClinicConcurrencyTests`: several requests book the same vet and slot at once, and exactly one succeeds with one row saved. A second case where different vets get the same slot should let both succeed.
- **Postgres and MySQL integration tests:** the schema scripts must run twice against an existing database without errors.
- **Full build** with `./mvnw verify`, then a manual booking in the running app.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing MySQL/Postgres databases never get the new columns | Scripts use `CREATE TABLE IF NOT EXISTS` and run on every startup; there's no migration tool | Add upgrade statements that can safely re-run (guarded on MySQL); test against an existing database |
| 2 | Double-booking under concurrent requests | The "is it taken?" check and the save are separate steps | Unique rule on (vet, date, time) in the database, plus `saveAndFlush` and catching the rejection |
| 3 | A database rejection shows up as an HTTP 500 | Spring raises the duplicate as a generic `DataIntegrityViolationException` | Catch only the slot rule's violation, as `PetController` does, and re-throw anything else |
| 4 | Visits that don't overlap exactly can still collide | The unique rule only blocks identical start times | Accept only slot-aligned times, checked on the server |
| 5 | Old visits break pages or rules | Existing rows have no vet or time | Allow empty values in the database; require them only for new bookings; display empty values safely |
| 6 | Sample-data inserts fail | `INSERT INTO visits VALUES (...)` lists values by position | Name the columns in all three `data.sql` files |
| 7 | Translation test fails | `I18nPropertiesSyncTest` requires every locale file to have the same keys | Add the new keys to all `messages_*.properties` |
| 8 | Anyone can book for any owner | The app has no login | Treat it as out of scope; leave this risk in place until login exists |
| 9 | Timezone or "today" edge cases | `LocalDate.now()`/`LocalTime` use the server's clock | One configured clinic timezone; reject past slots on the server |
| 10 | Vet list goes stale | `findAll()` is cached in `vets` | Use the uncached `findById` when saving; the vet list being stale is acceptable |

Riskiest: #1 — the schema upgrade on existing MySQL/Postgres databases, because if the unique rule never gets created there, nothing stops two bookings for the same slot.
