Most of this is already done in `HEAD`, and the working tree is clean. What's still missing is protection for accounts that never log in again. I didn't edit any files, including the plan file, because you asked for no edits.

## What's already in place

- **New hashes use a strong scheme.** `src/Conduit/Infrastructure/Security/PasswordHasher.cs:13` wraps ASP.NET Core Identity's `PasswordHasher<object>` with 210,000 iterations. That is PBKDF2-HMAC-SHA512 with a random salt and the settings stored inside the hash. `Create.cs:86` and `Edit.cs:187` store these hashes with an empty `Salt`.
- **Old hashes still work.** `PasswordHasher.cs:25` recognises old hashes (64-byte hash plus 16-byte salt). Those are a single HMAC-SHA512 keyed with the hard-coded string `"realworld"`, which is fast to brute-force. When one matches, it returns `SuccessRehashNeeded`.
- **Users are upgraded at login.** `Login.cs:79` rehashes the password and clears `Salt` after a successful login. Raising the iteration count later also triggers this, because Identity reports `SuccessRehashNeeded` when a hash used fewer iterations.
- **Tests exist.** `tests/...<home>` checks that new hashes are randomised, and that an old hash is upgraded only after a correct password.

**The gap:** an account whose owner never logs in again keeps its weak old hash forever. If the database leaks, those passwords are cheap to crack.

## Assumptions

- The goal is that no stored hash stays weak, not just the ones whose owners come back.
- No schema change is wanted. The `Hash`/`Salt` columns (`varbinary(max)`/BLOB) can hold any format.
- The upgrade runs as a deliberate operator step, not automatically on every startup.
- I'm keeping the existing Identity PBKDF2 scheme rather than switching to Argon2. Argon2 would need a new third-party package, and PBKDF2-SHA512 at 210k iterations meets the OWASP guidance.

## Ways this could go wrong (before planning)

1. The format check confuses the three hash types and rejects valid passwords. Today's check relies on lengths: Identity's format is 61 bytes and the old one is 64. Adding a third format makes that more fragile.
2. A partially failed batch upgrade leaves some rows unreadable, with no way back.
3. The batch job rehashes a row that was already upgraded, or overwrites a hash that a login or password change just wrote.
4. The upgrade runs at startup: PBKDF2 for every user blocks the app from starting, and several instances run it at the same time.
5. Saving the login upgrade fails and turns a successful login into an error.
6. The rewrite misses `Salt`, which still marks the old and the wrapped formats.
7. New hashes cost about 100 ms of CPU each. With no rate limit, a burst of login attempts can overload the server.
8. A missing user fails instantly while a wrong password takes about 100 ms, so response time reveals which emails are registered.
9. Hashes written by the new code can't be read by the old code, which breaks rolling back to an earlier deployment.
10. Backups still hold the old weak hashes.

## Plan: wrap the old hashes in place

The idea is to put each old HMAC hash inside PBKDF2. No plaintext password is needed, so nobody has to reset.

1. **Add a "wrapped" format to `PasswordHasher.Verify`**, with explicit checks in this order:
   - Old format: `hash.Length == 64 && salt.Length == 16`. Keep this branch unchanged.
   - Wrapped format: `salt.Length == 16 && hash.Length != 64`. Compute the old HMAC from the password and salt, then check the stored hash using Identity's `VerifyHashedPassword` with `Convert.ToBase64String(hmac)` in place of the password. On a match, return `SuccessRehashNeeded`. `Login.cs` then turns it into a plain new-format hash with no other changes.
   - Current format: `salt.Length == 0`. Keep this branch unchanged.
   - Move the HMAC calculation into a private `LegacyDigest(password, salt)` helper so the old and wrapped branches share it.
2. **Add `WrapLegacy(byte[] legacyHash)` to `PasswordHasher`.** It returns the Identity hash of `Convert.ToBase64String(legacyHash)`. It is internal to the security code and not added to `IPasswordHasher`'s public interface.
3. **Add a one-off upgrade step** in `src/Conduit/Infrastructure/Security/LegacyHashUpgrader.cs`:
   - Take `ConduitContext` and a `CancellationToken`.
   - Work in batches of about 500 and select only rows where `Salt.Length == 16 && Hash.Length == 64`.
   - Rewrite only `Hash` and keep `Salt`, since it identifies the wrapped format.
   - Save each batch with a check that `Hash` is still the old value, so it doesn't overwrite a login or password change made in the meantime. Rows that conflict are skipped.
   - It can safely be re-run.
   - It runs only when the operator passes an explicit flag (e.g. `--upgrade-legacy-hashes`) in `Program.cs`, after `DatabaseInitializer.InitializeAsync`. The app does not start serving during that run.
4. **No EF migration.** The model doesn't change, so no change is needed to `docs/database-migrations.md` either.
5. **Docs:** add a short section on running the upgrade, taking a backup first, and rotating or expiring old backups.

## Tests (in `PasswordHashingTests.cs`)

- A wrapped hash accepts the right password, rejects a wrong one, and returns `SuccessRehashNeeded`.
- An end-to-end path: create an old-format user, run the upgrader, log in, and confirm the hash is now the plain format with an empty `Salt`.
- Running the upgrader twice changes nothing the second time.
- The upgrader skips rows that are already in the new format.
- A row changed between the batch read and the save is not overwritten.
- Each format is classified correctly at its boundary lengths (61, 64, and 0- and 16-byte salt).

## Verification

- Run `dotnet run --project build/build.csproj -- test` (format, Release build, all tests).
- Manual check: run `make run-local` against a copy of a database that has old-format rows. Run with the flag and confirm through SQL that no row has a 64-byte hash. Log in as one of those users and confirm the row now has an empty `Salt`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Formats misclassified, valid logins rejected | Format is told apart only by hash/salt length | Explicit ordered checks; tests at 61/64 bytes and 0/16-byte salt |
| 2 | Inactive users keep weak hashes | Upgrade happens only at login; old scheme is one HMAC with key `"realworld"` | Wrap old hashes in PBKDF2 with the batch upgrader |
| 3 | Batch overwrites a newer hash | Login or Edit may rewrite `Hash` during the batch | Save only if `Hash` is unchanged; skip conflicts; safe to re-run |
| 4 | Startup stalls or instances race | Each row costs about 100 ms of PBKDF2 | Run only with an explicit flag, in batches, on one instance |
| 5 | Rollback can't read wrapped hashes | Older code doesn't know the wrapped format | Ship the verify change first, then run the upgrader |
| 6 | CPU overload from login floods | 210k iterations per attempt, no rate limit | Add login rate limiting (separate change) |
| 7 | Timing reveals registered emails | Missing users return before any hashing | Hash a dummy value when the user isn't found |
| 8 | Old hashes survive in backups | Wrapping only changes live rows | Back up, then expire old backups |
| 9 | Failed save breaks a good login | Login upgrade saves inside the login request | Keep the upgrade in a try/catch: log and continue |

Riskiest: #1, because getting the format check wrong silently locks users out of their accounts.
