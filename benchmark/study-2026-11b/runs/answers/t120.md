**Assumptions:**
- The new default is the combined form `[["username", "ip_address"]]`: a username is locked only from the IP it failed from. It is not `["username", "ip_address"]`, which locks if either one hits the limit.
- The old deprecated flags (`AXES_ONLY_USER_FAILURES`, `AXES_LOCK_OUT_BY_*`, `AXES_USE_USER_AGENT`) keep their current meanings. Only the case where no flags are set changes.
- Anyone who sets `AXES_LOCKOUT_PARAMETERS` explicitly is unaffected.
- This changes behaviour for existing users, so it ships as 10.0.0.
- No database migration is needed, because the combined form already works in the database, cache and admin.

**Plan:**
1. **`axes/conf.py:37-60`:** change only the "no flags set" fallback to `[["username", "ip_address"]]`. Any old flag, including `AXES_USE_USER_AGENT` alone, keeps its current result. | # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Weaker protection against one IP trying many usernames | The IP-only limit is gone, so each username/IP pair gets its own 3 tries | Changelog advice to use `["ip_address", ["username","ip_address"]]`, lockout tiers or rate limiting |
| 2 | Silent behaviour change on upgrade | Most installs rely on the implicit default | Major version, prominent changelog entry, documented opt-out |
| 3 | Existing lockouts released on upgrade | Old IP-only cache keys and filters no longer match the combined lookup | Document it; suggest `axes_reset` or a short monitoring window |
| 4 | Cache-key collisions | `make_cache_key_list` joins values with no separator (`"user1"+"1.2.3.4"` equals `"user"+"11.2.3.4"`) | Add a separator in a follow-up change (it also rotates keys) or document it |
| 5 | Old flags remapped by mistake | The `conf.py` fallback has nested branches, and the user-agent branch modifies the list in place | Pure-function refactor plus a test for each flag combination |
| 6 | Hidden test dependence on the old default | Many tests use "default settings" without saying IP-only | Run the suite with the flip first, then pin tests explicitly |
| 7 | Empty username falls back to IP-only | Blank values are dropped from the key, and the database filter matches empty usernames | Keep current behaviour and add tests for it |
| 8 | Custom callables or handlers assume a flat list | Third-party code may read `settings.AXES_LOCKOUT_PARAMETERS` and expect strings | Changelog note; nested lists are already a documented form |

Riskiest: #1 — one IP can now try many usernames before any lockout, unless users opt into keeping a separate IP-only limit.
