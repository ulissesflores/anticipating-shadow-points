I made no edits. I only read `axes/conf.py`. This is django-axes at 9.0.0.

**Assumptions**
- The change is to the fallback in `axes/conf.py:51`. It would go from `["ip_address"]` to `[["username", "ip_address"]]`, the same as `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP`.
- Explicit settings and the legacy flags keep working exactly as they do now.
- "New default" means a new release, not a silent patch.

**Ways this could go wrong, before planning**
- **Weaker brute-force protection.** Failure counts are tracked per (username, IP) pair. An attacker who cycles usernames from one IP, or cycles IPs against one username, never reaches the limit.
- **Silent behavior change on upgrade.** Existing sites that rely on the default would get different lockouts without touching their settings. 9.0.0 has just shipped, so this is a breaking default for a minor or patch release.
- **Old lockout records.** Existing `AccessAttempt` rows and cache keys were created under IP-only rules. After the change they may be orphaned, or they may stop matching, so some locked-out clients get unlocked.
- **Missing or unusual usernames.** API, token, or custom `USERNAME_FIELD` logins may give `username=None`. The lockout key then collapses or never matches.
- **Username normalization.** `Alice` and `alice` count as different keys unless a username callable normalizes them. That gives an easy bypass.
- **Legacy flag precedence.** `conf.py` picks the default only when no flag is set. A new default can clash with `AXES_ONLY_USER_FAILURES` and `AXES_LOCK_OUT_BY_USER_OR_IP`, and with the deprecation paths.
- **Tests and docs.** Tests, docs, and the changelog assume IP-only defaults, so many will fail or become misleading.
- **Reverse proxies.** If proxy IP headers are misconfigured, every user shares one IP. Combined keys then hide a problem that IP-only lockouts used to show loudly.
- **Reset and admin tooling.** `axes_reset`, the admin filters, and reset-on-success need checking against the combined key.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Username or IP rotation evades lockout | Counters are per (username, IP) pair | Document the tradeoff and keep the IP-only option. Consider an extra IP-only threshold. |
| 2 | Breaking default in a minor release | 9.0.0 just shipped and existing sites rely on the default | Ship in a major release with a loud changelog entry and an upgrade note. |
| 3 | Old attempts no longer match | Records and cache keys were made under IP-only rules | Add a note and a migration or reset step. Test upgrading with existing data. |
| 4 | `username=None` or custom login fields | The key degenerates for API or token auth | Fall back to IP when the username is missing. Test custom `USERNAME_FIELD`. |
| 5 | Case or whitespace username bypass | `Alice` and `alice` count as separate keys | Normalize usernames by default. Test mixed case. |
| 6 | Legacy flag conflicts | The default sits next to the `conf.py` deprecation logic | Leave the legacy flag branches unchanged and test each combination. |
| 7 | Tests and docs go stale | The suite and docs assume IP-only lockout | Update the expectations and the documented defaults together. |
| 8 | Proxy misconfiguration is masked | A shared IP plus per-username keys hides the problem | Keep the proxy and ipware docs and add a startup warning. |
| 9 | Reset and admin tools mismatch | Tools were built around IP-only keys | Verify `axes_reset` and the admin with combined keys. |

Riskiest: #1, because the new default weakens brute-force protection for every site that doesn't set the option explicitly.
