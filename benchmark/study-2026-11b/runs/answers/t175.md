I've written the plan to `claude-home/plans/change-the-default-signing-reflective-clover.md`; no repo files were changed. Two parts are worth checking before you approve:

- **The fallback-merge fix** changes how existing `fallback_signers` dicts behave.
- **The FIPS handling** decides whether a bad token raises `BadSignature` or `ValueError`.

**Assumptions:**
- This ships in 2.3.0, which is unreleased and already contains breaking changes.
- SHA-256 is the new default rather than SHA-512, because it keeps tokens shorter.
- `Serializer` keeps loading old tokens through a built-in SHA-1 fallback. Bare `Signer` has no fallback mechanism, so for it this is a documented break.

**The plan:**
1. **`signer.py`:** set `default_digest_method = hashlib.sha256` on both `HMACAlgorithm` and `Signer`, and update the docstrings. Keep `_lazy_sha1`, because tests and Flask import it.
2. **The derived key changes too.** The digest is also used in `derive_key` (`signer.py:200-208`), not just the HMAC.
3. **`serializer.py:102`:** set `default_fallback_signers = [{"digest_method": _lazy_sha1}]`. Two fixes come with it:
   - `iter_unsigners` (`serializer.py:297-307`) doesn't merge `signer_kwargs` into dict fallbacks. Without a merge, anyone using a custom `key_derivation` can't verify their old tokens.
   - On FIPS builds without SHA-1, a bad token would hit the fallback and raise `ValueError` instead of `BadSignature`. Catch that and skip the fallback.
4. **Tests:**
   - Update `test_iter_unsigners` and `test_digests`.
   - Re-sign the hardcoded token in `test_timed.py:70`, which was signed with SHA-1.
   - Add tests for: a 2.2-era token still loading, the kwargs merge, and FIPS behaviour.
5. **Docs:** regenerate every sample token (README, `signer.rst`, `serializer.rst`, `url_safe.rst`, `concepts.rst`). Rewrite the "Digest Method Security" section and add a "keep SHA-1" recipe.
6. **`CHANGES.rst`:** add a breaking-change entry covering token length, the fallback, the raw-`Signer` break and how to keep SHA-1.

**Verification:** run pytest, mypy/pyright and a Sphinx build with `-W`. Then load tokens created with 2.2.0 using the new build, and run Flask's test suite against it.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Every existing token stops verifying | The default digest affects both the MAC and the derived key | Default SHA-1 fallback on `Serializer`; old-token tests |
| 2 | Raw `Signer` / `TimestampSigner` users break | They have no fallback mechanism | Changelog entry plus a "pin SHA-1" recipe |
| 3 | Fallback silently fails for custom kwargs | Dict fallbacks don't merge `signer_kwargs` | Merge kwargs; add a test |
| 4 | FIPS: `ValueError` instead of `BadSignature` | The SHA-1 fallback runs whenever the primary signature fails | Catch it and skip that fallback |
| 5 | Longer tokens (27→43 chars) | Cookie and URL size limits | Document it; SHA-256 rather than SHA-512 |
| 6 | Repeat of the yanked 1.0.0 | That release made the same kind of change without a fallback | Ship with a fallback and a clear changelog |
| 7 | Timed test passes for the wrong reason | Its hardcoded token is signed with SHA-1 | Re-sign it with SHA-256 |
| 8 | Downstream breakage (Flask etc.) | Flask imports `_lazy_sha1` | Keep the symbol; run Flask's test suite |
| 9 | Stale doc tokens | Many hardcoded samples in docs | Regenerate them and check with a script |
| 10 | Rolling-deploy mismatch | Old app nodes can't read SHA-256 tokens from new nodes | Document: upgrade every node before relying on new tokens |

Riskiest: #1 — every token already issued (sessions, reset links, signed URLs) stops verifying unless the SHA-1 fallback is in place and covered by tests.
