I'm summarizing what I found. Most of this change is already in the repo.

## Current state (verified by reading, no edits made)

- `src/Conduit/Infrastructure/Security/PasswordHasher.cs` already issues ASP.NET Core Identity v3 hashes: PBKDF2-HMAC-SHA512 with 210,000 iterations and a random salt embedded in the payload.
- It still verifies legacy hashes. These are 64-byte HMAC-SHA512 values with a 16-byte `Salt` column, keyed with the constant `"realworld"`.
- A legacy match returns `SuccessRehashNeeded`. `Login.cs:79-84` then rewrites `Hash` and sets `Salt = []`. `Create.cs` and `Edit.cs` also use the new hasher.
- `PasswordHashingTests.cs` covers randomized new hashes and rehash-on-login.

I haven't run the build or tests. I'm assuming "stronger scheme without forced resets" means lazy upgrade on login, which is what's already there. So the plan covers the remaining gaps.

## Assumptions

- No Argon2 or bcrypt. That would add a dependency, and the repo pins packages centrally with locked restore. PBKDF2-SHA512 at the OWASP-level iteration count is acceptable.
- No schema change. `Hash` is already `byte[]`, so no SQLite or SQL Server migration is needed.
- Some legacy users may never log in again. Wrapping their hashes is optional and listed below.

## Plan

1. **Make the format dispatch explicit.** In `PasswordHasher.Verify`, replace the `hash.Length == 64 && salt.Length == 16` heuristic with a documented check. Legacy means `Salt.Length == 16` and `Hash.Length == 64`. Identity v3 means the first byte is `0x01`.
2. **Handle upgrades inside the hasher.** Identity already returns `SuccessRehashNeeded` when the stored iteration count is below 210,000. Add a test for this so a later bump of the iteration count upgrades users automatically.
3. **Make the login path uniform.** When the email is unknown, `Login.cs` returns 401 without doing any hashing. Run a dummy verify against a fixed hash so the response time doesn't reveal which emails exist.
4. **Keep legacy verification read-only and removable.** Add a comment and a query or metric for how many rows still have a 64-byte hash, so the legacy branch can be deleted once that count is near zero.
5. **Optional: wrap the remaining legacy hashes.** A one-off job could store PBKDF2(legacyHmac) with a version marker. Verification would then recompute the HMAC first. This protects dormant accounts, but it adds a third format, so I'd only do it if a database leak is a real concern for them.
6. **Tests** (`tests/Conduit.IntegrationTests/Features/Users`):
   - A legacy user logs in, then the stored hash is Identity v3.
   - A wrong password against a legacy hash fails and leaves the row unchanged.
   - A hash below the target iteration count is upgraded.
   - A password change through `Edit` stores a v3 hash.
   - A concurrent double login with a legacy hash doesn't break the account.
7. **Docs.** Add a short note to `docs/database-migrations.md` or the README on the hash formats and the removal criteria.

## Verification

- `dotnet run --project build/build.csproj -- test` (formats, builds in Release, runs all tests).
- Optionally `make test-hurl-with-managed-server` to confirm the RealWorld login contract is unchanged.
- Seed a legacy row, log in through the API, and confirm the row's hash is now the longer Identity payload.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Login CPU cost | PBKDF2 at 210k iterations runs synchronously on the request thread | Rate-limit login, benchmark, keep the count at the OWASP baseline |
| 2 | Legacy rows linger | Dormant users keep the weak HMAC hash with a constant key | Track the count, optionally wrap with PBKDF2 |
| 3 | Rehash write race | Concurrent logins both save the rehash on a tracked entity | Last write wins, both values are valid, add a test |
| 4 | Format misdetection | The 64-byte length check is a fragile heuristic | Check the version byte explicitly, add tests for each format |
| 5 | Email enumeration by timing | An unknown email skips hashing and returns faster | Dummy verify on the not-found path |
| 6 | Rollback breaks users | Old code can't read Identity v3 hashes after upgrades | Deploy forward-only, take a DB backup first |
| 7 | Dual-provider drift | SQLite and SQL Server could store `Hash` differently | Run the integration tests on both providers |
| 8 | Password length DoS | A very long password input makes PBKDF2 slower | Keep a max length in the FluentValidation rules |

Riskiest: #2, because dormant accounts stay on the weak constant-keyed HMAC until someone logs in, and lazy upgrade can't reach them.
