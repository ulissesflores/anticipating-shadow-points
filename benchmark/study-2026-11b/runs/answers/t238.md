## Plan: make `SessionMiddleware` cookies Secure and SameSite=Strict by default

### Context

`starlette/middleware/sessions.py:16-27` currently defaults to `same_site="lax"` and `https_only=False`. The request is to flip both defaults: `same_site="strict"` and `https_only=True`. The constructor already supports both options, so the change is to defaults and docs, not new mechanics.

### Assumptions

- "Secure" means `https_only=True`, which appends `; secure`. I am not adding any auto-detection from `scope["scheme"]`.
- This is a deliberate breaking change to defaults. It needs a release note, and callers can opt out explicitly.
- I'm not changing the `HttpOnly` flag, the cookie format, or the `Literal` type of `same_site`.
- The project's `AI_POLICY.md` applies to the contribution. I haven't read it here, and it needs checking before opening a PR.
- I am not writing the plan file, because you said not to edit any file.

### Steps

1. **Code, `starlette/middleware/sessions.py`.** Change the signature to `same_site: Literal["lax", "strict", "none"] = "strict"` and `https_only: bool = True`. Leave the flag-building logic at lines 34-36 as it is.
2. **Existing tests, `tests/middleware/test_session.py` and `tests/middleware/test_middleware.py:42`.**
   - Most tests use `TestClient` on `http://testserver`. With `secure` set by default, httpx won't send the cookie back over plain HTTP, so session round-trips fail.
   - Use `TestClient(app, base_url="https://testserver")` in those tests, or pass `https_only=False` where the test isn't about the cookie flags.
   - Prefer the `https://` base URL, so the new defaults are what the tests actually exercise.
3. **New tests.**
   - Default `Set-Cookie` contains `secure` and `samesite=strict`.
   - `https_only=False` and `same_site="lax"` still work as opt-outs.
   - The clear-session cookie (`expires=1970`) carries the same flags.
   - The existing `partitioned` and `same_site="none"` test still passes.

   - Update the stated defaults, and rewrite the "Set this to `True` in production" sentence.
   - Add a note on local HTTP development: use `https_only=False`, or use localhost (Chromium and Firefox treat `http://localhost` as a secure context for Secure cookies, Safari does not).
   - Check the `docs/config.md:173-188` example for assumptions about the old defaults.
   - Per `AGENTS.md`, each new heading gets explanatory text before any code snippet.
5. **Release notes, `docs/release-notes.md`.** Add a "Changed" entry that marks the change as breaking and shows the opt-out. Follow the repo's PR-link convention.

### Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Sessions silently stop working over plain HTTP | Browsers drop `Secure` cookies on `http://` (except localhost in some browsers), so existing HTTP deployments, such as behind a TLS-terminating proxy without scheme forwarding, lose sessions with no error | Release note, doc note, and an explicit `https_only=False` opt-out |
| 2 | Strict breaks cross-site login flows | OAuth/OIDC callbacks and links from email or other sites arrive as cross-site navigations, so the cookie isn't sent and the first request looks logged out | Document `same_site="lax"` for these apps |
| 3 | Test suite breaks widely | `TestClient` defaults to `http://testserver`, so the Secure cookie isn't replayed | Switch tests to an `https://` base URL |
| 4 | Behind-proxy scheme confusion | The flag is static, not derived from the request scheme, so a misconfigured proxy still gets `secure` cookies that never round-trip | Document `ProxyHeadersMiddleware` and `--proxy-headers` |
| 5 | Semver and compatibility | Changing security defaults in a minor release surprises downstream frameworks that rely on the defaults | Mark it breaking in the release notes, and consider a deprecation warning before the flip |
| 6 | Partial opt-outs behave unexpectedly | Users who set only `same_site="none"` now also get `secure` by default, which is correct. Users who set `same_site="none"` with `https_only=False` produce a cookie browsers reject | Test the combos, and consider a warning for `none` without `https_only` |
| 7 | Third-party code relies on the defaults | Libraries such as Authlib examples, and FastAPI docs and apps, assume lax and non-secure cookies | Search the docs and examples in this repo, and call it out in the PR |

Riskiest: #1. Sessions silently vanish on plain-HTTP deployments, including proxy setups that don't forward the scheme.
