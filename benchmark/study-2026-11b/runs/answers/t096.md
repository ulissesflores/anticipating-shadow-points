# Plan: "Download my data" export (profile, posts, comments)

I didn't edit any file, including the plan file, as you asked. This is a Flask app (Flasky) with Flask-SQLAlchemy, Flask-Login, and a `main` blueprint for the web UI.

## Assumptions
- **Format:** one JSON file, sent as an attachment (`flasky-<username>-export.json`). JSON keeps the nesting of post → comments and is machine-readable, which suits a data-portability request. A ZIP isn't needed, since everything is text.
- **Scope:** only the logged-in user's own data. No admin "export someone else" feature in this change.
- **Included:**
  - Profile: username, email, name, location, about_me, member_since, last_seen, confirmed, role name.
  - Posts: the user's posts with raw `body` and `timestamp`.
  - Comments: every comment the user wrote, with the `post_id` it belongs to, the `disabled` flag, and the timestamp.
- **Excluded:** `password_hash`, auth tokens, and `body_html`, which is derived and can be regenerated from `body`. Follows and comments received on the user's posts are out of scope unless you want them. I'd offer followers and following as an optional later addition.
- **Size:** synchronous and streamed is fine for a blog-scale app. Only add a background job if row counts turn out to be large.

## Design

1. **Serializer, `app/models.py`.** Add `User.export_data()`. The existing `to_json()` methods are API-shaped. They emit URLs, need `url_for` and a request context, and omit email and `about_me`, so don't reuse them. The new method returns a plain dict. It builds profile fields explicitly from an allow-list, so new columns such as `password_hash` can't leak by default. Datetimes are ISO-8601 in UTC.
   - Posts: `self.posts.order_by(Post.timestamp)`.
   - Comments: `self.comments.order_by(Comment.timestamp)`.
   - Include `exported_at` and a `schema_version: 1` field.
2. **Route, `app/main/views.py`.** Add `GET /user/<username>/export` or `/export`. I'd use `/export`, which is always the current user and has no username parameter to tamper with. Decorate it with `@login_required`. Build the response with `make_response(json.dumps(...))`, plus `Content-Type: application/json` and `Content-Disposition: attachment; filename=...`. Add `Cache-Control: no-store`, because the file contains an email address and private data.
3. **State-changing question.** A GET that only reads is fine and needs no CSRF token. If we later add re-authentication or an emailed link, switch to POST.
4. **UI.**
   - `app/templates/user.html`: next to "Edit Profile", shown only when `user == current_user`, add a "Download my data" button.
   - Optionally also link it from the `edit_profile.html` page.
5. **Unconfirmed users:** `login_required` alone lets them export. Decide whether to match the rest of the site. It's their own data, so I'd allow it.
6. **Abuse control.** The app has no rate limiter today. For v1, rely on the cost being bounded by one user's rows. Note a follow-up for Flask-Limiter if needed.
7. **API (optional, second step).** Add `GET /api/v1/users/me/export` behind the existing `HTTPBasicAuth`/token flow in `app/api/authentication.py`, reusing `export_data()`. Skip it in v1 unless API users need it.

## Tests (follow the existing `tests/test_client.py` and `tests/test_user_model.py` style)
- Model test: `export_data()` contains the expected keys. It has no `password_hash` and no `body_html`. Counts match the user's posts and comments.
- Client test:
  - Anonymous request is redirected to login.
  - Logged-in request returns 200, the attachment header, and valid JSON.
  - Another user's posts and comments are not in the file.
- Edge cases: a user with no posts or comments returns empty lists, and non-ASCII content round-trips.

## Verification
- Run `flask test` or the project's unittest runner, then start the dev server.
- Register two users and create posts and comments for each.
- Download the file as user A and confirm it has only A's data and no secrets.
- Check the `Content-Disposition` and `Cache-Control` headers with `curl -i` using a session cookie.
- Compare the counts in the file with the "N blog posts. N comments." line on the profile page.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Leaking another user's data or secrets | `to_json()` and the model hold `password_hash`, and the export touches email | Allow-list serializer; fixed `/export` route using `current_user`; leak test |
| 2 | Reusing API `to_json()` | It needs `url_for`, omits private fields, and isn't a full export | Separate `export_data()` method |
| 3 | Large exports hog workers | Synchronous request on small Heroku/Docker setups with Gunicorn | Cap by per-user data; stream or go async if sizes grow |
| 4 | Unthrottled repeated downloads | There's no rate limiting in the app | Add a limiter later; a cheap query meanwhile |
| 5 | Sensitive file cached or shared | Export contains email and private text | `Cache-Control: no-store`; HTTPS-only |
| 6 | Datetime and JSON encoding bugs | Naive UTC datetimes and Unicode text | Explicit ISO-8601 strings; `ensure_ascii=False` tests |
| 7 | Incomplete export for GDPR-style expectations | Follows, tokens, and received comments are omitted | Document scope; add a follow-ups list |
| 8 | Session-hijack risk without re-auth | A GET with a stolen cookie yields all personal data | Optional password re-entry or POST confirmation |
| 9 | Deleted or disabled comments handling | `disabled` comments are moderated and may be sensitive | Include the flag; confirm policy |
| 10 | Schema drift breaks the format silently | New columns won't appear in the export | `schema_version`; a test that fails on unreviewed columns |

Riskiest: #1, leaking another user's data or secrets through the export.
