## What exists today

- `src/Conduit/Infrastructure/Security/PasswordHasher.cs` issues ASP.NET Identity v3 hashes (PBKDF2, 210,000 iterations). The payload carries its own salt and parameters.
- It still verifies legacy hashes: exactly 64 bytes of HMAC-SHA512 with the fixed key `"realworld"` and a 16-byte salt. A successful legacy check returns `SuccessRehashNeeded`.
- `Login.cs:79-82` rehashes on successful login. `Create.cs` and `Edit.cs` always write the new format, with `Salt = []`.
- Format detection relies on `hash.Length == 64 && salt.Length == 16`. Everything else is treated as an Identity payload.

## Assumptions

1. The goal is a stronger scheme than the current PBKDF2 setting, or at least to finish the legacy-to-new migration. Candidates are Argon2id or a higher PBKDF2 count.
2. "No forced resets" means verify-then-upgrade on login. Existing hashes stay valid until each user next logs in.
3. The app runs on SQLite and SQL Server through the existing `Hash` and `Salt` byte-array columns, and a schema change is acceptable if needed.
4. The `IPasswordHasher` interface can change, but the RealWorld API contract and its 422 and 401 behaviour must not.

## Ways this could go wrong, before planning

- **Dormant accounts keep the weak hash.** Rehash-on-login never touches users who don't log in, so the unsalted-key HMAC-SHA512 hashes remain in the database indefinitely.
- **Format detection by length is fragile.** A new scheme whose output happens to be 64 bytes with a 16-byte salt would be misread as legacy. Today's `Salt = []` for new hashes is what prevents that collision.
- **A bad rehash can lock users out.** `Login.cs` writes the new hash after verifying. If the save fails, or two requests race, the stored hash could be left inconsistent.
- **Login becomes a DoS lever.** A heavier KDF costs more CPU and memory per attempt, and this endpoint is unauthenticated.
- **New dependency or platform risk.** Argon2 is not in the BCL, so it needs a third-party package. That means lock-file changes, a supply-chain review, and possible native-library issues on the CI and publish targets.
- **Column and migration limits.** A wider hash payload may not fit the existing columns. SQLite and SQL Server need separate migrations and snapshots, and baselining existing databases is documented separately.
- **Rollback is one-way.** Once users are upgraded, older builds can't verify their hashes, so a rollback breaks every upgraded account.
- **Test blind spots.** The tests use SQLite and EF Core InMemory. They won't catch a SQL Server column-length issue or a real legacy-hash fixture mismatch.
- **Leaked parameters or secrets.** The legacy key `"realworld"` is hard-coded. Cost parameters kept in config can drift between instances.
- **Timing and enumeration leaks.** Different code paths for legacy, new and unknown users can leak which accounts exist or which format they use.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Dormant accounts stay weak | Rehash only happens on login | Report remaining legacy rows; optionally wrap them in the new KDF in a batch job |
| 2 | Format detected by length | `64 bytes + 16-byte salt` could match a new format | Add an explicit version prefix or marker column |
| 3 | Failed or racing rehash write | `Login.cs` rewrites the hash after verifying | Compare-and-swap update; keep the old hash on failure |
| 4 | Login CPU/memory DoS | Unauthenticated endpoint with a heavier KDF | Tune cost with benchmarks; add rate limiting |
| 5 | New package or native dependency | Locked restore and CI publish are enforced | Prefer BCL PBKDF2; vet and pin any package |
| 6 | Column size and dual migrations | Two providers with separate snapshots | Check hash length; add migrations for both providers |
| 7 | One-way upgrade breaks rollback | Old builds can't read new hashes | Ship read-compat first, enable writes later |
| 8 | Tests miss real legacy data | No SQL Server tests, synthetic hashes | Add fixtures from real legacy hashes; run a SQL Server check |
| 9 | Hard-coded legacy key and drifting parameters | Fixed `"realworld"` key, per-instance cost | Keep the legacy path verify-only; store parameters inside the hash |
| 10 | Timing and enumeration side channels | Three verify paths with different costs | Run a dummy hash for unknown users; use constant-time compares |

Riskiest: #2, format detection by length, because a wrong guess silently locks out or misverifies existing users.
