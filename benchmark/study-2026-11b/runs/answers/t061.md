Below is the plan for adding email verification to this Remix Blues Stack app. I didn't edit any project files; the full plan is in `claude-home/plans/require-new-users-to-logical-bird.md`.

**Assumptions:**
- Only new users are blocked. The migration marks existing users as verified, using their sign-up date.
- The app sends no email today, so I'd add a small sender that calls an email provider's HTTP API, configured by environment variables. In dev with no API key, it prints the verification link to the console.
- Verification links last 24 hours and work once. Verifying logs the user in automatically.
- Signing up with an email that already has a verified account still shows the current "already exists" error.

**Plan:**

1. **Database**:
   - Add `User.emailVerifiedAt DateTime?`.
   - Add an `EmailVerificationToken` table that stores a SHA-256 hash of each token (never the raw token), its owner and its expiry, and cascades on user delete.
   - In the same migration, run `UPDATE "User" SET "emailVerifiedAt" = "createdAt"` so existing users aren't locked out.
2. **Model layer**:
   - `createUser(..., { verified })`.
   - `createVerificationToken`: 32 random bytes; it deletes the user's older tokens.
   - `consumeVerificationToken`: runs in a transaction, checks expiry, and is single-use.
   - A 60-second resend limit.
   - Replace the password when someone re-registers an unverified email.
3. **Email** (new `app/email.server.ts`): build the link from an `APP_ORIGIN` environment variable, never from the request's Host header.
4. **Routes**:
   - **`/join`**: stops logging the user in. It issues a token, sends the email, and redirects to a "check your inbox" page.
   - **New `/verify-email`**: opening the link shows a **Confirm** button, and verification happens on the button's form submit (POST). There are two reasons:
     - Email link scanners open links with GET and would use up single-use tokens.
     - `server.ts` only forwards non-GET requests to the primary region. A GET that writes to the database from a replica region would hit read-only Postgres.
   - **New `/resend-verification`**: always returns the same generic message, so it doesn't reveal which emails have accounts.
   - **`/login`**: if the password is correct but the email is unverified, refuse the login with "Please verify your email" and offer a resend.
5. **Extra safety check**: `getUser` and `requireUser` treat an unverified user as logged out. A future code path that creates a session by mistake still can't grant access.
6. **Tests and tooling**:
   - Mark the seed user and Cypress's `create-user.ts` as verified, so `cy.login()` keeps working.
   - Add a mock email handler in `mocks/index.js` that captures sent emails to a file. A Cypress script reads the link from it, and the sign-up smoke test becomes: sign up → login refused → verify → land on `/notes`.
   - Add Vitest unit tests for the token logic.
7. **Rollout**:
   - Set the Fly secrets `EMAIL_API_KEY`, `EMAIL_FROM` and `APP_ORIGIN` before deploying.
   - The existing Fly `release_command` runs the migration and backfill before the new code serves traffic.
   - Set up SPF/DKIM for the sending domain.

**Checks after implementing:** `npm run typecheck`, `npm run lint`, `npm test -- --run` and `npm run test:e2e:run`. Then a manual dev pass: sign up, copy the link from the console, confirm login is refused before verifying and works after. Also check that an expired or reused link shows an error, that resends are rate-limited, and that the seeded user still logs in.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New column is null for every current row | Backfill `emailVerifiedAt = createdAt` in the same migration |
| 2 | Verify link fails in replica regions | Only non-GET requests are forwarded to the primary region; replicas use read-only Postgres | Verify on the Confirm button's POST, never on page load |
| 3 | Link scanners use up tokens | Single-use tokens break when a scanner opens the link before the user | Opening the link only shows the page; the button does the write |
| 4 | Account squatting | Someone registers another person's email first and blocks them | Re-registering an unverified email replaces the password and old tokens |
| 5 | Email delivery fails in prod | No email setup exists; missing secrets or SPF/DKIM | Required-env checks, set secrets before deploy, configure the domain |
| 6 | Link poisoning via Host header | Building the URL from the request lets an attacker choose the domain | Use the `APP_ORIGIN` env var only |
| 7 | Email enumeration and resend abuse | The resend endpoint is public | Always the same response, 60s limit per user |
| 8 | Leaked tokens are usable | Raw tokens in the DB or logs can be replayed | Store only hashes, 24h expiry, delete after use |
| 9 | E2E and seed breakage | `cy.login()`, the seed and the sign-up smoke test assume instant login | Create test users as verified; capture emails with the mock handler |
| 10 | Logged-in unverified sessions | Some future path could call `createUserSession` early | `getUser`/`requireUser` reject unverified users |

Riskiest: #2. Verifying on a page load (GET) looks correct in local dev but fails in production replica regions. Even in the primary region, link scanners would use up the tokens.
