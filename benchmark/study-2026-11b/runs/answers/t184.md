I've written the plan to `<config>/plans/make-every-to-do-list-indexed-papert.md`. I edited no repo files and ran no builds or tests. This summary is based on reading the code.

## What the code does today
- `TodoList` and `TodoItem` are shared by everyone. `GetTodosQuery` returns every list.
- The update and delete handlers look rows up by id with `FindAsync([request.Id])`, with no owner check.
- `CreateTodoItemCommand` accepts any `ListId` without checking that the list exists.
- There are no EF migrations. `ApplicationDbContextInitialiser` drops and recreates the database on startup (`EnsureDeletedAsync` then `EnsureCreatedAsync`).
- The current user comes from `IUser`, filled in by `src/Web/Services/CurrentUser.cs` from login claims. The functional tests replace `IUser` with a mock.

## Assumptions
- A tenant is a company, and each user belongs to exactly one tenant, stored as `ApplicationUser.TenantId`. There's no switching between tenants and no admin view across tenants.
- The tenant always comes from the signed-in user, never from the request body or a header.
- All tenants share one database. Isolation is per row, using a `TenantId` column plus an EF filter that's added automatically to every query.
- Building screens or an API to manage tenants is out of scope; tenants are seeded. A user who self-registers has no tenant, sees nothing and can't write until assigned ("fail closed").
- All three database providers (Sqlite, SQL Server, PostgreSQL) must keep working.

## Plan
1. **Domain:**
   - Add a `Tenant` entity and an `ITenantEntity { Guid TenantId }` interface.
   - `TodoList` and `TodoItem` both implement it. Items get their own `TenantId` copy so they're filtered without joining to the list.
2. **Application:**
   - Add `Guid? TenantId` to `IUser`.
   - Add a "list exists" rule to `CreateTodoItemCommandValidator`. Because the query is filtered, another company's list id fails validation.
   - The rule that list titles must be unique becomes per-company automatically.
3. **Infrastructure:**
   - Add `ApplicationUser.TenantId`.
   - A custom claims factory puts a `tenant_id` claim into the login. Register it in both login setups (API-only and the default).
   - In `ApplicationDbContext`, add a filter to every `ITenantEntity`: `e.TenantId == _currentTenantId`. It reads a field on the context so each request uses its own tenant, and a missing tenant matches no rows.
   - Add a foreign key and index on `TenantId`.
   - Add a save hook next to `AuditableEntityInterceptor` that:
     - fills in `TenantId` on new rows;
     - throws if there's no tenant;
     - blocks changing `TenantId`;
     - checks that an item's tenant matches its list's tenant.
   - Seeding creates a default tenant, assigns the admin, sets the tenant on the sample list explicitly, and uses `IgnoreQueryFilters()` for its "already seeded?" check.
4. **Web:** `CurrentUser.TenantId` reads the claim. The API endpoints and the Angular/React clients don't change.
5. **Tests:**
   - Add `TenantId` to the mocked `IUser`, and give the test users a tenant in `TestApp`.
   - Add isolation tests:
     - reading another company's data returns nothing;
     - updating or deleting it returns not-found;
     - adding an item to another company's list fails validation;
     - the same list title is allowed in two companies;
     - a user without a tenant sees nothing and can't create anything.

**How to check it:** build with each database provider, run `dotnet test`, then run the app with two users in different companies and confirm that `GET /api/TodoLists` returns only the caller's own lists.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Filter captures a fixed tenant value | EF builds the model once and caches it, so a tenant value baked into the filter would be reused for every request | Filter reads a field on the context; test with two tenants in a row |
| 2 | Item added to another company's list | `CreateTodoItem` doesn't check `ListId`, and the foreign key alone will accept any list | Validator checks the list exists; save hook checks item and list tenants match |
| 3 | New users have no tenant | The built-in Identity register endpoint knows nothing about tenants | Fail closed (no rows, no writes); add tenant assignment later |
| 4 | Seeding breaks | Startup has no signed-in user, and the filter hides the "already seeded?" check | Set `TenantId` explicitly when seeding; use `IgnoreQueryFilters()` |
| 5 | Existing data is lost or left without a tenant | The startup drop-and-recreate wipes dev data; any real deployment needs a backfill | Backfill script to a default tenant before making the column required |
| 6 | Outdated tenant in the login | The tenant claim stays in the cookie or token until the user signs in again | Document it, or fall back to a database lookup if a user changes company |
| 7 | Tests mock `IUser` | Without a `TenantId`, every functional test sees nothing and fails | Update the mock and `TestApp` first |
| 8 | Raw SQL or `IgnoreQueryFilters` skips the filter | Any query added later that skips the filter leaks across companies | Code-review rule; tests check each handler for leaks |
| 9 | Differences between database providers | The template switches between three databases, and null handling and indexes can differ | Build and test against all three in CI |
| 10 | Overwriting `TenantId` on update | A full-object update could change which company owns a row | Save hook throws if `TenantId` changes; keep it out of DTOs |

Riskiest: #2, adding an item to another company's list. It's the one write path where the filter alone doesn't stop data from crossing between companies.
