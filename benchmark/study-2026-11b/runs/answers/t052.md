# Plan: tenant isolation for to-do lists and items

## Assumptions
- A tenant is a company. Each user belongs to exactly one tenant. Multi-tenant users and tenant switching are out of scope.
- The tenant ID comes from a server-trusted source: a `tenant_id` claim in the user's token, set at registration or login. The client never sends it.
- Shared database and schema, with a `TenantId` column on each row. This fits the template, and per-tenant databases would be heavier.
- Existing data is demo seed data. The initialiser calls `EnsureDeleted` and `EnsureCreated` and there are no EF migrations, so no real backfill is needed. If real data exists, add a migration step.
- Lists and items have no cross-tenant sharing.
- I only read the Domain, Application, Infrastructure and Web service code. I didn't read the test projects or the two frontends in detail.

## What I found
- `TodoList` and `TodoItem` both inherit `BaseAuditableEntity` (`Domain/Common/BaseAuditableEntity.cs`).
- There is no tenant concept anywhere in the code.
- Handlers query `IApplicationDbContext` directly. For example, `GetTodos` reads `_context.TodoLists` with no filter.
- `IUser` exposes only `Id` and `Roles`. `Web/Services/CurrentUser.cs` implements it from the HTTP context.
- `ApplicationUser` is an empty subclass of `IdentityUser`.
- `AuditableEntityInterceptor` is already a hook point for `SaveChanges`.

## Approach
1. **Domain**
   - Add `ITenantEntity { Guid TenantId }` (or `string`).
   - Apply it to `TodoList` and `TodoItem`.
   - The item's tenant must equal its list's tenant.
2. **Identity**
   - Add `TenantId` to `ApplicationUser`.
   - Add a `Tenant` entity, or at least a tenant table or ID, for registration.
   - Put the tenant in a claim when the token or cookie is issued, using a claims-principal factory or the sign-in step.
   - Seed the demo admin and demo data into a default tenant.
3. **Application**
   - Add `TenantId` to `IUser` (or a new `ITenantProvider`), and implement it in `CurrentUser` from the claim.
   - Create handlers need no explicit tenant assignment, because the interceptor sets it.
4. **Infrastructure, defence in depth**
   - Inject the tenant provider into `ApplicationDbContext`.
   - Add a global query filter on `TodoList` and `TodoItem`: `e.TenantId == CurrentTenantId`. Set it in `OnModelCreating`, or in a loop over `ITenantEntity` types.
   - Extend `AuditableEntityInterceptor`, or add a tenant interceptor, to stamp `TenantId` on added entities. Throw if the tenant is missing. Reject modified entities whose `TenantId` changed.
   - Add `TenantId` as the leading column of indexes, and add a composite foreign key from item to list `(TenantId, ListId)`. This prevents an item from pointing at another tenant's list.
5. **Handlers that take client-supplied IDs**
   - `CreateTodoItem` takes `ListId` from the request. Verify the list exists under the filter before inserting, and return `NotFound` if it doesn't.
   - Update and Delete go through the filtered `DbSet`, so another tenant's rows come back as not found.
   - `GetTodos` is filtered automatically through `ProjectTo`.
6. **Out-of-request paths**
   - Domain event handlers, the initialiser, and any background work have no HTTP user.
   - Give them an explicit `IgnoreQueryFilters()` or a scoped "system tenant" context, and make that visible in code review.
7. **Frontends**
   - No UI change if the tenant stays server-side.
   - Regenerate the NSwag clients only if DTOs change. They shouldn't.
   - Registration may need a company field, or an invite flow that assigns the tenant.

## Tests
- Functional tests: create two tenants with two users. Check that each tenant sees only its own lists and items.
- Cross-tenant tests for update, delete, and create-item with the other tenant's `ListId`. Each should return not found.
- A test that a missing tenant claim fails closed.
- Update `FunctionalTestSetup` to run as a user with a tenant.
- Unit-test the interceptor and the filter.

## Verification

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Query filter bypassed | Raw SQL or `IgnoreQueryFilters` would leak across tenants, and handlers hit the DbContext directly | Ban both outside the initialiser, and add a test for each handler |
| 2 | Cross-tenant `ListId` on item create | `CreateTodoItem` trusts the client's `ListId` | Look up the list through the filter, and add a composite FK |
| 3 | Tenant claim missing or spoofable | `CurrentUser` reads claims, and background paths have none | Fail closed, issue the claim only server-side, never read it from the request body |
| 4 | Non-request code paths | The initialiser and domain-event handlers run without an HTTP user | Use an explicit system-tenant scope, and test it |
| 5 | Existing data and schema change | There are no migrations, and init drops the database | Seed a default tenant, and add a real migration if production data exists |
| 6 | Registration and identity flow | Users have no tenant today, and the `.http` and frontend registration pages assume a flat user | Define tenant assignment (invite or company field) before coding |
| 7 | Tenant-change on update | A client could post a changed `TenantId` or reparent an item | The interceptor rejects tenant changes, and DTOs never expose `TenantId` |
| 8 | Test suite breakage | The functional and acceptance tests assume a single user and no tenant | Update the setup first, and keep an explicit two-tenant fixture |
| 9 | Template conditionals | `#if` branches (API-only, React, Angular) multiply the places to change | Change shared layers first, then build each template variant in CI |
| 10 | Unique and lookup performance | Without a `TenantId` index prefix, filtered queries scan | Add composite indexes starting with `TenantId` |

Riskiest: #1, a bypassed query filter, because it silently leaks one company's data to another and no test fails unless you write one.
