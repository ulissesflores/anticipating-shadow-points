**Context:** this is itsdangerous 2.3.0 (not yet released). The digest is used for two things: the HMAC itself, and deriving the key in `Signer.derive_key` (default `django-concat`). Changing the default therefore changes every token signed with default settings. The project has tried this before: 1.0.0 switched the default to SHA-512, was pulled from PyPI, and 1.1.0 reverted it (CHANGES.rst ~L105–125).

**Assumptions:**
- The change goes into the 2.3.0 section of the changelog as a documented breaking change.
- `Serializer` and its timed and URL-safe subclasses get a default SHA-1 fallback, so existing tokens still load.
- Plain `Signer` and `TimestampSigner` have no fallback mechanism, so their old signatures will stop verifying. This gets documented, not worked around.
- `_lazy_sha1` stays, because a test imports it and the fallback needs it.
- I believe Flask passes its own SHA-1 setting for session cookies, so those would be unaffected. I haven't checked this.

**Steps:**
1. **`src/itsdangerous/signer.py`**: change `default_digest_method` to `hashlib.sha256` in both places (`HMACAlgorithm` at L54 and `Signer` at L120). Update the comments and docstrings that say SHA-1 (L51–53, L94–97, L114–118) and add a `versionchanged:: 2.3` note.
2. **`src/itsdangerous/serializer.py`**: set `default_fallback_signers` (L102) to `[{"digest_method": _lazy_sha1}]`.
   - On FIPS builds, which may not include SHA-1, a token that fails SHA-256 would make the fallback raise `ValueError` instead of `BadSignature`. Either catch that in `iter_unsigners`/`loads` and skip the fallback, or only add the fallback when SHA-1 is available.
   - Document how to turn the fallback off (`fallback_signers=[]`) and that it will be removed later.
3. **Tests:**
   - `test_digests`: pin a new SHA-256 expected value.
   - `test_iter_unsigners`: the first signer should be SHA-256, followed by the SHA-1 fallback.
   - `test_fallback_signers`: add a case where an old SHA-1 token loads by default, and one where `fallback_signers=[]` rejects it.
   - `test_timed.py:70`: this token has a hard-coded SHA-1 signature. Regenerate it so the test still checks the "Malformed" error and not just a signature mismatch.
   - Add a test that simulates a missing SHA-1 and expects `BadSignature`.
4. **Docs:** update `docs/concepts.rst` L137–155 and `docs/serializer.rst` L80–105, and add a breaking-change entry to `CHANGES.rst`. Mention that signatures grow from 27 to 43 characters and show how to keep SHA-1.

**How to check it:** run `pytest` and `tox -e typing,style,docs`. Then by hand: take a token made with SHA-1 and confirm it loads with the new default serializer, is rejected when `fallback_signers=[]`, and fails with a plain `Signer`. Optionally, run Flask's test suite against this branch.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing tokens stop verifying | The digest changes both the derived key and the MAC | Default SHA-1 fallback in `Serializer` |
| 2 | Plain `Signer`/`TimestampSigner` tokens break | There is no fallback for them | Clear changelog entry and how to keep SHA-1 |
| 3 | FIPS builds raise `ValueError` on bad tokens | The SHA-1 fallback runs when the SHA-256 check fails | Skip the fallback if SHA-1 is missing; add a test |
| 4 | Repeats the 1.0.0 problem | That release was pulled for this exact kind of change | Put it in the 2.3.0 release notes; keep the fallback |
| 5 | Longer tokens | 27 → 43 characters, which can push cookies or URLs past size limits | Document the increase |
| 6 | Fallback keeps SHA-1 accepted | An attacker can still use the SHA-1 path | Announce removal of the fallback; allow `fallback_signers=[]` |
| 7 | Hard-coded tokens in tests | `test_timed.py:70` and `test_digests` assume SHA-1 | Regenerate the tokens and check the error path |
| 8 | Downstream code relies on the default | Projects other than Flask may not set a digest | Release notes; pin SHA-1 explicitly |
| 9 | Code that imports `_lazy_sha1` or checks the default | `test_iter_unsigners` compares against `_lazy_sha1` | Keep `_lazy_sha1` and update the check |

Riskiest: #1. Every token signed with default settings stops verifying when the new version is deployed (sessions, reset links, timed tokens), unless the SHA-1 fallback is in place, and plain `Signer` tokens have no fallback at all.
