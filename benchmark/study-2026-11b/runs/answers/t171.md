**Context:** In this repo (itsdangerous), both `Signer` and `HMACAlgorithm` use SHA-1 by default (`src/itsdangerous/signer.py:54` and `:120`). The same digest is also used to derive the signing key from the secret (`derive_key`), so changing the default changes both the key and the signature. Version 2.3.0 is unreleased and already contains breaking changes, so it's the natural place for this. The project tried this once before: 1.0.0 switched to SHA-512 and was pulled from PyPI because every existing token stopped working.

**Assumptions:**
- This ships in 2.3.0 (`pyproject` currently says `2.3.0.dev`).
- The new default is `hashlib.sha256`, used directly. The lazy wrapper exists only because SHA-1 can be missing on FIPS systems; SHA-256 is always there.
- Tokens signed with SHA-1 should keep working through `Serializer` without extra setup. Code that calls `Signer` directly gets no automatic fallback, and the docs will say so.

**Steps:**
1. **`signer.py`:** change both defaults to SHA-256. Keep `_lazy_sha1`, because the fallback needs it. Update the docstrings and comments that say "defaults to sha1" and add a `versionchanged:: 2.3` note.
2. **`serializer.py:102`:** set `default_fallback_signers = [{"digest_method": _lazy_sha1}]` so existing SHA-1 tokens still load. On FIPS systems, where calling SHA-1 raises `ValueError`, make loading still raise `BadSignature` for a bad token instead of `ValueError`.
3. **Tests:**
   - `test_digests`: the default should now equal SHA-256, with a fixed expected token. The existing SHA-1 value stays, but under an explicit `sha1` setting.
   - `test_iter_unsigners`: the first signer is now SHA-256, and the SHA-1 fallback is present by default.
   - New: an old SHA-1 token loads with a default serializer, and plain `Signer` rejects it.
   - `test_timed.py:70`: its hard-coded token has a SHA-1 signature. Under SHA-256 the signature check would fail before the "Malformed" timestamp check the test is meant to exercise, so the token needs regenerating.
   - New: with SHA-1 made unavailable (simulating FIPS), signing and loading still work, and a bad token still raises `BadSignature`.
4. **Docs:** regenerate every example token. SHA-256 signatures are 43 characters instead of 27. This affects `README.md:27`, `docs/signer.rst`, `serializer.rst`, `url_safe.rst` and `concepts.rst:77-81`. Rewrite the "Digest Method Security" section (`concepts.rst:137`) and the fallback example (`serializer.rst:97`).
5. **`CHANGES.rst` (2.3.0):** add a breaking-change entry covering the new default, the SHA-1 fallback, longer tokens, and how to keep the old behaviour with `digest_method=hashlib.sha1`.

**Verification:** run `pytest` and the type checkers, and build the docs. Then check by hand that a token made by 2.2.0 loads on the new code, and that everything works with SHA-1 made unavailable.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Every existing token and session stops verifying | The digest feeds both key derivation and the signature, so nothing old matches | Add the SHA-1 fallback by default in `Serializer`; put it in the changelog |
| 2 | Code that calls `Signer` directly breaks with no fallback | Fallbacks only exist in `Serializer` | Document pinning `digest_method=hashlib.sha1`; add a test that shows the rejection |
| 3 | Same rejection as 1.0.0, when the release was pulled | Users read a changed default as a broken release | Ship in 2.3.0 with the fallback and a clear upgrade note |
| 4 | Fallback raises `ValueError` on FIPS systems | `_lazy_sha1` fails when called, and the fallback runs on every bad token | Turn it into `BadSignature` or skip the fallback; test with SHA-1 made unavailable |
| 5 | Longer tokens (27 → 43 characters) | Cookie and URL size limits, plus database columns sized to the old length | Changelog note; users can pin SHA-1 |
| 6 | Mixed versions during a rolling deploy | Old servers can't read SHA-256 tokens from new ones | Document "upgrade readers first" or pin SHA-1 during the rollout |
| 7 | The fallback keeps accepting SHA-1 indefinitely | A SHA-1 token can still be accepted with no end date | Document how to set `fallback_signers=[]`; plan to remove the fallback later |
| 8 | Hard-coded tokens break in tests and docs | `test_timed.py:70`, `test_digests` and the example tokens are all SHA-1 | Regenerate them all; build the docs and run the doc examples |
| 9 | Downstream subclasses change behaviour without notice | Subclasses that inherit `default_digest_method` silently switch to SHA-256 | Call it out in the changelog |
| 10 | Slower loading of bad tokens | Each failed SHA-256 check now also tries SHA-1 | Small cost; accept it and note it |

Riskiest: #1: every existing token and session would stop verifying on upgrade, the same mistake that got 1.0.0 pulled, unless the SHA-1 fallback ships with the change.
