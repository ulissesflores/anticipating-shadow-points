## What's already there

Authors can already change an article's title, and the slug changes with it. `ArticleUpdate` (`articles/routers.go:152-177`) builds a new slug with `makeSlug`, adds `-N` via `makeUniqueSlug` if it collides, and retries if two requests race for the same slug. `TestArticleCreateDuplicateTitleSlugSuffix` covers this.

What's missing is **keeping shared links working**. The old slug is overwritten, and every `/:slug` handler looks articles up with `FindOneArticle(&ArticleModel{Slug: slug})`, so an old link returns 404. Worse, `makeUniqueSlug` only checks `article_models`, so a new article can take a freed slug. Old shared links would then quietly show someone else's article.

## Ways this could go wrong (before planning)

1. **Slug takeover:** a freed old slug goes to a different article, so shared links show the wrong content.
2. **Partial write:** the slug update succeeds but saving the old slug fails, or the reverse. The link breaks, or an alias points nowhere.
3. **Chained renames:** after A→B→C, A must still reach the article, not stop at B or loop.
4. **Rename back to an old slug:** the slug is in both the alias table and the article table, and lookup gets confused.
5. **Writes through old slugs:** PUT, DELETE, favorite or comment on an old slug must hit the same article, with the same author check.
6. **Deleted articles:** soft-deleted rows still occupy the unique index. Their aliases must not resolve to a deleted article, and their slugs must stay reserved.
7. **Spec suite conflict:** the pinned RealWorld hurl/bruno suite may expect 404 on an old slug after a retitle.
8. **Two retitles at once:** both read the same old slug, and one alias is lost or rejected as a duplicate.
9. **Links already broken:** articles retitled before this change kept no history, so those links can't be recovered.
10. **Wrong layer:** a 301 redirect makes the client do a second round trip and may lose the `Authorization` header on PUT/DELETE.

## Assumptions

- Only "don't break links" is new; the existing title → slug behaviour stays as it is.
- The API returns JSON to a single-page frontend, so "links" means `/api/articles/:slug` lookups. I assume a server-side redirect isn't needed.
- An old slug should work like the current one, for reads and writes. The response already carries the current `slug`, so clients can update their own state.
- Old slugs are kept permanently, and deleting an article doesn't free them.

## Plan

1. **Model (`articles/models.go`).** Add `ArticleSlugAlias { gorm.Model; Slug string \`gorm:"uniqueIndex"\`; ArticleID uint }` and register it in `Migrate` (`hello.go:15-22`).
2. **Lookup.** Add `FindArticleBySlug(slug)`. It tries `FindOneArticle` first; if no article is found, it looks up the alias and loads the article by `ArticleID`. It returns the article itself, so chained renames resolve in one step.
3. **Use it everywhere.** Replace the `FindOneArticle(&ArticleModel{Slug: slug})` calls in `routers.go`: Retrieve, Update, Delete, Favorite/Unfavorite, Comment create/list/delete. Change `ArticleDelete` to delete by `articleModel.ID` instead of by the URL slug. The final reload in `ArticleUpdate` should also use the ID.
4. **Reserve old slugs.** Make `makeUniqueSlug` also check the alias table with `Unscoped()`, so old slugs never go to another article.
5. **Save the alias in the same transaction as the update.** When a retitle changes the slug, insert an alias for the old slug and update the article inside one `db.Transaction`. Keep the existing retry on `ErrDuplicatedKey`. If the new slug is one of this article's own old slugs, delete that alias inside the same transaction.
6. **Tests (`articles/unit_test.go`):**
   - after a retitle, GET on the old slug returns 200 and the new slug;
   - A→B→C, then GET on A works;
   - after a retitle, a new article with the original title gets `-2`, not the freed slug;
   - renaming back to an original slug works;
   - PUT on an old slug by a non-author returns 403;
   - after delete, GET on old and new slugs returns 404;
   - DELETE on an old slug removes the right article.
7. **Check:** run `go build ./...`, `go test ./...` and `bash ./scripts/run-spec-tests.sh hurl` (and `bruno`). If the spec suite asserts 404 on old slugs, record that as a deliberate difference from the spec, or put alias lookup behind a setting.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Old slug goes to a new article | `makeUniqueSlug` only checks `article_models` | Also check the alias table (unscoped) |
| 2 | Alias saved but slug not updated, or the reverse | `Update` and the new insert are separate statements today | One transaction for both |
| 3 | Some handlers skip alias lookup | 8+ handlers each call `FindOneArticle` with the slug | One `FindArticleBySlug` used by every handler |
| 4 | DELETE by old slug deletes nothing | `DeleteArticleModel` filters on the URL slug | Delete by `ID` |
| 5 | Renaming back to an old slug collides | That slug is in both tables | Delete the article's own alias in the same transaction |
| 6 | Chained renames break or loop | Aliases might point to slugs, not articles | Aliases store `ArticleID` |
| 7 | Spec suite expects 404 on old slug | Pinned hurl/bruno suite is the source of truth | Run it; document the difference or add a setting |
| 8 | Concurrent retitles lose an alias | Both read the same old slug | Transaction plus unique index; return the error, don't retry blindly |
| 9 | Aliases reach deleted articles | Soft delete leaves rows behind | Normal (scoped) query when loading the article |
| 10 | Earlier links can't be fixed | No slug history exists before this change | Say so in the PR; no backfill possible |

Riskiest: #1, old slugs going to a new article. A shared link would show someone else's content with a 200 and no error, which is worse than the 404 it returns today.
