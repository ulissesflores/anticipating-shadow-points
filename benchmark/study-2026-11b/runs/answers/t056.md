I read the repo but changed nothing, as you asked. The repo is a .NET Clean Architecture template. It uses EF Core with `IdentityDbContext`, MediatR handlers and `TodoList`/`TodoItem` entities. There are no EF migrations folder and no tenant concept yet.

## Assumptions
- A "tenant" is a company. Each user belongs to exactly one tenant, and the tenant ID comes from a claim on the authenticated user.
- Both `TodoList` and `TodoItem` get a `TenantId`, as you asked. Items also inherit it from their list.
- Isolation is enforced in the data layer with EF global query filters, plus a stamp on save. It is not left to each handler.
- A single shared database is used, with a discriminator column. Separate schemas or databases per tenant are out of scope.
- Existing rows are assigned to a default tenant during migration.

## What could go wrong (before planning)
1. **Missed read path.** Queries that bypass the filter, such as `IgnoreQueryFilters`, raw SQL, or `ProjectTo` against a different context, would leak data across companies.
2. **Item and list tenant mismatch.** An item could point at a list from another tenant, for example `CreateTodoItem` with a foreign `ListId`. The same applies to `UpdateTodoItem` and `DeleteTodoItem` by ID.
3. **Missing tenant at write time.** Without a stamp on insert, rows get a null or default tenant and become invisible or shared.
4. **Backfill of existing data.** A non-null column added to populated tables fails, or silently puts everyone in one tenant.
5. **Missing or spoofed tenant claim.** The tenant could be absent from the token, taken from a client header, or lost in background jobs, the seeder and domain event handlers (`LogTodoItemCompleted`), which run without an HTTP user.
6. **Tests and seeding break.** The functional tests and `ApplicationDbContextInitialiser` assume a single global dataset.
7. **Cross-tenant ID guessing.** Some endpoints return 403 where they should return 404, which reveals that an ID exists.
8. **Performance.** Without `TenantId` in indexes, every query gets slower.
9. **Frontend and DTO drift.** The Angular and React clients might need tenant context, or might show empty lists after the change.
10. **Schema management.** There is no migrations folder, so schema changes depend on how the database is created, such as `EnsureCreated` or a custom flow.

## Plan (high level, not executed)
1. Add `ITenantEntity` with a `TenantId` property, and an `ITenantProvider` or an extension of `IUser` that reads the tenant claim.
2. Implement the tenant provider in `Web`, and add a tenant claim in Identity.
3. In `ApplicationDbContext`, apply a global query filter to every `ITenantEntity`. Add the stamp in the existing `Interceptors` folder, and fail the save if the tenant is missing.
4. Update the `TodoList` and `TodoItem` configurations with `TenantId` required, indexed and composite where useful.
5. Add a guard in the item handlers that checks the parent list belongs to the same tenant.
6. Migrate the schema and backfill existing rows to a default tenant, then seed per-tenant data.
7. Add functional tests with two tenants for list, get, update and delete, using both lists and items.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Filter bypassed | Handlers use `_context` directly, so one raw query leaks data | Global filter, grep for `IgnoreQueryFilters` and raw SQL, test both tenants |
| 2 | Item/list tenant mismatch | `CreateTodoItem` takes a `ListId` from the client | Check the list's tenant in the handler; add a composite FK |
| 3 | Tenant not stamped on save | Rows saved without a tenant vanish or are shared | Save interceptor that stamps and rejects an empty tenant |
| 4 | Backfill of existing rows | A non-null column on populated tables fails or merges everyone | Add as nullable, backfill, then make required |
| 5 | Tenant claim missing or spoofed | The user has only `Id` and `Roles` today; background code has no HTTP user | Take the tenant only from the validated token; explicit scope for jobs |
| 6 | Seeder and tests break | They assume one global dataset | Update the initialiser; add a two-tenant test fixture |
| 7 | 403 vs 404 leaks IDs | Fetching by ID across tenants reveals that it exists | Filter first so other tenants' IDs return 404 |
| 8 | Slow queries | Every query gains a `TenantId` predicate | Index `TenantId` and composite keys |
| 9 | Frontend or DTO breakage | Angular and React clients may rely on current payloads | Keep DTOs unchanged and smoke-test both UIs |
| 10 | Schema change process unclear | No migrations folder exists | Confirm how the schema is created before changing it |

Riskiest: #1, a query path that skips the tenant filter, because it leaks one company's data to another without any error.
