I wrote a plan to make the default lockout key the username and IP address together. The plan is saved at `claude-home/plans/lock-users-out-by-zany-star.md`. No repo files were edited and no tests were run.

## Why
When nothing is configured, Axes locks out by IP address alone (`axes/conf.py:51` sets `["ip_address"]`). So one user's failed logins block everyone behind the same NAT or proxy. The new default would lock only that username from that IP.

## Assumptions
- The new default is the combined form `[["username", "ip_address"]]`. It is not `["username", "ip_address"]`, which locks out by either one.
- Only the "nothing configured" fallback changes. An explicit `AXES_LOCKOUT_PARAMETERS` and the old flags (`AXES_ONLY_USER_FAILURES`, `AXES_LOCK_OUT_BY_*`, `AXES_USE_USER_AGENT`) keep their current meaning.
- No database migration is needed, because each attempt record already stores username, IP and user agent.
- This is a breaking change, so it ships in the next major version (10.0.0), with an entry under "Breaking changes" in the changelog.

## Steps
1. **`axes/conf.py:37-51`**: change the fallback to `[["username", "ip_address"]]` and fix the outdated comment on line 38. Check that the `AXES_USE_USER_AGENT` branch still works, since `[0]` is now a list and gets `user_agent` appended. Building a new list there is safer than changing one in place.
2. **`axes/checks.py:180`**: no change needed. The check that IP address is among the lockout parameters already passes when the IP is inside a combination. Optionally, add an info-level check that tells people upgrading without the setting that the default has changed.
3. **Handlers** (`axes/handlers/database.py:180`, `axes/handlers/cache.py:82`): they only special-case `["username"]` when the username is missing. With the combined default, attempts without a username are stored with an empty username for that IP. The cache key in `make_cache_key_list` (`axes/helpers.py`) skips empty values, so that key becomes a hash of the IP alone. Pin this behaviour with tests.
4. **`axes/utils.py:33` `reset_request`**: with the combined default, a reset needs both IP and username, so a reset by IP alone now silently returns 0. Either document this or let an IP-only reset clear every username for that IP.
5. **Docs**:
   - Update the default value in `docs/4_configuration.rst:93`.
   - In the upgrade list in `docs/2_installation.rst:160`, add how to keep the old behaviour.
   - Reword `docs/5_customization.rst:181`.
   - Update the reset examples in `docs/3_usage.rst`.
   - Add a changelog entry that gives the opt-out: `AXES_LOCKOUT_PARAMETERS = ["ip_address"]`.
6. **Existing tests**: tests in `test_login.py`, `test_handlers.py`, `test_attempts.py` and `test_management.py` likely assume the IP-only default. I haven't confirmed which ones. Pin those tests to `["ip_address"]` or change what they expect.
7. **New tests for the new default**:
   - The same user from the same IP is locked out at the limit.
   - A different user from the same IP is not locked out.
   - The same user from a different IP is not locked out.
   - Attempts without a username, `reset_request`, the old user-agent flag, and no W006 warning.
   - Because `conf.py` runs only once at import, these tests need to reload it or move the default logic into a function they can call.

## Verification
- Run the full `pytest` suite, plus tox across the supported Django versions, mypy and ruff.
- Manual check: run the test project, fail 10 logins as user A from one IP, then confirm A is locked out and user B can still log in from that IP.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Weaker protection against trying many usernames from one IP (password spraying, credential stuffing) | Each new username from an IP starts at 0 failures, so one IP can try 9 passwords on every account | Changelog security note; document `["ip_address", ["username","ip_address"]]` as a stronger option |
| 2 | Sites that set nothing change behaviour silently on upgrade | `conf.py` changes the fallback without any warning | Major version bump; info-level check when the setting isn't set; opt-out snippet in the docs |
| 3 | Many existing tests break | The suite assumes IP-only lockout | Pin those tests to `["ip_address"]` and add new tests for the default |
| 4 | Reset by IP alone stops working | `reset_request` requires both IP and username for a combination | Document it, or let an IP-only reset clear every username for that IP |
| 5 | Attempts without a username fall back to keying by IP | Lookups store an empty username; the cache key becomes a hash of the IP | Add tests; mention it in the docs |
| 6 | Old user-agent flag now appends to a nested list | `conf.py:54-60` changes `[0]` in place | Build a new list and add a test |
| 7 | Tests for the new default can't see it | `conf.py` applies the default once, at import | Move the default logic into a function and test that |
| 8 | Lockout records from before the upgrade no longer match | Records made under IP-only rules have different usernames | Release note: expect failure counts to effectively reset |

Riskiest: #1, the weaker protection against trying many usernames from one IP, because the new default leaves no per-IP failure limit.
