I changed nothing. This is a Remix + Prisma + Postgres app (the Blues Stack template). Email and password login goes through `verifyLogin` in `app/models/user.server.ts` and `app/routes/login.tsx`. `app/routes/join.tsx` signs users in immediately. The repo has no mailer.

## Assumptions
- "New users" means accounts created after this ships. Existing users are grandfathered in by a backfill.
- Verification uses a single-use, expiring token emailed as a link.
- I'd use a transactional email provider, such as Resend, Postmark or SES, configured through env vars.
- Signup stops creating a session. Login rejects unverified users and offers a resend.
- `createUserSession` stays the only place that sets the cookie.
- Email is the only identity. There's no OAuth.

## Ways this could go wrong
- **Existing users get locked out.** A new `emailVerifiedAt` column would be null for everyone, so a naive check blocks all current accounts.
- **A path bypasses the check.** `join` calls `createUserSession` directly. `getUserId` trusts any valid cookie, so sessions created before deploy stay valid. `cypress/support/create-user.ts` also mints sessions without verification.
- **Token flaws.** Tokens that are guessable, reusable, stored in plaintext, never expiring, or not tied to the email at issue time. A changed email must invalidate old tokens.
- **User enumeration.** The login error "not verified" reveals that an account exists. Resend and join responses can leak it in the same way.
- **Delivery failures.** There's no mail infrastructure in the repo. Missing SPF/DKIM puts mail in spam, and a provider outage or a send error during signup leaves a user stuck. Sending inline also slows the request.
- **Abuse.** The resend endpoint can be used to spam victims or run up provider costs. There's no rate limiting today.
- **Tests and mocks break.** Cypress e2e flows, `prisma/seed.ts` and the MSW mocks assume instant login. They need a test-only verification path that can't reach production.
- **Migration and deploy order.** The code and the schema change land at different times on Fly. If the code ships before the migration, queries fail. The backfill must run before the check is enforced.
- **Verification link flaws.** Open redirects through `redirectTo`, link prefetchers or email scanners consuming a one-time token, and links built from a wrong or spoofable host.
- **Typo'd emails strand accounts.** A user who mistypes their address can never verify, and the unique constraint blocks re-registering with the right one.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New nullable column is null for all current rows | Backfill `emailVerifiedAt` in the migration; enforce only after |
| 2 | Verification bypass | `join` and `create-user.ts` create sessions directly | Gate inside `createUserSession` or `verifyLogin`; remove the join auto-login |
| 3 | Weak or reusable tokens | Hand-rolled tokens are easy to get wrong | Random 32-byte token, hash it in the DB, short expiry, single use |
| 4 | Account enumeration | Distinct "unverified" and resend responses | Uniform messages; resend always returns the same reply |
| 5 | Email not delivered | No mailer exists; deliverability is unconfigured | Add a provider with SPF/DKIM; send async with retry; log failures |
| 6 | Resend abuse | No rate limiting in the app | Per-email and per-IP throttle with a cooldown |
| 7 | Tests and seeds break | Cypress, seed and mocks expect instant login | Test-only verified fixtures; mock the mailer in MSW |
| 8 | Deploy ordering | Migration and code ship separately on Fly | Backward-compatible two-step migration; backfill before enforcing |
| 9 | Scanners burn tokens | Prefetch GET consumes a one-time link | Confirm via a POST button on the landing page |
| 10 | Typo'd email strands users | Unique email blocks re-signup | Let unverified accounts re-register; purge stale ones |

Riskiest: #2, a verification bypass. A path that creates a session without the check silently defeats the whole feature.
