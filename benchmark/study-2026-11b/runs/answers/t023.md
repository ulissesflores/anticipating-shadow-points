I've written the plan but changed no code. The core problem is that a visit today has only a date and a description, with no vet and no time, so a clash between two bookings can't even be detected yet. The plan adds a vet and a fixed time slot to each visit, and lets a database unique rule on (vet, date, time) block double bookings, including two requests arriving at the same moment.

**Assumptions** (non-interactive run, so I chose instead of asking):
- **"Online" means the existing web form** at `/owners/{id}/pets/{petId}/visits/new`. The app has no login, and adding one is out of scope (it's listed as a risk below).
- **Fixed 30-minute slots, 09:00–17:00**, set through configuration. Each visit takes exactly one slot, so "same vet, same time" just means "same vet, date and start slot".
- **Old visits are left without a vet or time.** Empty values never count as a clash, so they don't block anything.
- **The server's clock and time zone decide what counts as "today" and "past"**, as the current form already does.
- **The demo databases get rebuilt from scratch**, so existing MySQL/Postgres databases need a one-off manual update.

**Steps:**
1. **Schema** (all three `db/*/schema.sql` files): add `vet_id` (linked to `vets`) and `start_time` to `visits`, plus the unique rule on (vet, date, start time). Postgres gets an add-if-missing update for databases that already exist; MySQL gets a written manual step.
2. **Seed data**: the H2 and MySQL `data.sql` files insert visits without naming columns, which will break once columns are added. Name the columns explicitly.
3. **`Visit.java`**: add the vet and start time. In `Pet.java`, sort visits by date, then time. The vet name has to be loaded with the visit, because pages render after the database session closes here.
4. **Repositories**: add a lookup for a single vet, and a new `VisitRepository` that lists a vet's booked times for a day (to show free slots and check before saving).
5. **New `VisitBookingService`**: check the slot is on the grid, within hours and in the future; check it's free; save; and turn a unique-rule error into a "slot taken" error. That database rule is what actually prevents double booking. The check before saving only gives a nicer message.
6. **`VisitController`**: provide the vet list and slot list to the form, and show "slot taken" next to the time field when the save is rejected. The existing date and description checks stay.
7. **Templates**: vet and time dropdowns on the booking form, and Vet and Time columns in visit history and on the owner page.
8. **Translations**: new labels and error messages go into every `messages*.properties` file, because an existing test fails if any language file is missing a key.

**Verification:**
- Controller tests for the success, slot-taken, missing-vet, off-grid-time and past-date cases.
- A database test that two identical bookings are rejected while two old visits with no vet are still accepted.
- A test where two threads book the same slot at once and exactly one succeeds.
- The MySQL and Postgres integration tests, so all three schemas are exercised.
- `./mvnw verify`, then booking the same vet and slot twice by hand.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Two simultaneous bookings both succeed | Today it's check-then-insert with no lock | Unique rule on (vet, date, start time); turn its error into a form error |
| 2 | Existing MySQL/Postgres databases never get the new columns | Setup scripts skip tables that already exist, and there's no migration tool | Add-if-missing update for Postgres; manual step for MySQL (or adopt Flyway) |
| 3 | Seed data fails to load | H2/MySQL insert visits without naming columns | Name the columns |
| 4 | Anyone can book for any owner | No login; owner id is just in the URL | Say so clearly; add login and ownership checks as a follow-up |
| 5 | Off-grid times (e.g. 09:10) dodge the unique rule | It only matches exact start times | Accept only grid times and pick them from a list |
| 6 | Vet name fails to load when the page renders | Pages render after the database session closes | Load the vet together with the visit |
| 7 | Old visits with no vet behave oddly | Empty values never clash, and the forms must handle a missing vet/time | Keep the fields optional for old rows; require them only for new bookings |
| 8 | Translation test fails | It requires every language file to have the same keys | Add each new key to all `messages*.properties` |
| 9 | Wrong "today" near midnight | Server time zone is used | Configure the clinic's time zone explicitly |
| 10 | Some deleted vets lose their visit links | `vet_id` links to the vets table | Never hard-delete vets that have visits (or soft-delete them) |

Riskiest: #2 — on an existing MySQL/Postgres database the new columns and unique rule are never created, so double bookings stay possible or saving fails, with nothing obviously wrong at startup.
