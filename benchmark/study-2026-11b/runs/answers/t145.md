**Assumptions** (non-interactive run, so I haven't asked): "stronger" means stronger than the old HMAC hashes. The PBKDF2 scheme already in use is acceptable, so I'm not switching to Argon2, which would add a third-party package. The API contract stays the same.

## What already exists (added in a51468c, "modernize (#152)")
- **New hashes:** `src/Conduit/Infrastructure/Security/PasswordHasher.cs` creates ASP.NET Identity V3 hashes (PBKDF2-HMAC-SHA512, 210,000 iterations). Each hash carries its own random salt inside it, so `Person.Salt` is stored empty.
- **Old hashes still work:** the old format (a 64-byte HMAC-SHA512 with the hard-coded key `"realworld"` and a 16-byte salt) is checked but never created. A correct password returns `SuccessRehashNeeded`.
- **Upgrade on login:** `src/Conduit/Features<home>:79-84` rewrites the hash after a successful login. `Create.cs` and `Edit.cs` always write the new format.
- **Tests:** `PasswordHashingTests.cs` covers the upgrade, including that a failed login doesn't upgrade.
- **No migration needed:** the `Hash` column is BLOB / `varbinary(max)` in both providers.

## Ways this change could go wrong
1. Users who never log in keep the weak HMAC hash forever, and that key is public in the source.
2. Telling the formats apart by byte length breaks if a new format ever ends up 64 bytes long.
3. A bug in the old-format check or the upgrade write locks out existing users, which is exactly what the request rules out.
4. An upgrade that runs twice could hash an already-upgraded hash again and make it unverifiable.
5. More iterations add CPU cost to every login, which makes the endpoint easier to overload.
6. Two logins at once both rewrite the hash. That's harmless, but a failed save must not fail the login.
7. Rolling back to an older build that can't read the new format locks out every upgraded user.
8. Login returns faster when the email doesn't exist, which reveals which accounts exist. This was there before and isn't made worse.

## Recommended next step (optional)
**Wrap the dormant old hashes:** run PBKDF2 over each stored HMAC value in a one-time pass that can safely run more than once. Mark the result with a version byte rather than relying on length. On login, recompute the HMAC from the password and check it against the wrapped value, then upgrade the row to a normal Identity hash. That removes weak hashes from the database without anyone resetting a password.

**Tests to add:**
- A wrapped hash verifies, rejects a wrong password, and upgrades on login.
- Running the wrapping pass twice changes nothing the second time.
- A hash with a lower iteration count is flagged and rewritten.
- Changing the password through `Edit` writes the new format.

**Validation:** `dotnet run --project build/build.csproj -- test`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Dormant old hashes stay weak | Upgrade only happens on login; HMAC key `"realworld"` is in the source | Wrap them in a one-time pass |
| 2 | Format detected by length | `Hash.Length == 64 && Salt.Length == 16` decides the path | Add a version byte to wrapped hashes |
| 3 | Lockout from an upgrade bug | No reset flow; users can't recover | Tests for each format, including wrong password |
| 4 | Upgrade runs twice and corrupts hashes | A startup or batch task may run again | Only touch rows without the marker; test running it twice |
| 5 | Login CPU cost | 210k PBKDF2 iterations on every login | Rate-limit login; keep iteration count set in one place |
| 6 | Rollback locks users out | Old builds can't read Identity hashes | Don't roll back past #152; keep the old-format check |
| 7 | Concurrent upgrade writes | Two logins at once both save | Rewrite is idempotent; failed save shouldn't fail login |
| 8 | Email enumeration by timing | Unknown email returns before any hashing | Verify against a dummy hash when the email isn't found |

Riskiest: #3, a bug in the old-format check or upgrade path that locks existing users out, since there's no reset flow to recover them.
