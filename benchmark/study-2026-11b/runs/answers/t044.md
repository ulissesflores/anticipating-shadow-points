This is `express-session` 1.19.0. I made no edits, as you asked.

**Assumptions**
- "By default" means that when `rolling` is undefined, it behaves as `true`. An explicit `rolling: false` still opts out.
- The change is `index.js:109`, from `Boolean(opts.rolling)` to `opts.rolling === undefined ? true : Boolean(opts.rolling)`. I'd also update the `rolling` section of `README.md` and the tests in `test/session.js`, around line 1158.
- This is a library, so the change reaches every downstream user. I assume it's shipped as a semver-major release, or behind an explicit decision to break the default.

**What could go wrong, before planning**
1. **Silent behavior change for all users.** Apps that never set `rolling` start getting a `Set-Cookie` on every response. Nothing in their code or config changes, so they get no warning.
2. **Absolute timeouts break.** Some apps use `maxAge` as a hard cap, for example a session that must end 30 minutes after login. With rolling, an active user never expires, which is a compliance and security regression.
3. **Caching and CDNs.** A `Set-Cookie` on every response can make shared caches skip caching, or leak or strip cookies. Cache rules that assumed the cookie was rare may stop working.
4. **Store load.** In `index.js`, `shouldTouch` and `touch` run on every request for existing sessions. For stores without `touch` and with `resave: true`, that means a full write per request. Redis and DB stores get more write traffic.
5. **Concurrent requests.** Parallel requests each refresh the expiry, and last-writer-wins races on the store become more frequent.
6. **Interaction with `saveUninitialized: false`.** Rolling only applies to existing sessions, so users may expect the cookie on every response and still not get it for uninitialized ones. The README note covers this, but the behavior is easy to misread.
7. **Session-only cookies.** If `cookie.maxAge` is unset, there is no `expires`, so rolling gives no benefit but still adds the header on every response.
8. **Tests and docs.** Existing tests that assert "no `Set-Cookie` on a second request" will fail, and the README's default of `false` becomes wrong.
9. **Static assets and health checks.** Requests that carry a session cookie but aren't real user activity, like polling, probes, and image loads, will keep sessions alive indefinitely.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Silent default flip | `index.js:109` affects every consumer without a code change | Ship as a major version, with a changelog and migration note |
| 2 | Hard session cap lost | `maxAge` was an absolute cap and now slides forever | Document how to opt out with `rolling: false`; suggest an absolute-lifetime check |
| 3 | Cache and CDN breakage | `shouldSetCookie` returns true on every response | Note in the docs; advise cache rules that ignore `Set-Cookie` or skip static routes |
| 4 | Store write amplification | `touch` or `save` fires on every request | Recommend stores that implement `touch`; load-test a Redis store |
| 5 | Concurrent write races | Parallel requests each refresh the expiry | Prefer `touch`, which doesn't rewrite session data; add a test with parallel requests |
| 6 | Misread `saveUninitialized` interaction | Uninitialized sessions still get no cookie | Keep the README note; add a test |
| 7 | Pointless header with no `maxAge` | Session-only cookies get no benefit from rolling | Skip setting the cookie when no `expires` or `maxAge` exists |
| 8 | Test and doc drift | Tests near `test/session.js:1158` assume the default is false | Update the tests and the README default text, and add a default-true test |
| 9 | Non-user traffic keeps sessions alive | Probes and assets refresh the expiry | Advise mounting the session middleware after static routes and health checks |

Riskiest: #1, the silent default flip, because it changes security-relevant behavior for every consumer, including the absolute-timeout case in #2, with no code change on their side.
