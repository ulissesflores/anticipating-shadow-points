This is a Remix "Blues Stack" app with Prisma on Postgres. I read the code and changed nothing.

## Assumptions
- "New users" means accounts created after this ships. Existing users are grandfathered with a backfill.
- There is no email provider in the repo, so I'd add one behind an env var (SMTP or an API) and mock it in `mocks/`.
- Verification is a single-use, hashed, expiring token sent by link. Login is blocked until it is used.
- `/join` stops creating a session. It shows "check your inbox" and offers a resend.
- The unverified-login message must not reveal whether an email is registered.

## What I found
- `app/routes/join.tsx` calls `createUserSession` right after `createUser`, so signup logs the user straight in.
- `verifyLogin` in `app/models/user.server.ts` has no verified check. `login.tsx` also calls `createUserSession` directly.
- `prisma/schema.prisma` has no verified field or token model. There is one migration, and the server has no mailer.
- `seed.ts` and `cypress/support/create-user.ts` call `createUser` and expect a usable user. The smoke e2e test signs up and expects to be logged in.
- Sessions use `userId` in a cookie, and `requireUserId` only checks that it exists.

## Ways this could go wrong
1. **Existing users get locked out.** A new non-null `emailVerified` column would be false for everyone already in the database.
2. **Existing sessions bypass the gate.** Cookies issued before the change keep working, and `requireUserId` never checks verification.
3. **A gap in the gate.** Only login gets checked, but `/join` also auto-logs in, and the password-session helper is called from two places.
4. **Email never arrives.** There is no provider, and spam filtering and deliverability are unproven. Users get stuck with no way back in.
5. **Weak or reusable tokens.** Tokens could be guessable, stored in plaintext, never expire, or be reusable.
6. **Account enumeration.** The existing "email already exists" error on `/join` and a distinct "unverified" login error both reveal which emails are registered.
7. **Email abuse.** An unthrottled resend endpoint can be used to spam victims or run up costs.
8. **Squatting on unverified emails.** A stranger could register someone else's email, then block the real owner at `/join` with "already exists."
9. **Tests, seed and CI break.** The seed user, `create-user.ts` and the Cypress smoke test all assume instant login. No inbox is available in CI.
10. **Migration and deploy ordering.** The Fly deploy runs migrations. If the code goes out before the backfill finishes, or the migration fails midway, users get locked out.
11. **Links break in production.** If the verification link is built from the request host or a missing `APP_URL`, it points to the wrong host behind Fly's proxy. Email scanners that prefetch links can also consume a one-time token.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New column defaults to unverified for every current row | Migration backfills existing users as verified |
| 2 | Old sessions skip the gate | `requireUserId` only checks that a `userId` exists | Check verified status in `requireUser`, or rotate `SESSION_SECRET` |
| 3 | Gate has a gap | `join.tsx` and `login.tsx` both call `createUserSession` | Enforce the check in `createUserSession` or one shared helper |
| 4 | Verification email not delivered | No mailer or provider exists in the repo | Add a provider with env config, a resend flow and logging; mock in dev |
| 5 | Weak or reusable tokens | Tokens are new and nothing validates them yet | Use random 32 bytes, store a hash, expire in about 24h, single use |
| 6 | Account enumeration | `/join` already says "user already exists" | Use generic messages and the same response for new and existing emails |
| 7 | Email abuse via resend | Public endpoint, no rate limiting in the app | Add per-email and per-IP throttling and a cooldown |
| 8 | Unverified squatting | Unique `email` blocks the real owner | Expire or overwrite stale unverified accounts |
| 9 | Tests and seed break | Seed, `create-user.ts` and the smoke test assume instant login | Add a verified option to `createUser` and update the tests |
| 10 | Deploy and migration ordering | The Fly deploy runs the migration against live data | Make it two-step and additive; verify the backfill before enforcing |

Riskiest: #1, existing users locked out. An unbackfilled non-null column would block every current user on deploy, and #2 means the gate silently fails to apply to old sessions.
