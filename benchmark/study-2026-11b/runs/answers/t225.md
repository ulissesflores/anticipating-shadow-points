# Plan: default signing digest SHA-1 → SHA-256 (itsdangerous)

I didn't write a plan file, because you said not to edit any file.

## Assumptions
- This is the `itsdangerous` library. `src/itsdangerous/signer.py` holds the default in two places:
  - `Signer.default_digest_method`, set to `_lazy_sha1`.
  - `HMACAlgorithm.default_digest_method`, set to `_lazy_sha1`.
- You want a library-level default change that ships in a major release. Callers who don't pass `digest_method` get SHA-256.
- Tokens already issued under SHA-1 should keep verifying during a transition.
- Python 3.9 or later is supported, so `hashlib.sha256` is always available.

## Findings
- `_lazy_sha1` exists so FIPS builds without SHA-1 don't fail on import. SHA-256 is FIPS-safe, so the lazy wrapper isn't needed for it. A plain `hashlib.sha256` is enough.
- The default digest also feeds key derivation, not only the HMAC. `derive_key` uses `digest_method(salt + secret_key)` for `django-concat` and `concat`. With the default `hmac` derivation it uses the digest as the HMAC digestmod. Changing the default therefore changes both the derived key and the signature length. Every existing signature stops verifying.
- Signature length grows from 20 to 32 bytes, so base64 output grows from 27 to 43 characters. Tokens get about 16 characters longer.
- `Serializer` already supports `fallback_signers`, and `docs/serializer.rst` documents a SHA-512 to SHA-1 rotation example. That is the migration path.

## Steps
1. **`signer.py`**
   - Change both `default_digest_method` attributes to `hashlib.sha256`, wrapped in `staticmethod`.
   - Rename or replace `_lazy_sha1`. It is imported by `tests/test_itsdangerous/test_serializer.py`, so keep a lazy `_lazy_sha256` only if import-time hashlib access is a concern.
   - Update the docstrings that say "defaults to SHA1".
2. **Backward-compatibility hook.** Document `Serializer(..., fallback_signers=[{"digest_method": hashlib.sha1}])` as the migration recipe. Consider adding a one-release `DeprecationWarning` on the old default before flipping it, if you want a softer path.
3. **Tests**
   - `test_serializer.py`: update `test_digests`. It currently asserts that the default equals the SHA-1 value `"[42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM"`. The default should now equal the SHA-256 value, and the SHA-1 value should stay as an explicit case.
   - `test_serializer.py`: change `assert next(unsigners).digest_method == _lazy_sha1` to the new default.
   - Add a test that a token signed with explicit SHA-1 still loads through `fallback_signers` under the new default.
   - Add a test that the default signature is 32 bytes.
   - Check the timed and URL-safe tests for hardcoded SHA-1 tokens.
4. **Docs and changelog**
   - `docs/signer.rst`, `docs/serializer.rst`, `docs/concepts.rst`: update mentions of the default and the rotation example.
   - `CHANGES.rst`: add a "Breaking" entry that states the default change, the longer tokens, and the fallback recipe.
5. **Release.** Make this a major version bump in `pyproject.toml`, with the changelog entry above.

## Verification
- Run `uv run pytest`, then the type check and lint config in `pyproject.toml`.
- Round-trip test: sign with the old default (explicit SHA-1), then load with the new default plus a fallback. Loading without the fallback should raise `BadSignature`.
- Print token length before and after.
- Check import on a FIPS-like environment by monkeypatching `hashlib.sha1` to raise.
- Run the downstream suites, for example Flask sessions, if reachable.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | All existing tokens fail verification | The default affects both key derivation and the HMAC, so old signatures are invalid | Document `fallback_signers` with SHA-1; major version bump |
| 2 | Users logged out or links broken at deploy | Sessions, reset links and confirmation emails use default signers | Roll out with the fallback first, then drop it after tokens expire |
| 3 | Longer tokens exceed limits | Signature goes from 27 to 43 base64 characters | Note it in the changelog; check cookie and URL length budgets |
| 4 | Mixed-version deployments disagree | Old and new app instances sign and verify differently during rollout | Deploy the fallback-capable version everywhere before flipping the default |
| 5 | Tests with hardcoded SHA-1 vectors fail | `test_digests` and the `_lazy_sha1` import assume the old default | Update expected values; keep explicit SHA-1 cases |
| 6 | Downstream libraries pin on the default | Flask and other consumers rely on `Signer` defaults or subclass it | Pre-release and notify; test against major consumers |
| 7 | Custom subclasses overriding `default_digest_method` | Subclasses that set it explicitly won't change, so behaviour diverges | Document that explicit overrides are unaffected |
| 8 | Silent half-migration | SHA-1 fallback left enabled indefinitely keeps the weak digest accepted | Set a removal date for the fallback; add a deprecation warning |

Riskiest: #1. Every token signed under the old default stops verifying, because the derived key changes along with the HMAC digest.
