# Plan: let users download their own data

The plan file is at `claude-home/plans/let-every-user-download-moonlit-fountain.md`. No files in the repo were changed.

## Context
Flasky runs on Flask 0.12 and SQLAlchemy 1.1, with Flask-Login session auth. A user currently has no way to take their data with them. After this change, a logged-in user clicks one button on their own profile page and gets one JSON file with their profile, all their posts and all their comments.

## Assumptions
- **Format:** one JSON file, downloaded as `flasky-<username>-<YYYYMMDD>.json`. It is built in the request; there is no background job and no ZIP.
- **Whose data:** only the logged-in user's (`current_user`). The URL has no username or id in it, and there is no admin "export someone else" option.
- **What's included:** profile, posts and comments. Follower and following lists are left out.
- **Other people's comments:** comments that others left on the user's posts are not included, because that is their data. Each post only gets a `comment_count`.
- **Hidden comments:** comments a moderator disabled are still included, marked `"disabled": true`, because they are still the user's data.
- **Unconfirmed accounts:** the existing hook at `app/auth/views.py:12` redirects them, so they can only export after confirming. That's acceptable because they can't post or comment before confirming anyway.
- **No new API endpoint, no database migration, no new dependency.**

## Changes
1. **`app/models.py`:** add a new `User.to_export_dict()` method. Keep it separate from `to_json()`, which is the public API view and must never include the email.
   - It lists the allowed fields explicitly:
     - **Profile:** id, username, email, name, location, about_me, role name, confirmed, member_since, last_seen, avatar URL.
     - **Posts:** id, full URL, body, body_html, timestamp, comment_count.
     - **Comments:** id, post_id, post URL, body, body_html, timestamp, disabled.
   - It also adds `export_format_version` and `exported_at`.
   - Posts and comments come from the existing `self.posts` and `self.comments` relationships, oldest first.
   - A small `_iso()` helper writes timestamps as ISO 8601 with a trailing `Z`, since the database stores them as UTC without a timezone. It also handles empty values.
   - URLs are built with `url_for(..., _external=True)` so they still work outside the site.
2. **`app/main/views.py`:** add a new route, `GET /export-data`, protected by `@login_required`.
   - It turns the dict into text with `json.dumps(indent=2, ensure_ascii=False)` and wraps it with `make_response`, which is already imported.
   - It sets the content type to `application/json`, adds a `Content-Disposition: attachment` header with a cleaned-up ASCII filename, and sends `Cache-Control: no-store`.
   - It uses `json.dumps` rather than `jsonify` because Flask 0.12's `jsonify` writes dates in HTTP format instead of ISO.
3. **`app/templates/user.html`:** add a "Download my data" button next to "Edit Profile". It only shows when `user == current_user`.
4. **Tests:**
   - **`tests/test_user_model.py`:** the export has the expected keys and counts and the `disabled` flag. No `password_hash` appears anywhere. Another user's posts and comments are not included.
   - **`tests/test_client.py`:**
     - A logged-out request is redirected to `/auth/login`.
     - A logged-in request returns 200 with the right content type and attachment header.
     - The file is valid JSON.
     - Non-ASCII text comes back intact.

## Verification
- Run `flask test`; all existing and new tests should pass.
- Manual check:
  1. Run `flask run`.
  2. Register and confirm a user, then write a post and a comment with non-ASCII text.
  3. Download from the profile page and inspect the file.
  4. Check that the button doesn't appear on another user's profile.
- Load fake data with `app/fake.py`, export a user with a lot of content, and watch the response time and the slow-query log.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Leaking private fields | It's easy to copy fields wholesale or reuse `to_json()`; `User` has `password_hash` and the token methods | List allowed fields explicitly; test that `password_hash` never appears |
| 2 | Including other users' data | Including the comments on a user's posts would export other people's text | Only the user's own comments; just counts on posts; test with a second user |
| 3 | Large accounts | The file is built in memory in one request; Gunicorn/Heroku have request timeouts | Order by indexed timestamp; check with fake data; stream or move to a background job later if needed |
| 4 | Date format | Dates are stored as UTC without a timezone, and `jsonify` writes them in HTTP format | `_iso()` helper with a `Z` suffix; `json.dumps` instead of `jsonify` |
| 5 | Unsafe filename header | Usernames go straight into `Content-Disposition` | Clean the username to ASCII and quote the filename |
| 6 | Unconfirmed users can't export | The `before_app_request` redirect applies to every route outside `auth` | Accept and document it; add an exception later if required |
| 7 | Cached copies of personal data | Proxies or the browser might keep the response | `Cache-Control: no-store` |
| 8 | Encoding problems | Unicode in posts and comments | `ensure_ascii=False`, UTF-8 response, round-trip test |

Riskiest: #1, leaking private fields such as `password_hash` or the email through a careless or reused serializer.
