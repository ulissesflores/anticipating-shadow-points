## Findings

- `TextSummary` (`app/models/tortoise.py`) has an implicit integer primary key. The migration creates it as `SERIAL`.
- Integer ids are exposed in four places:
  - Paths: `/summaries/{id}/` takes `id: int = Path(..., gt=0)` on GET, PUT and DELETE (`app/api/summaries.py`).
  - POST response: `SummaryResponseSchema.id: int` (`app/models/pydantic.py`).
  - Reads: `SummarySchema` is auto-generated by `pydantic_model_creator`, so it follows the model's pk type.
  - Background task: `generate_summary(summary_id, url)` in `app/summarizer.py`.
- `app/api/crud.py` filters everything by `id=`.
- Tests assert `id` from the POST response and use it in URLs. They also assert the 422 error shape for `loc: ["path","id"]` (`tests/test_summaries.py`).

## Assumptions

- Postgres 13 or later, so `gen_random_uuid()` is built in. Otherwise the migration enables `pgcrypto`.
- "Existing clients keep working" means clients can still send integer ids in URLs and still parse `id` as an int. A change of `id` from int to string is a breaking change for typed clients, so I will not flip it silently.
- The table is small enough for a single backfill. Deploys are rolling, so old and new app versions overlap against one database.
- Aerich migrations are the schema mechanism (`migrations/models/`).

## Approach: expand, then migrate, then contract

Keep the integer primary key internally. It stays the FK target and the background-task handle. Add a public UUID alongside it.

1. **Schema (expand)**
   - Add a new aerich migration.
   - Add `uuid UUID` as nullable, then backfill with `gen_random_uuid()`.
   - Then set `NOT NULL`, add a unique index and set a DB default.
   - Write a real `downgrade` that drops the column. The existing init migration's downgrade is empty.
   - Model: `uuid = fields.UUIDField(unique=True, default=uuid4)`.
2. **Read and write paths**
   - In `crud.py`, add one resolver that takes `int | UUID` and filters on `pk` or `uuid`.
   - In the routes, accept `Union[UUID, int]` for `{id}`. Keep `gt=0` for ints.
   - Disambiguation: a hyphenated string or 32-hex string is a UUID, and a digits-only value of 10 chars or fewer is an int. Parse deterministically and return 422 otherwise.
3. **Response shape (the compatibility seam)**
   - Phase A (now): `id` stays an int, and a new `uuid` field is added to every response.
   - Phase B: version the API. `/v2` (or an `Accept` version header) returns `id` as the UUID string and drops the int. `/v1` keeps the int `id`, plus `uuid`, and gets a `Deprecation` header.
   - Phase C: after clients migrate, which I would verify from access logs, retire the integer routes.
   - Build the response schemas explicitly instead of relying on `pydantic_model_creator`, so the shape is pinned per version.
4. **Background task**
   - Keep passing the internal pk to `generate_summary`. Nothing needs to change there.
5. **Tests**
   - Keep the existing int-based tests as the v1 contract tests.
   - Add tests for:
     - UUID path access.
     - Int and UUID both resolving to the same row.
     - Malformed ids returning 422 with the expected `loc`.
     - Backfill correctness (no null or duplicate uuids).
     - The v2 `id` type.
   - Update the validation-error cases whose `type` and `msg` change when the path type becomes a Union.
6. **Rollout order**
   - Deploy the migration first. The old app ignores the extra column.
   - Then deploy the new app, then announce the deprecation, then do the contract step later.
   - Update the README and the OpenAPI docs.

## Verification

Run the existing suite unchanged against Phase A. Then run the new tests and an old-client smoke test: POST, then GET, PUT and DELETE using the int id. Check the same operations with the UUID. Run the migration upgrade and downgrade on a database seeded with rows.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | `id` type change breaks typed clients | A JSON int becomes a string, and the POST response is parsed by clients | Keep int `id` on v1, add `uuid`, and flip only in v2 |
| 2 | Int/UUID path ambiguity | The `Union[UUID, int]` parse order can misroute 32-digit strings, and 422 bodies change | Explicit resolver and parse rules, with contract tests |
| 3 | Backfill locks or fails on a big table | `ALTER` plus `UPDATE` on Postgres during live traffic | Add the column nullable, backfill in batches, then add `NOT NULL` and the index |
| 4 | Rolling-deploy skew | Old pods insert rows without a uuid during the cutover | DB default `gen_random_uuid()`, and deploy the migration first |
| 5 | Empty downgrade in the existing migration | Rolling back is unsafe, and aerich state can drift | Write a real down-migration and test it |
| 6 | Auto-generated schema hides the contract | `pydantic_model_creator` changes the output when the model changes | Declare explicit response schemas per version |
| 7 | Background task or internal code using the wrong id | `generate_summary` updates by int id | Keep the pk internal and pass only the pk |
| 8 | Old links, bookmarks and cached URLs | Int ids are already in the wild | Keep int routes for the whole deprecation window and log their usage |
| 9 | ID enumeration is not fixed while int routes remain | Integer access still allows scraping, and the security gain is delayed | Pair the contract step with an end date and authorization checks |
| 10 | Test suite churn hides regressions | Many tests assert `id` and the error `loc` | Keep the old tests as the v1 contract and add new ones alongside |

Riskiest: #1, changing the `id` type, because strict clients break silently the moment it is flipped without versioning.
