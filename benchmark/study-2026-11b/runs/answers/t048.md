I've written the plan; I made no code changes. It is saved at `claude-home/plans/make-every-to-do-list-eager-koala.md`. In short: a `Tenant` table, a `TenantId` on both entities, the tenant taken from a sign-in claim, a database-level filter so every query is scoped automatically, and a save-time hook that stamps the tenant on new records.

## What I found
- `TodoList` and `TodoItem` (in `src/Domain/Entities`) have no owner at all. `GetTodosQuery` returns every list to any signed-in user, and the update/delete handlers look records up by Id alone.
- `IUser` / `CurrentUser` only expose the user Id and roles. `ApplicationUser` is an empty `IdentityUser`.
- The repo has no EF migrations. `ApplicationDbContextInitialiser` deletes and recreates the database on every start, so no existing data needs moving.
- There are already save-time hooks (`AuditableEntityInterceptor`, `DispatchDomainEventsInterceptor`), which gives a pattern to copy for stamping the tenant.
- The functional tests replace `IUser` with a mock in `WebApiFactory`.

## Assumptions
- Each user belongs to exactly one company. There is no switching between companies, and the Administrator role does **not** see across companies.
- `TenantId` is an `int`, like the existing keys.
- The tenant comes from a `tenant_id` claim added at sign-in. This works for both cookie and bearer login.
- When someone self-registers, a new company is created for them. Inviting users into an existing company is out of scope.

## Plan
1. **Domain:** add a `Tenant` entity and an `ITenantOwned { int TenantId }` interface; `TodoList` and `TodoItem` implement it.
2. **Application:**
   - Add `int? TenantId` to `IUser` and `DbSet<Tenant>` to `IApplicationDbContext`.
   - `CreateTodoItemCommandValidator` must check that `ListId` points to a list in the caller's company. The database filter doesn't apply to inserts, so without this check someone could add an item to another company's list.
3. **Web:**
   - `CurrentUser.TenantId` reads the claim.
   - Replace or wrap `<home>` so it creates the company and the user together in one transaction.
4. **Infrastructure:**
   - `ApplicationUser.TenantId`: a required link to `Tenant`.
   - A `TenantClaimsPrincipalFactory` that adds the `tenant_id` claim, registered in both login branches of `DependencyInjection.cs`.
   - `ApplicationDbContext` gets `IUser` injected and a filter on every tenant-owned type: `e.TenantId == _user.TenantId`. If there is no tenant, it returns nothing.
   - A new `TenantEntityInterceptor`:
     - stamps `TenantId` on new records, unless it is already set (needed for seeding);
     - throws if there is no tenant;
     - throws if a record's `TenantId` changes, or if an item's tenant differs from its list's tenant.
   - In the two entity configurations: the link to `Tenant` (deleting a company doesn't cascade), an index on `TenantId`, and optionally a unique `(TenantId, Title)` index for lists.
   - The seed creates a default company and assigns it explicitly to the admin and the "Tasks" list. Its `.Any()` checks must skip the filter (`IgnoreQueryFilters()`), because there is no signed-in user at startup.
5. **Handlers:** no code changes. `FindAsync` and the LINQ queries go through the filter. One caveat: `FindAsync` returns records already loaded in memory without filtering, which is safe with one database context per request.
6. **Tests:**
   - `RunAsUserAsync` takes a tenant.
   - The `IUser` mock returns `TenantId`.
   - `DatabaseResetter` also clears the `Tenants` table.

## Verification
- Build every template variant: SQLite, SqlServer, PostgreSQL, and `UseApiOnly`.
- New functional tests with user A (company 1) and user B (company 2):
  - B doesn't see A's lists.
  - B updating or deleting A's list or item gets NotFound.
  - B adding an item to A's list gets a validation error.
  - Both companies can have a list with the same title.
  - With no tenant, reads return nothing and writes throw.
- Run `dotnet test`, then register two companies in the UI and check each sees only its own data.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Item added to another company's list | `CreateTodoItem` sets `ListId` from the request, and the filter doesn't apply to inserts | Validator checks the list exists in the caller's company; interceptor checks item and list tenants match |
| 2 | No tenant claim yet when a user registers | `MapIdentityApi` register has no hook for a company | Custom register endpoint; with no tenant, reads return nothing |
| 3 | Seed re-runs or fails | Startup has no signed-in user, so the filter hides everything and the stamp has no tenant | Set `TenantId` explicitly; use `IgnoreQueryFilters()` in the seed |
| 4 | Filter doesn't cover some code paths | Raw SQL, `IgnoreQueryFilters` and records already in memory skip it | Ban raw SQL on these tables; tests across companies |
| 5 | Stale claim | A cookie or token keeps the old `tenant_id` after the user's company changes | Company is fixed per user; refresh the security stamp if it ever changes |
| 6 | Template variants break | `#if UseApiOnly` / database-provider branches in DI | Register the claims factory in both branches; build every variant |
| 7 | Tests fail with no tenant | The `IUser` mock has no `TenantId` | Extend `TestApp` and the mock; reset the `Tenants` table |
| 8 | Unique title rule leaks or collides | The validator now runs inside the filter; a database index would be global | Use a composite `(TenantId, Title)` index |
| 9 | Slower queries | Every query gains a `TenantId` condition | Index on `TenantId` |
| 10 | Real deployments with migrations | Forks that switched to migrations already have rows with no tenant | Backfill a default company, then make the column required |

Riskiest: #1. Adding an item to another company's list by `ListId` gets past the filter and puts data in the wrong company.
