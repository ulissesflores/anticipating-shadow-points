The repo already has most of this, so my assumption is that "stronger" means moving beyond the current scheme, probably to Argon2id, and that nothing is edited now (per your instruction).

## What exists today
- `src/Conduit/Infrastructure/Security/PasswordHasher.cs` issues ASP.NET Identity v3 hashes (PBKDF2, 210,000 iterations, random salt embedded in the payload).
- Legacy 64-byte HMAC-SHA512 hashes with a 16-byte salt are still verified. Verifying one returns `SuccessRehashNeeded`.
- `Login.cs:80-83` rewrites the hash on a successful login. This is a lazy upgrade, so nobody is forced to reset.
- `Users/Edit.cs` and `Users/Create.cs` always issue the new format.

## Assumptions
- Target is Argon2id (or a higher-cost PBKDF2) behind the existing `IPasswordHasher`.
- Identity's v3 format is distinguishable from any new format by its header byte (`0x01`), so I can add a new version tag and keep both verifiers.
- Both SQLite and SQL Server `Hash` columns are wide enough (to be verified), and I'd add no new column.
- Dormant users who never log in stay on the old hash. A bulk rehash is impossible because the plaintext is gone.

## What could go wrong (before planning)
1. **Wrong "needs rehash" signal.** A new format could be reported as `Success`, so nobody upgrades, or the old format could be reported as `SuccessRehashNeeded` forever, causing a write on every login.
2. **Format detection by length.** The legacy check is `Length == 64 && salt.Length == 16`. A new payload that happens to be 64 bytes would be misclassified and every login would fail.
3. **Column too narrow.** An Argon2 encoded hash is larger than the Identity payload. SQL Server or SQLite would truncate or reject it, and truncation would lock users out.
4. **Migrations for two providers.** If I change column size or add a version column, both providers need migrations and snapshots, plus baselining for existing databases.
5. **Login becomes a DoS lever.** A heavier hash costs more CPU and memory per request. Unauthenticated `/users/login` can be hammered, and `Login.cs` runs no hash for unknown emails.
6. **Email enumeration by timing.** An unknown email returns immediately with no hash, while a known one pays the hash cost. A slower hash makes this gap bigger.
7. **Rollback is one-way.** After users are upgraded, an older build can't read the new hashes, so reverting the deploy locks them out.
8. **Concurrent rehash writes.** Two simultaneous logins both rehash and save. The last write wins, and both are valid, but it can cause tracking noise or a conflict if a concurrency token is added.
9. **New dependency and CI.** Argon2 needs a package (a native or managed one), which means central versions, lock-file updates under locked restore, and warnings-as-errors. A native library may not run on all CI or deploy targets.
10. **Tests only cover the new path.** Without fixture hashes captured from real legacy and Identity v3 rows, a regression in old-format verification wouldn't be caught.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Wrong rehash signal | Only `SuccessRehashNeeded` triggers the write in `Login.cs` | Return it for every older format, `Success` only for current; unit-test each |
| 2 | Length-based format sniffing | Legacy check is `Length == 64 && Salt == 16` | Use an explicit version prefix; check the prefix before length |
| 3 | `Hash` column too narrow | Argon2 payload is bigger than Identity's | Check column sizes in both snapshots; add migrations if needed |
| 4 | Dual-provider migrations | SQLite and SQL Server have separate snapshots | Prefer no schema change; otherwise add both and test on both |
| 5 | Login CPU/memory DoS | Public login endpoint, heavier hash | Tune cost, add rate limiting, benchmark on target hardware |
| 6 | Timing leak on unknown email | Unknown email skips hashing entirely | Verify against a dummy hash when the user isn't found |
| 7 | One-way upgrade, no rollback | Old builds can't verify new hashes | Ship verify-only support first, then enable issuing a release later |
| 8 | Concurrent rehash writes | Two logins can upgrade the same row | Make the update idempotent; write only if the stored hash is unchanged |
| 9 | New package and locked restore | Warnings-as-errors, `packages.lock.json`, CI targets | Prefer a managed library; regenerate lock files; run the CI pipeline |
| 10 | Legacy path untested | Only new hashes get exercised by default | Add fixtures for legacy HMAC and Identity v3 hashes and run them through login |

Riskiest: #7, because upgrades are one-way. Once users are on the new format, a rollback locks them out, so verify-only support has to ship before any code starts issuing the new hashes.
