## Assumptions (non-interactive)

- This is the Remix "Blues Stack" app: Prisma on Postgres, cookie sessions, and email plus bcrypt password auth. The relevant files are `app/routes/join.tsx`, `app/routes/login.tsx`, `app/models/user.server.ts`, `app/session.server.ts`, `prisma/schema.prisma`, `cypress/support/create-user.ts`, `prisma/seed.ts` and `mocks/`.
- "New users" means users created after this ships. Existing users are grandfathered by backfilling `emailVerifiedAt`.
- The app has no email-sending capability today. I assume a transactional provider such as Resend or Postmark will be added, with its key supplied through env vars and Fly secrets.
- Verification uses a single-use, expiring token. Only a hash of the token is stored.
- No files are edited. This is a read-only plan, and I did not write the plan file because you said not to edit any file.

## Ways this could go wrong, before planning

1. **Existing users get locked out.** The new column defaults to null, so every current account looks unverified.
2. **Signup still logs the user in.** `join.tsx` calls `createUserSession` right after `createUser`. If this isn't removed, "verify before login" is bypassed.
3. **Other session paths skip the check.** `getUser`/`requireUser` in `session.server.ts` trust any cookie. Existing sessions, or a "remember me" session, stay valid for unverified users.
4. **Login leaks account state.** A distinct "please verify" error lets an attacker enumerate registered emails. The login error is currently generic.
5. **Token weaknesses.** Guessable, reusable, never-expiring or plaintext-stored tokens, or tokens that are not bound to the email.
6. **Email delivery fails.** Spam filtering, a missing SPF/DKIM setup, or provider downtime means users can never log in, and the failure is silent.
7. **Verification links are open to abuse.** Resend can be spammed, GET links can be consumed by mail scanners that prefetch them, and an unvalidated redirect target would be an open redirect.
8. **Migration or deploy hazards.** On Fly, the migration must run before the new code serves traffic, or login breaks mid-deploy. The `.env.example`, Fly secrets and mocks also need updating.
9. **Tests and tooling break.** The Cypress `create-user` command and the seed user are unverified, so the e2e smoke test fails. The MSW mocks need an email endpoint.
10. **Dead-end UX.** A typo'd email can never be fixed, and there is no resend path or expired-link handling.

## Planned approach (summary)

1. Add `emailVerifiedAt DateTime?` to `User` and a `EmailVerificationToken` model (hashed token, expiry, userId). The migration backfills existing users to `now()`.
2. In `createUser`, generate a token and send the email. `join.tsx` redirects to `/verify-email/sent` with no session.
3. Add `/verify-email` (POST-confirm or token-consume, single-use) and `/verify-email/resend` (rate-limited, with a generic response).
4. In `verifyLogin`, reject unverified users. `login.tsx` shows a neutral message and triggers a resend only when the password is correct.
5. In `getUser`/`requireUser`, destroy the session for unverified users.
6. Update the seed, the Cypress helper and the mocks, and add unit and e2e tests.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New nullable column makes all current users unverified | Backfill `emailVerifiedAt=now()` in the migration |
| 2 | Signup still creates a session | `join.tsx` calls `createUserSession` after `createUser` | Remove it and redirect to a "check your email" page |
| 3 | Unverified cookie sessions stay valid | `requireUser` and `getUser` only check that the user exists | Enforce verification in the session helpers and invalidate old sessions |
| 4 | Account enumeration | A distinct "unverified" login error reveals registered emails | Reveal it only after a correct password; keep other errors generic |
| 5 | Weak or reusable tokens | Auth tokens are security-critical and nothing exists yet | Use 32-byte random tokens, store a hash, expire in 24h, single use |
| 6 | Email never arrives | No email infrastructure exists; unverified users are blocked entirely | Set up SPF/DKIM, log send errors, provide a resend path and monitoring |
| 7 | Scanner prefetch or resend abuse | A GET link can be auto-consumed; resend can be spammed | Use a confirm-button POST and rate-limit per email and IP |
| 8 | Deploy-order breakage | Fly runs a migration against a live DB while old code serves traffic | Make the migration additive and backwards-compatible; deploy in two steps |
| 9 | Tests and seed break | The Cypress `create-user` and `seed.ts` users are unverified | Create them pre-verified and mock the email provider |
| 10 | Typo'd email strands the user | No way to change the email or recover | Add resend and change-email flows, and delete stale unverified accounts after a TTL |

Riskiest: #2/#3 together. If signup still creates a session, or the session helpers don't enforce verification, the whole feature is silently bypassed while appearing to work.
