## Ways this could go wrong (before planning)
1. **OAuth/OIDC logins break.** Libraries like Authlib keep the OAuth `state`/`nonce` in `request.session`. The identity provider redirects back to the app from another site, and browsers don't send `SameSite=Strict` cookies on cross-site navigations. The state check then fails and login breaks.
2. **Inbound links arrive logged out.** Someone clicking a link to the app from an email, Slack or another site gets no session cookie on that first request. They look logged out until the next same-site navigation.
3. **Sessions fail silently over plain HTTP.** Browsers won't set or send `Secure` cookies over `http://` except on `localhost`, and Safari has been inconsistent even there. `http://127.0.0.1`, LAN IPs, Docker hostnames and HTTP-only staging all lose sessions with no error.
4. **Test suites break, here and downstream.** `TestClient` defaults to `http://testserver`, and httpx's cookie jar won't send `Secure` cookies over HTTP. `test_secure_session` (`tests/middleware/test_session.py:140-148`) already shows this. Most session tests here and in user projects would fail.
5. **Clearing the session fails over HTTP.** The deletion `Set-Cookie` uses the same `security_flags`, so a browser rejects it on an insecure origin. Logout appears to do nothing.
6. **A pinned value can't be told apart from the default.** `https_only: bool` can't distinguish "passed False" from "left at default". A deprecation-warning transition would need a sentinel such as `None`.
7. **The docs go stale.** `docs/middleware.md:235-250` states the old defaults and says to set `https_only=True` in production. The `partitioned` note refers to `https_only=True` too.
8. **Ecosystem fallout.** FastAPI tutorials, admin panels and auth libraries depend on today's defaults, and they would hit failures 1 and 3 when users upgrade.

## Plan
1. **`starlette/middleware/sessions.py`:** change the defaults to `same_site: Literal["lax", "strict", "none"] = "strict"` and `https_only: bool = True`. The rest of the logic already handles both flags.
2. **Tests (`tests/middleware/test_session.py`, `tests/middleware/test_middleware.py`):**
   - Switch the clients in tests that rely on the defaults to `base_url="https://testserver"`, or pass `https_only=False` where the test is really about HTTP.
   - Add a test that the default `Set-Cookie` contains `secure` and `samesite=strict`, on both the write path and the clear path.
   - Add a test that `https_only=False, same_site="lax"` restores the old header.
3. **`docs/middleware.md`:**
   - Update the defaults text and the production advice.
   - Add a short note on opting out for local HTTP and for OAuth callback flows (`same_site="lax"`).
   - Per `AGENTS.md`, put explanatory text after each heading before any code.
4. **`docs/release-notes.md`:** add a "Changed" entry that marks this as breaking and shows the opt-out kwargs.
5. **Verification:** run `pytest tests/middleware/test_session.py tests/middleware/test_middleware.py`, the full test suite, and the type and lint checks. Then check by hand in a browser:
   - The cookie works on `https://` and on `http://localhost`.
   - It's dropped on `http://127.0.0.1` in Safari.
   - An OAuth-style cross-site redirect loses the session under Strict and keeps it under Lax.

**Recommendation:** I'd make `https_only=True` the default but think hard before making `same_site="strict"` one. `Lax` already blocks cross-site POST CSRF, and Strict breaks the very common login-with-provider flow. If you do want Strict, the docs need to say clearly how to opt out.
