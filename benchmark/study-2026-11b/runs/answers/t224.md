## Assumptions
- Only one resource exposes IDs: `TextSummary`, in the `textsummary` table. It has a `SERIAL` primary key, and Aerich owns the migrations.
- Existing clients send integer IDs in paths such as `/summaries/42/` and read `id` as an integer in JSON. I can't see the clients, so I can't confirm this.
- "Keep existing clients working" means a deprecation window. During it, integer IDs still work and UUIDs are added. After it, UUIDs become the only public ID.
- The integer stays as the internal primary key. No other table has a foreign key to it.

## Ways this could go wrong
1. **Type collision on `id`.** The response schemas declare `id: int`, and the routes use `Path(..., gt=0)` with an `int` type. A UUID in the same `id` field breaks every client that parses an integer.
2. **Ambiguous path parameter.** `/{id}/` must accept both an integer and a UUID. FastAPI tries union types in order, so a bad ordering gives 422s or a wrong lookup.
3. **Backfill and lock on the migration.** Adding a `NOT NULL` UUID column with a default can rewrite or lock the table. Rows created while the migration runs could end up with no UUID.
4. **Background task keeps the integer.** `create_summary` passes `summary_id` (an int) to `generate_summary`. If I change what `crud.post` returns, the task updates the wrong row or none.
5. **Generated schema drifts.** `SummarySchema` comes from `pydantic_model_creator`, so a new field changes the response shape and the OpenAPI document without anyone choosing to.
6. **Enumeration and IDOR.** Keeping integer lookups means IDs stay guessable. There is no auth in the code I read, so UUIDs only help if the integer path is later removed.
7. **Rollback.** The existing `downgrade` is empty. Once clients store UUIDs, rolling back orphans their references.
8. **Hidden consumers.** Stored links, caches, webhooks, logs or dashboards may hold integer IDs. I can't see them from this repo.
9. **Tests and CI.** Tests that assert `id == 1` or hard-code integer paths will fail. They would also miss a regression in the dual-ID path unless I add cases for it.
10. **Index and performance.** A UUID without a unique index makes lookups slow and allows duplicates. A UUID primary key would add index bloat and break the integer sequence.

## Plan
1. **Expand.** Add a `uuid` column with a unique index to `TextSummary`. Make it nullable, backfill it in batches, then set `NOT NULL` with a `uuid4` default. Do this in a new Aerich migration with a real `downgrade`.
2. **Dual lookup.** Add one resolver in `crud.py` that takes a string, parses it as an integer or a UUID, and queries the matching column. The routes use it, so they take `id: str` with that resolver rather than `int`.
3. **Responses.** Keep `id` as an integer and add `uuid`. Add an opt-in `/v2` or `Accept` version where `id` is the UUID.
4. **Deprecation signals.** Add a `Deprecation` header for integer-addressed calls, and log how often each ID form is used.
5. **Contract, later.** Make UUIDs the only public ID once the logs show no integer traffic.
6. **Tests.** Cover integer and UUID in every route, mixed or invalid IDs, the background task, and migration up and down.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | `id` changes type in responses | Schemas say `id: int`, so integer parsers break | Keep `id` as int, add `uuid`, and put UUID-as-`id` behind `/v2` |
| 2 | Path accepts int and UUID ambiguously | Routes use `Path(gt=0)` with `int` | One resolver with explicit parsing, and tests for bad input |
| 3 | Migration locks or leaves NULL UUIDs | Aerich runs one migration, and live inserts continue | Nullable column, batched backfill, then `NOT NULL`, with a default set first |
| 4 | Background task gets the wrong ID | `generate_summary` is called with an int from `crud.post` | Keep the internal integer for tasks, and add a test |
| 5 | Auto-generated schema drifts | `pydantic_model_creator` picks up new fields silently | Pin the response model explicitly |
| 6 | Integer IDs stay guessable | The dual-ID window keeps enumeration open, and there is no auth | Rate-limit, set a sunset date, and then remove integer lookups |
| 7 | Rollback is lossy | `downgrade` is empty, and clients may store UUIDs | Write a reversible migration and ship behind a flag |
| 8 | Unknown consumers use integer IDs | Clients and stored links are outside this repo | Log ID-form usage, announce the deprecation, and check logs before removal |
| 9 | Tests and CI break or miss cases | Tests likely hard-code integer IDs | Update the fixtures, and add dual-ID and migration tests |
| 10 | Missing unique index | UUID lookups would be slow or allow duplicates | Add a unique index in the migration |

Riskiest: #1, the `id` type change in responses, because it breaks clients silently and in production.
