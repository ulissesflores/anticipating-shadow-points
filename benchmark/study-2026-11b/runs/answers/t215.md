# Plan: online visit booking with no double-booking per vet

I made no edits, as requested. This is based on reading `Visit.java`, `VisitController.java`, `Owner.addVisit`, the H2 schema and `createOrUpdateVisitForm.html`.

## What the code does today

- A `Visit` has only `visit_date` (a `DATE`) and `description`. It has **no vet and no time**, so there is nothing to conflict on yet.
- `VisitController` already lets owners book a visit. It loads the owner, adds the visit to the pet, and saves the whole `Owner` aggregate.
- `Vet` is a separate read-only model, listed in `VetController` and cached via `CacheConfiguration`.
- Schemas are kept by hand in `db/{h2,mysql,postgres}/schema.sql`. Hibernate `ddl-auto=none`, so I'll hand-edit all three.

## Assumptions

1. Each visit gets a fixed-length slot (30 minutes), configurable through a property. Slots start on the grid (for example :00 and :30) between clinic hours (for example 09:00–17:00, Monday–Friday).
2. The owner picks a vet and a date, then chooses from the free slots. "Any vet" is out of scope.
3. A single vet can have at most one active visit per slot. Different vets can overlap.
4. There is no authentication, as in the current app. Existing "owner books for own pet" behaviour stays.
5. Cancellation and rescheduling are out of scope. Cancelled visits would simply free the slot later.
6. Legacy visits have no vet or time, so those columns stay nullable. The unique constraint ignores `NULL`s.
7. The database is the arbiter of correctness. An application-level check alone is not enough.

## Approach

**1. Schema (all three dialects)**
- Add `vet_id INTEGER` (FK to `vets`) and `visit_time TIME` to `visits`.
- Add `UNIQUE (vet_id, visit_date, visit_time)` as the hard guarantee.
- Add an index on `vet_id`.
- Seed a few vet-assigned visits in `data.sql` only if tests need them.

**2. Model**
- `Visit` gets `vet` (`@ManyToOne`, or a plain `vetId`) and `time` (`LocalTime`). Both are `@NotNull` for new bookings only, using a validation group or controller-level checks so legacy rows still load.
- Keep the `@InitBinder` that disallows `id` binding. Don't bind a vet reference unchecked. Look the vet up by id and reject unknown ids.

**3. Availability and booking logic**
- A new `VisitBookingService` (in `owner/`) with:
  - `availableSlots(vetId, date)`, which generates the grid and subtracts booked slots (query on `VisitRepository` or `OwnerRepository`).
  - `book(...)`, which is `@Transactional` and validates that the slot is on the grid, within hours, on a weekday and in the future.
  - Conflict handling: catch `DataIntegrityViolationException` on save, then translate it to a form error like "slot just taken, pick another". Don't rely on a check-then-insert alone, because two concurrent requests both pass the check.
- A `VisitRepository` with `existsByVetIdAndDateAndTime`, and a query for booked times by vet and date.

**4. Controller and view**
- `VisitController`: add `vets` and a slot-list model attribute. Add a GET endpoint (JSON or a fragment) for free slots by vet and date, so the form can refresh. The POST goes through the service and keeps the existing redirect with a flash message.
- `createOrUpdateVisitForm.html`: add a vet `<select>` using the existing `selectField` fragment and a time select. Show a clear "slot taken" error.
- Add i18n keys to all `messages_*.properties`. `I18nPropertiesSyncTest` fails if the files drift.

**5. Tests**
- Unit tests for slot generation: grid, hours, weekends, the past.
- `VisitControllerTests`: valid booking, taken slot, unknown vet, off-grid time.
- A concurrency test next to `PetClinicConcurrencyTests`. Two threads book the same vet and slot, and exactly one succeeds.
- Run the integration tests on MySQL and Postgres (the existing `*IntegrationTests` use containers), not just H2.

**6. Rollout**
- Run the migration on a copy of existing data first. Verify that legacy `NULL` rows pass the constraint on each database.

## Verification

- `./mvnw test` (includes checkstyle and spring-format).
- Start the app, book a slot, then book the same vet and slot again and confirm the form error. Book the same time with another vet and confirm it works.
- Fire two parallel `curl` POSTs for the same slot and confirm one succeeds and one gets the error, never a 500.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Check-then-insert race | Two owners submit the same slot at once, and an app-level check passes for both | Unique constraint on (vet, date, time); catch the violation as a form error |
| 2 | Data model has no vet or time | `Visit` has only a date, so the feature needs schema, entity and form changes together | Add nullable columns in all three schemas; validate only new bookings |
| 3 | Three hand-kept SQL dialects drift | `ddl-auto=none`, so H2, MySQL and Postgres schemas are edited manually | Change all three together; run the MySQL and Postgres integration tests |
| 4 | Legacy visits with `NULL` vet or time | Existing rows would break `NOT NULL` or confuse uniqueness | Keep columns nullable; unique key ignores `NULL`s; test on seeded data |
| 5 | Whole-`Owner` save on booking | `owners.save(owner)` rewrites the aggregate, so a constraint failure rolls back more than the visit | Save the visit through a dedicated repository in a small transaction |
| 6 | Time zone and "now" handling | `LocalDate.now()` uses the server zone, so "future slot" and past checks can be wrong near midnight | Inject a `Clock` and a clinic time zone; test boundary times |
| 7 | Forged vet or time input | Form fields are user-controlled, and the app has no auth | Look up the vet server-side; validate the grid, hours and range; keep the `id` binder rule |
| 8 | Stale slot lists in the UI | A slot looks free when rendered but is taken at submit | Treat the DB as the authority; re-render with fresh slots on conflict |
| 9 | Missing i18n keys | `I18nPropertiesSyncTest` fails if keys are not in every `messages_*.properties` | Add keys to all locale files in the same change |
| 10 | Slot rules change later | Fixed-length slots can't represent longer procedures, and a start-time key won't catch overlaps then | Document the assumption; move to range-overlap checks if durations vary |

Riskiest: #1, the check-then-insert race, because it is the exact failure the feature exists to prevent.
