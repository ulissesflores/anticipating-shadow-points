**How it works today:** this is the Remix Blues Stack (Prisma/Postgres, cookie sessions, deployed on Fly). The sign-up page (`app/routes/join.tsx`) logs the new user in straight away with `createUserSession`. The login page (`app/routes/login.tsx`) checks only the password. The app has no way to send email.

**Assumptions** (I couldn't ask, so I picked these):
- Existing users count as already verified, so they won't be locked out.
- Email goes out through a transactional email HTTP API (Resend-style) called with `fetch`, configured by `EMAIL_API_KEY`, `EMAIL_FROM` and `APP_ORIGIN`. When there's no key (local dev and CI), the email is printed to the console or caught by the test mocks.
- A link works once and expires after 24 hours. Clicking it verifies the email and logs the user in.
- The existing "A user already exists with this email" message stays as it is.

**Plan**
1. **Database:** add `User.emailVerifiedAt DateTime?` and a new `EmailVerificationToken` table (`tokenHash` unique, `userId` deleted with the user, `expiresAt`). The migration ends by setting every existing user's `emailVerifiedAt` to their `createdAt`. Fly's `release_command` runs the migration before the new code starts.
2. **User model (`app/models/user.server.ts`):**
   - `createUser` gets a `{ verified }` option.
   - `createEmailVerificationToken` makes a random 32-byte token, stores only its SHA-256 hash, and deletes the user's older tokens.
   - `consumeEmailVerificationToken` does its work in one transaction: find a matching, unexpired token, mark the user verified, delete their tokens.
3. **Sending email:** a new `app/email.server.ts` with `sendEmail` and `sendVerificationEmail`. Add the new variables to `.env.example` and set them as Fly secrets.
4. **Sign-up page:** create the user, create a token, send the email, then redirect to a "check your inbox" page. It no longer creates a session.
5. **Login page:** if the password is correct but the email isn't verified, return an error with a "Resend verification email" button. This only appears after a correct password, so it doesn't reveal which emails have accounts.
6. **New routes:**
   - `verify-email`: opening the link only checks the token and shows a "Confirm email" button. Clicking it uses up the token and logs the user in. Opening the link must not use up the token, because email link scanners open links automatically.
   - `verify-email.sent`: the "check your inbox" page.
   - `verify-email.resend`: sends a new link at most once per 60 seconds per user, and always shows the same message.
7. **Extra safety check:** `requireUser` and `getUser` in `app/session.server.ts` treat unverified users as logged out.
8. **Seed and test helpers:** `prisma/seed.ts` and `cypress/support/create-user.ts` create verified users. A new handler in `mocks/index.js` saves each outgoing email to a file so Cypress can read the link.

**How to verify**
- Run the migration on a seeded database and confirm the seeded user can still log in.
- Add Vitest tests for tokens: expiry, single use, and that only the hash is stored.
- Update the Cypress smoke test to cover: sign up → "check your inbox" → login refused → read the link from the saved email → confirm → `/notes` → using the link again fails.
- Run `npm run validate`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New column is null for all current users; the login check would reject them | Backfill `emailVerifiedAt = createdAt` in the same migration |
| 2 | Link used up before the user clicks it | Corporate mail scanners open links in emails | Opening the link only shows a page; a button press verifies |
| 3 | No email provider yet | The app can't send email today; a missing key breaks sign-up | Log the email when there's no key; fail clearly in production; set Fly secrets |
| 4 | End-to-end tests break | Smoke test expects to be logged in right after sign-up | Mock captures the email; test reads the link; helpers create verified users |
| 5 | Tokens stolen from the database | Stored raw tokens would act like passwords | Store only the SHA-256 hash, single use, 24h expiry |
| 6 | Resend button used to spam inboxes | The resend form is public | One email per minute per user, same message every time |
| 7 | Account enumeration widened | New messages could reveal which emails are registered | "Verify your email" only after a correct password; resend always gives the same reply |
| 8 | Wrong link domain | `APP_ORIGIN` differs between dev, staging and Fly | Required setting, checked at startup |
| 9 | Deploy order | Old code runs while the migration applies | The change only adds things, and old code ignores the new column |
| 10 | Users stuck unverified | Emails go to spam or bounce | Resend button on the login page; an admin can set the flag manually |

Riskiest: #1. If the backfill is missing, every existing user is locked out the moment the new code ships.
