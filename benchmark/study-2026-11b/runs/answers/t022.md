I've written the plan to `<config>/plans/make-sessions-roll-by-rippling-teapot.md`; no repo files were edited. The plan turns `rolling` on by default, which is a breaking change, so it targets the next major version (2.0.0).

**Assumptions**
- "Roll" means the existing `rolling` behaviour: the session cookie is sent again on every response with a fresh `maxAge`, so its expiry slides forward. The store side needs no change, because `shouldTouch` and `store.touch` already extend the stored session whatever `rolling` is set to.
- Changing the default is acceptable in a major release, without first adding a deprecation warning.
- Setting `rolling: false` explicitly remains the way to opt out.

**Plan**
1. **`index.js:109`**: change `Boolean(opts.rolling)` to `opts.rolling === undefined ? true : Boolean(opts.rolling)`, and update the JSDoc at `index.js:78` to `[options.rolling=true]`. `shouldSetCookie` (`index.js:481-492`) stays as it is.
2. **`README.md`, "rolling" section (around line 295)**:
   - Change the stated default to `true`.
   - Add a warning that without `cookie.maxAge`, rolling just re-sends a browser-session cookie on every response.
   - Show the `rolling: false` opt-out.
3. **`HISTORY.md` "unreleased"**: add a breaking-change entry. Leave `package.json` alone.
4. **`test/session.js`**:
   - Change "rolling option › should default to false" (around line 1159) so it expects `Set-Cookie` on the second request.
   - Add a test that `rolling: false` sends no cookie for an unmodified session that was loaded from the request.
   - Add a test that, with `maxAge` set, the second response's `Expires` is later than the first's.
   - Go through the 26 `shouldNotHaveHeader('Set-Cookie')` assertions. Where a test sends an existing session cookie, add `rolling: false` to its server options rather than flipping what it expects. Tests for new or uninitialized sessions shouldn't change, because `rolling` only applies when the cookie's session ID matches the loaded session.
5. **Verification**: run `npm test` and `npm run lint`. Then try a small app with `maxAge: 60000`: two requests carrying the cookie should both get `Set-Cookie`, with a later `Expires` the second time. With `rolling: false`, the second response should have no `Set-Cookie`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Silent breaking change for existing users | Apps that never set `rolling` start sending `Set-Cookie` on every response | Release in a major version, add a HISTORY entry and a README note on opting out |
| 2 | HTTP caching breaks | CDNs and proxies often won't cache responses that carry `Set-Cookie`, and some may cache the cookie itself | Document it; suggest `rolling: false` or skipping the middleware for static routes |
| 3 | Tests mass-fail or get "fixed" wrongly | 26 tests assert no `Set-Cookie`; flipping them would hide regressions | Add `rolling: false` where a test needs the old default; don't flip expectations |
| 4 | Does nothing without `maxAge` | The default cookie has no expiry, so rolling gives only extra headers | Say so in the README; consider a later warning when `maxAge` isn't set |
| 5 | Sessions never time out for active users | Any request, including polling or keep-alive calls, keeps the session alive | Document the need for an absolute timeout and app-level checks |
| 6 | Mismatch with `saveUninitialized: false` | The cookie still isn't set for uninitialized sessions, which can surprise people expecting "every request" | Keep the documented note; tests already cover this case |
| 7 | Extra overhead | Every response gets cookie serialization and signing, plus a larger header | Small cost; mention it in the release notes |
| 8 | Cookie and store expiry drift apart | Store TTL relies on `touch`/resave while the cookie now always slides | Note that a store without `touch` and with `resave: false` will expire server-side first |

Riskiest: #1. Every existing deployment that relies on the implicit default changes its cookie behaviour silently on upgrade.
