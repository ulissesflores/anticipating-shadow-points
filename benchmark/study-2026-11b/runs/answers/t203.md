I've written a plan for this; no repo files were edited. Every to-do list and item gets a tenant (company) ID. A database-level filter hides other companies' rows from every query, so handlers that look rows up by ID don't need separate owner checks.

## Assumptions
- One user belongs to exactly one company. The company is always taken from the signed-in user, never from what the client sends.
- If there's no signed-in user or the user has no company, access fails closed: they see nothing and writes are refused.
- There's no "super admin" who can see every company in this change.
- Screens for creating companies or inviting users are out of scope. The seed data creates a "Default" company and puts the administrator in it.
- Users who sign up through the existing registration endpoints start with no company until someone assigns one.
- The repo has no database migrations: the app drops and recreates the database on every start, so no existing data needs converting here. Real deployments with data will need a migration and a backfill.
- This is the `dotnet new` template, so every change has to build under all its options (SQLite / SQL Server / PostgreSQL, API-only, Angular / React).

## Steps
1. **Domain:**
   - Add a `Tenant` entity and an `ITenantOwned` marker with a `TenantId` property.
   - `TodoList` and `TodoItem` both carry `TenantId`. Items get their own copy so they can be filtered directly and the database can check that an item and its list share a company.
2. **Application:**
   - Add `TenantId` to `IUser`.
   - Add a `Tenants` table to `IApplicationDbContext`.
   - The data sent to and from the API (DTOs) stays the same; the tenant ID is never exposed or accepted.
3. **Identity:**
   - Add `ApplicationUser.TenantId`.
   - A custom claims factory adds a `tenant_id` claim at sign-in. This covers both cookie and bearer-token login, because both go through `SignInManager`.
   - `CurrentUser` reads that claim.
4. **Database model:**
   - In `ApplicationDbContext`, inject `IUser` and add a filter on lists and items: `TenantId == CurrentTenantId`.
   - Lists get a unique `(TenantId, Title)` index. Items get a composite foreign key `(ListId, TenantId) → TodoList(Id, TenantId)`, so the database itself refuses an item in another company's list.
   - A new `TenantInterceptor` sets `TenantId` on new rows, refuses saves when there's no tenant, and blocks changing `TenantId` later.
5. **Handlers:**
   - Update and delete automatically return 404 for another company's IDs.
   - `CreateTodoItem` loads the list through the filter first, so a foreign list ID gives a 404 instead of a database error.
   - The "title must be unique" rule becomes per company with no code change.
   - Add `[Authorize]` to the to-do commands and queries as a second layer.
6. **Seeding:** startup seeding runs with no signed-in user, so `ApplicationDbContextInitialiser` sets the tenant explicitly and bypasses the filter (`IgnoreQueryFilters`).
7. **Tests:**
   - The functional-test helper `TestApp` takes a tenant, and the mocked `IUser` returns it.
   - Raw database assertions bypass the filter, and the test database reset includes the `Tenants` table.
   - New isolation tests use two companies, A and B:
     - A only sees A's lists.
     - Updating or deleting B's rows gives a 404.
     - Creating an item in B's list gives a 404.
     - The same list title is allowed in both companies.
     - A user with no company gets a forbidden error.

**Verification:**
- Run `dotnet test`, then `build/test.ps1` to build every template option.
- Check by hand with the Aspire AppHost: log in as the seeded admin, then as a user in a second company, and confirm each sees only their own lists.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Item added to another company's list | `CreateTodoItemCommand.ListId` comes from the client, and the foreign key only checks `Id` | Composite FK `(ListId, TenantId)` plus a filtered lookup of the list in the handler |
| 2 | Filter bypassed or captured wrongly | The filter reads the current user's tenant from the database context; context pooling or `IgnoreQueryFilters` would break it | Keep the context non-pooled; grep for `IgnoreQueryFilters` and limit it to seeding and tests |
| 3 | Seeding breaks | Seeding runs with no user, so the filter hides everything and the interceptor refuses to save | Seed with an explicit tenant and `IgnoreQueryFilters()` |
| 4 | New sign-ups have no company | The built-in registration endpoint knows nothing about companies | Fail closed (empty list / forbidden); document an admin assignment step |
| 5 | Old tenant claim after a user moves company | The tenant lives in the login cookie or token | Refresh the security stamp when a user's company changes |
| 6 | Existing tests fail | Tests insert lists without a tenant and use a mocked `IUser` | Give `TestApp` and the mock a tenant; bypass the filter in raw-data helpers |
| 7 | Template options don't build | The `#if` blocks in the dependency-injection setup cover cookie and bearer, plus three database providers | Run `build/test.ps1` across all options |
| 8 | Duplicate-title race | The title check is only a validator | Unique `(TenantId, Title)` index |
| 9 | Adopters with existing data | Here the database is recreated each start, but real deployments use migrations | Ship a migration with a backfill to a default company |

Riskiest: #1, an item attached to another company's list through the client-supplied `ListId`.
