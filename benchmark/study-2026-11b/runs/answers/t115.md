This plan changes the default signing digest in this repo (itsdangerous 2.3.0.dev) from SHA-1 to SHA-256. No files were edited; the plan is saved at `claude-home/plans/change-the-default-signing-glittery-koala.md`. The main cost is that every token signed with the current default stops verifying after the upgrade unless the app adds a SHA-1 fallback.

**Assumptions** (no one was available to ask)
- It ships in the unreleased 2.3.0 as a documented breaking change. The maintainers might prefer to hold it for 3.0.
- There is no automatic SHA-1 fallback. It would keep SHA-1 in the default path, and on FIPS builds (where Python's `hashlib` has no SHA-1) a bad token would raise a hashlib error instead of the expected `BadSignature`. Apps that need to accept old tokens opt in through the existing `fallback_signers` option.
- The private helper `_lazy_sha1` stays, because tests and possibly other projects import it.

**Changes**
1. **`src/itsdangerous/signer.py`**
   - Set `default_digest_method = staticmethod(hashlib.sha256)` in two places, `HMACAlgorithm` (line 54) and `Signer` (line 120). Change both together; otherwise a `Signer` built with an explicit `HMACAlgorithm()` would sign with one hash but derive its key with another.
   - Update the docstrings (51–53, 94–97, 114–119) and add a `.. versionchanged:: 2.3` note.
   - Keep `_lazy_sha1`, documented as the way to set up a legacy fallback.
2. **`tests/test_itsdangerous/test_serializer.py`**
   - `test_digests`: the default now produces `[42].u5jm88LwiD3aYOixoxwYUWacbKYcSnVL8cnS-4lgb4U`. I computed this with the current code and an explicit SHA-256, not after the change. Keep the existing explicit-SHA-1 value as a legacy check.
   - `test_iter_unsigners`: expect `hashlib.sha256` for the first unsigner.
   - `test_fallback_signers`: rewrite it to show the real migration, where an old SHA-1 token loads through a SHA-1 fallback.
   - Add a test that a token signed with the new default is rejected by a SHA-1 signer.
3. **Docs**
   - Rewrite "Digest Method Security" in `docs/concepts.rst` (137–155): the default is now SHA-256, and it covers how to keep accepting old tokens or keep using SHA-1.
   - Turn the fallback example in `docs/serializer.rst` (95–104) into an upgrade recipe.
   - Add a breaking-change entry to `CHANGES.rst` covering invalidated tokens, longer signatures and the fallback recipe.
4. **Plain `Signer`/`TimestampSigner`** have no fallback option, so the docs need a manual recipe: catch `BadSignature` and retry with a SHA-1 signer, or keep SHA-1 explicitly.

**Verification**
- Run `pytest` plus the typing and docs builds through `tox`.
- Sign a token with the old code on `main` and confirm it fails under the new default but loads with a SHA-1 fallback.
- Grep `src` and `docs` for any leftover SHA-1 mentions.
- Optionally, with SHA-1 made unavailable (FIPS mode or a patched `hashlib.sha1`), confirm the default path never touches SHA-1.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing tokens invalidated on upgrade | Default-signed session cookies, reset links and email confirmations all fail `BadSignature` | Changelog entry plus a documented `fallback_signers=[{"digest_method": hashlib.sha1}]` recipe |
| 2 | Derived key changes as well | `derive_key` (all three methods) hashes with `digest_method` | A fallback with SHA-1 covers both; add a test |
| 3 | No fallback on plain `Signer`/`TimestampSigner` | Only `Serializer` has `fallback_signers` | Document catch-and-retry or keeping SHA-1 |
| 4 | Longer tokens | Signature grows from 27 to 43 chars, so cookies, URLs and DB columns may overflow | Call it out in the changelog |
| 5 | Breaking change in a minor release | Users pinned to `<3` get the change silently | Prominent changelog entry; maintainers may choose 3.0 |
| 6 | Defaults diverge | Changing `Signer` but not `HMACAlgorithm` gives inconsistent signatures | Change both together; test `algorithm=HMACAlgorithm()` |
| 7 | Downstream libraries assume SHA-1 | Code that imports `_lazy_sha1` or compares defaults | Keep `_lazy_sha1`; note it in the changelog |
| 8 | Mixed-version deployments | During a rolling deploy, old nodes reject new tokens | Advise deploying the fallback config before the switch |

Riskiest: #1. Every existing token signed with the default stops verifying the moment users upgrade.
