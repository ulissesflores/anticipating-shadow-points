Most of this is already in the repo. `src/Conduit/Infrastructure/Security/PasswordHasher.cs` creates new hashes with ASP.NET Identity's PBKDF2-HMAC-SHA512 at 210,000 iterations. It still accepts the old HMAC-SHA512 hashes, and `src/Conduit/Features<home>:79` rehashes a user's password to the new format the next time they log in successfully. `PasswordHashingTests.cs` covers this.

The real gap is that users who never log in keep the weak old hash in the database forever. The plan below closes that without resets. It is saved in `plans/store-passwords-with-a-sparkling-spring.md`; no repo files were edited.

**Assumptions**
- "Stronger" means stronger than the old HMAC-SHA512 hashes, which use a fixed key and so are effectively one SHA-512 per guess.
- The bar is OWASP-level PBKDF2, which uses only what .NET ships with, rather than Argon2id, which would need a third-party package.
- Running a one-off upgrade job is acceptable.

**Plan**
1. **Mark each hash with its format.** Today an old hash is recognised only by its size (a 64-byte hash with a 16-byte salt). Add an explicit first byte for each format, using one Identity doesn't use (e.g. `0xF1`). `Verify` then checks that byte to pick the scheme. Anything it doesn't recognise, or an empty hash, fails.
2. **Wrap old hashes in the new algorithm.** Store `0xF1 + PBKDF2(old hash)` and keep the old salt. To check a password, compute the old hash from it, check that against the stored PBKDF2 hash, and return "rehash needed". The existing login code then replaces it with a normal new hash. This is safe to do without knowing anyone's password.
3. **Add an upgrade job** that converts every old hash in the database this way. It runs on demand (a startup switch or a config-gated background service), works in batches, can be run twice safely, and only writes a row if its hash hasn't changed in the meantime. It can't live in an EF migration because the hashing has to run in C#. No schema migration is needed because the hash and salt columns have no size limit.
4. **Make the iteration count configurable**, never below 210,000. Identity already flags hashes with a lower count for rehash, so raising it later upgrades users as they log in.
5. **Stay on PBKDF2 for now.** Moving to Argon2id later only needs one more format byte.
6. **Update `docs/database-migrations.md`.** It still says the salt column exists for checking old hashes; it should describe the upgrade job, the backup step, and what can't be rolled back.
7. **Add tests** to `PasswordHashingTests.cs`:
   - A wrapped hash accepts the right password, rejects a wrong one, and is rehashed on login.
   - The upgrade job converts old rows, skips new ones, and changes nothing on a second run.
   - The old hash itself can't be used as a password.
   - A lower stored iteration count triggers a rehash.
   - Unknown format bytes fail.
8. **Check** with `dotnet run --project build/build.csproj -- test`, then seed an old-format user in SQLite, run the job, and log in through the API.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Accounts locked out by a wrong conversion | The job rewrites every old hash, and the plaintext isn't available to re-check it | Back up first; test on a copy first; verify a sample of converted rows before saving them |
| 2 | Old and new formats confused | Formats are currently told apart by size only | Explicit format byte; a test for every format |
| 3 | Login with the old hash instead of the password | The wrapped hash takes the old hash as its input | Tests prove the old hash itself fails as a password |
| 4 | Login and the job overwrite each other | Login rehashes while the job writes the same row | Write only if the hash is unchanged, otherwise skip the row |
| 5 | CPU spike or slow-login denial of service | 210k+ iterations on every login, plus the batch job | Keep the default cost; small batches; rate-limit login |
| 6 | Faster "no such user" reply reveals which emails exist | Login returns before hashing when the email doesn't exist | Hash a dummy password in that path too |
| 7 | Rollback breaks logins | An older build can't read the new format byte | Ship the code that reads the new format first; run the job later |
| 8 | SQLite and SQL Server behave differently | Separate providers and transactions | Run the job's tests on both |
| 9 | Pressure to adopt Argon2id via an unvetted package | No Argon2 is built into .NET | Decide it separately; the format byte makes it easy to add later |

Riskiest: #1. Converting every stored old hash in bulk is the only step that can lock users out with no way back, so a verified backup must come first.
