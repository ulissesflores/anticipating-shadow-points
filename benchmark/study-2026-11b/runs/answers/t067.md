# Plan: replace integer summary IDs with UUIDs (compatibly)

I didn't write the plan file, because you said not to edit any file. I read the code and didn't run anything.

## Assumptions
- The repo is a FastAPI + Tortoise ORM + Postgres service with one model, `TextSummary`. It uses aerich migrations (`project/migrations/models/0_..._init.py`) and has a single resource, `/summaries/`. `id` is a serial integer on the table. It is exposed in the path `/{id}/` as `int, gt=0`, and in the POST, GET, PUT and DELETE response bodies.
- "Existing clients keep working" means three things:
  - Old integer IDs that clients stored still resolve.
  - Responses keep the `id` field with its current type for a deprecation window.
  - Clients that send only integers don't break.
- The app has other consumers and a live database. Rows can't be dropped, and deploys must be rolling with no downtime.
- The background task `generate_summary(summary_id, url)` in `app/summarizer.py` takes the internal key. I haven't read that file, so I'm assuming it keys on the row's id.

## Design
Keep the integer primary key internally and add a public UUID column next to it. Don't swap the primary key. Swapping would rewrite every foreign key and index and force a risky table rewrite. The table has no foreign keys today, but the pattern should stay safe if any are added.

- Model: add `uuid = fields.UUIDField(unique=True, default=uuid4, index=True)`. Leave `id` as the primary key.
- API contract:
  - Expose `id` as the UUID and `legacy_id` as the integer. This is the end state, but it changes the type of `id`, so it breaks old clients.
  - To avoid that break, keep `id` as the integer during the transition and add `uuid` as a new field. Clients migrate at their own pace. Then flip in a later major version or under `/v2`.
  - I recommend the additive route. Responses carry `id` (int, deprecated) and `uuid` for one or two release cycles. Add a `Deprecation` header when an integer ID is used.
- Path parameter: accept `id: Union[UUID, int]`, with the UUID tried first, and look the row up by the matching column. A shared dependency `resolve_summary_key` in `app/api/summaries.py` should do this so all four routes use it. Return 404 for unknown values and 422 for malformed ones, as today. Validation errors for `loc: ["path","id"]` change message text, so tests need updating.
- `crud.py`: add a helper such as `_filter_key(key)` that returns `filter(uuid=key)` or `filter(id=key)`. Use it in `get`, `put` and `delete`. `post` returns the UUID and the integer id.
- Pydantic: `SummaryResponseSchema` gains `uuid: UUID`. `SummarySchema` is generated by `pydantic_model_creator`, so it picks the new field up automatically.

## Migration (expand, backfill, contract)
1. **Expand.** Add a new aerich migration with `ALTER TABLE textsummary ADD COLUMN uuid UUID`. Add `DEFAULT gen_random_uuid()` for new rows (built in since Postgres 13). Create a unique index with `CREATE UNIQUE INDEX CONCURRENTLY`, because plain `CREATE INDEX` locks the table. Write the migration by hand rather than using autogenerate, so these options are explicit.
2. **Backfill.** Fill existing rows in batches, with `UPDATE ... WHERE uuid IS NULL` over id ranges. Then set `NOT NULL`. On large tables, add the constraint as `NOT VALID` and then run `VALIDATE`.
3. **Deploy the dual-key code.** It accepts both forms and returns both fields.
4. **Contract, later and optional.** Once metrics show no integer-ID traffic, drop the deprecated `id` from responses. The internal integer key can stay forever.
5. Write the `downgrade` function. The existing init migration has an empty one, so downgrades aren't currently reversible.

## Testing
- Update `tests/test_summaries.py`. Existing tests use `summary_id` from the POST response and `"loc": ["path","id"]` error shapes. Parametrize them over both integer and UUID paths.
- Add tests:
  - an unknown UUID returns 404
  - a malformed ID returns 422
  - an old integer ID still resolves to the same row as its UUID
  - PUT and DELETE work with either form
  - the response includes both fields
- Add a migration test: seed rows on the old schema, apply the migration, and check that all rows have unique, non-null UUIDs.
- Run the full flow with `docker-compose` against Postgres. The tests use `web_test` created by `db/create.sql`.
- Check that the OpenAPI schema now shows `uuid` and the `Union` path parameter.

## Rollout
1. Ship the migration alone first (steps 1 and 2).
2. Ship the code.
3. Announce the deprecation, with a date for step 4.
4. Watch the integer-ID usage metric before contracting.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Changing the type of `id` in responses breaks clients | Clients parse `id` as an int and build URLs from it | Keep `id` an int and add `uuid`; flip only in a major version |
| 2 | Table lock or long rewrite during migration | A plain `ADD COLUMN ... DEFAULT` and index build can lock `textsummary` | Add the column nullable, backfill in batches, use `CREATE INDEX CONCURRENTLY` |
| 3 | Code deployed before migration, or a rollback after it | Rolling deploys mean old and new pods overlap, and a model with `uuid` fails on the old schema | Expand and backfill first, deploy second, and keep the old code compatible with the new column |
| 4 | Integer and UUID path parsing is ambiguous | `Union[UUID, int]` may coerce wrongly, and `"123"` could be read as either | Try UUID first, then int; keep one shared resolver; test edge cases |
| 5 | Sequential integer IDs stay usable as an enumeration vector | Integer lookups still work, so the security gain is partial | Add auth or ownership checks, and set a date to retire integer lookup |
| 6 | Background task keys on the wrong ID | `generate_summary(summary_id, url)` gets the id from `crud.post` | Pass the same internal key it uses today; test the task end to end |
| 7 | Backfill duplicates or leaves NULLs | A unique constraint added before the backfill finishes will fail | Backfill, verify, then add `NOT NULL` and the unique index |
| 8 | Hand-written migration drifts from aerich state | Aerich tracks model state, so a manual migration can desync | Generate it with aerich, then edit it, and run a clean-DB migration in CI |
| 9 | Existing tests encode the integer contract | `gt=0` and the 422 error shapes change | Update the tests deliberately and keep a legacy-integer test set |
| 10 | Stored integer IDs in client caches or logs go stale if integer lookup is removed | Removing integer lookup too early silently breaks them | Add a `Deprecation` header and a usage metric, and set a sunset date |

Riskiest: #1, because changing the type of `id` in responses breaks every existing client at once, with no warning.
