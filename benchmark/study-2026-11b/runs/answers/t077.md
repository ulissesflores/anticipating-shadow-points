## Assumptions

- I read the repo (a FastAPI + Tortoise ORM + Postgres + aerich service) but did not edit anything. Your no-edit instruction overrides plan mode's plan-file step, so there is no plan file.
- The only integer ID exposed is `TextSummary.id`, used in `/summaries/{id}/` and in the `id` field of the responses.
- Existing clients are unknown external callers. They send integers in paths and may parse `id` as an integer.
- Postgres is 13 or later, so `gen_random_uuid()` is available without an extension.
- I treat "keep clients working" as the hard constraint, so this is not a big-bang swap of the primary key.

## Ways this could go wrong (before planning)

1. Clients that parse `id` as an int break if `id` suddenly becomes a UUID string.
2. Old integer IDs that clients have stored, bookmarked or cached stop resolving.
3. The migration locks or rewrites the table, or leaves NULL or duplicate UUIDs after backfill.
4. A deploy and migration ordering gap: old code runs against the new schema, or new code runs against the old one, during a rolling deploy.
5. The path parameter's int-only validation (`Path(..., gt=0)`) rejects UUIDs. If I loosen it, the 422 error shape changes, and `tests/test_summaries.py` asserts that shape.
6. Callers that pass the integer internally (`generate_summary(summary_id, ...)` in the background task, and the `crud.*` functions) get mixed up with the public identifier.
7. Swapping the primary key itself would rewrite any foreign keys and indexes. Currently there are none, but any added later would be affected.
8. Anyone relying on integer ordering or `created_at` ties for pagination loses the sort order, because random UUIDs (v4) don't sort.
9. Integer-looking input is ambiguous or a probing vector. Dual lookup could leak existence or allow enumeration if the integer path stays open for good.
10. The downgrade migration is empty, so rollback is impossible after the backfill.

## Plan (recommended, not executed)

1. **Schema:** keep the integer primary key as an internal surrogate. Add a `uuid` `UUIDField(unique=True, default=uuid4)`. The aerich migration adds the column as nullable, backfills with `gen_random_uuid()`, then sets NOT NULL and a unique index. Write a real downgrade.
2. **Responses:** return `uuid` alongside the existing integer `id`, marked deprecated. Add `uuid` to `SummaryResponseSchema` and `SummarySchema`. Existing int parsers keep working.
3. **Path lookup:** accept `int | UUID` in `/summaries/{id}/`. Route to the integer or UUID column by type, in one helper in `crud.py`. Keep 404 and 422 behaviour for invalid input.
4. **v2 (optional):** add `/v2/summaries/` where `id` is the UUID. Set a deprecation window and `Deprecation`/`Sunset` headers on v1.
5. **Internals:** keep background tasks and the `crud` functions on the internal integer. Only the API layer deals with UUIDs.
6. **Tests:** cover both ID forms for get, put and delete. Cover the 422 shape, backfill correctness and the migration on a populated DB.
7. **Rollout:** run the migration first (expand), then deploy the code. Remove integer exposure only after the sunset (contract).

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Clients break on a non-int `id` | `id: int` is in the response contract | Keep int `id`, add `uuid`, use v2 for a UUID `id` |
| 2 | Stored integer IDs stop resolving | Clients may cache or bookmark `/summaries/3/` | Dual lookup by int or UUID through the sunset |
| 3 | Backfill leaves NULL or duplicate UUIDs | Added column on a populated table | Nullable, backfill, then NOT NULL and unique, in separate steps |
| 4 | Deploy and migration order mismatch | Rolling deploy runs mixed versions | Expand, then deploy, then contract; the new column is nullable until code is live |
| 5 | 422 error shape changes | Tests assert `loc: ["path","id"]` and int errors | Update the tests deliberately and document the change |
| 6 | Public and internal IDs get mixed | The background task and `crud` take an int | Convert only at the API boundary, with one lookup helper |
| 7 | Empty downgrade blocks rollback | The existing migration's downgrade is blank | Write an explicit downgrade that drops the column |
| 8 | Integer enumeration stays open | Dual lookup keeps guessable IDs reachable | Put a sunset date on int access and monitor its usage |
| 9 | Lost ordering | UUIDv4 doesn't sort by creation | Sort on `created_at`, or use UUIDv7 |
| 10 | Wrong assumptions about clients | Who the clients are is unknown | Check access logs for the ID format in use before the sunset |

Riskiest: #1, swapping the response `id` to a UUID breaks existing clients immediately, so the plan keeps the integer `id` and adds `uuid` beside it.
