## Assumptions
- The target is this repo, `express-session` 1.19.0. "Roll by default" means flipping the default of the existing `rolling` option from `false` to `true`.
- Users can still pass `rolling: false` to get the old behavior.
- This is a breaking default change, so it needs a major version bump and a `HISTORY.md` entry. Releasing is out of scope.

## What I found
- `index.js:109` has `var rollingSessions = Boolean(opts.rolling)`. An omitted option becomes `false`.
- `index.js:491` is the only place the flag is used. In `shouldSetCookie`, an existing session gets `rollingSessions || (cookie.expires != null && isModified(session))`.
- `shouldTouch` (`index.js:~472`) doesn't depend on `rolling`. Store `touch` calls therefore don't change. Only `Set-Cookie` emission does.
- `README.md` (~line 295) documents `rolling` with a default of `false`. `index.js:78` has the JSDoc.
- `test/session.js` has a `describe('rolling option')` block (~line 1158). Other tests may assume that unmodified requests get no `Set-Cookie`.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Breaking default for existing apps | Sessions that used to expire at a fixed time now slide forever | Major bump, a prominent HISTORY note, and a README migration line |
| 2 | Sessions never expire for active or polling clients | `maxAge` becomes idle timeout, so health checks or XHR pings keep sessions alive | Document it. Recommend an absolute-lifetime check in app code |
| 3 | `Set-Cookie` on every response breaks CDN and cache behavior | Shared caches won't cache, or may strip, responses that carry cookies | Tell users to use `rolling: false` or to mount the middleware after static routes |
| 4 | Existing tests fail or silently pass | Many tests assume cookies are only set on modification | Audit each failure and pin `rolling: false` deliberately |
| 5 | Stale cookie `Expires` vs store TTL drift | The cookie rolls but the store only extends via `touch`. Stores without `touch` and with `resave: false` expire server-side early | Document the `touch` and `resave` interaction. Keep the existing warning text |
| 6 | Parallel-request races | Multiple in-flight responses each set a cookie, and the last one wins | The values are identical apart from `Expires`. Note it as low impact |
| 7 | Privacy and compliance, consent-gated cookies | Cookies get re-sent on every response, not only after consent-gated changes | `saveUninitialized: false` still blocks cookies for new sessions. Document this |
| 8 | Downstream wrappers pass `rolling` through | Libraries that forward `undefined` now get `true` | Treat only `undefined` as unset and keep explicit `false` honored |
| 9 | Increased response header size and bandwidth | Every response grows by a cookie header | Accept it as a minor cost and mention it in the docs |

Riskiest: #1, the breaking default for existing apps, because it silently changes session lifetime semantics, and the session-lifetime effect in #2 compounds it.
