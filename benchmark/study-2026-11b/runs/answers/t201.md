**Where this stands:** the repo already contains most of this change, so I made no edits and ran nothing beyond read-only greps and file reads.

- `src/Conduit/Infrastructure/Security/PasswordHasher.cs` issues ASP.NET Identity V3 hashes (PBKDF2, 210k iterations, random salt embedded in the payload).
- The same file still verifies legacy 64-byte HMAC-SHA512 hashes that have a 16-byte salt, and returns `SuccessRehashNeeded` for them.
- `Login.cs:79-84` rewrites the hash on a successful login. `Create.cs` and `Edit.cs` always write the new format.

**Assumptions**
- "Stronger" means a memory-hard or iterated KDF. I assume Identity V3 PBKDF2 at 210k iterations counts, rather than Argon2id or bcrypt.
- "No forced reset" means lazy rehash on the next successful login. I assume bulk re-hashing is impossible, because the plaintext isn't available.
- The remaining work is a gap review and tests, not a new design. I haven't checked whether the integration tests cover the legacy-to-new upgrade path.
- One deployment runs against SQLite or SQL Server, with possibly more than one app instance.

**Ways this could go wrong, before planning**
- Legacy verification breaks. The detection `hash.Length == 64 && salt.Length == 16` is a heuristic, and an off-by-one or an empty salt would lock users out.
- Dormant accounts keep the weak legacy hash indefinitely, because lazy migration only upgrades users who log in. The legacy scheme uses a fast HMAC with a constant key (`"realworld"`), so a database leak is still cheap to crack.
- The rehash happens inside the login request. A failed `SaveChangesAsync` or a concurrent login could fail an otherwise valid login, or race.
- Rolling back the app after hashes are upgraded locks those users out, because old code can't read the new format.
- A higher iteration count raises login CPU cost. That enables CPU-based denial of service on `/users/login` without rate limiting.
- Unknown emails return immediately, while valid ones pay the full hash cost. The timing difference allows user enumeration.
- Future changes to the work factor depend on `SuccessRehashNeeded` from Identity, and the legacy branch bypasses that logic.
- The `Hash` and `Salt` columns have no format marker. Detection by length is fragile if a new algorithm such as Argon2 is added later.
- Tests may not seed real legacy-format hashes, so the migration path could be untested.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Legacy users locked out | Detection relies on a 64-byte hash and 16-byte salt | Add tests with real legacy fixtures, including edge lengths |
| 2 | Dormant accounts stay weak | Rehash only happens on login | Add a metric and a sunset plan; optionally wrap legacy hashes in the new KDF offline |
| 3 | Rehash write fails or races | It runs inline in `Login.Handle` | Log and swallow save errors, and use optimistic concurrency |
| 4 | Rollback breaks logins | Old code can't verify Identity V3 payloads | Ship verify-only support first, then enable writes |
| 5 | Login CPU denial of service | 210k PBKDF2 iterations per attempt, with no throttle visible | Add rate limiting and tune the iteration count |
| 6 | User enumeration by timing | A missing user skips hashing | Run a dummy hash when the user isn't found |
| 7 | Format ambiguity | There is no version column, only length sniffing | Add a scheme marker or prefix in a migration for both providers |
| 8 | Migration gaps | SQLite and SQL Server need separate snapshots | Add a migration to both providers if the schema changes |
| 9 | Untested upgrade path | RealWorld contract tests don't cover hashing | Add integration tests for the legacy login, upgrade and relogin sequence |
| 10 | Password change skips rehash | The `Edit.cs` and `Create.cs` paths must stay consistent | Use one hashing entry point and assert it in tests |

Riskiest: #1 — legacy-hash detection by length could lock out existing users.
