## Assumptions

- "Without breaking links" means the old slug URL must keep working: `GET /api/articles/<old-slug>` and the front-end link it backs. A redirect or alias is acceptable, and the old URL doesn't have to stay canonical.
- Only the article's author can rename it. The existing ownership checks in `ArticleUpdate` stay as they are.
- This is a SQLite/GORM service, and the schema is migrated by `AutoMigrate`. I haven't verified the migration setup.
- Current state: `ArticleUpdate` (`articles/routers.go:152-160`) already regenerates the slug when the title changes. It overwrites `slug` in place and keeps no record of the old value. After a rename, the old slug returns 404 in `FindOneArticle(&ArticleModel{Slug: slug})`, which every `:slug` route uses (update, delete, favorite, unfavorite, comments). So the missing piece is old-slug resolution, not slug generation.

## How this could go wrong, before planning

1. **Old links 404.** This is the current behavior, and it is the bug being fixed.
2. **Slug hijack.** Once an article leaves its old slug, `makeUniqueSlug` sees the slug as free. A new article titled the same as the old title would take it, and shared links would then open the wrong article.
3. **Redirect loops or chains.** Renaming A→B→A, or A→B→C, can leave aliases pointing at each other or at stale slugs.
4. **Alias and live slug collide.** An alias can equal a live slug, or two articles can claim the same alias. The alias table needs its own unique index, and `makeUniqueSlug` must check it too.
5. **Wrong handler behavior on old slugs.** If resolution is added only to `GET`, write routes behave inconsistently. Writes through an old slug should either work or fail cleanly. Silently mutating via an alias is a surprise.
6. **Concurrent renames.** `makeUniqueSlug` is check-then-act, so races are possible. The existing retry on `ErrDuplicatedKey` only covers the `articles.slug` index, not a new alias table. The alias insert and the slug update must share one transaction.
7. **Soft-delete interaction.** `makeUniqueSlug` uses `Unscoped()`, so deleted articles hold their slugs. Aliases of deleted articles need the same treatment, or they would resolve to a deleted row or be reused.
8. **Redirect contract in a JSON API.** An HTTP 301 on an API route may break clients that don't follow redirects. Serving the article directly, with the canonical slug in the body, is safer. The RealWorld spec and the hurl/bruno suite (#57) don't define redirects.
9. **Lookup cost and N+1.** An extra alias query on every miss adds latency. A recent commit (#49) removed N+1 queries, so the fallback must not regress that.
10. **Existing data and tests.** There is no backfill problem, because old slugs are only recorded from now on. However, tests that expect 404 for a stale slug will change. Also, a title that changes but produces the same slug must not create a self-alias (`base != articleModel.Slug` handles this today).

## Proposed approach (not executed)

- Add an `ArticleSlugModel` (`slug` unique, `article_id` indexed) in `articles/models.go`, and include it in `AutoMigrate`.
- In `ArticleUpdate`, do the slug change in one transaction. Insert the old slug into the alias table, then update the article. Retry on duplicate-key errors, as the code already does.
- Make `makeUniqueSlug` also reject any slug present in the alias table, which closes the hijack.
- Add a resolver. On a miss in `FindOneArticle`, look up the alias and load the article by `article_id`. Use it for `GET`, which returns the canonical slug in the body. Decide separately whether writes accept aliases. I'd allow it only for the author.
- Delete aliases when the article is hard-deleted. Rely on soft delete otherwise.
- Tests: rename then fetch by the old slug, A→B→A, a new article reusing an old title, a concurrent rename, and a delete after rename. Then run `go test ./...` and the hurl/bruno suite.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Old slug hijacked by a new article | Rename frees the old slug, and `makeUniqueSlug` only checks `articles` | Check the alias table in `makeUniqueSlug` |
| 2 | Alias and slug update not atomic | Two writes in `ArticleUpdate`, and the retry only covers the `articles.slug` index | One transaction, plus unique index on alias |
| 3 | Rename back (A→B→A) loops or conflicts | The old slug is now both an alias and the live slug | Drop the alias when its slug becomes live again |
| 4 | Concurrent renames collide | `makeUniqueSlug` is check-then-act | Retry on `ErrDuplicatedKey` across both tables |
| 5 | Writes via old slug behave inconsistently | Every `:slug` route calls `FindOneArticle` | Central resolver, with explicit write policy |
| 6 | 301 breaks API clients | The hurl/bruno suite and clients expect JSON | Serve the article directly with the canonical slug |
| 7 | Deleted articles' aliases linger | `makeUniqueSlug` uses `Unscoped`, so soft-deleted rows hold slugs | Cascade alias deletion, and resolve only live articles |
| 8 | Extra query on each lookup miss | Commit #49 removed N+1 queries | Query the alias only on a miss, indexed |
| 9 | Existing tests expect 404 for stale slugs | Behavior change | Update tests and add rename-specific coverage |
| 10 | Schema change in prod DB | Depends on how `AutoMigrate` is run | Additive table only, no changes to existing columns |

Riskiest: #1, an old slug being reused by another article, because shared links would silently open the wrong content.
