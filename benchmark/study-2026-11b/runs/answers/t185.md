**Assumptions** (non-interactive run, no files edited, no plan file written):
- This is `itsdangerous`. The default is `default_digest_method = staticmethod(_lazy_sha1)`, set in `src/itsdangerous/signer.py` on both `Signer` and `SigningAlgorithm`. The docs and docstrings also say "SHA1".
- "Default signing digest" means that class attribute. It does not mean the key-derivation hash.
- Changing the default is wanted even though it breaks signatures that already exist.
- A release note goes in `CHANGES.rst` under the unreleased 2.3.0 entry.

**What could go wrong, before planning**
- **Existing signatures stop verifying.** Any token or cookie signed with SHA-1 fails `unsign` or `loads` once a consumer upgrades. That means sessions, password-reset links, and confirmation tokens.
- **Rollout skew.** During a rolling deploy, old and new app instances sign and verify with different digests, so users on mixed fleets get intermittent failures.
- **Fallback signers mask or miss the problem.** `default_fallback_signers` is `[]`. A SHA-1 fallback would keep old tokens valid, but it also keeps accepting SHA-1 forever.
- **Key derivation changes too.** The derived key is `digest_method(salt + secret)` under the default `key_derivation="django-concat"`. A new digest means a new key, not just a new MAC, so a custom `digest_method` that already works could behave differently.
- **Signature length and format change.** The base64 signature grows from 28 to 43 characters, so cookie, URL, and header size limits can be exceeded. Anything that parses or length-checks tokens breaks too.
- **Hard-coded tests.** `tests/test_itsdangerous/test_serializer.py` asserts that the default equals SHA-1 (`default_value == sha1_value`, `_lazy_sha1`). The literal `"[42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM"` is a SHA-1 value. These tests fail by design and need rewriting.
- **FIPS and import-time laziness.** The `_lazy_sha1` wrapper exists so FIPS builds don't fail at import. A replacement must stay lazy, and `hashlib.sha256` is not lazy-safe in every restricted build.
- **Downstream and third-party code.** Flask, Werkzeug, and others pin or assume the default. Code that reads `Signer.default_digest_method` or compares it to `hashlib.sha1` can break.
- **Cross-system interop.** Other services (non-Python, or older itsdangerous) that verify the same tokens will reject the new ones.
- **Little security gain for the effort.** HMAC-SHA1 is not practically broken. The change is mainly policy and compliance, so the breakage cost may exceed the benefit unless a migration path exists.
- **Semver.** This is a breaking behavioural change. It fits a major release, or it needs an opt-in. A 2.3.0 minor bump may not be appropriate.

**Main risks**

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing tokens fail verification | Default feeds both the MAC and the derived key | Ship a SHA-1 fallback signer for a migration window |
| 2 | Mixed-version rollout | Old and new instances disagree on the digest | Deploy verify-both first, then switch signing |
| 3 | Permanent SHA-1 fallback | `default_fallback_signers` is empty, and a fallback added for migration may never be removed | Add a documented removal date and a deprecation warning |
| 4 | Key derivation shifts | `django-concat` hashes `salt+secret` with the digest | Test derived-key vectors and document the change |
| 5 | Longer signatures | The base64 signature grows from 28 to 43 characters | Check cookie and URL limits, and tell users |
| 6 | Tests and docs pin SHA-1 | The default-equals-SHA-1 assertion and the hard-coded signature fail | Update the tests, the docstrings, and `CHANGES.rst` |
| 7 | FIPS and import-time breakage | `_lazy_sha1` exists to avoid import-time failure | Keep the default lazy, and test with a restricted hashlib |
| 8 | Downstream Flask and Werkzeug breakage | They assume the current default | Run their test suites, and coordinate the release |
| 9 | Cross-service interop | External verifiers still expect SHA-1 | Inventory verifiers and give an explicit-config escape hatch |
| 10 | Semver violation | Tokens silently stop validating on a minor bump | Release as a major, or make it opt-in first |

Riskiest: #1, because existing signed tokens stop verifying on upgrade, with no code error to point at.
