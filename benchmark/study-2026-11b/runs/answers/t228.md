# Plan: default signing digest SHA-1 → SHA-256

**Assumptions**
- The repo is `itsdangerous`, with version 2.3.0 unreleased. I'm treating this as a deliberate behavior change in that release. I'm also assuming the maintainers accept a break for existing signed data.
- The old default stays reachable through an explicit `digest_method` or `fallback_signers`. I'm not adding a new config knob.
- I haven't edited anything, as you asked. The plan file Plan mode asked for is skipped for the same reason.

**What I found**
- `src/itsdangerous/signer.py:40` defines `_lazy_sha1`. `SigningAlgorithm.default_digest_method` (line 54) and `Signer.default_digest_method` (line 120) both point to it.
- `digest_method` also feeds key derivation, in `derive_key` at lines 201–209. Changing the default therefore changes the derived key as well as the HMAC.
- `tests/test_itsdangerous/test_serializer.py` has two assertions that depend on the default. `test_iter_unsigners` (line 180) checks for `_lazy_sha1`. `test_digests` (lines 186–) pins the default output to the SHA-1 vector `-9cNi0CxsSB3hZPNCe9a2eEs1ZM`.
- `CHANGES.rst` (line 105) records that the default was already moved off SHA-1 once and then reverted in PR #113. That history matters here.
- `docs/concepts.rst` (lines 137–152), `docs/serializer.rst` (lines 82–103) and the docstrings in `signer.py` all say SHA-1 is the default.

**Steps**
1. **Code:**
   - In `signer.py`, add `_lazy_sha256(string=b"")` that calls `hashlib.sha256` at runtime. Keep it lazy so FIPS builds don't fail at import (issue #375).
   - Point both `default_digest_method` attributes at it.
   - Keep `_lazy_sha1`, since tests and users may import it.
   - Update the docstrings at lines 51–52, 94–100 and 114–120.
2. **Migration path:**
   - The default is `default_fallback_signers`, in `serializer.py` around line 102. Check what it holds. Leave it empty by default, so SHA-1 tokens stop validating unless users opt in.
   - Document the opt-in as `fallback_signers=[{"digest_method": hashlib.sha1}]`. The example is already in `docs/serializer.rst`.
3. **Tests:**
   - Update `test_iter_unsigners` to expect the SHA-256 default.
   - In `test_digests`, replace the default-equals-SHA-1 assertion with default-equals-SHA-256. Pin a new SHA-256 vector, and keep the explicit SHA-1 and SHA-512 vectors.
   - Add a test that a SHA-1-signed token fails to load by default and loads with the SHA-1 fallback.
   - Add a test for the timestamp and URL-safe serializers' token round trip.
4. **Docs and changelog:**
   - Rewrite the "Digest Method Security" section in `docs/concepts.rst` so SHA-256 is the default.
   - Add a prominent `CHANGES.rst` entry under 2.3.0 saying existing signatures are invalidated, with the fallback recipe.
5. **Verify:**
   - Run `uv run pytest`, plus the type check and linters from `pyproject.toml`.
   - Hand-check one SHA-1 token against the new default and the fallback.
   - Run once in a FIPS-like environment (SHA-1 disabled) to confirm import still succeeds.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing tokens stop validating | Cookies, reset links and sessions signed with SHA-1 fail `loads`, because the default has no fallback | Document the SHA-1 `fallback_signers` recipe, add a changelog warning, and add a test for the fallback |
| 2 | Key derivation changes too | `derive_key` hashes with `digest_method`, so the key changes along with the HMAC | State this in the docs, and test the old-to-new fallback end to end |
| 3 | Signature length and token format change | A SHA-256 MAC is longer than SHA-1, which affects length-limited cookies and URLs, plus any schema or regex that assumes the old length | Note the longer tokens in the changelog, and check size limits in dependents |
| 4 | Downstream libraries pin the default | Flask and similar libraries rely on the default or on subclass overrides | Pin the version and test against dependents, or release as a major or minor bump with a notice |
| 5 | Rollout skew across instances | Mixed old and new versions reject each other's tokens during a deploy | Roll out the fallback first, then the new default |
| 6 | Hardcoded test vectors break | `test_digests` and `test_iter_unsigners` encode SHA-1 | Regenerate the expected vectors from the new default, and keep the explicit SHA-1 vector |
| 7 | FIPS import-time failure | A non-lazy `hashlib.sha256` reference could break FIPS builds | Keep the lazy wrapper, and test with SHA-1 disabled |
| 8 | Another revert like PR #113 | The default was already reverted once, so it may have hit hidden breakage | Read PR #113's reasoning before merging, and ship the migration docs with the change |

Riskiest: #1, because existing SHA-1-signed tokens fail validation by default unless users add the fallback.
