## How this change could go wrong

These come from reading `project/app` (FastAPI + Tortoise ORM + Aerich on Postgres):

1. **Changing what `id` means breaks clients.** Responses like `{"id": 1, "url": ...}` (`app/models/pydantic.py:9`, and the auto-generated `SummarySchema`) currently return a number. Clients that store or compare it as a number will break if it becomes a string, even though the field name stays the same.
2. **Existing rows need a UUID.** `fields.UUIDField(default=uuid4)` only fills in the value from Python for new rows. The migration has to backfill old rows in SQL before the column can be NOT NULL and UNIQUE.
3. **Tests won't catch a bad migration.** `tests/conftest.py` builds the test database with `generate_schemas=True`, so a broken Aerich migration still passes CI.
4. **Validation errors look different.** Paths use `id: int = Path(..., gt=0)`. Accepting `int | UUID` changes the 422 error body for `0` and `abc`, and the tests compare those bodies exactly. Clients that parse errors may also notice.
5. **Two lookup paths can drift apart.** `get`, `put` and `delete` in `crud.py` must each send ints to `id=` and UUIDs to `uuid=`. Missing one creates a 404 that only happens for some callers.
6. **Changing the primary key itself causes knock-on bugs.** `generate_summary(summary_id: int, ...)` in `summarizer.py` and the ordering of `get_all` both rely on the int key. Keep it as an internal key.
7. **Keeping int lookups keeps IDs guessable.** If the reason for UUIDs is to stop people walking through sequential IDs, that protection only arrives when int lookups are removed.
8. **Nobody sees the deprecation, so it never ends.** Without warnings and a set end date, int lookups will stay forever.

## Assumptions (non-interactive)
- "Keeping clients working" means existing int IDs in paths and the numeric `id` field keep working during a deprecation period. It does not mean keeping them forever.
- The database is Postgres 13 or later, so `gen_random_uuid()` is built in.
- Nothing outside this API uses the int primary key as a foreign key.

## Plan (expand, then migrate, then contract)
I wrote the plan to `claude-home/plans/replace-the-integer-ids-immutable-pillow.md` and edited no project files.
1. **Model:** in `app/models/tortoise.py`, add `uuid = fields.UUIDField(unique=True, default=uuid4)` and keep the int primary key.
2. **Migration:** a new Aerich migration that adds a nullable column, backfills it with `gen_random_uuid()`, then sets NOT NULL, a UNIQUE index and a default. Include a real downgrade.
3. **Schemas:** `SummaryResponseSchema` gets `uuid: UUID` and keeps `id: int`, marked deprecated. `SummarySchema` picks up `uuid` automatically.
4. **Routes:** in `app/api/summaries.py`, the path parameter becomes `Union[int, UUID]`, with ints still required to be above 0. Calls that use an int get a `Deprecation` header.
5. **CRUD:** `app/api/crud.py` sends each type to the right filter, and `post` returns both IDs.
6. **Later release:** a `/v2` (or a sunset date) where `id` becomes the UUID and int lookups are removed.

**Verification:** the existing tests should pass, apart from the updated 422 assertions. Add tests for get, put and delete by UUID and by int, a malformed UUID (422) and an unknown UUID (404). Run `aerich upgrade` on a copy of a database that already has data, and check there are no NULL or duplicate UUIDs.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | `id` changes type in place | Clients and tests treat `response["id"]` as an int | Add a `uuid` field; flip `id` only in `/v2` |
| 2 | Existing rows lack a UUID | `UUIDField` default is set in Python only | Backfill with `gen_random_uuid()`, then NOT NULL and UNIQUE |
| 3 | Migration never tested | Tests use `generate_schemas=True` | Run `aerich upgrade` on a copy of a populated DB in CI |
| 4 | 422 error body changes | `Path(gt=0)` int becomes `int \| UUID` | Update assertions; document the change |
| 5 | CRUD lookups drift apart | Three functions filter by `id=` separately | One shared helper that builds the filter |
| 6 | Swapping the primary key | Summarizer task and ordering use the int key | Keep the int primary key internal |
| 7 | IDs stay guessable | Int lookups still allowed | Set a deadline for removing int lookups |
| 8 | Deprecation never ends | No signal to clients | `Deprecation`/`Sunset` headers; log int usage |

Riskiest: #1. Changing what `id` contains silently breaks every existing client.
