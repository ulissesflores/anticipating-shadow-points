I haven't edited anything. This is a read-only analysis of `starlette/middleware/sessions.py`, the tests, and `docs/middleware.md`.

## Assumptions

- "Secure by default" means changing the constructor defaults to `https_only=True` and `same_site="strict"`. The `https_only` parameter is what emits the `Secure` flag, so I won't add a new parameter.
- The change is a deliberate breaking change. It goes in the release notes, and the `docs/middleware.md` defaults are updated (lines 235 and 237).
- Callers who pass these arguments explicitly keep their current behavior.

## Ways this could go wrong

- **Plain-HTTP sessions stop working.** Browsers drop `Secure` cookies set over `http://`, so dev servers, the test client and internal HTTP deployments lose sessions. The failure is silent: no error, the session is just empty.
- **`TestClient` breaks.** The default base URL is `http://testserver`. `tests/middleware/test_session.py` and `tests/middleware/test_middleware.py` use defaults at about 10 call sites and would fail or need changes.
- **`Strict` breaks cross-site login flows.** OAuth and OIDC redirect callbacks, payment returns, and links from email or other sites arrive without the cookie on that first navigation. State or CSRF tokens stored in the session are then lost. Starlette's own `docs/config.md` example may be affected.
- **Users appear logged out when following external links.** Under `Strict`, the first top-level navigation from another site is anonymous.
- **Reverse-proxy TLS termination.** If the proxy forwards HTTP to the app, the server-side scheme is irrelevant here because the cookie flag is static. The browser sees HTTPS, so it works, but the behavior differs from what people expect from "secure only over HTTPS".
- **Clearing cookies.** The deletion `Set-Cookie` reuses the same flags. If a Secure-less existing cookie is overwritten over HTTP, deletion fails, and a stale cookie can persist.
- **Interaction with `partitioned`, `same_site="none"` and `https_only`.** The docs already say `partitioned` needs `https_only=True` and `none` for cross-site embeds. The new defaults make `same_site="none"` the only override needed for embeds, but users who override only one of the two could get inconsistent combinations.
- **Third-party and downstream code.** Frameworks that subclass or wrap `SessionMiddleware` (FastAPI apps, Starlette-based libraries) inherit the new defaults and break without any code change on their side.
- **Semantics drift.** Silently changing defaults in a minor release violates semver expectations. There is no deprecation path unless one is added.
- **Docs and tests drift.** The docs say "Defaults to `'lax'`" and "Defaults to `False`", so they go stale if not updated.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Sessions vanish over plain HTTP | `https_only` default flips to `True`, and browsers reject `Secure` cookies on `http://` | Release-note it; document `https_only=False` for local dev |
| 2 | Existing tests fail | `TestClient` uses `http://testserver`, and about 10 tests use the defaults | Use an `https://` base URL, or pass explicit args in tests |
| 3 | Cross-site redirect flows lose session | `Strict` omits the cookie on top-level cross-site navigation (OAuth callbacks) | Document `same_site="lax"` for OAuth apps |
| 4 | Users logged out via external links | The first navigation from another site is anonymous | Same as #3; note it in the docs |
| 5 | Silent breaking change for downstream libraries | Wrappers and subclasses inherit the defaults | Deprecation warning cycle, or a major-version bump |
| 6 | Cookie clear fails over HTTP | The delete cookie carries the same `Secure` flag | Add a test for clearing under both settings |
| 7 | Inconsistent override combos | `partitioned` and `none` interplay with the new defaults | Validate or document the combinations |
| 8 | Stale docs | `docs/middleware.md` states the old defaults | Update the docs and add a release note |
| 9 | Semver violation | Defaults change in a minor release | Gate behind a warning, or ship in a major release |

Riskiest: #1, because the cookie silently stops working on any non-HTTPS deployment and every test or dev setup using the defaults.
