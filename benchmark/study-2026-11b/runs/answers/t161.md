## Finding

The code already half-does this. `ArticleUpdate` (`articles/routers.go:152-160`) regenerates the slug when the title changes, using `makeSlug` and `makeUniqueSlug`. The old slug is then overwritten, so `GET /api/articles/<old-slug>` returns 404 and previously shared links break. The task is to keep old slugs resolvable. I made no edits.

## Assumptions

- Old links must keep working on every `:slug` route, not only GET. That covers favorite, comments, PUT and DELETE.
- I'm treating this as a JSON API. Clients that follow an old link should get the article, with the canonical slug in the body so they can update their URLs.
- SQLite with GORM AutoMigrate, as in `hello.go`. No migration tool is involved.
- Only the author can change a title. This is already enforced in `ArticleUpdate`.

## Plan

1. **Alias table.** Add `ArticleSlugModel{ID, ArticleID, Slug uniqueIndex, CreatedAt}` in `articles/models.go`. Register it in `hello.go` and in the test DB setup in `articles/unit_test.go:339`.
2. **Record old slugs atomically.** When `ArticleUpdate` changes the slug, insert the old slug into the alias table in the same transaction as the article update. Use or extend `articleModel.Update`. This replaces the current retry loop's lone `Update` call, and the `gorm.ErrDuplicatedKey` retry stays.
3. **Make slug generation alias-aware.**
   - `makeUniqueSlug` (`models.go:299`) must also treat alias slugs as taken. Otherwise a new article could claim a retired slug and hijack the old link.
   - If an article returns to a slug it once had, for example A→B→A, delete that alias row for the same article instead of treating it as a collision.
4. **Resolve aliases on every `:slug` route.** Add one helper, `findArticleBySlug(slug)`. It tries `FindOneArticle` first. On a miss, it looks up the alias and loads the live article. Replace the `FindOneArticle(&ArticleModel{Slug: slug})` calls at `routers.go:101,115,196,216,232,248,270,301`.
   - GET responses return the canonical slug.
   - Write routes act on the resolved article.
   - Authorization is unchanged because it checks `AuthorID`.
5. **Cleanup on delete.** `ArticleDelete` is a soft delete. Alias lookups must join to non-deleted articles so a deleted article's old links return 404. Also delete the alias rows on delete, so retired slugs don't accumulate.
6. **Chain growth.** Aliases always point at `ArticleID`, not at the previous slug. A→B→C therefore needs no chain-walking. Optionally cap the alias count per article, say 50, to bound abuse.
7. **Docs and spec.** Update the README to note that old slugs keep resolving. The existing hurl and bruno suites must still pass.

## Tests

Add these in `articles/unit_test.go`:
- Rename, then GET the old slug, which returns 200 with the new canonical slug.
- Rename twice. Both old slugs resolve.
- Rename back to a former slug.
- Another article's title can't claim a retired slug. It gets a `-2` suffix instead.
- Old-slug favorite and comment calls work.
- Old slug after delete returns 404.
- Rename without a title change adds no alias.
- A non-author PUT through an old slug returns 403.

## Verification

Run `go build ./...`, `go test ./...` and `golangci-lint run`. Then start the server with `go run hello.go` and check by hand: create an article, PUT a new title, then GET the old and new slugs with curl. Finally, run the hurl and bruno spec suites from commit a41289b.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Retired slug reused by another article | `makeUniqueSlug` checks only the `slug` column, so a new article could take an old URL | Check the alias table in `makeUniqueSlug`; test it |
| 2 | Alias write not atomic with the update | Today's update and retry loop aren't transactional, so a crash could leave a renamed article with no alias | Single transaction for the update plus alias insert |
| 3 | Some `:slug` handler still skips alias lookup | Eight call sites repeat `FindOneArticle`, so one missed site leaves a broken link | One helper; grep and test every route with an old slug |
| 4 | Rename back (A→B→A) hits the unique index | The old slug is both the target and an existing alias | Delete the same-article alias before the update |
| 5 | Deleted articles leak through aliases | Soft delete leaves rows, so aliases could resolve to dead articles | Join on `deleted_at IS NULL`; remove aliases on delete |
| 6 | Concurrent renames race on slugs | `makeUniqueSlug` check-then-insert races, as the code already notes | Keep the unique index and the duplicate-key retry; apply it to alias inserts too |
| 7 | Schema change on existing databases | New table via AutoMigrate. Articles renamed before this change have no alias | Idempotent AutoMigrate; document that earlier renames can't be recovered |
| 8 | Clients keep using stale slugs forever | Transparent resolution hides the rename | Return the canonical slug in every response; consider a 301 for GET later |
| 9 | Unbounded alias growth | Each rename adds a row | Cap per article; clean up on delete |
| 10 | Spec-suite regression | The RealWorld hurl and bruno tests passed recently and expect 404 for missing slugs | Run both suites; unknown slugs still return 404 |

Riskiest: #1, because a retired slug reused by another article would send shared links to the wrong article without any error.
