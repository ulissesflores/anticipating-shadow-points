## What the code does today

- **Visits have no vet and no time.** `Visit` (`src/main/java/org/springframework/samples/petclinic/owner/Visit.java`) only has `date` (a `LocalDate`) and `description`. The `visits` table has `id, pet_id, visit_date, description` in the H2, MySQL and Postgres schema files. So "same vet at the same time" can't be expressed yet.
- **Booking already exists but isn't really online.** `VisitController.processNewVisitForm` adds a visit through `Owner.addVisit` and saves it with `owners.save(owner)`. There is no login, so anyone can book for any owner ID.
- **The repo already has a pattern for blocking duplicates under concurrency.** Duplicate pet names are blocked by a named database constraint (`unique_owner_pet_name`). `PetController` catches `DataIntegrityViolationException` and checks the constraint name (`isDuplicatePetNameViolation`, around line 202). `PetClinicConcurrencyTests` proves it with two threads posting at once. I'll reuse this pattern.
- **Schema changes don't reach existing databases.** `spring.jpa.hibernate.ddl-auto=none` is set. The H2 schema drops and recreates its tables, but MySQL and Postgres use `CREATE TABLE IF NOT EXISTS`, so a database that already exists won't get new columns.
- **Sample data inserts by column position:** `INSERT INTO visits VALUES (default, 7, '2013-01-01', 'rabies shot')`.

## Ways this could go wrong (before planning)

1. **Race condition.** A "check the slot is free, then insert" in Java lets two requests both pass the check. Only a database constraint is safe.
2. **Overlapping times dodge the constraint.** A unique key on `(vet, date, time)` only catches exact matches. 10:00 and 10:15 with 30-minute visits would both get in unless times must fall on slot boundaries, checked on the server.
3. **Existing MySQL/Postgres databases aren't migrated,** so the app fails at runtime on the missing columns.
4. **Positional `INSERT`s in `data.sql` break** once columns are added, and startup fails.
5. **Old visits have no vet.** The new column has to allow NULL. All three databases let multiple NULLs through a unique key, which is the behaviour we want here.
6. **Detecting the constraint error differs by database.** Error messages differ, so the constraint needs the same explicit name in all three schemas. The Postgres `IF NOT EXISTS` index problem was already hit once (commit 88e37c1).
7. **No authentication.** "Online booking" lets anyone book or spam slots for any owner or pet. That's an existing gap, made bigger by this change.
8. **Time zones.** `LocalDate.now()` uses the server's zone, so "past slot" and "today" checks can be off for users elsewhere.
9. **Tests and translations.** `VisitControllerTests`, the JMeter plan, and `I18nPropertiesSyncTest` (every message file needs the same keys) will break or fail if not updated.
10. **Tampered vet IDs.** A forged form value pointing to a missing vet must give a form error, not an HTTP 500.

## Assumptions (no one to ask in this run)

- Visits use fixed 30-minute slots during clinic hours (09:00–17:00 assumed), and times must fall on a slot boundary.
- "Online" means the existing web form, extended. Adding login is out of scope, but I flag it as a risk.
- Old visits keep `vet_id = NULL`.
- Cancelling or rescheduling is out of scope.

## Plan

1. **Schema (all three `schema.sql` files):** add a nullable `vet_id` (foreign key to `vets`) and a `visit_time` column to `visits`. Add a constraint named `unique_vet_visit_slot` on `(vet_id, visit_date, visit_time)`. In Postgres, create it idempotently, the same way as the pet-name index.
   - Also ship a short `ALTER TABLE` migration note or script for existing MySQL/Postgres databases.
   - Change the `data.sql` visit inserts to list their columns explicitly.
2. **`Visit` entity:** add `@ManyToOne Vet vet` and `LocalTime time`. Validate both as required for new bookings, and validate that the time is on a slot boundary and within clinic hours.
3. **`VisitController`:**
   - Inject `VetRepository` and expose `vets` and the list of slots to the form.
   - Bind the vet through a formatter modelled on `PetTypeFormatter`. An unknown ID becomes a field error.
   - Reject slots in the past.
   - Optionally pre-check whether the slot is free, for a friendlier message.
   - Wrap `owners.save(owner)` in a `DataIntegrityViolationException` catch that matches `unique_vet_visit_slot` and turns it into a "slot already booked" field error, as `PetController` does.
4. **Template `createOrUpdateVisitForm.html`:** add vet and time dropdowns (using the `selectField` fragment), and show vet and time in "Previous Visits" and on the owner details page.
5. **Translations:** add the new keys to every `messages*.properties` file.
6. **Tests:**
   - Update `VisitControllerTests`: success, slot taken, off-boundary time, past date, unknown vet.
   - Add a two-thread double-booking test to `PetClinicConcurrencyTests` that asserts exactly one visit is saved.
   - Run the MySQL and Postgres integration tests (Testcontainers) to check the constraint name matching.

**Verification:** run `./mvnw test`, including the concurrency test and the database integration tests. Then start the app with `./mvnw spring-boot:run` and book the same vet and slot from two browser tabs; the second should get the "already booked" error.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Double booking under concurrent requests | The controller saves via `owners.save` with no lock; checking in Java first is a race | Named unique constraint plus catching `DataIntegrityViolationException`; two-thread test |
| 2 | Overlapping but different times both get booked | The unique key only catches exact (vet, date, time) matches | Fixed slots, server-side boundary check; no free-form times |
| 3 | Existing MySQL/Postgres databases lack the new columns | `ddl-auto=none` and `CREATE TABLE IF NOT EXISTS` skip changes | Ship an `ALTER TABLE` migration script and document it |
| 4 | Startup fails on sample data | `data.sql` inserts visits by column position | Use explicit column lists |
| 5 | Constraint error not recognised on one database | Each database words the error differently; matching is by name | Same constraint name everywhere; run MySQL/Postgres integration tests |
| 6 | Old visits break the new rules | Existing rows have no vet or time | Nullable columns; require them only on new bookings |
| 7 | Anyone can book or spam slots for any owner | No authentication in the app | Note as out of scope; add login and rate limiting later |
| 8 | Wrong "past slot" or "today" checks | `LocalDate.now()` uses the server's time zone | Use one clinic time zone via an injected `Clock` |
| 9 | Build fails on translations | `I18nPropertiesSyncTest` needs the same keys in every file | Add keys to all `messages_*.properties` |
| 10 | Forged vet ID causes HTTP 500 | Form values can be tampered with | Formatter turns unknown IDs into field errors; test it |

Riskiest: #1. Two concurrent bookings of the same vet slot, if the rule is checked only in Java rather than enforced by a database constraint.
