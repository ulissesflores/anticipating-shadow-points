# Plan: default signing digest SHA-1 → SHA-256 (itsdangerous)

**Assumptions**
- This is the `itsdangerous` library at 2.3.0 (unreleased). The change counts as a breaking change and goes in that release.
- I'm not editing any file or writing a plan file, as you asked.
- The goal is to change the default only. Explicit `digest_method=` settings keep working. Nothing is added to auto-detect the digest of old tokens.

## What the code does today

- `src/itsdangerous/signer.py:40` defines `_lazy_sha1`, which calls `hashlib.sha1` only at runtime so FIPS builds don't break at import.
- `HMACAlgorithm.default_digest_method` (line 54) and `Signer.default_digest_method` (line 120) both use it.
- The digest also feeds key derivation. With the default `django-concat`, line 204 computes `digest_method(salt + b"signer" + secret_key)`. Changing the default therefore changes the derived key and the signature length, so every existing signature stops verifying.
- `Serializer` and `TimedSerializer` inherit the default through `Signer`.

## Steps

1. **`signer.py`**
   - Add `_lazy_sha256`, mirroring `_lazy_sha1`, so the lazy-access FIPS fix from 2.2.0 (issue #375) stays.
   - Point both `default_digest_method` attributes at it.
   - Keep `_lazy_sha1` available (private but imported by tests), so users can name it explicitly in fallback signers.
   - Update both `default_digest_method` comments and the `digest_method` param docstring. They say "defaults to SHA1".
   - Add a `.. versionchanged:: 2.3` note to `Signer`.
2. **Tests**
   - `test_serializer.py:180`: the fallback-signer assertion `next(unsigners).digest_method == _lazy_sha1` becomes `_lazy_sha256`.
   - `test_digests` (line 186): the default must now equal the explicit-SHA-256 value. Keep the SHA-1 and SHA-512 vectors, but assert SHA-1 explicitly.
   - Regenerate the hardcoded signature in `test_timed.py:70` (`TgPVoaGhoQ.AGBfQ6…`) and any other SHA-1 vectors. Check each regenerated value against an independent HMAC computation.
   - Add a migration test: a token signed with `digest_method=hashlib.sha1` loads through a default serializer with `fallback_signers=[{"digest_method": hashlib.sha1}]`. Add a test that a SHA-1 token is rejected without the fallback.
3. **Docs**
   - `docs/concepts.rst:140-153`: rewrite "Digest Method Security". The default is now SHA-256, and SHA-1 in HMAC is still not considered broken. Say tokens get longer (43 base64 characters instead of 27).
   - `docs/serializer.rst:97`: keep the SHA-1 fallback example, but frame it as the upgrade path.
   - Add a short "Upgrading from 2.2" section with the fallback snippet.
4. **`CHANGES.rst`**: under 2.3.0, add "Change the default digest method from SHA-1 to SHA-256. Existing signatures won't verify unless a SHA-1 fallback signer is configured."
5. **Verification**
   - Run `uv run pytest`, `mypy` and `pre-commit run -a`.
   - Check that a token produced by 2.2.0 loads in the new version only via the fallback.
   - Run with a SHA-1-less OpenSSL, or mock `hashlib.sha1` to raise. The default path must still work, and importing must not touch the hash.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | All existing signed data is invalidated | Both the HMAC and the `django-concat` derived key use the digest, so old signatures never match | Document the fallback signer. Release as a minor version with a clear changelog entry. Add a migration test |
| 2 | Silent behavior change for downstream users | Flask sessions, Django-adjacent code and others rely on the implicit default. They get logged out or fail verification | Mention in the release notes. Consider a pre-release. Tell users to pin `digest_method` before upgrading |
| 3 | Longer tokens (27 → 43 characters) | Cookies, URLs and email links have size limits. Stored tokens may exceed DB column widths | Document the size delta. Check length-sensitive tests |
| 4 | Rolling deploys with mixed versions | Old nodes can't verify tokens signed by new nodes, and the reverse | Roll out in two phases: add the SHA-256 fallback while still signing with SHA-1, then flip the default |
| 5 | Hardcoded test vectors go stale | Several literal signatures (`test_timed.py:70`, `test_digests`) encode SHA-1 | Regenerate them and cross-check with an independent HMAC |
| 6 | Subclasses that override `default_digest_method` | Tests show the override pattern. Users who set SHA-1 or SHA-512 explicitly stay unaffected, but hybrid setups may behave differently | Keep the attribute name and semantics unchanged. Add a test for the override |
| 7 | FIPS import-time regression | Eagerly referencing `hashlib.sha256` would break the lazy design from #375 | Use a `_lazy_sha256` wrapper and test the import path |
| 8 | Docs and docstrings still say SHA-1 | The `signer.py` docstrings, `concepts.rst` and the comments all state the old default | Grep for `sha1` and `SHA-1` after the change |
| 9 | Third-party code imports `_lazy_sha1` | It is private, but the tests import it | Keep it defined, since the fallback examples need it |

Riskiest: #1 — every existing signature and token fails verification after the upgrade unless users configure a SHA-1 fallback.
