I've written the plan to `claude-home/plans/make-the-session-middleware-s-compressed-dijkstra.md`. The code change is two lines, but it will break things for existing users, so the plan spends most of its effort on tests, docs and migration notes. No files were edited.

**Assumptions**
- Only the defaults change: `same_site` goes to `"strict"` and `https_only` goes to `True`. Parameter names and how they work stay the same, and anyone can still opt out.
- Shipping this is a breaking change in behaviour, so it goes under "Changed" in the release notes with a migration line. The maintainer decides which version it lands in.
- AI_POLICY.md says to search for duplicate PRs and issues before opening one. I tried with `gh search`, but it returned nothing from this sandbox, so I couldn't confirm there's no duplicate. Repeat that search by hand before opening a PR.

**Plan**
1. **`starlette/middleware/sessions.py`:** change the two defaults in the signature. Nothing else needs to change, because `security_flags` already adds `; secure`, and both the write and the clear `Set-Cookie` headers use it.
2. **`tests/middleware/test_session.py`:** the test client defaults to `http://testserver`, and httpx won't send a `Secure` cookie back over http. Every test that does a round trip on the defaults would therefore lose its session without an obvious error.
   - Switch those clients to `base_url="https://testserver"`.
   - Add a test that checks the default header contains `secure` and `samesite=strict`, on both the write and the clear cookie.
   - Add an opt-out test (`https_only=False`, `same_site="lax"`) that checks the cookie still round-trips over http. This keeps both branches of `if https_only` covered, since the project requires 100% coverage.
3. **`docs/middleware.md`:** update the stated defaults. Explain that `strict` drops the cookie when users arrive from another site (OAuth or SSO callbacks, links in emails). Remove the now-redundant `https_only=True` from the example, and add a short opt-out section with explanatory text before the snippet, as AGENTS.md requires. Optionally change the example in `docs/config.md` to `https_only=not settings.DEBUG`.
4. **`docs/release-notes.md`:** add a "Changed" entry with the migration hint.

**Verification:** run `scripts/test` and `scripts/check` (100% coverage must hold). Then check the `Set-Cookie` header from a real uvicorn app over HTTPS.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | OAuth/SSO logins break | Login callbacks arrive from another site; with `Strict` the browser leaves out the session cookie that holds the login state, so the check fails | Document `same_site="lax"` for these flows and put it in the release notes |
| 2 | Plain-HTTP dev and internal deployments lose sessions without any error | Browsers drop `Secure` cookies on http (127.0.0.1, LAN IPs, docker hostnames, older Safari even on localhost) | Release note plus the `https_only=not DEBUG` example |
| 3 | Users appear logged out when they arrive from a link | With `Strict`, the first visit from an email or another site is sent without the cookie | Explain in docs; `lax` is the standard fallback |
| 4 | Test suite failures that don't point to the cause | The test client defaults to http and httpx drops `Secure` cookies, so the visible failure is just empty sessions | Move the tests to `https://testserver` |
| 5 | Breaking change in a 1.x release | Every app relying on the defaults changes behaviour when it upgrades | "Changed" entry with migration steps; maintainer picks the version |
| 6 | Apps behind a proxy that serve http to the browser | Some setups really serve http end-to-end, so the cookie is never stored | Same opt-out; document it |
| 7 | Coverage drops below 100% | The opt-out branch could go untested once the default changes | Add the explicit opt-out test |
| 8 | Duplicate PR breaks AI_POLICY | The duplicate search couldn't run from here | Search GitHub by hand before opening a PR |

Riskiest: #1. `SameSite=Strict` as the default breaks OAuth/SSO login callbacks and other flows where users arrive from another site, and the cause is hard to spot.
