# Plan: require email verification before login

I explored the repo read-only and edited nothing. That includes the plan file that plan mode names, because you said not to edit any file.

## What's there today
This is a Remix "Blues Stack" app with Prisma/Postgres and cookie sessions.
- `app/routes/join.tsx` creates the user and immediately calls `createUserSession`, so signup logs the user in.
- `app/routes/login.tsx` calls `verifyLogin` from `app/models/user.server.ts` and then `createUserSession`.
- `app/session.server.ts` has `requireUser`, `requireUserId` and `getUser`. They only check that the user exists.
- The `User` model in `prisma/schema.prisma` has no verification field.
- There is no email-sending code or dependency.
- `cypress/support/create-user.ts`, `prisma/seed.ts` and `cypress/e2e/smoke.cy.ts` all assume a new user is logged in at once.

## Assumptions
- Existing users are grandfathered in as verified, so nobody is locked out on deploy.
- Verification uses a single-use, expiring token, emailed as a link. I'll use a 24h expiry and store only a SHA-256 hash of the token.
- Email goes through a provider (Resend or SMTP via nodemailer), configured by new env vars. In dev and test the email is logged instead of sent.
- Unverified users who try to log in get a clear "verify your email" message and a resend option. We don't reveal whether other emails exist.
- Signup no longer creates a session. It shows a "check your inbox" page.

## Steps
1. **Schema and migration** (`prisma/schema.prisma`, new migration)
   - Add `emailVerifiedAt DateTime?` to `User`.
   - Add an `EmailVerificationToken` model with `tokenHash @unique`, `userId` (cascade delete), `expiresAt` and `createdAt`.
   - The migration backfills `emailVerifiedAt = createdAt` (or `now()`) for all existing rows.
2. **Model layer** (`app/models/user.server.ts`)
   - Add `createVerificationToken(userId)`: invalidate old tokens, generate 32 random bytes, store the hash and return the raw token.
   - Add `verifyEmailToken(token)`: look up by hash, check expiry, set `emailVerifiedAt` and delete the user's tokens in one transaction.
   - Make `verifyLogin` return the user including `emailVerifiedAt`. The login route decides what to do with it, so a wrong password and an unverified account stay distinguishable internally.
3. **Mailer** (new `app/email.server.ts`)
   - Implement `sendVerificationEmail(to, url)`. Build the URL from a new `APP_URL` env var, not from the request Host header.
   - Add env vars to `.env.example`. Add a mock or log-only path so `mocks/index.js` and Cypress don't hit a real provider.
4. **Signup** (`app/routes/join.tsx`)
   - Create the user, create a token, send the email, then redirect to `/verify-email?sent=1`. Don't create a session.
   - For an existing email, return a generic outcome or keep the current message. That choice is an enumeration trade-off (see the risks table).
5. **Verify and resend routes** (new `app/routes/verify-email.tsx`, `app/routes/resend-verification.tsx`)
   - `GET /verify-email?token=…` should not change state on GET, so prefetchers and mail scanners can't consume the token. Render a confirm button that POSTs, or accept the risk and verify on GET.
   - The resend action is rate-limited per email and IP, and always returns the same response.
6. **Login** (`app/routes/login.tsx`)
   - After a valid password, if `emailVerifiedAt` is null, don't create a session. Return an error with a resend link.
7. **Defense in depth** (`app/session.server.ts`)
   - Make `requireUser` redirect to `/verify-email` if `emailVerifiedAt` is null. This covers sessions that exist before the deploy or that come from any other path.
8. **Fixtures and tests**
   - `prisma/seed.ts`: set `emailVerifiedAt`.
   - `cypress/support/create-user.ts`: create the user as verified.
   - `smoke.cy.ts`: change the register test to sign up, read the token from the test mailer, visit the link, log in and check the notes page.
   - Add Vitest unit tests for token creation, expiry, reuse and tampering.

## Verification
- Run `npm run typecheck`, `npm run lint`, `npm test -- --run` and `npm run test:e2e:run`.
- Run `prisma migrate deploy` against a copy of a populated DB. Confirm existing users can still log in.
- Manual flow, covering each of these:
  - Sign up, then try to log in. It should be blocked.
  - Click the link, then log in. It should work.
  - Reuse the link. It should fail.
  - Use an expired link. It should fail.
  - Resend, then confirm the old token is dead.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | Migration adds a nullable field, and nothing marks current users verified | Backfill `emailVerifiedAt` in the migration |
| 2 | Verified check missed on some path | Auth is only `requireUser` and `requireUserId`, and `requireUserId` skips the user lookup | Enforce in `requireUser` and `login`. Make `requireUserId` check too, or document it |
| 3 | Token leaks or is guessable | New secret-bearing flow, with the raw token in a URL | 32 random bytes, store only the hash, single-use, 24h expiry |
| 4 | Mail scanners consume the token | GET-based links get prefetched | Confirm via POST button, or accept and document the risk |
| 5 | Email provider failure blocks signup | Signup now depends on an external send | Create the user first, send best-effort, and keep resend available |
| 6 | Host-header injection in link | Building the URL from the request could point links at an attacker | Use a fixed `APP_URL` env var |
| 7 | Account enumeration | Join says "user already exists", and resend could leak status | Generic responses and rate limits |
| 8 | Resend abuse and email bombing | No rate limiting exists in the app | Per-email and per-IP throttle, with a cooldown |
| 9 | E2E and seed tests break | Cypress and seed assume instant login | Update the fixtures, plus a test mailer hook |
| 10 | Missing prod config | New env vars (`APP_URL`, mail creds) aren't in `fly.toml` and secrets | Add `invariant` checks at startup and update the deploy docs |

Riskiest: #1, existing users locked out. It hits every current user on deploy and is only prevented by getting the backfill migration right.
