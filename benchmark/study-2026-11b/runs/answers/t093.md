No files edited, as you asked. This is `itsdangerous`. The default digest is `_lazy_sha1`, set in `src/itsdangerous/signer.py:40-54` and `:114-120`.

**Assumptions**
- "Default" means `Signer.default_digest_method` and `HMACAlgorithm.default_digest_method`, not a new per-call argument.
- Callers can still pass `digest_method=...` or set `fallback_signers` explicitly.
- It would ship as a major or minor release with a `CHANGES.rst` entry. I haven't confirmed which.
- The change would use a lazy `hashlib.sha256` wrapper like the existing `_lazy_sha1`, so it stays safe on FIPS builds.

**Where it could go wrong**
- **Existing tokens.** The signature changes, so every token signed before the upgrade fails verification.
- **Derived keys.** The digest is also used to derive the signing key (`signer.py:201-209`). The change alters the key, not just the MAC.
- **Fallback signers.** By default, fallback signers inherit the class default. Old tokens won't verify unless SHA-1 is listed explicitly.
- **Mixed fleets.** During a rolling deploy, old and new instances reject each other's tokens.
- **Token length.** SHA-256 signatures are longer (43 base64 chars vs 27). That could break cookie, URL or DB column size limits.
- **Pinned fixtures.** `tests/test_serializer.py:180-192` hardcodes `_lazy_sha1` and the value `"[42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM"`. Downstream libraries probably pin similar values.
- **Subclass overrides.** Subclasses that override `default_digest_method` or rely on `digest_method == _lazy_sha1` behave differently. The tests also import the private `_lazy_sha1`.
- **Cross-system tokens.** Other services that verify these tokens, possibly in other languages, still expect SHA-1.
- **Docs.** `docs/serializer.rst` and the docstrings say "defaults to SHA-1" in several places. They would go stale.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | All existing tokens invalid | Signature and derived key change with the digest | Add SHA-1 fallback by default for a deprecation window |
| 2 | Fallbacks don't cover old tokens | Fallback signers inherit the new class default | Make the fallback explicitly SHA-1 and test it |
| 3 | Rolling-deploy mismatch | Old and new instances reject each other's tokens | Ship fallback first, then flip the default |
| 4 | Longer tokens | 43 vs 27 base64 chars may exceed cookie, URL or column limits | Document it and check downstream size limits |
| 5 | Key derivation shifts | The digest feeds `derive_key` (`signer.py:201-209`) | Test derived keys for both digests |
| 6 | Subclass and private-API breakage | `default_digest_method` overrides and `_lazy_sha1` imports | Keep `_lazy_sha1` and note the change in `CHANGES.rst` |
| 7 | Hardcoded test and downstream fixtures | `test_serializer.py:180-192` pins SHA-1 values | Update the tests and add dual-digest cases |
| 8 | Non-Python verifiers | Other services still expect SHA-1 | Inventory consumers and have them pass `digest_method` explicitly |
| 9 | FIPS or lazy-import regression | Replacement must stay lazy | Keep the lazy wrapper pattern |
| 10 | Stale docs | Docs say SHA-1 is the default | Update `docs/serializer.rst` and docstrings |

Riskiest: #1, because every token issued before the upgrade would stop verifying, which would silently log users out.
