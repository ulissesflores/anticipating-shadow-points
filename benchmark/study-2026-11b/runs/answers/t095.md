# Plan: require email verification before login (Remix Blues Stack)

I didn't write the plan file, because you said not to edit any file. Everything below comes from reading `prisma/schema.prisma`, `app/models/user.server.ts`, `app/session.server.ts`, `app/routes/join.tsx`, `app/routes/login.tsx`, `server.ts`, `app/db.server.ts`, `prisma/seed.ts` and the Cypress support files.

## Assumptions
- "New users" means accounts created after this change ships. Existing users count as already verified and must not be locked out.
- The repo has no email sending today: there's no mailer dependency and `.env.example` only has `DATABASE_URL` and `SESSION_SECRET`. I assume we add a transactional email provider (Resend, Postmark or SES) called over HTTP. MSW (`mocks/index.js`) mocks it in dev and E2E.
- Verification is a single-use link that expires after 24h. We store only a hash of the token.
- Unverified users can't get a session at all. They can't log in, and signup no longer logs them in.
- Out of scope: changing your email address, password reset, and admin tools.

## Ways this could go wrong
1. **Existing users locked out.** If the migration adds `emailVerifiedAt` as null for every row, every current user fails the new check. That includes the seeded `rachel@remix.run`.
2. **Signup still logs people in.** `join.tsx:61` calls `createUserSession` right after `createUser`, which bypasses the gate completely.
3. **Sessions already open stay open.** `requireUserId` only checks that the cookie has a `userId`. An unverified user who signed up before the deploy keeps their session unless the check also runs on requests.
4. **The verify link fails in non-primary regions.** `server.ts:61-80` replays only non-GET requests to the primary region, and `db.server.ts` points other regions at the read-only replica (port 5433). A GET `/verify?token=…` that writes `emailVerifiedAt` will throw outside the primary region.
5. **Link scanners use up the token.** Outlook Safe Links and similar tools prefetch GET links. If the GET itself consumes the token, the user clicks a link that is already dead.
6. **Leaking which emails exist.** Login currently returns one message, "Invalid email or password". Adding "please verify your email" before the password check would reveal which accounts exist. The resend endpoint can leak the same way.
7. **Weak tokens.** Tokens stored in plaintext, never expiring, reusable, or compared with timing leaks.
8. **Email sending fails.** If the send throws after the user row is created, the account exists but no email went out, and signup rejects the address as "already exists". The user is stuck with no way to resend.
9. **Abuse of resend and signup.** Unlimited resends or signups let anyone send email to arbitrary addresses, which hurts the sender's reputation.
10. **Tests and tooling break.** `cypress/support/create-user.ts`, `prisma/seed.ts` and the smoke test "register and login" all assume a new user can log in straight away.
11. **Migration on deploy.** `fly.toml` runs `prisma migrate deploy` as the release command, so the backfill has to be safe while the old code is still serving traffic.

## Plan
1. **Schema** (`prisma/schema.prisma` plus a new migration):
   - Add `emailVerifiedAt DateTime?` to `User`.
   - Add a new `EmailVerificationToken` model with `id`, `tokenHash` (unique), `userId` (cascade delete), `expiresAt` and `createdAt`.
   - In the same migration, run `UPDATE "User" SET "emailVerifiedAt" = "createdAt"` so every existing user counts as verified.
2. **Model** (`app/models/user.server.ts`):
   - `createUser` leaves `emailVerifiedAt` null.
   - Add `createVerificationToken(userId)`: it generates 32 random bytes, stores their sha256, and returns the raw token.
   - Add `consumeVerificationToken(raw)`: in one transaction it looks up the hash, checks the expiry, sets `emailVerifiedAt`, and deletes all of that user's tokens.
   - `verifyLogin` keeps its current signature. The caller decides what to do about verification.
3. **Mailer** (new `app/email.server.ts`): a single `sendVerificationEmail(email, url)` function that reads its provider key from env and builds the URL from a configured `APP_URL`, never from the request's Host header. Add an MSW handler that logs the link so dev and Cypress can pick it up.
4. **Signup** (`app/routes/join.tsx`): create the user and token, send the email, then redirect to `/verify-pending?email=…` without creating a session. If an unverified user signs up again with the same email, resend the link instead of returning "already exists".
5. **Login** (`app/routes/login.tsx`): check the password first. Only when the password is correct and `emailVerifiedAt` is null, refuse to log in and show "verify your email" with a resend option. A wrong password still gets the generic error, so nothing leaks.
6. **Verify route** (new `app/routes/verify.tsx`):
   - The GET loader only renders a "Confirm email" button, so scanners can't consume the token.
   - The POST action consumes the token, which gets it replayed to the primary region (fixes #4 and #5), then calls `createUserSession` and redirects to `/notes`.
   - Expired or invalid tokens get a page offering to resend.
7. **Resend route** (new `app/routes/resend-verification.tsx`, POST only): always responds "if the account exists, we sent an email". Add a simple throttle: at most one token per user every 60s, enforced by checking `createdAt` on the latest token.
8. **Session hardening** (`app/session.server.ts`): `requireUser` and `getUser` log out users whose `emailVerifiedAt` is null. This covers sessions opened before the deploy.
9. **Tooling**:
   - `prisma/seed.ts` and `cypress/support/create-user.ts` create users with `emailVerifiedAt: new Date()`.
   - Update the smoke test: sign up, assert the pending page, read the token through a new `cypress/support/get-verification-link.ts` (via `cy.exec`, as `create-user.ts` already does), confirm, then reach Notes.
   - Add `EMAIL_PROVIDER_KEY` and `APP_URL` to `.env.example` and the Fly secrets docs.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New nullable column means everyone, Rachel included, counts as unverified | Backfill `emailVerifiedAt = createdAt` in the migration |
| 2 | Verify link fails outside primary region | GETs aren't replayed (`server.ts:65`) and non-primary regions use the read replica | Make the GET a confirm page and write only in a POST |
| 3 | Signup still logs users in | `join.tsx` calls `createUserSession` right away | Redirect to the pending page with no session |
| 4 | Old unverified sessions keep working | `requireUserId` only checks the cookie | Check `emailVerifiedAt` in `requireUser`/`getUser` |
| 5 | Link scanners consume the token | Mail security tools prefetch GET links | Consume the token only on POST |
| 6 | Reveals which emails exist | Verify message shown before password check, or resend that confirms the account | Check password first; resend always returns the same reply |
| 7 | Stuck after send failure | User row exists but email failed, and signup says "already exists" | Unverified re-signup resends; resend route available |
| 8 | Token weakness | Plaintext, reusable or never-expiring tokens | Store sha256 only, 24h expiry, single use in a transaction |
| 9 | Email bombing via resend | No rate limiting exists today | Throttle per user (60s) and use one generic reply |
| 10 | E2E/seed break | `create-user.ts`, seed and smoke test assume instant login | Create pre-verified users; read the link from the DB in Cypress |

Riskiest: #2 — in production the link fails only outside the primary region, so local tests won't catch it.
