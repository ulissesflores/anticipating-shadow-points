## What the code does today
- **A visit has no vet and no time.** `Visit` (`owner/Visit.java`) only has `date` (a `LocalDate`, stored as a `DATE` column) and `description`. The `visits` table only has `pet_id`, `visit_date` and `description`. So "same vet at the same time" can't be expressed yet.
- **Booking already works over the web.** `VisitController` handles `POST /owners/{ownerId}/pets/{petId}/visits/new`. It checks that the date is in the future, then calls `owner.addVisit(...)` and `owners.save(owner)`, which saves the new visit through cascade.
- **There is no login.** There's no Spring Security, so anyone can book for any owner by changing the ID in the URL.
- **There's already a pattern for stopping duplicates.** `PetController` (around lines 128–204) relies on a database constraint called `unique_owner_pet_name`. It catches `DataIntegrityViolationException`, checks the constraint name in the error message, and shows a normal form error. `PetClinicConcurrencyTests` tests this by firing two requests at the same moment.
- **Schema setup is basic.** `ddl-auto=none`, and the schema comes from `db/{h2,mysql,postgres}/schema.sql`. For MySQL and Postgres these use `CREATE TABLE IF NOT EXISTS`, and there's no Flyway or Liquibase, so new columns won't appear in a database that already exists.
- **Translations are checked.** `I18nPropertiesSyncTest` requires every message key to exist in all 11 `messages*.properties` files.

## Assumptions (I couldn't ask)
1. "Online" means the existing public web form. Adding login is a separate piece of work, but I list it as a risk.
2. Visits use fixed 30-minute slots, so "same time" means the same vet, date and slot start. Checking arbitrary overlapping time ranges is out of scope.
3. Visits that already exist keep `vet_id = NULL` and are left out of the clash check.
4. All times are in the clinic's single time zone, which is the server zone.

## Ways this could go wrong (before planning)
- **Two people book at once.** If we only "check, then insert", both can pass the check and both get saved.
- **The constraint doesn't exist everywhere.** The constraint might be added to H2 but not MySQL/Postgres, or not to databases that already exist.
- **Old rows with no vet.** If the columns are `NOT NULL`, startup data and existing rows break the schema. If they're nullable, we must make sure the clash check still applies to new bookings.
- **"Same time" is unclear.** With free-form times, 10:00 and 10:15 overlap but wouldn't clash under a simple equality check.
- **The error is detected the wrong way.** Matching the constraint name in the error text is fragile: Postgres reports index names, MySQL reports key names, and some drivers change the case.
- **The clash is detected too late.** Because the save goes through `owners.save(owner)` cascade, the error only appears when the save finishes. If it isn't caught there, the user gets an HTTP 500 instead of a form error.
- **Users can tamper with the form.** Someone could send a vet ID that doesn't exist, a time outside opening hours, a slot not on the 30-minute grid, or a past date and time.
- **Anyone can book for anyone.** That's possible today, and opening booking to owners makes it more visible.
- **Translations and tests break.** New message keys missing from any of the 11 language files fail the build. Existing `VisitControllerTests` need the new fields.
- **The visit pages get confusing.** The "Previous Visits" table and the owner page don't show the vet or time.

## Plan
1. **Database schema** (`db/h2|mysql|postgres/schema.sql`):
   - Add `vet_id INT NULL` with a foreign key to `vets`, plus `visit_time TIME NULL`.
   - Add a constraint named `unique_vet_visit_slot` on `(vet_id, visit_date, visit_time)`, with the same name in all three databases.
   - Because NULLs don't count as duplicates, old rows with no vet won't trigger it.
   - Add a migration note or `ALTER` script for existing MySQL/Postgres databases.
2. **`Visit.java`:**
   - Add `@ManyToOne Vet vet` and `LocalTime time`.
   - Require both on new bookings. Do this in a controller check rather than a bean constraint, so old visits still load.
3. **`VisitController`:**
   - Inject `VetRepository` and provide the list of vets and allowed slots to the form.
   - Check that the vet exists, the slot is on the grid and within opening hours, and the date and time are in the future.
   - As a friendly pre-check, ask the repository whether that vet already has a visit in that slot.
   - Wrap `owners.save(owner)` in `try/catch DataIntegrityViolationException`, and show a form error such as `visit.slotTaken` when the constraint was violated. This copies `PetController.isDuplicatePetNameViolation`, but checks the exception's cause chain or the constraint name without caring about case.
   - The database constraint is the real guarantee. The pre-check only gives a nicer message.
4. **Pages:**
   - Add a vet dropdown (reusing `fragments/selectField.html`) and a time input to `createOrUpdateVisitForm.html`.
   - Show the vet and time in the "Previous Visits" table and on `ownerDetails.html`.
5. **Translations:** add the new keys to all 11 `messages*.properties` files.
6. **Tests:**
   - Extend `VisitControllerTests` to cover: missing vet, unknown vet, slot off the grid, slot already taken (the pre-check), and the database error turning into a form error.
   - Add a two-thread booking test to `PetClinicConcurrencyTests` (same vet and slot, so exactly one should succeed) and one where different vets book the same slot (both should succeed).
   - Run `./mvnw test`, plus `MySqlIntegrationTests` and `PostgresIntegrationTests` (these need Docker) so all three databases enforce the constraint.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Two simultaneous requests double-book a slot | The current flow is "validate, then `owners.save`", with no locking | Unique constraint on `(vet_id, visit_date, visit_time)` plus a two-thread test |
| 2 | Constraint missing on MySQL/Postgres or existing databases | `CREATE TABLE IF NOT EXISTS` and no migration tool | Change all three schemas and ship an `ALTER` script |
| 3 | Clash shows as HTTP 500 instead of a form error | The error only appears when the cascaded save finishes | `try/catch DataIntegrityViolationException` around `save`, following `PetController` |
| 4 | Constraint detected by fragile text match | Each database reports constraint or index names differently | Same name in all databases, case-insensitive match, check the cause chain |
| 5 | Overlapping times slip through | An equality constraint can't detect overlapping time ranges | Fixed 30-minute slots, grid checked on the server |
| 6 | Old visits with no vet break the schema or the check | Existing rows and `data.sql` have no vet | Nullable columns, check only new bookings |
| 7 | Anyone can book or flood slots for any owner | There's no login, and IDs are in the URL | Treat as a known gap, follow up with login and rate limits |
| 8 | Tampered input (bad vet ID, past time, odd minutes) | Today only the date is checked on the server | Check vet exists, grid, opening hours, and future date and time |
| 9 | Build fails on translation keys | `I18nPropertiesSyncTest` checks all 11 files | Add every key to every file |
| 10 | Wrong day or slot from time zone mismatch | `LocalDate.now()` uses the server's zone | Set one clinic zone and use it in all checks |

Riskiest: #1 — if the database doesn't enforce a unique constraint on vet, date and slot, two simultaneous bookings both succeed, and no check in the application code can prevent that.
