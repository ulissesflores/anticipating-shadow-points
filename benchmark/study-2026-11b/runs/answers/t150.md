I've written the plan to `<config>/plans/replace-the-integer-ids-adaptive-otter.md`; no project files were edited. The approach is to add UUIDs alongside the integer IDs now and remove the integer IDs in a later change.

**Assumptions:**
- "Keeping clients working" means every request that works today returns the same status and fields; adding new fields is acceptable.
- Integer IDs stay during a deprecation window. Removing them, or making `id` a UUID, is a separate later change (a `/v2` or a cutover date).
- The database is Postgres 17, so `gen_random_uuid()` is built in. Migrations use aerich 0.8.2.
- The integer primary key stays as the internal key, so the background `generate_summary` task is unchanged.

**What could go wrong (found before planning):**
- **Response type changes:** if `id` itself became a UUID, clients that parse it as an int would break.
- **Path parameter changes:** making `{id}` a `str` or a union type changes the exact 422 errors for `/0/` and `/abc/`. The tests assert those bodies exactly.
- **Migration:** adding a column with a random default rewrites the table under a lock. Existing rows also need a value.
- **Test/production schema drift:** production uses aerich migrations, but the test fixtures (`tests/conftest.py`) build the schema directly. A broken migration wouldn't show up in tests.
- **Strict clients:** adding `uuid` to `SummaryResponseSchema` changes the POST and DELETE responses. Clients that compare responses exactly would fail, and so do two existing tests.
- **Route order:** the integer route and the UUID route could shadow each other.
- **No security gain yet:** while integer routes exist, IDs can still be guessed one after another.
- **Missing index:** without a unique index on `uuid`, lookups are slow and duplicates are possible.
- **Empty rollback:** the existing migration's `downgrade` is empty, so rollback needs real work.

**Approach:**
1. **Model:** add `uuid = fields.UUIDField(unique=True, default=uuid4)` to `TextSummary` in `app/models/tortoise.py`. The generated `SummarySchema` picks it up automatically.
2. **Migration:** add a new aerich migration that runs `ADD COLUMN uuid UUID NOT NULL DEFAULT gen_random_uuid()` (which also fills existing rows) and creates a unique index. Give it a working `downgrade`.
3. **Schema:** `SummaryResponseSchema` keeps `id: int` and gains `uuid: UUID`.
4. **Routes:** leave the `/{id}/` integer routes exactly as they are. Add `/{uuid:uuid}/` routes for GET, PUT and DELETE, registered before the integer routes. Starlette's UUID matcher only accepts UUID-shaped strings, so `/0/` and `/abc/` still get today's 422s.
5. **Deprecation:** mark the integer routes `deprecated=True` in OpenAPI and send a `Deprecation` header from them.
6. **Lookups:** in `app/api/crud.py`, add a function that turns a UUID into the integer key, then reuse the existing `get`, `put` and `delete`.

**Verification:**
- Run `aerich upgrade` on a database that already has rows and check every row gets a distinct uuid; then run `aerich downgrade`.
- Run the existing tests. Only the exact-match checks on POST and DELETE should need updating to include `uuid`.
- Add tests for UUID routes, unknown-UUID 404s, unchanged `/0/` and `/abc/` errors, and integer and UUID routes returning the same record.
- Diff `/openapi.json` before and after: the only changes should be additions and deprecation flags.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Changing `id` to a UUID breaks clients | `id: int` is in every response and clients store it | Keep `id: int` and add a separate `uuid` field |
| 2 | 422 error bodies change | Tests check the exact `gt=0` error for `/0/` | Keep the integer routes; add separate UUID-matching routes |
| 3 | Route shadowing | Two routes match `/summaries/{x}/` | Register UUID routes first; test `/0/`, `/abc/` and a UUID |
| 4 | Strict clients break on the extra field | DELETE and POST responses are compared exactly in tests | Announce the change; update the tests; document the new field |
| 5 | Migration locks or fails on existing rows | A random default on a new column rewrites the table | One `ADD COLUMN … DEFAULT gen_random_uuid()` in a maintenance window |
| 6 | Tests don't exercise the migration | Test fixtures build the schema directly | Run `aerich upgrade` and `downgrade` against a seeded database |
| 7 | Slow lookups or duplicate UUIDs | No index on the new column | `unique=True` plus a unique index |
| 8 | IDs can still be guessed | Integer routes stay live | Deprecation headers, then remove them in v2 |
| 9 | Rollback fails | The current `downgrade` is empty | Write a real `downgrade` that drops the index and column |
| 10 | Background task gets the wrong key | `generate_summary` takes the integer ID | Keep passing the integer key internally |

Riskiest: #1 — changing `id` itself to a UUID silently breaks every existing client, which is why the plan adds a `uuid` field instead.
