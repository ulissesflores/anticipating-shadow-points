I've written the plan to `claude-home/plans/change-the-default-signing-abstract-hanrahan.md` and changed no repository files. No tests were run, since this was planning only. This repo is **itsdangerous** (2.3.0.dev), and the default is `_lazy_sha1` in `src/itsdangerous/signer.py:54` and `:120`.

**How this could go wrong:**
1. **Every existing token stops working.** SHA-1 is used both for the HMAC and for deriving the key (`derive_key`, `django-concat`). Changing the default makes all old signatures fail with `BadSignature`: cookies, password-reset links, API tokens.
2. **Only part of the library gets the fix.** `Serializer` has `default_fallback_signers` (currently `[]`, `serializer.py:102`), so a SHA-1 fallback can be added there. Bare `Signer` and `TimestampSigner` have no fallback mechanism, so their users break with no fix in the library.
3. **Tokens get longer.** The signature grows from 27 to 43 base64 characters. Cookies (4 KB limit), URLs and fixed-width database columns can overflow.
4. **The fallback can crash on FIPS builds.** The SHA-1 default is deliberately lazy because SHA-1 may be missing on FIPS builds (`signer.py:40-45`). A default SHA-1 fallback would call `hashlib.sha1` when a token fails to verify, so `loads()` raises `ValueError` instead of `BadSignature`.
5. **Downstream code relied on the default.** Projects that pinned test vectors or shared tokens between services get mismatches. Flask pins SHA-1 for its sessions, so Flask sessions are fine, but other libraries may not.
6. **Tests and docs go stale.** `test_digests` asserts that the default equals SHA-1, and `test_iter_unsigners` asserts `_lazy_sha1` comes first. `docs/concepts.rst` also says SHA-1 is the default.
7. **Mixed versions during a rolling deploy.** New instances issue SHA-256 tokens that old instances reject.

**Assumptions:**
- This goes into the unreleased 2.3.0 as a documented breaking change.
- A SHA-1 entry in `Serializer.default_fallback_signers` keeps old tokens loading, and is marked for removal later. The project already did this once with SHA-512.
- Users of bare `Signer` get a changelog migration note: pass `digest_method=hashlib.sha1` to keep the old behaviour.

**Plan in brief:**
- Point both `default_digest_method`s at SHA-256.
- Add the SHA-1 default fallback, and turn a missing SHA-1 on FIPS builds into `BadSignature`.
- Update the docstrings, `docs/concepts.rst`, `docs/serializer.rst` and `CHANGES.rst`.
- Tests: pin a SHA-256 vector, keep the SHA-1 vector, and add a test that SHA-1 tokens still load through each serializer. Add tests that a bare `Signer` rejects SHA-1 and for the FIPS case.
- Check with `uv run pytest` and mypy/pyright, then round-trip a token signed by 2.2.0 by hand.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | All existing tokens become invalid | Digest feeds both the HMAC and the derived key | SHA-1 default fallback in `Serializer` |
| 2 | Bare `Signer`/`TimestampSigner` users break | No fallback mechanism on those classes | Changelog migration note; pass `digest_method=sha1` |
| 3 | Larger tokens | Signature grows from 27 to 43 chars; cookie, URL and DB limits | Document size change in CHANGES |
| 4 | FIPS crash in the fallback | `hashlib.sha1` raises on FIPS when a token fails to verify | Turn it into `BadSignature` or skip; add test |
| 5 | Downstream relied on the default | Shared tokens and pinned vectors in other libraries | Breaking-change note; Flask pins SHA-1 already |
| 6 | Rolling-deploy mismatch | Old instances reject new SHA-256 tokens | Release notes: deploy all, or pin sha1 first |
| 7 | Fallback never removed | SHA-1 stays tried forever | Mark as transitional, remove in a later release |
| 8 | Stale tests and docs | `test_digests`, `test_iter_unsigners` and `concepts.rst` assume SHA-1 | Update; pin both vectors |

Riskiest: #1. Every token already issued (sessions, reset links, API tokens) is rejected at once unless the SHA-1 fallback is in place.
