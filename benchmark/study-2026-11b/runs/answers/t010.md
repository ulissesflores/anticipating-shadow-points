**What already exists:** changing the title already changes the slug (`articles/routers.go:152-177`). The missing piece is that the old slug is thrown away, so links that were already shared return 404.

## Plan
1. **Store old slugs.** Add a new table, `ArticleSlugAliasModel`, with a unique `Slug` and an `ArticleID`, and no soft-delete. Register it in `hello.go` and in both test setups in `articles/unit_test.go` (`TestMain` and `resetDBWithMock`).
2. **One lookup for all article URLs.** Add `FindArticleBySlug(slug)`: check the current slug first, then the alias table, and load the article by ID. Use it in all 7 handlers that take a `/:slug`.
3. **Fix delete.** `ArticleDelete` currently deletes with `DeleteArticleModel(&ArticleModel{Slug: slug})`. Called with an old slug, that would delete nothing and still return 204. Change it to delete by `articleModel.ID`.
4. **Keep old slugs reserved.** `makeUniqueSlug` (`models.go:299`) also needs to check the alias table. Otherwise a new article with the old title could take the old slug and take over its links.
5. **Change the update handler:**
   - Only change the slug when the title actually changes. Today the check `base != articleModel.Slug` is always true for slugs with a number suffix like `foo-2`, so the slug changes on every save, even with the same title. With aliases, each of those saves would add a useless alias.
   - In one transaction: save the old slug as an alias, remove this article's own alias if the author renames back to it, and apply the update. Keep the existing retry on duplicate-key errors.
   - Read the article back using its own current slug, not the slug from the URL (which may be an old one).
6. **Old URLs return the article directly (200), not a redirect.** The response body contains the current slug, so clients can update their links. A 301 on a JSON API breaks PUT and DELETE, and the spec tests expect 200.
7. **Deleted articles keep their aliases.** That matches how soft-deleted rows already keep their slug.

**Assumptions:**
- "Shared links" means URLs built from the slug; there is no separate short-link system.
- Old slugs are kept forever.
- The RealWorld API spec's behaviour stays the same.

**Verification:**
- New unit tests:
  - after a rename, every endpoint still works through the old slug
  - after two renames, both old slugs still work
  - renaming back to an old slug works
  - a new article with the old title gets `-2`
  - saving the same title doesn't change the slug
  - deleting through an old slug really deletes
- Then run `go test ./...`, `go vet ./...` and `scripts/run-spec-tests.sh`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | A new article takes an old slug | `makeUniqueSlug` only checks the articles table | Also check the alias table; add a test |
| 2 | Delete through an old slug silently does nothing | `ArticleDelete` deletes by the slug from the URL | Delete by ID; add a test |
| 3 | Slug changes on every save | `base != articleModel.Slug` is true for `foo-2` slugs | Only change it when the title changes |
| 4 | Article saved without its alias | Update and tag replacement aren't in a transaction today | Save the alias and the slug change in one transaction |
| 5 | Two simultaneous edits pick the same slug | No database rule stops an alias and an article slug from matching | Check both tables, keep the retry; SQLite runs one write at a time |
| 6 | Renaming back conflicts with the article's own alias | The alias's unique slug blocks the rename | Remove the article's own alias in the same transaction |
| 7 | One handler still uses the old lookup | 7 handlers each look up the article themselves | Use one helper everywhere; check with grep |
| 8 | Spec tests break | Hurl and bruno tests check exact responses | Answer 200 with the current slug; run `run-spec-tests.sh` |
| 9 | Migration missing somewhere | Tables are registered separately in `hello.go`, `TestMain` and `resetDBWithMock` | Add the new table in all three places |
| 10 | Aliases build up forever | Nothing ever deletes them | Accepted; one small indexed row per rename |

Riskiest: #1. Without it, a new article could quietly take an old slug, and shared links would open the wrong article.
