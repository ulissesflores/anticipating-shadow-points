## Plan: "Download my data" export (profile, posts, comments)

**Assumptions**
- The app is Flasky (Flask, Flask-SQLAlchemy, Flask-Login). Users only export their own data.
- The export is one JSON file. It's machine-readable and reuses the existing `to_json` pattern. Zip or CSV would add complexity for no clear gain.
- Authenticated users only (`@login_required`). Admins don't get export-on-behalf.
- The export covers:
  - the profile: username, name, location, about_me, member_since, last_seen, and the account email (the user's own);
  - the user's posts: `body` as Markdown source, timestamps, and the `body_html` rendering omitted;
  - the user's comments: `body`, timestamp, the post they were on, and the `disabled` flag.
- It excludes `password_hash`, tokens, and role internals.
- Synchronous generation is fine for this app's scale. If accounts grow large, move to a background job.

**Steps**
1. **Model** (`app/models.py`): add `User.export_data()`. It returns a dict with the profile fields above, `posts` (id, body, timestamp), and `comments` (id, body, timestamp, post_id, disabled). It builds these from the `lazy='dynamic'` relationships `User.posts` and `User.comments`. It doesn't reuse `User.to_json()`, because that emits URLs and counts meant for the API. Add an `"exported_at"` UTC timestamp and a `"format_version": 1` field.
2. **Route** (`app/main/views.py`): add `@main.route('/export-data')`, `@login_required`.
   - Prefer POST with CSRF, since the export is sensitive and POST avoids prefetch or link-sharing triggers.
   - Build the response with `json.dumps(..., indent=2)` and a `Response` with `Content-Type: application/json`.
   - Set `Content-Disposition: attachment; filename="<username>-data-<date>.json"`.
   - Set `Cache-Control: no-store`.
   - Iterate the posts and comments queries with `yield_per` or a streaming generator, to bound memory.
3. **UI**: add a "Download my data" button on `edit_profile.html` (or the user menu in `base.html`). It's a small form with the CSRF token, using the existing Flask-WTF setup.
4. **Re-auth** (optional hardening): require a password re-entry or a fresh login before export, since the file contains the email and all private content.
5. **API parity** (optional, later): `GET /api/v1/users/<id>/export`, with token auth and a self-only check. Skip it in v1.
6. **Tests**:
   - Add to `tests/test_client.py`: anonymous gets a redirect to login; a logged-in user gets valid JSON with only their own posts and comments; no `password_hash` key appears anywhere in the output; the headers are correct.
   - Add to `tests/test_user_model.py`: a unit test for `export_data()` with seeded users.

**Verification**
- Run `flask test` (or `python -m unittest discover tests`) and confirm the new tests pass.
- Manual check: run `flask run`, log in as a seeded user from `app/fake.py`, click the button, and inspect the file. Confirm that another user's data is absent, and that a user with 0 posts and 0 comments still exports.
- Check the response headers with `curl -i` using a session cookie.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Leaking secrets or other users' data | `User` holds `password_hash`, and the `Follow` and `Comment` relationships touch other users | Build the export from an explicit allow-list of fields, and assert `password_hash` is absent in a test |
| 2 | Session hijack gives full data theft | The file contains the email and all content in one request | Require POST with CSRF, require re-auth, and send `no-store` |
| 3 | Large accounts exhaust memory or time | `lazy='dynamic'` queries can load every post and comment at once | Stream with `yield_per`, and move to a background job if exports grow |
| 4 | Comments from others on the user's posts | Unclear whether "their comments" includes replies by others | Define scope as comments authored by the user, and document it |
| 5 | Unescaped or stale HTML in the file | `body_html` is sanitized HTML, and `body` is the Markdown source | Export `body` only, and document that |
| 6 | Timezone and format ambiguity | The models use naive `datetime.utcnow` | Emit ISO 8601 with an explicit UTC `Z` |
| 7 | Unconfirmed accounts exporting | Unconfirmed users are only partly restricted in this app | Apply the same `before_app_request` confirmation gate |
| 8 | Abuse and load via repeated exports | The export is a heavy read | Rate-limit it, for example one per minute per user |
| 9 | Disabled (moderated) comments | The user may not see these in the UI, so exporting them reveals moderation state | Decide with the product owner, and default to including them with `disabled: true` |
| 10 | Schema drift breaks the export | New columns on `User`, `Post` or `Comment` get silently left out | Add a test that compares the exported keys with the model columns |

Riskiest: #1, leaking secrets or other users' data, because the export packs the whole account into one downloadable file.
