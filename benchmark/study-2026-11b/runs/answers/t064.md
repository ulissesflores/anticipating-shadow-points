**Assumptions (non-interactive):**
- This is the Flasky app (Flask 0.12, SQLAlchemy 1.1). User, Post and Comment models are in `app/models.py`. Routes are in `app/main/views.py`, and there is a token-authenticated API in `app/api/`.
- "Every user" means each logged-in user downloads only their own data. It does not mean an admin export of everyone.
- The format is one JSON file. The "single file" requirement rules out a zip with several files.
- Synchronous generation is fine at this app's scale. If accounts get large, I'd move to a background job.
- The export includes profile fields, authored posts and authored comments. It excludes the password hash, auth tokens, `role_id` and the other users' data.
- I made no edits, and I did not write a plan file because you said no file edits.

**Ways this could go wrong, before planning:**
1. **Data leakage.** `User.to_json()` and `Post.to_json()` are built for public API output. Reusing them might drop fields the user should get. A hand-built dict might include `password_hash`, `email` of other users, or the `disabled` flag on comments.
2. **Access control.** A route like `/export/<username>` invites IDOR. A user could download someone else's data, including their email. Export should use `current_user` only, with no id in the URL.
3. **Authentication gaps.** The API uses token auth and the web UI uses sessions. A cross-site request that triggers a download is a CSRF-style risk if it is a GET. It should be a POST with a CSRF token.
4. **Memory and timeouts.** `user.posts` and `user.comments` are `lazy='dynamic'`. A heavy user's export loaded in one go could exhaust memory or hit the Heroku 30-second limit, since the app deploys on Heroku and Docker with Gunicorn.
5. **Abuse.** The export is expensive and has no rate limit, so it is a cheap DoS lever.
6. **Completeness and correctness.** Comments *on* the user's posts by others belong to those authors. It's unclear whether "their comments" includes them. Timestamps are naive UTC and need a clear ISO-8601 format. Unicode and Markdown fields (`body` vs `body_html`) must survive round trips.
7. **Privacy of other people's data.** Comments the user wrote on others' posts include context. Quoting other users' content or emails would leak their data.
8. **Header and filename injection.** A username in `Content-Disposition` can break headers if it isn't sanitized.
9. **Unconfirmed or disabled accounts.** Should unconfirmed users or users with moderated comments be able to export? Moderated comments may reveal moderation state.
10. **Testing gaps.** The tests cover the model, client and API. Nothing covers downloads or auth edge cases.

**Plan, briefly:**
- Add `User.export_data()` in `app/models.py`. It returns a dict with `profile`, `posts` and `comments`, built explicitly from an allow-list of fields. Iterate with `yield_per` or paginate.
- Add a POST-only route in `app/main/views.py`, behind `@login_required`, that uses `current_user` and returns `application/json` with a fixed `Content-Disposition` filename.
- Add a button on the user's own profile page (`user.html`) with a CSRF-protected form.
- Add tests in `tests/test_client.py` and `tests/test_user_model.py`: auth required, no cross-user access, no secrets, correct content.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Secret/field leakage | Public `to_json()` helpers differ from what a private export needs | Explicit allow-list; test excludes `password_hash` |
| 2 | IDOR on export | Many routes take `<username>` or `<id>` | Use `current_user`, no id in URL |
| 3 | CSRF-triggered download | Session-cookie auth on web routes | POST with CSRF token |
| 4 | Memory/timeout on big accounts | `lazy='dynamic'` relations, Heroku 30s limit | Stream or paginate; cap size |
| 5 | Export used for DoS | No rate limiting exists | Per-user throttle |
| 6 | Wrong scope of "comments" | Comments on user's posts belong to others | Define scope; own authored only |
| 7 | Other users' data exposed | Comments reference other users | Include only usernames/ids, not emails |
| 8 | Filename/header injection | Username goes into `Content-Disposition` | Fixed or sanitized filename |
| 9 | Moderation state leaked | `Comment.disabled` is internal | Omit or document the field |
| 10 | Untested edge cases | No download or auth tests today | Add client and model tests |

Riskiest: #1, leaking sensitive fields because the export reuses public serializers or a loose field list.
