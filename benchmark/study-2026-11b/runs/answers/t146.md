**What I found**
- `app/routes/join.tsx` creates the user and calls `createUserSession` straight away, so signup logs the user in.
- `verifyLogin` in `app/models/user.server.ts` only checks the password. It never looks at the user's status.
- `User` has no `emailVerified` field or token table, and the repo has no email-sending code or provider.
- `prisma/seed.ts` and `cypress/support/create-user.ts` create users and sessions directly. The Cypress script's cookie bypasses `/login`.
- The session cookie holds only `userId`, so any gate must also apply to sessions that already exist.

**Assumptions**
- Existing users are grandfathered: the migration marks them verified.
- Verification means a single-use link, hashed in the DB, valid for 24 hours.
- I'd add a transactional email provider such as Resend, configured by an env var, with a mock in `mocks/` for e2e tests.
- Unverified users are blocked at login and in the session loader (`requireUserId`), not only at `/login`.

**Ways this could go wrong**

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | The new column would default to unverified for current rows, and `User` has no verified flag today | Backfill `emailVerifiedAt = now()` for existing rows in the same migration |
| 2 | Signup still auto-logs-in | `join.tsx` calls `createUserSession` right after `createUser` | Remove that call. Redirect to a "check your email" page. |
| 3 | Gate only on `/login` | Cookies hold just `userId`, and `requireUserId` never checks status | Check verification in `getUser`/`requireUserId`, and in `verifyLogin` |
| 4 | No email infrastructure | The repo has no mail code, provider, secrets or Fly config | Add a provider, set Fly secrets, and add a dev/mock transport |
| 5 | Token weakness | Guessable, reusable or non-expiring tokens would let someone verify an email they don't own | Use 32-byte random tokens, store only the hash, make them single-use with an expiry, and compare in constant time |
| 6 | Wrong-address signups and typos | Unverified accounts hold an email forever, which blocks the real owner under the unique constraint | Allow re-signup or resend for unverified accounts, and purge stale ones |
| 7 | Resend and verify abuse | Without limits these endpoints can be used for spam or enumeration | Rate-limit them, give a uniform response, and keep the "user exists" message from leaking |
| 8 | Delivery failures | Spam filtering or a provider outage leaves users stuck with no way in | Add a resend button, log send errors, and decide whether signup fails or queues when sending fails |
| 9 | Tests and seed break | Seed and the Cypress `create-user` helper make users who aren't verified, so e2e tests fail | Set `emailVerifiedAt` in the seed and helper, and add e2e coverage for verified and unverified paths |
| 10 | Unsafe migration on deploy | Fly runs `prisma migrate deploy`, and the new schema running against old code could break requests | Use a two-step additive migration (nullable column, then backfill, then enforce), and test it on a copy of prod data |

Riskiest: #1, because a migration without the backfill locks out every existing user at once.
