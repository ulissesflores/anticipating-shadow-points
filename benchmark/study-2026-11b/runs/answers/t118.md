# Plan: "Download my data" export (Flasky, Flask 0.12)

I'm not editing any files, as you asked. I also didn't write the plan file that plan mode suggests, because that would break your instruction.

## Assumptions
- "Profile, posts and comments" means the user's own records. Comments are the ones they authored, including comments on other people's posts. Comments received on their posts are not included.
- The file is JSON, which is a single file and lossless. A zip or CSV isn't needed.
- It is a synchronous download from a logged-in web page. Only the owner can download, with no admin override.
- Profile fields included: `username`, `name`, `location`, `about_me`, `member_since`, `last_seen`, `email`, `confirmed` and the role name.
- Left out: `password_hash`, `avatar_hash` and tokens.
- Follows are out of scope.
- Posts and comments include `body` (the markdown source), `timestamp` and ids. `body_html` is left out because it can be regenerated.
- Disabled comments are included, with a `disabled` flag, because they are the user's own content.
- No schema migration is needed.

## Design
1. **Serializer, `app/models.py`.** Add `User.export_data()`. It returns `{"exported_at", "profile", "posts", "comments"}`.
   - `profile` is built from an explicit allow-list of fields. The existing `User.to_json()` is built for the API and adds URLs, so don't reuse it as-is.
   - `posts` come from `self.posts.order_by(Post.timestamp)`. `comments` come from `self.comments.order_by(Comment.timestamp)`.
   - Iterate with `yield_per` or `.all()`, depending on the size decision in the risks below.
2. **Route, `app/main/views.py`.** Add `@main.route('/export')`, protected with `@login_required`.
   - It uses `current_user` only. It takes no username or id parameter, so there is no IDOR surface.
   - It returns `Response(json.dumps(data, indent=2), mimetype='application/json')` with `Content-Disposition: attachment; filename="<username>-data-YYYYMMDD.json"` and `Cache-Control: no-store`.
   - Use `isoformat()` for datetimes.
3. **UI.**
   - Add a "Download my data" link in `app/templates/user.html`, shown only when `user == current_user`.
   - Put the same link in the `base.html` account dropdown.
   - Prefer a POST form with CSRF to a GET link. The data is sensitive and a GET can be prefetched or triggered cross-site. Flask-WTF is already in use.
4. **Rate limit.** Use a simple per-user throttle, for example a `last_export_at` check in memory or in the session. This adds a column and a migration only if it must persist across workers, so start without one.
5. **API parity (optional, phase 2).** Add `GET /api/v1/users/me/export` in `app/api/users.py`, reusing the same method and the token auth that already exists.

## Tests, `tests/`
- Add `tests/test_export.py`, using the pattern in `test_client.py`.
  - An anonymous request redirects to login.
  - A logged-in user gets JSON containing their own posts and comments and none from another user.
  - The response has the attachment headers.
  - The output contains no `password_hash` and no other user's email.
  - A user with no posts or comments gets empty lists.
  - Unicode and markdown bodies round-trip.
- Add a unit test for `User.export_data()` in `test_user_model.py`.

## Verification
- Run `flask test` (or the project's test command).
- Run the dev server with `fake.py` data. Download as user A and diff the file against the DB. Then try the export URL as user B and confirm it returns only B's data.
- Check the file opens with `python -m json.tool`.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Leaking sensitive fields | `User` holds `password_hash`, and `to_json()` is API-shaped | Explicit allow-list; test asserts forbidden keys are absent |
| 2 | Wrong user's data (IDOR) | Other routes take `<username>` or `<id>` params | Use `current_user` only; no id parameter; cross-user test |
| 3 | Large export exhausts memory or blocks a worker | Lazy `dynamic` relationships; Gunicorn on Heroku has few workers | `yield_per` streaming; row cap or a background job if heavy users exist |
| 4 | CSRF or prefetch of a sensitive GET | A `<a href>` can be triggered cross-site | POST with a CSRF token; `Cache-Control: no-store` |
| 5 | Abuse as a DoS vector | Heavy queries can be repeated | Per-user throttle; auth required |
| 6 | Incomplete export | Disabled comments, comments on others' posts, and deleted posts are easy to miss | Define scope in the spec; tests for each case |
| 7 | Datetime or encoding errors | Naive UTC datetimes; non-ASCII bodies | `isoformat()` plus `Z`; `ensure_ascii=False` with UTF-8 |
| 8 | Old pinned stack | Flask 0.12 and SQLAlchemy 1.1 lack newer helpers | Stick to `Response` and core ORM APIs; test on the pinned versions |
| 9 | Unconfirmed accounts or stale sessions | `confirmed` is a flag, and the export includes the email | Require login only; consider requiring a confirmed account |
| 10 | Privacy and compliance expectations | The export is a GDPR-style request, and the scope may be wrong | Confirm the legal scope; log export events without logging contents |

Riskiest: #1, leaking sensitive fields such as `password_hash` or other users' data in the export.
