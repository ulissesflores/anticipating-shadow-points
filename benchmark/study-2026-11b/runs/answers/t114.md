The plan below is also saved to `<config>/plans/lock-users-out-by-buzzing-owl.md`. I made no other edits.

**Why the change:** today, if `AXES_LOCKOUT_PARAMETERS` is not set, Axes locks out by IP address only (`axes/conf.py:50-51`). That means one attacker behind a shared address (an office network, a proxy, a mobile carrier) can lock out every user on that address. With username and IP together, a username is locked only from the address where it failed.

**Assumptions:**
- 9.0.0 is already tagged, so this goes in an unreleased **10.0.0** as a breaking change.
- Only the "nothing configured" case changes. Explicit lists, callables and dotted paths behave exactly as before.
- The old deprecated flags keep their meaning. `AXES_USE_USER_AGENT` set on its own still means IP address plus user agent, not username + IP + user agent.
- No migration is needed: `AccessAttempt` already stores both username and IP address.

**Changes:**
1. **`axes/conf.py:37-60`**: change the final `else` branch so the default becomes `[["username","ip_address"]]` only when no deprecated flag is set. When `AXES_USE_USER_AGENT` is set alone, keep `["ip_address"]` so the existing code still turns it into IP address + user agent. Also fix the outdated comment on line 38.
2. **No code change needed elsewhere.** These already handle the combined form:
   - the lookup helpers in `axes/helpers.py`;
   - the database handler (`axes/handlers/database.py:368`) and the cache handler;
   - the security check (`axes/checks.py:179`): it already accepts `ip_address` inside a nested list, so the new default doesn't trigger warning W006;
   - the verbose startup log in `axes/apps.py`.
3. **Tests:**
   - Add `@override_settings(AXES_LOCKOUT_PARAMETERS=["ip_address"])` to the tests that rely on the old default, mainly `test_lockout_by_ip_*` in `tests/test_login.py` (around lines 383-410 and 526-555).
   - Run the helper, attempt, handler and logging tests and pin any that expect IP-only cache keys or counts.
   - Add tests for:
     - the new default;
     - each deprecated flag still mapping as before;
     - W006 not firing on the default;
     - same user on a different IP allowed;
     - different user on the same IP allowed.
4. **Docs:**
   - `docs/4_configuration.rst:93`: change the default value.
   - `docs/2_installation.rst`: add an upgrade note: set `["ip_address"]` to keep the old behaviour.
   - `docs/5_customization.rst:181`: fix the wording.
   - `docs/3_usage.rst`: explain the trade-off and suggest `["ip_address", ["username","ip_address"]]` for stricter setups.
5. **`CHANGES.rst`**: add a 10.0.0 entry with the breaking-change notice and the one-line opt-out.

**Verification:**

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Weaker default protection | One IP can try many usernames (password spraying) and never be locked | Document it; suggest `["ip_address", ["username","ip_address"]]` or a rate limit/WAF |
| 2 | Silent behaviour change on upgrade | Sites that never set the parameter change behaviour with no error | Release as 10.0.0 with a breaking notice and a one-line opt-out |
| 3 | Current lockouts drop at upgrade | Cache keys change from IP-only to username+IP, so active IP lockouts stop applying | Mention in the changelog; admins can reset or monitor |
| 4 | Deprecated flags change meaning | `AXES_USE_USER_AGENT` would get username added through the shared `else` branch | Change the default only when no deprecated flag is set; add a test for each flag |
| 5 | Tests relying on the old default | `test_lockout_by_ip_*` and similar assume IP-only | Pin `["ip_address"]` on them explicitly |
| 6 | Requests with no username | Missing username is treated as empty and lockouts still apply per IP, which may surprise | Keep and extend the existing empty-username tests |
| 7 | Rotating IPs avoid lockout | An attacker changing IPs gets new attempts for the same user | Document it; suggest also locking by username for high-value accounts |
| 8 | Docs left out of date | The default is described in 4+ docs files | Grep for `ip_address` defaults in docs during review |

Riskiest: #1 — the new default no longer limits a single IP trying many usernames.
