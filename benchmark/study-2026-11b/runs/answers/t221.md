**Assumptions** (non-interactive run, no files edited):
- "Moderator" is a new role. The code has no roles or admin flag today.
- "Hide" means soft-hide: the comment stays in the database but is removed from public reads.
- An appeal is a single request from the comment's author, filed within 7 days of the hide. A moderator other than the one who hid the comment decides it. The result is "restored" or "upheld".
- The 7 days run from the hide time. This is a REST/JSON API with no UI, so appeals are API-only.

**What I found in the repo** (Laravel 5.5, RealWorld API):
- `Comment` has no soft-deletes, status or hidden-at column.
- `CommentController::index` returns every comment, and `destroy` hard-deletes.
- `User` has no role.
- The queue driver defaults to `sync`, and nothing sends notifications.
- `CommentTransformer` always exposes `body`.

**Ways it could go wrong (before planning):**
1. **Hidden content still leaks.** `index`, article payloads, the `with` eager-loads, and any future comment counts or feeds can bypass a status check. The author may also still need to see their own hidden text.
2. **Privilege escalation.** There is no role system yet. A bad authorization check, or mass-assignment of a role through `$fillable` or `UpdateUser`, could let anyone moderate.
3. **The 7-day window is ambiguous.** It could be measured from the hide, from the notification, or from the comment's creation. Timezones, `created_at` vs `hidden_at`, and edits to the comment can all shift it. A re-hide after a successful appeal could reset or bypass the limit.
4. **The author never learns of the hide.** There is no notification path, so the deadline can expire unseen. That makes the appeal right hollow.
5. **The appeal flow breaks.** Possible faults include duplicate or concurrent appeals, the original moderator ruling on their own hide, appeals on restored or deleted comments, and a status that moves out of order.
6. **No audit trail.** Without who, when and why recorded, there is no accountability. A reviewer cannot see the original reason, and hiding is not reversible if the data is overwritten.
7. **Interaction with existing deletes.** The author's own `destroy` and the cascade deletes (user or article) would erase the evidence and pending appeals. An author could delete a hidden comment to dodge review.
8. **Abuse and load.** Spam appeals, retaliatory hiding by a moderator, and unbounded pending queues with no pagination or rate limits.
9. **Schema and contract changes.** A migration on a live `comments` table, a changed API response that breaks RealWorld spec clients, and tests that assume every comment is visible.
10. **Legal and privacy issues.** Hidden text is still stored, which matters for retention and deletion requests. Reasons given by moderators may also expose reporter identities.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Hidden comments leak | `index` is unfiltered, and `Comment` eager-loads relations everywhere | Global scope or `visible()` scope; add tests for each read path |
| 2 | Privilege escalation | No role system exists, and `$fillable` is loose | Role column outside `$fillable`; policy-based checks; deny by default |
| 3 | Ambiguous 7-day window | No `hidden_at` timestamp exists | Store `hidden_at`; compute the deadline server-side in UTC; one appeal per hide |
| 4 | Author not notified | No mail or notification code, and the queue is `sync` | Return hidden state to the author; send a notification; start the clock on notice |
| 5 | Broken appeal state machine | Concurrent requests, and moderators can rule on their own hides | Explicit states; row lock or unique constraint; require a different moderator |
| 6 | No audit trail | Hide or delete would overwrite or lose history | Append-only `comment_moderation_events` table with actor, reason and time |
| 7 | Delete bypasses review | `destroy` hard-deletes, and FKs cascade | Block author deletion while hidden or under appeal; soft-delete |
| 8 | Abuse and retaliation | No rate limits or reporting controls | Throttle appeals; require a reason; paginate the moderator queue |
| 9 | Contract and migration breakage | Spec-based clients and tests assume every comment is returned | Additive nullable columns; keep the response shape; update tests |
| 10 | Privacy and retention | Hidden text stays in the database | Define retention; redact reasons in public output |

Riskiest: #1, hidden comments leaking through unfiltered read paths, because the failure is silent and exposes the very abuse the feature is meant to remove.
