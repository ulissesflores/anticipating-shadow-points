**Finding:** most of this change is already in the repo, so the plan is a short hardening pass. I didn't edit any file, as you asked.

## What exists today
- `src/Conduit/Infrastructure/Security/PasswordHasher.cs` issues ASP.NET Identity v3 hashes: PBKDF2-HMAC-SHA512, 210,000 iterations, random per-hash salt embedded in the payload. New hashes are written with an empty `Person.Salt`.
- `Verify` still accepts the legacy format: exactly 64 bytes plus a 16-byte salt, HMAC-SHA512 with the static key `"realworld"`. A legacy match returns `SuccessRehashNeeded`.
- `Login.cs:79-84` rehashes on a successful login, and `Edit.cs` and `Create.cs` use the new hasher. `PasswordHashingTests` already covers the rehash flow.

## Assumptions
- "Stronger" means at least OWASP-grade. PBKDF2-SHA512 at 210k iterations is the current baseline. Argon2id would be stronger, but it needs a third-party package (for example Konscious or Isopoh) or a native dependency. I assume that isn't wanted unless you ask for it.
- Lazy migration (rehash on login) is the intended no-reset path. A mass re-hash is impossible because the plaintext isn't available.
- Both SQLite and SQL Server are in use.

## Plan
1. **Confirm the baseline is already green.** Run `dotnet run --project build/build.csproj -- test` to check the existing hasher and its tests.
2. **Close the remaining gaps in `PasswordHasher` and `Login`.**
   - Make the work factor configurable through options, with 210k as the default. Identity returns `SuccessRehashNeeded` when a stored hash has fewer iterations than configured. Future bumps then migrate automatically.
   - Run a dummy `Verify` against a fixed hash when the email isn't found (`Login.cs:61-64`). That removes the timing gap between "no such user" and "wrong password".
   - Persist the rehash, with the password check kept separate from the write. Currently a failed `SaveChanges` would turn a correct login into a 500, so catch and log it and still let the login succeed.
3. **Decide on dormant legacy accounts.** Users who never log in keep the weak HMAC hash forever. Options:
   - Wrap them: re-hash the legacy hash with PBKDF2 in a migration, and verify as `PBKDF2(HMAC_legacy(password))`. This needs a new format marker and a migration for both providers (SQLite and SQL Server contexts and snapshots).
   - Or leave them as they are and add a sunset date after which unmigrated legacy hashes are rejected, which forces a reset for those users only.

   I recommend wrapping if dormant users matter. If you don't want a migration, skip it. In either case, document the choice in `docs/database-migrations.md`.
4. **Check column constraints.** Confirm `Hash` has no max length that a 61+ byte payload could break on SQL Server. Today it is `byte[]` with no configured limit.
5. **Optional: remove `Salt`.** It is vestigial, but dropping it needs a two-provider migration and would break the legacy verify path. I recommend deferring this until the legacy hashes are gone.
6. **Tests, in `tests/Conduit.IntegrationTests/Features/Users`.**
   - Add a test that a lower-iteration Identity hash returns `SuccessRehashNeeded`.
   - Add a test that Login succeeds when the rehash write fails.
   - Add a test that an unknown email still returns 401.
   - Add a test for wrapped legacy hashes, if step 3 goes ahead.
   - Keep the existing legacy-rehash and `LoginTests`, `CreateTests` and `EditTests` cases green.
7. **Verify.** Run `dotnet run --project build/build.csproj -- test`, which formats, builds in Release and tests. If the `realworld` submodule is available, also run `make test-hurl-with-managed-server` to confirm the API contract hasn't changed.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Dormant users stay on weak HMAC | Rehash only happens on login, and the legacy key `"realworld"` is static | Wrap legacy hashes in a migration, or set a sunset date |
| 2 | Lock-out from a bad verify change | Legacy detection is a length check (64 bytes with a 16-byte salt) | Keep the existing legacy tests and add a fixture for each format |
| 3 | Login CPU cost and DoS | 210k iterations per attempt, with no visible rate limiting | Add rate limiting on login, and size the iteration count with benchmarks |
| 4 | Rehash write failure breaks login | `SaveChangesAsync` runs inside the login handler | Catch and log, and return success |
| 5 | Username-enumeration timing | An unknown email skips hashing entirely | Do a dummy verify |
| 6 | Dual-provider migration drift | SQLite and SQL Server have separate snapshots | Add both migrations and test on both |
| 7 | Rollback can't read new hashes | Old code can't verify Identity v3 payloads | Ship the verifier first, then enable issuing |
| 8 | Argon2 package or native dependency | It adds supply-chain and platform risk, and locked restore needs lock-file updates | Stay on PBKDF2 unless Argon2 is required |
| 9 | Plaintext in logs or errors | Passwords flow through the Login, Create and Edit commands | Keep them out of logging and validators' messages |
| 10 | Hash column length limits | The migration or provider may cap `varbinary` length | Check the schema in both providers before shipping |

Riskiest: #1, because dormant users keep a weakly hashed password indefinitely.
