# Plan: "Download my data" export (profile, posts, comments)

This is a read-only plan. I wrote no files, including the plan file, because you said not to edit any.

## Context
The app is a Flask/Flasky blog with SQLAlchemy, Flask-Login and a `main` blueprint. The `User`, `Post` and `Comment` models in `app/models.py` already have `to_json()` methods. `User.posts` and `User.comments` are `lazy='dynamic'` relationships. Users manage their own data at `/edit-profile`, and `user.html` shows the profile page. No export feature exists today.

## Assumptions
- **Format:** one JSON file, `flasky-export-<username>.json`. JSON keeps the nesting and is easy to produce. CSV can't hold three entity types in one file.
- **Who can use it:** every logged-in user, for their own data only. There is no `<username>` parameter, so there's no way to export someone else's data. Admins get no special route.
- **What the file contains:**
  - Profile: username, email, name, location, about_me, member_since, last_seen.
  - Posts: raw `body` and timestamp. I'd skip `body_html`, because it is derived from `body`.
  - Comments: raw `body`, timestamp, `disabled` flag and the parent `post_id`.
  - Excluded: `password_hash`, auth tokens, `avatar_hash` and follow relations.
- **Unconfirmed users:** they can use it too. It only needs login.
- **Delivery:** synchronous download. Per-user data in a blog app is small, so a background job isn't justified yet.
- **Tests:** no CSRF token on the route. A GET that only reads data needs none.

## Approach
1. **Serializer in `app/models.py`.** Add `User.to_export_json()`.
   - It returns the profile, plus `posts` and `comments` lists.
   - Write new `to_export_json` methods rather than reusing the public `to_json`. The public `to_json` returns URLs and comment counts instead of full bodies, and it omits private fields like email.
   - Query with `.order_by(timestamp)`.
   - For the comments query, use `yield_per` or chunked iteration. That keeps memory flat for heavy users.
2. **Route in `app/main/views.py`.**
   - Add `GET /export`, decorated with `@login_required`.
   - Build the payload from `current_user._get_current_object()`.
   - Return it with `Content-Disposition: attachment; filename=...` and `Content-Type: application/json`.
   - Add `Cache-Control: no-store` so proxies and browsers don't cache personal data.
   - Use `json.dumps` with an ISO-8601 datetime handler. `jsonify` would work, but it sorts keys and doesn't stream.
3. **UI.**
   - Add a "Download my data" button to `user.html`, shown only when `user == current_user`, next to Edit Profile.
   - Optionally add the same link to the account dropdown in `base.html`.
4. **Abuse limiting.** Add a simple rate limit, for example one export per user per minute. Flask-Limiter would add a dependency, so a small in-process check or a `last_export` timestamp is the lighter option. Pick one in implementation.
5. **Docs.** Add a short README note.

## Critical files
- `app/models.py` (new `to_export_json`)
- `app/main/views.py` (new route)
- `app/templates/user.html` (button)
- `tests/test_client.py` and `tests/test_user_model.py` (tests)

## Verification
- **Unit test** in `tests/test_user_model.py`:
  - Create a user with 2 posts and 3 comments.
  - Assert the export contains exactly those rows.
  - Assert it has no `password_hash` and nothing belonging to other users.
- **Client test** in `tests/test_client.py`:
  - Anonymous `GET /export` returns a 302 redirect to the login page.
  - A logged-in user gets 200, a JSON attachment header and the expected content.
  - User A never receives user B's data.
- Run `flask test` (or `pytest tests/`).
- **Manual check:** run the dev server, log in, click the button and open the downloaded file.
- **Large-data check:** use `app/fake.py` to generate a user with thousands of posts and comments, then check the response time and memory use.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Leaking another user's data | The route reads `current_user`, and `/user/<username>` pages are public, so a `<username>` parameter would be an easy mistake | No username parameter; test that A never gets B's data |
| 2 | Exposing secrets in the export | Reusing the model's column list could include `password_hash` or tokens | Explicit allow-list of fields; test asserts they are absent |
| 3 | Memory and timeouts on heavy users | `dynamic` relationships plus a single `json.dumps` build the whole file in memory; Heroku and Gunicorn workers time out at about 30s | Chunked queries, optional streaming response, and a worker timeout check |
| 4 | Export used for scraping or load | Every export runs unbounded queries | Per-user rate limit and no-store caching |
| 5 | Cached or shared sensitive file | The file contains email and private content | `Cache-Control: no-store` and an attachment disposition |
| 6 | Session hijack gives an attacker the full dump | A single GET returns everything | Optionally require password re-entry; log exports |
| 7 | User-generated content breaking the file | Post bodies may hold arbitrary text, and datetimes are not JSON serializable | Serialize via `json.dumps` with a datetime handler and `ensure_ascii=False` plus UTF-8 |
| 8 | Incomplete data vs. legal expectations (GDPR-style) | Follows, avatar hash and moderation state are excluded | Document the scope, and add follows later if required |
| 9 | Disabled or moderated comments leaking | Moderators hide comments via `disabled`, and the author may see content that was hidden from others | Include the flag, and confirm the policy with product |
| 10 | Weak test coverage | The existing tests include slow Selenium tests and no export tests | Add focused unit and client tests |

Riskiest: #1, leaking another user's data through the export route.
