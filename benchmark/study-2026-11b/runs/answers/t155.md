This is `express-session` 1.19.0. It already has a `rolling` option, and the default is `false` (`index.js:109`). I made no edits.

**Assumptions**
- "Default" means changing `Boolean(opts.rolling)` so that an undefined `rolling` becomes `true`. An explicit `rolling: false` would still opt out.
- This is a semver-minor or major behaviour change for a widely used library. I'm assuming a major bump or a clearly documented release is acceptable.
- The change would touch `index.js:109`, the `rolling` section of the README, the options JSDoc, `HISTORY.md`, and `test/session.js` (the rolling tests and any test that assumes there is no `Set-Cookie` header).

**How it could go wrong (before planning)**
- **Every response now sets a cookie.** `shouldSetCookie` (`index.js:~480`) returns true whenever the session ID matches. That breaks caching, because `Set-Cookie` makes responses uncacheable behind shared caches and CDNs.
- **Anonymous and bot traffic.** The cookie is sent on every response, but only when a session exists. With `saveUninitialized: true`, which is also the deprecated default, every visitor gets a session and a cookie. Session-store load and cookie churn rise sharply.
- **Store writes and touches.** `shouldTouch` fires whenever the session isn't being saved. Every request then calls `store.touch`, or a full `save` if the store has no `touch` and `resave` is true. Stores without `touch` take a write on every request.
- **Sessions never expire for active clients.** Polling, health checks, keep-alives and prefetches extend the session forever. The absolute lifetime is lost, which is a security regression for apps that relied on a fixed `maxAge`.
- **Multi-tab and race conditions.** Concurrent requests each re-save or touch the session. With `resave: true` this can overwrite newer data with stale data (last write wins).
- **Existing tests and docs contradict the new default.** The README says the default is `false`. Tests that assert no `Set-Cookie` header on unmodified sessions will fail.
- **Interaction with `cookie.expires`.** With `maxAge` unset (a browser-session cookie), rolling does nothing useful and only adds a header.
- **Interaction with `unset: 'destroy'` and `regenerate`.** Cookie-setting paths change slightly in these cases and need checking.

**Plan sketch (not executed)**
1. Change the default to `opts.rolling === undefined ? true : Boolean(opts.rolling)`.
2. Update the README, JSDoc and `HISTORY.md`, and flag the change as breaking.
3. Fix the existing tests and add the following:
   - the default now rolls
   - `rolling: false` opts out
   - a `touch` call happens on an unmodified session
4. Run `npm test` and check the `Set-Cookie` and store call counts.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Silent breaking change to a library default | Every consumer upgrading gets different cookie and store behaviour | Make it a major release with a loud changelog and migration note |
| 2 | `Set-Cookie` on every response | `shouldSetCookie` returns true on every request with a session, which breaks CDN and shared caching | Document `rolling: false`; consider skipping rolling for static or cacheable routes |
| 3 | Higher store load | `store.touch` runs on every request, and stores without `touch` get full saves | Recommend stores that implement `touch`; warn in the docs |
| 4 | Sessions never expire for active clients | Polling and keep-alives extend sessions indefinitely, and the absolute timeout is lost | Document it; suggest an app-level absolute max-age check |
| 5 | Anonymous sessions amplified | `saveUninitialized` defaults to true, so every visitor gets a session and cookie churn | Pair this change with a `saveUninitialized: false` recommendation |
| 6 | Race and overwrite with `resave: true` | Concurrent requests re-save stale session data | Warn against `resave: true` with rolling |
| 7 | Existing tests assert the old behaviour | `test/session.js` expects no cookie on unmodified sessions | Update the tests and add explicit default and opt-out cases |
| 8 | Docs and code drift | README, JSDoc and the deprecation messages all state `false` | Update every mention in one change |
| 9 | Session-only cookies | Without `maxAge` there is no expiry to extend, so extra headers add no value | Skip rolling when `cookie.expires` is null |
| 10 | Edge flows (`regenerate`, `unset: 'destroy'`) | Cookie-setting logic shifts around these | Add tests for those flows with rolling on |

Riskiest: #1. It silently changes cookie, caching and store-load behaviour for every existing user, and the lost absolute session timeout (#4) is its worst consequence.
