## Plan: make `rolling` default to `true` in express-session

**Assumptions**
- This is `express-session` 1.19.0 on `master`. "Every request extends expiry" means flipping the `rolling` option default from `false` to `true`.
- I'm not adding a new option, and I'm not changing the `cookie.maxAge` semantics.
- This is a breaking default change, so it ships in the next major or behind a documented opt-out. The maintainers decide which.
- I did not write the plan file, because you said not to edit any file.

**What the code does today**
- `index.js:109` sets `rollingSessions = Boolean(opts.rolling)`, so an unset option is `false`.
- `shouldSetCookie` (`index.js:491`) returns `rollingSessions || (cookie.expires != null && isModified(session))` for an existing session. With rolling on, the `Set-Cookie` header goes out on every response.
- `shouldTouch` (`index.js:471`) decides whether `store.touch` runs. The store-side expiry is already extended through `touch`, or through a resave when the store has no `touch`. So the server side needs no new logic.
- `README.md:295` documents `rolling` as default `false`. `test/session.js:1158` has the `rolling option` tests.

**Steps**
1. **`index.js`:** change line 109 to `opts.rolling === undefined ? true : Boolean(opts.rolling)`. Update the JSDoc at line 78 to say the default is `true`.
2. **`README.md`:** change the `rolling` section to say the default is `true`. Keep the existing note that a `saveUninitialized: false` session with no data still gets no cookie. Add a short note on how to opt out with `rolling: false`. Add a warning that rolling combined with a `resave: true` store with no `touch` method causes a store write on every request.
3. **`HISTORY.md`:** add an "unreleased" entry marked as a breaking change. Say that a `rolling` default of `false` must now be set explicitly.
4. **Tests (`test/session.js`):**
   - Add a case that a request with no `rolling` option re-sends `Set-Cookie` with a fresh `Expires`.
   - Add a case that `rolling: false` keeps the old behaviour.
   - Find existing tests that assume no cookie on an unmodified request. Pass `rolling: false` in them, or update the assertions. I haven't run the suite, so I don't know how many fail.
5. **Verify:** run `npm test` and `npm run lint`. Then run a manual check with a small Express app, `maxAge` set to a few seconds and the `MemoryStore`. Confirm that a request just before expiry keeps the session alive, and that `Set-Cookie` appears on every response.

**Interactions to handle**
- Responses to static assets, health checks and polling endpoints will each extend the session. Document this, and tell users to mount `session()` only on routes that need it.
- A `cookie.maxAge` of `null` (a browser-session cookie) gets `Set-Cookie` on every response with no expiry change. It is harmless, but it adds header noise.
- Users on the default `saveUninitialized: true` already get cookies from new sessions. The rolling cost applies to existing sessions.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Silent breaking change for existing apps | Every upgrader gets a `Set-Cookie` on all responses, and their sessions stop expiring while the client stays active | Ship in a major, add a changelog entry, and show the `rolling: false` opt-out |
| 2 | Sessions never expire for active or polling clients | A heartbeat or a bot hitting the app keeps the session alive forever, which weakens the security assumption | Document it, and advise an absolute-lifetime check in the app |
| 3 | Extra store writes or touches on every request | The stores in `session/` and external ones with no `touch` fall back to a full resave | Recommend `resave: false` with a store that has `touch`, and put a README warning on it |
| 4 | Caching and CDN interference | `Set-Cookie` on every response makes responses uncacheable at shared caches | Advise mounting session only on dynamic routes |
| 5 | Existing tests fail or encode the old default | Many tests in `test/session.js` assume no cookie on an unmodified request | Run the suite, then fix each case with an explicit `rolling: false` |
| 6 | Race conditions on parallel requests | Concurrent requests each re-set the cookie and touch the store, and the last write wins | Keep the current `touch` semantics. Add no new locking. Mention this in the docs |
| 7 | Downstream stores or middleware assume the old default | Wrappers around `session()` that read `opts.rolling` may now see `undefined` and behave differently | Normalise the option in one place and note it in the changelog |
| 8 | `Set-Cookie` after headers sent, or on error responses | Rolling cookies on 4xx or 5xx responses and redirects may surprise clients | Add a test for error and redirect paths, and keep the existing `on-headers` hook |

Riskiest: #1, the silent breaking default change, because every existing deployment changes expiry behaviour on upgrade without any code change on its side.
