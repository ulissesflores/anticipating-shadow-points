Most of this is already done. Commit `a51468c` replaced the old hash with ASP.NET Identity's password hasher: PBKDF2-HMAC-SHA512 at 210,000 iterations, a random salt per password, and a versioned format stored in `Person.Hash`.

The old scheme was HMAC-SHA512 keyed with the public string `"realworld"`, plus a 16-byte GUID salt. `PasswordHasher.Verify` still accepts old hashes, and `Login.cs` replaces each one with a new hash on the user's next successful login. No one has to reset their password. `PasswordHashingTests.cs` covers this.

The remaining problem is that users who never log in again keep the weak old hash indefinitely. The plan (saved to `plans/store-passwords-with-a-snappy-nest.md`) closes that gap.

**Assumptions:** Keep PBKDF2 through Identity rather than adding Argon2, which would need a new package. Make no API contract or schema changes.

**Plan**
1. **Wrap old hashes** (`src/Conduit/Infrastructure/Security/PasswordHasher.cs`): add a format that stores a PBKDF2 hash of the old hash, keeping the old 16-byte salt.
   - `Verify` picks the format from the stored data:
     - salt 16 bytes and hash 64 bytes → old format
     - salt 16 bytes and first hash byte `0x01` → wrapped
     - empty salt → plain Identity
   - A correct password on a wrapped hash returns `SuccessRehashNeeded`, so the existing code in `Login.cs` replaces it with a plain hash and clears `Salt`.
2. **One-time upgrade of untouched old hashes:** a repeatable `LegacyPasswordUpgrader` wraps rows with salt 16 bytes and hash 64 bytes, in batches of about 100.
   - It runs once, from a CLI switch or a config flag, after `DatabaseInitializer.InitializeAsync`.
   - It can't be an EF migration because SQL can't compute PBKDF2.
3. **Equal login timing** (`Login.cs`): when the email is unknown, check against a dummy hash before returning 401. Otherwise the response time reveals whether an email is registered.
4. **Configurable cost:** read the iteration count from config (default 210,000) and register the hasher as a singleton (`src/Conduit/ServicesExtensions.cs:86`). A higher count already triggers a rehash at the next login.
5. **Docs:** describe the hash formats in `docs/database-migrations.md`.
6. **Tests** (`PasswordHashingTests.cs`):
   - A wrapped hash logs in with the right password and is rehashed.
   - A wrong password leaves the row unchanged.
   - Running the upgrader twice changes nothing and skips current hashes.
   - An unknown email still returns 401.
   - Raising the iteration count causes a rehash.

**Verification:** run `dotnet run --project build/build.csproj -- test`. Then seed an old-format row in SQLite, run the upgrade flag, confirm `Hash[0]==0x01`, log in through `/api/users/login`, and confirm `Salt` is empty.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Format misdetection locks users out | Format is inferred from byte lengths and the salt, with no explicit version column | Check formats in a fixed order; test every format |
| 2 | Upgrade interrupted halfway | Batch writes on a live database while users log in | Repeatable selection, save per batch, back up first |
| 3 | Startup stalls or CPU spikes | 210,000 iterations is about 50–100 ms per row | Run as an explicit one-off command in batches, not on every startup |
| 4 | Old hashes stay crackable until the upgrade runs | The HMAC key `"realworld"` is public, so these are effectively fast salted SHA-512 hashes | Run the upgrade right after deploy |
| 5 | Login CPU used for denial of service | Password has no maximum length and login has no rate limit | Add rate limiting; keep the cost configurable |
| 6 | Email enumeration through timing | Unknown emails return 401 without hashing | Check against a dummy hash |
| 7 | Rollback to an older build breaks logins | Builds before `a51468c` can't read Identity or wrapped hashes | Deploy forward only; note it in the release notes |
| 8 | Two logins at once both rehash | No concurrency token on `Person` | Harmless because both hashes are valid; last write wins |
| 9 | SQLite and SQL Server behave differently | Separate providers and contexts | Integration tests on SQLite; manual check on SQL Server |

Riskiest: #1, format misdetection, because one wrong branch in `Verify` silently locks out existing users, which is exactly what this change must avoid.
