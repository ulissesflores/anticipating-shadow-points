I made no edits, and I didn't write a plan file, because you said not to edit any file. I only read the code. The service is a small FastAPI, Tortoise ORM and Postgres app with aerich migrations. It has one model, `TextSummary`, and routes at `/summaries/{id}/`.

## Assumptions

- "Keeping existing clients working" means three things. Old clients can still send integer IDs in URLs. They can still read an integer `id` in responses. They keep working until a published deprecation date.
- UUID becomes the canonical public identifier. The integer stays as the internal primary key during the transition.
- The database is Postgres, and existing rows must be backfilled. There are no other consumers of the table.
- Nobody has pinned the API to a version, so I'm assuming a deprecation window of at least one release is acceptable.

## Ways this could go wrong, before planning

1. **Type clash in `id`.** Clients that parse `id` as an int break if it becomes a string. A single field can't be both.
2. **Ambiguous path parsing.** A dashless 32-digit all-numeric string is a valid UUID and also a valid integer. The route `Path(..., gt=0)` in `app/api/summaries.py` currently returns 422 for non-positive IDs, and the tests assert that shape.
3. **Migration on live data.** The only migration (`0_..._init.py`) has an empty `downgrade`. Adding a NOT NULL unique UUID column to existing rows needs add-nullable, backfill, then constrain, in that order. Doing it in one step locks the table or fails.
4. **Backfill and write race.** Rows inserted during the backfill, or by old app instances during a rolling deploy, get no UUID.
5. **Internal call sites.** `generate_summary(summary_id, url)`, the `crud.*` functions and the background task all pass integer IDs. If the PK type changes, a mixed-type call fails quietly. The task runs after the response, so errors surface late.
6. **Response schemas.** `SummarySchema` is generated by `pydantic_model_creator`. It will start emitting the new field, or a changed `id`, automatically. The DELETE response `{"id", "url"}` is asserted exactly in tests.
7. **Enumeration and IDOR.** Integer IDs stay guessable as long as they're accepted. There is also no auth here, so UUIDs add no real protection.
8. **Rollback.** Once clients hold UUIDs, reverting the code strands them. The empty `downgrade` makes this worse.
9. **Stale references.** Bookmarks, logs, caches and third-party links hold integer IDs. Cache keys that mix the two formats can collide or miss.
10. **Test and CI breakage.** `tests/test_summaries.py` asserts `id` equality and 422 error shapes (`loc: ["path","id"]`). Contract changes will fail these tests, and mocks that use integer IDs would pass for the wrong reason.

## Plan

1. **Schema, expand step.**
   - Add a nullable `uuid` column (`UUIDField`, unique index) with a new aerich migration.
   - Give the model `default=uuid4` so new rows always get one.
   - Backfill existing rows in batches with a separate migration. Then set the column NOT NULL.
2. **Lookup.**
   - Change the path param to `str`.
   - Add one resolver that accepts the canonical hyphenated UUID or a positive integer. It returns 422 for anything else, which keeps the current error shape.
   - Make `crud.get`, `put` and `delete` filter on the resolved field.
3. **Responses.**
   - Keep `id: int` unchanged.
   - Add `uuid: UUID` to the create, read, update and delete responses.
   - Send `Deprecation` and `Sunset` headers when a request uses an integer ID.
4. **Internals.** Pass the model instance, or the UUID, to `generate_summary`. Don't pass a bare integer.
5. **Contract, later release.** After the sunset date, make `uuid` the only identifier. Then drop integer lookups and the integer `id` field.
6. **Tests.**
   - Add UUID and integer round-trips.
   - Add a malformed-ID 422 case and the all-digit 32-character edge case.
   - Add a migration test against rows that already exist.
   - Keep the existing integer tests green. They serve as the backward-compatibility check.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | `id` type change breaks clients | One field can't be int and string | Keep `id` as int, add a separate `uuid` field, and deprecate on a schedule |
| 2 | Int/UUID path ambiguity | Dashless digit strings parse both ways | Accept only hyphenated UUIDs or short positive ints, with a strict resolver |
| 3 | Locking or failing migration | The table has existing rows, and the init migration has no downgrade | Add nullable, backfill in batches, then add NOT NULL and the index; write a real downgrade |
| 4 | Rows missing UUIDs during rollout | Old and new instances write at the same time | Use a DB-level default and deploy the model default before the backfill |
| 5 | Wrong ID type in background task | `generate_summary` takes a bare int and runs after the response | Pass the object or UUID, and add a type-checked test |
| 6 | Auto-generated schemas shift the contract | `pydantic_model_creator` exposes new fields silently | Define explicit response schemas and snapshot them in tests |
| 7 | Guessable IDs remain | Integer lookups stay open and there is no auth | Set a sunset date and note that this change is not a security control |
| 8 | Rollback strands clients | UUID-only consumers can't use old code | Keep both lookups during the window; make the migrations reversible |
| 9 | Stale integer references | Logs, caches and bookmarks hold old IDs | Keep integer lookup until the sunset and namespace cache keys |
| 10 | Tests pass for the wrong reason | Mocks and 422 shape assertions use integers | Add dual-format cases and run integration tests against real Postgres |

Riskiest: #1. A single `id` field can't serve both old and new clients, so the compatibility promise fails unless `id` stays an integer and `uuid` is added alongside it.
