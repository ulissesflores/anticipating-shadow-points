## Assumptions
- "All of their data" means the user's own profile, their posts and their comments, as one JSON file. I'm leaving out password hash, auth tokens and other users' private data.
- The download is an authenticated, session-based route such as `/export`, plus a button on the user's own profile page. It is not an admin tool.
- The existing `to_json()` methods on `User`, `Post` and `Comment` in `app/models.py` are reused. They were written for the public API, so they need an audit before reuse.
- Most users have a modest amount of data. A synchronous download is acceptable at first, with streaming as a fallback.
- Comments the user wrote on other people's posts count as "their comments". Comments other people left on the user's posts do not.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Another user's data is exposed (IDOR) | Routes like `/user/<username>` and `/edit-profile/<int:id>` take a target in the URL, and a copied pattern could skip the ownership check | Use no URL parameter and export only `current_user`. Add a test that user A cannot get user B's data. |
| 2 | Secrets or internal fields leak | `User` has `password_hash`, `email`, `role_id` and `confirmed`. `to_json()` is shaped for the public API, so it may leave out or add the wrong fields. | Write an explicit export serializer with a field allowlist. Never serialize the model wholesale. |
| 3 | Export is slow or blocks the worker | `posts` and `comments` are `lazy='dynamic'`. A prolific user means large queries and one big in-memory payload under Gunicorn or Heroku's 30s limit. | Stream the response, use a paginated or chunked query, and cap the size. Consider a background job later. |
| 4 | N+1 queries | Serializing each comment that links to its post and author triggers extra queries per row | Use eager loading (`joinedload`) or plain column queries. |
| 5 | Session-hijack or CSRF-style abuse | A GET that returns all personal data can be hit through a stolen session or a cross-site trigger | Require `@login_required` and `confirmed`. Consider re-entering the password. Send `Cache-Control: no-store`. |
| 6 | Abuse or DoS through repeated downloads | A heavy endpoint available to every user is easy to hammer | Add rate limiting (for example, one export per few minutes per user). |
| 7 | Wrong or incomplete content | `body_html` is derived content. Disabled (moderated) comments, followers and the following list are easy to forget, and the format must match what the user expects. | Decide the scope explicitly. Export raw `body`, mark `disabled`, and document the schema. |
| 8 | Encoding and file-format problems | Non-ASCII text, naive UTC datetimes and filename injection from the username in `Content-Disposition` | Use UTF-8 JSON with ISO 8601 timestamps. Build the filename from the user id, not free text. |
| 9 | Privacy and legal gaps | The export may omit data the user is entitled to (GDPR-style access), or include data about other people | Review field coverage with the owner. Exclude other users' emails. |
| 10 | Regression in the test suite | The existing tests (`test_client.py` and `test_api.py`) run against the same models, and a new route could break a url_map assumption | Add unit and client tests for the route, then run the full suite. |

Riskiest: #1/#2. A data-export endpoint that leaks another user's data, or fields like `password_hash`, is a serious privacy breach, so the export should serve only `current_user` and use an explicit field allowlist.
