## Ways this could go wrong

I only read the repo (Clean Architecture .NET template). I changed nothing.

**What I found**
- `TodoList` and `TodoItem` derive from `BaseAuditableEntity` and have no owner field.
- `GetTodos` reads `_context.TodoLists` directly, with no filter.
- `ApplicationDbContext` is an `IdentityDbContext<ApplicationUser>`, so users have no company either.
- `IUser` and `CurrentUser` expose only a user id.
- There is no `Migrations` folder, and `ApplicationDbContextInitialiser` seeds the data.
- Handlers use `_context.TodoLists.FindAsync(id)` and similar lookups, which skip any filter you don't apply.

**Assumptions**
- "Tenant" means a company. Each user belongs to exactly one tenant.
- The tenant id comes from a claim in the sign-in token, never from the request body or URL.
- The database is shared and rows carry a `TenantId` column.
- Existing rows go to a single default tenant.
- A list's items always share the list's tenant.

**Failure modes**
1. **Missed read path.** Handlers that bypass the filter, such as `FindAsync`, `IgnoreQueryFilters`, raw SQL, or projections that skip it, leak or expose rows.
2. **Cross-tenant IDs.** A user can read or delete a row by guessing its integer id. Without a tenant check, `UpdateTodoItem` or `DeleteTodoList` works on another company's data.
3. **Unsafe tenant source.** If the tenant comes from client input, or the claim is missing at sign-in, every row leaks or every call fails.
4. **Item and list mismatch.** A new item could point at a `ListId` that belongs to a different tenant.
5. **Background code with no user.** Domain event handlers, the seeder and any job have no HTTP user. They would write null or default tenants, or see no data.
6. **Backfill failure.** Adding a non-null `TenantId` to rows that already exist fails the migration, or tags everything with the wrong tenant.
7. **Missing indexes.** Without indexes that lead with `TenantId`, queries slow down as data grows.
8. **Tests break or lie.** Functional tests that use one fake user hide leaks. Existing tests fail until they set a tenant.
9. **Client assumptions.** The Angular and React clients and the API may assume global ids and an unfiltered list.
10. **Identity mismatch.** If the tenant isn't on `ApplicationUser` and in the token, the claim, the user record and the data can disagree.

**Plan outline (not executed)**
1. Add `ITenantEntity { TenantId }`, put `TenantId` on `ApplicationUser`, and add a `TenantId` claim.
2. Add `ITenantProvider` (or extend `IUser`) that reads the claim.
3. In `ApplicationDbContext`, add global query filters on both entities, plus an `ISaveChangesInterceptor` that stamps `TenantId` on insert and rejects changes to it.
4. Add a migration that backfills a default tenant, then makes the column non-null and indexed.
5. Add tests with two tenants for list, get, update and delete.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Query bypasses the filter | Handlers use `_context` directly, with `FindAsync` and `ProjectTo` | Global query filters, ban `IgnoreQueryFilters`, review every handler |
| 2 | Cross-tenant id access | Integer ids are guessable | Filter applies to lookups, return 404 for other tenants |
| 3 | Tenant from untrusted source | `IUser` has only an id today | Take it from a signed claim, fail closed if missing |
| 4 | Item attached to another tenant's list | `ListId` comes from the request | Validate the list is in the tenant, stamp the item from the list |
| 5 | No user in background paths | Domain events and the seeder run without a request | Explicit tenant scope for system code, tests for it |
| 6 | Migration or backfill failure | The schema has no tenant column, and existing rows exist | Add nullable, backfill, then make non-null, rehearse on a copy |
| 7 | Slow queries | Every query now filters on tenant | Composite indexes with `TenantId` first |
| 8 | Tests pass but leaks remain | Tests use a single user | Add two-tenant isolation tests for every endpoint |
| 9 | Client or API contract drift | Both frontends assume the current responses | Keep response shapes unchanged, run the client builds |
| 10 | Identity and data disagree | `ApplicationUser` has no tenant | Single source of truth, set at registration, put it in the token |

Riskiest: #1, a missed read or write path that silently exposes another company's data.
