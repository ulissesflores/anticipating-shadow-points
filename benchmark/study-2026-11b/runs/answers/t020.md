# Plan: tenant-scope to-do lists and items

## Context
This is the Clean Architecture template (.NET, EF Core, MediatR, Angular and React clients). Today `TodoList` and `TodoItem` are global, so every authenticated user sees every list.

- **Entities:** both inherit `BaseAuditableEntity` (`src/Domain/Common/BaseAuditableEntity.cs`).
- **Reads:** `GetTodosQueryHandler` (`src/Application/TodoLists/Queries/GetTodos/GetTodos.cs`) reads `_context.TodoLists` with no filter.
- **By-id commands:** the update, delete and detail handlers use `FindAsync([request.Id])`. That is 4 call sites: `UpdateTodoItem`, `UpdateTodoItemDetail`, `DeleteTodoItem` and `UpdateTodoList`.
- **Create:** `CreateTodoItem` trusts a client-supplied `ListId`.
- **Identity:** `IUser` exposes only `Id` and `Roles`. `ApplicationUser` is a bare `IdentityUser`, and there is no tenant concept anywhere.
- **Schema:** there are no migrations. `ApplicationDbContextInitialiser` runs `EnsureDeleted` then `EnsureCreated` and seeds data.

## Assumptions
- "Company" equals "tenant". One user belongs to exactly one tenant, and the tenant id is a `Guid`.
- The tenant id comes from a `tenant_id` claim on the authenticated principal, populated from `ApplicationUser.TenantId`.
- Row-level isolation in a shared database, not a database or schema per tenant.
- Admin roles do not cross tenants.
- Existing dev data can be dropped, since the initialiser already recreates the database. If a real deployment exists, add a real migration and backfill.

## Steps
1. **Domain**
   - Add `ITenantEntity { Guid TenantId { get; set; } }`.
   - Implement it on `TodoList` and `TodoItem`. Putting `TenantId` on the item too, not only the list, avoids a join in the filter and allows a direct index.
   - Optionally add a `Tenant` entity with a name.
2. **Identity and current tenant**
   - Add `TenantId` to `ApplicationUser` (`src/Infrastructure/Identity/ApplicationUser.cs`).
   - Add `Guid? TenantId` to `IUser` (`src/Application/Common/Interfaces/IUser.cs`). Implement it in `CurrentUser` (`src/Web/Services/CurrentUser.cs`), reading the `tenant_id` claim.
   - Emit the claim at sign-in with a custom `IUserClaimsPrincipalFactory<ApplicationUser>`.
   - Registration must assign or create a tenant. For example, accept an invite or company code, or create a new tenant on first sign-up.
3. **Query isolation (primary control)**
   - In `ApplicationDbContext`, inject `IUser` and add `HasQueryFilter(e => e.TenantId == CurrentTenantId)` on both entities.
   - Do it generically in `OnModelCreating` over `ITenantEntity` types.
   - Expose `CurrentTenantId` as a context property so EF re-evaluates it per request.
   - Fail closed. If there is no tenant, the filter matches nothing.
   - Because filters apply to `FindAsync`, `ProjectTo` and navigation includes, most handlers become safe with no change.
4. **Write isolation**
   - Add `TenantEntityInterceptor`, modelled on `AuditableEntityInterceptor`. On `Added`, it stamps `TenantId` from `IUser`. On `Modified`, it throws if `TenantId` changed.
   - Register it in `Infrastructure/DependencyInjection.cs`.
   - In `CreateTodoItem`, check that `ListId` resolves to a list. The filter makes a foreign list return null, so use `Guard.Against.NotFound`. Otherwise a cross-tenant `ListId` would pass.
5. **Schema**
   - Configure `TenantId` as required and indexed in `TodoListConfiguration` and `TodoItemConfiguration`. Use composite indexes such as `(TenantId, ListId)`.
   - Update seed data in `ApplicationDbContextInitialiser` with two tenants and a user in each.
6. **Hardening**
   - Add `[Authorize]` plus a tenant-required check in `AuthorizationBehaviour` (`src/Application/Common/Behaviours/`). Reject authenticated users who have no tenant.
   - Audit every `IgnoreQueryFilters` and raw SQL call. Currently there are none.
   - Domain event handlers and background work run outside a request, so give them an explicit tenant scope.
7. **Clients**
   - The API contract mostly does not change, because the tenant is implicit.
   - Regenerate the NSwag clients only if a DTO changes.
   - Registration UI (Angular and React) needs a company field if sign-up creates or joins a tenant.
8. **Tests**
   - In `tests/Application.FunctionalTests`, extend `FunctionalTestSetup` and the user-running helpers to run as a user in a chosen tenant.
   - Add cross-tenant cases for each handler: get, update, delete, create with a foreign `ListId`, and detail update.

## Verification
- Run `dotnet test` for the unit and functional suites. The new cross-tenant tests must prove tenant B gets "not found" for tenant A's ids and an empty `GetTodos`.
- Run the app with Aspire and log in as the two seeded users. Confirm that each sees only its own lists, and that calling the API with another tenant's id returns 404.
- Inspect the generated SQL or EF logs and confirm `WHERE TenantId = @p` appears on every to-do query.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Missed filter leaks cross-tenant data | Handlers call `_context` directly, with no repository layer | Global query filter; a test per handler |
| 2 | Cross-tenant `ListId` on create | `CreateTodoItem` trusts the client's `ListId` | Resolve the list through the filtered set first |
| 3 | No tenant on the principal | Template users have no tenant concept; the seeded admin would see nothing | Fail closed; seed tenants; reject tenantless users |
| 4 | Stale or forged tenant claim | Cookies and bearer tokens outlive membership changes | Derive the claim server-side only; short token lifetime |
| 5 | Filter bypass | `IgnoreQueryFilters` or raw SQL is easy to add later | Code-review rule; analyzer or grep check in CI |
| 6 | Existing data has no tenant | A required column cannot be added to populated rows | Backfill a default tenant in a migration; dev DB is recreated |
| 7 | Background and domain-event code | `TodoItemCompletedEvent` handlers have no HTTP user | Pass the tenant on the event; use an explicit scope |
| 8 | Query filter on `FindAsync` assumptions | Tests or code may rely on global lookups | Add tests; use a test-only context without a filter |
| 9 | Orphaned client work | Registration UI and NSwag clients need updates | List in scope; regenerate clients |
| 10 | Performance regression | Every query gains a `TenantId` predicate | Composite indexes starting with `TenantId` |

Riskiest: #1, a missed filter leaking another company's data.
