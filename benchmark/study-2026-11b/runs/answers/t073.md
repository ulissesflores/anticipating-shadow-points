**Finding:** the repo already contains most of this change, so the plan is to verify it, close a few gaps and decide on the long tail. I read these files and did not run any tests:

- `src/Conduit/Infrastructure/Security/PasswordHasher.cs` hashes new passwords with ASP.NET Identity's `PasswordHasher<T>`. That is PBKDF2-HMAC-SHA512 at 210,000 iterations, with a random salt stored inside the payload.
- `Verify` still accepts the legacy format, which is a 64-byte HMAC-SHA512 hash with a 16-byte salt. A successful legacy check returns `SuccessRehashNeeded`.
- `Login.cs` (lines 81–82) then rehashes the password and writes it back with an empty `Salt`. `Edit.cs` and `Create.cs` also write the new format.
- `PasswordHashingTests.cs` covers the legacy-to-new upgrade.

## Assumptions
- "Stronger" means a slow, salted, work-factor-tunable KDF. PBKDF2-SHA512 at 210k iterations is acceptable under OWASP guidance and needs no new dependency. Argon2id would be stronger still, but it needs a third-party package and a lock-file update.
- The `Hash` and `Salt` columns are `byte[]` with no length cap that blocks the roughly 61-byte Identity payload. I didn't check the migrations.
- Existing users are upgraded lazily at their next successful login. Nothing needs an offline reset.

## Verification
- **Legacy login:** a seeded legacy user logs in once and the row is rewritten to the new format.
- **Wrong passwords:** wrong passwords against both formats return 401 and do not rewrite the row.
- **Password edit:** changing a password writes the new format.
- **Hash randomness:** two hashes of the same password differ.
- **Manual check:** run the app with `make run-local`, or run the optional Hurl/Bruno RealWorld suite.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Dormant users stay on legacy HMAC | The upgrade only happens at login, and the legacy scheme uses a constant key `"realworld"` | Option B wrap migration, or force a reset after a deadline |
| 2 | Format sniffing by length | Legacy is identified only by 64-byte hash plus 16-byte salt | Named constant, tests, and a version marker if option B is used |
| 3 | Login CPU cost | 210k iterations per login and per rehash can be abused for DoS | Rate-limit login, benchmark, keep the count configurable |
| 4 | Rehash write fails or races | `SaveChanges` runs in the login path, and concurrent logins can both rewrite | Last write wins safely, since both hashes are valid. Don't fail the login on a save error |
| 5 | Rollback breaks users | Older code can't read new-format hashes, so rolled-back users can't log in | Ship the verify path first, and don't remove legacy support |
| 6 | Account enumeration by timing | The unknown-email 401 skips hashing, which is now more expensive | Dummy verify on the not-found path |
| 7 | Column or schema mismatch | The two providers have separate migrations, and the payload is longer than 64 bytes | Check column types, and add migrations for both providers if needed |
| 8 | Hash rewrite on password edit | `Edit.cs` sets `Salt = []`, so a partially failed update could leave a mixed state | Single `SaveChanges`, with a test |
| 9 | Dependency drift if switching to Argon2 | A new package needs central versions and lock files, and CI enforces a locked restore | Stay on Identity PBKDF2 unless Argon2 is required |

Riskiest: #1, because accounts that never log in keep the weak, constant-keyed legacy hash indefinitely.
