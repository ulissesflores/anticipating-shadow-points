# Plan: require email verification before login

I only read the repo and edited nothing. The plan file in the plan-mode instructions would be an edit, so I'm giving the plan here instead.

## What the code does today

This is a Remix "Blues Stack" app on Prisma and Postgres, with cookie sessions.

- `app/routes/join.tsx` creates the user and then calls `createUserSession`, so signup logs the user in immediately.
- `app/routes/login.tsx` calls `verifyLogin` (`app/models/user.server.ts`) and then `createUserSession`. Nothing checks verification status.
- `app/session.server.ts` stores only `userId` in the cookie. `requireUser` and `getUser` look the user up by id.
- The `User` model in `prisma/schema.prisma` has no verification field. The app has no email-sending code.
- `cypress/e2e/smoke.cy.ts`, `cypress/support/create-user.ts` and `prisma/seed.ts` all create users directly and expect them to be logged in.
- The `mocks/` folder uses msw, which can stub an email provider in e2e runs.

## Assumptions

- "New users" means accounts created after this ships. Existing users are grandfathered and keep logging in.
- Verification is a link sent by email, with a single-use token that expires after 24 hours. The token is stored as a hash.
- I'll use an email provider over HTTP (Resend or Postmark), with its API key in an env var. In development and tests, the mailer logs the link or is stubbed through msw.
- No new auth library. I'll extend the existing session and model code.

## Steps

1. **Schema and migration** (`prisma/schema.prisma`, new migration).
   - Add `User.emailVerifiedAt DateTime?`.
   - Add an `EmailVerificationToken` model with `tokenHash @unique`, `userId` (cascade delete), `expiresAt` and `createdAt`.
   - In the same migration, run `UPDATE "User" SET "emailVerifiedAt" = "createdAt"` so existing users stay able to log in.
2. **Model layer** (`app/models/user.server.ts`).
   - Add `createVerificationToken(userId)`. It generates a random token with `crypto.randomBytes`, stores its SHA-256 hash, and deletes the user's older tokens.
   - Add `verifyEmailToken(token)`. It checks the hash and expiry, sets `emailVerifiedAt`, and deletes the token.
   - Add an `isVerified` helper.
   - Change `verifyLogin` to return a distinct result for "correct password, unverified". The password must be checked first, so the response doesn't reveal which emails are registered.
3. **Mailer** (new `app/email.server.ts`). One `sendVerificationEmail(to, url)` function. The base URL comes from a new env var, which goes in `.env.example`. Without an API key, it logs the link to the console.
4. **Signup** (`app/routes/join.tsx`).
   - Create the user and send the email.
   - Remove the `createUserSession` call.
   - Redirect to a new `/verify-email?sent=1` page.
   - Keep the "email already exists" error as it is today.
5. **Login** (`app/routes/login.tsx`). If the password is correct but the account is unverified, don't create a session. Show "Please verify your email" with a resend button.
6. **New routes.**
   - `app/routes/verify-email.tsx` is the "check your inbox" page.
   - `app/routes/verify-email.$token.tsx` consumes the token. On success it either redirects to `/login` with a notice or creates the session. I'll redirect to `/login` so the token link isn't a login credential.
   - `app/routes/resend-verification.tsx` is a POST-only route. It always returns the same message, whether or not the email exists, and is rate-limited per email and per IP.
7. **Defence in depth** (`app/session.server.ts`). In `requireUserId` and `requireUser`, reject sessions whose user has no `emailVerifiedAt`. This closes any path that issues a session without the check, and it ends sessions that were open before the migration for users who were never verified.
8. **Tests and tooling.**
   - Update `prisma/seed.ts` and `cypress/support/create-user.ts` to set `emailVerifiedAt`.
   - Rewrite the Cypress smoke test to sign up, read the token from the stub, visit the link, then log in.
   - Add vitest unit tests for token creation, expiry, reuse and the login gate.

## Verification

- Run `npm run typecheck`, `npm run lint`, `npm test -- --run`, and `npm run test:e2e:run`.
- Run `prisma migrate deploy` on a copy of production-like data and confirm every existing user has `emailVerifiedAt` set.
- Check these by hand:
  - A new user can't log in before verifying.
  - A used token fails.
  - An expired token fails.
  - Resending invalidates the earlier link.
  - An old user still logs in.
  - `/notes` rejects a forged unverified session.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | The new column is null for everyone already in the database | Backfill `emailVerifiedAt` in the migration itself |
| 2 | Email never arrives | The app has no mail code or provider, and spam filters can drop it | Use an authenticated sending domain, add a resend flow, and log failures |
| 3 | Account enumeration | `join` already says "user exists", and the new login and resend messages could leak the same | Check the password first, return neutral resend responses, and accept the signup leak or fix it separately |
| 4 | Token weaknesses | Tokens that are guessable, reusable, stored in plaintext or never expiring | Use 32 random bytes, store a hash, make tokens single-use, and expire them after 24h |
| 5 | Session bypass | `join` and `create-user.ts` issue sessions directly, and cookies are valid on their own | Remove the join session, and enforce verification in `requireUser` |
| 6 | Email abuse | An open resend route can be used to spam or mail-bomb an address | Rate-limit per email and per IP, and add a cooldown |
| 7 | Broken e2e and seed flows | The Cypress smoke test, seed and helper script assume instant login | Update them in the same PR and stub the mailer in msw |
| 8 | Wrong base URL in links | Fly deploys and previews have different hosts | Use an explicit env var and fail loudly if it's unset in production |
| 9 | Unverified squatting | Someone can register an email they don't own and block the real owner | Allow re-signup to overwrite an unverified account, and purge stale ones |
| 10 | Migration on live DB | A schema change plus backfill on Fly Postgres during a deploy | Make the migration additive, take a backup, and deploy the migration before the code |

Riskiest: #1, existing users locked out if the backfill is missed or runs after the code that checks `emailVerifiedAt`.
