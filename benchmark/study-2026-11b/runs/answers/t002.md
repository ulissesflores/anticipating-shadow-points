Here is the plan. I didn't edit any repo files; the plan is saved at `claude-home/plans/replace-the-integer-ids-snappy-spark.md`.

## What exists today
- `textsummary.id` is a Postgres `SERIAL` primary key (`migrations/models/0_20250421234125_init.py`).
- That integer leaks out in two places. Every response has `id: int`: `SummaryResponseSchema` and the `SummarySchema` built by `pydantic_model_creator`. Every path takes `{id}` as `int = Path(gt=0)` (`app/api/summaries.py`).
- `crud.py` and `summarizer.py` look rows up with `filter(id=...)`.
- Schema changes are made with aerich, by hand. Nothing in `Dockerfile.prod` or CI runs `aerich upgrade`.

## Assumptions
- Existing clients store the integer `id` and send it back. So changing the type of `id` in place would break them.
- The integer primary key stays as an internal key. There are no foreign keys, but swapping a primary key is risky for little gain.
- The database is Postgres 17, so `gen_random_uuid()` is available without an extension.
- "Keep clients working" means the current `/summaries` response shape doesn't change, apart from added fields.

## Plan
1. **Model:** add `uuid = fields.UUIDField(default=uuid4, unique=True)` to `TextSummary` and keep `id` as the primary key.
2. **Migration** (aerich, checked by hand), in this order:
   - add a nullable `uuid` column;
   - fill existing rows with `gen_random_uuid()`;
   - set the column default;
   - set `NOT NULL`;
   - add a unique index.

   It also gets a real `downgrade`, which the current init migration doesn't have.
3. **Lookup helper in `crud.py`:** look up by UUID if the value is a UUID, otherwise by the integer. `get`, `put` and `delete` take this reference, and `post` returns both IDs.
4. **v1 (`/summaries`), kept compatible:**
   - The path accepts either form. All digits means a legacy integer, which must still be greater than 0. Anything else is parsed as a UUID, and an invalid value returns 422.
   - Responses keep `id: int` and add a new `uuid` field.
   - Requests that use an integer get `Deprecation` and `Sunset` headers and are counted.
5. **v2 (`/v2/summaries`), new:**
   - `id` is the UUID, the integer never appears, and paths accept UUIDs only.
   - It uses its own pydantic schemas in `app/models/pydantic.py` rather than `pydantic_model_creator`, which would output both IDs.
6. **Background task:** `generate_summary` keeps using the internal integer key, so it doesn't change.
7. **Sunset:** when integer traffic on v1 reaches zero, remove the integer lookup and then v1.

## Verification
- Run `docker-compose exec web python -m pytest`. The existing integer-based tests must still pass; only the expected JSON gains the `uuid` key. Passing them is the proof that old clients still work.
- Add tests for:
  - v1 get, update and delete by UUID;
  - full create/read/update/delete on v2;
  - v2 rejecting integers;
  - malformed IDs returning 422;
  - unknown UUIDs returning 404.
- Run `aerich upgrade` on a copy of the database with existing rows. Check that no row has a null `uuid`, then run `aerich downgrade` to test the rollback.
- Compare the OpenAPI spec for `/summaries` before and after; it should only gain fields.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Changing `id`'s type breaks clients | Every response and path uses `id: int` | Keep v1 `id` as an integer, add `uuid`; put the UUID `id` in v2 only |
| 2 | Migration not applied before deploy | Nothing runs `aerich upgrade` automatically | Add an explicit release step; ship the migration before the code |
| 3 | Rows left without a UUID / `NOT NULL` fails | Existing rows need filling before the constraint is added | Add nullable, fill, then constrain, all in one migration; verify the null count is 0 |
| 4 | Ambiguous path parsing | `"123"` could be read as an integer or a string | All digits means integer, otherwise strict UUID parsing, otherwise 422 |
| 5 | Auto-generated schema exposes both IDs | `pydantic_model_creator(TextSummary)` includes every field | Write explicit response schemas for v2 |
| 6 | Integers stay guessable on v1 | v1 still accepts integer IDs | Deprecation headers, metrics, and a dated sunset |
| 7 | Tests miss production behaviour | Tests use `generate_schemas=True`, not migrations | Also test the migration on a copy with data |
| 8 | Lock or slow fill on a large table | One `UPDATE` across the whole table | Fill in batches if the table is large; build the index `CONCURRENTLY` |
| 9 | No rollback path | The init migration's `downgrade` is empty | Write a real `downgrade` that drops the column |

Riskiest: #1. Changing the type of the `id` field would break every existing client, which is why that field must not change on v1.
