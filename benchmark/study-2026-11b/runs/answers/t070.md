## Plan

**Where rolling is decided today**
- `index.js:109` has `var rollingSessions = Boolean(opts.rolling)`, so an unset option means `false`.
- `rollingSessions` is read in one place, `shouldSetCookie` (`index.js:~491`). With it on, every response for an existing session re-sends the `Set-Cookie` header with a fresh expiry. With it off, the cookie is re-sent only when the session was modified.
- Store-side expiry is handled separately. `shouldTouch` and `store.touch` (or a resave) already extend it on every request. So the change only affects the cookie's expiry in the browser.

**Assumptions**
- "Default" means that omitting `rolling` now behaves like `rolling: true`. An explicit `rolling: false` still opts out.
- This ships as a breaking change, so a major version bump to 2.0.0, with a HISTORY entry. A deprecation cycle (a warning when `rolling` is undefined, like the existing `resave` one) is the softer alternative.
- The `saveUninitialized: false` guard stays as it is. No cookie is sent when no session was loaded for the request, as documented in the README note.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Breaking default change | Every existing user gets a `Set-Cookie` on every response after upgrading | Major bump, a HISTORY entry, and an optional one-release deprecation warning |
| 2 | Sessions never expire for active users | Rolling extends the cookie with no absolute cap, so a polling tab keeps the session alive | Document it, and suggest an absolute-lifetime check in the app |
| 3 | HTTP cache and CDN breakage | A `Set-Cookie` on every response stops shared caches storing public pages | Document `rolling: false` for cacheable routes, or a per-route opt-out |
| 4 | Many existing tests fail | The suite assumes cookies are not re-sent on unmodified sessions | Make the opt-out explicit per test and review each diff |
| 5 | Cookie-size and bandwidth overhead | Each response adds a signed cookie header, which matters for APIs and static assets | Note it in the README and keep the guidance on mounting the middleware per route |
| 6 | Parallel-request cookie races | Concurrent responses may overwrite each other's cookie with different expiry values | Expiry is derived from the same `maxAge`, so it is low impact. Add a note |
| 7 | Session-fixation or cookie-handling surprises | Proxies and clients now see cookies on read-only requests | Keep the `secure`, `httpOnly` and `sameSite` defaults, and test proxy and secure-cookie paths |
| 8 | Stores that lack `touch` | With `resave: false` and no `touch`, the cookie rolls but the store entry doesn't, so the two expiries drift apart | Add a README warning and a test for this case |
| 9 | Docs and typings drift | `@types/express-session` and the README still say the default is `false` | Update the README and send a PR to DefinitelyTyped |

Riskiest: #1, the breaking default change, because it silently changes cookie and caching behavior for every existing deployment on upgrade.
