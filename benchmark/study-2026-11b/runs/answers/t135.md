I've planned a "Download my data" feature for this Flasky app. A logged-in user clicks a button on their own profile and gets one JSON file with their profile, posts and comments. I didn't change any code; the plan is saved at `claude-home/plans/let-every-user-download-shimmying-bear.md`.

## Assumptions
- **Format:** one JSON file named `flasky-<username>-<YYYYMMDD>.json`. JSON needs nothing new installed, which suits this old Flask 0.12 setup.
- **What's included:**
  - the user's profile: username, email, name, location, about me, role name, confirmed flag, member since, last seen;
  - every post they wrote;
  - every comment they wrote, including ones a moderator disabled, marked as disabled.
- **What's left out:**
  - other people's comments on the user's posts, because that's someone else's data;
  - followers and following;
  - the password hash, avatar hash, tokens and internal role id.
- **How it runs:** the file is built during the request. One user's data is small and the app has no background job queue.
- **Who can export:** confirmed users only. The app already sends unconfirmed users to a "please confirm" page for every page outside login, and an unconfirmed user can't have posts or comments yet.
- Admins can't export another user's data in this change.

## Changes
1. **`app/models.py`:** add `User.export_data()`. It returns a plain dictionary with `export_version`, `exported_at`, `profile`, `posts[]` and `comments[]`.
   - Each post and comment links back to its page on the site.
   - Dates are written as ISO format (`2026-11-14T10:00:00Z`). This Flask version would otherwise turn them into email-style date strings.
   - I won't reuse the existing `to_json()` methods. They're built for the API, with relative API links, no email and no disabled flag.
2. **`app/main/views.py`:** add a `GET /export` page that requires login.
   - It only ever exports the logged-in user's own data. There's no user id in the address, so nobody can ask for someone else's file.
   - The response makes the browser save the file instead of showing it, and tells it not to cache the file.
3. **`app/templates/user.html`:** add a "Download my data" button next to "Edit Profile". It only shows on your own profile.
4. **Tests:**
   - `tests/test_client.py`: export works for the owner, the file downloads correctly and is valid JSON, it contains the posts, comments and email, no password hash or other people's comments leak, and a logged-out visitor is sent to the login page.
   - `tests/test_user_model.py`: `export_data()` has the expected sections and leaves out the excluded fields.

## Verification
Run `flask test`. Then run the app by hand: log in, download the file and check its contents. Log in as a second user and confirm `/export` only ever returns that user's data.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Secrets leak into the file | The `User` model holds the password hash and avatar hash next to profile fields | Explicit allow-list of fields; a test that the password hash is absent |
| 2 | One user gets another's data | Adding a `<username>` or `<id>` to the address later would make this easy to get wrong | No user id in the address, only the logged-in user; a two-user test |
| 3 | Other people's data is exported | Comments on the user's posts belong to other users | Export only comments the user wrote; test for it |
| 4 | Dates in the wrong format | Flask 0.12 turns dates into email-style strings | Write dates as ISO format explicitly |
| 5 | Slow or memory-heavy for very active users | The whole file is built in memory with no paging | Fine at current sizes; stream or queue it later if needed |
| 6 | Copies of the file stay in caches or proxies | It's a personal-data download | Tell browsers and proxies not to store it; site is served over HTTPS |
| 7 | Unconfirmed users can't export | The existing confirm check redirects them | Accepted for now; allow the export page for them if required |
| 8 | Repeated downloads put load on the server | The app has no rate limiting | Low cost per request; add a limit if it's abused |
| 9 | Disabled comments upset moderators | Users would see content a moderator hid | Include them with a disabled flag, which is the user's right of access |
| 10 | The file's layout drifts over time | Others may later rely on its fields | Include `export_version` and update it when the layout changes |

Riskiest: #1. A secret field like the password hash leaking into the export.
