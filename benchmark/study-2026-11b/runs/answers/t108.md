## Finding

The repo already does most of this. `src/Conduit/Infrastructure/Security/PasswordHasher.cs` has these properties:
- **New hashes:** ASP.NET Identity's PBKDF2-HMAC-SHA512 with 210,000 iterations. The salt is embedded in the payload, and `Person.Salt` is left empty.
- **Legacy hashes:** 64-byte `HMACSHA512("realworld", password+salt)` values are still verified.
- **Rehash on login:** `Login.cs:79` rewrites a legacy hash after a successful login. `Create.cs` and `Edit.cs` also write new-format hashes.

So the open question is what "stronger" means beyond that. I have not edited anything.

## Assumptions

- **Target:** a memory-hard algorithm, Argon2id, is the goal. PBKDF2 is already in place, and its only upgrade is a higher iteration count. Argon2id is not in the .NET BCL, so it needs a new package.
- **Migration style:** it stays lazy, rehashing on successful login. I'm not wrapping stored hashes, and there is no forced reset.
- **Schema:** the `Hash` and `Salt` columns stay as they are. A format marker or prefix inside `Hash` tells the algorithms apart, so there is no schema change and no second pair of migrations (SQLite and SQL Server).
- **Dormant accounts:** accounts that never log in keep their old hashes. I'm treating that as acceptable but not ideal.

## Ways this could go wrong (before planning)

1. **Algorithm detection is wrong.** `PasswordHasher.cs` picks the legacy format by `hash.Length == 64`. A new format whose output happens to be 64 bytes, or Identity's own payload, could be misrouted or never verify.
2. **Lockout.** A bad verifier, a changed parameter set, or a rehash that writes a corrupt value could make users unable to log in, and there is no reset path.
3. **Rehash write failures.** The rehash happens in `Login` and shares `SaveChangesAsync` with the response. A concurrent write, a DB error, or a lost update (for example a password change in `Edit.cs` racing a login) could overwrite a newer hash with an older one.
4. **Rollback is one-way.** After rollout, rehashed users can't be verified by the old code, so reverting the deploy locks them out.
5. **Cost and denial of service.** Argon2id with high memory and an unthrottled `/users/login` lets an attacker exhaust CPU or RAM. Parameters tuned on a laptop may differ on production hardware.
6. **Mixed or stale parameters.** Identity's `SuccessRehashNeeded` is only returned for older Identity formats. If I add an algorithm, upgrades between parameter versions need explicit handling, or people stay on weak hashes.
7. **Legacy hashes stay forever.** The HMAC code has to remain verifiable for dormant accounts, and the hash is unsalted-key (a constant key, "realworld"). The weak hashes remain in the DB until each user logs in.
8. **Test fixtures and RealWorld contract.** Existing integration tests may seed legacy hashes. The Hurl and Bruno suites expect the exact login and register behavior and status codes.
9. **Dependency and supply chain.** A new package means central version management, `packages.lock.json` updates, locked-restore CI failures, and a trust decision.
10. **Information leaks.** Timing differences between legacy, new, and unknown-user paths could reveal which format an account uses or whether the account exists. Logging passwords or hashes on error paths is also a risk.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Format detection misroutes | Legacy check is `hash.Length == 64` | Use an explicit version prefix. Add a test per format. |
| 2 | Users locked out | No reset flow exists | Verify before rewrite. Keep legacy and current verifiers. Add round-trip tests. |
| 3 | Stale rehash overwrites a newer hash | `Login` and `Edit` both write `Hash` | Use a concurrency token or a conditional update. Rehash only if the hash is unchanged. |
| 4 | Rollback locks out rehashed users | The old build can't read the new format | Ship a read-compatible verifier first. Enable writes in a later release. |
| 5 | Login CPU/RAM denial of service | Heavy hashing runs on an unauthenticated endpoint | Benchmark on production hardware. Add rate limiting and a concurrency cap. |
| 6 | Weak hashes persist for dormant users | Migration happens only at login | Report the share of legacy hashes. Consider a hash-wrapping batch job later. |
| 7 | Contract or test regressions | RealWorld suites and seeded hashes depend on current behavior | Run the full `test` target and the Hurl and Bruno suites. |
| 8 | Dependency or lock-file failure | CI enforces locked restore | Pin in `Directory.Packages.props`. Commit the lock files. |
| 9 | Timing and logging leaks | Different code paths per format and for unknown users | Do a dummy hash on unknown users. Never log secrets. |
| 10 | Redundant work | Most of the migration already exists | Confirm the target algorithm before building. Possibly just raise iterations. |

Riskiest: #3. A stale rehash can silently overwrite a newer password hash, and the login path already writes to `Hash`.
