This is the `itsdangerous` library. I made no edits, and I didn't write a plan file, since you said not to change any file.

## Assumptions
- "Default signing digest" means `default_digest_method` on `Signer` and `HMACAlgorithm`, currently `_lazy_sha1` in `src/itsdangerous/signer.py:40-54,120`.
- The new default should be a lazy `hashlib.sha256` wrapper, so FIPS builds are still safe at import time.
- The change ships in the unreleased 2.3.0, which is already a breaking release (it drops Python 3.8/3.9 and removes deprecated code).
- Existing tokens must keep verifying, so a SHA-1 fallback is needed.

## How this could go wrong
1. **Existing signatures stop verifying.** Cookies, sessions, password-reset links and email-confirmation tokens signed with SHA-1 fail on upgrade. Users get logged out or their links break.
2. **Silent fallback gap.** `Serializer` adds a fallback only if you set it. The 1.1.0 history shows a default change breaking users, and 1.0.0 was yanked for the same reason.
3. **Signer and verifier on different versions.** During a rolling deploy, or between services that share a secret (such as Flask and a worker), tokens signed by the new version are rejected by the old one.
4. **Key derivation changes too.** The `django-concat`, `hmac` and `none` derivations all use `digest_method`, so derived keys change along with the signature.
5. **Signature length changes.** Tokens get longer, from 28 to 44 base64 characters. This can break URL, cookie-size or DB-column limits, and any code that assumes a fixed length.
6. **Tests and docs encode SHA-1.** `test_serializer.py:180,192` assert `_lazy_sha1` and a fixed SHA-1 signature. `docs/concepts.rst:142` and the docstrings say SHA-1 is the default.
7. **Subclass and monkeypatch overrides.** Code that sets `default_digest_method` or reads `signer.digest_method == sha1` behaves differently.
8. **Fallback performance.** Each old token needs two HMAC checks. That is small, but it adds up under heavy load.
9. **Fallback hides downgrade attacks.** If SHA-1 stays in the fallback forever, the security gain is only partial.
10. **FIPS or unusual builds.** SHA-256 is generally available, but the lazy-access guarantee must be kept.

## Plan, in short
1. Add `_lazy_sha256` and point `default_digest_method` at it in both classes (`signer.py`).
2. Make `Serializer`'s default fallback signer SHA-1, so old tokens still verify.
3. Update the tests: keep SHA-1 tokens verifying, add SHA-256 round trips, and fix the fixed-signature assertion.
4. Update `docs/concepts.rst` and `docs/serializer.rst`, and add a loud entry to `CHANGES.rst` under 2.3.0 with the migration steps.
5. Run `pytest`, then `mypy` and the pre-commit checks.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Old SHA-1 tokens rejected | Default changes with no fallback set | Default SHA-1 fallback signer, plus a test |
| 2 | Mixed-version deploys | Old verifiers reject new tokens | Release notes: upgrade verifiers first |
| 3 | Derived keys change | All key derivations use `digest_method` | Test fallback across derivations |
| 4 | Longer signatures | Cookie, URL or column limits | Document the length; check size limits |
| 5 | Tests and docs assert SHA-1 | `test_serializer.py:180,192`, `concepts.rst` | Update them and add SHA-256 vectors |
| 6 | Subclass overrides break | Users set `default_digest_method` | Keep the attribute name and the lazy callable |
| 7 | Permanent SHA-1 fallback | Downgrade path stays open | Document how to drop the fallback later |
| 8 | FIPS import-time failure | Eager `hashlib` access | Keep the lazy wrapper |
| 9 | History repeats | 1.0.0 was yanked for this kind of change | Prerelease first, with a clear changelog |

Riskiest: #1, because tokens in the wild stop verifying the moment the default changes unless the SHA-1 fallback is on by default.
