## Plan: article title change with link-preserving slug

### What the code already does
- `ArticleUpdate` (`articles/routers.go:152-160`) already regenerates the slug when the title changes, using `makeSlug` and `makeUniqueSlug`.
- The old slug is simply overwritten. Every later request to `/api/articles/<old-slug>` and its sub-routes (comments, favorite) returns 404. That is the broken-link problem to fix.
- A smaller bug sits in the same block. The check is `base != articleModel.Slug`. If the stored slug carries a collision suffix (`foo-2`) and the author re-saves the same title, `base` is `foo`, so the code thinks the title changed and rewrites the slug. The comparison has to be against the slug of the *old title*, not the stored slug.

### Assumptions
- This is a JSON API with no HTML pages. Old slugs resolve transparently and return 200 with the canonical `slug` in the body. I'm not using HTTP 301, because RealWorld clients don't follow redirects on XHR calls. Clients that care read `article.slug`.
- Old slugs resolve on every `/:slug` route, reads and writes alike. Writes act on the current article.
- An old slug stays reserved for as long as its article exists.
- Auth rules are unchanged. Only the author can rename.

### Design
1. **Alias table.** Add `SlugAliasModel{ID, Slug uniqueIndex, ArticleID index, CreatedAt}` in `articles/models.go`. Add it to `db.AutoMigrate` in `hello.go` and in both test setups in `articles/unit_test.go` (lines ~339 and ~1597).
2. **Resolver.** Add `resolveArticle(slug)` in `articles/models.go`. It calls `FindOneArticle` by current slug first. If that misses, it looks up the alias, then loads the article by `ArticleID`. Replace the `FindOneArticle(&ArticleModel{Slug: slug})` calls in all `/:slug` handlers (`routers.go:101,115,196,216,232,248,270,301`) with it. The fast path costs no extra query.
3. **Rename in one transaction.** In `ArticleUpdate`, when the slug changes, do the article update and the insert of `{old slug → article}` in a single `db.Transaction`. Before the update, delete any alias row equal to the new slug. That makes renaming back to an earlier title work, and the alias never shadows a live slug. Keep the existing `ErrDuplicatedKey` retry loop.
4. **Reserve aliases in `makeUniqueSlug`.** Also count `slug_alias_models` as occupied. Without this, a new article titled like the old one would take the shared URL and silently hijack it.
5. **Fix the comparison.** Compare `makeSlug(newTitle)` with `makeSlug(articleModel.Title)`. Don't compare it with the stored slug.
6. **Lifecycle.** When an article is deleted, hard-delete its aliases in the same transaction as `DeleteArticleModel`. The resolver must also skip aliases whose article is soft-deleted.
7. **Chained renames (A→B→C).** Keep both A and B pointing at the same `ArticleID`. Resolution is by ID, so there are no chains to walk.

### Tests (`articles/unit_test.go`)
- After a rename, GET by the old slug returns 200 and the new slug in the body.
- Old slug works for comments and favorite.
- A→B→C resolves A, B and C.
- Renaming back to A removes the A alias and keeps A as the live slug.
- A new article with the old title gets `-2` and doesn't take over the alias.
- Same-title PUT on a suffixed slug leaves the slug unchanged.
- Deleting an article makes the old slug return 404.
- The rename and alias insert roll back together on failure.
- Non-author PUT is still 403 and creates no alias.
- Run `go test ./...`, `go fmt ./...` and `scripts/run-spec-tests.sh`. Add a hurl case for the old-slug GET only if it doesn't conflict with the spec suite.

### Open follow-ups (not in scope)
- Existing rows need no backfill. Old slugs that were already overwritten can't be recovered.
- Optionally add `Location` or canonical-link headers on alias hits.

### Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Alias hijack | `makeUniqueSlug` only checks the `articles` table, so a new article could claim an old shared slug | Make `makeUniqueSlug` also check aliases, and test it |
| 2 | Rename and alias not atomic | `articleModel.Update` runs alone today, so a failed alias insert leaves a dead link | Run both in one transaction |
| 3 | Race on the unique index | Two concurrent renames or creates can pick the same slug | Keep the `ErrDuplicatedKey` retry; add the alias unique index |
| 4 | Missed `/:slug` handler | Eight handlers look up by slug, and one left on `FindOneArticle` still 404s | Route all of them through `resolveArticle`; grep for stragglers |
| 5 | Wrong rename trigger | The `base != Slug` check misfires on suffixed slugs and breaks links on a no-op save | Compare against the old title's slug; add a test |
| 6 | Alias shadows a live slug | Renaming back to an old title leaves an alias equal to the live slug | Delete the matching alias in the rename transaction |
| 7 | Deleted articles still resolve | Soft delete keeps rows and slug occupancy | Hard-delete aliases on delete; resolver ignores soft-deleted articles |
| 8 | Alias table growth | Every rename adds a row, with no cap | Accept it; optionally cap per article later |
| 9 | Spec-suite or client mismatch | Spec tests (hurl/bruno) may expect 404 on unknown slugs | Only aliased slugs resolve; run `scripts/run-spec-tests.sh` |
| 10 | AutoMigrate wiring missed | Production and two test setups each list models by hand | Update all three; the tests fail fast if one is missed |

Riskiest: #1, the alias hijack, because a reused old slug would silently point already-shared links at a different author's article.
