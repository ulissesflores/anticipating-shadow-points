## Finding: the stronger scheme is already in place

Commit `a51468c` ("modernize") already did most of this:

- **New hashing:** `src/Conduit/Infrastructure/Security/PasswordHasher.cs:13` uses ASP.NET Core Identity's `PasswordHasher<T>`. That is PBKDF2 with HMAC-SHA512, 210,000 iterations and a random salt stored inside the hash.
- **Old hashes still work:** a 64-byte hash with a 16-byte salt is treated as the old format, `HMACSHA512(key="realworld", password‖salt)`. It is checked in constant time and returns `SuccessRehashNeeded`.
- **Upgrade on login:** `Features<home>` rehashes the password after a successful old-format login and clears `Salt`. `Create.cs` and `Edit.cs` only ever write the new format.
- **Tests:** `PasswordHashingTests.cs` already checks that new hashes are randomized, that a wrong password leaves an old hash alone, and that a right one upgrades it.

So users already keep their passwords. **What's still missing:** a user who never logs in again keeps the old hash forever. That old hash is one SHA-512 over a key that is public ("realworld"), so it's very fast to crack if the database leaks. Raising the iteration count later is already handled by Identity on the next login.

## Assumptions
- The goal is that no fast hash remains in the database, including for dormant accounts.
- No schema change is wanted. `Hash` and `Salt` (both `byte[]`) stay as they are.
- Production databases may hold many old-format rows, so the upgrade must run in batches and be safe to re-run.

## Plan: wrap dormant old hashes in PBKDF2 (no password needed)
1. **New "wrapped" format in `PasswordHasher`:** store `Hash = PBKDF2(base64(oldHMAC))` and keep the old 16-byte `Salt`. To tell formats apart:
   - Salt is 16 bytes and hash is 64 bytes → old format (unchanged).
   - Salt is 16 bytes and hash is not 64 bytes → wrapped. Recompute the HMAC from the password and salt, check it against the PBKDF2 hash, and return `SuccessRehashNeeded`.
   - Salt is empty → new format (unchanged).
   
   A new-format hash is 61 bytes, so it can't be mistaken for an old one. Add a method `WrapLegacy(byte[] hash)`.
2. **One-off upgrade job:** an idempotent, batched step that loads rows where the hash is 64 bytes and the salt is 16 bytes, wraps them and saves. It should take a cancellation token, and run as a hosted service or a CLI switch rather than an EF migration, because SQL can't run PBKDF2. Byte-length filters differ between SQLite and SQL Server, so filter in C# over a selection keyed by `PersonId`.
3. **Login:** no change. The existing `SuccessRehashNeeded` path moves wrapped users to the native format and clears `Salt`.
4. **Tests** in `PasswordHashingTests`:
   - wrapped hash plus right password → upgraded
   - wrapped hash plus wrong password → unchanged
   - the job is idempotent and skips native hashes
   - a native hash is never treated as old or wrapped
   - an iteration-count bump comes back as `SuccessRehashNeeded`
5. **Docs:** note the operational step in `docs/database-migrations.md`.
6. **Validate:** `dotnet run --project build/build.csproj -- test`, then the Hurl suite for login and register.

## Ways this could go wrong
- The format check misreads a row: an old hash read as native fails to verify, which locks the user out.
- The upgrade job crashes halfway, leaving a mix of old, wrapped and new rows.
- PBKDF2 at 210k iterations adds about 100 ms of CPU per login, which makes login a cheaper target for overload attacks.
- Two simultaneous logins both rehash. This is harmless because either hash is valid, but don't add a version check that turns it into a 500 error.
- If the job runs at startup on a large table, deployment slows or times out.
- Unknown emails return before any hashing, so response times show which emails exist. This was already true and is now a bigger gap.
- A rollback to a build without the "wrapped" branch locks out every wrapped user.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Format misdetected | Length-based check (64/16 bytes) | Tests for each format; native hash is 61 bytes |
| 2 | Dormant users stay on fast hash | Upgrade only happens at login | Wrap old hashes in a batch job |
| 3 | Rollback locks out wrapped users | Old build can't read the wrapped format | Ship verify code first, run the job in a later release |
| 4 | Partial job run | Many rows, process can crash | Idempotent, batched, re-runnable |
| 5 | Login CPU load | 210k iterations, called synchronously in `Login.cs` | Rate-limit login; tune iteration count |
| 6 | Email check by timing | Unknown email skips hashing | Verify against a dummy hash |
| 7 | Rehash race on login | Concurrent `SaveChangesAsync` | Accept last write; no concurrency check |
| 8 | Provider differences | SQLite and SQL Server compare byte lengths differently | Filter in C#, test both providers |
| 9 | Slow startup | Job run inside app boot | Run as a separate command or background service |

Riskiest: #3. A rollback after wrapping locks out every dormant old-format user until the build is redeployed.
