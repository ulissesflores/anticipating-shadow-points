**What the code does today:** `ArticleUpdate` already regenerates the slug when the title changes (`routers.go:152-161`). Nothing remembers the old slug, so the old URL returns 404. The missing piece is keeping old links working, not changing titles.

## Assumptions
- Shared links are `GET /api/articles/:slug` and the frontend URLs built from it. Old slugs should keep resolving permanently.
- The API serves JSON, so I'll answer an old slug with the article itself plus the canonical slug in the body, not a 301. A 301 is awkward for XHR clients and the RealWorld spec doesn't define one. A redirect or a `Location` header can be added later.
- Only `GET` follows old slugs. Writes (PUT, DELETE, favorite, comments) keep requiring the current slug, or they also resolve aliases. I'll go with resolving aliases everywhere, because a client holding a stale slug shouldn't get a 404 on favorite.
- Authors can change titles often, so aliases must not grow without bound.
- SQLite in dev, and GORM `AutoMigrate` creates the new table.

## Ways this could go wrong
1. **Slug collisions:** an old slug may match an existing or future article's current slug. `makeUniqueSlug` only checks `articles.slug` today, so it must also check the alias table.
2. **Alias hijacking:** author A renames away from `foo`, then author B creates "Foo" and takes `foo`. Old links to A's article now show B's content, and which one wins is ambiguous.
3. **Alias precedence:** if lookup checks aliases before current slugs, a stale alias can shadow a live article.
4. **Rename chains and loops:** A→B→A. A rename back to a former slug must reclaim it and delete the alias row, or the unique index breaks.
5. **Existing slug bug:** `base != articleModel.Slug` compares against a suffixed slug such as `foo-2`. An unchanged title then triggers a rename and a needless alias.
6. **Non-atomic update:** the slug update, tag replacement and alias insert are separate writes. A failure between them leaves a renamed article with no alias, or an alias pointing at nothing.
7. **Concurrent renames:** the check-then-insert in `makeUniqueSlug` races. The existing retry on `ErrDuplicatedKey` has to cover the alias table too.
8. **Delete cascade:** `DeleteArticleModel` soft-deletes. Aliases must follow, and soft-deleted slugs still hold the unique index.
9. **Authorization and leakage:** following an alias must not expose anything a direct request wouldn't, and the update must still check the author.
10. **Clients caching the old slug:** the `slug` in the response differs from the requested one. Clients that key state on the request slug (favorites, comments) can desync.
11. **Unbounded growth and cleanup:** there is no cap on alias rows per article.
12. **Test and spec drift:** the hurl and bruno RealWorld suites and `articles/unit_test.go` may assume the old slug 404s after a rename.

## Plan
1. Add `ArticleSlugAlias{ID, ArticleID, Slug uniqueIndex}` in `articles/models.go`, with a migration entry next to the existing models.
2. Add a `FindArticleBySlug` helper. It tries the current slug first, then the alias, and returns the article. Use it in all `:slug` handlers.
3. Make `makeUniqueSlug` check both `articles.slug` and `aliases.slug`, including soft-deleted rows.
4. In `ArticleUpdate`, wrap the slug update, tag replacement and alias insert in one transaction. Fix the comparison so it only renames when the title's base slug actually changed. Delete any alias that equals the new slug.
5. Cap aliases per article, or accept the growth explicitly.
6. Tests: rename then GET by the old slug; chained renames; rename back; slug collision with another author's article; delete cascade; write by old slug; concurrent rename.
7. Run `go test ./...`, then the hurl and bruno suites.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Alias/slug collision | `makeUniqueSlug` only checks `articles.slug` | Check both tables, including soft-deleted rows |
| 2 | Alias hijacking by new article | A new article can claim a freed slug and capture old links | Reserve aliases permanently; current slug never takes an alias |
| 3 | Non-atomic update | Slug, tags and alias are separate writes in `ArticleUpdate` | Wrap in one transaction |
| 4 | Needless renames | `base != articleModel.Slug` mismatches suffixed slugs like `foo-2` | Compare against the slug base, not the suffixed value |
| 5 | Rename back or chain loops | A→B→A breaks the alias unique index | Delete the alias when a slug is reclaimed |
| 6 | Concurrent rename race | Check-then-write in `makeUniqueSlug` races | Rely on the unique index and extend the retry to aliases |
| 7 | Delete leaves stale aliases | Soft-delete keeps slugs in the unique index | Cascade-delete aliases or tie them to the article's `deleted_at` |
| 8 | Client slug desync | The response slug differs from the requested one | Document it; return the canonical slug in the body |
| 9 | Alias lookup precedence | An alias checked first can shadow a live article | Resolve the current slug first, then the alias |
| 10 | Spec and test drift | Existing suites may expect a 404 after a rename | Update the tests and run hurl and bruno |

Riskiest: #2, alias hijacking, where a freed slug is reused by a different article and silently breaks the "old links keep working" promise.
