Most of this is already in the code. The plan below covers the part that isn't: users who never log in still have weak hashes. The full plan is saved at `claude-home/plans/store-passwords-with-a-nifty-hartmanis.md`. I edited no repo files.

## What's already in place (commit a51468c)
- **Stronger hashing for new passwords:** `src/Conduit/Infrastructure/Security/PasswordHasher.cs` uses ASP.NET Identity's v3 format (PBKDF2 with SHA-512, 210,000 iterations, a random salt stored inside the hash). `Person.Salt` is saved as empty.
- **Old hashes still work:** old-format hashes are HMAC-SHA512 with the public key `"realworld"`, 64 bytes plus a 16-byte salt. They still verify, and the hasher marks them as needing a rehash.
- **Upgrade on login:** `src/Conduit/Features<home>:79-84` rewrites the hash in the new format after a successful login.
- **Tests:** `tests/Conduit.IntegrationTests/Features<home>` covers both paths.

**The gap:** someone who never logs in keeps the fast, cheap-to-crack old hash forever. Also, the old format is recognised only by its byte length.

## Plan: wrap the dormant old hashes
1. **Hasher:** add a "wrapped" format. It is a v3 hash of the old HMAC output, and it keeps the original 16-byte salt.
   - Formats are told apart by salt length: an empty salt is the new format; a 16-byte salt with a 64-byte hash is an old raw hash; a 16-byte salt with any other length is wrapped.
   - A wrapped hash also reports that it needs a rehash, so the existing login code turns it into the new format and clears the salt. `Login.cs` needs no change.
   - Optionally, remove the unused `salt` parameter from `Hash`.
2. **One-off upgrade job:** a new `LegacyPasswordUpgrader`, a background service registered in `ServicesExtensions.cs` and switched by config.
   - It works through old raw rows in batches of 100.
   - Each row is only written if its hash hasn't changed since it was read, so it never overwrites a login that upgraded the row at the same moment.
   - It can be re-run safely, honours cancellation, and never logs hashes.
3. **No database migration:** `Hash` and `Salt` are already variable-length binary columns in both SQLite and SQL Server.
4. **Later, separate PR:** once every environment has no old raw rows left, remove the code that checks raw old hashes.

**Tests to add:**
- A wrapped hash accepts the right password and rejects a wrong one.
- Logging in as a wrapped user upgrades the hash, and a wrong password leaves the row unchanged.
- The upgrade job wraps only old raw rows, does nothing on a second run, and gives way to a concurrent login.

**Verification:**
- Run `dotnet run --project build/build.csproj -- test`.
- Then `make run-local`: seed an old-format user in SQLite, restart, check the row was wrapped, and log in to confirm it moves to the new format.

**Assumptions:**
- Identity's PBKDF2 counts as "stronger". It's built in and needs no new package; Argon2id would add a third-party dependency for little gain.
- The length rule is safe because new-format hashes are 61 bytes, not 64.
- Running the job inside the app at startup is acceptable, rather than as a separate command-line tool.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Wrapped hash checked the wrong way | A 16-byte salt then means "wrapped" unless the hash is 64 bytes, and one wrong branch fails every old user's login | Classify by salt plus length; test every format both ways |
| 2 | Job overwrites a concurrent login upgrade | Login and the job both write `Hash` | Write only if the hash hasn't changed |
| 3 | Startup CPU spike | Each wrap costs 210,000 PBKDF2 iterations, roughly 100 ms per user | Small batches, low parallelism, config switch |
| 4 | Old-format check removed too early | Any raw rows still left could no longer log in | Remove only after the count is zero everywhere |
| 5 | Old hashes were already leaked | Wrapping doesn't help with copies taken before the change | Wrap soon; consider a breach notice if backups leaked |
| 6 | Mixed versions during a rolling deploy | Old app instances can't read wrapped hashes | Deploy all instances first, then enable the job |
| 7 | Dropping the `salt` parameter touches many call sites | Create, Edit, Login and the tests all call `Hash` | Leave it out or do it in a separate PR |
| 8 | Hashes appear in logs or errors | New logging code in the job | Log counts and IDs only |

Riskiest: #1, because one wrong branch in format detection locks out every user still on an old hash.
