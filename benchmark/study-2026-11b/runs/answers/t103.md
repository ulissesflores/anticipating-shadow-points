# Plan: self-service data export (profile, posts, comments) as one file

## Assumptions
- This is Flasky (Flask, SQLAlchemy and Flask-Login), with `User`, `Post` and `Comment` models in `app/models.py`.
- "Their data" means what the user authored: their profile fields, their posts, and the comments they wrote. It excludes other people's comments on their posts. It excludes follow lists too, though adding them later is cheap.
- "Single file" means one JSON download, because it is lossless and fits the existing `to_json` style. A CSV or ZIP is out of scope.
- Only the logged-in user can export their own data. No admin export for other users.
- Export runs synchronously. A personal blog-scale dataset is small, so no background job or email link.
- Credentials and secrets are never exported: `password_hash`, tokens and the role's internal ID.

## Design
1. **Model layer** (`app/models.py`)
   - Add `User.to_export()` returning a dict with these parts:
     - `profile`: email, username, name, location, about_me, member_since, last_seen, confirmed.
     - `posts`: id, body (the raw markdown), timestamp.
     - `comments`: id, post_id, body, timestamp, disabled.
   - Don't reuse the API `to_json` methods. They call `url_for('api...')`, they omit email and `about_me`, and they add counts that an export doesn't need.
   - Export raw `body`, not `body_html`. The HTML is derived and sanitised on set, so it can be regenerated.
2. **Route** (`app/main/views.py`)
   - Add `@main.route('/export')` with `@login_required`.
   - It builds `current_user.to_export()` and returns it as a JSON response.
   - It sets `Content-Disposition: attachment; filename=<username>-data.json`, plus `Cache-Control: no-store`.
   - Make it POST-only with CSRF, or GET behind a recent re-authentication check (see the risks). I recommend POST using the existing Flask-WTF form pattern.
   - Query `posts` and `comments` with `order_by(timestamp)`. They are `lazy='dynamic'`, so this is cheap.
   - Serialise datetimes as ISO 8601, because the stock `jsonify` encoder emits HTTP-date strings.
3. **UI**
   - Add a "Download my data" button on the edit-profile page (`app/templates/edit_profile.html`) or in the user dropdown in `base.html`.
4. **Hardening**
   - Rate-limit the endpoint, for example one request per minute per user. Check whether Flask-Limiter is in the requirements. If it isn't, add a simple `last_seen`-style timestamp check.
   - Write an audit log line for each export.

## Tests (`tests/`)
- Add a client test in `tests/test_client.py`:
  - An anonymous request is redirected to login.
  - A logged-in user gets valid JSON with the attachment header.
  - The export contains only that user's posts and comments.
  - The output contains no `password_hash`.
- Add a model unit test for `to_export()` in `tests/test_user_model.py`.

## Verification
- Run `python -m unittest discover tests` or `flask test`, depending on how `flasky.py` registers the test command.
- Manually seed fake data with `app/fake.py`, log in as two different users, and download both files. Confirm that neither file contains the other user's data.
- Open the file in a JSON viewer and check that the unicode and markdown bodies survive intact.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Data leak to another user | The export includes email and private fields, and any ID-based or session mix-up exposes them | Use `current_user` only, take no ID parameter, and add a cross-user test |
| 2 | CSRF or drive-by download | A GET endpoint can be triggered from another site, and the response is sensitive | Use POST with a CSRF token, or require recent re-authentication |
| 3 | Secrets in the export | The `User` model holds `password_hash`, and tokens are derived from `SECRET_KEY` | Use an explicit allowlist of fields, never `__dict__`, and add a test |
| 4 | Memory and slow responses | A heavy user's posts and comments are loaded in one request on a Gunicorn worker (Heroku and Docker) | Stream or iterate the query, set a size cap, and rate-limit |
| 5 | Wrong or incomplete scope | "All their data" is ambiguous, and followers, follows and comments received may be expected | Document the assumption, put the scope in the UI text, and keep `to_export` easy to extend |
| 6 | Datetime and encoding bugs | The default `jsonify` emits HTTP-date strings, and non-ASCII markdown can be mangled | Use ISO 8601 and UTF-8, and test unicode bodies |
| 7 | Abuse for scraping or load | Repeated exports from a hijacked session drain data and CPU | Per-user rate limit and an audit log |
| 8 | Stale or inconsistent snapshot | Posts and comments are read in separate queries, and a write between them skews the file | Read in one request and accept eventual consistency, or wrap in one transaction |
| 9 | Privacy and compliance gaps | The export may not meet GDPR-style portability expectations on format or completeness | Use a machine-readable JSON format, state the covered scope, and have the privacy owner review it |
| 10 | Caching of sensitive file | Proxies or the browser may cache the download | Send `Cache-Control: no-store` and use `attachment` disposition |

Riskiest: #1, a data leak to another user, because the export bundles the most sensitive personal data and any access-control slip exposes it.
