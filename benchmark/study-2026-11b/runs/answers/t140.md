**Assumptions**
- This is django-axes 9.0.0, where `axes/conf.py:42-51` derives `AXES_LOCKOUT_PARAMETERS` from legacy flags and falls back to `["ip_address"]`.
- "Username and IP together" means the combination `[["username", "ip_address"]]`. It does not mean the OR form `["username", "ip_address"]`.
- Only the fallback default changes. Explicit settings and the legacy flags keep their current meaning.
- I made no edits and didn't run any tests.

**Ways this could go wrong, before planning**
1. **Wording is ambiguous.** "Together" could mean AND (a combined key) or OR (either one triggers a lockout). The two behave very differently, and I'm assuming AND.
2. **Weaker brute-force protection.** An attacker who rotates IPs, for example through a botnet or proxy pool, gets a fresh counter for every IP. Per-username throttling is gone.
3. **Credential stuffing and password spraying get easier.** Many usernames from one IP each stay under the threshold, because the combined key never accumulates failures for any single pair.
4. **Silent upgrade change.** Existing deployments that rely on the default switch behavior on upgrade. Existing `AccessAttempt` rows were keyed by IP and won't match the new combined key, so current lockouts are effectively reset.
5. **Legacy flag interplay.** The flag-to-parameters mapping in `conf.py` has to keep working, or `AXES_ONLY_USER_FAILURES` users get an unintended default. The `user_agent` handling at `conf.py:54-60` assumes `[0]` is a string, and it would now hit a nested list.
6. **Username normalization.** Case and whitespace variants (`Bob` vs `bob`) create separate counters, which lets an attacker dodge the limit. `AXES_USERNAME_CALLABLE` and the oversized-username fix from #1523 also affect the key.
7. **Missing username.** Requests that don't carry the username field (non-standard forms, APIs, or the username under a different key) produce `None` or empty keys. Those could all share one bucket, or none.
8. **Proxy and IP accuracy.** Behind a misconfigured proxy, every user shares the proxy IP. Lockouts would then hit all of one user's attempts through that proxy and stay per-username only in a narrow sense.
9. **Tests, docs and changelog drift.** Many tests assume the IP-only default. `docs/2_installation.rst` and `docs/3_usage.rst` document it, and the changelog needs a clear breaking-change note.
10. **Data and performance.** The new key uses more distinct keys for cache and database handlers. The `AccessAttempt` unique constraints, the `reset`/`axes_reset_ip` commands and the admin filters are all IP-oriented.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | AND vs OR misread | Combined key vs `["username","ip_address"]` differ greatly | Confirm intent; document the choice |
| 2 | IP rotation evades lockout | Per-user counter is lost once the IP changes | Docs warning; suggest `[["username","ip_address"],"username"]` |
| 3 | Credential stuffing from one IP | Each user/IP pair stays under the limit | Keep a per-IP rule or a rate limit alongside |
| 4 | Silent behavior change on upgrade | Default is derived in `conf.py`; old attempt rows no longer match | Major-version note; migration guide; opt-out setting |
| 5 | Legacy flags and `user_agent` break | `conf.py:54-60` assumes `[0]` is a string | Handle nested lists; test each flag combination |
| 6 | Username normalization gaps | Case variants make separate counters | Normalize via `AXES_USERNAME_CALLABLE`; test it |
| 7 | Missing username in request | Empty keys collapse into one bucket or none | Define fallback behavior; test API/JSON logins |
| 8 | Proxy/IP misconfiguration | A shared proxy IP distorts the key | Document `AXES_IPWARE_*`; add tests |
| 9 | Tests and docs assume IP-only | Many assertions and doc sections hardcode it | Update tests, docs and changelog together |
| 10 | Stale data and tooling | Reset commands, admin and constraints are IP-oriented | Verify reset/admin paths; add a data note |

Riskiest: #4, the silent default change on upgrade, because it alters security behavior for every existing deployment without any action from them.
