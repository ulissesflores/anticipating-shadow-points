I've written the plan to `claude-home/plans/change-the-default-signing-mellow-yao.md`. No repo files were edited. The repo is **itsdangerous 2.3.0.dev**.

**Assumptions:**
- "Signing digest" means `default_digest_method` on both `Signer` and `HMACAlgorithm` (`src/itsdangerous/signer.py:54`, `:120`). The same setting also controls key derivation (`derive_key`, `:200-209`).
- Tokens signed with SHA-1 must keep verifying for at least one release.
- 2.3.0 is unreleased and already breaking, so it's the right release for this change.

**Ways this could go wrong (found before planning):**
- **It has gone wrong before.** Release 1.0.0 changed the default to SHA-512 and was pulled from PyPI because existing tokens stopped working; 1.1.0 switched back to SHA-1 (`CHANGES.rst:105-125`).
- **Every existing token stops verifying.** Key derivation uses the same digest, so it isn't just the HMAC that changes. Sessions, password-reset links and email-confirmation links all break.
- **Only `Serializer` has a fallback mechanism.** `Serializer.default_fallback_signers` is currently empty. Plain `Signer` and `TimestampSigner.unsign` can't fall back to SHA-1 at all.
- **The fallback must not break FIPS builds.** A SHA-1 fallback that references `hashlib.sha1` when the module loads would undo the 2.2.0 fix for FIPS builds, which may not include SHA-1. It needs to keep using the lazy `_lazy_sha1`.
- **Tokens get longer.** The signature grows from 27 to 43 base64 characters, which matters for cookies (4 KB limit) and URLs.
- **Rolling deploys break.** If old and new instances run side by side, servers still on the old version reject tokens the new ones sign.
- **Other code verifies these tokens.** Ports in other languages and hard-coded test values assume HMAC-SHA1.
- **Some users won't notice.** Anyone who sets the digest explicitly (Flask pins SHA-1) is unaffected, so the change only hits people relying on the default.
- **Tests depend on the current default:** `test_iter_unsigners` expects `_lazy_sha1` first, and `test_digests` checks that the default equals SHA-1.

**Plan:**
1. Point both defaults at a SHA-256 function.
2. Set `Serializer.default_fallback_signers = [{"digest_method": _lazy_sha1}]`.
3. Document how users of plain `Signer` can migrate.
4. Update the tests and add one showing an old-default token still loads.
5. Update `docs/concepts.rst`, `docs/serializer.rst` and `CHANGES.rst` with clear migration notes.
6. Verify with pytest, the type checkers, a strict Sphinx build, a check that 2.2.0 tokens still load on the new branch, and a FIPS-like import test.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | All existing tokens stop verifying | The digest also drives key derivation, so both key and signature change | SHA-1 entry in `default_fallback_signers` |
| 2 | Plain `Signer`/`TimestampSigner` can't fall back | Fallback exists only in `Serializer.iter_unsigners` | Document pinning `digest_method=sha1`; maybe add an option later |
| 3 | Repeat of the pulled 1.0.0 release | Same kind of change, previously reverted | Ship only with the fallback and loud changelog notes |
| 4 | FIPS builds break | A fallback that touches `hashlib.sha1` at import fails there | Keep the fallback lazy (`_lazy_sha1`); test the import |
| 5 | Mixed-version deploys reject tokens | Old servers can't check SHA-256 tokens | Upgrade all servers first, or pin SHA-1 during rollout |
| 6 | Tokens get bigger | Signature grows from 27 to 43 characters | Note it in the changelog; check cookie size limits |
| 7 | Other verifiers break | Ports and hard-coded test values assume HMAC-SHA1 | Changelog note and a pinning recipe |
| 8 | SHA-1 is accepted forever | A permanent fallback keeps the old path open | Plan to deprecate and remove the fallback later |
| 9 | Tests fail | Tests assume the default is `_lazy_sha1` / SHA-1 | Update them; keep SHA-1 golden values |
| 10 | Docs contradict the code | `concepts.rst` says the default is SHA-1 | Update the docs and add `versionchanged` |

Riskiest: #1 — every existing token stops verifying, because key derivation also uses the digest; without a lazy SHA-1 fallback this repeats the pulled 1.0.0 release.
