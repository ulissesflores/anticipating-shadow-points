I wrote a plan for exposing UUIDs as the public ID without breaking current clients; no code was changed. It's saved at `claude-home/plans/replace-the-integer-ids-ethereal-unicorn.md`.

**What the code does today:** `TextSummary.id` is a Postgres auto-increment integer (`SERIAL`) and appears everywhere. Paths are `/summaries/{id}/` with `id: int = Path(gt=0)` (`app/api/summaries.py:19`). Responses carry `id: int` (`app/models/pydantic.py:8`). The background summarizer looks rows up by the integer. Tests check exact 422 error bodies and `id` values. Migrations run by hand with aerich; nothing in deploy or CI runs them, and tests build the schema from the models, so a migration is never tested.

**Assumptions:**
- "Keep clients working" means `id` stays an integer on `/summaries/*`. Only new fields can be added there.
- The integer primary key can stay as an internal key. No foreign keys depend on it.
- The database is Postgres 17, which has `gen_random_uuid()` built in.

## Ways this could go wrong (before planning)
1. **Changing the type of `id` in place.** Clients that store or parse `id` as a number break, even if the URLs keep working.
2. **Swapping the primary key to a UUID.** That needs a destructive table rewrite, and a down-migration can't recover the old integers.
3. **Backfill mistakes.** Existing rows end up with NULL or duplicate UUIDs.
4. **Locking during migration.** Adding the unique index without `CONCURRENTLY` blocks writes.
5. **Migration skipped in production.** Nothing runs aerich automatically, so new code could hit a database without the column.
6. **Accepting both an int and a UUID in one path parameter.** The validator's choice is ambiguous and the existing 422 bodies change, so the tests break.
7. **Background task gets the wrong key.** The summarizer could receive a UUID where it expects an integer, and the summary is never saved.
8. **Integers still leak.** `pydantic_model_creator` keeps emitting the int `id` on the new API, which defeats the point.
9. **No working rollback.** The existing migration's `downgrade` is empty.

## Recommended approach
1. **Model:** add a `uuid` column (`UUIDField(unique=True, default=uuid4)`) and keep the integer `id` internally.
2. **Migration, written by hand in steps:** add the column as nullable, backfill with `gen_random_uuid()`, set the default and NOT NULL, then build the unique index with `CONCURRENTLY`. Write a real `downgrade`.
3. **Existing `/summaries` routes:** same paths and validation as today. Responses gain an extra `uuid` field and a deprecation header pointing to v2.
4. **New `/v2/summaries` routes:** take a UUID in the path and return `id` as a UUID taken from the `uuid` column. The integer is never emitted.
5. **CRUD:** add a lookup helper that works by either key. The summarizer keeps using the internal integer.
6. **Tests:** leave the current suites untouched as the compatibility check. Add a v2 suite covering a malformed UUID (422), an unknown UUID (404) and an integer sent to v2 (422), plus one test that creates a summary via v1 and reads it via v2.
7. **Verification:** run the migration on a copy of a database with existing rows, and confirm both versions in `/openapi.json`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Clients break on `id` type change | `id: int` is in every response schema and test | Keep int `id` on `/summaries`; UUIDs only under `/v2` |
| 2 | Backfill leaves NULL/duplicate UUIDs | Existing rows have no UUID; the ORM default only covers new rows | Hand-written migration: backfill, then NOT NULL and a unique index |
| 3 | Migration not applied before deploy | Nothing in `entrypoint.sh` or `release.sh` runs aerich | Explicit release step; test on a database copy |
| 4 | Migration never tested | Tests use `generate_schemas=True`, not migrations | Run `aerich upgrade` and `downgrade` against a seeded database |
| 5 | Ambiguous int-or-UUID path parameter | Union parsing changes the 422 bodies the tests assert exactly | One type per version: int on v1, UUID on v2 |
| 6 | Integer still leaks on v2 | `pydantic_model_creator` includes `id` automatically | Separate v2 schema with `id` taken from `uuid` |
| 7 | Background task gets a UUID | `generate_summary` filters by the integer `id` | Always pass the internal integer key to it |
| 8 | Index build locks writes | A plain `CREATE UNIQUE INDEX` blocks inserts | `CONCURRENTLY`, in a separate non-transactional step |
| 9 | No rollback path | The existing `downgrade` is empty | Write a `downgrade` that drops the column |

Riskiest: #1. Changing the type of the public `id` in place breaks every existing client at once, and only a separate v2 route avoids it.
