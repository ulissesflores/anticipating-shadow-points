This is `express-session` 1.19.0. The change itself is one line, but it changes default behaviour for every user of the package. I didn't edit any files, including the plan file plan mode normally asks for, because you said not to.

## What the code does today

- `index.js:109`: `var rollingSessions = Boolean(opts.rolling)`. If the option isn't set, the value is `false`.
- `index.js:483-492` (`shouldSetCookie`): when the browser already sent the cookie, the cookie is only re-sent if `rolling` is on, or if the cookie has an expiry and the session was modified.
- `index.js:251-259`: re-sending the cookie calls `req.session.touch()`, which resets the expiry to now + `maxAge`. That is the "rolling" behaviour.
- Server-side expiry only moves when the session is saved (`shouldSave`) or when the store has a `touch` method (`index.js:362`). The `rolling` option doesn't affect that path.
- The docs (`README.md:295-301`) say "The default value is `false`". The test at `test/session.js:1159` checks that default, and 26 tests assert there is no `Set-Cookie` header.

## Ways this could go wrong (before planning)

1. **It breaks existing apps.** Every app that doesn't set `rolling` would start sending `Set-Cookie` on every response. This needs a major version, not a patch in `unreleased`.
2. **Caching and leaks.** A `Set-Cookie` header on every response stops CDNs from caching those responses. Worse, a misconfigured shared cache could store one user's session cookie and serve it to someone else.
3. **Sessions that never end.** Background polling, health checks and auto-refresh would keep idle sessions alive forever. There's no absolute timeout to stop this.
4. **Browser and server can disagree.** If `resave: false` and the store has no `touch` method, the cookie gets extended but the store record still expires. Users would be logged out even though their cookie looks valid.
5. **It does nothing without `maxAge`.** The default cookie has no expiry and lasts until the browser closes. "Extending expiry" only means something when `maxAge` or `expires` is set.
6. **Explicit `false` must still work.** The fix has to tell "not set" apart from `false`. Code like `opts.rolling || true` would quietly ignore `rolling: false`.
7. **Test fallout.** Many of the 26 no-`Set-Cookie` tests use default options and would fail. Each one needs `rolling: false` added or its expectation flipped, and that should be a deliberate choice per test.
8. **Interaction with other settings.** The `saveUninitialized: false` rule must still hold, since that check runs before `rolling`. The `secure` cookie check must also still hold.
9. **Outside docs go stale.** README, HISTORY and `@types/express-session` (which lives outside this repo) all say the default is `false`.

## Assumptions

- "Roll by default" means the `rolling` option defaults to `true` when it isn't set, and `rolling: false` still turns it off. It doesn't mean adding an absolute session lifetime.
- This ships as a semver-major change (2.0) with a HISTORY entry, not as a patch.
- The store-side behaviour (`touch` / `resave`) stays as it is. The README will explain how to keep the store expiry in sync.

## Plan

1. **`index.js:108-109`:** use `var rollingSessions = opts.rolling === undefined ? true : Boolean(opts.rolling)`. Update the JSDoc at `index.js:78`.
   - Optionally add a `deprecate(...)` warning when `rolling` is missing, like the existing `resave` warning at `index.js:121`. That would help if this ships in a minor release first.
2. **`README.md` `##### rolling`:** change the default to `true`. Add three notes:
   - Rolling only affects expiry when `cookie.maxAge` or `expires` is set.
   - For server-side expiry to roll too, the store needs `touch` (or set `resave: true`).
   - Set-Cookie on every response affects caching.
3. **`HISTORY.md`:** add a "breaking: `rolling` now defaults to `true`" entry and start a 2.0 section.
4. **Tests (`test/session.js`):**
   - Change "should default to false" (line 1159) to "should default to true" and expect `Set-Cookie` on the second request.
   - Add a test that `rolling: false` gives no `Set-Cookie` on an unmodified session.
   - Add a test that `rolling: undefined` (passed explicitly) behaves as `true`.
   - Add a test that `saveUninitialized: false` with the default `rolling` still sends no cookie for an uninitialized session.
   - Go through the 26 no-`Set-Cookie` assertions. Where a test is about other behaviour (resave, the `secure` check, the `cookie.expires` modified case), pass `rolling: false` explicitly so it keeps testing what it was meant to test.
5. **Verification:** run `npm test` and `npm run lint`. Then do a manual check with `maxAge: 60000`: two requests should return two `Set-Cookie` headers with later `Expires` values, and `store.touch` should be called when `resave: false`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Silent breaking change | Every app without `rolling` set changes behaviour on upgrade | Ship as major (2.0); HISTORY entry; optional deprecation warning first |
| 2 | Responses can't be cached / cookie leaks via shared cache | A `Set-Cookie` on every response blocks CDN caching and risks one user's cookie being served to others | Document it; recommend `Cache-Control: private` |
| 3 | Sessions never expire | Polling keeps them alive and there's no absolute timeout | Document it; consider an absolute-lifetime option later |
| 4 | Cookie extended but store record expires | Store expiry only moves via save or `touch`, not via `rolling` | Document `touch` / `resave`; test that `store.touch` is called |
| 5 | `rolling: false` ignored | A naive `opts.rolling \|\| true` overrides it | Check for `undefined`; add explicit-false test |
| 6 | Test churn hides real regressions | 26 no-`Set-Cookie` assertions, many using defaults | Pin `rolling: false` per test on purpose; don't bulk-flip |
| 7 | `saveUninitialized: false` stops holding | Rolling must not create cookies for empty sessions | Keep the `cookieId !== sessionID` check first; add a test |
| 8 | Change seems to do nothing | Without `maxAge` the cookie lasts until the browser closes | README note; manual check with `maxAge` |
| 9 | Outside docs and types go stale | `@types/express-session` says the default is `false` | Open a DefinitelyTyped follow-up |
| 10 | More Set-Cookie writes and secure-cookie edge cases | `onHeaders` now always runs `touch` and `setcookie` | Keep the `secure` check; run the existing secure/proxy tests |

Riskiest: #1, because flipping the default silently changes cookie and caching behaviour for every existing app that doesn't set `rolling`.
