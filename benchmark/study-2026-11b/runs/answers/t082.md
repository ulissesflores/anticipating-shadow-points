I've written the plan to `claude-home/plans/make-every-to-do-list-polished-sunrise.md`; no source files were changed. Today nothing separates companies' data: `GetTodosQuery` (`src/Application/TodoLists/Queries/GetTodos/GetTodos.cs`) returns every list in the database. The approach is a shared database with a tenant column on each row, plus one automatic filter that hides other tenants' rows. Logged-in users see only their own company's rows, and anyone without a company sees nothing.

**Assumptions**
- A tenant is a company, and each user belongs to exactly one.
- Admins only see their own company's data.
- The company comes from the logged-in user's sign-in information, never from what the request sends.
- Screens for managing companies are out of scope. The seeder creates a "Default" company.
- Every startup rebuilds the database from scratch (`EnsureDeleted`/`EnsureCreated`) and there are no migrations, so existing rows don't need to be filled in.

**Plan**
1. **Domain:** add a `Tenant` entity and an `ITenantOwned` interface. `TodoList` and `TodoItem` both get a `TenantId`; the item stores its own copy so filtering doesn't need a join.
2. **Who the user is:** add `TenantId` to `ApplicationUser`. A custom claims factory puts a `tenant_id` claim on the user's sign-in, which covers both cookie and bearer logins. `IUser` and `CurrentUser` expose it as `int? TenantId`.
3. **Read isolation:** `ApplicationDbContext` takes `IUser` and applies a filter to every `ITenantOwned` type: `e.TenantId == CurrentTenantId`. If the user has no tenant, it matches nothing. The existing `FindAsync` lookups and the unique-title validators then become per-company with no code changes.
4. **Write isolation:** a `TenantInterceptor` fills in `TenantId` when a row is created. It throws if a changed or deleted row belongs to another company, or if someone tries to change `TenantId` itself.
5. **Database guarantee:** a composite foreign key from item `(ListId, TenantId)` to list `(Id, TenantId)`, plus indexes on `TenantId`. With this, the database itself refuses an item whose company differs from its list's.
6. **Handlers:** `CreateTodoItem` and `UpdateTodoItemDetail` must check that the target list is visible to the user, so nobody can add or move an item into another company's list.
7. **Seeding and registration:** the seeder creates the Default company, assigns the administrator to it, and bypasses the filter (there's no logged-in user at startup). Self-registration creates a new company for the user. Until that exists, a user with no company sees nothing and can't create anything.
8. **Tests:** the mocked user in `WebApiFactory` and `TestApp.RunAsUserAsync` get a tenant. New tests cover:
   - get, update and delete across companies;
   - `GetTodos` returning only the user's own lists;
   - creating an item in another company's list;
   - the same list title in two companies;
   - a user with no company.

**Verification:** build and run the full test suite. Generate the template once per database option (SQLite, PostgreSQL, SQL Server) and build each, so all the `#if` variants still compile. Then try it by hand with two users in different companies: calling each other's IDs directly should return 404.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Write path skips the filter | The filter only affects reads; `CreateTodoItem` accepts any `ListId` | Validate the list is visible; composite FK; interceptor check |
| 2 | Seeder sees no data or writes without a company | It runs at startup with no logged-in user, so `TodoLists.Any()` is filtered | `IgnoreQueryFilters()` and an explicit `TenantId` in the seeder |
| 3 | Registered users have no company | `MapIdentityApi` registration knows nothing about companies | Fail closed; create a company on registration |
| 4 | Item moved into another company's list | `UpdateTodoItemDetail` sets `ListId` freely | Visibility check on the list plus the composite FK |
| 5 | Out-of-date company on a user's sign-in | The claim is captured at login | Single company per user; refresh the sign-in if it changes |
| 6 | Filter value fixed when the model is built | EF caches the model; a captured local value would freeze one tenant | Filter on a property of the context instance; test with two tenants |
| 7 | Template variants break | `#if UseApiOnly` / database-provider branches in DI | Build the template for each option |
| 8 | Downstream projects that use migrations | Existing rows have no `TenantId` | Document a migration that fills in a default company |
| 9 | Existing tests fail | Test users have no company, so they see nothing | Give the test user a company in `TestApp` and `WebApiFactory` |
| 10 | Admin expects to see everything | Today the "Administrator" role has no limits on to-do data | State that admins are limited to their company; opt-in bypass later |

Riskiest: #1. Creating or moving items by `ListId` could reach another company's list unless the writes are checked explicitly, because the automatic filter only covers reads.
