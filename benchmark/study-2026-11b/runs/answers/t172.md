I made no edits, since you asked for none. I only read the repo. It's a FastAPI + Tortoise ORM + Postgres app with one table, `textsummary`, whose PK is `SERIAL`. The integer id is exposed in `GET/PUT/DELETE /summaries/{id}/`, in the POST response, and in the list output. `Path(..., gt=0)` enforces the int, and `crud.py`, `generate_summary(summary_id, …)` and the tests all assume int.

## Assumptions
- "Keep clients working" means old clients that send or parse an integer `id` must not break during a transition window. It does not mean ints are supported forever.
- Existing rows must keep working under their old integer ids. Production has real data and the Aerich migration history must stay linear.
- Clients are external and I can't see them. I assume some store ids and some parse `id` as a number.
- I'll do a dual-ID transition rather than a hard swap. The int stays as the internal PK, and a new `uuid` column becomes the public identifier.

## Ways this could go wrong (before planning)
1. **Response type change.** If `id` in responses becomes a UUID string, every client that parses it as an int breaks. That conflicts directly with the compatibility requirement.
2. **Path ambiguity and validation.** `/{id}/` is typed `int` with `gt=0`. A `Union[int, UUID]` could mis-parse, and the existing 422 contract (and its tests) would change.
3. **Migration on a live table.** Adding a NOT NULL UUID column to existing rows locks the table or fails. Backfill needs a default or a batched update, and Aerich's `downgrade` is empty here.
4. **Duplicate or missing UUIDs.** A non-unique backfill, or rows inserted mid-migration with NULL, breaks lookups.
5. **Background task race.** `create_summary` hands the int id to `generate_summary`. If the task and the lookup disagree on identifier, summaries are written to the wrong row or lost.
6. **Enumeration and IDOR assumptions.** UUIDs hide guessability, but if int lookups stay open forever the benefit is zero. The app has no auth, so UUIDs aren't a security boundary anyway.
7. **Stored references.** Bookmarks, logs, caches and other services keyed on ints go stale when the int is removed.
8. **Test and tooling drift.** Tests assert `id == summary_id` as an int and a 422 for bad ids. The `pydantic_model_creator` schema auto-exposes `id`, so it changes silently with the model.
9. **Indexing and performance.** A missing unique index on the UUID column means seq scans. A random UUID PK also fragments the index if it later becomes the real PK.
10. **No end date for the old behavior.** The legacy int path lingers forever without a deprecation signal.

## Plan
1. **Migration 1 (additive).** Add `uuid UUID` (nullable), backfill with `gen_random_uuid()` in batches, then add a unique index and set NOT NULL. Give the model `uuid = fields.UUIDField(unique=True, default=uuid4)`. Write a real `downgrade`.
2. **Responses (additive).** Keep `id: int` and add `uuid: UUID` to `SummaryResponseSchema` and `SummarySchema`. Old clients are unaffected.
3. **Paths.** Accept either form in `/{id}/`. A digits-only value resolves by int and a UUID-shaped value resolves by `uuid`. Anything else returns 422 as today. Put the lookup in one `crud._resolve(identifier)` helper used by get, put and delete.
4. **Background task.** Keep passing the internal int PK, so the summarizer is unchanged.
5. **Deprecation.** Send `Deprecation` and `Sunset` headers on int-addressed requests, and log their usage.
6. **Phase 2 (after usage drops to about zero).** Flip `id` to the UUID in a `/v2` router or behind a version header. Eventually drop the int path.
7. **Tests.** Cover int and UUID access for each verb, a UUID-shaped miss returning 404, malformed ids returning 422, backfill uniqueness, and the old response shape still containing an int `id`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | `id` type changes in responses | Old clients parse `id` as an int | Keep int `id`, add `uuid`, and flip only in `/v2` |
| 2 | Path union mis-parses | `{id}` is `int` with `gt=0`, and tests assert 422 | Single resolver, digits-first, explicit tests |
| 3 | Locking or failing migration | Existing rows, and `downgrade` is empty | Nullable add, batched backfill, then constrain, with a real downgrade |
| 4 | Duplicate or NULL UUIDs | Inserts can land mid-migration | Default at the DB level, unique index, post-check query |
| 5 | Background task uses the wrong id | `generate_summary(summary_id)` runs after the response | Keep the internal int PK for tasks |
| 6 | False sense of security | There's no auth, and int access stays open | Treat UUIDs as opaque only, and plan auth separately |
| 7 | Stale stored int references | Bookmarks, logs and other services hold ints | Keep the int path through a sunset window and publish the date |
| 8 | Auto-generated schema drift | `pydantic_model_creator` follows the model | Pin response schemas explicitly and add contract tests |
| 9 | Missing index or fragmentation | The UUID is queried on every request | Unique index now, and don't make a random UUID the clustered PK |
| 10 | Legacy path never retired | No end date is set | Deprecation headers, usage metrics, and a dated removal |

Riskiest: #1. Changing the type of `id` in responses silently breaks every existing client, so keep `id` as an int and add `uuid` alongside it.
