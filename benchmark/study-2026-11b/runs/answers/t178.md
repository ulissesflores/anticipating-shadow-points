# Plan: online visit booking with no double-booking per vet

## Findings
- This is Spring PetClinic (Spring MVC, Thymeleaf, JPA).
- `Visit` has only `date` (a `LocalDate`) and `description`. It has no vet and no time of day.
- `Vet` has no relationship to visits.
- `VisitController.processNewVisitForm` saves the visit through `Owner` cascade. It only checks that the date is in the future.
- `ddl-auto=none`, and the schema is hand-written in three places: `db/h2/schema.sql`, `db/mysql/schema.sql` and `db/postgres/schema.sql`. There are no migrations.
- `PetClinicConcurrencyTests` and `VisitControllerTests` already exist.

## Assumptions (stated rather than asked)
1. A visit needs a vet and a start time, so I'm adding both fields. Today's day-granular `Visit` can't express a clash.
2. Time is a fixed 30-minute slot grid, 09:00–17:00 on the clinic's local time. Two visits clash only if they have the same vet, date and slot. There are no variable durations or overlap math.
3. "Booking" extends the existing `/owners/{ownerId}/pets/{petId}/visits/new` flow. I'm not adding auth, accounts or a new public API.
4. A visit is hard-deleted if it's ever removed, which frees the slot. Cancel and reschedule are out of scope.
5. Existing visit rows get `vet_id = NULL` and a null slot. They're legacy rows and are exempt from the rule.
6. The app may run with more than one instance, so the guarantee has to be enforced in the database. An in-app check alone isn't enough.

## Design
The database enforces uniqueness, and the app catches the violation. A check-then-insert in Java would race. The unique constraint is the only reliable guard, and the pre-check is just for friendlier UX.

1. **Schema.** Do this in all three `schema.sql` files.
   - Add `vet_id INTEGER` and `visit_time TIME` to `visits`.
   - Add a foreign key to `vets(id)`.
   - Add `UNIQUE (vet_id, visit_date, visit_time)`.
   - NULLs are distinct in H2, MySQL and Postgres, so legacy rows don't collide.
   - The `data.sql` seed rows stay unchanged.
2. **Model.** In `Visit.java`, add a `time` field (`LocalTime`) and a `vet` reference (`@ManyToOne`, `vet_id`). Keep the default constructor working, since `Visit()` is created in the controller.
3. **Availability.** Add a `VisitRepository` method that returns the booked times for a vet on a date. The form uses it to show only free slots. It's advisory only.
4. **Controller.** In `VisitController`:
   - Add `vets` and the slot list to the model.
   - Validate that vet and time are present, that the time is on the grid, and that the date is in the future (already checked).
   - Wrap `owners.save(owner)` in a catch for `DataIntegrityViolationException`. On a clash, call `result.reject("visit.slotTaken")` and redisplay the form with refreshed free slots.
   - Keep the `setDisallowedFields("id", "*.id")` binder rule. Validate that the vet id exists.
5. **View and i18n.**
   - Update `createOrUpdateVisitForm.html` with a vet select, a date input and a slot select.
   - Show the vet and time in the visit list on `ownerDetails.html`.
   - Add the new message keys to every `messages_*.properties`. `I18nPropertiesSyncTest` fails if any locale is missing a key.
6. **Transactions.** Make sure the save runs in its own transaction, so the violation surfaces as an exception the controller can catch and not as a commit-time failure outside the handler.

## Tests
- `VisitControllerTests` (MockMvc):
  - A valid booking redirects.
  - A missing vet or off-grid time gives a validation error.
  - A `DataIntegrityViolationException` from save re-renders the form with the slot-taken error.
- A concurrency test, modelled on `PetClinicConcurrencyTests`: N threads book the same vet, date and slot. Exactly one succeeds and the rest get the slot-taken error.
- Repository test: two pets can book the same slot with different vets, and the same vet can book different slots.
- Run the integration tests on H2 and on MySQL/Postgres through the existing `MySqlIntegrationTests` and `PostgresIntegrationTests` (these need Docker/Testcontainers).

## Verification
Run `./mvnw test`, which includes the checkstyle and format plugins. Then run the app, book a visit, and try the same vet, date and slot from a second browser session. The second attempt should show the error. Finally, run the schema scripts against fresh MySQL and Postgres instances.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Race: two owners book the same slot at once | A check-then-save in Java passes for both | Unique constraint on (vet, date, time); catch the violation |
| 2 | Schema drift across three DB dialects | Hand-written `schema.sql`, no migrations, `ddl-auto=none` | Change all three together; run Postgres/MySQL integration tests |
| 3 | Existing deployed databases don't get the new columns | `schema.sql` only runs on init, and `DROP TABLE` isn't safe in prod | Provide a separate `ALTER TABLE` script; note it in the README |
| 4 | Legacy visits have no vet or time | New NOT NULL columns would break old rows | Keep nullable columns; rely on NULL-distinct uniqueness |
| 5 | The violation escapes the controller as HTTP 500 | The `Owner` cascade save can throw at flush or commit | Catch in the handler, with the transaction scoped to the save; test it |
| 6 | Missing i18n keys fail the build | `I18nPropertiesSyncTest` requires every locale | Add keys to all `messages_*.properties` |
| 7 | Stale availability list shown to the user | Slots can be taken between page load and submit | Treat the list as advisory; the constraint decides; re-render with fresh slots |
| 8 | Fixed 30-minute grid doesn't fit real appointment lengths | Real visits vary in length | Document the assumption; leave duration as a later extension |
| 9 | Timezone and "tomorrow" logic | `LocalDate.now()` uses the server zone | Pin a clinic `Clock`/zone bean and use it for validation |
| 10 | Tampered form posts (bad vet id, off-grid time) | Binder-level input is user-controlled; the repo has had input-hardening commits | Server-side validation; verify the vet exists; keep the disallowed-id fields |

Riskiest: #1, a race that double-books a vet. Only the database unique constraint prevents it reliably, and it must be correct in all three dialects.
