# Plan: require email verification before login (Remix Blues Stack)

I didn't edit any file, including the plan file. This plan is inline only.

## What the code does today
- `app/routes/join.tsx` creates the user and immediately calls `createUserSession`. This is the main gap.
- `app/routes/login.tsx` calls `verifyLogin` in `app/models/user.server.ts` and then `createUserSession`. It has no verified check.
- The `User` model in `prisma/schema.prisma` has no verification field. There is one migration, `prisma/migrations/20220224172159_init`.
- The repo has no mailer and no email dependency. It has bcryptjs, a cookie session in `app/session.server.ts`, msw mocks in `mocks/index.js`, and Cypress e2e tests.
- `cypress/support/create-user.ts`, `prisma/seed.ts` and `cypress/e2e/smoke.cy.ts` all assume a new user is logged in right away.

## Assumptions
- "New users" means accounts created after this ships. Existing users are grandfathered by a backfill.
- I'll use a transactional email provider such as Resend or Postmark, with an HTTP API called through `fetch`. I'll read its API key from an env var (`EMAIL_API_KEY`) and set `EMAIL_FROM` and `APP_ORIGIN` the same way.
- Verification links expire after 24 hours and can be used once.
- Signup no longer creates a session. It shows a "check your email" page.
- Login for an unverified user fails with a clear message and a resend option.

## Steps
1. **Schema and migration.**
   - Add `emailVerifiedAt DateTime?` to `User`.
   - Add an `EmailVerificationToken` model with `id`, `tokenHash` (unique), `userId` (cascade delete), `expiresAt` and `createdAt`.
   - The new migration backfills `emailVerifiedAt = now()` for all existing rows, so current users aren't locked out.
2. **Token helpers in `app/models/user.server.ts`.**
   - `createVerificationToken(userId)` generates 32 random bytes, stores only the SHA-256 hash, and returns the raw token.
   - `consumeVerificationToken(raw)` checks expiry and single use, and sets `emailVerifiedAt` in one transaction.
   - Add a resend helper that invalidates older tokens.
3. **Mailer in `app/email.server.ts`.** It has one `sendVerificationEmail(email, url)` function. In dev and test it logs the link or routes to msw, and `mocks/index.js` gets a handler for it.
4. **`join.tsx`.** After `createUser`, create a token, send the email, and redirect to `/verify-email/sent`. Don't create a session.
5. **`login.tsx` and `verifyLogin`.**
   - `verifyLogin` returns the user, or a distinct "unverified" result after the password check passes.
   - Return the unverified error only after the password is correct, so the message doesn't reveal which emails are registered.
   - Link to the resend action.
6. **New routes.**
   - `verify-email.tsx` takes the token from the query string. Its loader consumes the token, shows a success or failure message, and links to `/login`.
   - `verify-email.sent.tsx` is the "check your email" page.
   - `verify-email.resend.tsx` is a POST that is rate-limited and returns the same response whether or not the email exists.
7. **Defense in depth in `app/session.server.ts`.** `requireUser` and `getUser` also check `emailVerifiedAt`, and log out any unverified session. This catches sessions that already exist.
8. **Tests and tooling.**
   - Update `cypress/support/create-user.ts` and `prisma/seed.ts` to set `emailVerifiedAt`. Add an option to create an unverified user.
   - Rewrite the Cypress signup test: sign up, assert the "check your email" page, read the link from a test-only hook or a DB query, visit it, then log in.
   - Add vitest tests for the token lifecycle: expired, reused, tampered and valid tokens.
9. **Config.** Add the new env vars to `.env.example`, `fly.toml` secrets and the deploy workflow. The release command already runs `prisma migrate deploy`.

## Verification
- Run `npm run validate` (vitest, lint, typecheck, Cypress).
- Manually, on a fresh DB:
  - Sign up and confirm no session cookie is set.
  - Try to log in before verifying and confirm it is blocked.
  - Click the link, log in, and confirm it works.
  - Reuse the link and confirm it fails.
  - Wait out the expiry and confirm it fails.
  - Confirm the seeded and backfilled users can still log in.
- Run the migration against a copy of production data first.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | The column is new and defaults to null for every current row | Backfill `emailVerifiedAt` in the same migration; test on a data copy |
| 2 | Email never arrives | The repo has no mailer; deliverability depends on SPF/DKIM and domain setup | Use a managed provider, verify the sending domain, and ship the resend flow |
| 3 | Token leak or replay | Tokens travel in URLs, which end up in logs and referrers | Store only the hash, make it single-use, give it a short expiry, and redact it in logs |
| 4 | Account enumeration | Join already says "user already exists"; login errors could leak status | Check the password before revealing "unverified"; keep resend responses uniform |
| 5 | Existing sessions bypass the gate | The session cookie holds only `userId` and `requireUser` doesn't check status | Add the `emailVerifiedAt` check in `requireUser` and `getUser` |
| 6 | Broken tests and tooling | The Cypress smoke test, `create-user.ts` and the seed all assume instant login | Update them in the same PR; add a test-only way to read the link |
| 7 | Email abuse or cost | The resend and signup endpoints can trigger unlimited emails | Add per-email and per-IP rate limits, plus a cooldown |
| 8 | Deploy ordering | Code reading `emailVerifiedAt` before the migration runs would crash on Fly | Rely on `release_command` migrating first; keep the migration backward compatible |
| 9 | Email-provider outage during signup | A failed send would leave a user who can't log in | Create the user, log the failure, and let the resend flow recover |
| 10 | Verification race or double-click | A mail scanner prefetches the GET link and burns the token | Make the GET show a confirm button that POSTs the verification |

Riskiest: #1, existing users locked out by the new null column.
