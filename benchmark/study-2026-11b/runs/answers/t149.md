# Plan: integer IDs to UUIDs in the summaries API

You asked for no file edits, so I did not write the plan file. This plan is the answer.

## Context
The repo is a FastAPI + Tortoise ORM + Postgres service with Aerich migrations. The only resource is `TextSummary`, served under `/summaries/`.

- `app/models/tortoise.py`: the model has an implicit auto-increment `id`. The `SummarySchema` is generated from it.
- `app/api/summaries.py`: the routes are `/{id}/` with `id: int = Path(..., gt=0)`. The POST handler returns `{"id": <int>, "url": ...}`.
- `app/api/crud.py`: every function is typed `id: int`.
- `app/models/pydantic.py`: `SummaryResponseSchema.id: int`.
- `app/summarizer.py`: the background task is called with the integer ID.
- `migrations/models/0_..._init.py`: the table uses `SERIAL`.
- `tests/`: the tests assert 422 errors with int-style validation messages.

## Assumptions
- The integer ID is the only public identifier. No other table has a foreign key to `textsummary.id`.
- "Keeping existing clients working" means three things. Old clients can still call `GET`, `PUT` and `DELETE /summaries/<int>/`. Their stored integers stay valid. They keep parsing `id` as an integer in responses until they migrate.
- There is one Postgres database and a rolling deploy. Downtime is not wanted.
- The production data is small enough for a one-shot backfill.

## Approach: expand, then migrate, then contract
I'd keep the integer primary key and add a separate public UUID. Changing the primary key itself touches every index and foreign key, and it has no benefit for clients here.

1. **Schema (expand).** Add a migration. It adds `uuid UUID NOT NULL DEFAULT gen_random_uuid()` with a unique index. `gen_random_uuid()` is built in from Postgres 13. On older versions it needs the `pgcrypto` extension. The backfill runs in batches. Rows are backfilled before `NOT NULL` is enforced, and the unique index is built with `CREATE INDEX CONCURRENTLY`. I'd also write a real `downgrade`, because the init migration has an empty one.
2. **Model.** Add `uuid = fields.UUIDField(unique=True, default=uuid4)` and keep `id` as the primary key. Add a `uuid` field to `SummarySchema`.
3. **Dual-accept routes.** Change the path parameter to `ident: str`. Parse it with a small helper in `crud.py`. A UUID-shaped value looks up by `uuid`. An all-digit value looks up by `id`. Anything else returns 422 with the same error shape as today. GET, PUT and DELETE all use this helper.
4. **Responses.** Keep the integer `id` and add a `uuid` field. Existing clients ignore the new field, and new clients use it. The POST response gains `uuid` too. I'd add `uuid` to `SummaryResponseSchema` and keep `id: int`. The background task keeps using the internal integer.
5. **Deprecation signalling.** When a request uses an integer ID, add `Deprecation` and `Sunset` headers and log it with a counter. That gives real usage data before step 7.
6. **Docs.** Update the README and the OpenAPI description. The OpenAPI `id` path type changes from integer to string, so I'd call that out in release notes.
7. **Contract (later, separate release).** Once the integer-ID usage metric reaches about zero for an agreed window, stop returning `id`. Keep the integer primary key internally, or drop it deliberately in its own migration.

## Tests
- Update the existing tests whose 422 assertions depend on int validation. Those are the incorrect-ID cases in `tests/test_summaries.py`, which also has a parametrized update test.
- Add cases for the following:
  - a lookup by UUID and by integer returns the same row
  - the POST response includes `uuid`
  - a malformed or non-positive ID returns 422
  - an unknown UUID returns 404
  - the migration backfills existing rows
  - the migration downgrades cleanly
- Keep `tests/test_summaries_unit.py` mocking `crud`, and adjust it for the new helper.

## Verification
- Run the tests with `docker-compose up` and `pytest` inside the web container, plus the linters configured in `setup.cfg`.
- Run the migration against a copy of production-like data and check that the row count matches, every `uuid` is unique and non-null, and the old integer IDs still resolve.
- Smoke-test an old client against the new build, then roll back to the old build against the migrated schema. The old build must still work, because the new column is additive.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Clients break on the response shape | `id` is an int in the response model and the OpenAPI spec | Keep `id` as an int and add `uuid`. Defer removal. |
| 2 | Ambiguous ID parsing | `/{id}/` must accept both int and UUID | Strict, disjoint parsing (digits vs UUID) with tests |
| 3 | Enumeration and IDOR persist | Integer lookup stays available and the endpoints have no auth | Add the sunset timeline. Consider auth. |
| 4 | Migration locks or slow backfill | The table is backfilled and indexed while live | Batched backfill, `CONCURRENTLY` index, run off-peak |
| 5 | Rolling deploy mixes old and new code | Old pods don't know the `uuid` column | Additive-only schema and a default on the column |
| 6 | Empty `downgrade` in the Aerich init migration | Rollback is currently a no-op | Write an explicit downgrade and test it |
| 7 | Background task uses a stale ID | `generate_summary` receives the integer from POST | Keep the integer internally, or pass the UUID everywhere in one change |
| 8 | Tortoise/Aerich autogenerated migration is wrong | A UUID column with a default may be generated unsafely | Hand-write and review the SQL |
| 9 | Tests silently encode old 422 behaviour | Validation messages are asserted verbatim | Update the asserted messages deliberately |
| 10 | The deprecation never ends | No owner or metric for the sunset | Usage counter, `Sunset` header, tracked removal ticket |

Riskiest: #1, clients breaking on the response or path contract, because the `id` field's type and the route parameter are both public API.
