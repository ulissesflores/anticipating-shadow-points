**Assumptions**
- The change covers both `Signer.default_digest_method` and `HMACAlgorithm.default_digest_method`. It flows through `TimedSigner`, `Serializer`, `URLSafeSerializer` and the timed variants.
- The key-derivation step also uses the digest. Its default `django-concat` is `digest(salt + b"signer" + secret_key)`, so the derived key changes as well as the signature.
- The change is a new major version or a deliberately breaking change. It is not a silent patch release.
- I'll keep `_lazy_sha1` as a lazy SHA-1 helper for fallbacks. I'll add a lazy SHA-256 helper so FIPS and import-time behavior stays the same. I assume SHA-256 stays available wherever SHA-1 was.

**Ways it could go wrong, before planning**
- Every signature already issued stops verifying. This covers sessions, tokens, reset links and cookies, and it hits every downstream user at once.
- The tests pin the SHA-1 value `"[42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM"` (`tests/test_itsdangerous/test_serializer.py:192`). `test_digests` and the fallback-signer tests assume `_lazy_sha1` is the default (line 180).
- Signatures get longer (43 base64 characters instead of 27). Cookies, URLs, database columns or tokens with fixed length limits could overflow.
- Rolling deploys can mix old and new workers. They would reject each other's signatures during the rollout.
- Users who subclass or override `default_digest_method` could get unexpected behavior. Code that sets the digest explicitly is unaffected.
- Code that compares `signer.algorithm.digest_method` to a specific function could break.
- Docs, docstrings and `CHANGES.rst` could still say SHA-1.
- The default fallback signers might not include SHA-1, which would remove the old-token compatibility path.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | All existing signatures invalidated | The digest feeds both the key derivation and the HMAC, so every old token fails | Add a SHA-1 fallback signer by default, or document an opt-in migration; major-version bump |
| 2 | Rolling deploy splits old and new workers | Old workers reject SHA-256 signatures and new workers reject SHA-1 ones | Ship fallback-aware code first, then flip the default |

| 8 | Stale docs and docstrings | Several docstrings say "defaults to SHA1" | Update the docstrings, docs and `CHANGES.rst` with a versionchanged note |
| 9 | Fallback order mismatch | Serializer fallback lists may be built assuming SHA-1 is primary | Re-check the order, and test old-to-new and new-to-old verification |
