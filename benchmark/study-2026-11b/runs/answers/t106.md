## What the code does today

- `TodoList` and `TodoItem` (`src/Domain/Entities/`) inherit from `BaseAuditableEntity` and have no owner field. `CreatedBy` holds a user ID.
- `ApplicationDbContext` (`src/Infrastructure/Data/ApplicationDbContext.cs:10`) has no query filters, and `ApplicationUser` is an empty `IdentityUser`.
- `IUser` / `CurrentUser` (`src/Web/Services/CurrentUser.cs`) only provide the user ID and roles.
- Records are loaded in several ways: `FindAsync` in the Update and Delete handlers for items and lists, `Where` in `DeleteTodoList`, `ProjectTo` in `GetTodos`, and `AnyAsync` in the title-uniqueness validators.
- `CreateTodoItemCommand` accepts any `ListId` without checking it.
- The schema is created with `EnsureDeleted` + `EnsureCreated` (`ApplicationDbContextInitialiser.cs:44`). There are no migrations.
- This repo is a `dotnet new` template: `DependencyInjection.cs` uses `#if UsePostgreSQL/UseSqlServer` and `UseApiOnly` branches.

## Ways this could go wrong (before planning)

1. **A query misses the filter.** Any read that isn't filtered by tenant leaks data. That covers `ProjectTo`, validators, raw SQL, `ExecuteDelete`, and future handlers.
2. **Items in someone else's list.** `CreateTodoItem` takes `ListId` straight from the client. Without a check, tenant A can add items to tenant B's list. This is the only unguarded way in that I found.
3. **The tenant ID comes from the client.** If a request can set `TenantId` in the body, a header or the query string, a user can switch tenants.
4. **No tenant in context.** The seeder, background jobs and domain-event handlers run without an HTTP request. The tenant could be null, so the filter either hides everything or, if written badly (`TenantId == null`), shows everything.
5. **The filter is fixed at model-build time.** EF caches the model. The filter must read a field on the `DbContext` instance; if the tenant value is captured as a constant, every tenant gets the first tenant's ID.
6. **Item rows with the wrong tenant.** If `TodoItem.TenantId` isn't stamped, or doesn't match its list's tenant, the item filter and the list filter disagree.
7. **Unique titles are global.** `BeUniqueTitle` will run under the filter and only check the current tenant. But any database unique index has to become (`TenantId`, `Title`), or tenants will block each other's titles.
8. **Existing data and schema.** Production databases built from this template need a migration and a backfill for existing rows. The template itself rebuilds the schema on every start, which hides this problem.
9. **Template variants.** The change must compile and behave the same on SQLite, PostgreSQL and SQL Server, and in the API-only and SPA versions.
10. **Tests.** The functional tests (`tests/Application.FunctionalTests/TestBase.cs`, `TestApp.cs`) log in a user who has no tenant. Without updates, existing tests fail, or they pass without testing isolation at all.

## Assumptions (stated instead of asked)

- "Tenant" means a company. Each user belongs to exactly one company, and the company is fixed when the user is created.
- Shared database, with a `TenantId` column on each table plus EF global query filters. No database per tenant.
- The tenant comes from a `tenant_id` claim on the logged-in user. It never comes from request input.
- Administrators get no cross-tenant view. Seed data goes into a default "Demo" tenant.
- No tenant UI or tenant-management screens are in scope.

## Plan

1. **Domain:** Add a `Tenant` entity (`Id`, `Name`) and an `ITenantOwned { string TenantId }` interface. Put `TenantId` on both `TodoList` and `TodoItem`.
2. **Application:** Add `ITenantContext { string? TenantId }` in `Application/Common/Interfaces`. In `CreateTodoItem`, check that the list exists under the filter before adding the item, and throw `NotFoundException` if it doesn't.
3. **Identity:** Add `TenantId` to `ApplicationUser`. Add the `tenant_id` claim through a custom `IUserClaimsPrincipalFactory<ApplicationUser>`; the cookie and bearer schemes both use it. Implement `ITenantContext` in `Web/Services/CurrentTenant.cs`, next to `CurrentUser`.
4. **DbContext:**
   - Inject `ITenantContext` into `ApplicationDbContext`.
   - Add `HasQueryFilter(e => e.TenantId == _tenantId)` for every `ITenantOwned` type, so missing tenant matches nothing.
   - Make `TenantId` required, with a foreign key to `Tenant` and an index.
   - Replace any global unique index on title with (`TenantId`, `Title`).
5. **Writes:** Add `TenantInterceptor`, modelled on `AuditableEntityInterceptor`.
   - Added entities get the current tenant.
   - A change to `TenantId` on a modified entity is rejected.
   - Saving with no tenant throws.
   - An item's tenant must match its list's tenant.
   - Register it in `DependencyInjection.cs`.
6. **Seeder:** Create the demo tenant, give the administrator that tenant, and set `TenantId` explicitly on the seed list and items. The seeder runs with no tenant in context, so it needs a way to run without the filter, such as a system tenant scope.
7. **Tests:**
   - Change `RunAsUserAsync` to create users with a tenant.
   - Add a functional test where tenant A can't see, update, delete or add items to tenant B's lists.
   - Add a unit test for the interceptor.
   - Add a test for the "no tenant" case.

## Verification

- `dotnet build` and `dotnet test` for each database provider, through the template's own test matrix if it has one.
- Manual check: create two users in different tenants. Each user should only see their own lists through `GET /api/TodoLists`. `PUT`/`DELETE` and `POST /api/TodoItems` with the other tenant's IDs should return 404.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Items added to another tenant's list | `CreateTodoItem` trusts the client's `ListId` with no ownership check | Check the list under the filter first; interceptor also checks list and item tenants match |
| 2 | Filter bypassed or missed | `ProjectTo`, validators and future raw SQL or `ExecuteDelete` | Global query filters on all `ITenantOwned` types; avoid `IgnoreQueryFilters`; isolation tests |
| 3 | Filter fixed to one tenant | EF caches the model, so a captured value applies to everyone | Filter reads a field on the context; test with two tenants in one process |
| 4 | Null tenant shows all or nothing | Seeder and event handlers run without an HTTP request | Filter matches nothing when tenant is missing; interceptor refuses to save; explicit system scope for seeding |
| 5 | Tenant ID taken from request input | Easy shortcut in endpoints or DTOs | Read it only from the `tenant_id` claim; keep `TenantId` out of commands and DTOs |
| 6 | Claim missing from tokens or cookies | Two auth paths (cookie and bearer, `UseApiOnly`) | One claims-principal factory used by both; test each scheme |
| 7 | Unique title rule clashes across tenants | A global title index would block other tenants | Index on (`TenantId`, `Title`); validators run under the filter |
| 8 | Existing rows have no tenant | Template uses `EnsureCreated`; real apps built from it have data | Migration with a default tenant backfill, then make the column NOT NULL |
| 9 | Breaks some template variants | `#if` branches for SQLite, PostgreSQL, SQL Server and API-only | Build and test every variant |
| 10 | Tests pass without testing isolation | Test users have no tenant | Give `TestBase` users tenants; add tests that try to cross tenants |

Riskiest: #1 — `CreateTodoItem` trusts the `ListId` from the client, so a global read filter alone won't stop a company from writing into another company's list.
