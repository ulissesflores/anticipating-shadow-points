## What the code does today

This is the Remix "Blues stack": Prisma with Postgres, cookie sessions, and deployment on Fly.
- `app/routes/join.tsx:59-66` creates the user and **logs them in straight away** with `createUserSession`.
- `app/routes/login.tsx:49` calls `verifyLogin`, which only checks the password hash.
- `app/session.server.ts` stores only `userId` in the cookie. `requireUserId` and `requireUser` never re-check anything about the user.
- `prisma/schema.prisma`: the `User` table has no verification field. There is no code that sends email.
- Tests: `cypress/support/create-user.ts` and `cy.login()` create users directly. `smoke.cy.ts` expects signup to land you logged in.

## Ways this could go wrong (before planning)

1. **Existing users get locked out.** Adding `emailVerifiedAt` as null with no backfill would block every current account, including the seed user `rachel@remix.run`.
2. **Gate in the wrong place.** Checking only in `login.tsx` would miss two paths: `join.tsx` still creates a session, and old cookies still work.
3. **Sessions that already exist.** People who sign up while the change is rolling out keep a valid cookie. `requireUser` doesn't re-check verification.
4. **Weak tokens.** Guessable tokens, tokens with no expiry, reusable tokens, or tokens stored in plaintext would let someone take over an account.
5. **Account enumeration.** Different responses for "unverified" versus "wrong password", or a resend endpoint that reveals whether an email exists.
6. **Email doesn't arrive.** There's no provider, so users who never get the email are stuck. A resend option is required.
7. **Resend abuse.** With no rate limit, the resend endpoint can be used to spam people or run up provider costs.
8. **Squatting an address.** Someone signs up with another person's email and never verifies, and the real owner can't register. The current code returns "A user already exists".
9. **Broken tests and CI.** `create-user.ts`, `smoke.cy.ts` and the seed all assume users can log in immediately, so `npm run validate` fails.
10. **Deployment.** A new secret (`EMAIL_API_KEY`) is missing in Fly or `.env.example`, so the app crashes on boot or sends nothing. The migration runs during deploy (`prisma migrate deploy`), so a bad backfill goes straight to production.

## Assumptions (non-interactive)

- "New users" means accounts created after the deploy. Existing users are marked verified by backfill.
- Verification is a link with a token that expires (24h, single use). The token is stored hashed.
- The email provider sits behind a small `sendEmail` interface (Resend or Postmark through `fetch`). In dev and tests, MSW in `mocks/index.js` intercepts the call and logs the link.
- Unverified users can't log in. They get a neutral message and a link to resend the email.

## Plan

1. **Schema and migration** (`prisma/schema.prisma`, new migration):
   - Add `emailVerifiedAt DateTime?` to `User`.
   - Add a new `EmailVerificationToken { id, tokenHash @unique, userId, expiresAt, createdAt }` table, with cascade delete.
   - In the same migration: `UPDATE "User" SET "emailVerifiedAt" = "createdAt"`, so existing users stay able to log in.
2. **Model** (`app/models/user.server.ts`):
   - `createUser` leaves `emailVerifiedAt` null.
   - Add `createEmailVerificationToken(userId)`: random 32 bytes, stores the sha256 hash, deletes the user's earlier tokens.
   - Add `verifyEmailToken(token)`: in one transaction, find the hash where it hasn't expired, set `emailVerifiedAt`, delete the token.
   - `verifyLogin` returns `emailVerifiedAt`, or a separate status, so the route can tell the cases apart.
3. **Email** (new `app/email.server.ts`):
   - `sendVerificationEmail(email, url)` builds the link from `APP_URL`, not from the request's Host header.
   - Add the env var to `.env.example` and to the Fly secrets docs in the README.
4. **Routes**:
   - `join.tsx`: after `createUser`, create a token, send the email, and redirect to `/verify-email/sent`. **Don't** call `createUserSession`.
   - New `verify-email.$token.tsx`: on success, create the session and redirect to `/notes`. On an invalid or expired token, show an error with a resend link. Do it as a POST, or have the GET render a confirm button, so link scanners in mail clients don't consume the token.
   - New `verify-email.resend.tsx`: always shows the same response, and is rate-limited per email and per IP (a timestamp on the token row is enough to start).
   - `login.tsx`: if the password is valid but the user is unverified, return an "Please verify your email" error with a resend link, and don't create a session.
5. **Defense in depth** (`session.server.ts`): `requireUser` also requires `emailVerifiedAt`, and otherwise redirects to `/verify-email/sent`. This closes the gap from cookies issued during the rollout.
6. **Seed and tests**:
   - `prisma/seed.ts` sets `emailVerifiedAt: new Date()`.
   - `cypress/support/create-user.ts` marks test users as verified.
   - Rewrite `smoke.cy.ts`: sign up, see the "check your email" page, read the token from the DB with a small `cy.exec` script, visit the link, and confirm you land logged in.
   - Add vitest unit tests for token expiry and single use.

## Verification

- Run `npm run setup` on a copy of the DB and check that existing rows now have `emailVerifiedAt` set.
- Run `npm run dev`, sign up, check the console (MSW) for the link, and confirm login is blocked before verifying and works after.
- Test an expired token, a reused token, and resend for an email that doesn't exist (the response must be identical).
- Run `npm run validate` (unit tests, lint, typecheck, Cypress).
- Deploy to staging on Fly with the new secret before production.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New nullable column; seed user and production rows have no value | Backfill `emailVerifiedAt = createdAt` in the migration |
| 2 | Signup still logs users in | `join.tsx` calls `createUserSession` directly | Redirect to "check email" with no session |
| 3 | Cookies get past the gate | Session holds only `userId`; `requireUser` checks nothing else | Check verified in `requireUser` too |
| 4 | Token forgery or replay | No token infrastructure exists yet | 32-byte random, hashed, 24h, single-use, inside a transaction |
| 5 | Link scanners use up tokens | A GET request that verifies is triggered by mail previews | Confirm by POST, or a button on the page |
| 6 | Account enumeration | Login and join currently reveal whether an account exists | Same response wording for resend, login and unverified |
| 7 | Mail not delivered or resend abused | No provider; no rate limiting anywhere | Resend flow, per-email and per-IP throttle, dev mock through MSW |
| 8 | Email squatting | "User already exists" blocks the real owner | Let signup for an unverified address re-send the email, or expire unverified accounts |
| 9 | CI and e2e break | `create-user.ts` and `smoke.cy.ts` assume instant login | Verified test users; e2e reads the token from the DB |
| 10 | Deploy crashes or misconfiguration | New env vars; the migration runs automatically on Fly | `.env.example`, Fly secrets, staging deploy first |

Riskiest: #1. A migration without the backfill locks out every existing user as soon as Fly deploys.
