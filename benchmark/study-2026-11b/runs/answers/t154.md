## What the code looks like today
This is Spring PetClinic. A `Visit` has only a `date` (`LocalDate`), a `description` and a `pet_id`. The `visits` table has no vet column and no time-of-day column. `VisitController.processNewVisitForm` adds the visit to the owner's pet and calls `owners.save(owner)`. It has no `@Transactional` and no uniqueness check. `Vet` is only read through `VetRepository`. Vets have no schedule or availability data.

## Assumptions
- "Online booking" extends the existing owner → pet → new-visit form. No new login or auth layer is added.
- A slot has a start time and a fixed length, 30 minutes by default. Two bookings conflict when the same vet has overlapping intervals.
- The owner picks a vet and a start time. Any vet may be booked until working hours are defined, and the clinic is in one time zone.
- The schema is maintained in three scripts (H2, MySQL, Postgres) with no migration tool, so each needs the same change.
- Existing visits have no vet or time. They stay valid, and new constraints apply only to rows that have both.
- Cancelled visits are out of scope. If they are added later, they must free the slot.

## Plan outline
1. Schema: add `vet_id` (foreign key), `start_time` and `end_time` to `visits`, nullable for old rows. Add a database-level guard against double-booking.
2. Model: extend `Visit` with `vet`, `startTime` and `duration`. Add `Vet` lookup for the form.
3. Service: put booking in a `@Transactional` service method that re-checks for overlap. Map the database constraint violation to a friendly form error.
4. Controller and view: add a vet and time selector. Show only free slots, but treat that list as a hint, not the guard.
5. Tests: add concurrent-booking, boundary, and per-database tests. Run them against MySQL and Postgres, not only H2.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Race: two owners book the same slot at once | The current save path has no transaction or lock. A check-then-insert passes for both requests. | Enforce it in the database, and catch the violation. |
| 2 | Overlap is not equality | A unique key on (vet, start) misses a 10:00–10:30 booking against a 10:15 one. | Use slot-aligned start times, or a Postgres exclusion constraint. On H2 and MySQL, lock the vet row inside a transaction. |
| 3 | Three databases behave differently | H2, MySQL and Postgres lack a shared range-constraint feature. Tests default to H2. | Lock the vet row in code, and add DB-specific schema and Testcontainers runs. |
| 4 | Existing data and schema migration | `visits` rows have no vet or time. There is no Flyway or Liquibase, only `schema.sql`. | Use nullable columns, and apply constraints only where the values are set. Document the manual migration. |
| 5 | Time zones and DST | `LocalDate` is used today. Adding times raises server-versus-clinic zone and DST-shift issues. | Store the clinic-zone local time, and fix one zone in config. |
| 6 | Stale form lists and double submit | The slot list loads before the POST. A double-click or back button resubmits. | Re-validate on POST, and use post-redirect-get. The unique violation covers the rest. |
| 7 | Client-controlled input | A user can post any vet id, past time or huge duration. The repo already added integer-overflow guards. | Validate server-side: the vet exists, the time is future and within hours, and the duration is whitelisted. |
| 8 | Owner can book for someone else's pet | `loadPetWithVisit` trusts the path ids, and there is no auth. | Keep the owner/pet ownership check, and note the auth gap. |
| 9 | Slot hoarding and abuse | Anyone can book many slots with no limit, which blocks vets for real owners. | Cap bookings per pet or owner, and require future dates only. |
| 10 | Existing flows and tests break | The visit form and the `Visit()` default of tomorrow have tests and i18n strings in about 10 languages. | Keep old fields compatible, add new message keys with an English fallback, and run the full suite. |

Riskiest: #1, the double-booking race, because the current save path has no transaction or lock. An application-level check alone will still let two simultaneous requests both succeed, so the guarantee has to live in the database.
