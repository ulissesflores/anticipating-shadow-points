I've written a plan to give every to-do list and item a tenant (company), so each company only sees its own data. Nothing in the repo was changed; the plan is in `plans/make-every-to-do-list-pure-lamport.md`.

**Where things stand:** this repo is the Clean Architecture `dotnet new` template. Any signed-in user can currently see and change every `TodoList` and `TodoItem`. The database setup (`ApplicationDbContextInitialiser`) deletes and recreates the database on each start, so there are no migrations and no data to backfill in the template itself.

**Assumptions:**
- Each user belongs to exactly one company, read from a `tenant_id` value attached to their login.
- Registering a new user creates a new company for them; inviting people into an existing company is out of scope.
- Administrators get no cross-company view.
- List titles only need to be unique within a company.

**Plan:**
1. **Domain:** add a `Tenant` entity and an `ITenantOwned` interface. `TodoList` and `TodoItem` both get a `TenantId`; items store their own copy so filtering doesn't need a join.
2. **Who the tenant is:**
   - Add `TenantId` to `ApplicationUser`.
   - At sign-in, put a `tenant_id` claim on the user (this covers both cookie and API-token logins).
   - `CurrentUser` reads that claim and exposes it through `IUser`.
   - A custom `UserManager` creates a company when a new user registers.
3. **Automatic filtering:** `ApplicationDbContext` applies one filter to every `ITenantOwned` table: rows must match the current user's tenant. Existing query handlers then need no changes.
4. **Writes:**
   - A new `TenantInterceptor` stamps `TenantId` on new rows and refuses any change to it.
   - The link from item to list includes `TenantId`, so the database itself rejects an item pointing at another company's list.
5. **Application:**
   - Every todo command gets `[Authorize]`, and a signed-in user without a company is refused.
   - Validators check that `ListId` belongs to the user's company when creating an item or moving it to another list.
   - The existing unique-title checks become per-company automatically.
   - Another company's ids return 404, not 403, so they aren't revealed.
6. **Seed and tests:**
   - The seed data gets a default company that owns the administrator and the "Tasks" list.
   - The test helpers can sign in as a user of a given company.
   - New tests cover: cross-company reads and writes are blocked, items can't be attached to a foreign list, duplicate titles are allowed across companies, and a user without a company is refused.
7. **Verify:**
   - Build each database variant (SQLite, PostgreSQL, SQL Server) and the API-only variant.
   - Run the functional, unit and Playwright tests.
   - By hand, register two users and confirm each sees only their own lists and gets 404 on the other's ids.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Filter fixed to one tenant | The filter must read a property on the database context; capturing a local value bakes in the first tenant and leaks it to everyone | Use the `CurrentTenantId` property; test with two tenants |
| 2 | Linking to another company's list | `CreateTodoItem` and `UpdateTodoItemDetail` accept any `ListId` and don't check it today | Validator check plus the database-level link that includes `TenantId` |
| 3 | Users with no company | Registration via `MapIdentityApi` has no tenant field, so new users would see nothing or crash | Create a company on registration; refuse users without one |
| 4 | Seeding and background code have no user | The startup seed has no logged-in user, so the interceptor would reject its writes | Set `TenantId` explicitly; allow a preset value when there's no user |
| 5 | Filter bypassed later | Someone adding `IgnoreQueryFilters()` or raw SQL in Application code silently leaks data | Keep bypasses in Infrastructure and tests only; review rule |
| 6 | Logins issued before the change | Existing cookies and tokens have no `tenant_id` | Treat a missing claim as Forbidden; force re-login |
| 7 | Existing projects have real data | Adding a required `TenantId` to filled tables needs a backfill; the template itself has no migrations | Document a migration: add nullable, backfill, then make required |
| 8 | Test helpers break | `TestApp.FindAsync` and the test user stand-in don't know about tenants | Add tenant to `RunAsUserAsync`; bypass the filter in `FindAsync` |
| 9 | One of the 6 template variants breaks | Code switches on `UseApiOnly` and the three databases | Build every variant in CI |
| 10 | Uniqueness changes | Title uniqueness becomes per company, so the same title can now exist in two companies | Optional database index on (`TenantId`, `Title`); test it |

Riskiest: #1. A filter that captures the wrong value silently shows one company's lists and items to every other company, and nothing errors.
