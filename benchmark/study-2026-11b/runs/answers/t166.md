**Assumptions** (this is a non-interactive run, so I'm not asking):
- The repo is ItsDangerous 2.3.0.dev. "Default signing digest" means `default_digest_method` on `HMACAlgorithm` and `Signer` in `src/itsdangerous/signer.py:54` and `:120`, which both use `_lazy_sha1` today. `TimestampSigner` and the serializers inherit the default, so they change too.
- This is a deliberate breaking change for the unreleased 2.3.0. It is not a security fix: `docs/concepts.rst:146` correctly says SHA-1 is not insecure inside HMAC.
- I edited no files, including the plan-mode plan file, because you said not to edit anything.

## Ways this could go wrong (read before planning)

1. **Every token signed before the upgrade stops validating.** The digest is used in two places: the HMAC itself, and key derivation (`signer.py:201-209`). With the default `django-concat` mode, the signing key is `sha1(salt + b"signer" + secret)`. Changing the default changes both, so Flask session cookies, password-reset links and email-confirmation tokens all become invalid at once.
2. **Tokens get longer.** The signature grows from 20 to 32 bytes, which is 27 to 43 base64 characters. That can push cookies past the 4 KB limit and break URL-length or fixed-width database columns.
3. **Mixed versions during a rolling deploy.** While old and new servers run side by side, each rejects the other's tokens, so users get logged out or see "bad signature" errors.
4. **Downstream code that relies on the default.** Flask's `SecureCookieSessionInterface` already pins `digest_method = sha1` explicitly, so it won't change. Other libraries, or code that compares against `Signer.default_digest_method`, may silently change behaviour.
5. **Removing `_lazy_sha1` breaks things.** The tests import it (`test_serializer.py:16`, `:180`), third parties may too, and a fallback still needs SHA-1. It must be kept, not deleted.
6. **FIPS laziness gets lost.** If the new default is written as `staticmethod(hashlib.sha256)`, it is evaluated at import time. A lazy wrapper, `_lazy_sha256`, keeps the same pattern even though SHA-256 is FIPS-approved.
7. **Hardcoded values in tests and docs go stale.** `test_digests` asserts `default == sha1` and hardcodes the SHA-1 token. `test_iter_unsigners` asserts `_lazy_sha1`. The README shows a SHA-1 example token, and the docstrings and `concepts.rst` say "defaults to sha1".
8. **No migration path by default.** Unless docs or a helper show `fallback_signers=[{"digest_method": hashlib.sha1}]`, users won't know how to accept old tokens. And a fallback only works on `Serializer`, not on bare `Signer` or `TimestampSigner`.
9. **Weak communication.** Without a prominent CHANGES entry and a version bump that signals a breaking change, users will hit mass logouts in production by surprise.

## Plan (summary)

1. In `signer.py`:
   - Add `_lazy_sha256` next to `_lazy_sha1`, and keep `_lazy_sha1` exported.
   - Point `HMACAlgorithm.default_digest_method` and `Signer.default_digest_method` at `_lazy_sha256`.
   - Update the docstrings and comments, with a `.. versionchanged:: 2.3` note.
2. Tests:
   - In `test_digests`, assert `default == sha256` with a newly computed constant, and keep the SHA-1 constant as an explicit case.
   - In `test_iter_unsigners`, expect `_lazy_sha256`.
   - Add a test that a default serializer with an SHA-1 fallback loads an old SHA-1 token.
   - Add a test that the key-derivation output changes as well.
3. Docs:
   - In `concepts.rst`, describe the new default and show the SHA-1 fallback recipe.
   - In `serializer.rst`, flip the example to "sign with SHA-256, fall back to SHA-1".
   - Regenerate the README example token.
   - Add a CHANGES 2.3.0 entry marked as breaking, with migration steps and a note on token length.
4. Verify:
   - Run `uv run pytest`, then `pyright`/`mypy` and a docs build.
   - Run a manual round-trip: a token signed by 2.2 must fail under the new default and pass with the fallback.
   - Grep for leftover "sha1" default claims.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | All existing tokens are rejected | The digest drives both the HMAC and `django-concat` key derivation | Documented SHA-1 `fallback_signers` recipe; breaking-change note |
| 2 | Rolling-deploy mismatch | Old and new nodes reject each other's tokens | Deploy the fallback first, then switch the default |
| 3 | Tokens get longer | 27→43 signature characters, close to cookie/URL limits | Call out the size in CHANGES; recommend SHA-256 over SHA-512 |
| 4 | No fallback for bare `Signer` or `TimestampSigner` | `fallback_signers` exists only on `Serializer` | Document a manual try-SHA-1 pattern for signer-only users |
| 5 | `_lazy_sha1` removed or renamed | Tests and third parties import it | Keep it; add `_lazy_sha256` alongside |
| 6 | FIPS/import-time regression | An eager `hashlib` reference breaks the lazy pattern | Use a lazy wrapper for SHA-256 |
| 7 | Stale tests and docs | Hardcoded SHA-1 token, "defaults to sha1" text, README token | Update constants, docstrings, `concepts.rst` and README together |
| 8 | Downstream behaviour silently changes | Libraries that don't pin a digest inherit the new one | Release notes; check Flask, which pins SHA-1 |
| 9 | Change is mistaken for a security fix | Docs say HMAC-SHA1 is still secure | Frame it as modernisation/compliance, not a vulnerability |

Riskiest: #1, because every existing token is invalidated: the default change hits both the HMAC and key derivation, so all outstanding sessions and links break at upgrade unless a SHA-1 fallback is configured.
