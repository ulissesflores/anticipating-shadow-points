**Plan: make `rolling` default to `true` in express-session**

This is the express-session 1.19.0 repo, and I made no edits.

**Assumptions**
- "Sessions roll by default" means the `rolling` option defaults to `true`. Every response that has a loaded session then re-sends the cookie with a fresh expiry. Users can still pass `rolling: false` to opt out.
- This is a behavior change, so it should ship as a semver-major release. A minor release with the same flip would be unsafe. I'm not planning a deprecation cycle. Say so if you'd prefer one.
- `saveUninitialized` and `resave` keep their current defaults.

**What the code does today**
- `index.js:109` has `var rollingSessions = Boolean(opts.rolling)`, so an undefined `rolling` means `false`.
- `index.js:491` (`shouldSetCookie`) returns `rollingSessions || (cookie.expires != null && isModified(session))` for existing sessions. A new session is still gated by `saveUninitialized`.
- The store-side expiry is refreshed separately, by `touch` at `index.js:363` or by a resave. With `rolling` on, the cookie and the store therefore need to move together.

**Steps**
1. In `index.js:109`, change the default to `opts.rolling === undefined ? true : Boolean(opts.rolling)`. Update the JSDoc at `index.js:78` to say "default true".
2. Check that the store's expiry also extends on every request.
   - Today `shouldTouch` runs only when the session is unmodified and `resave` is false. Stores that implement `touch` handle this.
   - Stores without `touch`, plus `resave: false`, would renew the cookie but let the stored session expire on its old schedule. Confirm that is acceptable, or document that such stores need `resave: true`.
3. Update the `rolling` section of `README.md` (around line 295) to state the new default and give the `rolling: false` opt-out. Update the `maxAge` and `saveUninitialized` cross-references, and any example config that relied on the old default.
4. Add a `HISTORY.md` entry that flags the breaking change.
5. Update tests in `test/session.js`:
   - Add a test that omitting `rolling` re-sends `Set-Cookie` on a second request with a refreshed `Expires`.
   - Add a test that `rolling: false` keeps the old behavior.
   - Review the `rolling option` block (line 1158) and other tests that assume no `Set-Cookie` on unmodified sessions. Expect several existing assertions to need `rolling: false` or new expectations.
   - Cover the `saveUninitialized: false` combination.
6. Bump the major version in `package.json`.

**Verification**
- Run `npm test` and the lint script, and check the coverage report.
- Manually run an Express app with the default MemoryStore. Make two requests and confirm `Set-Cookie` appears on both with an advancing `Expires`.
- Repeat with `rolling: false` and confirm the old behavior.
- Repeat with a store that has no `touch` method.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Breaking default for every consumer | Anyone relying on a fixed absolute timeout silently gets sessions that never expire while the user is active | Major release, a loud HISTORY and README note, and a documented `rolling: false` opt-out |
| 2 | Absolute lifetime lost (security) | A stolen cookie stays valid indefinitely if it is used regularly | Document it, and recommend an app-level absolute cap |
| 3 | Cookie and store expiry drift | With no `touch` and `resave: false`, the cookie renews but the store entry still expires | Verify the store path, document the requirement, and add a test with a touch-less store |
| 4 | `Set-Cookie` on every response | Caches and CDNs may skip caching, and responses get larger | Note it in the docs, and tell users to set `Cache-Control` and scope sessions to the routes that need them |
| 5 | Extra store writes | A `touch` on every request raises load on Redis or SQL stores | Mention it in the upgrade notes, and advise a sensible `maxAge` and store TTL handling |
| 6 | Many existing tests break | Tests assume no cookie on unmodified sessions | Audit them, pin `rolling: false` where the old behavior is intended, and add new default tests |
| 7 | Interaction with `saveUninitialized: false` | Rolling only applies to loaded sessions, so users may expect it to apply to new ones | Keep the current semantics, and test and document the combination |
| 8 | Session-less requests such as static assets | A session may be loaded for every asset request, and each one rolls it | Advise mounting the middleware only on the routes that need it |

Riskiest: #1, because flipping the default silently changes session lifetime semantics for every existing user.
