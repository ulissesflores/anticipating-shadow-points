I've written the plan to `claude-home/plans/change-the-default-signing-structured-turtle.md`; no project files were changed. This repo is **itsdangerous** (2.3.0.dev). The core change is small, but making it safe for existing tokens takes more work.

**Assumptions** (non-interactive run, so I didn't ask):
- **Release:** this goes into the unreleased 2.3.0, which already contains breaking removals.
- **New default:** plain `hashlib.sha256`. It doesn't need the lazy wrapper because SHA-256 exists in FIPS builds.
- **Old tokens:** SHA-1 tokens must still load by default through `Serializer`, `TimedSerializer` and `URLSafeTimedSerializer` for one release. Code that calls `Signer` directly gets no fallback; the docs will say so.
- **Key derivation:** stays `django-concat`. It hashes with the same function, so derived keys change too.

**Plan**
1. **`src/itsdangerous/signer.py:40-54,120`**
   - Set `HMACAlgorithm.default_digest_method` and `Signer.default_digest_method` to `hashlib.sha256`.
   - Keep `_lazy_sha1`, because the fallback needs it.
   - Update the docstrings that mention SHA-1 and add `versionchanged:: 2.3`.
2. **`src/itsdangerous/serializer.py:102`**
   - Set `default_fallback_signers = [{"digest_method": _lazy_sha1}]`.
   - The catch: `iter_unsigners` (lines 297-307) replaces the user's `signer_kwargs` with the fallback's settings instead of merging them. A plain SHA-1 fallback would therefore drop a custom `key_derivation` or `sep` and still reject old tokens. So merge the default fallback over `signer_kwargs` in `__init__`, and leave user-supplied fallbacks as they work today.
   - Skip the fallback when the user has pinned SHA-1, so verification doesn't run twice.
3. **Tests**
   - `test_digests` gets a new SHA-256 expected token for the default. The SHA-1 value `-9cNi0Cx…` stays as an explicit-SHA-1 case.
   - `test_iter_unsigners` should expect SHA-256 first and the extra SHA-1 fallback.
   - New tests:
     - old SHA-1 tokens load under all three serializers;
     - custom `key_derivation`/`sep` survive in the fallback;
     - `fallback_signers=[]` turns the fallback off;
     - a direct `Signer.unsign` rejects a SHA-1 signature;
     - the signature is now 43 characters.
4. **Docs**
   - Rewrite `docs/concepts.rst:137-155` ("Digest Method Security") for the new default and fallback.
   - Update the example in `docs/serializer.rst:93-104`.
   - Add a breaking-change entry to `CHANGES.rst` 2.3.0 that explains how to keep SHA-1.
5. **Verification**
   - Run `uv run pytest` plus the repo's lint and type checks.
   - Sign a token with the 2.2.0 wheel and confirm this branch's `URLSafeTimedSerializer` loads it, while a direct `Signer` raises `BadSignature`.
   - Build the docs and check that no SHA-1-default wording is left.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing tokens and cookies stop validating | The new hash changes both the derived key and the signature | Default SHA-1 fallback in `Serializer` |
| 2 | Code that uses `Signer` directly breaks with no fallback | Only `Serializer` supports fallbacks | Changelog note and a one-line way to keep SHA-1 |
| 3 | Fallback drops custom `key_derivation`/`sep` | Fallback settings replace `signer_kwargs` instead of merging | Merge the default fallback over `signer_kwargs`, plus a test |
| 4 | Repeat of the 1.0.0 yank | The project already reverted a default-hash change after users broke | Ship in 2.3.0 with the fallback and a clear upgrade note |
| 5 | Tokens get longer (27 → 43 characters) | Cookies and URLs have size limits | Document it; SHA-1 can still be kept |
| 6 | Hard-coded tokens break downstream tests | Golden values like `-9cNi0Cx…` change | Changelog note; tests keep a SHA-1 case |
| 7 | The fallback keeps SHA-1 in use and slows rejection | FIPS builds and compliance scans flag SHA-1; failed checks run twice | Keep `_lazy_sha1`, allow `fallback_signers=[]`, remove the fallback in 3.0 |
| 8 | Unclear effect on mixed-version deployments | Old instances can't read new SHA-256 tokens during a rolling upgrade | Document "upgrade every instance before relying on SHA-256 tokens" |

Riskiest: #1. Every default token, cookie and reset link already issued stops validating unless the SHA-1 fallback is in place and keeps the user's other signer settings.
