## Assumptions
- The repo is `express-session` 1.19.0. "Roll by default" means the `rolling` option defaults to `true` when it isn't set, and an explicit `rolling: false` still turns it off.
- This changes default behaviour, so it is semver-major. It should go into the next major release, not a 1.x patch.
- You said not to edit any files, so I haven't written the plan file that plan mode normally asks for. The plan is below instead.

## What can go wrong (before planning)
1. **Every response with a session gets `Set-Cookie`.** `shouldSetCookie` (`index.js:491`) returns `true` for any existing session when `rollingSessions` is on. That adds response headers and can stop CDNs or proxies from caching responses that carry `Set-Cookie`.
2. **Store writes on every request.** On each request the middleware calls `req.session.touch()` (`index.js:347-351`), then either saves or calls `store.touch`. With `resave: true`, which is still the deprecated default, or with stores that have no `touch`, write load on Redis, SQL and similar stores goes up a lot.
3. **Sessions that never expire for active clients.** A polling tab or a monitoring bot keeps the session alive forever. With no absolute timeout, a stolen cookie stays valid as long as it's used.
4. **Silent behaviour change for current users.** Code that never set `rolling` relied on the old default. A one-line change to `Boolean(opts.rolling)` at `index.js:109` would flip every app with no warning.
5. **Tests break.** `test/session.js:1159` asserts "should default to false", and about 26 other assertions check `shouldNotHaveHeader('Set-Cookie')`. Some of those cover unmodified sessions with the default options and will start failing.
6. **Truthiness trap.** `Boolean(opts.rolling)` turns `undefined` into `false`. The new default must test for `=== undefined`, otherwise `rolling: false` and a missing option become hard to tell apart.
7. **Cookies with no `maxAge`.** When `maxAge` is unset there is nothing to roll, but a cookie is still sent on every response, which is just overhead.
8. **Docs and changelog drift.** `README.md:295-301` says "The default value is `false`", and `HISTORY.md` needs an entry.
9. **Concurrent requests race.** Rolling writes from parallel requests can overwrite each other's session changes in stores that write the whole session (made worse by risk 2).

## Plan
1. **`index.js:108-109`**: change the default:
   ```js
   var rollingSessions = opts.rolling === undefined ? true : Boolean(opts.rolling)
   ```
   Optionally, to match how `resave` and `saveUninitialized` are handled, add `deprecate('undefined rolling option; provide rolling option')` for one minor release first, then flip the default in the major.
2. **Leave `shouldSetCookie`, `shouldTouch` and `shouldSave` alone.** They already handle `rolling: true`, and the `saveUninitialized: false` guard for uninitialized sessions stays in place.
3. **`index.js:78` JSDoc and `README.md` `##### rolling`**: change the default to `true`. Add a note on store write load (point to `touch` and `resave: false`), on `Set-Cookie` and caching, and on opting out with `rolling: false`.
4. **`HISTORY.md`, "unreleased"**: add a breaking-change entry, "Change default `rolling` to `true`".
5. **Tests in `test/session.js`:**
   - Rewrite "should default to false" (around line 1159) as "should default to true": the second request with no session change still gets `Set-Cookie`.
   - Add "should not roll when `rolling: false`", which asserts `shouldNotHaveHeader('Set-Cookie')`.
   - Go through the ~26 `shouldNotHaveHeader('Set-Cookie')` assertions. Where a test is about something else, pass `rolling: false` explicitly. Where the expectation itself should change, update it.
   - Add a test that the default `rolling` calls `store.touch` on an unmodified session when `resave: false`.
6. **Verify**: run `npm test` (and `npm run lint` if it's defined), then check by hand with a small Express app with `maxAge: 60000` that the `Expires` value moves forward on each request.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Silent breaking change | Apps that never set `rolling` change behaviour on upgrade | Release as semver-major; deprecation warning first; HISTORY entry |
| 2 | Store write load | Every request saves or `touch`es; `resave` still defaults to `true` | Document `resave: false` plus stores that implement `touch` |
| 3 | `Set-Cookie` on every response | `shouldSetCookie` returns `true` for every existing session | Document it; `rolling: false` opts out |
| 4 | Sessions never expire for active clients | Polling or a stolen cookie keeps extending expiry | Recommend an app-level absolute timeout |
| 5 | Wrong default check | `Boolean(undefined)` is `false`, and a truthy check would ignore `rolling: false` | Use `=== undefined`; test the explicit `false` case |
| 6 | Test churn hides regressions | About 26 no-`Set-Cookie` assertions depend on the old default | Pin `rolling: false` per test, don't delete the assertions |
| 7 | Race on concurrent requests | More full-session writes means more lost updates | Document it; prefer stores with `touch` |
| 8 | Useless cookies without `maxAge` | A browser-session cookie gets resent with nothing to roll | Accept and document it, or skip when `expires` is null |
| 9 | Docs out of date | README says default is `false` | Update README and JSDoc in the same change |

Riskiest: #1. Flipping the default silently changes cookie, store and caching behaviour for every app that never set `rolling`.
