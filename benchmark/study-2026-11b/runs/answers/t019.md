# Plan: vet-aware visit booking with no double-booking

I made no edits and wrote no plan file, because you asked for none.

## What the code does today

- `Visit` has only `visit_date` (a date) and `description`. It has no vet and no time of day.
- `VisitController.processNewVisitForm` adds the visit to the pet through `Owner.addVisit` and saves the owner. There is no vet choice and no conflict check.
- The `visits` table is the same in `db/h2`, `db/mysql` and `db/postgres`: `id, pet_id, visit_date, description`. Schemas are applied from `schema.sql`, with `ddl-auto=none` and no migration tool.
- `PetClinicConcurrencyTests` already has a two-thread race test for duplicate pet names. That pattern is reusable.

"The same vet at the same time" can't be expressed yet, so the change adds both concepts.

## Assumptions

1. Owners already book visits online (`/owners/{id}/pets/{id}/visits/new`). The work is to add a vet and a time slot to that flow, then enforce uniqueness.
2. Slots are fixed-length, 30 minutes, on a 30-minute grid, within clinic hours (09:00–17:00). Free-form durations would need range-overlap logic, which I'm avoiding.
3. Two visits conflict when they have the same `vet_id` and the same `visit_date` + `visit_time`. Different vets at the same time are fine. A pet can't be in two places, but that rule is out of scope.
4. Existing rows have no vet or time, so the new columns are nullable. The unique constraint ignores rows with NULLs.
5. There is no auth or vet schedule model. Vet availability is "every slot in clinic hours".
6. The database is the source of truth for exclusivity. An application-level check alone is not enough.

## Steps

1. **Schema** (all three `db/*/schema.sql`, plus `data.sql` where needed)
   - Add `vet_id INTEGER` and `visit_time TIME` to `visits`.
   - Add a foreign key to `vets(id)`.
   - Add `UNIQUE (vet_id, visit_date, visit_time)`. Nullable columns don't collide on legacy rows in H2, MySQL or Postgres.
   - Document the manual `ALTER TABLE` for existing MySQL and Postgres databases, since there is no migration tool.
2. **Model** (`owner/Visit.java`)
   - Add `vet` (`@ManyToOne`, or a plain `vetId` to avoid coupling `owner` to `vet`) and `time`.
   - Keep the `@NotNull` and `@Size` validation style already used.
3. **Slot rules**
   - Put the rules in a small `VisitSlots` helper: clinic hours, step size, and "date is after today", which the controller already checks.
   - Validate that the time is on the grid and inside hours.
4. **Controller** (`VisitController`)
   - Add `@ModelAttribute("vets")` from `VetRepository.findAll()`, which is cached.
   - In `processNewVisitForm`, validate the vet and time, then save.
   - Wrap the `owners.save(owner)` call. On `DataIntegrityViolationException` caused by the slot constraint, call `result.rejectValue("time", "visit.slotTaken")` and return the form.
   - Don't rely on a pre-check query. A check-then-insert has a race, so the unique constraint decides.
   - Optionally add a cheap `existsByVetAndDateAndTime` query only to render "taken" slots in the form.
5. **UI** (`createOrUpdateVisitForm.html`, `selectField.html`)
   - Add a vet `<select>` and a time `<select>`.
   - Add the new message keys to all `messages_*.properties` files. `I18nPropertiesSyncTest` enforces that they stay in sync.
6. **Tests**
   - `VisitControllerTests`: missing vet, off-grid time, and slot-taken error paths.
   - Integration test: second booking of the same vet and slot is rejected, and the same slot with another vet is accepted.
   - Concurrency test modelled on `PetClinicConcurrencyTests`: two threads book the same vet and slot at once, exactly one succeeds and the other gets a form error, not a 500.
   - Run the existing MySQL and Postgres integration tests, since the constraint behaves slightly differently on each.

## Verification

- `./mvnw test` covers the new unit, controller and concurrency tests plus the H2 integration test.
- The MySQL and Postgres integration tests need Docker, so run them if it's available.
- Manually book the same vet and slot twice in the running app and confirm the second attempt shows a validation error.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Check-then-insert race | Two owners submit the same slot at once; an app-level check passes for both | DB unique constraint is the arbiter; concurrency test |
| 2 | Constraint violation surfaces as HTTP 500 | Recent commits fixed other 500s; the error comes from `owners.save()` | Catch `DataIntegrityViolationException`, map to a field error |
| 3 | Schema drift across 3 databases | H2 is recreated on start, MySQL and Postgres are not; no Flyway or Liquibase | Update all three schemas, document manual `ALTER` |
| 4 | Legacy visits have no vet or time | Existing rows would break `NOT NULL` columns or a constraint | Nullable columns; unique constraint ignores NULLs |
| 5 | Wrong constraint catch | Other violations (pet FK, name uniqueness) could be shown as "slot taken" | Check the constraint name or re-query before mapping |
| 6 | Time zone and "today" drift | The controller uses server `LocalDate.now()`; a clinic time zone isn't defined | Fix a clinic `Clock` or zone; test around midnight |
| 7 | Fixed-slot assumption | Real visits vary in length; a grid hides overlaps | State the assumption; plan range-overlap or exclusion constraint later |
| 8 | Vet cache is stale | `findAll` is `@Cacheable("vets")`; a removed vet could still be offered | FK catches it; short cache TTL |
| 9 | Owner-wide save | `owners.save(owner)` rewrites the whole aggregate, so an unrelated failure rolls back the booking | Keep the booking in one transaction; consider saving the visit directly |
| 10 | i18n sync test fails | New keys missing from any of the ~10 message files | Add keys to every locale in the same change |

Riskiest: #1, the check-then-insert race, because without the database unique constraint two owners can still double-book the same vet.
