# Plan: require email verification before login

## Context
This is a Remix "blues-stack" app with Prisma/Postgres and cookie sessions.

- **Sign-up today:** `app/routes/join.tsx` calls `createUser` and then `createUserSession`, so new users are logged in immediately.
- **Login today:** `app/routes/login.tsx` calls `verifyLogin`, which only checks the password hash.
- **Missing pieces:** the `User` model has no verification state. The repo has no mailer, no token model and no email-related env vars.

## Assumptions
- "New users" means accounts created after this change. Existing users are grandfathered in by a backfill. They are not forced to verify.
- Verification uses a single-use link with a 24-hour expiry. The link is emailed and contains a random token.
- The email provider is SMTP through `nodemailer`, configured by env vars (`SMTP_URL`, `EMAIL_FROM`, `APP_ORIGIN`). A provider API such as Resend would be an easy swap.
- Verifying does not log the user in. They are sent to `/login` with a notice. This keeps a forwarded or leaked link from becoming a session.
- Sessions that already exist for unverified users are not a concern, because new users never get a session before verifying.

## Steps

1. **Schema** (`prisma/schema.prisma` plus a new migration)
   - Add `emailVerifiedAt DateTime?` to `User`.
   - Add an `EmailVerificationToken` model with `id`, `userId` (cascade delete), `tokenHash @unique`, `expiresAt` and `createdAt`.
   - The migration sets `emailVerifiedAt = createdAt` for every existing row, so current users keep working.

2. **Token and mail helpers** (new `app/models/verification.server.ts` and `app/email.server.ts`)
   - `createVerificationToken(userId)` generates 32 random bytes with `crypto.randomBytes`, stores only the SHA-256 hash, and deletes any older tokens for that user.
   - `consumeVerificationToken(token)` looks up the hash and checks expiry. In one transaction it sets `emailVerifiedAt` and deletes the token.
   - `sendVerificationEmail(email, token)` builds the link from `APP_ORIGIN`.
   - In dev and test (`NODE_ENV !== "production"`, or no `SMTP_URL`), it logs the link to the console instead of sending.
   - Add the new vars to `.env.example`, `fly.toml` secrets docs and the README.

3. **Sign-up** (`app/routes/join.tsx`)
   - After `createUser`, create a token and send the email. Do not call `createUserSession`.
   - Redirect to a new `/verify-email/sent` page, or `/login?verify=sent`, that says "check your inbox".

4. **Login** (`app/routes/login.tsx` and `app/models/user.server.ts`)
   - Keep `verifyLogin` returning the user. After a successful password check, `login.tsx` rejects users where `emailVerifiedAt` is null.
   - Return a 403-style error: "Please verify your email" with a "resend" action.
   - Check the password first so the unverified state does not reveal whether an email is registered.

5. **Verify route** (new `app/routes/verify-email.tsx`)
   - The loader reads `?token=`, calls `consumeVerificationToken`, then redirects to `/login?verified=1` or shows an "invalid or expired" page with a resend form.
   - Because a GET changes state, mail scanners that prefetch links could consume the token. Make the loader render a confirm button instead, and do the actual consume in the POST `action`.

6. **Resend** (new `app/routes/verify-email.resend.tsx`)
   - POST only. Always return the same response whether or not the email exists, to avoid account enumeration.
   - Rate limit it per email and per IP. A simple approach is to refuse if a token was created within the last 60 seconds, since `createdAt` is already stored.

7. **Defence in depth** (`app/session.server.ts`)
   - In `requireUser` and `getUser`, treat a user with `emailVerifiedAt === null` as logged out. This covers any session minted by another path.

8. **Test and seed tooling**
   - `prisma/seed.ts`: set `emailVerifiedAt: new Date()` for the seeded user.
   - `cypress/support/create-user.ts`: mark the user verified, since it mints a session directly.
   - `cypress/e2e/smoke.cy.ts`: the register-and-login test must change.
     - It signs up and sees "check your inbox".
     - It then reads the token from the DB or from a test-only log helper, visits the verify link and logs in.
   - Add vitest unit tests for token creation, expiry, single use and the `verifyLogin` plus unverified rejection.

## Verification
- `npm run typecheck`, `npm run lint` and `npm test -- --run`.
- `npx prisma migrate dev` on a copy of a DB with existing users. Confirm they stay able to log in.
- Manual run:
  1. Sign up. Confirm there is no session and a link is logged.
  2. Try to log in before verifying. Confirm it is rejected.
  3. Use the link. Confirm login works.
  4. Reuse the link and use an expired one. Confirm both fail.
  5. Resend, and confirm the old token is dead.
- `npm run test:e2e:run` with the updated Cypress flow.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New column defaults to null, so every current account looks unverified | The migration backfills `emailVerifiedAt = createdAt`. Test it on real-shaped data |
| 2 | No mail infra today | The app has no mailer, so a bad SMTP setup means nobody can ever register | Console-log fallback in dev, a startup check on SMTP vars, a deliverability test in staging |
| 3 | Token leak or replay | A plaintext or reusable token turns into account takeover | Store only the SHA-256 hash, make it single use, expire it in 24h, and don't auto-login on verify |
| 4 | Link prefetch consumes token | Mail scanners fire GET requests, so GET-consumed tokens fail for real users | Confirm button with a POST consume |
| 5 | Account enumeration | The join page already says "user already exists", and resend or login could leak more | Uniform responses on resend, and check the password before revealing the unverified state |
| 6 | Resend abuse | The resend endpoint can be used to spam an address or burn email quota | Per-email cooldown from `createdAt`, per-IP limit |
| 7 | Squatted or unverified emails | An unverified row holds the unique email, so a real owner cannot sign up | Let sign-up re-send and overwrite the password of an unverified account, or purge unverified accounts after N days |
| 8 | Tests and tooling break | `create-user.ts`, the seed and the Cypress smoke test all assume instant login | Update them in the same PR, and run the e2e suite in CI |
| 9 | Wrong link origin | A bad `APP_ORIGIN` behind Fly's proxy produces dead or wrong-host links | Make `APP_ORIGIN` an explicit required env var and don't derive it from the request |

Riskiest: #2, because a missing or broken email setup would block every new sign-up. The app has no mail code today and nothing in the repo can show that delivery works.
