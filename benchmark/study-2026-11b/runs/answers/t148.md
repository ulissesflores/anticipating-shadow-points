## What the code does today
- `Visit` has only `date` (a `LocalDate`) and `description`. It has no vet and no time of day (`owner/Visit.java`).
- The `visits` table is `pet_id, visit_date, description`. There is no `vet_id` and no unique constraint. The schema is hand-written in three dialects (`db/h2`, `db/mysql`, `db/postgres`), and `ddl-auto=none`.
- `VisitController.processNewVisitForm` saves through `owners.save(owner)`, which cascades the visit. It checks only that the date is in the future. Vets are a separate, read-only, cached aggregate in `vet/`.
- No authentication exists. Owners are addressed by URL id.

## Assumptions
1. A visit is a fixed-length slot, 30 minutes, on one vet's calendar. The slot length is configurable.
2. "Same time" means overlapping intervals for the same vet, not just identical start times.
3. Vets have no working hours or schedules yet. Phase 1 treats all slots as bookable inside a configurable clinic day, for example 09:00–17:00.
4. The owner picks a vet and a slot. Auto-assigning a vet is out of scope.
5. Existing visits have no vet or time. They are legacy and never conflict with new bookings.
6. The app must still run on H2, MySQL and Postgres.

## Ways this could go wrong
- **Race condition.** Two owners submit the same slot at once. A check-then-insert in Java passes for both. This is the core failure.
- **Overlap versus equality.** A unique index on `(vet_id, start)` blocks identical starts but allows a 09:00 visit and a 09:15 visit. Range exclusion constraints exist only in Postgres, not in H2 or MySQL.
- **Dialect drift.** The schema is hand-maintained for three databases. A constraint that works on one can be missing or behave differently on another.
- **Legacy data.** Making `vet_id` and the time `NOT NULL` breaks existing rows and `data.sql`. Leaving them nullable makes the constraint ignore old rows.
- **Time handling.** `LocalDate` becomes a date-time. Time zones, DST and the clinic's local time need a decision. The "tomorrow" default and the `isAfter(today)` check also need rework.
- **Aggregate boundary.** Visits hang off Pet and Owner. A vet-wide uniqueness rule doesn't fit that aggregate, so a conflict surfaces as a late `DataIntegrityViolationException` and an HTTP 500. Recent commits show this class of bug was already fixed once for other fields.
- **Form tampering.** The vet id and slot come from user input. Unknown vets, past times and out-of-hours slots need server-side validation. The existing `setDisallowedFields` list must stay correct.
- **Stale availability UI.** The slot list is read-only and can be out of date. The user sees "booked" only after submitting, so the error path must be friendly. The vets list is cached, so a cached availability view would be wrong.
- **Cancel and reschedule.** None exists today. Without it, a slot can never be freed and bookings pile up.
- **Abuse.** There is no auth or rate limit. One user can block a vet's whole day. The id-in-URL pattern also exposes other owners' pets.
- **Test gap.** Unit tests on H2 won't reveal a race or a Postgres-only constraint. Verifying it needs a concurrent test and Testcontainers runs.

## Plan (proposed, not applied)
1. **Schema, all three dialects.** Add `vet_id` and `start_time` to `visits` (nullable for legacy rows). Add a unique index on `(vet_id, start_time)` over fixed-grid slots, so overlap becomes equality. Snap starts to the slot grid in code.
2. **Entity.** Add a `Vet` reference and a `LocalDateTime` start to `Visit`. Keep `date` readable for legacy rows.
3. **Service layer.** Add a booking service in `owner/`, because the controller shouldn't carry the rule. It validates the vet, the grid alignment, the clinic hours and a future time. It then saves inside a transaction and catches `DataIntegrityViolationException` to return a clean "slot taken" form error. The database constraint is the real guard, and the pre-check is only for UX.
4. **UI.** Add a vet picker and a slot picker to `createOrUpdateVisitForm`, plus i18n messages in all the `messages_*.properties` files.
5. **Tests.** Cover the service on H2. Add a concurrent double-booking test that expects exactly one winner. Run the MySQL and Postgres paths against real containers.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Double-booking race | The current save path is check-then-act, with no locking. | DB unique index on `(vet_id, start_time)` as the authority. Catch the violation. |
| 2 | Overlap not enforced | Index covers equal starts only. Range constraints are Postgres-only. | Fixed slot grid, aligned in code and validated. |
| 3 | Dialect drift | Three hand-written schemas, `ddl-auto=none`. | Change all three together and run CI on each DB. |
| 4 | Legacy rows break | Existing visits have no vet or time. | Nullable columns, no backfill, and tests with `data.sql`. |
| 5 | HTTP 500 on conflict | The cascade save surfaces the error late. | Booking service with explicit handling and a form error. |
| 6 | Time and time-zone bugs | `LocalDate` becomes a date-time. DST and local time are undefined. | Clinic-local `LocalDateTime` and one configured zone. |
| 7 | Tampered input | The vet and slot come from the form. | Server-side validation and the disallowed-fields list. |
| 8 | Slots never freed | No cancel or reschedule exists. | Include cancel in scope, or ship with a clear limitation. |
| 9 | Slot hoarding and data exposure | No auth, ids in URL. | Out of scope here. Flag it, and add per-owner limits later. |
| 10 | Race goes untested | H2 unit tests hide concurrency and dialect differences. | Concurrent test and Testcontainers for MySQL and Postgres. |

Riskiest: #1, the double-booking race, because a Java-level check alone will pass for both concurrent requests and the database constraint is the only reliable guard.
