## Assumptions
- This is `express-session` 1.19.0, and "sessions roll" means the `rolling` option.
- "By default" means a change to the library default: `rolling` becomes `true` when the option is undefined. An explicit `rolling: false` keeps working as an opt-out.
- A breaking default change is acceptable, shipped in the next major version or flagged clearly if it goes out earlier.

## Findings
- `index.js:109` sets `var rollingSessions = Boolean(opts.rolling)`, so an undefined option becomes `false`.
- `shouldSetCookie` (`index.js:~490`) is the only consumer. For an existing session it returns `rollingSessions || (cookie.expires != null && isModified(...))`. With rolling on, the cookie is re-sent on every response, which resets `expires` to `maxAge`.
- The store side already extends expiry through `touch()` or `save()` (`shouldTouch`, `index.js:~471`), independent of `rolling`. So this change mostly affects the client cookie.
- The README `rolling` section (`README.md:~295`) says the default is `false`. Tests are in `test/session.js`, in the `rolling option` block (~line 1158) and in other tests that assume no `Set-Cookie` on follow-up requests.

## Plan

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Silent breaking change | The default flips for every existing user, with no code change on their side | Ship in a major version, put it in HISTORY, give a migration note |
| 2 | Sessions never expire for active users | Each request resets `maxAge`, so there is no absolute lifetime | Document it, and advise an app-level absolute timeout |
| 3 | Set-Cookie on every response breaks caching | Shared caches and CDNs may skip or split cached responses that carry `Set-Cookie` | Note it in the docs, and tell users to opt out for cacheable routes |
| 4 | Cookie sent on static or health-check routes | Extra headers, and polling endpoints keep sessions alive | Keep the middleware off those routes, and document that |
| 5 | Many existing tests assume non-rolling | Wide test churn can hide a real regression | Pin `rolling: false` in old tests, and review the diff by hand |
| 6 | Interaction with `saveUninitialized: false` | New unmodified sessions get no cookie, so "rolls by default" isn't universal | Keep the README note and add an explicit test |
| 7 | Store and cookie TTL drift | The store only extends expiry via `touch` or `save`, while the cookie always rolls | Verify the touch path with a custom store, and document `resave` with `touch` |
| 8 | Dynamic cookie option functions (1.19 feature) | The cookie options are resolved per request, so more Set-Cookie calls exercise that path | Add a test combining a cookie function with the rolling default |
| 9 | Third-party stores or middleware read `rolling` | Wrappers or tests may rely on `opts.rolling` being undefined | Search dependents, and keep the option's public shape unchanged |

Riskiest: #1, the silent breaking default change, which alters behavior for every existing deployment without any code change.
