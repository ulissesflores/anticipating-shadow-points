Right now `app/routes/join.tsx` logs a user in as soon as their account is created. The plan below changes sign-up to send a verification email instead, and the user only gets a session after they click the link. I haven't edited any repo files. The plan is saved at `claude-home/plans/require-new-users-to-splendid-pearl.md`.

**Assumptions**
- This applies to new users only. Existing users are marked as verified when the migration runs.
- Email goes through a provider's HTTP API called with plain `fetch`, so no new SDK. In dev and tests, the mock server in `mocks/index.js` catches the call.
- Links last 24 hours, work once, and can be resent. Clicking one logs the user in and sends them to `/notes`.
- There's no "change email" feature, so it's out of scope.

**Plan**
1. **Database.**
   - Add `User.emailVerifiedAt DateTime?`.
   - Add a new `EmailVerificationToken` table: `tokenHash` (unique), `userId` (deleted with the user), `expiresAt`, `createdAt`.
   - The migration also runs `UPDATE "User" SET "emailVerifiedAt" = "createdAt"` so current users aren't locked out. On Fly this runs automatically through `release_command`.
2. **Sending email.** New `app/email.server.ts` with a `sendEmail()` function. It needs three new settings: `EMAIL_API_KEY`, `EMAIL_FROM` and `APP_URL`. Build links from `APP_URL`, not the incoming `Host` header, so a forged header can't change the link.
3. **Token helpers** in `app/models/user.server.ts`.
   - Create a token: generate 32 random bytes and store only their sha256 hash. Delete the user's older tokens.
   - Use a token: in one transaction, check it hasn't expired, set `emailVerifiedAt`, and delete the user's tokens.
4. **Sign-up** (`join.tsx`): create the user, send the link, and redirect to a "check your inbox" page without logging them in. If someone signs up again with an unverified email, resend the link.
5. **Login** (`login.tsx`): if the password is right but the email isn't verified, refuse with "Please verify your email" and offer a resend. This message only shows after a correct password, so it doesn't reveal which emails exist.
6. **New pages.**
   - `verify-email.tsx`: opening the link only shows a "Confirm email" button. Pressing it uses the token and logs the user in, with redirects passed through the existing `safeRedirect`. Doing this on a button press stops mail scanners from using up the token just by fetching the link.
   - `verify-email.sent.tsx`: the "check your inbox" page.
   - `verify-email.resend.tsx`: always returns the same generic message and is rate-limited (no more than once a minute, plus an hourly cap).
7. **Backstop:** `requireUser` and `requireUserId` in `app/session.server.ts` log out any unverified user.
8. **Seed data and tests.**
   - Mark the seed user `rachel@remix.run` and Cypress test users (`cypress/support/create-user.ts`) as verified, or `cy.login()` will break.
   - The mock email handler writes each email to `mocks/.emails/`, which is git-ignored.
   - Rewrite the Cypress sign-up test to read the link from that file and click through. Add a test that login is refused before verifying.
   - Add unit tests for token expiry and single use.

**How to check it works:** run `npm run setup` and `npm run dev`, then:
- Sign up and confirm you are not logged in.
- Log in before verifying and confirm it's refused.
- Click the link, press confirm, and confirm you land on `/notes`.
- Reuse the link and confirm it fails; do the same with an expired one.
- Confirm `rachel@remix.run` can still log in.

Finally, run `npm run validate`, then deploy to staging to test real email delivery (the sending domain needs SPF/DKIM set up).

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | Login now requires `emailVerifiedAt`, which is empty for everyone today | Backfill in the migration; check the seed user can still log in |
| 2 | Emails not delivered (spam, provider down, bad settings) | No email code exists yet, so the whole sign-up flow depends on new setup | SPF/DKIM, check settings at startup, resend button, log send failures |
| 3 | Mail scanners use up the link | Corporate mail filters fetch links before the user clicks | Token is only used when the confirm button is pressed |
| 4 | Sign-up form used to spam people with emails | Join and resend now send mail to any address typed in | Rate limits; generic responses |
| 5 | Someone claims an address before its owner | Anyone can register an address they don't own; the owner then can't sign up | Re-sign-up resends the link and old tokens are cancelled; email says "ignore if this wasn't you" |
| 6 | Cypress and seed data break | `cy.login()` and the smoke test assume instant access | Mark test users verified; the mock captures emails for the new test |
| 7 | Accounts created mid-deploy | Fly's rolling deploy runs the migration while old servers can still create users | Re-run the backfill after deploy, or accept a small number of affected users |
| 8 | Token leaks or guessing | Raw tokens in the database or logs would let someone verify an account | Store only the hash, 32 random bytes, 24h expiry, single use |
| 9 | Link points to an attacker's site | Building the link from the `Host` header lets a forged request change it | Use `APP_URL` only |
| 10 | Extra database load per request | The `requireUser` backstop adds a check to every protected page | Store the verified flag in the session at login |

Riskiest: #1. A missing or broken backfill would lock every existing user out at once.
