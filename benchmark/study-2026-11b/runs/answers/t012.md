## What's already there
Changing an article's title already changes its slug. `ArticleUpdate` (`articles/routers.go:152-174`) builds a new slug from the title, makes it unique with `makeUniqueSlug` (`articles/models.go:299`), and retries if another request takes the same slug first. **The missing part is keeping old links working.** Every handler looks up articles with `FindOneArticle(&ArticleModel{Slug: slug})`, so after a rename the old slug returns 404. The work is to keep a history of slugs and look it up when the current slug doesn't match.

## Ways this could go wrong
1. **Someone takes over an old link.** `makeUniqueSlug` only checks the `articles` table. If the article "go-tips" is renamed and someone then publishes a new "Go Tips", the new article gets `go-tips` and shared links open the wrong article.
2. **Two tables can't enforce uniqueness together.** If current slugs stay in `articles` and old ones go in a separate table, the database can't stop the same slug from being in both. Two requests at the same moment could both claim it.
3. **Half-finished renames.** `articleModel.Update` runs outside a transaction. If saving the old slug and changing the article's slug are separate writes, one can succeed without the other: you lose the alias or end up with a stray row.
4. **Renaming back to an earlier title.** Going A → B → A must give the article `a` again, not `a-2`. Its own old slug shouldn't count as taken.
5. **Chains of renames.** A → B → C must keep both `a` and `b` working. Pointing old slugs at the article's ID avoids chains; pointing them at the next slug creates them.
6. **Deleted articles.** Articles are soft-deleted. An old slug must not bring back a deleted article, and it should stay reserved, as `makeUniqueSlug` already does for soft-deleted rows.
7. **Too many lookups.** If every handler checks the current slug, then the history, then loads the article, a miss can cost three queries. That undoes the N+1 query work in #49.
8. **API spec suite.** The RealWorld hurl and bruno tests check what PUT returns. A redirect response or a changed response shape could fail #57's spec-compliance work.
9. **Existing data and test setup.** Current articles have no history rows. `hello.go` and `articles/unit_test.go:339` must create the new table, or lookups fail.
10. **Writes through an old slug.** If PUT, DELETE, favorite or comments only accept the current slug, an author with an old tab open gets 404s. If they also accept old slugs, the permission checks must use the article that was found, not the slug in the URL. `ArticleDelete` currently deletes by slug again at `routers.go:207`.

## Assumptions
- "Shared links" means front-end URLs like `/article/<slug>`. The front end calls `GET /api/articles/<slug>`, so the API has to resolve old slugs.
- An old slug returns **200 with the article**, and its body includes the current `slug`, so the front end can update its URL. I'm avoiding 301 redirects because of possible cross-origin (CORS) and auth-header problems and because they could break the spec suite.
- Old slugs never expire and are never given to another article.

## Plan
1. **One table for every slug.** Add `ArticleSlugModel { gorm.Model; Slug string \`gorm:"uniqueIndex"\`; ArticleID uint \`gorm:"index"\` }` in `articles/models.go`. It holds both current and old slugs, so a single unique index covers risks 1 and 2.
2. **Migration and backfill.** In `hello.go` and the articles test setup, call `AutoMigrate(&ArticleSlugModel{})`. Then add a slug row for each existing article that doesn't have one.
3. **Uniqueness check.** Change `makeUniqueSlug` to check `ArticleSlugModel` with `Unscoped`. Give it the article ID, so a slug that already belongs to that article counts as free (risk 4).
4. **Create.** In `ArticleCreate`, insert the article and its slug row in one transaction. Keep the existing retry on `gorm.ErrDuplicatedKey`.
5. **Rename.** In `ArticleUpdate`, use `db.Transaction`: insert the new slug row unless it already belongs to this article, then update `articles.slug`. Old rows stay, all pointing at the same article ID (risks 3 and 5).
6. **Lookup.** Add `FindArticleBySlug(slug) (ArticleModel, error)`. It tries `FindOneArticle` first, so the common case is still one query. On a miss it reads `ArticleSlugModel` and loads the article by ID, which skips deleted articles (risks 6 and 7). Use it in all eight slug handlers in `routers.go`. Change `ArticleDelete` to delete by `articleModel.ID`.
7. **Tests** (`articles/unit_test.go`):
   - after a rename, an old slug returns 200 with the new slug;
   - A → B → C, and A → B → A;
   - a new article with a retired title gets a `-2` slug;
   - after a delete, the old slug returns 404;
   - PUT and favorite work through an old slug and still check the author.

**Verification:** run `go build ./...`, `go test ./...`, `bash scripts/run-spec-tests.sh hurl` and `bash scripts/run-spec-tests.sh bruno`. Then a manual curl test: create an article, rename it, `GET` the old slug, and check the body shows the new slug.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | A new article takes a retired slug | `makeUniqueSlug` only checks `articles` | One `ArticleSlugModel` table with a unique index; check it with `Unscoped` |
| 2 | The same slug ends up in two places | Two tables can't share a unique index; the code already retries on races | Keep every slug in one table and keep the `ErrDuplicatedKey` retry |
| 3 | Partly saved rename | `ArticleModel.Update` runs outside a transaction | Insert the slug row and update the article in one `db.Transaction` |
| 4 | Renaming back gives `a-2` | The uniqueness check doesn't know which article owns a slug | Pass the article ID; its own slugs count as free |
| 5 | Old slug brings back a deleted article | Articles are soft-deleted | Load the article by ID with normal scoping; keep the slug reserved |
| 6 | Wrong delete or permission bypass via old slug | `ArticleDelete` deletes by the URL slug again | Use `articleModel.ID` after the lookup in every write handler |
| 7 | Spec suite breaks | #57 pins hurl and bruno compliance | Return 200 instead of a redirect; run both suites |
| 8 | Existing articles have no slug rows | Created before the table existed | Backfill at startup; migrate the table in tests too |
| 9 | Extra queries on every request | #49 removed N+1 queries | Check the current slug first; history only on a miss |
| 10 | Chains of renames break | Old slugs pointing at the next slug | Point every slug at the article ID |

Riskiest: #1, a new article taking a retired slug, because shared links would silently open someone else's article instead of returning a 404.
