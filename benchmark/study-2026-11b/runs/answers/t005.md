## What the code does today
This is the Remix "Blues stack" (Prisma, Postgres, cookie sessions, deployed on Fly).
- **`prisma/schema.prisma`**: `User` has only `id`, `email` and timestamps. Nothing records whether an email is verified.
- **`app/routes/join.tsx:62-69`**: right after `createUser`, it calls `createUserSession`, so a new user is logged in immediately.
- **`app/routes/login.tsx:49-63`**: it checks `verifyLogin` (password only), then creates a session.
- **`app/session.server.ts`**: the cookie stores only `userId`. `requireUserId` and `requireUser` never look at the user's state, so any existing cookie stays valid.
- **No way to send email**: there's no mail package, and `.env.example` has only `DATABASE_URL` and `SESSION_SECRET`. `mocks/index.js` uses MSW, so a mail provider's HTTP API can be mocked.
- **Other callers of `createUser` or user creation**: `cypress/support/create-user.ts` (used by `cy.login()`) and `prisma/seed.ts`. The e2e test `smoke.cy.ts` expects to be logged in right after signing up.

## Ways this could go wrong
1. **Locking out existing users.** If the new `emailVerifiedAt` column starts as null, every current user is suddenly "unverified" and can't log in.
2. **The check only runs at login.** Session cookies issued before the change, and the one `join` issues today, would bypass it. `requireUser` and `requireUserId` never check verification.
3. **Token security.** Guessable or reusable tokens, tokens that never expire, or tokens stored in plaintext would let an attacker verify someone else's email or take over the account.
4. **Revealing who has an account.** A different error for "unverified" versus "wrong password", or a resend endpoint that answers differently, lets someone test which emails are registered. Showing "please verify" only after the password checks out is acceptable.
5. **Email fails to send.** The user row gets created but the email never arrives, so the address is stuck: signing up again says "already exists". Users need a way to resend.
6. **Resend becomes a spam relay.** An unthrottled resend endpoint can be used to flood any inbox and run up provider costs.
7. **Broken tests and seed.** `cy.login()` and the seed user would come out unverified, and the signup e2e flow changes. Tests have no inbox to read the token from.
8. **Link problems.** The link needs a correct absolute URL (an `APP_URL` setting on Fly). Email security scanners often open links automatically, so a GET request that verifies right away can be triggered by the scanner rather than the user.
9. **Losing the `redirectTo` destination.** The link sends the user back from email, so where they were originally going should be carried along or dropped deliberately.
10. **Migration order on Fly.** Migrations run at deploy. If the code that enforces verification goes live before the backfill runs, existing users get locked out briefly.

## Assumptions
- "New users" means accounts created after this ships. Existing users count as already verified (backfilled).
- An unverified user can't get any session at all, rather than a limited one.
- Verification works through a single-use link that expires after 24 hours and is sent through an email provider's HTTP API (for example Resend or Postmark). In development and tests, the link is logged to the console or mocked instead of sent.
- The only password-change flow is the one that exists, so there's no reset flow to integrate.

## Plan
1. **Schema and migration**
   - Add `emailVerifiedAt DateTime?` to `User`.
   - Add a `VerificationToken` model: `tokenHash` (unique), `userId` (cascade delete) and `expiresAt`.
   - In the same migration, backfill: `UPDATE "User" SET "emailVerifiedAt" = "createdAt"`.
2. **`app/models/user.server.ts`**
   - `createVerificationToken(userId)`: generate a random 32-byte token, store its SHA-256 hash, and return the raw token.
   - `consumeVerificationToken(raw)`: in one transaction, look up the hash, check it hasn't expired, set `emailVerifiedAt`, and delete the user's tokens.
   - `verifyLogin` keeps its current behaviour and returns the user, which now includes `emailVerifiedAt`.
3. **New `app/email.server.ts`**
   - `sendVerificationEmail(email, url)` calls the provider's API, configured by `EMAIL_API_KEY` and `APP_URL` in the environment and `.env.example`.
   - When no key is set, it logs the link instead.
4. **`join.tsx`**
   - After `createUser`, create a token and send the email, then redirect to `/verify-email/sent` instead of calling `createUserSession`.
   - If an unverified user signs up again with the same email, resend the link instead of showing "already exists".
5. **`login.tsx`**
   - After the password checks out, if `emailVerifiedAt` is null, return a generic "Please verify your email" message with a resend option and create no session.
6. **New routes**
   - `verify-email.$token.tsx`: a GET shows a confirm button, and the POST does the verification (so scanners can't trigger it). Afterwards it either creates the session or sends the user to `/login?verified=1`.
   - `verify-email.sent.tsx`: a "check your inbox" page with a resend form, limited per email (for example one send per 60 seconds, enforced by token `createdAt`) and always giving the same response.
7. **`session.server.ts`**: make `requireUser` reject unverified users as a second safeguard. A user record is already loaded there, so it costs nothing extra.
8. **Tests and seed**
   - In `prisma/seed.ts` and `cypress/support/create-user.ts`, set `emailVerifiedAt: new Date()`.
   - Update `smoke.cy.ts`: sign up, see the "check your inbox" page, then verify through a test-only helper script (like `delete-user.ts`) that marks the user verified or prints a fresh link.
   - Add Vitest unit tests for token expiry and single use.

## How to check it
Run `npm run validate`, which covers unit tests, lint, typechecking and the e2e run with mocks. Then check by hand:
- Sign up and confirm you're not logged in.
- Logging in shows the "verify" message.
- The link from the log verifies the account. Reusing it fails, and so does an expired one.
- The seeded `rachel@remix.run` can still log in.
- Run the migration against a copy of production data and confirm the backfill left no user with a null `emailVerifiedAt`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | `User` has no verified field; a new column would be null for everyone | Backfill `emailVerifiedAt = createdAt` in the same migration |
| 2 | Check skipped by existing sessions | `requireUser` only reads `userId` from the cookie; `join` logs in immediately | Remove the session from `join`; check verification in `requireUser` too |
| 3 | Weak or reusable tokens | No token setup exists yet | 32 random bytes, stored hashed, single use, 24h expiry |
| 4 | Revealing which emails exist | Login and join errors are specific | Show "verify" only after the password checks out; resend always answers the same |
| 5 | Stuck accounts after a failed send | No mail setup; join currently errors on duplicate emails | Resend flow, and re-signup of an unverified email resends the link |
| 6 | Resend used for inbox flooding | New endpoint that anyone can call | Limit per email and per IP |
| 7 | e2e, seed and `cy.login()` break | They create users with no verification step | Mark test and seed users verified; add a helper for e2e |
| 8 | Link scanners or wrong URL | Fly host isn't set as config | Confirm with a POST; add `APP_URL` setting |
| 9 | Deploy order on Fly | Migrations run at release | Put the backfill in the same migration as the column |
| 10 | Mail provider secret missing in prod | `.env.example` has only two variables | Fail at startup in production; log the link in development |

Riskiest: #1, locking out every existing user because they would all count as unverified unless the migration backfills `emailVerifiedAt`.
