I've written a plan to change the default signing digest from SHA-1 to SHA-256 so that existing tokens still load. Nothing in the repo was edited; the plan is in `claude-home/plans/change-the-default-signing-majestic-cat.md`.

**Assumptions** (non-interactive run, so I didn't ask):
- The change ships in the unreleased 2.3.0, which already contains breaking removals.
- Tokens signed with SHA-1 by older versions must keep loading through `Serializer`.
- Applications keep the same secret key.

**What makes this risky:** this project has tried this before. 1.0.0 switched the default to SHA-512 and was pulled from PyPI because existing signatures stopped verifying (`CHANGES.rst:115-124`). 1.1.0 switched back and added `fallback_signers` so the default could change later. Also, the digest isn't only used for the HMAC: the default key derivation hashes the secret with it too (`signer.py:200-209`). Swapping the HMAC alone isn't enough, so the old-token fallback has to use SHA-1 for both steps.

**Ways it could go wrong:**
1. Every existing session cookie, password-reset link and email-confirmation link fails to verify, unless a SHA-1 fallback is added.
2. People who call `Signer.unsign` directly don't get the `Serializer` fallback, so their old tokens break.
3. The default is set in two places (`HMACAlgorithm` at `signer.py:54` and `Signer` at `signer.py:120`). Changing only one leaves the code inconsistent.
4. During a rolling deploy, servers still on the old version reject SHA-256 tokens from upgraded servers.
5. The signature grows from 27 to 43 base64 characters. That can exceed cookie limits, URL limits or database column sizes.
6. Tests that check against the private `_lazy_sha1` name (`test_iter_unsigners`), plus downstream code that may import it, break if it's renamed or removed.
7. A permanent SHA-1 fallback means SHA-1 is accepted indefinitely. Without a removal date it never goes away.
8. Libraries built on this one that pin SHA-1 themselves won't change, which may confuse users. I believe Flask's session cookie does this, but that's from memory and not checked here.

**Plan:**
- **`signer.py`:** set both `default_digest_method` attributes to SHA-256 and keep `_lazy_sha1` as it is.
- **`serializer.py:101`:** set `default_fallback_signers = [{"digest_method": _lazy_sha1}]`, with a stated removal version.
- **Tests:**
  - Update `test_digests` to the SHA-256 value and keep the SHA-1 test value.
  - Update `test_iter_unsigners` to expect SHA-256.
  - Add a test that an old SHA-1 token loads, and that the timed and URL-safe serializers sign with SHA-256.
- **Docs:** update `concepts.rst:137-155`, the `serializer.rst` example, and add a `CHANGES.rst` entry with migration notes.
- **Check:** run pytest, mypy/pyright and the docs build, then sign tokens with 2.2.0 and load them with the new code.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | All existing tokens and cookies stop verifying | Already happened with 1.0.0, which was pulled from PyPI | Default SHA-1 entry in `default_fallback_signers` |
| 2 | Fallback that only swaps the HMAC | Key derivation also hashes with `digest_method` | Use a `{"digest_method": sha1}` fallback; add a test with an old token |
| 3 | Direct `Signer` users get no fallback | Fallback only exists in `Serializer` | Changelog note: pin SHA-1 or verify in two passes |
| 4 | Only one default gets changed | Set separately at `signer.py:54` and `:120` | Change both; test `HMACAlgorithm()` on its own |
| 5 | Mixed versions during a rolling deploy | Old servers can't read SHA-256 tokens | Document: upgrade every node before relying on it |
| 6 | Longer tokens | Signature goes from 27 to 43 characters | Changelog note; check cookie and URL sizes |
| 7 | Tests and imports break | Tests check against `_lazy_sha1` | Keep `_lazy_sha1`; update assertions |
| 8 | SHA-1 accepted forever | The fallback has no end date | Give a removal version in the docs |
| 9 | Downstream behaviour differs | Libraries may pin SHA-1 themselves | Explain the scope in the changelog |

Riskiest: #1, every existing signed token stops working at upgrade. This exact change already forced a release to be pulled from PyPI.
