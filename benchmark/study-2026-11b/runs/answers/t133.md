## What exists today

- **No vet and no time on a visit.** `Visit` (`owner/Visit.java`) has only `date` (a day, no time), `description` and `pet_id`. The `visits` table matches this in all three schemas (`db/h2`, `db/mysql`, `db/postgres`). So "same vet at the same time" can't be expressed yet.
- **How booking works now.** `VisitController.processNewVisitForm` checks the visit is in the future, then calls `owners.save(owner)` and relies on the cascade. There is no service layer and no `@Transactional`.
- **No login.** There's no Spring Security dependency, so anyone can open `/owners/{id}/pets/{id}/visits/new` for any owner.
- **No migration tool.** `ddl-auto=none`. The schema comes from `schema.sql`: H2 drops and recreates tables on every start, while MySQL and Postgres use `CREATE TABLE IF NOT EXISTS`, so new columns never reach an existing database. There's no Flyway or Liquibase.
- **Ids are blocked from form binding.** `@InitBinder` blocks `id` and `*.id`, so a form field named `vet.id` would be silently dropped.
- **Translations are checked by a test.** `I18nPropertiesSyncTest` requires every new message key in all 11 `messages_*.properties` files.

## Assumptions (instead of asking)

1. **Fixed slots.** Visits use fixed 30‑minute slots during clinic hours (say 09:00–17:00). "Same time" means the same vet, date and slot start. This lets a plain unique constraint enforce the rule on H2, MySQL and Postgres. Visits of different lengths would need overlap checks, which only Postgres can enforce in the database.
2. **Login is out of scope.** "Online" means the existing public visit form gains a vet and a time slot. The missing login is flagged as a risk below, not solved here.
3. **Any vet can see any pet.** No matching on specialty, and no cancelling or rescheduling in this change.
4. **Old visits stay valid.** Existing rows keep `vet_id` and `visit_time` as NULL. All three databases allow several NULLs under a unique constraint.

## Plan

1. **Database**
   - Add `vet_id` (foreign key to `vets`) and `visit_time` to `visits` in all three `schema.sql` files.
   - Add `UNIQUE (vet_id, visit_date, visit_time)`.
   - Write separate one-off `ALTER TABLE` scripts for MySQL and Postgres databases that already exist.
   - Update the three `data.sql` files where needed.
2. **Model**
   - `Visit` gets `@ManyToOne Vet vet` and `LocalTime time`.
   - Server-side checks: the vet is set, and the time is on the 30‑minute grid and within opening hours. Without the grid check, 10:07 and 10:00 would both pass the unique constraint even though they overlap.
3. **Binding**
   - Add a `VetFormatter` modelled on `PetTypeFormatter` and bind the form field `vet` (not `vet.id`).
   - Load vets through `VetRepository.findAll()`. Its `@Cacheable("vets")` is fine for the vet list, but availability must never be cached.
4. **Controller**
   - Inject `VetRepository`.
   - Offer only free slots in the form: a new query lists booked slots per vet and date.
   - On submit, still treat the database constraint as the real guard. Catch `DataIntegrityViolationException` from `owners.save(owner)` (Spring Data's `save` commits inside its own transaction, so the error surfaces there). Show a field error like "slot just taken" and re-display the form instead of a 500 error.
5. **Template and translations**
   - Add vet and slot selects to `createOrUpdateVisitForm.html`, and show vet and time in the visit lists (old rows have none).
   - Add the new keys to every `messages_*.properties` file.
6. **Tests**
   - `VisitControllerTests`: mock `VetRepository`; cover off-grid time, outside opening hours, unknown vet, and a duplicate turning into a form error.
   - `ClinicServiceTests`: saving a duplicate fails.
   - A test where two threads book the same slot at once, run against the MySQL/Postgres Testcontainers setup.

**Verification:** run `./mvnw test`, including `MySqlIntegrationTests` and the Postgres equivalent. Then by hand in the running app: book the same vet and slot from two browser tabs; the second should get a friendly error and the database should hold exactly one row.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Two people book the same slot at the same moment | The controller checks first and saves later; nothing locks in between | Unique constraint on (vet, date, time) and catch the duplicate error |
| 2 | Visits of different lengths overlap anyway | A unique constraint only matches identical start times | Fixed slots, checked on the server |
| 3 | Existing MySQL/Postgres databases break | `IF NOT EXISTS` skips new columns and there are no migrations, so every owner page fails with a SQL error | Ship `ALTER` scripts, or add Flyway |
| 4 | The three schema files drift apart | H2, MySQL and Postgres DDL are maintained by hand | Change all three; run the container tests in CI |
| 5 | The vet field is silently ignored | `*.id` is blocked from binding | Bind `vet` through a `VetFormatter` |
| 6 | Bookings for other people's pets, or spam that fills a vet's calendar | There is no login; URLs use guessable ids | Add a login and ownership check before going public; limit request rates |
| 7 | Duplicate shows as a 500 page | The error only appears when `save` commits | Catch it and show it as a form error |
| 8 | Old visits have no vet or time | Existing rows are NULL | Allow NULL; templates handle missing values |
| 9 | Wrong day or slot because of time zones | `LocalDate.now()` uses the server's zone | Set an explicit clinic time zone |
| 10 | Build fails on translations | `I18nPropertiesSyncTest` | Add keys to all 11 files |

Riskiest: #1, two people booking the same slot at once. A check in Java alone will let duplicates through under concurrent requests; only the database unique constraint, with the error handled, actually prevents them.
