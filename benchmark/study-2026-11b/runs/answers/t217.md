# Plan: tenant-scope all to-do lists and items

## Context and assumptions

This is the Jason Taylor Clean Architecture template. It uses .NET with EF Core, MediatR handlers and ASP.NET Identity, and has Angular and React clients. `TodoList` and `TodoItem` derive from `BaseAuditableEntity`. Handlers use `IApplicationDbContext` directly, and nothing filters by user or company today.

I haven't edited any files. I also haven't read the handlers beyond `GetTodos` and `DeleteTodoItem`, the web endpoints, or the tests. The plan assumes the other handlers follow the same pattern.

I assumed the following instead of asking:
- A "tenant" is a company. Each user belongs to exactly one tenant.
- Tenant identity comes from an authenticated claim, never from client input.
- There is no existing production data. The initialiser calls `EnsureDeletedAsync` and `EnsureCreatedAsync` and the repo has no migrations folder, so a schema reset is acceptable. If real data exists, add a backfill step.
- Shared database and shared schema, with a `TenantId` column. This is the simplest option that fits the template. Database-per-tenant is out of scope.
- A tenant can't be changed after creation. A missing tenant means the request is denied. It does not mean "see everything".

## Steps

1. **Domain**
   - Add `Tenant` (Id, Name) in `Domain/Entities`.
   - Add `ITenantOwned { Guid TenantId }`, or put `TenantId` on a new `BaseTenantEntity : BaseAuditableEntity`.
   - Make `TodoList` and `TodoItem` implement it. Items carry their own `TenantId` and don't inherit it from the list, which allows a DB-level check and an index.

2. **Identity and tenant resolution**
   - Add `TenantId` to `ApplicationUser`.
   - Emit a `tenant_id` claim at sign-in. A claims factory over `UserClaimsPrincipalFactory` fits here.
   - Add `Guid? TenantId` to `IUser`, or a new `ITenantProvider`. Implement it in `Web/Services/CurrentUser.cs` by reading the claim.
   - Registration needs a rule for how a user gets a tenant, for example invite or company creation. Put the placeholder in `RegisterPage` and the Identity API endpoints.

3. **Persistence (`Infrastructure`)**
   - Add a `TenantId` column and index to `TodoListConfiguration` and `TodoItemConfiguration`. Make it composite with the foreign key where practical.
   - Add a global query filter on both entities: `e.TenantId == _tenantProvider.TenantId`. Inject the provider into `ApplicationDbContext` and re-evaluate it per request.
   - Add a `TenantInterceptor` next to `AuditableEntityInterceptor`. On `Added`, it stamps `TenantId` from the provider. On `Modified`, it rejects any change to `TenantId`. Register it in `DependencyInjection.cs`.
   - Update the seeder (`ApplicationDbContextInitialiser`) to create two demo tenants, with users and data in each.

4. **Application layer**
   - Handlers for `GetTodos` and for the todo item and list commands (create, update, delete) need no changes if the filter works. `FindAsync` ignores global filters on the primary-key lookup only in some cases, so switch the update and delete handlers to `FirstOrDefaultAsync(x => x.Id == id)`. This guarantees a cross-tenant ID returns 404 and not data.
   - `CreateTodoItem` must verify that `ListId` belongs to the caller's tenant. The filter covers this once the lookup goes through the filtered query.
   - Add an `[Authorize]` check so a request with no tenant claim fails with `ForbiddenAccessException`, in `AuthorizationBehaviour`.

5. **Web and clients**
   - Do not add `TenantId` to DTOs or request bodies. Regenerate the NSwag clients only if the contracts change, which they shouldn't.
   - Domain event handlers and anything running outside an HTTP request (background jobs, `LogTodoItemCompleted`) need an explicit tenant context. Otherwise the filter returns nothing.

6. **Tests**
   - Update the functional-test harness under `tests/Application.FunctionalTests` to run as a user with a tenant.
   - Add isolation tests. Tenant A cannot list, read, update or delete tenant B's lists or items. Creating an item in B's list from A fails. A user with no tenant is denied. A cross-tenant ID returns 404.
   - Add an architecture-style test that every `ITenantOwned` entity has a query filter.

## Verification

- Run `dotnet build` and `dotnet test` on the solution.
- Run the new isolation tests.
- Start the AppHost, log in as a seeded user in each of the two tenants, and confirm each sees only its own data.
- Try a direct API call using an ID from the other tenant and confirm it gets 404.
- Inspect the generated SQL (EF logging) to confirm the tenant predicate is on every todo query.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Filter bypassed by `IgnoreQueryFilters` or raw SQL | Handlers use `DbSet` directly with no repository layer | Ban the call in review or an analyzer, and add isolation tests |
| 2 | Tenant claim is missing or stale | Identity is cookie or bearer, and the claim is set at sign-in | Deny when the claim is absent; refresh the claim when the tenant changes |
| 3 | `FindAsync` skips the filter | Update and delete handlers use `FindAsync` | Use filtered `FirstOrDefaultAsync` and test cross-tenant IDs |
| 4 | Writes land in the wrong tenant | Interceptor and `CreateTodoItem` accept a `ListId` from the client | Stamp `TenantId` in the interceptor and validate the parent list's tenant |
| 5 | Background work has no tenant | Domain events and the initialiser run outside HTTP | Pass an explicit tenant context and fail closed when it's missing |
| 6 | Existing data can't be migrated | No migrations; the DB is dropped on startup | Confirm no real data, or add a backfill and a real migration |
| 7 | Filter cached across tenants | A filter capturing a scoped value must read it per request | Reference the provider on the context instance, and test two tenants in one process |
| 8 | Query performance degrades | Every query gains a `TenantId` predicate | Add composite indexes starting with `TenantId` |
| 9 | Tests and clients break | Functional tests assume a single user with no tenant | Update the test harness first; keep DTO contracts unchanged |

Riskiest: #1, a bypass of the query filter, because it silently leaks one company's data to another and nothing else would catch it.
