## What exists today (project/)
- **Model**: `app/models/tortoise.py` defines `TextSummary`. It has no explicit primary key, so Tortoise adds `id SERIAL`. The only migration is `migrations/models/0_20250421234125_init.py` (aerich).
- **API**: `app/api/summaries.py` has `/{id}/` routes for GET, PUT and DELETE with `id: int = Path(..., gt=0)`. POST and DELETE return `SummaryResponseSchema {id: int, url}` from `app/models/pydantic.py`. GET and PUT return `SummarySchema`, which `pydantic_model_creator` builds automatically.
- **Internal uses of the int id**: `crud.py` (`filter(id=...)`, and `post()` returns `summary.id`) and `summarizer.generate_summary(summary_id: int, ...)`, which runs as a background task.
- **Tests**: `tests/conftest.py` builds the schema with `generate_schemas=True`, so migrations are never tested. Both test files check exact 422 error bodies for `id=0` (`loc: ["path","id"]`), and the unit tests hard-code `"id": 1`.
- **Deploy**: Heroku via `release.sh`. Neither `entrypoint.sh` nor the release step runs `aerich upgrade`.

## Assumptions
1. "Existing clients" means anything that reads `id` as an integer from responses and calls `/summaries/{int}/`. Changing the type of `id` in place would break them, so the old contract stays exactly as it is.
2. The goal is ids that can't be guessed or enumerated. The integer path is kept only for a deprecation window, not forever.
3. Postgres is version 13 or later, so `gen_random_uuid()` is built in. If it's older, the migration needs `pgcrypto`.
4. Only API-facing ids change. The internal primary key and foreign-key-style uses stay integers.

## Ways this could go wrong (checked before planning)
- **Changing the type of `id` breaks clients.** Clients parse it as an int, store it in int columns, and build URLs from it. Switching `id` to a string in `/summaries/` fails all of them.
- **Swapping the primary key is risky.** Turning the SERIAL PK into a UUID PK means rewriting the table and breaks `summarizer`, crud and anything that joins on the int id.
- **Backfill and defaults.** If you add the column `NOT NULL` without a backfill, the migration fails on existing rows. If the default is only set in Python (`uuid.uuid4`), rows inserted by old app instances during a rolling deploy get no uuid.
- **Deploy order.** No migration step exists in the pipeline. New code that reads a missing `uuid` column causes 500 errors on every request.
- **Tests miss migration bugs.** `generate_schemas=True` builds the schema straight from the models, so the tests pass even with a broken migration.
- **Ambiguous path parsing.** A single route typed `Union[int, UUID]` misreads a 32-digit, all-numeric, unhyphenated UUID as an int. It also changes the 422 error bodies that clients and tests match exactly.
- **Ordering.** Clients may expect lists to come back in ascending `id` order. `get_all()` has no `order_by`, and UUIDv4 values have no meaningful order.
- **Enumeration stays possible.** Keeping integer lookups means ids can still be guessed until v1 is shut off.
- **Background tasks.** `generate_summary` must keep receiving the internal int (or switch to the uuid) consistently. Otherwise summaries are never filled in, and nothing reports the error.

## Plan
1. **Model**: add `uuid = fields.UUIDField(unique=True, default=uuid.uuid4)` to `TextSummary` and keep the int `id` as the internal primary key.
2. **Migration** (`aerich migrate`, then edit the generated file by hand):
   - `ADD COLUMN uuid UUID DEFAULT gen_random_uuid()` (nullable at first)
   - `UPDATE ... SET uuid = gen_random_uuid() WHERE uuid IS NULL`
   - `SET NOT NULL`
   - add a unique index
   - write a real `downgrade` that drops the column

   The database-side default covers rows inserted by old app instances during the rollout.
3. **v1 (`/summaries/`) stays as it is**:
   - `id: int`, the same paths, and the same 422 bodies.
   - Responses gain a `uuid` field. Adding a field doesn't break existing clients, and it lets them map old ids to new ones.
   - Responses add `Deprecation` and `Link` headers pointing to v2.
4. **v2 (`/v2/summaries/`)**:
   - A new router whose response schemas put the UUID in `id` and leave the int out.
   - Path parameter typed `id: UUID`, so there's no union ambiguity.
   - The list endpoint orders by `created_at`.
   - New CRUD helpers (`get_by_uuid` and similar) reuse the existing `TextSummary` queries.
5. **Internals**: keep `summarizer.generate_summary` and the crud mutations keyed on the int primary key. v2 converts uuid to the internal id once, at the edge.
6. **Deploy**: add `aerich upgrade` as a release step and run it before the new code goes live. Release in two phases: migration first, then code.
7. **Tests**:
   - Keep every existing v1 test passing unchanged.
   - Add v2 tests: create, get, list, update and delete by uuid; bad UUID returns 422; unknown uuid returns 404.
   - Check that a v1-created item is reachable through v2 using its `uuid`.
   - Add a migration test that runs `aerich upgrade` against a database seeded with old-style rows.

## Verification
- `docker compose exec web python -m pytest` passes for both v1 and v2.
- On a database copy with existing rows, run `aerich upgrade` and confirm `SELECT count(*) FROM textsummary WHERE uuid IS NULL` returns 0.
- Use `curl` to check that a v1 response still has an int `id` plus a `uuid`, and that v2 `GET /v2/summaries/{uuid}/` returns the same record.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Changing `id` to a UUID in place | Clients parse `id` as an int and build `/summaries/{int}/` URLs | Leave v1 unchanged; put UUID `id`s in `/v2` |
| 2 | Code deployed before the migration | Heroku release never runs `aerich upgrade` | Add a migrate step; release migration before code |
| 3 | Rows left with a NULL uuid | The default is Python-side only, and old instances keep inserting during rollout | DB default `gen_random_uuid()`, backfill, then NOT NULL |
| 4 | Migration bugs not caught by tests | conftest uses `generate_schemas=True` | Add a test that runs `aerich upgrade` on seeded data |
| 5 | `Union[int, UUID]` path is ambiguous | An all-digit hex UUID parses as an int; 422 bodies change | Separate routes, with one strict type each |
| 6 | Swapping the primary key | The summarizer and crud are keyed on the int PK | Keep the int PK internal; add a unique `uuid` column |
| 7 | List order changes | `get_all()` has no ordering, and UUIDs have no meaningful order | `order_by("created_at")` in v2 |
| 8 | Enumeration stays possible | Int lookups still work in v1 | Deprecation headers and a sunset date for v1 |
| 9 | Background summary never fills in | `generate_summary` is passed the id from `post()` | Keep passing the internal int; cover it with a test |
| 10 | Exact-match tests and clients break | Tests assert on full 422 bodies and `"id": 1` | Freeze the v1 contract; don't edit the existing tests |

Riskiest: #1. Changing the type of `id` in place would break every existing client right away, which is the one thing you said this change must not do.
