# Plan: UUID public IDs for the summaries API, with integer-ID compatibility

I made no edits. The repo is a FastAPI + Tortoise ORM + Aerich + Postgres app. Its only model is `TextSummary`. It has an integer `id`, which is `SERIAL` in `migrations/models/0_…_init.py`. Every route in `app/api/summaries.py` uses `id: int = Path(..., gt=0)`. `crud.py` filters by `id`, and `generate_summary(summary_id, url)` is queued with the integer.

## Assumptions
- Existing clients send integer IDs in URLs, and they read `id` from responses as an integer.
- The deployed database has real rows, so the migration must keep them.
- Postgres is version 13 or later, so `gen_random_uuid()` is built in. Otherwise the migration enables `pgcrypto`.
- No other table has a foreign key to `textsummary.id`. That is true today, since there is only one model.
- The service is deployed on its own, so the new and old code will run side by side briefly during a rollout.

## Approach
Keep the integer primary key as an internal detail and add a UUID as the public identifier. Rewriting the primary key in place is riskier and gains nothing here. Ship it in two phases so that no client breaks.

**Phase 1 (additive, non-breaking)**
1. **Model** (`app/models/tortoise.py`): add `uuid = fields.UUIDField(unique=True, default=uuid4)`. `SummarySchema` is built by `pydantic_model_creator`, so it picks up the new field automatically.
2. **Migration** (a new Aerich file next to the init migration):
   - Add the `uuid` column as nullable.
   - Backfill with `UPDATE textsummary SET uuid = gen_random_uuid()`.
   - Set the column to `NOT NULL`.
   - Create a unique index.
   - Write a real `downgrade`. The init migration's is empty.
3. **Lookup helper** in `crud.py`: `get`, `put` and `delete` take an identifier that is either an integer or a UUID. A small `parse_ref(raw: str)` returns `{"id": n}` or `{"uuid": u}`. Digits mean the legacy integer. A valid UUID string means the UUID. Anything else gives 422.
4. **Routes**: change the path parameter to `ref: str`, validated by that helper. Drop `gt=0` in favour of the helper's own checks.
5. **Responses**: keep `id` as an integer, since changing its type would break clients. Add `uuid` and mark `id` deprecated in the OpenAPI description. `SummaryResponseSchema` gets `uuid: UUID`.
6. **Background task**: keep passing the internal integer to `generate_summary`. Nothing changes there.
7. **Docs and notice**: announce the deprecation, and add a `Deprecation` header on integer-ID requests.

**Phase 2 (breaking, opt-in)**
- Add a versioned router (`/v2/summaries`) where `id` is the UUID and the integer is gone. Keep the legacy router as it is, with a published sunset date.
- Remove integer lookups only when access logs show negligible integer-ID traffic.

## Tests (`tests/test_summaries.py`, `test_summaries_unit.py`)
- Existing integer-path tests must pass unchanged. They are the compatibility proof.
- New tests:
  - GET, PUT and DELETE by UUID.
  - POST returns a `uuid`.
  - A malformed reference gives 422.
  - An unknown UUID gives 404.
  - An integer and a UUID for the same row return the same object.
- Update the unit tests that mock `crud` so they cover the new signature.
- Test the migration on a database seeded with legacy rows: every row gets a unique, non-null UUID.

## Verification
1. Run `docker-compose up`, then `aerich upgrade` on a database seeded with old rows.
2. Run the existing test suite (`pytest`) before and after, and confirm it passes both times.
3. Use `curl` against a running instance to hit `/summaries/1/` and `/summaries/<uuid>/`. Compare the responses.
4. Run `aerich downgrade` and confirm it reverses cleanly.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Changing the `id` type in responses | Clients parse `id` as an integer, so a UUID string breaks them silently | Keep `id` as an integer, add `uuid`, and flip only under `/v2` |
| 2 | Backfill and `NOT NULL` locking the table | `ALTER` plus `UPDATE` on a live Postgres table can block writes | Add nullable, backfill in batches, then add the constraint; the table is small, but rehearse on a copy |
| 3 | Old and new code running together during rollout | Old pods don't write `uuid`, so rows can end up with `NULL` | Give the column a DB default `gen_random_uuid()`, and deploy the migration before the code |
| 4 | Ambiguous or malformed identifiers | A string like `123` could be read as either type, and bad input could cause a 500 | Digits-only means integer, strict UUID parsing otherwise, and 422 on anything else |
| 5 | Sequential integer IDs stay reachable | The integer path still allows enumeration, so the security gain is partial | Treat Phase 2 removal as the real fix; consider rate limits or auth in the meantime |
| 6 | Empty or unreliable `downgrade` | The init migration's downgrade is empty, so rollback is untested | Write and test a real downgrade; take a backup first |
| 7 | Hidden integer consumers | Webhooks, logs, dashboards or other services may store integer IDs | Search logs and consumers first; keep integer lookups until traffic is near zero |
| 8 | Mocked tests hide signature changes | `test_summaries_unit.py` monkeypatches `crud`, so type changes can slip through | Update the mocks and add integration tests that use UUIDs |
| 9 | Auto-generated schema drift | `pydantic_model_creator` changes the OpenAPI output as soon as the field is added | Snapshot the OpenAPI spec and review the diff |

Riskiest: #1, changing the type of `id` in responses, because it breaks existing clients silently.
