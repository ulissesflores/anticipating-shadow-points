## Ways this could go wrong (listed before planning)
1. **Easier password spraying.** With the new default, an attacker on one IP who tries a different username each time never reaches the failure limit. Today's default blocks that IP.
2. **Silent upgrade change.** Projects that never set `AXES_LOCKOUT_PARAMETERS` get weaker protection against attacks across many accounts, with no warning. The existing check (W006 in `axes/checks.py:183-202`) stays quiet because `ip_address` is still in the nested list.
3. **Old flag gets a new meaning.** In `axes/conf.py:53-60`, `AXES_USE_USER_AGENT` (an old, deprecated setting) adds `user_agent` to the first lockout entry. If I only change the fallback, `AXES_USE_USER_AGENT=True` on its own would become username + IP + user agent. The upgrade docs (`docs/2_installation.rst:165`) promise IP + user agent.
4. **Tests break.** `tests/test_login.py` around lines 383-410 and 526-556 (`test_lockout_by_ip_*`) assume IP-only blocking. Other test files probably do too.
5. **Missing usernames.** Requests with no username store `username=None`. Then all anonymous failures from one IP share one bucket, which could be good or bad.
6. **Cache lockouts reset on upgrade.** The cache handler builds its keys from the lockout settings, so active cache lockouts disappear after deploy. Lockouts stored in the database still match, because those rows hold both username and IP.
7. **Reset tools.** Resetting by IP still works, but the docs should explain which commands release a username + IP lockout.

## Assumptions (no questions asked, since this is a non-interactive run)
- Only the default for unset projects changes. Explicit lists, callables and the deprecated flags keep their documented meanings.
- The new default is `[["username", "ip_address"]]`. A plain `["username", "ip_address"]` would mean username **or** IP, which is not what you asked for.
- This is a breaking change for 10.0.0, with a CHANGES.rst entry and an upgrade note.
- No migration is needed.

## Plan summary
1. **`axes/conf.py:37-60`:** change the fallback to `[["username", "ip_address"]]`. Keep `AXES_USE_USER_AGENT` used alone mapped to `[["ip_address", "user_agent"]]`, and fix the stale comment.
2. **Tests:** pin the existing IP-default tests with `override_settings(AXES_LOCKOUT_PARAMETERS=["ip_address"])`. Add tests for the new default:
   - same user, same IP: blocked
   - different user, same IP: allowed
   - same user, different IP: allowed
   - empty username
   - no W006 warning
3. **Docs:**
   - `docs/4_configuration.rst:93`: new default value.
   - `docs/2_installation.rst`: upgrade note on how to keep IP-only blocking.
   - `docs/5_customization.rst:181`: reword.
   - `CHANGES.rst`: entry under breaking changes, with a security warning.
4. **Verify:** full `pytest` run, `manage.py check`, and a manual check with two users from the same IP.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Password spraying from one IP never triggers a lockout | Each new username starts a fresh username + IP counter | Security note in CHANGES and docs; suggest adding `"ip_address"` as a second entry |
| 2 | Silent security downgrade on upgrade | Unset projects change behaviour, and W006 stays quiet | Major version bump, upgrade note, and a "set it explicitly" line in the docs |
| 3 | `AXES_USE_USER_AGENT` mapping changes | The `[0].append("user_agent")` code adds `user_agent` to the new nested default | Special-case that flag to keep `[["ip_address","user_agent"]]`; add a test |
| 4 | Tests relying on the old default fail or lose coverage | The `test_lockout_by_ip_*` tests assume IP-only | Pin those tests with `override_settings`; add tests for the new default |
| 5 | Cache lockouts lost at deploy | Cache keys come from the lockout settings | Mention it in CHANGES; it only affects cache users during their cool-off period |
| 6 | Failures with no username share one bucket per IP | A missing username is stored as `None` | Add an empty-username test and document the behaviour |
| 7 | Docs and reset guidance drift out of date | Several docs state the IP-only default | Update the configuration, installation, customization and usage docs together |

Riskiest: #1. The new default lets an attacker on a single IP try one password across many usernames without ever being locked out, which the current IP-only default prevents.
