Retitling already changes the slug today, so the real gap is that old links break: changing the title regenerates the slug (`articles/routers.go:152-160`), and all 8 `/:slug` handlers then look up only the new one. I wrote a plan to fix that and edited no project files. Nothing was built or run; the plan is in `claude-home/plans/let-authors-change-an-toasty-candle.md`.

## Assumptions (no one to ask in this run)
- **Old slugs keep working in place.** A request with an old slug gets 200, the article with its current slug in the body, and a `Link: rel="canonical"` header. I chose this over a 301 redirect because a redirect causes CORS and auth-header problems for API clients.
- **Old slugs work on every article route, including edits, deletes and comments.** Who can edit or delete is still checked against the article's author, so permissions don't change.
- **An old slug is never reused**, even after its article is deleted. Deleted articles already hold their slug today.

## What could go wrong (found in the code)
1. **Re-saving the same title can change the slug.** The code compares the new title's slug to the current one. If an article has `foo-2` because `foo` was taken, saving it unchanged turns it into `foo-3`. Recording old slugs would make that churn pile up, so slugs should change only when the title text changes.
2. **A new article could take over a shared link.** The unique-slug check (`makeUniqueSlug`, `models.go:299`) only looks at current slugs. It also ignores a database error from its count query.
3. **Deleting via an old slug would silently do nothing.** `ArticleDelete` deletes where slug equals the URL value (`routers.go:207`). With an old slug that matches nothing and still returns 204, so it has to delete by ID.
4. **Concurrent creates and renames could claim the same slug** if old slugs live in a separate table with no shared unique index.
5. **Changing the title back (A → B → A)** would hit a duplicate-key error unless the article can reuse a slug it already owns.
6. **Partial updates.** The update and the tag replacement run separately with no transaction. Adding a third write for the old slug would widen that gap.
7. **Existing articles have no history yet**, so they need a one-time backfill.
8. **The RealWorld spec suite might expect 404 for an old slug.** It isn't cached locally, so I couldn't check.

## Plan
- **New table** `ArticleSlugModel{Slug (unique), ArticleID}`: one row for every slug an article has ever had, with no chains. A single unique index then covers current and old slugs.
- **Migration:** add the table in `hello.go` and the test setup, plus an idempotent backfill from `article_models`, including deleted rows.
- **Create:** save the article and its slug row in one transaction, keeping the existing retry on duplicate keys.
- **Update:**
  - Regenerate the slug only when the title text changes.
  - Reuse a slug the article already owns.
  - Run the article update, the slug row and the tags in one transaction.
- **Unique-slug check:** look in the new table and handle the count error.
- **Lookup:** add `FindArticleBySlug`, which tries the current slug first and then the history table, and use it in all 8 handlers.
- **Delete:** delete by `articleModel.ID`.
- **Tests:**
  - Requests with an old slug work on every route.
  - A → B → C leaves both A and B working.
  - Re-saving the same title keeps the slug.
  - Changing back (A → B → A) reuses A.
  - A new article can't take an old slug.
  - Deleting via an old slug really deletes.
  - The backfill registers existing articles.
- **Verify:** `go test ./...`, `scripts/run-spec-tests.sh hurl` and `bruno`, then a manual retitle followed by a GET with the old slug.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Old slug taken by a new article (link hijack) | `makeUniqueSlug` only checks `article_models` | One slug table with a single unique index |
| 2 | Delete via old slug silently does nothing | `DeleteArticleModel(&ArticleModel{Slug: slug})` returns 204 when nothing matches | Delete by `articleModel.ID` |
| 3 | Slug changes when the title didn't | Compares `foo` with `foo-2`, so it becomes `foo-3` | Regenerate only if `title != articleModel.Title` |
| 4 | Race between create and rename | Separate tables can't share a unique index | Write the slug row in the same transaction and keep the retry |
| 5 | A → B → A fails with duplicate key | A is already in this article's history | Reuse slugs the article owns |
| 6 | Partial writes | Update and `ReplaceTags` aren't in a transaction | Wrap all writes in `db.Transaction` |
| 7 | Existing articles missing from history | New table starts empty | Idempotent backfill at startup |
| 8 | Spec suite expects 404 for old slugs | Hurl specs not checked locally | Run `run-spec-tests.sh` before merging |
| 9 | Clients cache or display a stale slug | API answers on the old URL | Return the current slug in the body and a `Link rel=canonical` header |
| 10 | Count errors ignored | `Count(&count)` error is dropped, which breaks the AGENTS.md rule | Return and handle the error |

Riskiest: #1. If an old slug can be given to a new article, a link someone already shared quietly shows a different article.
