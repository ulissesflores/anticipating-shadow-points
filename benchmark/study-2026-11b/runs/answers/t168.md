# Plan: require email verification before login

I read the code but changed no files, as you asked. The Remix "blues stack" (Prisma, Postgres, cookie sessions) has no email-sending code at all.

## Assumptions
- Only new users are affected. Existing users, including the seed user, are backfilled as verified, so nobody is locked out.
- Verification uses a single-use, expiring link sent by email. I'd store only a SHA-256 hash of the token and set a 24-hour expiry.
- A transactional email provider (Resend, Postmark or SES) is available. The project needs an API key, a `MAIL_FROM` address and `APP_ORIGIN` in `.env.example`, Fly secrets and the Dockerfile/CI environment.
- Signup no longer logs the user in. It shows a "check your email" page instead.
- Login for an unverified user is refused with a message and a "resend" option.

## Current state
- `app/routes/join.tsx` creates the user and immediately calls `createUserSession`.
- `app/routes/login.tsx` calls `verifyLogin` (`app/models/user.server.ts`) and then `createUserSession`.
- `app/session.server.ts` has `requireUserId` and `requireUser`. They trust any session cookie that exists.
- `prisma/schema.prisma` has `User`, `Password` and `Note`, with one init migration.
- `cypress/support/create-user.ts`, `prisma/seed.ts` and `cypress/e2e/smoke.cy.ts` all create users and log in directly.

## Steps
1. **Schema and migration.** Add `emailVerifiedAt DateTime?` to `User`. Add an `EmailVerificationToken` model with `id`, `userId` (cascade delete), `tokenHash @unique`, `expiresAt` and `createdAt`. The migration backfills `emailVerifiedAt = createdAt` for existing rows, so it must be written by hand.
2. **Model layer** (`user.server.ts`, plus a new `verification.server.ts`):
   - `createVerificationToken(userId)` generates 32 random bytes, stores the hash and returns the raw token. It deletes the user's older tokens first.
   - `consumeVerificationToken(raw)` checks the hash and expiry, sets `emailVerifiedAt` and deletes the token, all in one transaction.
   - `verifyLogin` returns a distinct result for the unverified case. That means a discriminated result such as `{ status: "unverified" }`, not `null`.
3. **Mailer.** Add `app/email.server.ts` with `sendVerificationEmail(email, url)`. In dev and test it logs the link, so the Cypress mock setup and `mocks/index.js` keep working. In production it calls the provider.
4. **Routes.**
   - `join.tsx`: create the user, send the email, redirect to `/verify-email/sent`. No session is created.
   - New `verify-email.$token.tsx`: its loader consumes the token. It shows success with a link to log in, or an expired/invalid message. It must not auto-login.
   - New `verify-email.resend.tsx`: a POST route that is rate-limited and returns the same response whether or not the email exists.
   - `login.tsx`: if the user is unverified, return a 403 with a "verify your email" message and the resend form. The password check must run first.
5. **Defense in depth.** `requireUser`/`getUser` also reject users where `emailVerifiedAt` is null and log them out. This covers sessions that already exist.
6. **Test tooling.** `create-user.ts` and `seed.ts` set `emailVerifiedAt`. Update the smoke test and add one for the verify flow. Add Vitest unit tests for token consume, expiry and reuse.
7. **Docs and config.** Update `README.md`, `.env.example` and `fly.toml` secrets notes.

## Verification
- Run `npm run validate` (unit tests, lint, typecheck and Cypress e2e).
- Manual flow:
  1. Sign up and confirm no session cookie is set.
  2. Try to log in and confirm it is refused.
  3. Open the emailed link and confirm login now works.
  4. Re-use the link and confirm it fails.
  5. Wait past expiry and confirm it fails.
- Run the migration against a copy of production data and check that old users can still log in.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | The new column is nullable, so every current row would read as unverified | Backfill `emailVerifiedAt` in the migration, and test it on a data copy |
| 2 | Unverified users keep access through old sessions | `requireUser` only checks that the cookie's user exists | Add the verified check to `requireUser` and `getUser` |
| 3 | Email delivery fails or lands in spam | No mail code exists, and Fly needs SPF/DKIM on the sending domain | Pick a provider, configure the domain, and add a resend flow |
| 4 | Account enumeration | Signup already says "user already exists", and login or resend could leak more | Return identical resend responses, and consider changing the signup message |
| 5 | Token weakness or replay | Tokens will be new, security-critical code | Use 32 random bytes, store only the hash, make tokens single-use with expiry, and consume them in a transaction |
| 6 | Resend or signup abuse | There is no rate limiting today, so the form could be used to spam email | Add per-email and per-IP limits, and a cooldown |
| 7 | Broken tests and tooling | Cypress, `create-user.ts` and the seed log in straight after creating users | Mark test users verified, and update the e2e tests |
| 8 | Deploy ordering | Code that reads the new column would fail before the migration runs | Run `prisma migrate deploy` before the new code goes live, and deploy the migration separately first |
| 9 | Missing secrets in production | New env vars aren't in Fly or CI | Add startup `invariant` checks like the one for `SESSION_SECRET` |
| 10 | Users who can't verify | A typo'd email means a user can never log in | Add a resend flow, and allow correcting the email while unverified |

Riskiest: #1, existing users locked out. It affects every current user the moment the migration ships, so the migration must backfill them.
