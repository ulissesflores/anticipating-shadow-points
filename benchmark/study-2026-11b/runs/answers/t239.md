## What I found
This is the Clean Architecture .NET template with Angular and React clients.
- **Entities:** `TodoList` and `TodoItem` have no tenant concept. `TodoItem` reaches a tenant only through `ListId`.
- **Data access:** `ApplicationDbContext` extends `IdentityDbContext<ApplicationUser>` and exposes `TodoLists` and `TodoItems`. Handlers such as `GetTodosQueryHandler` query `_context` directly with no filter.
- **Current user:** `IUser` exposes only `Id` and `Roles`, so there is no tenant claim yet.
- **Migrations:** none are tracked in git, so the schema is probably created at startup by `ApplicationDbContextInitialiser`.
- **Auditing and events:** audit interceptors exist under `Data/Interceptors`. `TodoItem.Done` raises a domain event.

## Assumptions
- A tenant is a company, and each user belongs to exactly one tenant.
- The tenant ID will be a claim on the login token, exposed via `IUser.TenantId`.
- Isolation is enforced in the database layer (EF global query filter plus a stamp on save), not by hand in each handler.
- `TodoItem` gets its own `TenantId` column, so it can be filtered and indexed directly instead of joining through its list.
- Existing rows are backfilled into one default tenant.
- Admin and cross-tenant access is out of scope.

## What could go wrong
1. **Leaks through bypasses.** `IgnoreQueryFilters`, raw SQL and `ExecuteUpdate` skip the filter.
2. **Mismatched parent and child.** An item could be created in tenant A under a list from tenant B.
3. **Create paths that don't stamp a tenant.** Rows get `TenantId = null` and disappear for everyone.
4. **Backfill failure.** A non-null column added to existing rows fails, or old data lands in the wrong tenant.
5. **No tenant on the user.** Identity has no tenant, so tokens and the seeded users need updating.
6. **Cross-tenant guessing by ID.** Update and delete by `Id` hit another tenant's row unless the filter covers them.
7. **Tests break.** Functional tests assume one global dataset and a user with no tenant.
8. **Background work has no tenant.** The domain-event handler and the DB initialiser run without a request user.
9. **Query performance.** Without a leading `TenantId` index, every filtered query scans more rows.
10. **Clients and mappers.** AutoMapper DTOs and the generated API clients may expose or ignore the new field.

## Plan
1. Add `ITenantEntity { TenantId }` and `IUser.TenantId`, and read the claim in `Web/Services/CurrentUser`.
2. Put `TenantId` on `TodoList` and `TodoItem`, then add a migration with a default-tenant backfill and an index on `TenantId`.
3. In `ApplicationDbContext.OnModelCreating`, add a global query filter on `TenantId` for both entities.
4. In the save interceptor, stamp `TenantId` on new entities and reject any write whose tenant differs from the user's.
5. In `CreateTodoItem`, check that the target list is visible, which the filter already ensures.
6. Make the initialiser and event handlers tenant-aware or explicitly tenant-scoped.
7. Add two-tenant tests covering list, get, update, delete and create-under-foreign-list. Each should come back empty or not found, never forbidden, so existence isn't revealed.

Verify by running the new tests, plus a `grep` for `IgnoreQueryFilters` and raw SQL.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Filter bypass | Raw SQL, `IgnoreQueryFilters` or `ExecuteUpdate` skip it | Ban them by grep and review; test each path |
| 2 | Parent/child tenant mismatch | `TodoItem` links to a list only via `ListId` | Stamp on save and validate list tenant on create |
| 3 | Unstamped new rows | Several create paths and the seeder | Stamp in the interceptor, make the column non-null |
| 4 | Bad backfill | Existing rows have no tenant | Default-tenant migration, check before the NOT NULL step |
| 5 | No tenant on user | `IUser` has only `Id` and `Roles` | Add a tenant claim and update seeded users |
| 6 | Cross-tenant ID guessing | Update and delete take a bare `Id` | Rely on the filter; return NotFound |
| 7 | Tests break | Tests assume one global dataset | Add a tenant fixture and two-tenant cases |
| 8 | Missing tenant in background code | Domain-event handler and initialiser run without a request | Pass the tenant explicitly; fail closed |
| 9 | Slow queries | Every query now filters by tenant | Index `TenantId`; composite with `ListId` |
| 10 | Client and DTO drift | Angular and React clients are generated from the API | Keep `TenantId` out of DTOs; regenerate clients |

Riskiest: #1, filter bypass, because a single unfiltered query silently shows one company's data to another.
