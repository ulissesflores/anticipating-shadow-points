I didn't edit any files, including the plan file, because you asked for no edits. The plan is below. This repo is django-axes 9.0.0, and the default lives in `axes/conf.py:50-51`, where it falls back to `["ip_address"]`.

## Assumptions
- "The new default" means: when `AXES_LOCKOUT_PARAMETERS` is unset and none of the deprecated `AXES_*` flags are set, the value becomes `[["username", "ip_address"]]`, which locks a username and IP pair together.
- Anyone who sets `AXES_LOCKOUT_PARAMETERS` explicitly sees no change. The deprecated flags (`AXES_ONLY_USER_FAILURES`, `AXES_LOCK_OUT_BY_USER_OR_IP`, `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP`, `AXES_USE_USER_AGENT`) keep working as they do now.
- This changes behaviour, so it ships as a documented breaking change in the next major release (10.0.0), not in a 9.x patch.

## Ways this could go wrong
1. **Weaker protection against password spraying.** With the pair as the key, one IP can try N usernames and each pair gets its own `AXES_FAILURE_LIMIT`. Today that IP gets locked after `FAILURE_LIMIT` failures in total. This is the security cost of fewer false lockouts on shared NAT or office IPs.
2. **Upgrades change silently.** Sites that rely on the default lose IP-wide lockout with no warning. The W006 check (`axes/checks.py:183`) still passes because `ip_address` is inside the pair, so nothing flags it.
3. **Existing lockouts disappear on upgrade (cache handler).** Cache keys are `sha256` of the concatenated values (`axes/helpers.py` `make_cache_key_list`). The old `sha(ip)` keys are never read again, so every current cache lockout lifts at once.
4. **Reset by IP or username stops working on the cache handler.** `AxesCacheHandler.reset_attempts` (`axes/handlers/cache.py:47-51`) builds keys from `AccessAttempt(username=None, ip_address=ip)`. That gives `sha(ip)`, which no longer matches `sha(username+ip)`. As a result `axes_reset_ip` and `axes_reset_username` clear nothing and still report success.
5. **Requests with no username.** The username can be missing, for example a different form field name or `AXES_USERNAME_CALLABLE` returning None. The cache key then shrinks to `sha(ip)` and the database filter becomes `username=None`. The result is lockouts that behave like IP-only or by IP-and-NULL-username, inconsistently between handlers.
6. **Key collisions.** Values are joined with no separator, so `"ab"+"1.2.3.4"` and `"a"+"b1.2.3.4"` produce the same key. This already exists, but it now affects every default install.
7. **Interaction with deprecated flags.** If the fallback's `else` branch changes, `AXES_USE_USER_AGENT` takes its "append to list" path (`conf.py:59-60`) and produces `[["username","ip_address","user_agent"]]`. Separately, `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP=False` now has no effect.
8. **Tests and docs drift.** `tests/settings.py` doesn't set the parameter, so tests that assume IP-only by default will fail: test_login (36 references), test_helpers, test_handlers, test_attempts. These docs state the IP-only default:
   - `docs/4_configuration.rst:93`
   - `docs/3_usage.rst:14`
   - `docs/5_customization.rst:181`
9. **Version placement.** 9.0.0 was released on 2026-10-30. Slipping this into 9.x would break semantic versioning.

## Plan
1. **`axes/conf.py:50-51`**: change the final `else` fallback to `[["username", "ip_address"]]`. Leave the three deprecated-flag branches unchanged. Check that the `AXES_USE_USER_AGENT` path still builds the intended combination.
2. **`axes/handlers/cache.py` `reset_attempts`**: make reset by IP or username either work or fail clearly when the pair is the key. Keys are hashed, so they can't be enumerated by IP alone. The minimum is to raise `NotImplementedError` with a clear message (like the existing `ip_or_username` case) when only one of `ip_address` or `username` is given and the lockout parameters are combined. Also allow resetting with both values.
3. **Tests**:
   - Add a test in `tests/test_conf.py` for the new default, plus one for each deprecated flag.
   - Add `AXES_LOCKOUT_PARAMETERS = ["ip_address"]` with `override_settings` to tests that rely on IP-only, or update what they assert.
   - Add tests for the pair default: same IP with a different username is not locked, same username from a different IP is not locked, the pair is locked. Run these for both the database and cache handlers.
   - Add a test for cache reset under the new default.
4. **Docs**: update the default in `4_configuration.rst`, the intro in `3_usage.rst`, and the wording in `5_customization.rst`. Add a "how to keep IP-only" snippet (`AXES_LOCKOUT_PARAMETERS = ["ip_address"]`) and an explanation of the spraying trade-off.
5. **`CHANGES.rst`**: add a 10.0.0 "Breaking changes and upgrading" entry covering the new default, the one-line opt-out, existing cache lockouts being dropped, and the cache reset limits.
6. **Optional**: add a system check warning, shown only when the default is in effect, that points users to the new behaviour.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Password spraying from one IP is no longer limited | Each username and IP pair gets its own `FAILURE_LIMIT` | Document the trade-off; suggest `["ip_address", ["username","ip_address"]]` for strict setups |
| 2 | Silent behaviour change on upgrade | Installs that rely on the default get no warning; W006 still passes | Major release, CHANGES entry, optional startup check |
| 3 | Cache lockouts lifted on upgrade | Key changes from `sha(ip)` to `sha(username+ip)` | Call it out in the upgrade notes |
| 4 | Cache reset commands do nothing | `reset_attempts` hashes only the IP or only the username | Raise a clear error or require both values; add tests |
| 5 | Missing username weakens the key | None is skipped in cache keys and becomes a NULL filter in the database | Test the no-username path on both handlers |
| 6 | Deprecated-flag fallback changes | The `USE_USER_AGENT` append path and `COMBINATION=False` now behave differently | Test each flag combination in test_conf |
| 7 | Many tests break | `tests/settings.py` depends on the IP-only default | Pin IP-only in those tests; add new pair tests |
| 8 | Docs contradict the code | Three doc files state IP-only | Update all of them in the same change |
| 9 | Semver violation | 9.0.0 has just been released | Ship as 10.0.0 |

Riskiest: #1, because the new default makes it easier to spray passwords from a single IP, and nothing warns the operators who rely on the default.
