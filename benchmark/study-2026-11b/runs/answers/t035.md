## What the code does today
- `Visit` has only a `visit_date` (a `DATE`) and a `description`. It has no vet, no time and no duration.
- `visits` has a `pet_id` foreign key and nothing else. `Pet` and `Owner` have no vet link.
- `VisitController` saves the visit by saving the whole `Owner` aggregate, with no locking and no uniqueness check.
- The schema comes from hand-written `schema.sql` files for H2, MySQL and Postgres (`ddl-auto=none`). There is no migration tool.
- The only date rule is that the visit must be after today.

## Assumptions
- A visit is a time slot, not a whole day. I assume 30-minute slots on a fixed grid, such as 09:00–17:00 on weekdays. Without a time, "same time" has no meaning.
- Each visit gets one vet. The owner picks from a list or the system auto-assigns.
- I assume no vet-schedule or availability data exists yet. I'd start with a simple working-hours rule.
- Visits can be booked by anonymous users, as they can now. There is no auth.
- Existing visits stay valid. They have no vet or time, so they're legacy data.
- The app runs as several instances behind a load balancer on MySQL or Postgres, so H2-only fixes aren't enough.

## Ways this could go wrong
1. Two owners book the same vet and slot at once. A check-then-insert in the controller passes for both. Only a database unique constraint stops this.
2. The constraint is added to one schema file but not the others, so the databases behave differently.
3. The `Visit` entity has no vet or time, so the change touches the model, three schemas, seed data, forms, i18n bundles in about 10 languages and tests.
4. Existing rows have null vet and time. A unique index treats nulls differently on MySQL, Postgres and H2, so legacy rows could block the migration or slip past the check.
5. `owners.save(owner)` writes the whole aggregate. A constraint violation surfaces as a generic 500, and the user loses their form input.
6. Time zones and DST. `LocalDate.now()` uses the server zone, and the clinic's zone may differ.
7. Cancel and reschedule don't exist. A cancelled visit must free its slot, or the slot is blocked for good.
8. Double submit or refresh on POST creates duplicates, or a confusing "slot taken" error on the second click.
9. Bots can fill every slot, because booking is anonymous and unauthenticated.
10. An overlap rule is harder than equality. Variable-length visits need a range or exclusion constraint, which only Postgres has natively. The slot grid avoids this.
11. Recent commits show hardening of user-controlled input. Vet id, date and time are new untrusted inputs: bad ids, out-of-range values, past dates.
12. The existing `PetClinicConcurrencyTests` may assume today's single-date semantics. Existing tests may break.

## Plan (summary)
1. Add `vet_id` and `start_time` to `visits`, with a slot grid, in all three schemas. Add `UNIQUE (vet_id, visit_date, start_time)`.
2. Add `Visit.vet` and `Visit.startTime`. Add a slot-availability query in a new repository method or service.
3. Update the form to select a vet and show only free slots for the chosen date.
4. In `VisitController`, catch the constraint violation (`DataIntegrityViolationException`) and re-show the form with "slot just taken".
5. Treat legacy rows as null vet and time. The new check applies only to rows with both set.
6. Tests: a concurrent double-booking test (N threads, one winner), a controller test for the conflict message, and a legacy-data test. Run on H2, then on MySQL and Postgres through the existing integration tests.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Race: two bookings for one slot | The controller saves the whole owner with no lock or check | `UNIQUE(vet_id, visit_date, start_time)`, plus a friendly handler for the violation |
| 2 | Schemas drift across DBs | Three hand-written `schema.sql` files, no migration tool | Change all three together and run the MySQL and Postgres integration tests |
| 3 | No vet or time in the model | `Visit` has only a date, so the change spreads widely | Add the fields, update forms, i18n and seed data, and keep the scope to a fixed slot grid |
| 4 | Null legacy rows vs unique index | Null handling differs between H2, MySQL and Postgres | Keep the columns nullable, migrate or ignore legacy rows, and test each DB |
| 5 | Generic 500 on conflict | `owners.save(owner)` throws a raw constraint error | Catch it, return to the form with the input kept and a clear message |
| 6 | Time zone and DST errors | `LocalDate.now()` uses the server zone | Use a configured clinic zone and a `Clock` bean |
| 7 | Cancelled visits block slots | No cancel flow exists | Add a cancel path, or a status column that the unique rule honors |
| 8 | Double submit and bot abuse | Booking is anonymous and POST isn't idempotent | Post-redirect-get, a disabled submit button, and rate limiting |
| 9 | Unvalidated vet, date and time input | The recent commits show input hardening is an ongoing concern | Bind only allowed fields, check the vet exists, and check the slot is on the grid and in range |
| 10 | Existing tests break | The concurrency and visit tests assume date-only visits | Update the fixtures and add a concurrent booking test |

Riskiest: #1, the race between two simultaneous bookings. App-level checks can't stop it, so only a database constraint enforced on all three databases does.
