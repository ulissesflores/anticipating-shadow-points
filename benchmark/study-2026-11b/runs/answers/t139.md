- **New hashes** use ASP.NET Identity's `PasswordHasher<object>`. That is PBKDF2-HMAC-SHA512 with 210,000 iterations and a per-hash random salt. The salt is embedded in the versioned blob, so `Person.Salt` is stored as `[]`.

- **Rehash on login:** `Features<home>` rewrites the hash after a successful legacy login. `Edit.cs` and `Create.cs` always use the new hasher.

## Assumptions
- "Stronger" means a memory-hard KDF (Argon2id), since PBKDF2 at 210k iterations already meets the OWASP guidance for SHA-512.
- No forced reset is allowed. Rehashing therefore happens lazily at login, which is the mechanism already in place.
- The `Hash` and `Salt` columns stay as they are. I assume `Hash` is an unbounded `varbinary` or `BLOB`, which I haven't checked. An Argon2 blob is about 100 bytes, so a length limit could matter. If so, no migration is needed. If not, one is needed for both the SQLite and SQL Server contexts.
- A new NuGet dependency is acceptable. `Konscious.Security.Cryptography.Argon2` and `Isopoda.Argon2` are candidates, to be vetted first. The alternative is to keep PBKDF2 and only raise the iteration count.

## Plan
1. **Confirm the baseline.** Run `dotnet run --project build/build.csproj -- test`. Read `PasswordHashingTests.cs` to see what it covers, and check the `Hash` column type and length in the migration snapshots.
2. **Add a scheme marker.** Hashes get a prefix byte or a magic header, such as `0xA2` plus the Argon2 parameters. Today the scheme is inferred from length, which breaks once three formats coexist. Identity's blob starts with `0x01`, so the dispatch order would be:
   - 64 bytes plus a 16-byte salt means legacy HMAC.
   - The Argon2 marker means Argon2id.
   - `0x01` means Identity PBKDF2.
3. **Implement Argon2id in `PasswordHasher`.**
   - Parameters: about 19 MiB memory, 2 iterations, parallelism 1, a 16-byte random salt, and a 32-byte output.
   - Store the parameters in the blob so they can be tuned later.
   - Compare with `CryptographicOperations.FixedTimeEquals`.
   - Return `SuccessRehashNeeded` for PBKDF2 hashes, and for Argon2 hashes whose parameters are below the current ones.
4. **Keep the call sites unchanged.** `Login.cs`, `Create.cs` and `Edit.cs` already go through `IPasswordHasher`. The only change is that `Login.cs` rehashes PBKDF2 hashes too, which it already does for any `SuccessRehashNeeded`.
5. **Set the dependency up.** Add the package to `Directory.Packages.props` and refresh the `packages.lock.json` files. The build enforces locked restore.
6. **Tests.** Add or extend integration tests for:
   - a legacy HMAC user logging in and being rehashed to Argon2id;
   - a PBKDF2 user logging in and being rehashed;
   - a wrong password failing for each of the three formats;
   - an empty or corrupt hash failing without throwing;
   - the login response never exposing `Hash` or `Salt`.
7. **Finish.** Run `format`, then `test`, then optionally `make test-hurl-with-managed-server`. Document the scheme and tuning in `docs/`.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Scheme misdetection | Length-based sniffing already exists, and a third format could collide | Add an explicit version marker and dispatch tests for every format |
| 2 | Unmigrated users stay weak | Rehash only happens on login, so dormant accounts keep the legacy HMAC with a fixed key | Report the share of legacy rows, and set an expiry or a forced-reset policy for dormant accounts |
| 3 | Login DoS | Memory-hard hashing is expensive, and `Login` is unauthenticated | Add rate limiting and lockout, and keep memory use modest |
| 4 | Rollback is one-way | Older builds can't verify the new blobs after rollout | Ship a verify-only release first, then enable issuing |
| 5 | Dependency and supply chain | Locked restore, and a third-party crypto package | Vet the package, pin the version, and consider staying on PBKDF2 |
| 6 | Column length or migration | The two providers have separate snapshots | Check the column type first, and add migrations to both if it changes |
| 7 | Timing and user enumeration | An unknown email returns early without hashing | Hash a dummy value on a miss to keep timing even |
| 8 | Rehash write failure | `SaveChanges` inside a login could fail or race | Make it best-effort, so login succeeds even if the rehash fails |
| 9 | Test and CI slowness | Argon2 cost multiplies across many test logins | Lower the parameters via options in the test host |
| 10 | Input handling | Password normalization and long inputs differ between schemes | Use the same UTF-8 bytes everywhere and cap the password length |

Riskiest: #2, because users who never log in keep the weak legacy hash indefinitely, and "no forced reset" means the change doesn't reach them.
