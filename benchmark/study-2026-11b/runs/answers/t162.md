## Finding

The repo has already done the first hop. `src/Conduit/Infrastructure/Security/PasswordHasher.cs` issues ASP.NET Identity v3 PBKDF2 hashes: HMAC-SHA512, 210,000 iterations, a random 16-byte salt and a versioned payload. It still verifies the legacy `HMACSHA512("realworld", password+salt)` hashes, which are 64 bytes with a 16-byte salt. `Login.cs:79-82` re-hashes on `SuccessRehashNeeded`, and `PasswordHashingTests.cs` covers the upgrade.

## Assumptions

- You want something stronger than the current PBKDF2, so the target is **Argon2id**. PBKDF2 is only CPU-hard, and Argon2id is memory-hard.
- Old hashes can't be converted directly, because the plaintext is unknown. The upgrade therefore has to happen on the user's next successful login, as it does today.
- The `Person.Hash` and `Person.Salt` columns stay as they are, so no schema change or EF migration is needed. Argon2id output carries its own salt and parameters in a version-prefixed blob.
- A library will be added, such as `Konscious.Security.Cryptography.Argon2` or `Isopoh.Cryptography.Argon2`. .NET has no built-in Argon2.

## Plan

1. **Formalise the hash format.**
   - Replace the length checks (`hash.Length == 64`, `salt.Length == 16`) with an explicit format marker.
   - Argon2id blobs start with a distinct prefix byte: `0x02` for Argon2id, while Identity v3 starts with `0x01`.
   - The scheme is then chosen by tag instead of by guessing from size.
2. **Add Argon2id.** In `PasswordHasher`, `Hash` produces `[0x02 | version | m | t | p | salt(16) | hash(32)]`. Use OWASP-grade parameters, for example m=19 MiB, t=2, p=1, and keep them in `IOptions` so they can be tuned.
3. **Dispatch in `Verify`.** Handle three schemes:
   - Argon2id: verify, and return `SuccessRehashNeeded` if the stored parameters are below the current ones.
   - Identity v3 PBKDF2: verify through `PasswordHasher<object>`, and always return `SuccessRehashNeeded` on success.
   - Legacy HMAC: keep the existing branch.
   - Compare hashes with `CryptographicOperations.FixedTimeEquals`.
4. **Keep call sites unchanged.** `Create.cs`, `Edit.cs` and `Login.cs` already call `Hash`/`Verify` and re-hash on `SuccessRehashNeeded`. Make sure `Login` saves the new hash with the request cancellation token.
5. **Register options and the package.** Update `ServicesExtensions.cs:86`, add the package to `Directory.Packages.props`, and refresh the `packages.lock.json` files.
6. **Tests.** Extend `PasswordHashingTests.cs` to cover:
   - Argon2id round-trip, and a wrong password failing.
   - A legacy HMAC hash upgrading to Argon2id on login.
   - An Identity v3 hash upgrading to Argon2id on login.
   - An Argon2id hash with weaker parameters being flagged for rehash.
   - Garbage or empty blobs failing without throwing.
   - Fix up `LoginTests.cs` and `CreateTests.cs` where they depend on the hash format.
7. **Docs.** Document the rollout and the sunset path in `docs/`. Once monitoring shows the legacy and PBKDF2 populations are small, force a reset for the remaining accounts or accept that they stay on the old scheme.
8. **Validate.** Run `dotnet run --project build/build.csproj -- test`. This formats, builds with warnings as errors, and runs the tests.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Login becomes a DoS lever | Each Argon2id check uses about 19 MiB and CPU, and `/users/login` is anonymous | Add rate limiting and a concurrency cap, and benchmark the parameters |
| 2 | Wrong scheme detection | The current code guesses by byte length, so an Argon2id blob could be mistaken for a legacy hash | Use an explicit prefix byte and a version, with tests for each format |
| 3 | Dormant users never upgrade | Rehash only happens on login, so old hashes remain indefinitely | Track the hash-scheme mix, and set a sunset or forced-reset policy |
| 4 | Rollback can't read the new hashes | Older builds can't verify the `0x02` blobs | Ship a verify-only release first, then enable issuing |
| 5 | Third-party crypto dependency | Argon2 comes from a NuGet package, not the BCL, so there is supply-chain and maintenance exposure | Pin the version, review the package, and keep the lock files |
| 6 | Timing side channels | There are now three code paths with different costs | Use fixed-time comparison, and optionally run a dummy hash when the user is not found |
| 7 | Parameters too high for hosting | Memory-hard hashing can OOM small containers under concurrent logins | Make the parameters configurable and load-test on production-sized hardware |
| 8 | Failed upgrade write | The rehash is saved inside the login request, and a failed save could surface as a login error | Make the rehash best-effort and non-fatal, and log it |
| 9 | Test and build drift | The strict analyzers and locked restore fail CI if lock files or formatting are stale | Run the `test` target locally and commit the lock files |

Riskiest: #1, because memory-hard hashing on an unauthenticated endpoint makes login a cheap DoS target unless it is rate limited and tuned.
