I've written the plan to `claude-home/plans/make-every-to-do-list-giggly-cupcake.md`. No repository files were changed and nothing was built or run.

**What I found in the code:**
- This is the Clean Architecture template. It uses `#if` switches for SQLite, Postgres and SQL Server, and creates the database with `EnsureCreatedAsync` instead of migrations.
- `TodoList` and `TodoItem` have no owner field, and no query filters them. `GetTodos` returns every list in the database.
- `IUser` only provides `Id` and `Roles`. Login goes through `MapIdentityApi`.
- `CreateTodoItem` takes a client-supplied `ListId` and doesn't check who owns that list.

**Assumptions** (I couldn't ask):
- A tenant is a company, and each user belongs to exactly one.
- The tenant comes from a claim in the user's token, never from anything the client sends.
- Anyone who self-registers gets a new tenant of their own; invites are out of scope.
- The seeded admin and sample data go into a "Default" tenant.
- The API stays the same, so the Angular and React clients don't change.
- The dev database can be dropped and recreated.

**Ways this could go wrong:**
- A query path the filter doesn't cover leaks data between companies.
- One company adds items to another company's list by passing its `ListId`.
- Code with no logged-in user (seeding, tests, background work) sees no data, or saves rows with no tenant.
- The tenant ID is taken from the client, or changed on update.
- Tokens issued before the change have no tenant claim.
- The provider variants drift apart, and existing databases lack the new column.

**Plan:**
1. Add a `Tenant` entity and an `ITenantOwned` marker. Put `TenantId` on `TodoList`, `TodoItem` and `ApplicationUser`.
2. A custom claims factory adds a `tenant_id` claim at login. `IUser` and `CurrentUser` expose it.
3. `ApplicationDbContext` applies a global query filter to every `ITenantOwned` type, so new entities are covered automatically.
4. A save interceptor fills in `TenantId` on new rows, refuses to save without one, and blocks changing it.
5. The `CreateTodoItem` and `UpdateTodoItemDetail` validators check that the list exists. Because that lookup is filtered, another company's list looks like it doesn't exist.
6. Add `TenantId` indexes. Registration creates a tenant. The seeder sets its tenant explicitly through an override that works without an HTTP request.
7. Add tests with two companies: neither can read, update, delete or attach items to the other's data, and `GetTodos` returns only their own lists.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Item attached to another tenant's list | `CreateTodoItem`/`UpdateTodoItemDetail` accept a raw `ListId` with no ownership check | Validator checks the list through the filtered query; item's TenantId copied from its list |
| 2 | Missed query path leaks data | Filters only cover what they're applied to; raw SQL and `IgnoreQueryFilters` skip them | Apply the filter by looping over all `ITenantOwned` types; cross-tenant tests for every endpoint |
| 3 | Null tenant outside a request | Seeder, `TestApp.FindAsync` and event handlers run with no HttpContext | Explicit tenant override for system code; interceptor throws if TenantId is null |
| 4 | TenantId from the client or changed later | Commands bind request fields directly | Take TenantId only from the claim; mark it unmodified on update |
| 5 | Old tokens have no tenant claim | Tokens from `MapIdentityApi` keep claims from when they were issued | Reject requests without the claim; force everyone to log in again |
| 6 | Self-registration has no tenant | `/register` only creates a user | Create a tenant on user creation or wrap the endpoint |
| 7 | Existing databases lack the column | `EnsureCreated` never updates an existing schema | Recreate dev databases; tell template users |
| 8 | Provider variants drift apart | `#if` code for SQLite, Postgres and SQL Server | Build and test each template variant |
| 9 | Existing tests break | Tests run as one user with no tenant | Add a tenant-aware `RunAsUserAsync`; Respawn resets the Tenants table |
| 10 | Uniqueness only enforced in code | The unique-title validator becomes per-company with no database constraint | Add a unique index on (TenantId, Title) |

Riskiest: #1. A client-supplied `ListId` lets one company write into another company's list even when every read is filtered.
