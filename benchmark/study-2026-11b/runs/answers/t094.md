## Plan: make `rolling` default to `true` in express-session

**Current behaviour:** `index.js:109` sets `var rollingSessions = Boolean(opts.rolling)`, so rolling is off unless set. Without it, a session that wasn't modified never gets its cookie sent again, and the browser-side expiry doesn't move. The decision itself is made in `shouldSetCookie` (`index.js:~490`).

**Assumptions:**
- "Every request extends expiry" means the existing `rolling: true` behaviour: any request that loads an existing session gets a new `Set-Cookie` with a fresh `maxAge`. New sessions that haven't been used yet still follow `saveUninitialized`.
- Only an unset option changes. An explicit `rolling: false` still turns it off.
- No store changes are needed. With `resave: false`, the server-side copy is already refreshed on every request through `store.touch()` (`shouldTouch`).
- This changes a default people rely on, so it should ship in the next major version (2.0), not a 1.x release.

**Steps:**
1. **`index.js:108-109`:** change to `opts.rolling === undefined ? true : Boolean(opts.rolling)`. Unlike `resave`, this needs no deprecation warning.
2. **`index.js:78`:** update the JSDoc to say the default is `true`.
3. **`README.md` `##### rolling` section:**
   - Change the text to "The default value is `true`."
   - Explain how to turn it off with `rolling: false`.
   - Keep the existing note about `saveUninitialized`.
4. **`HISTORY.md` `unreleased`:** add a breaking-change entry.
5. **`test/session.js:1159`:**
   - Change "should default to false" to "should default to true", expecting `Set-Cookie` on the second request.
   - Add a test showing that an explicit `rolling: false` sends no cookie.
6. **Other tests in `test/session.js`:** 37 assertions check that no `Set-Cookie` header is sent. Any of them that send an existing session cookie with default options will now fail. Fix each one by passing `rolling: false` where the test is really about something else, rather than loosening the assertion.

**Verification:**
- Run `npm test` and `npm run lint`.
- Manual check with a small app using `maxAge: 60000`:
  - The second request carrying the cookie should get a `Set-Cookie` with a later `Expires`.
  - With `rolling: false`, it should get no `Set-Cookie`.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Silent breaking change for existing apps | Apps that never set `rolling` start getting `Set-Cookie` on every response | Ship in a major version, list it as breaking in HISTORY, document `rolling: false` |
| 2 | Responses with `Set-Cookie` stop being cached | Shared caches and CDNs usually won't cache them, so static or public routes behind the session middleware lose caching | README note: mount the session middleware after static routes |
| 3 | Many existing tests fail | Up to 37 "no `Set-Cookie`" assertions were written assuming rolling is off | Add `rolling: false` per test, keeping each test's intent |
| 4 | Sessions effectively never expire for active users | An idle timeout becomes a sliding window, so there's no absolute session lifetime | Document it; suggest apps enforce their own absolute timeout |
| 5 | Extra header bytes on every response | Without `maxAge`, the cookie is re-sent on each response but there's no expiry to extend | Accept it, or limit rolling to `expires != null` (scope creep) |
| 6 | Store load if `resave: true` | Rolling only resends the cookie, but users may assume it also needs resave | README already explains `touch`; repeat it near `rolling` |
| 7 | Concurrent requests overwrite cookies | Parallel responses each set the cookie, so the latest-arriving one wins | Harmless: same ID, only the expiry differs |
| 8 | Docs and code disagree | JSDoc, README and the tests all state the old default | Update all three in the same commit |

Riskiest: #1, existing apps silently start sending `Set-Cookie` on every response (which also causes #2, broken caching), so this has to ship as a documented major-version change.
