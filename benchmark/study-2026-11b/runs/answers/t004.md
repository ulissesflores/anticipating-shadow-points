I've written a plan to make username + IP address the default lockout key; no repo files were edited. The plan is at `claude-home/plans/lock-users-out-by-wise-balloon.md`. I couldn't hand it over for approval because the plan-approval tool isn't available in this session.

## What I assumed
- **New default:** `AXES_LOCKOUT_PARAMETERS = [["username", "ip_address"]]`. The nested list means the two are used together; the flat list `["username", "ip_address"]` means either one.
- **Release:** HEAD is already tagged `9.0.0`, so this is a breaking change for the next major release (10.0.0).
- **Scope:** only the "nothing configured" fallback changes. Explicit settings, callables, dotted paths and the old deprecated settings that set the parameters behave as they do now.

## Ways it could go wrong
1. **Weaker protection by default.** One IP can now try many usernames without being blocked (password spraying), with a separate failure counter for each username.
2. **Lockouts lift on deploy.** Cache keys change from a hash of the IP to a hash of username + IP. The database lookup also starts filtering on username. Anyone currently locked out (by either backend) gets unlocked when the upgrade goes out.
3. **Existing tests break.** The `test_lockout_by_ip_*` tests in `tests/test_login.py` (around lines 380–560) rely on the current default. For example, `..._blocks_when_diff_user_same_ip_...` would now let the login through.
4. **Requests with no username.** The cache key is built by joining the non-empty values, so a missing username leaves an IP-only key. All failures without a username then share one bucket per IP. In the database they become rows with a null username.
5. **Cache key collisions.** `make_cache_key_list` joins values with no separator, so `"a1" + "1.2.3.4"` and `"a" + "11.2.3.4"` produce the same key. This is narrow, but now every default install is exposed to it.
6. **Old settings resolve to the new default.** Projects that set the deprecated flags to `False`, or rely on the defaults without setting anything, silently get the new mode. Setting `AXES_USE_USER_AGENT` alone now gives `[["username","ip_address","user_agent"]]`.
7. **`reset_request` changes behaviour.** With the default treating username and IP as a pair, resets go through a different path.
8. **Docs go stale.** These pages still say "Default: only use IP address" or "not only by IP address":
   - `docs/4_configuration.rst:93` and lines 120–125
   - `docs/2_installation.rst`
   - `docs/5_customization.rst:181`

## The plan
1. **`axes/conf.py:36-51`:** set the final `else` to a fresh `[["username", "ip_address"]]` list, and fix the stale comment. The existing user-agent branch already handles the nested form.
2. **`checks.py` and `apps.py`:** no code changes. Add tests that the new default raises no W006 warning (the check that `ip_address` is present) and produces the right startup log text.
3. **Tests:**
   - Pin `@override_settings(AXES_LOCKOUT_PARAMETERS=["ip_address"])` on the tests that rely on the old default, rather than changing their assertions.
   - Add tests for the new default against both the database and cache backends:
     - different user, same IP → allowed
     - same user, different IP → allowed
     - same user, same IP → blocked
     - missing username → still locked out
     - user-agent setting → `[["username","ip_address","user_agent"]]`
     - `reset_request` with an IP only, and with an IP plus username
4. **Docs and `CHANGES.rst`:** add a 10.0.0 breaking-change entry. It should cover the new default, the one-line opt-out (`AXES_LOCKOUT_PARAMETERS = ["ip_address"]`) and the fact that lockouts are released on deploy.
5. **Verification:** run the full `pytest` suite, then check by hand with both backends: lock out user A from one IP, confirm user B from that IP is still allowed and user A is still blocked.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Password spraying no longer blocked by default | Each username gets its own counter per IP, so one IP can try every account | Document the trade-off and the `["ip_address"]` opt-out; suggest `[["username","ip_address"], "ip_address"]` with a higher limit |
| 2 | Lockouts lifted on upgrade | Cache keys change and database lookups add a username filter | Say so in CHANGES.rst; deploy outside an active attack |
| 3 | Test suite failures | `test_lockout_by_ip_*` tests rely on the implicit default | Pin `["ip_address"]` on those tests and add new tests for the default |
| 4 | Missing username shares one bucket per IP | Empty values are dropped from the key, and the database stores a null username | Add tests for this; document how `AXES_USERNAME_FORM_FIELD` affects it |
| 5 | Cache key collisions | No separator in `"".join(values)` | Optionally add a separator now, since keys are reset anyway |
| 6 | Silent behaviour change for implicit configs | Deprecated flags set to `False`, or no setting at all, resolve to the new default | Major version bump plus an upgrade note |
| 7 | `reset_request` scope changes | It now requires username and IP together | Test resets with an IP only and with an IP plus username |
| 8 | Stale docs | Several pages still describe IP-only as the default | Update them and grep for leftover wording |

Riskiest: #1. Weaker protection by default: one IP can try many usernames, each with its own failure counter, so password spraying is no longer blocked out of the box.
