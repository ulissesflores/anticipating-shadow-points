This is a two-line code change, but it breaks backward compatibility in ways that matter. I didn't edit any repository files. I only wrote the plan file at `claude-home/plans/make-the-session-middleware-s-typed-shamir.md`.

**Assumptions**
- "Secure by default" means changing the default values of the existing `https_only` and `same_site` parameters. Users can still turn either off. No new parameter is added.
- This ships in the next release as a breaking change, listed under "Changed" in the release notes with a migration note.
- The middleware will add `secure` whatever the request scheme is, as it does today with `https_only=True`. It won't check whether the request came over HTTPS.

**Plan**
1. **Code** (`starlette/middleware/sessions.py:24-25`): change the defaults to `same_site="strict"` and `https_only=True`. Nothing else needs to change: the flag string is built once in `__init__` and used both when writing and when clearing the cookie.
2. **Tests** (`tests/middleware/test_session.py`, and check `tests/middleware/test_middleware.py`):
   - The test client won't send a `Secure` cookie back to `http://testserver`, so any test that writes a session and then reads it will fail.
   - Fix those tests by switching to `base_url="https://testserver"` (as `test_secure_session` and `test_partitioned_session` already do) or by passing `https_only=False`.
   - Add a test that the default `Set-Cookie` contains `secure` and `samesite=strict`, both when writing and when clearing the cookie.
   - Add a test that `https_only=False, same_site="lax"` gives back the old header.
3. **Docs** (`docs/middleware.md`, SessionMiddleware section):
   - Update the stated defaults for `same_site` and `https_only`.
   - Explain how to opt out for local HTTP development and for OAuth/SSO logins (use `same_site="lax"`).
   - Simplify the example, since `https_only=True` is now the default.
   - Per AGENTS.md, keep explanatory text after each heading, before any code.
4. **Release notes**: add an entry under "Changed" that marks it as breaking and gives the one-line opt-out.
5. **Before opening a PR**: AI_POLICY.md requires searching open and closed PRs, issues and discussions for an existing proposal first. Duplicate PRs get the contributor banned.

**Verification**
- Run `pytest tests/middleware/test_session.py tests/middleware/test_middleware.py`, then `scripts/test` and `scripts/check`.
- Do a manual browser check: HTTPS, plain `http://localhost` (Chrome and Safari), and a cross-site redirect back into the app.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | OAuth/SSO logins break | With Strict, the cookie isn't sent when an identity provider redirects the user back (a cross-site navigation), so the saved login state is missing | Document `same_site="lax"` for OAuth; say so clearly in release notes |
| 2 | Users look logged out after following links from other sites | Strict drops the cookie on any navigation that starts on another site, e.g. an email or Slack link | Document the trade-off; Lax stays one kwarg away |
| 3 | Downstream test suites fail silently | The test client defaults to `http://testserver`, so it drops `Secure` cookies and sessions come back empty without any error | Release note telling users to use an `https://` base_url or `https_only=False` |
| 4 | Local development over plain HTTP loses sessions | Safari (and some setups using LAN IPs or `.local` names) won't store `Secure` cookies over http | Document `https_only=False` for development |
| 5 | Silent behaviour change on upgrade | Defaults change without any warning or error | Mark as breaking in release notes; consider a minor-version bump |
| 6 | Starlette's own tests break | Most session tests write and then read the session over http | Update the tests as in step 2 |
| 7 | Clearing the cookie stops working if flags differ | Browsers may not replace an old non-Secure cookie with a Secure one after the upgrade | Old cookies are still accepted (signature unchanged); they expire within `max_age`. Note it |
| 8 | Duplicate PR | AI_POLICY.md bans contributors who open duplicate PRs | Search PRs, issues and discussions first |

Riskiest: #1, because the Strict default breaks OAuth/SSO login redirects for anyone who upgrades without changing their config.
