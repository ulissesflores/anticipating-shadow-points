## Ways this could go wrong

This is a .NET Clean Architecture app with an Angular/React client. `TodoList` and `TodoItem` are `BaseAuditableEntity`. Handlers use `IApplicationDbContext` directly, and `IUser` exposes only `Id` and `Roles`. I found no existing tenant concept, no `HasQueryFilter`, and no Migrations folder under `src/Infrastructure/Data`.

1. **Leaks through unfiltered reads.** `GetTodosQuery` reads `_context.TodoLists` with no filter. A missed handler or a raw query shows another company's data.
2. **ID-based access.** `DeleteTodoItem` uses `FindAsync(id)`. Update and detail commands likely do the same. Integer IDs are guessable, so a user could read or modify another tenant's row by ID unless every lookup is tenant-scoped.
3. **Child/parent mismatch.** `CreateTodoItem` takes a `ListId`. Without a check, a tenant A item could be attached to a tenant B list. Items must inherit the list's tenant.
4. **Write-side gaps.** If `TenantId` isn't stamped on insert, rows get a null or default tenant. Those rows are invisible, or visible to everyone.
5. **Tenant source trust.** If the tenant comes from a request header or body, users can spoof it. It must come from a validated claim.
6. **Existing data.** Current rows have no tenant. A non-null column breaks the migration, and a guessed default assigns data to the wrong company.
7. **Filter bypass.** `IgnoreQueryFilters`, raw SQL, `ExecuteDelete`/`ExecuteUpdate`, and the seeder or background jobs have no HTTP user. In those paths the tenant is null, so the filter returns nothing or everything.
8. **Identity coupling.** `ApplicationUser` has no tenant link. Users in several companies, admins and a support role all need an explicit rule.
9. **Performance and uniqueness.** There is no tenant index, and any unique constraints would need to include `TenantId`.
10. **Test and client breakage.** Functional tests assume a single user. DTOs and the generated API client may also change.

## Assumptions

- "Company" is the tenant. Each user belongs to exactly one tenant.
- A shared database with a `TenantId` column is acceptable. I'm not proposing a database per tenant.
- The tenant comes from a `tenant_id` claim issued at login.
- Existing data goes into one default tenant, or is migrated by an explicit mapping you supply.

## Plan

1. **Domain:** add `ITenantEntity { Guid TenantId }`. Implement it on `TodoList` and `TodoItem`. Optionally add a `Tenant` entity.
2. **Identity:** add `TenantId` to `ApplicationUser`. Emit it as a claim. Add `ITenantProvider` in Application, implemented in Web beside `CurrentUser`.
3. **Isolation in the data layer:**
   - In `ApplicationDbContext.OnModelCreating`, apply `HasQueryFilter(e => e.TenantId == _tenantId)` to both entities.
   - Add a `TenantInterceptor`, modelled on `AuditableEntityInterceptor`, that stamps `TenantId` on insert.
   - Reject changes to `TenantId` on update.
4. **Handlers:** `FindAsync` skips query filters, so replace it with `FirstOrDefaultAsync(x => x.Id == id)`. Validate the parent list in `CreateTodoItem`.
5. **Migration:**
   - Add a nullable column.
   - Backfill it.
   - Make it NOT NULL.
   - Add an index on `TenantId`.
6. **Failure mode:** if no tenant resolves, throw. Never fall back to "all rows".
7. **Tests:** add cross-tenant tests for read, update, delete and create-under-foreign-list. Each should return not found.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Unfiltered query leaks data | Handlers query `DbSet` directly, with no filter today | Global query filter on both entities, plus a cross-tenant test per handler |
| 2 | `FindAsync` bypasses filters | `DeleteTodoItem` and likely the update commands use it | Replace with filtered `FirstOrDefaultAsync` |
| 3 | Item attached to another tenant's list | `CreateTodoItem` accepts a raw `ListId` | Load the list through the filter and copy its `TenantId` |
| 4 | Tenant spoofed by the client | `IUser` has no tenant source yet | Take the tenant only from a signed claim, never from the request |
| 5 | Backfill breaks existing data | Current rows have no tenant | Nullable column, backfill, then NOT NULL, in separate steps |
| 6 | Null tenant in seeder or jobs | No HTTP user outside requests | Explicit tenant scope for those paths, and fail closed |
| 7 | Filter escaped by raw SQL or bulk ops | `IgnoreQueryFilters`, `ExecuteDelete` and raw SQL skip filters | Ban them in review and add an analyzer or test |
| 8 | Users in multiple tenants | `ApplicationUser` has no tenant model | Decide the rule up front (one tenant per user) and document it |
| 9 | Test suite and client churn | Functional tests assume one user | Add a tenant-aware test harness and update the DTOs and API client |
| 10 | Missing index slows queries | Every query gains a `TenantId` predicate | Index `TenantId`, or a composite index with the existing keys |

Riskiest: #1, an unfiltered query or ID lookup silently exposing one company's data to another.
