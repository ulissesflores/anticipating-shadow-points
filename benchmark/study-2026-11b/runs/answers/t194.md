**Assumptions:** The repo is `itsdangerous`, and "default signing digest" means `default_digest_method` on `Signer` and `HMACAlgorithm` (`src/itsdangerous/signer.py:54` and `:120`). Both currently use `_lazy_sha1`. I'm assuming this is a deliberate breaking change for 2.3.0, which is unreleased according to `CHANGES.rst`. I made no edits, so there is no plan file.

## What could go wrong

- **Existing signatures stop validating.** HMAC-SHA1 is 20 bytes and HMAC-SHA256 is 32 bytes. Every token, cookie and link signed before the upgrade fails with `BadSignature`.
- **Key derivation changes too.** `key_derivation` (default `django-concat`) hashes salt and secret with `digest_method`. The derived key changes along with the MAC, so there is no partial compatibility.
- **Rolling deploys split in two.** Old and new app instances reject each other's tokens until the rollout finishes.
- **Signatures get longer.** Output grows from about 27 to about 43 base64 characters. This can break length-limited cookies (4 KB), URLs, DB columns and QR codes. The tokens are also a different length from the old ones, so any code that assumes a fixed length breaks.
- **Dependents hard-code SHA-1 or rely on the default.** Flask sessions, Django-style signers and other frameworks may depend on the default. A wrong guess gives silent session logout or an interoperability failure.
- **Other implementations of the same format.** Services that verify tokens in other languages, or in older library versions, still use SHA-1.
- **This has been tried and reverted.** `CHANGES.rst` shows a switch to SHA-512 (:pr:`80`) that was changed back to SHA-1 (:pr:`113`). That is a sign of breakage in the wild.
- **Tests encode the old default.** `tests/test_itsdangerous/test_serializer.py:186-192` asserts that the default equals SHA-1 (`"[42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM"`). `:180` checks `_lazy_sha1` as the fallback default. These will fail or pass for the wrong reason.
- **FIPS laziness may be lost.** The 2.2.0 change deferred `hashlib.sha1` access so FIPS builds could override it. A new `_lazy_sha256` needs the same import-time care.
- **Docs contradict the code.** `docs/concepts.rst:137-152`, `docs/serializer.rst:82-103` and the docstrings in `signer.py` all say the default is SHA-1.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | All existing signatures and tokens invalid | `default_digest_method` is the only source of the digest; SHA-1 and SHA-256 MACs differ | Document a fallback-signer migration: `fallback_signers=[{"digest_method": hashlib.sha1}]` |
| 2 | Derived key changes | `django-concat` hashes salt and secret with the digest | Cover it in the migration notes; test the derived key explicitly |
| 3 | Rolling-deploy split | Old and new instances reject each other's tokens | Two-phase rollout: ship verify-both first, then flip the signing default |
| 4 | Longer signatures overflow limits | The signature grows from about 27 to about 43 characters | Note the size change in the changelog; check cookie and URL budgets |
| 5 | Dependents and cross-language verifiers assume SHA-1 | Flask, Django-style signers and other-language verifiers rely on the default | Search known dependents; announce it in a major or minor bump |
| 6 | Reverted before | SHA-512 was reverted in :pr:`113` | Read :pr:`80` and :pr:`113` first; ship an opt-in warning period |
| 7 | Tests lock in SHA-1 | `test_serializer.py:180,186-192` | Update the fixtures and keep a SHA-1 compatibility test |
| 8 | FIPS import-time failure | A SHA-256 default evaluated eagerly would break overrides | Add `_lazy_sha256` mirroring `_lazy_sha1` |
| 9 | Stale docs | `concepts.rst`, `serializer.rst` and docstrings still say SHA-1 | Update them together with the code |
| 10 | Changelog gap | 2.3.0 notes don't mention a breaking change | Add a prominent entry with upgrade steps |

Riskiest: #1, because every signature issued before the upgrade fails validation and users are logged out or links break.
