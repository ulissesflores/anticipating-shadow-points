| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Sessions silently stop working on plain HTTP | Browsers drop `Secure` cookies over HTTP (except `localhost`), so dev on `127.0.0.1`, LAN or Docker hostnames loses the session with no error | Document `https_only=False` for dev; release note |
| 2 | OAuth/SSO logins break | `Strict` withholds the cookie when the identity provider redirects back, so login state kept in `request.session` (e.g. by Authlib) is missing | Document using `same_site="lax"` for OAuth apps |
| 3 | Users arriving from links look logged out | `Strict` blocks the cookie on any cross-site navigation (email, Slack, search results) | Explain the tradeoff in the docs; `lax` opt-out |
| 4 | HTTPS ends at a proxy, app sees HTTP | The cookie is still marked `Secure` and the browser talks HTTPS, so this mostly works, but direct HTTP health checks or internal callers lose the session | Note this in the docs |
| 5 | Breaking change in a minor release | Starlette is at 1.10.0; existing apps change behaviour after upgrading with no code change | "Changed" release note; maintainer decides the version |
| 6 | Large test churn | Most `test_session.py` tests use `http://testserver` and will fail | Switch them to `https://testserver`; add opt-out test |
| 7 | Downstream test suites break | Users' TestClient tests on `http://testserver` lose sessions after upgrading | Release note tells them to use an `https://` base URL |
| 8 | Duplicate PR | `AI_POLICY.md` bans contributors who open duplicate PRs | Search existing PRs, issues and discussions first |
| 9 | Docs left inconsistent | `partitioned` and the examples still say to set `https_only=True` | Update them in the same PR |

Riskiest: #2, because `SameSite=Strict` silently breaks OAuth/SSO login callbacks that keep their state in `request.session`.
