## What's there today (Remix "Blues" stack: Prisma, Postgres, Fly)
- **No verification state anywhere.** `prisma/schema.prisma` has `User { id, email, createdAt, updatedAt }` and nothing more.
- **Sign-up logs you straight in.** `app/routes/join.tsx` calls `createUser` and then `createUserSession`.
- **Login only checks the password.** `verifyLogin` in `app/models/user.server.ts` does the check, then `app/routes/login.tsx` creates the session.
- **The session cookie only holds `userId`.** `requireUser`/`requireUserId` in `app/session.server.ts` never look at any account status.
- **No way to send email.** There's no mailer dependency or config. `mocks/index.js` sets up MSW with no handlers for an email provider.
- **Tests assume sign-up means logged in.** The e2e smoke test expects sign-up to land you logged in. The `cy.login()` helper (`cypress/support/create-user.ts`) calls `createUser` and builds a session cookie directly. The seed user `rachel@remix.run` is created the same way.
- **Fly runs migrations on deploy.** `fly.toml` has `release_command = "npx prisma migrate deploy"`.

## Ways this could go wrong (before planning)
1. **Existing users get locked out.** A new `emailVerifiedAt` column starts as NULL for everyone, so every current account fails the new check unless the migration fills it in.
2. **The check is only partly enforced.** If I only change `login.tsx`, sign-up still logs people in. Sessions already open, including 7-day "remember me" cookies, also stay valid.
3. **Token security mistakes.** Tokens could be guessable, stored in plain text, never expire, be reusable, or be compared in a way that leaks timing.
4. **Account enumeration.** Responses like "please verify" or "already exists" tell an attacker which emails are registered.
5. **Email delivery fails.** The provider may be down or emails may land in spam. If the user can't resend, they're stuck for good, and the email address can never be used to sign up again.
6. **Abuse of resend or sign-up.** Without rate limits, someone can make the app email-bomb a third party.
7. **Broken or open-redirect links.** The verification link needs the app's public base URL, which doesn't exist yet. `redirectTo` has to be carried through and still go through `safeRedirect`.
8. **Tests and CI break.** The smoke test, `cy.login()`, and the seed user all assume an account works the moment it's created. CI and e2e runs must not send real email.
9. **Missing secrets on deploy.** Mail provider credentials and the base URL have to exist on Fly before the release goes out.
10. **Race conditions.** The same token could be used twice at once, or someone could sign up again with an email that's still pending.

## Assumptions (stated instead of asked)
- "Verify" means clicking a single-use link sent by email. Codes and magic-link login are out of scope.
- Everyone who exists at deploy time is treated as already verified.
- Email goes out through a small `sendEmail()` wrapper around one HTTP provider (e.g. Resend or Postmark), configured with `EMAIL_API_KEY`, `EMAIL_FROM` and `APP_URL`. In development and the `start:mocks` e2e run, MSW intercepts those requests so nothing is really sent.
- A link expires after 24 hours. Resending invalidates any earlier link.

## Plan
1. **Schema and migration.**
   - Add `emailVerifiedAt DateTime?` to `User`.
   - Add a `VerificationToken { id, tokenHash @unique, userId, expiresAt, createdAt }` model that is deleted along with its user.
   - In the same migration, run `UPDATE "User" SET "emailVerifiedAt" = now()` to cover existing accounts.
2. **Model (`app/models/user.server.ts`).**
   - `createVerificationToken(userId)`: makes 32 random bytes, stores only their SHA-256 hash, and deletes the user's older tokens.
   - `consumeVerificationToken(raw)`: in one transaction, deletes the token and sets `emailVerifiedAt` if the token exists and hasn't expired.
   - `verifyLogin` keeps returning the user. The route decides what to do based on `emailVerifiedAt`.
3. **Email module.** A new `app/email.server.ts` with `sendVerificationEmail(email, token)`, which builds the link from `APP_URL`. Add an MSW handler for the provider in `mocks/`.
4. **Routes.**
   - `join.tsx`: create the user and token, send the email, and redirect to a new `/verify-pending` page instead of calling `createUserSession`.
   - New `verify.tsx` (`/verify?token=…`): consumes the token, then either logs the user in through `createUserSession` and goes to `safeRedirect(...)`, or shows "link invalid or expired" with a resend option.
   - `login.tsx`: if the password is right but the account isn't verified, show a generic "Please verify your email" message with a resend button, and don't create a session.
   - New `resend-verification` action: always answers with the same generic message, and is rate-limited per email (e.g. at most one token per 60 seconds, based on the newest token's `createdAt`).
5. **Defense in depth.** `requireUser` in `session.server.ts` checks `emailVerifiedAt` and logs the user out if it's NULL. That closes the stale-session gap. `requireUserId` only reads the cookie, so routes that rely on it need either the same check or a switch to `requireUser`.
6. **Seed and tests.**
   - The seed user and `create-user.ts` set `emailVerifiedAt: new Date()`.
   - Rewrite the smoke sign-up test to: sign up, see the pending page, read the token from a test-only path (the MSW handler logs it, or a `cypress/support/get-verification-token.ts` script reads it from the DB), visit `/verify`, and confirm the user is logged in.
   - Add vitest unit tests for the token functions: expired, reused, and wrong tokens.
7. **Configuration.** Add the new variables to `.env.example`. Before deploying, run `fly secrets set EMAIL_API_KEY EMAIL_FROM APP_URL`.

## Verification
- `npm run setup` on a copy of the database that already has users: they can still log in afterwards.
- `npm run validate`, which runs vitest, lint, typecheck and the Cypress e2e suite against mocks.
- Manually: sign up and confirm login is blocked. Check that an expired or reused link is rejected and that resend works. Check that a session cookie created before verification is rejected by `requireUser`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New column is NULL; Fly runs `migrate deploy` on release | Backfill `emailVerifiedAt = now()` in the same migration |
| 2 | Bypass through sign-up or old sessions | `join.tsx` logs in right away; `requireUser` only checks that the user exists | Remove auto-login; check verification in `requireUser` |
| 3 | Weak or reusable tokens | Nothing exists yet, so it's easy to store raw or long-lived tokens | 32 random bytes, store the hash, 24h expiry, one-time delete in a transaction |
| 4 | Account enumeration | Login and sign-up already return different errors | Generic messages on resend and the unverified-login path |
| 5 | Users stuck when email fails | No mailer exists; the unique email blocks signing up again | Resend flow; log send failures; let unverified users re-register |
| 6 | Email-bombing through resend | No rate limiting anywhere in the app | Cooldown per email (and ideally per IP) |
| 7 | Broken links or open redirect | No base-URL config; `redirectTo` passes through the email link | `APP_URL` variable; keep using `safeRedirect` |
| 8 | CI and e2e break | Smoke test, `cy.login()` and seed assume new users can log in | Seed and helpers set verified; e2e reads the token through mocks or the DB |
| 9 | Deploy without mail secrets | `.env.example` and Fly secrets lack them; CI copies `.env.example` | Validate env at startup; set Fly secrets before deploying |
| 10 | Token race or double use | Two clicks or prefetching email scanners can hit the link at once | Atomic `delete` that returns the row; check expiry in the transaction |

Riskiest: #1, existing users locked out. A missing backfill would lock out every current account in production on the next deploy.
