Read-only look at the repo: it's the Laravel RealWorld API. `app/Comment.php` has only `body` and `user_id` as fillable fields. `CommentTransformer` returns every comment unconditionally. `app/User.php` and the migrations have no role or moderator concept. I didn't edit any file, and I didn't write the plan file, because you said no edits.

## Assumptions
- A "moderator" is a new user role, either an `is_moderator` flag or a `role` column on `users`. No such concept exists today.
- "Hide" is a soft state, not a delete. Hidden comments stay in the database and are masked or omitted for everyone except the author and moderators.
- Only the comment's author can appeal. They get one open appeal per hide, and it must be filed within 7 days of the hide time, not the comment's creation time.
- A moderator, other than the original hider, decides the appeal: restore or uphold. Upholding is final.
- Hiding a comment keeps its API shape, and a moderator-only `hiddenAt` / status field is added.
- The 7-day window is enforced server-side, using a UTC timestamp.

## Ways this could go wrong
1. **Authorization gap:** the codebase has no roles, so the first moderator check is likely to be forgotten on one route.
2. **Leakage:** hidden bodies still come out through `Article::comments`, eager loads, `User::comments()` or the transformer.
3. **Appeal window errors:** the 7 days are counted from the wrong timestamp, ignore timezones, or aren't enforced on the server.
4. **Appeal abuse:** an author appeals repeatedly or concurrently, and double submits create duplicate appeals.
5. **Self-dealing:** a moderator hides a rival's comment, or decides an appeal on a comment they hid themselves.
6. **No audit trail:** the hide reason and the moderator ID aren't recorded, so there's nothing to review in a dispute.
7. **Migration risk:** a new nullable column or table has to apply cleanly to existing rows and be reversible.
8. **Client breakage:** RealWorld frontends expect a fixed comment shape, so a changed shape or a 403/404 on the author's own comment may break them.
9. **Notification gap:** the author never learns about the hide, so the appeal window expires unnoticed.
10. **Missing tests:** the repo has few tests for this area, so regressions in comment listing, delete or visibility would go undetected.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Missing authz on a route | No roles exist, so every check is new | Add a policy or middleware, plus a test per route |
| 2 | Hidden body leaks | `$with`, relations and `CommentTransformer` all expose the body | Mask in the transformer and use a visibility scope |
| 3 | Wrong 7-day window | Clock or timezone mistakes, and the wrong start time | Store `hidden_at` in UTC and check it server-side |
| 4 | Duplicate or repeated appeals | Nothing prevents repeated requests | Unique open appeal per hide, plus a transaction |
| 5 | Moderator conflict of interest | A single role can both hide and decide | A different moderator must decide the appeal |
| 6 | No audit trail | No history is stored | Log the moderator, reason and decision |
| 7 | Unsafe migration | Existing comments and a shared DB | Nullable columns, reversible `down()` |
| 8 | Client contract break | Frontends expect a fixed shape | Add fields only, and keep the author's view stable |
| 9 | Author unaware of hide | Window expires silently | Include status in the author's response, and notify |
| 10 | Thin test coverage | Few existing tests to catch regressions | Feature tests for hide, appeal, expiry and visibility |

Riskiest: #2, because a hidden abusive comment that still leaks through any listing path defeats the whole feature.
