## What I found
This is a small FastAPI + Tortoise ORM + Postgres service with one model, `TextSummary`, in `project/app/models/tortoise.py`.
- `id` is an implicit `SERIAL`, created in `migrations/models/0_*_init.py`.
- The integer shows up in several places:
  - Path params `id: int = Path(..., gt=0)` on GET, PUT and DELETE in `api/summaries.py`.
  - `SummaryResponseSchema.id: int` in `models/pydantic.py`.
  - `SummarySchema`, which is auto-generated from the model.
  - `crud.py` signatures.
  - The `generate_summary(summary_id, url)` background task.
  - Tests that assert 422 for bad or zero ids.

## Assumptions
- Existing clients send and parse integer ids and have already stored them.
- Clients can't all be upgraded at once, so I'm assuming a deprecation window.
- There is production data in Postgres, and a deploy may briefly run old and new code side by side.
- The integer primary key stays internal. Only the public identifier changes.

## Ways this could go wrong
- **Response type change.** Clients that parse `id` as an int will break if `id` becomes a string.
- **Stored int ids.** Bookmarks, URLs and foreign references held by clients stop resolving.
- **Ambiguous path parsing.** A `Union[UUID, int]` path param is order-sensitive. A 32-digit all-numeric string is a valid UUID and a valid int.
- **Backfill problems.** Backfilling UUIDs on a large table can lock it. `gen_random_uuid()` needs PG13+ or `pgcrypto`.
- **Rolling deploy.** Old code that doesn't know the new column can insert rows with no UUID.
- **Empty downgrade.** The existing migration's `downgrade` is empty, so rollback is unproven.
- **Background task.** `generate_summary` receives an id from the POST handler. If the id type and the lookup key drift apart, summaries never get written.
- **Error contract.** The 422 and 404 shapes tests rely on (`gt=0`, int type errors) will change.
- **Information leak.** Returning both the int and the UUID defeats the purpose, since the int remains enumerable. Dropping the int too early breaks clients.
- **Generated schema.** `pydantic_model_creator` changes output automatically when the model changes, so the contract can shift without anyone editing the schema.

## Recommended approach
1. Add a `uuid` column. It should be unique, indexed and non-null, with a default of `uuid4`. Backfill it in batches, then add the constraint. Keep the integer PK internal.
2. Make the routes accept either form. Try the UUID first, and fall back to an int only when the value is short and purely numeric. Route legacy ints through a clearly marked deprecated path that logs usage.
3. Phase the responses:
   - Phase A: keep `id` as an int and add `uuid`. Existing clients are unaffected.
   - Phase B: after the usage logs show legacy int lookups have stopped, flip `id` to the UUID, or move to `/v2`.
4. Pass the UUID to the background task and have `crud` look rows up by it.
5. Write a real `downgrade`. Update the tests, and add contract tests for both id forms.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | `id` response type changes | Clients parse `id` as an int, and POST returns `id` | Keep int `id` and add `uuid` first; flip in a later phase or under `/v2` |
| 2 | Stored int ids stop resolving | Clients hold ids in URLs and bookmarks | Accept both forms in the deprecation window; log legacy use |
| 3 | Path parsing ambiguity | `int` or `UUID` unions are order-sensitive | Parse the UUID first; treat only short numeric strings as ints; test edge cases |
| 4 | Backfill locks the table | Single `ALTER` or `UPDATE` on a live Postgres table | Add the column nullable, backfill in batches, then add NOT NULL and the index |
| 5 | Mixed-version rows during rollout | Old code inserts rows with no UUID | Set a DB default (`gen_random_uuid()` or `pgcrypto`) before deploying new code |
| 6 | Unsafe rollback | Existing `downgrade` is empty | Write and rehearse a downgrade on a data copy |
| 7 | Background task mismatch | `generate_summary` takes `summary_id` from the POST handler | Switch the task and `crud` to the same key; add an end-to-end test |
| 8 | Error contract changes | Tests expect 422 on `gt=0` and int type errors | Keep 422/404 shapes; update tests deliberately |
| 9 | Int ids stay enumerable | Responses still expose them | Remove the int from responses once clients migrate |
| 10 | Auto-generated schema drift | `pydantic_model_creator` follows the model silently | Pin an explicit response schema and add contract tests |

Riskiest: #1, changing the type of `id` in responses, because it breaks every existing client at once without any server-side error.
