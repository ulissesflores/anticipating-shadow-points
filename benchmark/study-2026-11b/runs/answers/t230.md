## Plan: email verification before login

**Where things stand:** this is a Remix app using Prisma/Postgres, cookie sessions and Fly.io. Right now `/join` logs the new user in immediately (`app/routes/join.tsx` calls `createUserSession`). `/login` only checks the password (`verifyLogin` in `app/models/user.server.ts`). The app has no email sending at all.

### Assumptions
- **Sending email:** I'll add a small `sendEmail` that calls Resend's HTTP API with `fetch`, so no new dependency. If `RESEND_API_KEY` isn't set (local dev and tests), it prints the email to the console instead.
- **Existing users:** they count as already verified. The migration fills in their `emailVerifiedAt`.
- **Links:** they last 24 hours, work once, and only a hash is stored. Resending is limited to once every 60 seconds.
- **No auto-login:** clicking the link verifies the email and sends the user to `/login`.
- **Signing up again with an unverified email:** this replaces the password and sends a new link. Otherwise someone could sign up with another person's email and lock them out, and the app has no password reset to recover from that.

### Steps
1. **Schema and migration:**
   - Add `User.emailVerifiedAt DateTime?` and a new `EmailVerificationToken` table (`tokenHash` unique, `userId` deleted along with the user, `expiresAt`).
   - In the same migration, run `UPDATE "User" SET "emailVerifiedAt" = "createdAt"` so existing users aren't locked out.
2. **Model functions** in a new `app/models/email-verification.server.ts`:
   - `createVerificationToken`: 32 random bytes in base64url; store the sha256 hash and delete the user's older tokens.
   - `consumeVerificationToken`: in one transaction, check the link, set `emailVerifiedAt` and delete the user's tokens.
   - `canResend`.
   - `createUser` gets a `{ verified }` option for the seed and tests.
3. **`app/email.server.ts`:** builds links from a new `APP_URL` setting, not the request's Host header, which an attacker could fake to put their own domain in the link. Add `APP_URL`, `RESEND_API_KEY` and `EMAIL_FROM` to `.env.example` and to Fly secrets.
4. **Routes:**
   - **`join.tsx`:** create the user (or update an unverified one), send the link, then redirect to `/verify-email/sent`. It no longer creates a session.
   - **`login.tsx`:** after the password checks out, refuse with "Please verify your email" and offer a resend button. The check comes after the password, so it doesn't tell strangers whether an email is verified.
   - **New `verify-email.tsx`:** opening the link shows a Confirm button, and only clicking it (a POST) uses up the link. Email security scanners open links automatically and would otherwise use them up.
   - **New `verify-email.sent.tsx`:** the "check your inbox" page.
   - **New `verify-email.resend.tsx`:** always gives the same reply, so it doesn't reveal which emails have accounts.
5. **Sessions:** no change needed, since `join` and `login` are the only places that create sessions. Optionally, `requireUser` could also log out anyone unverified as a second safeguard.
6. **Seed and tests:**
   - Mark the seed user as verified.
   - `cypress/support/create-user.ts` creates verified users, so `cy.login()` keeps working.
   - New `create-verification-link.ts` script and matching Cypress command for e2e tests to get a link.
   - Rewrite the sign-up smoke test: sign up → login is blocked → open link and confirm → login works. Add a test for a bad or expired link.
   - Add an msw mock for Resend in `mocks/index.js`, and Vitest tests for the token helpers.

### How to check it
- Run `prisma migrate dev` and confirm existing users got `emailVerifiedAt` filled in.
- Manual run-through in dev: sign up, find the link in the console, see login blocked, confirm, log in.
- Try a reused link, an expired link, and resending too quickly.
- Run `npm run validate`.
- Deploy to Fly staging with the secrets set and confirm a real email arrives.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New nullable column means everyone counts as unverified | Fill it in within the same migration; check row counts on staging |
| 2 | Email doesn't arrive, so no one can sign up | First time this app sends email; new secrets, sender domain and DNS setup | Set up the sender domain first; log send failures; add the resend button |
| 3 | Missing `APP_URL`/`RESEND_API_KEY` in production | Fly needs secrets set before deploy; local dev silently prints to the console instead | Fail on startup in production if they're missing; add to the README |
| 4 | Email scanners use up the link | Some mail systems open links automatically | Opening the link only shows a Confirm button; clicking it does the work |
| 5 | Someone signs up with another person's email | Email must be unique and there's no password reset | Signing up again on an unverified email replaces the password and sends a new link |
| 6 | Fake links pointing to an attacker's domain | Building links from the request's Host header can be spoofed | Build links from `APP_URL` only |
| 7 | Revealing which emails have accounts, or spamming them | The new resend and verify pages | Same reply every time; only say "unverified" after a correct password; 60s limit |
| 8 | E2E tests break | The sign-up test expects instant login; `create-user.ts` creates unverified users | Test users created verified; script to get a link; mock Resend |
| 9 | Leaked or guessed links | Links work like temporary passwords | 32 random bytes, stored hashed, 24h expiry, single use, cleared after use |
| 10 | Order problem during deploy | Code that reads `emailVerifiedAt` could run before the column exists | Fly runs `prisma migrate deploy` as the release step before new code starts; keep that |

Riskiest: #1 — if the fill-in step for existing users is missing or wrong, every current user is locked out the moment the deploy goes live.
