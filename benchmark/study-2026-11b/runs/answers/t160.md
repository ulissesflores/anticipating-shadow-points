**What the code does now.** This repo is `express-session` 1.19.0. Rolling is an existing opt-in flag. `index.js:109` reads it as `Boolean(opts.rolling)`, which makes it `false` when unset. `shouldSetCookie` (`index.js:489-491`) uses it: when it is true, an existing session gets a fresh `Set-Cookie` on every response. The `onHeaders` hook (`index.js:251-255`) then calls `req.session.touch()`, which pushes `expires` out to now + `maxAge`. So "rolling by default" means changing what happens when the option is left unset.

**Assumptions:**
- Expiry rolls only when `cookie.maxAge` or `expires` is set. Without one, the cookie lasts until the browser closes, and rolling just re-sends `Set-Cookie` on every response with no expiry to extend.
- An explicit `rolling: false` must keep working as a way to opt out.
- `saveUninitialized: false` must keep its current behaviour: no cookie for uninitialized sessions (`test/session.js:1197`).
- This is a semver-major change for a widely used library.

## Ways this could go wrong
1. **Opt-out lost.** A truthiness default such as `opts.rolling || true` would make `rolling: false` impossible to set.
2. **Silent breaking change.** Every app that never set `rolling` would start sending `Set-Cookie` on every response. That stops CDNs and proxies from caching those responses, and adds bytes to each one.
3. **Sessions that never end.** An app that relies on a fixed timeout from login would get sessions that last as long as the user keeps making requests. That can break compliance rules about absolute session limits.
4. **Background traffic keeps sessions alive.** Polling, health checks, static assets and XHR calls served through the middleware would all extend sessions.
5. **Store expiry falls out of sync.** The cookie expiry rolls, but the store's TTL only moves forward if `store.touch` or a resave runs (`shouldTouch`, `index.js:476`). A store without `touch` combined with `resave: false` would delete sessions whose cookies are still valid.
6. **Concurrent requests.** Parallel responses each set a slightly different expiry. That's mostly harmless, but it is more cookie churn.
7. **Docs, tests and HISTORY get out of step.** The README (`README.md:295-301`) and the "should default to false" test (`test/session.js:1159`) both say the default is false.
8. **Breaking with no warning.** The project changed the `resave` default with a deprecation step first (`index.js:121`). Skipping that step here would surprise users.

## Plan
1. **`index.js:108-109`:** change to `var rollingSessions = opts.rolling === undefined ? true : Boolean(opts.rolling)`. Optionally call `deprecate('undefined rolling option; provide rolling option')` to match the `resave` pattern. Update the JSDoc at `index.js:78`.
2. **`README.md` `##### rolling`:** state that the default is `true`. Explain that `rolling: false` opts out, and that expiry only rolls when `cookie.maxAge` is set. Note that the store needs `touch` or `resave: true` to keep its TTL in step.
3. **`test/session.js`:** in the `rolling option` block:
   - Change "should default to false" to "should default to true" and expect `Set-Cookie` on the second request.
   - Add a test that `rolling: false` suppresses the cookie on an unmodified session.
   - Add a test that, with the default and `saveUninitialized: false`, an uninitialized session still gets no cookie.
   - Add a test that, with `maxAge` set, `Expires` moves forward on the next request.
   - Check the other tests that call `createServer(null, …)` and assert `shouldNotHaveHeader('Set-Cookie')`, such as the `resave` and `cookie` tests. Pass `rolling: false` where a test is really about something else.
4. **`HISTORY.md` under `unreleased`:** add "**breaking:** `rolling` now defaults to `true`" and schedule it for the next major release.
5. **Verify:** run `npm test` and `npm run lint`. Run a small manual app with `cookie.maxAge: 60000`, make two requests a few seconds apart, and check that the second `Expires` is later than the first.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Opt-out broken | A `||`-style default turns `false` into `true` | Use `=== undefined`; add a test for `rolling: false` |
| 2 | Silent breaking change for all users | Widely used middleware; most apps never set `rolling` | Major version bump, HISTORY entry, optional deprecation warning |
| 3 | Responses can no longer be cached | `Set-Cookie` on every response blocks CDN and proxy caching | Document it; tell users to mount the session middleware only on routes that need it |
| 4 | Sessions with no hard end | Expiry slides forward forever while the user is active | Document it; suggest an absolute-timeout check in the app |
| 5 | Store deletes sessions with valid cookies | Store TTL rolls only through `touch` or `resave` | README note; test with a store that has `touch` |
| 6 | Polling keeps sessions alive | Every request through the middleware rolls the expiry | Docs: exclude polling and static routes |
| 7 | Uninitialized sessions get cookies | Default `true` combined with `saveUninitialized: false` | Keep the existing guard; add a regression test |
| 8 | Other tests break | Several tests assume no `Set-Cookie` with default options | Run the full suite; pin `rolling: false` where needed |
| 9 | Docs and code disagree | README says the default is `false` | Update README, JSDoc and HISTORY in the same change |

Riskiest: #2, because changing the default silently changes cookies, caching and session lifetime for every downstream app that never set `rolling`.
