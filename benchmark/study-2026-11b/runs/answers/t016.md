The plan is to change one line so that `rolling` is on unless someone sets it to `false`. The real work is in the tests, the docs and shipping it as a breaking change. I wrote the full plan to `claude-home/plans/make-sessions-roll-by-abundant-turtle.md`; no repo files were edited. The plan-approval tool wasn't available in this session, so the plan is below instead.

**Assumptions** (since I couldn't ask):
- "Roll by default" means making the current `rolling: true` behavior the default. The existing exception stays: with `saveUninitialized: false`, a session that was never used gets no cookie.
- Only `undefined` becomes `true`. An explicit `rolling: false` still turns it off, and no deprecation warning is added.
- The stored session's expiry already gets refreshed on every request whatever `rolling` is set to (`index.js:347-371`). What changes is that the browser cookie is now re-sent on every response too.
- Apps that never set `rolling` will start getting a cookie on every response, so this ships in the next major release (2.0.0).

**Changes**
1. **`index.js:109`**: `var rollingSessions = opts.rolling === undefined ? true : Boolean(opts.rolling)`. Also update the JSDoc at `index.js:78` to show `[options.rolling=true]`. `shouldSetCookie` (`index.js:486-492`) already handles rolling sessions, so no other code changes.
2. **`README.md`** (`##### rolling`, around line 295): say the default is `true`, and explain how to turn it off with `rolling: false`.
3. **`HISTORY.md`** (`unreleased`): add a breaking-change entry.
4. **`test/session.js`**:
   - In `describe('rolling option')` (around line 1158), change "should default to false" to "should default to true", expecting a cookie on the second request. Add a test that `rolling: false` keeps the old behavior.
   - Add `rolling: false` to the tests that check no cookie is sent when the browser sends its cookie back: around lines 1805, 2189 ("Set-Cookie only once for browser-session cookies"), 2476 and 2495 ("should not reset cookie…"). Fix any other failures from the full run the same way, in the tests and not in `index.js`.
5. **Verify**: run `npm test`, then a manual check with two GETs sharing one cookie. The second response should carry a `Set-Cookie` with a later `Expires`, and none when `rolling: false`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Breaking default for existing apps | Apps that never set `rolling` start getting `Set-Cookie` on every response | Release as 2.0.0; HISTORY/README explain how to opt out |
| 2 | CDN or proxy caching breaks | Many caches won't cache a response that has `Set-Cookie`, so cacheable GETs stop being cached | Document it; tell people to use `rolling: false` or skip the session on static routes |
| 3 | Sessions never time out for idle-polling clients | Background polling now extends the cookie forever | Document it; suggest a server-side absolute timeout |
| 4 | Concurrent requests overwrite each other's cookie | Parallel responses each send a cookie with a slightly different `Expires` | Harmless (the last one wins), but mention it in the docs |
| 5 | Existing tests fail | At least 5 tests assert no `Set-Cookie` when the cookie is sent back | Add `rolling: false` to those tests and run the full suite |
| 6 | Explicit falsy values handled wrong | `null`, `0` or `''` must stay false; only `undefined` turns rolling on | Use the `=== undefined` check, plus a test for `rolling: false` |
| 7 | Extra bandwidth and signing work | Every response now signs the cookie and sends the header | Small cost; mention it in the README |
| 8 | Unclear how it combines with `saveUninitialized: false` | Users may expect every visitor to get a cookie | Keep the current exception and its README note |
| 9 | People think the store expiry changes too | The store expiry already refreshes on every request; only the cookie changes | Say so in the HISTORY entry |

Riskiest: #1, the breaking default, because every existing app that never set `rolling` starts sending `Set-Cookie` on every response.
