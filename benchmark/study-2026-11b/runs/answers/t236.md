I've written the plan to `claude-home/plans/let-moderators-hide-abusive-glistening-wadler.md`. Nothing in the repo was edited, and nothing was run beyond reading the code.

**Assumptions**
- The app has no roles today, so I'd add a yes/no `users.is_moderator` field. Only the database or a seeder can set it.
- "Hide" means the comment is kept but marked hidden (`hidden_at`, `hidden_by`, `hidden_reason`). It is not deleted.
- Only the author and moderators can see a hidden comment, and it comes with a `hidden` flag.
- The 7 days start when the comment is hidden (`hidden_at`). Each hide allows one appeal.
- A moderator resolves the appeal as `upheld` (stays hidden) or `overturned` (unhidden). The moderator who hid the comment can't resolve its appeal.
- No notifications in this version, and the change is API only (this repo has no frontend).

**Changes**
1. **Database:** three new migrations:
   - add `is_moderator` to users;
   - add the three hide fields to comments;
   - a new `comment_appeals` table holding the comment, author, appeal text, status (`pending`, `upheld` or `overturned`), who resolved it, when, and a note.
2. **Models:**
   - `app/Comment.php` gets an `isHidden()` check, a link to its appeals, an `appealDeadline()` (hide date + 7 days) and a `visibleTo($user)` filter for listing.
   - A new `app/CommentAppeal.php` model.
   - `User::isModerator()` is added, and `is_moderator` stays out of the user fields the API can set.
3. **Permission checks:** these follow the existing pattern in `app/Http/Requests/Api/DeleteComment.php`. There are four new request classes: `HideComment`, `UnhideComment`, `AppealComment` and `ResolveAppeal`.
   - Permission failures return 403.
   - "Appeal window closed" or "already appealed" returns 422, so clients can tell the two apart.
4. **Routes,** all requiring login:
   - `POST` and `DELETE articles/{article}/comments/{comment}/hide`
   - `POST articles/{article}/comments/{comment}/appeal`
   - `GET moderation/appeals` and `PUT moderation/appeals/{appeal}`
   - These check that the comment belongs to the article. The existing `destroy` doesn't.
5. **Controllers:**
   - New `CommentModerationController` and `CommentAppealController`.
   - `CommentController@index` switches to the `visibleTo(auth()->user())` filter. The user can be null there, because logging in is optional for that endpoint.
   - Resolving an appeal as `overturned` unhides the comment, inside a single transaction.
6. **Response format:**
   - `CommentTransformer` adds a `hidden` field.
   - Only the author and moderators get a `moderation` block (hidden date, reason, appeal deadline, appeal status).
   - Authors never see who hid the comment (`hidden_by`).
   - A new `CommentAppealTransformer` formats appeals.
7. **Tests:**
   - New `CommentModerationTest` and `CommentAppealTest`, in the same style as `CommentTest.php`.
   - They cover permission failures, the public list filtering, an appeal on day 6 versus day 8 (using `Carbon::setTestNow`), duplicate appeals, both appeal outcomes, the hider not being allowed to resolve, and `PUT /user` not being able to make someone a moderator.
   - Check with `vendor/bin/phpunit` and `php artisan migrate:fresh` plus a rollback.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Users make themselves moderators | `UserController@update` saves whatever user fields are allowed; no roles exist | Keep `is_moderator` out of the allowed fields; test `PUT /user` |
| 2 | Hidden comments leak | Comments are returned in places other than `index` | Filter everywhere with the `visibleTo` scope; only author and moderators get the `moderation` block |
| 3 | 7-day window off by timezone | Hide date is compared to `now()`; app and DB timezones may differ | Store UTC, compare with Carbon, test with `setTestNow` |
| 4 | Two appeals at once | Two quick POSTs can both pass the "no appeal yet" check | Transaction with `lockForUpdate` |
| 5 | Comment from another article | Current routes don't check `{comment}` belongs to `{article}` | Check `article_id` in the new request classes |
| 6 | Hiding again after an overturn | "One appeal per hide" needs each appeal tied to a specific hide | Compare appeal `created_at` with `hidden_at` |
| 7 | Clients see new response fields | `hidden` is new and `index` now filters | New fields only, nothing removed or renamed |
| 8 | Moderator account deleted | `hidden_by` / `resolved_by` point at users | `onDelete('set null')` |
| 9 | Author deletes a comment under appeal | `destroy` deletes for good; appeals are deleted with it | Accept for now, or block deletion while an appeal is pending |

Riskiest: #1. If `is_moderator` can be set through the user endpoints, any user can make themselves a moderator.
