## Assumptions (non-interactive)
1. **One JSON file**, downloaded as `flasky-export-<username>-<UTC date>.json`. JSON fits the data's nested shape and needs no new dependencies.
2. **Self-service only.** A logged-in user can export only their own data. There is no `<username>` in the URL, so one user can't request another user's export. Admin export of other users and an API endpoint are out of scope.
3. **"Their data" means:**
   - **Profile:** username, email, name, location, about_me, member_since, last_seen, role name and confirmed.
   - **Posts:** all of them, with `body` (the raw Markdown) and timestamp.
   - **Comments:** every comment the user wrote, including ones a moderator has hidden (flagged with `disabled`), plus the id of the post each one is on.

   Other people's comments on the user's posts are left out, because they are other people's data. Followers and following lists are also left out, since you didn't ask for them; they're easy to add later.
4. **Never exported:** `password_hash`, `avatar_hash`, `role_id` and internal tokens.
5. **Size:** the file is built in memory with one query per table. That's fine at this app's scale; streaming is a later step if needed.
6. **Pinned versions stay as they are** (Flask 0.12.2, SQLAlchemy 1.1). The code must work with them, so no newer Flask features.

## Plan
1. **`app/models.py`:**
   - Add `User.to_export_dict()`, `Post.to_export_dict()` and `Comment.to_export_dict()`.
   - Use explicit allow-lists of fields. Don't reuse the existing `to_json()` methods: they output API URLs and leave out fields the export needs.
   - Write dates as ISO-8601 UTC.
   - Add a `schema_version` field and an `exported_at` timestamp.
2. **`app/main/views.py`:** add `GET /export`, protected by `@login_required`.
   - Query `current_user.posts` and `current_user.comments`, both sorted by timestamp.
   - Serialize with `json.dumps(..., ensure_ascii=False, indent=2)`.
   - Return a `Response` with `application/json; charset=utf-8`, `Content-Disposition: attachment; filename=...` and `Cache-Control: no-store, private`.
3. **`app/templates/user.html`:** add a "Download my data" button inside the existing `{% if user == current_user %}` block, next to Edit Profile.
4. **Unconfirmed users:** the auth blueprint sends unconfirmed users to `/auth/unconfirmed`, so they can't reach `/export` for now. I'm accepting that and noting it as a limitation.
5. **`tests/test_client.py`:** add tests covering:
   - Anonymous request → redirect to login.
   - Logged-in user → 200, attachment header, valid JSON with their posts and comments.
   - No `password_hash` anywhere in the output.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Leaking sensitive fields | The `User` model holds `password_hash` and `avatar_hash`; serializing it carelessly would include them | Explicit field allow-list, plus a test that `password_hash` is absent |
| 2 | Exporting someone else's data (IDOR) | Existing profile routes take `<username>`, so it's tempting to copy that pattern | No ID in the URL; only ever use `current_user` |
| 3 | Including other people's content | `post.comments` includes other users' comments on the user's posts | Export only comments where the author is the user; reference posts by id |
| 4 | File cached by a shared proxy or the browser | GET responses are cacheable, and production runs behind Heroku/Docker proxies | `Cache-Control: no-store, private` |
| 5 | Dates fail to serialize | `json.dumps` can't handle `datetime`, and Flask 0.12's `jsonify` uses RFC-822 dates | Convert to ISO strings yourself in `to_export_dict` |
| 6 | Garbled non-ASCII text or a broken filename | The default `ensure_ascii`, plus usernames inside a header | `ensure_ascii=False`, utf-8 charset, filename built from a sanitized username |
| 7 | Memory and time spikes for heavy users | `lazy='dynamic'` loads with `.all()`; slow-query logging is on | Fine at this scale; add a streaming or async job if exports grow |
| 8 | Unconfirmed users locked out | The `before_app_request` redirect sends them to `/auth/unconfirmed` | Document it, or exempt the endpoint if access-rights compliance requires it |
| 9 | Hidden comments left out or mishandled | Moderators hide comments by setting `disabled`; it's tempting to filter those out | Include them with a `disabled` flag |
| 10 | Export goes stale as the schema changes | New columns won't be picked up automatically | `schema_version` plus a test that checks the export's keys |

Riskiest: #1. A sloppy serializer would put password hashes and internal fields into a file that users download and share.
