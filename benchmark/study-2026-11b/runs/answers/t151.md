## What the code has today
This is the Laravel 5.5 RealWorld API, with JWT login through the `auth.api` middleware.
- **No roles:** the `users` table has no role or moderator column. The only permission check is "is this your comment?" in `app/Http/Requests/Api/DeleteComment.php:13-17`.
- **Comment lookup ignores the article:** comments are found by id alone. `CommentController::destroy` takes `$article` and never uses it, so `/articles/A/comments/{id of a comment on article B}` still resolves.
- **Every comment is shown:** `CommentController@index` returns all of an article's comments, and `CommentTransformer` has no hidden or visible field.

## Assumptions (no one to ask in this run)
- A moderator is a `users.is_moderator` boolean, set only through the database or seeder. It is not in `$fillable`, so `PUT /api/user` can't grant it.
- Hiding doesn't delete anything and can be undone. A hidden comment is visible, marked as hidden, only to its author and to moderators. Everyone else, including logged-out readers, doesn't see it.
- The 7 days are counted from `hidden_at`, on the server clock in UTC. The author gets one appeal per hide. A moderator either approves it (the comment comes back) or rejects it (final).
- This is API only; the repo has no frontend.

## Ways this could go wrong
1. Someone makes themselves a moderator through mass assignment if `is_moderator` ends up in `$fillable`.
2. A moderator hides, or an author appeals, a comment through another article's URL, because the comment lookup isn't tied to the article.
3. Hidden comments still show up because one read path skips the visibility filter.
4. The 7-day rule is checked in only one place, or against the wrong clock or time zone.
5. Two quick requests create two appeals.
6. Re-hiding a comment after approval reuses the old appeal or the old deadline.
7. The new response fields break existing clients or the RealWorld spec tests.
8. Approving an appeal updates the appeal but not the comment, leaving the two out of sync.
9. A moderator approves the appeal on their own comment.
10. The migrations fail on SQLite in tests because of `enum` or a foreign key added with `ALTER`.

## Plan
1. **Migrations:**
   - `users.is_moderator`.
   - On `comments`: `hidden_at`, `hidden_by` and `hidden_reason`, plus an index on `(article_id, hidden_at)`.
   - A new `comment_appeals` table with status `pending`/`approved`/`rejected`, who resolved it, and when. It's unique on `(comment_id, hide_at_snapshot)` so the database itself allows only one appeal per hide.
2. **Models:**
   - `User`: `isModerator()`.
   - `Comment`: `isHidden()`, `appealDeadline()`, `canBeAppealed()`, a `visibleTo($user)` filter and an `appeals()` relation.
   - A new `CommentAppeal` model.
3. **Permission checks:** four new form requests that follow the `DeleteComment` pattern: `HideComment`, `UnhideComment`, `CreateCommentAppeal` and `ResolveCommentAppeal`. Each also checks `comment.article_id == article.id`. The appeal request checks that the caller is the author, the comment is hidden, it's within 7 days, and there's no earlier appeal for this hide.
4. **Routes and controller:**
   - `POST`/`DELETE articles/{article}/comments/{comment}/hide`
   - `POST articles/{article}/comments/{comment}/appeal`
   - `GET moderation/appeals`
   - `POST moderation/appeals/{appeal}/approve` and `/reject`

   These go in a new `ModerationController`, which reuses the response helpers in `ApiController`.
5. **Reading comments:** `index` uses `visibleTo(auth()->user())`. The transformer adds a `hidden` flag, and adds the reason, deadline and appeal status only for the author and moderators.
6. **Approving:** runs in one database transaction that marks the appeal approved and clears the `hidden_*` fields.
7. **Factories and seeder:** add a moderator option and one seeded moderator.

## How I'll check it
Run `vendor/bin/phpunit`, extending `CommentTest` and adding a new `ModerationTest`. The tests cover:
- a non-moderator trying to hide (403);
- who can see a hidden comment;
- an appeal on day 6 (allowed) and day 8 (refused), using `Carbon::setTestNow`;
- a duplicate appeal, a mismatched article in the URL, approve/reject, and `PUT /user` trying to set the moderator flag.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Anyone can make themselves a moderator | `User` uses `$fillable`, and `PUT /api/user` passes its input straight through | Keep `is_moderator` out of `$fillable`; add a test |
| 2 | Comment from a different article | Comment lookup is by id only; `$article` is unused in `destroy` | Check `article_id` matches in every new request class |
| 3 | Hidden comments still visible | `index` returns all comments and other code may read the relation directly | Add `visibleTo` and test it as guest, other user, author and moderator |
| 4 | 7-day window wrong or skippable | The deadline could be computed in several places or with the wrong time zone | One `canBeAppealed()` in UTC; test with `Carbon::setTestNow` |
| 5 | Duplicate appeals | Two concurrent requests both pass the check | Unique `(comment_id, hide_at_snapshot)`; turn the clash into a 422 |
| 6 | Re-hiding reuses the old appeal or deadline | Restore then hide again on the same row | Store the hide timestamp on the appeal and match against the current `hidden_at` |
| 7 | Response changes break clients | The RealWorld spec fixes the comment JSON shape | Only add fields, never rename; add the details only for author and moderator |
| 8 | Appeal and comment get out of sync | Approving updates two tables | Wrap it in `DB::transaction` |
| 9 | Moderator approves their own appeal | The author is also a moderator | `ResolveCommentAppeal` refuses when the comment author is the caller |
| 10 | Migrations fail in tests | `enum` or a foreign key added with `ALTER` can fail on SQLite | Use a string status column; make the new foreign key columns nullable |

Riskiest: #1, anyone making themselves a moderator through mass assignment on `PUT /api/user`. It would hand the whole moderation feature to any logged-in user.
