I've written the plan to `<config>/plans/replace-the-integer-ids-functional-sedgewick.md` and edited nothing else. The idea is to add a UUID column as the public ID and serve it from a new `/v2/summaries` API. The current `/summaries` API keeps working with integer IDs.

## What the code does today
- `TextSummary` (`project/app/models/tortoise.py`) uses an automatic `SERIAL id` primary key.
- That key is exposed in `/summaries/{id}/` (`Path(..., gt=0)`) and in every response (`SummaryResponseSchema.id: int`, and the auto-generated `SummarySchema`).
- The background job `generate_summary` (`app/summarizer.py`) looks rows up by that integer.
- Production uses Postgres 17, but the CI tests run on SQLite with `generate_schemas=True`.

## Assumptions
- "Existing clients" are callers of `/summaries/...` that send integer IDs and read `id` as an integer. That contract stays the same; responses gain one extra `uuid` field.
- Nothing else references `textsummary.id`, so the integer can stay as the internal key.
- Picking a shutdown date for v1 is out of scope.

## Plan
1. **Model:** add `uuid = fields.UUIDField(unique=True, default=uuid.uuid4)`. Keep the integer `id` as the internal primary key, so the background job and the migration bookkeeping don't change.
2. **Migration**, written by hand (`migrations/models/1_<ts>_add_uuid.py`):
   - add the column as nullable;
   - fill existing rows with `gen_random_uuid()`;
   - then make it required, give it a default and add a unique index;
   - include a real `downgrade` that drops the column.
3. **Database functions** (`crud.py`): add `get_by_uuid`, `put_by_uuid` and `delete_by_uuid`. `post` returns both IDs.
4. **Schemas:**
   - v1 keeps `id: int` and adds `uuid: UUID`.
   - v2 gets explicit schemas where `id: UUID` is filled from the `uuid` column, with no integer anywhere.
5. **Routes:**
   - v1 stays the same, including its validation error messages. It gains `Deprecation` and `Link: rel="successor-version"` headers pointing to v2.
   - The new `app/api/summaries_v2.py` is mounted at `/v2/summaries` with `/{id}/` typed as a UUID.
6. **Tests:**
   - update the exact-match assertions in both summary test files for the new `uuid` field;
   - add a v2 test suite;
   - add a test that creates a record through v1 and reads the same record through v2.
7. **Rollout:** deploy the migration first, then the app. Announce v2, watch v1 traffic, and pick a shutdown date later.

**Verification:**
- Run `aerich upgrade`, `downgrade` and `upgrade` again on a dev database that already has rows, and check every row gets a unique `uuid`.
- Run pytest on both Postgres and SQLite.
- Check manually that the same record comes back from `/summaries/<int>/` and `/v2/summaries/<uuid>/`, and that `/v2/summaries/123/` returns 422.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | The migration is never tested on Postgres in CI | CI runs pytest on SQLite with `generate_schemas=True`; the aerich migration and `gen_random_uuid()` never run there | Add a CI job that runs `aerich upgrade` against Postgres 17 on seeded data |
| 2 | Filling and locking a large table | `UPDATE` on every row plus the unique index can lock `textsummary` | Fill in batches; use `CREATE UNIQUE INDEX CONCURRENTLY` outside a transaction |
| 3 | The extra `uuid` field breaks strict v1 clients or tests | Unit tests use exact `==` on responses; strict client deserializers may reject unknown fields | Update the tests; note the change in the changelog; drop `uuid` from v1 if strict clients exist |
| 4 | Test mocks fail response validation | `pydantic_model_creator` adds `uuid` to `SummarySchema`; mocked dicts without it cause 500s | Add `uuid` to every mock and fixture |
| 5 | The app and the migration are deployed in the wrong order | The model expects a required `uuid` column; Heroku releases the image with no migration step | Run the migration as a release step before the app goes live; keep the column nullable until it is filled |
| 6 | UUIDs behave differently on SQLite and Postgres | SQLite stores them as `CHAR(36)`, so comparison and case can differ from native `UUID` | Always compare as `uuid.UUID`; run the v2 tests on both databases |
| 7 | The integer ID still leaks through v1 | v1 remains open to enumeration, which is the problem UUIDs are meant to fix | Add deprecation headers, track v1 usage, and set a shutdown date |
| 8 | Two ID functions get mixed up | `crud.get(id)` and `get_by_uuid` sit side by side; a v2 route could call the integer one | Separate v2 module; tests where an int and a UUID would collide |
| 9 | The downgrade loses data | The current migration has an empty `downgrade`; dropping `uuid` loses mappings clients already stored | Never regenerate UUIDs; back up the table before downgrading |

Riskiest: #1 — the backfill migration is the only irreversible step, and the SQLite-only CI never runs it against the production database.
