Most of this change is already in the code. Commit `a51468c` (#152) moved new passwords to ASP.NET Identity's PBKDF2-HMAC-SHA512 at 210,000 iterations. Old HMAC hashes still verify and are upgraded on the next successful login (`src/Conduit/Features<home>:78-83`), so nobody has to reset. Account creation and password changes already write only the new format. My plan covers the gaps that are left. I read the code and git history but ran no builds or tests.

**Assumptions** (non-interactive run):
- "Stronger scheme" means Identity's PBKDF2 format, not Argon2 or bcrypt. Switching to those would add a dependency and isn't needed.
- Old hashes are exactly what the old code produced: a 64-byte HMAC-SHA512 keyed with "realworld", plus a 16-byte random salt.
- Database schema changes should be avoided, so no migrations.

**Ways this could go wrong** (checked against the code):
1. **Login can undo a password change.** Login loads the user, checks the old password, then writes a new hash. A password change in between gets overwritten, and the old password works again. Nothing guards against this.
2. **The upgrade can break login.** If saving the upgraded hash fails, the user gets a 500 error even though their password was correct.
3. **Login timing reveals which emails exist.** An unknown email returns immediately, while a real one runs 210,000 PBKDF2 iterations. The stronger hash makes that gap bigger.
4. **Users who never log in keep weak hashes.** The old scheme is a fast hash with a public key, so a database leak still exposes those accounts.
5. **Old and new hashes are told apart only by length (64/16 bytes).** A new hash is 61 bytes, so they don't collide today. A future format change could break this silently.
6. **Each login costs real CPU.** Without rate limiting, the login endpoint is an easy way to overload the server.
7. **Raising the iteration count later.** Hashes made with fewer iterations need to be flagged for an upgrade, and no test covers that today.

**Plan** (saved to `plans/store-passwords-with-a-golden-hollerith.md`):
1. **`Login.cs`:** save the upgraded hash only if the stored hash is unchanged since it was read, using `ExecuteUpdateAsync … WHERE Hash == oldHash`.
2. **Upgrade failures:** catch and log them so the login still succeeds.
3. **Unknown emails:** check the password against a fixed dummy hash so timing matches a real account.
4. **Tests:** add tests for the length check, the iteration-count upgrade, and a password change racing a login.
5. **Separate PR (recommended):** a one-off job that wraps every old hash in PBKDF2 behind a marker byte. That protects dormant accounts right away, with no schema change.

Validate with `dotnet run --project build/build.csproj -- test`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Upgrade-on-login undoes a password change | `Login.cs` saves the new hash with no concurrency check | Save only if the hash is unchanged (`WHERE Hash == oldHash`) |
| 2 | Dormant accounts keep weak hashes | Upgrade happens only at login; old key "realworld" is public | Wrap old hashes in PBKDF2 offline |
| 3 | Failed upgrade blocks a valid login | Save happens inside the login request and transaction | Catch and log; don't fail the login |
| 4 | Timing reveals registered emails | Unknown email skips the 210k-iteration check | Verify against a dummy hash |
| 5 | Old and new hashes confused | Detection relies only on 64/16-byte lengths | Add a marker byte; test the lengths |
| 6 | CPU exhaustion on login | 210k PBKDF2 iterations per attempt, no rate limit | Rate-limit the login endpoint |
| 7 | Future iteration bumps don't upgrade hashes | No test for the "needs upgrade" result | Add a lower-iteration test |
| 8 | Lost-update tests flaky on SQLite | Concurrency is hard to reproduce in tests | Test the conditional update directly |

Riskiest: #1. A concurrent login can silently restore an old password after the user changed it, for example after a compromise.
