## Context
This is a Remix Blues Stack app (Prisma/Postgres, cookie sessions, deployed on Fly). Today, `app/routes/join.tsx` creates the user and logs them in straight away by calling `createUserSession`. `app/routes/login.tsx` only checks the password through `verifyLogin` in `app/models/user.server.ts`. The app has no email-sending code yet, and the `User` model has no field for verification.

## Assumptions
- **Existing users:** they count as already verified, so only new sign-ups are affected.
- **Email provider:** there isn't one, so I'll add a small HTTP sender (e.g. Resend or Postmark via `fetch`), set by environment variables. In dev and tests it will be replaced by a mock (MSW) through the existing `mocks/index.js`.
- **Token:**
  - 32 random bytes, sent in the link as base64url.
  - Only its SHA-256 hash is stored.
  - It expires after 24 hours and works once.
- **Sessions:** unverified users get no session at all. No "limited" logged-in state.

## Steps
1. **Database** (`prisma/schema.prisma` plus a new migration):
   - Add `User.emailVerifiedAt DateTime?`.
   - Add an `EmailVerificationToken` model with `tokenHash @unique`, `userId`, `expiresAt` and `createdAt`; it is deleted when its user is deleted.
   - The migration sets `"emailVerifiedAt" = "createdAt"` for all existing users.
2. **User model** (`app/models/user.server.ts`):
   - `createVerificationToken(userId)` deletes any older tokens and returns the new raw token.
   - `consumeVerificationToken(raw)` hashes the token, finds an unexpired match, sets `emailVerifiedAt` and deletes the tokens, all in one `$transaction`.
3. **Email sender** (new `app/email.server.ts`): `sendVerificationEmail(email, url)`. The provider env vars are required only in production. Add an MSW handler that logs the verification link.
4. **Sign-up** (`join.tsx`): create the user and token, send the email, then redirect to a "check your inbox" page. It no longer calls `createUserSession`. `redirectTo` is carried through in the link.
5. **New `verify-email` routes:**
   - Opening a valid link verifies the email, logs the user in, and redirects using `safeRedirect`.
   - An invalid or expired link shows an error and a resend form.
   - The resend action always gives the same generic reply and is rate-limited (at most one token per 60 seconds per user).
6. **Login** (`login.tsx`): if the password is correct but `emailVerifiedAt` is empty, refuse with "Please verify your email" and a resend link. This message only appears after a correct password, so it doesn't reveal which emails have accounts.
7. **Extra safety** (`session.server.ts`): `getUser` and `requireUser` treat unverified users as logged out.
8. **Tests and tooling:**
   - `cypress/support/create-user.ts` and `prisma/seed.ts` create users already verified.
   - Update the smoke test: sign up, get the link from a new helper script, visit it, then use notes.
   - Add a Cypress case where logging in before verifying is refused.
   - Add Vitest tests for token expiry and single use.
   - Document the new env vars (`EMAIL_API_KEY`, `EMAIL_FROM`, `APP_ORIGIN`) in `.env.example` and the Fly secrets.

## Verification
1. Run `prisma migrate dev` and check that existing users got `emailVerifiedAt`.
2. Run the app with `npm run dev` and try it by hand:
   - Signing up sets no session cookie.
   - The link appears in the log; opening it logs you in at `/notes`.
   - Opening the same link again fails.
   - Logging in before verifying is refused.
3. Run `npm run validate` (unit tests, lint, typecheck, Cypress).

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | The new column is null for every current row | Backfill in the migration; check the row count after deploy |
| 2 | Verification emails never arrive | There's no email provider yet; production secrets could be missing | Require the env vars in production; check provider errors in logs |
| 3 | Some route still logs people in without verifying | `createUserSession` is called from `join.tsx` and the Cypress helper | Remove the call from sign-up; check verification in `requireUser` too |
| 4 | Stolen tokens from database or logs | Tokens grant login | Store only the hash; 24h expiry; single use; don't log links in production |
| 5 | Finding out which emails have accounts | Sign-up and resend can reveal whether an email exists | Generic replies; "not verified" only after a correct password |
| 6 | Resend abuse | Anyone can trigger emails, which costs money | 60s per-user limit; generic reply |
| 7 | Wrong link host on Fly | Request origin can differ behind the proxy | Use the `APP_ORIGIN` env var |
| 8 | Cypress and the seed user break | Test and seed users are created unverified | Mark them verified; add a helper that fetches the link |
| 9 | Users stuck if the link expires | One-time 24h links | Resend option on the error page and the login page |
| 10 | Migration fails or is slow on deploy | The Fly release step runs `migrate deploy` | Nullable column plus one `UPDATE`; test against a copy of the database |

Riskiest: #1. If the backfill is missed, every existing user is locked out as soon as the deploy goes out.
