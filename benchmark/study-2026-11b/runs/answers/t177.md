# Plan: make `[["username", "ip_address"]]` the default lockout

**Assumptions**
- This is django-axes at 9.0.0, the latest commit being "Prepare 9.0.0 release".
- "Together" means a combined lockout. A client is locked only when the same username fails from the same IP. In axes that is `AXES_LOCKOUT_PARAMETERS = [["username", "ip_address"]]`. It does not mean the "user OR ip" mode, which is `["username", "ip_address"]`.
- The change ships in a new major or minor release, because it changes security behaviour.
- Explicit settings keep working. The legacy flags `AXES_ONLY_USER_FAILURES`, `AXES_LOCK_OUT_BY_USER_OR_IP` and `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP` keep precedence over the new default.
- I only read the code and edited no files.

## Where the default lives
- `axes/conf.py:39-60` sets the default. The final `else` branch gives `["ip_address"]`, and the comment above it says the default will be that value once the legacy flags are removed.
- `AXES_USE_USER_AGENT` handling at `conf.py:54-60` does `[0]` indexing on the list. It must also work when `[0]` is already a list (the `else` branch does this).
- `axes/helpers.py:317-330` (`get_lockout_parameters`) and `get_client_parameters` (~333) already support nested lists, so no logic change is needed there.
- `axes/checks.py` has check W006 (`axes_lockout_params_check`, ~183). It requires `ip_address` in the parameters, and the new default passes.
- `axes/apps.py:40-53` inspects the parameters. I'd confirm it handles nested lists.

## Steps
1. **`axes/conf.py`**: change the final default from `["ip_address"]` to `[["username", "ip_address"]]`. Update the stale comment. Keep the legacy-flag branches as they are.
2. **User-agent handling**: confirm `AXES_USE_USER_AGENT` still appends correctly to the nested default. The existing `else` branch covers it.
3. **Tests**: find tests that assume IP-only locking by default. Search `tests/` for `ip_address` and `LOCKOUT_PARAMETERS`. Update them or pin them with `override_settings`. Add tests for these cases:
   - Same IP with different usernames: not locked after N failures for a single user.
   - Same username and IP: locked.
   - Same username from a different IP: not locked.
   - A legacy flag or explicit setting still overrides the default.
4. **Docs**: update the `AXES_LOCKOUT_PARAMETERS` entry in `docs/4_configuration.rst`, plus any default-behaviour text in `docs/3_usage.rst` and `docs/7_architecture.rst`.
5. **`CHANGES.rst`**: add a prominent "behaviour change" entry. It should give the one-line opt-out, `AXES_LOCKOUT_PARAMETERS = ["ip_address"]`.
6. **Optional**: emit a one-time deprecation or notice via the system checks framework for projects that set nothing, so the change isn't silent.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Brute-force protection weakens | One IP can now try unlimited different usernames, because each pair counts separately (credential stuffing). | Document it clearly. Tell users to add `AXES_LOCKOUT_PARAMETERS` with `ip_address` or a rate limiter. |
| 2 | Silent behaviour change on upgrade | Projects that never set the option change behaviour without any error. | Major-version bump, loud changelog, and a system-check notice. |
| 3 | Attacker rotates IPs against one account | A botnet or proxy pool resets the per-pair counter for each new IP. | Recommend `["username", "ip_address"]` (OR mode) for high-risk sites. |
| 4 | Legacy flag precedence confusion | The old flags are only read when the new setting is `None`. A new default must not override them. | Change only the final fallback and add tests for each legacy flag. |
| 5 | Existing tests assume IP-only locking | Many tests rely on the default and could fail or pass for the wrong reasons. | Audit them, pin the settings explicitly, and add new tests. |
| 6 | User-agent suffix breaks on nested default | `conf.py:54-60` mutates `[0]` in place. | Test `AXES_USE_USER_AGENT` combined with the new default. |
| 7 | Stale lockout records and cache keys | Existing `AccessAttempt` rows and cache entries were keyed IP-only, so they won't match the new scheme. | Note it in the upgrade notes. Old records expire or can be reset. |
| 8 | Username enumeration or casing issues | Pair locking depends on how usernames are normalised, and `AXES_USERNAME_CALLABLE` can differ. | Verify case handling and callable usage in tests. |

Riskiest: #1, the weaker brute-force protection, because the new default lets one IP try many usernames without being locked.
