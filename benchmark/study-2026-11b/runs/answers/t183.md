**Plan: make username + IP the default lockout key**

I made no edits, as you asked, and didn't write the plan file.

**Assumptions**
- "Username and IP together" means a combined key, `[["username", "ip_address"]]`. It does not mean "username OR IP", which is `["username", "ip_address"]`.
- This repo is django-axes. 9.0.0 is already prepared, so the change ships as a breaking change in the next major version, or as 9.1 with a loud note.
- Anyone who sets `AXES_LOCKOUT_PARAMETERS` explicitly, or any of the legacy flags, keeps their current behavior.

**What I found**
- `axes/conf.py:39-60` sets `AXES_LOCKOUT_PARAMETERS` to `None` by default. It then maps the legacy flags (`AXES_ONLY_USER_FAILURES`, `AXES_LOCK_OUT_BY_USER_OR_IP`, `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP`) onto it. The `else` branch falls back to `["ip_address"]`.
- `AXES_USE_USER_AGENT` mutates element `[0]` of that list. `isinstance(..., str)` makes it work with a nested list, so the new default is compatible.
- `axes/checks.py:183-200` (W006) warns when `ip_address` is absent. The combined key contains it, so no warning fires.
- `axes/handlers/database.py:180` and `axes/handlers/cache.py:82` special-case `== ["username"]`. They are unaffected.
- `docs/4_configuration.rst:93` documents the default as `["ip_address"]`. Lines 35-43 and 122-126 describe the legacy flags.
- `docs/5_customization.rst:181` and `CHANGES.rst` also need updating.
- Tests that depend on the default are in `tests/test_handlers.py`, `test_attempts.py`, `test_login.py`, `test_helpers.py`, `test_checks.py` and `test_logging.py`.

**Steps**
1. In `axes/conf.py`, change the final fallback to `[["username", "ip_address"]]` and update the "default value will be" comment. Keep the legacy-flag precedence unchanged. Make sure each settings load builds a fresh list, because `AXES_USE_USER_AGENT` mutates it.
2. Update the default in `docs/4_configuration.rst`. Add a security note to `docs/3_usage.rst` and `docs/5_customization.rst`. Explain how to restore IP-only locking with `AXES_LOCKOUT_PARAMETERS = ["ip_address"]`, and how to get "either" behavior with `["username", "ip_address"]`.
3. Add a "Breaking changes and upgrading" entry to `CHANGES.rst`.
4. Run the suite. Tests that assumed IP-only locking will fail. Fix each by setting `AXES_LOCKOUT_PARAMETERS=["ip_address"]` through `override_settings` where IP-only is what the test is about. Otherwise update the expectations.
5. Add new tests for four cases:
   - the default locks the `(user, ip)` pair;
   - the same IP with a different username is not locked;
   - the same username from a different IP is not locked;
   - the default combines correctly with `AXES_USE_USER_AGENT`.
6. Consider an `AXES_VERBOSE` startup log line or a system-check info message when the default is in effect. That makes the change visible to existing deployments.

**Verification**
- Run `python manage.py test` or `pytest` for the full suite.
- Run `mypy`.
- Manually check with the test project: three bad logins as user A from IP X lock out A@X, while B@X and A@Y can still try.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Weaker brute-force protection | An attacker who rotates IPs against one user never reaches the per-pair limit | Document it. Recommend `["username", "ip_address"]` (either) or a proxy rate limit |
| 2 | Password spraying goes unnoticed | One IP trying many usernames gets a fresh counter for each pair | Keep an IP-only option in the docs. Consider an additional IP key |
| 3 | Silent behavior change on upgrade | Deployments relying on the implicit default are now locked differently | Major-version bump, changelog entry, startup log |
| 4 | Legacy flags interact with the new default | The `None` fallback chain can mask or reorder the flags | Keep their precedence and add tests for each flag |
| 5 | Username-less or odd credentials | Requests with no username produce an empty key part and unclear lockouts | Test missing-username and truncated-username (9.0.0 change) cases |
| 6 | Mutation of the shared default list | `AXES_USE_USER_AGENT` edits `[0]` in place | Build a fresh list on each load and test it |
| 7 | Existing `AccessAttempt` rows | Old IP-based attempts may or may not count toward the new keys | Check the lookup filters and note it in the upgrade notes |
| 8 | Test suite churn | Many tests assume IP-only | Pin `override_settings` explicitly in each affected test |
| 9 | Username enumeration or lockout abuse | A per-user key lets someone lock a victim's pair from a shared or NAT IP | Document it. Use `AXES_NEVER_LOCKOUT_*` and cool-off settings |

Riskiest: #1, because the new default lets an attacker rotate IPs or spray usernames without ever reaching a lockout.
