This is already done on `master`. Commit `a51468c` ("modernize (#152)") switched password storage to a stronger scheme, and existing users keep their passwords. Nothing here needs rewriting; what's left is closing a few gaps around it. I edited no repository files; the plan is in `plans/store-passwords-with-a-agile-pixel.md`.

**What's already there:**
- **New hashes:** `src/Conduit/Infrastructure/Security/PasswordHasher.cs` uses ASP.NET Core Identity's v3 format: PBKDF2-HMAC-SHA512 with 210,000 iterations and a random salt stored inside the hash.
- **Old hashes still work:** the old format (HMAC-SHA512 keyed with the public string `"realworld"`, 64-byte hash, 16-byte GUID salt) is still accepted. It's recognised by its length and flagged for upgrade.
- **Upgrade on login:** `Features<home>` replaces an old hash after a successful login. Sign-up (`Create`) and profile edit (`Edit`) only write the new format.
- **Tests:** `PasswordHashingTests.cs` already covers this.
- **No database change needed:** the hash columns are `BLOB` / `varbinary(max)`.

## Ways this could go wrong
1. **Dormant accounts stay weak.** Users who never log in keep the old hash indefinitely, and since its key is public it's no better than a fast salted SHA-512.
2. **Misreading the format.** If a new-format hash were ever exactly 64 bytes with a 16-byte salt, it would be checked as an old one. Today the lengths are 61 bytes (new) and 64/16 (old), so they don't collide, but that depends on nobody adding a format later.
3. **Lost update.** A login that upgrades the hash and a password change running at the same time can collide. The login saves a hash of the *old* password, and the user's new password quietly stops working.
4. **Timing leak.** An unknown email is rejected right away, while a real one spends about 100 ms hashing. That makes it easy to tell which emails have accounts.
5. **CPU exhaustion.** Each login attempt now costs a lot of CPU, and nothing rate-limits the endpoint.
6. **Locked out on rollback.** Older builds can't read the new format, so rolling back leaves upgraded users unable to log in.
7. **Old hashes overwritten too early.** Upgrading on a failed login, or before the password was verified, would destroy the old hash. The current code and tests prevent this; keep it that way.
8. **Raising the cost later.** Increasing the iteration count without the automatic upgrade path would leave old hashes behind; with it, there's a burst of rehashing.
9. **Scope creep.** Moving to Argon2id would add a third-party package, lock-file changes and memory tuning.

## Assumptions
- PBKDF2-SHA512 through Identity counts as "stronger", so Argon2id is out of scope.
- No API or schema changes, and no forced resets.

## Plan (closing the gaps)
1. **Protect dormant accounts:** run a one-time job that re-hashes each old hash with PBKDF2 and marks it with a version byte. `Verify` checks wrapped hashes, and the next login stores a plain new-format hash. Running the job twice must change nothing.
2. **Fix the lost update:** in `Login.cs`, only write the upgraded hash if the stored hash hasn't changed since it was read (`ExecuteUpdateAsync … Where Hash == oldHash`).
3. **Fix the timing leak:** when no account matches the email, still verify against a fixed dummy hash.
4. **Make the iteration count configurable**, defaulting to 210k, so raising it later upgrades users automatically on login.
5. **Optionally**, add the framework's built-in rate limiter to `POST /users/login`.
6. **Tests:** wrapped-hash login, running the job twice, the concurrent password-change case, the unknown-email path still hashing, and an upgrade when the iteration count is raised. Validate with `dotnet run --project build/build.csproj -- test`, then seed an old-format row and log in through `make run-local`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Dormant accounts stay weak | Old hashes only upgrade on login; key `"realworld"` is public | One-time job re-hashes them with PBKDF2 |
| 2 | Lost update on rehash | Login save has no concurrency check; `Edit` can run at the same time | Write only if `Hash == oldHash` |
| 3 | Format misread | Old format detected only by 64/16 byte lengths | Version byte on wrapped hashes; length tests |
| 4 | Email timing leak | Unknown email returns before any hashing | Verify a dummy hash anyway |
| 5 | Login CPU exhaustion | 210k SHA-512 rounds per attempt, no rate limit | Rate limiter on login |
| 6 | Rollback locks users out | Old builds can't read the new format | Hasher reads all formats; roll forward only |
| 7 | Old hash lost before verification | Upgrading on a failed attempt would destroy it | Keep upgrade-after-success test |
| 8 | Raising iterations later | Needs the upgrade path and causes a burst of rehashing | Configurable count; rely on automatic upgrade |
| 9 | Argon2 scope creep | New package, lock files, memory tuning | Stay on Identity PBKDF2 |

Riskiest: #1 — users who never log in keep fast, publicly-keyed HMAC hashes indefinitely, so a database leak exposes them.
