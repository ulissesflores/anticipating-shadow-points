**Assumptions** (non-interactive, no files edited)
- This is `express-session` 1.19.0. The option is read at `index.js:109` as `Boolean(opts.rolling)`, so it defaults to `false`.
- "Roll by default" means `rolling` defaults to `true` when it is `undefined`. An explicit `rolling: false` still opts out.
- The planned change is small. At `index.js:109`, use `opts.rolling === undefined ? true : Boolean(opts.rolling)`. Then update the README `rolling` section, add a `HISTORY.md` entry, and adjust the tests in `test/session.js` near line 1158 and line 267 that assume the old default.
- Behaviour already in the code: `shouldSetCookie` (`index.js:491`) re-sends the cookie on every response when rolling is on. Sessions are touched at lines 251 and 347. Stores with `touch` get `store.touch` (line 363), and stores without it get a full resave.
- Release as a semver-major, or behind a documented opt-in. This changes observable defaults for every consumer.

**Ways it could go wrong (before planning)**
- Every response now emits `Set-Cookie`. That breaks CDN or proxy caching, and it adds cookie headers to static or public routes that sit behind the session middleware.
- Stores without `touch` take the resave path on every request. That means extra writes and lost-update races between concurrent requests.
- Stores that do implement `touch` (Redis and similar) get one extra round-trip per request, which adds load and latency.
- An idle session never expires while a client keeps polling. That undermines security policies that rely on idle timeouts, and it makes sessions effectively immortal. Rolling also doesn't enforce an absolute lifetime, so one needs to be added separately.
- Tests, downstream apps, and snapshot or header assertions that expect no `Set-Cookie` on unchanged sessions will fail.
- A session-less request combined with `saveUninitialized: false` must still not set a cookie. The HISTORY note at line 200 shows this was a past bug, so it can regress.
- Cookies with no `maxAge` or `expires` gain nothing from rolling but still pay the header cost.
- Docs and defaults diverge. Wrapper libraries and the README currently describe `false`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Breaking default change | Every consumer silently gets new behaviour | Semver-major, a HISTORY note, a README migration line |
| 2 | `Set-Cookie` on every response | `shouldSetCookie` returns true whenever rolling is on, which breaks CDN and cache behaviour | Document it, and advise `rolling: false` for public routes |
| 3 | Resave writes for stores without `touch` | The `shouldTouch` fallback becomes a full save | Warn in the docs, and recommend stores that implement `touch` |
| 4 | Extra store load | One `touch` per request on Redis or DB stores | Note the cost and suggest throttling via `unset` or a custom touch |
| 5 | Idle timeout never fires | Polling clients keep sessions alive forever | Add an absolute-lifetime guidance note or option |
| 6 | Regression with `saveUninitialized: false` | Past bug history at HISTORY.md:200 | Keep the existing tests at test/session.js:1199 and 1221 |
| 7 | Existing tests fail | Several tests assume the default is `false` | Set `rolling: false` explicitly in those tests and add tests for the new default |
| 8 | Concurrent-request races | Many parallel requests each rewrite expiry | Rely on the store's atomic `touch`, and document the limits |

Riskiest: #1, the silent breaking default change, which makes #2 and #3 hit every existing deployment at once.
