I wrote a plan for making lists and items belong to a company (tenant), and changed no repo files. It's at `claude-home/plans/make-every-to-do-list-partitioned-forest.md`. Right now there is no tenant concept at all: `GetTodos.cs` returns every list to every logged-in user, `ApplicationUser` has no extra fields, and `IUser` only exposes the user's id and roles.

## Ways this could go wrong (found in this code)
1. **Wrong or missing tenant source.** Login can use either a cookie or a bearer token, and both are built from the same user claims. If the company id isn't added to those claims, it's missing for one or both login styles.
2. **Filter evaluated once and cached.** EF Core builds its model once. A filter that copies the tenant into a local variable keeps the first request's value for every later request.
3. **Filter that fails open.** With no tenant set (seeding, background work, a broken claim), `TenantId == null` must match nothing, not everything.
4. **Writes aren't filtered.** EF filters only apply to reads. `CreateTodoItem` takes any `ListId`, and `UpdateTodoItemDetail.cs:35` reassigns `ListId`, so a user could attach or move an item into another company's list.
5. **Unique-title check leaks data.** `CreateTodoListCommandValidator` and `UpdateTodoListCommandValidator` check titles globally today. That reveals other companies' titles and blocks legitimate duplicates.
6. **`FindAsync` shortcut.** Four handlers use `FindAsync`, which returns an already-loaded entity without applying the filter.
7. **Seeding and tests.** `TrySeedAsync` and `TestApp.FindAsync/CountAsync` run with no logged-in user. Once filters are on, they would silently see nothing or fail to save.
8. **Template variants.** `#if` blocks for SQLite, PostgreSQL and SQL Server, API-only vs cookie login, and Angular vs React all need to still build.
9. **Existing data.** This repo recreates the database on start, so no migration is needed here. Real apps built from the template will need a migration plus filling in a company for existing rows.

## Assumptions
- Each user belongs to exactly one company. There is no switching between companies and no cross-company admin view.
- The company is identified by a `Guid TenantId` on `ApplicationUser`, carried as a `tenant_id` claim.
- Each user who signs up through the built-in identity endpoints gets a new company.
- The company id is never sent to or accepted from the client, so the generated frontend clients don't change.

## Approach
- **Domain:** add a `Tenant` entity and an `ITenantOwned` interface on both `TodoList` and `TodoItem`. Items store their own company id so their filter doesn't need a join.
- **Current company:** expose `IUser.TenantId`, read from the claim. A custom claims factory adds the claim at login for both cookie and bearer.
- **Reads:** a global query filter on `ApplicationDbContext` that reads the company from a context property (not a copied value) and matches nothing when it's missing.
- **Writes:** a `TenantInterceptor` that:
  - stamps the company on new rows;
  - refuses to change the company on existing rows;
  - checks that an item's list belongs to the same company.
- **Validation:**
  - Check that `ListId` refers to a list in the user's company in both item commands.
  - Make title uniqueness per company, backed by a unique index on `(TenantId, Title)`.
  - Replace `FindAsync` with filtered queries.
- **Seed and tests:** a default company for the seeded admin, `IgnoreQueryFilters()` in seed checks and test helpers, and a company id in the test user mock. Add tests showing one company can't read, change, delete or attach to another's data.
- **Verification:** `dotnet test`, the template matrix across all database and frontend variants, then a manual check with two registered users.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Item attached to another company's list | `CreateTodoItem` and `UpdateTodoItemDetail` trust the `ListId` from the request; read filters don't cover writes | Check `ListId` against the user's lists, plus a parent-company check in the interceptor |
| 2 | Filter keeps the first request's company | EF caches the model, so a copied value sticks | Filter on a context property; test with two companies in a row |
| 3 | Filter shows everything when company is missing | Seeding, tests and broken claims have no company | Match nothing when null; refuse to save without a company |
| 4 | Company claim missing for one login style | Cookie and bearer logins both come from the claims factory | Custom factory registered in both `#if` branches |
| 5 | Title check reveals or blocks across companies | The validators check titles globally today | Per-company check plus a unique index on `(TenantId, Title)` |
| 6 | `FindAsync` skips the filter | It can return an already-loaded entity unfiltered | Switch to filtered `FirstOrDefaultAsync` |
| 7 | Seeding and tests break silently | `TrySeedAsync`, `TestApp.CountAsync` and `FindAsync` run with no user | `IgnoreQueryFilters()` and an explicit company id |
| 8 | Company id changed on update | Nothing stops an edit to it | Interceptor refuses to change the company on existing rows |
| 9 | Template variant fails to build | Many `#if` database and frontend combinations | Run the template matrix |
| 10 | Existing real data breaks | Here the database is recreated; real apps keep theirs | Document a migration that fills in a company for existing rows |

Riskiest: #1. A user can attach or move an item into another company's list, because read filters don't stop writes and both item commands accept any `ListId`.
