## Context
This is the Flasky app (Flask 0.12, SQLAlchemy 1.1, Flask-Login). The data lives in three places in `app/models.py`:
- **User:** email, username, name, location, about_me, member_since, last_seen, role, confirmed.
- **Post:** body and body_html, linked to the author by `author_id`.
- **Comment:** body, body_html and `disabled`, linked to the author and the post.

The models already have `to_json()` methods, but those are built for the API. They return URLs and counts, not the data itself.

## Assumptions
1. The export is for "my data": only the logged-in user can download it, and only their own data. Admins don't get to export other users in this version.
2. The file is one JSON file (`flasky-<username>-<date>.json`), sent as an attachment. JSON can hold nested data and needs no new dependencies.
3. "Comments" means comments **the user wrote**, including ones a moderator disabled (marked `disabled: true`). Comments that **other people** left on the user's posts are their data, so the export only shows how many each post has.
4. `password_hash` and all tokens are left out. Follows are included only as lists of usernames, which is optional and cheap.
5. Downloads happen synchronously. Data per user is small, so there is no background job.

## How it could go wrong (considered before planning)
- **Data from the wrong user:** an IDOR through a `<username>` or `<id>` URL parameter.
- **Secrets leaking:** if the export reuses `__dict__` or `to_json`, `password_hash` or internal fields could end up in the file.
- **Other people's data leaking:** comments others made on the user's posts.
- **Stealing data through a GET link:** a GET export with no extra check can be triggered from another site. CSRF can't read the response, so the risk is low, but a POST with a CSRF token is cleaner.
- **Crashes on serialisation:** `datetime` values and `None` fields can break `json.dumps`.
- **Slow exports or timeouts** for heavy users: `lazy='dynamic'` relationships can trigger one query per post.
- **Missing records:** comments on deleted posts, or posts whose `author_id` is null.
- **Stored XSS or formula injection** if someone later opens the file in a viewer. Exporting the raw `body` is safe, but the file must be served as `application/json` with an attachment disposition.
- **The file going stale** when someone later adds a model field and forgets the export.
- **Caching of personal data:** a proxy or the browser could keep a copy without `Cache-Control: no-store`.

## Plan
1. **`app/models.py`:** add `User.export_data()`, which returns a plain dict:
   - `profile`: an explicit allowlist of fields, with dates as ISO-8601 strings.
   - `posts`: id, body, body_html, timestamp and comment_count, ordered by timestamp.
   - `comments`: id, post_id, body, body_html, timestamp and disabled.
   - `following` / `followers`: usernames, leaving out the user's automatic follow of themselves.
   - `exported_at` and `format_version`.

   It must use an allowlist, not `__dict__`.
2. **`app/main/views.py`:** add a route `@main.route('/export', methods=['POST'])` with `@login_required`. It must not take a user parameter; it always uses `current_user`. It does the following:
   - Build `json.dumps(current_user.export_data(), indent=2, ensure_ascii=False)` and wrap it with `make_response`, which is already imported.
   - Set `Content-Type: application/json; charset=utf-8`, `Content-Disposition: attachment; filename=...` and `Cache-Control: no-store`.
3. **`app/main/forms.py`:** add an empty `ExportForm(FlaskForm)` so the request carries a CSRF token. Pass it from the `user()` view, which is around line 60.
4. **`app/templates/user.html`:** inside the existing `{% if user == current_user %}` block, next to "Edit Profile", add a small POST form with a "Download my data" button.
5. **`tests/test_client.py`:** add tests that check:
   - An anonymous user is redirected to login.
   - A logged-in user gets a 200 response with an attachment header and valid JSON.
   - The file contains their post and comment, but not another user's post, comment or email.
   - `password_hash` is absent.
   - Disabled comments are included.
6. **Optional, for the API:** add `GET /api/v1/users/me/export` behind the existing token auth in `app/api/users.py`, reusing `export_data()`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Exporting another user's data (IDOR) | Most existing routes take `<username>` or `<id>` | No user parameter; always use `current_user` |
| 2 | Secret fields leak | `User` holds `password_hash`; `to_json` exists and could be extended carelessly | Explicit field allowlist; test that `password_hash` is absent |
| 3 | Third-party comments leak | Comments on your posts belong to other users | Export your own comments; only counts for others' |
| 4 | Export triggered from another site | A GET would bypass Flask-WTF CSRF | POST plus a CSRF token through `ExportForm` |
| 5 | JSON serialisation crash | `datetime` fields and `None` values | Use `.isoformat()` with None guards |
| 6 | Slow export / N+1 queries | `lazy='dynamic'` relationships cause one count query per post | One grouped count query; order once |
| 7 | Personal data cached | No cache headers today | `Cache-Control: no-store` |
| 8 | Export silently goes stale | New model fields won't appear automatically | `format_version` plus a test listing the expected keys |
| 9 | Disabled or orphaned comments skipped or crash | `disabled` flag; `post_id` can point to a deleted post | Include with the flag; keep the raw `post_id` |

Riskiest: #1. Exporting another user's data would leak a whole account in one request, so the route must only ever use `current_user`.
