# Plan: make username + IP the default lockout

I read the code but did not run anything or edit any file. The target is django-axes at `ba99261` (9.0.0 release prep).

## Context

The default lockout key is IP only. `axes/conf.py:42-51` sets `AXES_LOCKOUT_PARAMETERS = ["ip_address"]` when the setting is `None` and no legacy flag is set. A comment there says the default will only be settled once the legacy `AXES_LOCK_OUT_*` flags are removed. The new default is the combined parameter `[["username", "ip_address"]]`. That is the same result the legacy `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP=True` flag produces today.

## Assumptions

- This is a breaking behaviour change, so it goes in the next release as 10.0.0. It is not a patch to 9.0.0.
- Explicit settings keep working unchanged: an explicit `AXES_LOCKOUT_PARAMETERS`, `AXES_ONLY_USER_FAILURES`, `AXES_LOCK_OUT_BY_USER_OR_IP` and `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP`. Only the final `else` fallback changes.
- Users who want the old behaviour set `AXES_LOCKOUT_PARAMETERS = ["ip_address"]`.
- No new migration is needed. `AccessAttempt` rows are already keyed on username, IP and user agent (`axes/handlers/database.py:~190`). The cache handler builds its keys from `get_client_parameters`.

## Steps

1. **`axes/conf.py`**
   - Change the final fallback at line 51 to `[["username", "ip_address"]]`.
   - Update the stale comment at lines 37-38.
   - Check the `AXES_USE_USER_AGENT` branch at lines 53-60. It takes the `else` path and appends `user_agent` to the inner list. That gives `[["username", "ip_address", "user_agent"]]`, which is correct. Add a test for it.
2. **`axes/checks.py`** (`axes_lockout_params_check`, around line 183)
   - It already accepts nested lists that contain `ip_address`, so the default passes. No code change is needed.
3. **Handlers and utils** (`axes/handlers/database.py:180`, `axes/handlers/cache.py:83`, `axes/utils.py:39`)
   - Both handlers only special-case `== ["username"]`.
   - Confirm that the reset, lockout-check and `get_client_parameters` paths all work with a nested-list default when `username` is `None`. The cache and database handlers should give the same result. Add tests rather than changing code unless one fails.
4. **Docs and changelog**
   - `docs/4_configuration.rst:93`: change the default shown.
   - `docs/4_configuration.rst:~123`: update the deprecated-flag text.
   - `docs/3_usage.rst`, `docs/5_customization.rst` and `docs/2_installation.rst`: update any statement that the default is IP only.
   - `CHANGES.rst`: add a "Breaking changes and upgrading" entry. It should explain the new default, the credential-stuffing trade-off and the one-line opt-out.
   - Review the `README.rst` description of lockout.
5. **Tests**
   - Update tests that assume the IP-only default: `tests/test_attempts.py`, `test_handlers.py`, `test_login.py`, `test_helpers.py`, `test_logging.py` and `test_checks.py`.
   - Add a test that a different username from the same IP is not locked.
   - Add a test that the same username from a different IP is not locked.
   - Add tests for the explicit opt-outs, for the legacy flags and for the user-agent combination.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Weaker brute-force and credential-stuffing protection | One IP can try unlimited different usernames, and each pair gets its own counter | Say so in CHANGES. Document `["ip_address", ["username","ip_address"]]` as a hardened option |
| 2 | Silent behaviour change on upgrade | Anyone relying on the implicit IP-only default is changed with no setting touched | Ship in a major release. Put a prominent note in the upgrade section |
| 3 | Distributed attacks on one account | An attacker rotating IPs never reaches the limit for a single username | Recommend adding `"username"` as a separate parameter. Keep the opt-out easy |
| 4 | Lockout-bypass reports | Users who lock by IP only will see unlocked logins from other usernames | Explain it in the docs, with an FAQ entry |
| 5 | Existing tests encode the old default | Many tests assume IP-only, so failures could be masked by fixing assertions loosely | Update tests deliberately and add the new cross-user and cross-IP cases |
| 6 | `username=None` handling | The handler guard only checks `== ["username"]`. Missing usernames now create or key on a `None` username | Add tests for the `None` username on both handlers |
| 7 | Custom callables and legacy-flag interaction | Precedence between `AXES_LOCKOUT_PARAMETERS`, the legacy flags and the user-agent append is subtle | Test the combinations. Keep the legacy branch order unchanged |
| 8 | Cache and database handler divergence | The two handlers build lockout keys differently | Run the same behaviour tests against both handlers |
| 9 | Stale docs | The default appears in several docs files | Grep for `ip_address` and "default" across `docs/` and the README |

Riskiest: #1, weaker protection against brute force and credential stuffing from a single IP.
