# Plan: online visit booking with no double-booking per vet

This plan is based on a read-only look at the repo (Spring PetClinic, Spring Boot 4.1, JPA, H2/MySQL/Postgres). I edited no files and wrote no plan file, as you asked.

## What exists today
- `VisitController` already lets an owner book a visit for a pet at `/owners/{ownerId}/pets/{petId}/visits/new`.
- A `Visit` has only `date` (a `LocalDate`) and `description`. It has no vet and no time of day.
- The `visits` table is `(id, pet_id, visit_date, description)` in all three schemas (`db/h2`, `db/mysql`, `db/postgres`). It has no constraint on vet or time.
- With no vet or time on a visit, two bookings can't conflict yet. The feature needs the schema to change first.

## Assumptions
1. Visits go in fixed-length slots: 30 minutes, 09:00–17:00 on weekdays. The values live in config. Fixed slots mean "same vet, same time" is exact equality, so a plain unique constraint can enforce it. Variable-length visits would need overlap logic and a Postgres-only exclusion constraint.
2. The owner picks the vet. The vet must exist in `vets`, and specialty matching is out of scope.
3. The existing rule stays: the visit date must be in the future (today's check is `isAfter(now)`).
4. No authentication exists, so ownership checks stay as they are. This change adds none.
5. Existing visits have no vet. They stay valid and don't conflict with anything.
6. Cancelling and rescheduling are out of scope. A cancel would simply delete the row, which frees the slot.

## Approach
The database enforces the rule, and the app turns a violation into a friendly form error. A check in app code alone would still let two concurrent requests both pass.

1. **Schema (all three DBs).** Add `vet_id INTEGER` (nullable, FK to `vets`) and `visit_time TIME` to `visits`. Add a unique constraint on `(vet_id, visit_date, visit_time)`.
   - All three databases treat NULLs as distinct in unique constraints, so legacy rows with no vet are unaffected.
   - The schemas are re-run scripts, not migrations (no Flyway/Liquibase). Document the manual `ALTER TABLE` for existing MySQL/Postgres installs.
2. **Model.** In `owner/Visit.java`, add `@ManyToOne Vet vet` and `LocalTime time`. Don't add a visits collection to `Vet`, because `Vet` objects are cached through `CacheConfiguration`.
3. **Slot rules.** Add a small `VisitSlots` helper in `owner/` that checks a time is on the slot grid and within working hours, and lists the slots for a day. Keep it pure so it's easy to test.
4. **Availability query.** Add `VisitRepository` with `findBookedTimes(vetId, date)`. The form uses it to hide taken slots.
5. **Controller.** In `VisitController`:
   - Expose the vets list, as `minVisitDate()` is exposed today.
   - Add a GET endpoint that returns free slots for a vet and date, so the form can refresh the dropdown.
   - In `processNewVisitForm`, validate the slot grid, then save.
   - Catch `DataIntegrityViolationException` around `owners.save(owner)` and call `result.rejectValue("time", "visit.slotTaken")`. This is the authoritative check. Make sure the exception is raised on that call and not at a later commit. If it isn't, use a flush.
   - Keep the existing `setDisallowedFields("id", "*.id")`.
6. **View and i18n.** Update `pets/createOrUpdateVisitForm.html` with vet and time selects. Add the `visit.slotTaken` and related messages to every `messages_*.properties` file, with English as the fallback.
7. **Tests.**
   - Unit tests for `VisitSlots`.
   - A MockMvc test for the happy path and the slot-taken path.
   - A concurrency test: two threads book the same vet and slot, and exactly one succeeds.
   - A schema test on each database. The repo's existing MySQL and Postgres integration test setup can be reused.

## Verification
- Run `./mvnw test`, including the concurrency test.
- Run the app on H2, book a slot, then book it again for the same vet. The second attempt should show the "slot taken" error. A different vet at the same time should still succeed.
- Run the same check against MySQL and Postgres using the `docker-compose.yml` already in the repo.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Race condition if the rule lives only in app code | Two owners can submit the same slot at once; a read-then-write check passes for both | Unique `(vet_id, visit_date, visit_time)` constraint, then catch the violation |
| 2 | Three divergent schema files | H2, MySQL and Postgres are edited by hand, so one can drift | Change all three in one commit and run schema tests on each |
| 3 | No migration tool | Existing MySQL/Postgres databases won't pick up the new columns or constraint | Document the `ALTER TABLE` steps in the README and release notes |
| 4 | Constraint error surfaces at the wrong point | `save` is transactional, so a failure at commit can escape the `try/catch` and return HTTP 500 | Test the failure path and flush inside the guarded call |
| 5 | NULL vet on legacy rows | Unique constraints treat NULLs as distinct, so old rows would never conflict | State this as intended, and make `vet_id` required for new bookings in validation |
| 6 | Fixed-slot assumption is wrong | Real visits vary in length; an equality constraint misses overlaps | Confirm the assumption; if wrong, use a Postgres exclusion constraint or a locking check |
| 7 | Timezones and "today" | `LocalDate.now()` uses the server zone, so slot cutoffs can be off for owners elsewhere | Use one configured clinic zone for all comparisons |
| 8 | Cached `Vet` entities | The vets list is cached, so a visits collection on `Vet` would go stale | Keep the relation one-way from `Visit` to `Vet` |
| 9 | Slot enumeration and abuse | The availability endpoint and booking form are open and unauthenticated | Validate the vet, date range and slot; consider rate limiting |
| 10 | Missing translations | About ten message bundles, and a missing key shows raw text | Add keys to all bundles and rely on the English fallback |

Riskiest: #1, because a booking check that only runs in app code lets two concurrent requests both book the same slot.
