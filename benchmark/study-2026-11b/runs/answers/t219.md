I've written the plan to `claude-home/plans/lock-users-out-by-lively-knuth.md`; no repo files were edited. The change itself is small: one branch in `axes/conf.py`. Most of the effort goes into updating tests that quietly assume IP-only lockout, and into the docs.

**What I assumed**
- Only the case where nothing is configured changes. Explicit `AXES_LOCKOUT_PARAMETERS` settings and the deprecated `AXES_ONLY_USER_FAILURES` / `LOCK_OUT_BY_*` flags keep working exactly as now.
- `AXES_USE_USER_AGENT` used on its own keeps its documented meaning, IP address plus user agent (`[["ip_address", "user_agent"]]`). It does not quietly gain username as well.
- This breaks existing behaviour, so it ships as 10.0.0 with an upgrade note.

**Plan**
1. **`axes/conf.py:36-60`**
   - Today the last `else` sets `["ip_address"]`. Split it into two cases:
     - `AXES_USE_USER_AGENT` alone gives `[["ip_address", "user_agent"]]`, as it does now.
     - No flags at all gives `[["username", "ip_address"]]`.
   - Fix the outdated comment on line 37.
   - Build a new list each time, because the user-agent branch changes `[0]` in place.
2. **No logic changes elsewhere.** The code that builds lockout lookups, the database and cache handlers, `reset_request` and the `ip_address` check (warning W006) already handle the combined form. W006 still passes because `ip_address` is part of the pair. With verbose logging on, the startup message will read "blocking by combination of username and ip_address".
3. **Docs**
   - `docs/4_configuration.rst:93`: change the default value.
   - `docs/2_installation.rst`: add an upgrade note: set `AXES_LOCKOUT_PARAMETERS = ["ip_address"]` to keep the old behaviour.
   - Check the wording in `docs/3_usage.rst` and `docs/5_customization.rst:181`.
   - `CHANGES.rst`: add a "Breaking changes" entry.
4. **Tests**
   - Find the tests in `test_login`, `test_handlers`, `test_middleware`, `test_attempts` and `test_helpers` that rely on IP-only lockout without setting it, and pin each with `@override_settings(AXES_LOCKOUT_PARAMETERS=["ip_address"])`. Don't pin it globally in `tests/settings.py`, or nothing would test the real default.
   - Add three tests:
     - How the default is chosen: no flags, each legacy flag, and the user-agent flag alone.
     - Same IP with a different username is not locked, and the same username from another IP is not locked.
     - A failure with no username is stored with an empty username and does not lock out other users.
5. **Verification:** run the full `pytest` suite and `mypy axes`. Then check by hand: fail N logins as user A, confirm A is locked out while user B can still log in from the same IP, and confirm that setting `["ip_address"]` brings back the old behaviour.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Weaker protection against one IP trying many usernames | Under the new default, a single IP gets the failure limit (3) for every username, so password spraying and credential stuffing from one IP are no longer stopped | Document it clearly; suggest `["ip_address", ["username","ip_address"]]` for sites with high exposure |
| 2 | Silent behaviour change on upgrade | Sites that never set the parameter switch modes with no warning | Major version bump, CHANGES "Breaking" entry, upgrade note giving the one line that restores the old behaviour |
| 3 | Many existing tests break | Lots of tests rely on the IP-only default without setting it | Pin those tests one by one; don't pin globally |
| 4 | Legacy user-agent flag changes meaning | The no-flags branch feeds the `AXES_USE_USER_AGENT` handling, so the user agent would be added on top of username+IP | Give user-agent-alone its own case; add a test for it |
| 5 | Shared list changed in place | `conf.py` modifies `[0]` in place, and the new default is a nested list | Build a new list literal in each branch |
| 6 | No-username attempts behave differently | Failures without a username are stored with an empty username plus the IP, and the `== ["username"]` guard doesn't apply to them | Add a test for no-username failures; document the behaviour |
| 7 | Locked-out IP can still browse other pages | Page requests carry no username, so they no longer match a lock | Document that lockout now applies only to login attempts |
| 8 | Reset tools need both username and IP | `reset_request` needs both values for combined records, so resetting by IP alone may miss records | Document it in the reset/CLI docs; add a test |
| 9 | Unchanged rows left in existing databases | Records stored under the old default don't match the new lookups | Note in the upgrade guide: run `axes_reset` after upgrading if needed |

Riskiest: #1. The new default no longer stops one IP from trying many usernames, which is a quiet security downgrade for sites that relied on the old default.
