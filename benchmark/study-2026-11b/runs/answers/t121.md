## Plan: expose UUIDs on `/summaries` without breaking existing clients

**Current state.** The API is FastAPI with Tortoise ORM, Postgres 17 and aerich migrations. The only resource is `/summaries`. Its ID is `TextSummary.id`, an auto-incrementing integer (`SERIAL`). That ID is exposed in:
- the paths `GET`, `PUT` and `DELETE /summaries/{id}/`, which only accept integers above 0;
- the response field `SummaryResponseSchema.id: int`;
- `SummarySchema`, which is generated from the model.

**Assumptions** (I couldn't ask, so I assumed these):
- "Keep existing clients working" means today's `/summaries/...` URLs and response shapes don't change during a deprecation period.
- The integer stays as the internal primary key. The UUID is added as a second, unique public key.
- New clients use a versioned `/v2/summaries/`, where `id` is a UUID.
- The production deploy (Heroku, via `release.sh`) doesn't run `aerich upgrade` today, so the migration needs to be run as an explicit step.

**Steps**
1. **Model** (`project/app/models/tortoise.py`): add a `uuid` field: unique, filled automatically with a random UUID. Build two response schemas from the model:
   - v1: integer `id` plus a new `uuid` field.
   - v2: only the UUID, returned under the name `id`.
2. **Migration** (new aerich file under `project/migrations/models/`): hand-written SQL that is safe on a table with existing rows:
   - add a nullable `uuid` column;
   - fill existing rows with `gen_random_uuid()`, which is built into Postgres 13 and later;
   - set that as the column default and make it `NOT NULL`;
   - add a unique index;
   - write a real downgrade that drops the column.
3. **CRUD** (`project/app/api/crud.py`): add one lookup helper that accepts either an integer or a UUID. `get`, `put` and `delete` all use it. `post` returns both keys instead of only the integer.
4. **v1 routes** (`project/app/api/summaries.py`):
   - Paths accept either an integer above 0 or a UUID.
   - Responses keep the integer `id` and add a `uuid` field. Adding a field doesn't break clients that read JSON.
   - Responses carry `Deprecation` and `Sunset` headers.
5. **v2 routes** (new `project/app/api/summaries_v2.py`, mounted at `/v2/summaries` in `project/app/main.py`):
   - Paths accept only UUIDs. A malformed value gets a 422 error.
   - `id` in responses is the UUID, and the integer is never exposed.
6. **Background summary job** (`project/app/summarizer.py`): it keeps using the internal integer ID, so it needs no change.
7. **Later, in a separate release**: once logs show no v1 integer traffic, retire integer lookups (for example, return 410).

**Verification**
- Run the migration against existing data. Then confirm no row has an empty `uuid` and every `uuid` is unique.
- The existing `tests/test_summaries.py` and `tests/test_summaries_unit.py` must pass unchanged, because they are the backward-compatibility contract. Only the unit-test mocks need updating, to include `uuid`.
- New tests:
  - v1 lookup by UUID;
  - a full create/read/update/delete cycle on v2;
  - v2 rejects an integer ID with 422;
  - v2 returns 404 for an unknown UUID.
- Run pytest and the flake8/black/isort checks that the prod Dockerfile enforces. Rehearse the migration on a copy of production data first.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Migration not applied in production | `release.sh` only swaps the image; it never runs `aerich upgrade` | Add an explicit migrate step before the image swap; the new code depends on the column existing |
| 2 | Backfill locks or fails on a populated table | Adding the column, filling it and making it `NOT NULL` on `textsummary` in one go | Run the steps in the stated order; use a concurrent index build if the table is large; rehearse on a copy |
| 3 | Clients break if `id` changes type in place | Many clients parse `id` as an integer | Never change v1's `id`; put the UUID in a new `uuid` field and in `/v2` |
| 4 | Enumeration risk remains | v1 still accepts integer IDs until sunset | Set a sunset date, watch v1 integer traffic, then return 410 |
| 5 | Rows created without a UUID | Something writing outside the ORM would skip the app-side default | Database-level `DEFAULT gen_random_uuid()` plus `NOT NULL` |
| 6 | Integer/UUID path ambiguity | v1 accepts either type, and the current error messages are pinned by tests | Try the integer first, then the UUID; keep the existing 422 message for 0 so current tests stay green |
| 7 | Unit-test mocks get out of sync | `test_summaries_unit.py` mocks return dicts without `uuid` | Update the mocks and add a schema test |
| 8 | Downgrade loses data | The init migration's downgrade is empty | Write a real downgrade; take a backup before migrating |
| 9 | Lookups by UUID get slow | No index on the new column | The unique constraint also serves as the index |

Riskiest: #1. The production deploy never runs migrations, so new code shipped before the `uuid` column exists would fail on every request.
