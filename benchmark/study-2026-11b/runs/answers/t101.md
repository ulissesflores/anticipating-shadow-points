## Assumptions
- **What counts as the "default".** `AXES_LOCKOUT_PARAMETERS` is the only switch. Today, when it is unset and no old flag is set, it falls back to `["ip_address"]` (`axes/conf.py:51`). The new fallback becomes `[["username", "ip_address"]]`.
- **Users who already chose a setting.** Anyone who sets `AXES_LOCKOUT_PARAMETERS` explicitly, or uses the deprecated `AXES_ONLY_USER_FAILURES` / `AXES_LOCK_OUT_BY_*` / `AXES_USE_USER_AGENT` flags, keeps exactly today's behaviour.
- **Version.** 9.0.0 has just been released, so this is a breaking change for the next major release (10.0.0) with an upgrade note, not a patch.

## Ways this could go wrong
1. **Security gets weaker.** One IP can try many usernames (password spraying) without being blocked, because each username/IP pair has its own counter. The `axes.W006` check (`axes/checks.py:183`) only warns when `ip_address` is missing entirely, so it stays silent.
2. **Silent change on upgrade.** Sites that never set the option change behaviour without any warning.
3. **A trap in the deprecated `AXES_USE_USER_AGENT` handling** (`conf.py:53-60`). If the new default is simply put in the shared fallback, the code that appends `user_agent` sees a list and adds to it. The result is `[["username","ip_address","user_agent"]]` instead of today's `[["ip_address","user_agent"]]`.
4. **Cache handler loses lockouts.** Cache keys are built from the lockout parameters (`helpers.make_cache_key_list`). On deploy every key changes, so all current lockouts and failure counts are dropped.
5. **Cache key collisions.** `make_cache_key_list` joins the values with no separator, so username `a1` at IP `2.3.4.5` gives the same key as username `a` at IP `12.3.4.5`. With username in the default key, an attacker can choose a username that lands on someone else's key.
6. **Requests with no username.** The middleware or signal path may run without credentials. The empty username is skipped when the key is built, so the cache key collapses to an IP-only key. The database handler would instead filter on `username=None`, so the two handlers can disagree.
7. **Tests that assume IP-only.** Many tests rely on the old default. Some will fail; worse, some may keep passing for the wrong reason.
8. **Docs and messages go stale.** The configuration table (`docs/4_configuration.rst:93`), the migration guide (`docs/2_installation.rst:160`), the `conf.py:38` comment and the startup log in `apps.py` all describe the old default.

## Plan
1. **`axes/conf.py`:** set the new default only in the final `else` branch, i.e. when no deprecated flag is set. Keep the `AXES_USE_USER_AGENT` path producing `[["ip_address","user_agent"]]`; the cleanest way is to apply it to `["ip_address"]` before choosing the new default. Update the comment on line 38.
2. **`axes/checks.py`:** add an Info-level check when `AXES_LOCKOUT_PARAMETERS` is unset, saying the default changed and how to restore it (`AXES_LOCKOUT_PARAMETERS = ["ip_address"]`).
3. **Optional hardening:** put a separator in `make_cache_key_list`. This changes keys too, so it belongs in the same release that already drops cached state.
4. **Docs:** update the configuration table and the customization page. Add a "Breaking changes" entry to `CHANGES.rst` covering the opt-out, the spraying trade-off and the cache reset.
5. **Tests:**
   - Pin `AXES_LOCKOUT_PARAMETERS=["ip_address"]` in the tests that rely on IP-only behaviour.
   - Add tests that check the default value and the lockout outcome: same IP with a different username gets in, same username from the same IP is blocked.
   - Add a test for the legacy `AXES_USE_USER_AGENT` mapping.
   - Add a test for the new check.
6. **Verify:** run the full test suite with both the database and cache handlers, and run `manage.py check` with and without the setting.
