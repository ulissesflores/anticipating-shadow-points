## Ways this could go wrong (before planning)

1. **Strict breaks logins that come from other sites.** OAuth or OIDC callbacks arrive as a top-level navigation from the identity provider's domain. With Strict, the browser doesn't send the session cookie on that request, so the OAuth `state` stored in the session (Authlib and similar libraries do this) disappears and the login fails.
2. **Strict makes users look logged out when they follow a link in.** Clicking a link from email, Slack or a search result opens the page without the session. The page renders as anonymous, and a reload fixes it, which is confusing.
3. **Secure breaks plain-HTTP setups.** Chrome and Firefox accept Secure cookies on `http://localhost`, but Safari has historically not, and a LAN IP or a hostname like `http://myapp.test` won't work. The session silently fails to stick.
4. **`TestClient` breaks.** It defaults to `http://testserver`, and httpx's cookie jar won't send a Secure cookie back over http. Starlette's own `tests/middleware/test_session.py` tests use http, and so do many downstream test suites.
5. **Large knock-on impact.** FastAPI and other frameworks re-export `SessionMiddleware` with Starlette's defaults, so every app that relied on them changes behaviour when it upgrades.
6. **Docs drift.** `docs/middleware.md:235-239` states the old defaults. The `partitioned` note tells users to set `https_only=True`, which becomes redundant.
7. **Stale cookies right after upgrade.** A browser already holds a Lax, non-Secure cookie. The next write replaces it with new flags, so it's mostly harmless, but it's worth one test.
8. **Duplicate PR.** `AI_POLICY.md` threatens a ban for duplicate PRs.
