## What I found

- **No tenant concept exists yet.** `ApplicationUser` (`src/Infrastructure/Identity/ApplicationUser.cs`) is an empty `IdentityUser`. `IUser` (`src/Application/Common/Interfaces/IUser.cs`) only exposes `Id` and `Roles`.
- **No handler filters by user.** For example, `GetTodosQuery` (`src/Application/TodoLists/Queries/GetTodos/GetTodos.cs:43`) returns every list. `UpdateTodoItemDetail` (`…/UpdateTodoItemDetail.cs:35`) sets `ListId` to whatever the client sends.
- **Database setup is simple.** There are no migrations: `ApplicationDbContextInitialiser` calls `EnsureDeleted` then `EnsureCreated` and seeds a "Tasks" list. That seeding runs with no HTTP user.
- **Registration is the stock Identity API.** `MapIdentityApi<ApplicationUser>()` in `src/Web/Endpoints/Users.cs` gives no place to choose a tenant when signing up.
- **List titles are unique across the whole system.** `CreateTodoListCommandValidator.BeUniqueTitle` checks every list, which would tell one company that another company's list title exists.
- **This repo is a template.** It ships 3 database providers (SQLite, PostgreSQL, SQL Server) and 3 client options (Angular, React, none). Functional tests use `RunAsUserAsync` and Respawn.

## Ways this could go wrong (before planning)

1. **Data leaks through a forgotten path.** Any query, `FindAsync`, validator or raw SQL that skips the tenant filter exposes another company's data.
2. **Cross-tenant references.** An item could be created in, or moved to, another tenant's list just by sending that list's `ListId`.
3. **The tenant comes from the client.** If the tenant id is read from the request body or a header the user controls, anyone can switch companies.
4. **Wrong use of EF global filters.** Filters that capture a constant get frozen into the cached model. Filters that run with no tenant either crash or return nothing, for example in seeding or background work.
5. **Seeding and admin tasks have no user.** The initialiser would fail, or create rows with no tenant.
6. **Uniqueness checks leak.** Global uniqueness lets companies discover each other's list titles.
7. **Stale tenant in tokens.** Bearer and cookie tokens issued before the change, or before a user moves company, carry no tenant or the wrong one.
8. **Tests and template variants.** The functional tests, three database providers and Playwright tests all assume a single shared dataset.

## Assumptions

- A tenant is a company, and each user belongs to exactly one tenant for now.
- The tenant is stored on `ApplicationUser.TenantId` and added to the user's claims as a `tenant_id` claim. It is never taken from the request.
- Registration creates a new tenant, or attaches to an existing one by a server-side rule (for example, an invite). Both the full join/invite flow and admin tooling across tenants are out of scope.
- No data migration is needed, because the template recreates the database on every startup. I'll call this out for real deployments.
- `TenantId` is added to **both** `TodoList` and `TodoItem` (stored on items too), so each one can be filtered without a join and indexed.

## Plan

1. **Domain**
   - Add an `ITenantEntity { Guid TenantId }` interface, or a `BaseTenantEntity`.
   - `TodoList` and `TodoItem` implement it.
2. **Application**
   - Add `string? TenantId` to `IUser`, or a separate `ITenantProvider` interface.
   - In `CreateTodoItem` and `UpdateTodoItemDetail`, load the target list and check it belongs to the current tenant. Return "not found" rather than "forbidden", so the response doesn't confirm the list exists elsewhere.
   - Make `BeUniqueTitle` per tenant. The global filter will do this automatically, but add an explicit test for it.
3. **Infrastructure**
   - Add `TenantId` to `ApplicationUser`, and add a `Tenant` entity (`Id`, `Name`).
   - In `ApplicationDbContext`, inject the tenant provider. Add `HasQueryFilter(e => e.TenantId == _tenantId)` for every `ITenantEntity`, referencing an instance member, not a captured constant.
   - Configure indexes on `TenantId`, and a unique index on `(TenantId, Title)` for lists.
   - Extend `AuditableEntityInterceptor`, or add a `TenantEntityInterceptor`, to:
     - stamp `TenantId` on added entities;
     - reject any modification where `TenantId` changes or doesn't match;
     - throw if there is no tenant, unless explicitly in system mode.
   - Add a `UserClaimsPrincipalFactory<ApplicationUser>` that emits the `tenant_id` claim.
   - Give seeding a default tenant: the admin user gets that tenant, and seeding runs with an explicit system or tenant scope.
4. **Web**
   - `CurrentUser` reads `tenant_id` from the claims.
   - Registration has to assign a tenant. Either wrap the register endpoint, or keep `MapIdentityApi` and assign a tenant on first login (my recommendation: a custom register endpoint).
   - The Angular and React clients need no change beyond regenerating the NSwag clients if the DTOs change. Keep `TenantId` out of the DTOs.
5. **Tests**
   - Add `RunAsUserAsync(..., tenant)` to the test helpers.
   - Add isolation tests: tenant A can't list, get, update, delete or add items to tenant B's lists. Title uniqueness is per tenant. Seeding still works.
   - Run all of this against each database provider using `build/test.ps1`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Cross-tenant `ListId` reassignment | `UpdateTodoItemDetail` and `CreateTodoItem` trust the `ListId` the client sends | Load the list through the filtered set; check its tenant in the interceptor too |
| 2 | Query filter bypassed or missing | `FindAsync` returns already-tracked entities without filtering; future `IgnoreQueryFilters` or raw SQL skip it | Interceptor rejects writes from another tenant; isolation tests for each endpoint |
| 3 | Filter frozen in the cached model | EF caches the model, so a captured tenant value would apply to every request | Reference a DbContext instance member; test two tenants in one process |
| 4 | Tenant taken from client input | Easy shortcut via a header or body field | Use only the server-issued `tenant_id` claim |
| 5 | Seeding has no tenant | The initialiser runs with no HTTP user and calls `TodoLists.Any()` | Explicit system or tenant scope for seeding; seed a default tenant |
| 6 | Registration can't assign a tenant | `MapIdentityApi` has no tenant hook | Custom register endpoint or first-login assignment |
| 7 | Stale or empty tenant claim | Tokens issued before the change carry no `tenant_id` | Fail closed when the claim is missing; shorten token lifetime or force re-login |
| 8 | Title uniqueness leaks or blocks | `BeUniqueTitle` checks titles across all tenants | Check per tenant plus a unique index on `(TenantId, Title)` |
| 9 | Breaks template variants or tests | 3 database providers, Respawn, Playwright tests all assume one shared dataset | Update test helpers; run `build/test.ps1` on every provider |
| 10 | No backfill path for real deployments | Template uses `EnsureDeleted`/`EnsureCreated`, but adopters will have existing data | Document a migration that backfills a default tenant before making `TenantId` NOT NULL |

Riskiest: #1 — moving an item into, or creating one in, another company's list by sending its `ListId`. The current code allows it, and a read-only query filter alone won't stop it.
