# Plan: lock out by username and IP address together by default (django-axes)

I didn't write the plan file, because you asked me not to edit any files. The full plan is below.

## Assumptions
- The new default applies only when `AXES_LOCKOUT_PARAMETERS` is unset and none of the deprecated `AXES_ONLY_USER_FAILURES` / `AXES_LOCK_OUT_BY_*` / `AXES_USE_USER_AGENT` flags are set. Explicit settings and the deprecated-flag mapping stay as they are.
- "Username and IP address together" means the combined parameter `[["username", "ip_address"]]`, not `["username", "ip_address"]`. The second form locks on either one, which is a different behaviour.
- This changes behaviour, so it goes in a new major release section (10.0.0) of `CHANGES.rst` under "Breaking changes", along with how to opt out.
- No new migrations are needed, because `AccessAttempt` already stores both `username` and `ip_address`.

## Ways this could go wrong
1. **It weakens protection for everyone using the default.** With IP-only, one IP trying many usernames gets locked out. With username+IP, it never does: an attacker can try one password across thousands of accounts (password spraying) from a single IP. The combination is strictly more lenient. What you gain is that users behind a shared NAT or office IP no longer lock each other out.
2. **Upgrades change behaviour silently.** Anyone who relied on the default gets the new behaviour with no setting change and no warning.
3. **Blank usernames can collide with IP-only keys.** `make_cache_key_list` (`axes/helpers.py:378`) drops falsy values. If the username is `None` (wrong form field, a middleware-only check), the combined cache key becomes the IP-only hash. The database handler filters `username IS NULL` instead, so the two handlers behave differently.
4. **Cache keys can collide.** The values are joined with no separator, so `"a1"+"2.3.4.5"` and `"a"+"12.3.4.5"` give the same key. This bug already exists for anyone who configured a combination; the new default exposes every install to it.
5. **Username case and spelling bypass per-user counters.** `Alice`, `alice` and `alice ` are counted separately. Under IP-only this didn't matter.
6. **Existing lockouts reset on deploy.** Database: failures are now summed per (username, IP), so an IP locked out by mixed usernames is suddenly unlocked. Cache: every key changes, so all counters reset.
7. **Tests depend on the old default.** `tests/settings.py` doesn't set the parameter, and many tests ("same IP, different user is locked") assume IP-only. They will fail, or worse, still pass while no longer testing what they say they test.
8. **The setting is resolved once, at import time.** `axes/conf.py` computes it when the module loads, so testing the default needs the setting deleted and the module reloaded, not just `override_settings`.
9. **The default list can get mutated.** With `AXES_USE_USER_AGENT` set, the code mutates `[0]` (`conf.py:53-60`). The new default must be a fresh nested list literal, not a shared constant.
10. **A proxy misconfiguration would no longer show up.** If ipware returns the proxy's IP for everyone, IP-only locked everyone out, which was visible. Username+IP keeps working per user, so the misconfiguration goes unnoticed.

## Implementation
1. **`axes/conf.py:50-51`**: change the final `else` to `settings.AXES_LOCKOUT_PARAMETERS = [["username", "ip_address"]]` and update the stale comment at line 38. Keep the deprecated-flag branches as they are.
2. **Docs**:
   - `docs/4_configuration.rst:93`: change the default column and description.
   - `docs/5_customization.rst:181`: fix the "not only by IP address" wording.
   - `docs/2_installation.rst:160`: make the "no flags" mapping say explicitly to set `["ip_address"]` to keep the old behaviour.
   - Add a short note on the spraying trade-off and suggest `[["username","ip_address"], "ip_address"]` with a higher limit, or lowercasing via `AXES_USERNAME_CALLABLE`.
3. **`CHANGES.rst`**: add a new unreleased section with a breaking-change entry, the opt-out line `AXES_LOCKOUT_PARAMETERS = ["ip_address"]`, and a note that existing counters and lockouts are re-scoped.
4. **No change needed in**:
   - `axes/checks.py`: W006 already passes, because `ip_address` is part of the combination.
   - `axes/apps.py`: the verbose log line already prints "combination of username and ip_address".
5. **Tests**:
   - Run the suite and sort the failures. Where a test is really about IP lockout, add `@override_settings(AXES_LOCKOUT_PARAMETERS=["ip_address"])` to it. Don't pin the whole suite globally, or the new default never gets tested.
   - Add login tests for three cases: same user and same IP → locked; same IP, different users → not locked; same user, different IP → not locked.
   - Add a `tests/test_conf.py` test that deletes the setting, reloads `axes.conf` and checks the default, and another confirming the deprecated flags still map as before.
6. **Out of scope, recommended as follow-ups**: put a separator in the cache-key join (risk 4), and treat `None` usernames the same way in both handlers (risk 3).

## Verification
- Run `pytest` (or `tox` for the matrix).
- Run `python manage.py check --deploy` to confirm no new warnings.
- Manual check with the test app: post bad passwords for two usernames from one IP and confirm neither is locked at the limit, then confirm a single username does get locked.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Password spraying not stopped | Combination never locks an IP that tries many users | Document trade-off; suggest `[["username","ip_address"], "ip_address"]` |
| 2 | Silent behaviour change on upgrade | Default is applied at import, no warning | Major version, breaking-change entry, opt-out snippet |
| 3 | `None` username equals IP-only key | `make_cache_key_list` drops falsy values | Test it; follow-up to handle `None` explicitly |
| 4 | Cache-key collisions | Values joined with no separator | Follow-up: add a separator, noting keys reset once |
| 5 | Case variants bypass counters | Usernames not normalised | Document lowercasing via `AXES_USERNAME_CALLABLE` |
| 6 | Active lockouts lifted on deploy | Failures re-scoped per (user, IP); cache keys change | Call it out in `CHANGES.rst` |
| 7 | Tests assume IP-only | `tests/settings.py` leaves default unset | Per-test overrides plus new default tests |
| 8 | Default not testable via override | Resolved once in `conf.py` at import | Reload `axes.conf` in a dedicated test |
| 9 | Shared default list mutated | `AXES_USE_USER_AGENT` branch appends to `[0]` | Use a fresh literal; keep the flag-mapping test |
| 10 | Proxy/IP misconfiguration hidden | Per-user lockouts mask everyone sharing one IP | Keep the ipware setup docs prominent |

Riskiest: #1 — the new default quietly stops locking out one IP that tries many usernames (password spraying), so every install that relies on the default loses protection.
