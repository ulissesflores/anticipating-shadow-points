Here is the plan. I made no edits, as you asked, so there is no plan file.

## Assumptions
- This is django-axes at 9.0.0, so the change would go into the next release.
- "Username and IP together" means one combined parameter, `AXES_LOCKOUT_PARAMETERS = [["username", "ip_address"]]`. It does not mean the OR form `["username", "ip_address"]`.
- Only the default changes. Explicit `AXES_LOCKOUT_PARAMETERS` and the deprecated `AXES_*` flags keep their current meaning.
- Because this changes a security default, I'd ship it as a documented breaking change, with a minor or major bump.

## What I found
- The default is set in `axes/conf.py:42-51`. When `AXES_LOCKOUT_PARAMETERS` is `None` and no legacy flag is set, it falls back to `["ip_address"]`.
- The `AXES_USE_USER_AGENT` block (`conf.py:53-60`) handles a nested first element by appending `"user_agent"` to the inner list. It will work unchanged with the new default.
- `axes/checks.py` warning W006 fires only if `ip_address` is missing from the parameters. The new default contains it, so no change is needed.
- `axes/apps.py:40-57` already prints combined parameters correctly in the verbose startup log.
- `get_lockout_parameters` in `axes/helpers.py:314` returns the list as is.
- The docs that state the old default are `docs/4_configuration.rst:93`, the migration notes at `docs/2_installation.rst:160`, and `docs/3_usage.rst`. `CHANGES.rst` needs a new entry.
- Many tests in `tests/test_login.py` rely on the implicit IP-only default. They need an explicit override, or their expectations need updating.

   - Run `manage.py check --deploy` to confirm no new warnings.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Weaker brute-force protection | An attacker from one IP who rotates usernames (password spraying) is never locked. | Call it out in the docs, and recommend `["ip_address", ["username","ip_address"]]` for strict setups. |
| 2 | Silent behavior change on upgrade | Anyone relying on the implicit IP-only default loses protection with no code change. | Add a prominent breaking-change note and a major or minor bump. Consider a one-time startup warning. |
| 3 | Distributed attack on one account | The attacker spreads attempts across many IPs, so the per-IP-and-username counter never reaches the limit. | Document it, and suggest adding `"username"` or a CAPTCHA/rate limiter. |
| 4 | Missing or spoofed client IP | When `ip_address` is `None` or behind a proxy, all users collapse into one bucket or lockouts are bypassed. | Document the `AXES_IPWARE_*` and proxy settings, and test with a `None` IP. |
| 5 | Stale counters at the switch | Old IP-keyed attempts and cache entries do not match the new combined keys. | Note in the changelog that the counters effectively reset at upgrade. |
| 6 | Test suite breakage | Many tests assume the IP-only default. | Pin explicit parameters in those tests, then add new default tests. |
| 7 | Username normalization gaps | Case or whitespace variants of a username get separate buckets (the 9.0 truncation fix covers length only). | Check that `AXES_USERNAME_CALLABLE` normalizes usernames, and test case variants. |
| 8 | Callable and legacy flag interplay | A user-supplied callable or deprecated flags might get mixed with the new default. | Apply the default only when the setting is `None` and no flag is set, and test that. |
| 9 | Inconsistent docs | The old default is quoted in several places (configuration, installation, usage). | grep for `["ip_address"]` and fix every mention. |

Riskiest: #1, because rotating usernames from a single IP would bypass lockout entirely.
