# Plan: change the default signing digest from SHA-1 to SHA-256

I didn't edit any file, as you asked. This is the `itsdangerous` library, and the next release is 2.3.0 (unreleased).

## Assumptions
- This is a breaking change. It ships in the unreleased 2.3.0 under a major-style note, not in a patch release.
- SHA-256 becomes the default only for signing. Existing SHA-1 signatures must still verify, so a SHA-1 fallback signer is added by default.
- Keep the lazy-evaluation pattern. FIPS builds may lack SHA-1, which is the issue behind #375. SHA-256 is always available, but the lazy wrapper keeps the default overridable at runtime.
- Key derivation and the digest are separate settings (`key_derivation="django-concat"` hashes with `digest_method`). Changing the digest therefore also changes the derived key, not just the MAC.

## Steps

   - Update the docstrings and comments at lines 51, 95 and 114–115 that say "defaults to SHA1".
   - Add a `.. versionchanged:: 2.3` note.
2. **`src/itsdangerous/serializer.py`**

   - Import `_lazy_sha1` for this. Keep it under that name, or move it to a shared private helper.
   - Add a `versionchanged` note in the docstring next to the SHA-512 history (lines 79–84).
   - Confirm that `unsign`'s fallback loop (around line 297) also covers `TimestampSigner` and the URL-safe serializers, since the signer class is inherited.
3. **Tests (`tests/test_itsdangerous/test_serializer.py`)**

4. **Docs**

   - `docs/serializer.rst` (lines 82–103): the example that moves from SHA-1 to SHA-512 needs updating.
   - `CHANGES.rst`: add an entry under 2.3.0, with a migration note covering how to disable the fallback and how to pin SHA-1.
5. **Verification**
   - Run the repo's test and typing configuration (`uv run pytest`, plus mypy/pyright if configured in `pyproject.toml`).
   - Run an interop check by hand. Sign with the old version (git stash or a tag), then `loads` with the new one. Also sign with the new version and `loads` with the old one, to confirm that case fails.
   - Re-run `git grep -ni sha1` to catch leftovers.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Outstanding SHA-1 tokens stop verifying | Sessions, reset links and cookies signed before the upgrade fail with `BadSignature` | Default SHA-1 fallback signer; test the old-to-new path |
| 2 | New tokens rejected by older consumers | Rolling deploys or other services on the old version only verify SHA-1 | Document the upgrade order (upgrade verifiers first); changelog note |
| 3 | Fallback keeps SHA-1 acceptance alive indefinitely | The weaker digest stays accepted for verification with no end date | Document how to drop the fallback; plan its removal in a later release |
| 4 | Tests and fixtures pin SHA-1 values | `test_digests` and downstream suites hard-code signatures | Regenerate vectors; note in release notes |
| 5 | Signature length and token size change | SHA-256 gives 43 base64 chars against SHA-1's 27, which affects cookie and URL length limits | State it in the changelog; check the documented limits |
| 6 | Key derivation output changes with the digest | `django-concat` uses `digest_method`, so derived keys change, not just the MAC | The fallback signer re-derives with SHA-1; test it |
| 7 | Fallback mutates a shared default list | `default_fallback_signers` is a class attribute | Keep the existing `list(...)` copy at line 229 |
| 8 | Downstream libraries subclass or override the default | Flask, for example, sets `digest_method` itself | Keep the `default_digest_method` attribute API unchanged |
| 9 | Double verification cost on bad tokens | Failures now try two digests | Negligible, but note it |

Riskiest: #1, outstanding SHA-1 tokens stop verifying unless the default SHA-1 fallback is in place.
