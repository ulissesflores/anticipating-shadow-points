## Plan: make `rolling` default to `true` in express-session

**Assumptions** (non-interactive, so I didn't ask)
- This is express-session 1.19.0. Flipping a default is a breaking change, so it should ship as a major version, or at least be flagged as breaking under `unreleased` in `HISTORY.md`.
- Setting `rolling: false` explicitly must still turn rolling off.
- Behaviour with `saveUninitialized: false` stays the same: new sessions that were never modified still get no cookie.
- The store side needs no change. On every request `req.session.touch()` resets the expiry, and either a save or `store.touch()` writes it back (`index.js:251-254`, `index.js:347-375`). Only the cookie part is gated by `rolling`.

**Changes**
1. **`index.js:109`**: change `Boolean(opts.rolling)` to `opts.rolling === undefined ? true : Boolean(opts.rolling)`. The existing `shouldSetCookie` logic (`index.js:483-492`) then handles the rest.
2. **`index.js:78`**: update the JSDoc to say the default is `true`.
3. **`README.md:295-314`**: change "The default value is `false`" to `true`. Add opt-out advice: use `rolling: false`, or mount the session middleware only on routes that need it, so cacheable or static routes don't get a cookie.
4. **`HISTORY.md`**: add "**Breaking:** `rolling` option now defaults to `true`".
5. **`test/session.js`**:
   - Rewrite `rolling option › should default to false` (~line 1159) as `should default to true`. It should expect `Set-Cookie` on the second request.
   - Add a test that explicit `rolling: false` sends no cookie on an unmodified session.
   - About 26 tests check that a follow-up request has no `Set-Cookie`. They go through `createSession()` (~line 2838), which sets `maxAge` to 60s, so they will fail. Fix: the helper sets `rolling: false` only when the `rolling` key is missing. The new default test passes `rolling: undefined` so it gets the real default.

**Verification**
- Run `npm test` and `npm run lint`.
- Manual check: a small Express app with `cookie.maxAge: 10000`. A second request carrying the cookie should get a `Set-Cookie` with a later `Expires`. With `rolling: false`, there should be no `Set-Cookie`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Silent behaviour change for existing apps | Apps that never set `rolling` will start sending `Set-Cookie` on every response | Release as a major version; add a breaking note in HISTORY and README |
| 2 | CDN/proxy caching breaks | Many caches won't store responses that carry `Set-Cookie`, and static routes behind the session middleware get one | Document `rolling: false` or mounting the middleware per route |
| 3 | Sessions never expire for active or polling clients | Every request extends the expiry, so background polling keeps a session alive forever | Document it; suggest an absolute timeout stored in session data |
| 4 | Test suite breaks widely | About 26 tests expect no `Set-Cookie`, and the helper sets a 60s `maxAge` | Default the helper to `rolling: false` unless the key is given |
| 5 | Helper default hides the real default | Pinning `rolling: false` in the helper means most tests no longer exercise the new default | Write explicit tests for the default (`undefined`), `true` and `false` |
| 6 | `rolling: undefined` vs missing key confusion | `opts.rolling === undefined` treats both the same | Spell out "undefined means the default" in the docs |
| 7 | Overhead on every response | Each response now signs and serializes the cookie | Minor cost; benchmark only if someone raises it |
| 8 | Conflicts with `saveUninitialized: false` | Users may expect a cookie on brand-new sessions | Keep the README note that rolling only affects loaded sessions |

Riskiest: #1. Existing apps that never set `rolling` change behaviour without warning, which also brings on the caching problem in #2.
