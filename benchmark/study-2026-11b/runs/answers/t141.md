**Assumptions:** This is the Remix "Blues Stack" app, with Prisma on Postgres, email and password login (`verifyLogin` in `app/models/user.server.ts`) and a signup route at `app/routes/join.tsx`. It has no mailer and no `emailVerified` field today. "New users" means accounts created after the change ships. I did not edit any files.

## Ways this could go wrong

- **Existing users get locked out.** If the migration adds `emailVerifiedAt` as null and the login check requires it, every current user is blocked. The column needs a backfill.
- **`join` still logs people in.** `join.tsx` presumably calls `createUserSession` right after `createUser`. If that stays, unverified users get in through signup, and the gate only covers `/login`.
- **Other paths create sessions.** `cypress/support/create-user.ts` and `prisma/seed.ts` call `createUser` and `createUserSession` directly. Any session cookie issued elsewhere bypasses the gate. Sessions that already exist stay valid after the change.
- **Tests break.** The Cypress e2e flow and the Vitest tests sign up and then expect to be logged in. They will all fail unless the test helpers mark users as verified.
- **No email infrastructure.** The repo has no mailer, provider, API key, sender domain, SPF or DKIM setup, and the mocks in `mocks/` don't cover one. Verification mail may land in spam or never send, and then nobody can log in. Fly deployment needs new secrets.
- **Weak tokens.** Predictable, non-expiring or reusable tokens would let someone verify an address they don't own. Tokens should be random and stored hashed. They should be single-use and expire.
- **Account enumeration.** Telling a user "email not verified" at login, or "already registered" at signup, reveals which emails have accounts. Responses need to stay uniform.
- **Dead end for unverified users.** There is no resend flow, so an expired or lost email permanently strands the user. Resend also needs rate limiting, or it becomes an email-bombing tool.
- **Pre-registration squatting.** An attacker can sign up with a victim's address first. If the unverified account keeps its password or its email slot, the real owner is blocked or the attacker holds a claim on that address.
- **Rollout ordering.** If the code deploys before the migration, or the reverse, login can crash against the old or new schema. Fly's rolling deploys can leave old and new instances running together. The `Password` relation and the `onDelete: Cascade` rules also need checking before any cleanup of unverified accounts.
- **Mail-sending failure at signup.** If the send fails after `createUser` succeeds, the user ends up half-registered. A synchronous send also slows signup and adds a failure point.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New nullable column blocks every current user at login | Backfill existing rows as verified in the migration |
| 2 | Signup still creates a session | `join.tsx` likely logs users in after `createUser` | Remove auto-login; redirect to a "check your email" page |
| 3 | Other session paths bypass the gate | Cypress and seed helpers call `createUserSession` directly | Check verification inside session creation; update helpers |
| 4 | No mail infrastructure | No mailer, secrets or domain auth exist yet; mail may go to spam | Pick a provider, set Fly secrets, mock it in tests, add a dev log fallback |
| 5 | Weak or reusable tokens | Anyone could verify an address they don't own | Random tokens, hashed at rest, single-use, short expiry |
| 6 | Account enumeration | Distinct errors reveal which emails are registered | Use uniform messages and neutral resend responses |
| 7 | No resend path or rate limit | Expired mail strands users; resend can be abused | Add a resend route with throttling and a cooldown |
| 8 | Squatting on someone's email | An attacker's unverified signup can block the real owner | Let a later signup or verification take over; purge stale unverified accounts |
| 9 | Tests and e2e break | Existing flows assume instant login after signup | Update fixtures; add verification tests |
| 10 | Deploy ordering and mail failure | Mixed schema and code versions during rollout; partial signup if the send fails | Ship an additive migration first; send mail with retry and a resend option |

Riskiest: #1, because a missing backfill locks out every existing user at deploy time.
