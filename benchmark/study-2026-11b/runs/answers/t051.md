## What the code does now

- **`src/itsdangerous/signer.py:40`**: `_lazy_sha1` calls `hashlib.sha1` only when a signature is made, not at import time. This was done on purpose for FIPS builds (CHANGES 2.2.0, #375).
- **`HMACAlgorithm.default_digest_method` (line 54)** and **`Signer.default_digest_method` (line 120)** both default to `_lazy_sha1`.
- **`digest_method` is used twice.** It produces the HMAC signature, and it also derives the signing key in `derive_key()` (`django-concat` hashes `salt + b"signer" + secret_key` with it). Changing the default therefore changes both the derived key and the signature.
- **`Serializer.default_fallback_signers` is empty.** No fallback for old tokens is set up today.
- **This was tried before.** Version 1.0.0 switched the default to SHA-512 and was **yanked from PyPI**. Version 1.1.0 went back to SHA-1, and the fallback-signer mechanism was added at that point "to support changing the default in the future without breaking existing signatures."
- **Tests that pin SHA-1:** `test_digests` (`tests/test_itsdangerous/test_serializer.py:186`) has a hard-coded SHA-1 token, and `test_iter_unsigners` asserts `digest_method == _lazy_sha1`.
- **Docs that say SHA-1:** `docs/concepts.rst:140-155` ("Digest Method Security") and the docstrings in `signer.py:52, 94-100, 115`.

## Assumptions

1. The target is the 2.3.0 release, which is unreleased and already contains breaking changes ("Remove previously deprecated code").
2. "Default" means both `Signer.default_digest_method` and `HMACAlgorithm.default_digest_method`.
3. Tokens signed with the old default must keep verifying for at least one release, so a SHA-1 fallback is required.
4. `TimestampSigner`, `URLSafeSerializer` and the timed serializers inherit the new default and need no separate change.

## How this could go wrong

- **Every existing token fails at once.** That includes Flask session cookies, password-reset links and email-confirmation links. Both the derived key and the HMAC change, so nothing signed with SHA-1 verifies. This is what got 1.0.0 yanked.
- **The fallback is set up in a way that misses some users:**
  - A SHA-1 entry in `default_fallback_signers` only helps users of `Serializer`. Anyone calling `Signer` or `TimestampSigner` directly gets no fallback.
  - Users who pass their own `fallback_signers=[...]` replace the default list, so they silently lose the SHA-1 fallback.
- **The FIPS fix is undone.** If the fallback references `hashlib.sha1` directly instead of `_lazy_sha1`, FIPS builds break again. A fallback that is always tried also means a SHA-1 attempt on every token that fails verification.
- **Tokens get longer.** A SHA-256 signature is 43 base64 characters instead of 27. That pushes cookies closer to the 4 KB limit and makes URLs longer.
- **Subclasses and callers relying on the old value break:**
  - Code that compares against `_lazy_sha1` or reads `default_digest_method`.
  - Subclasses that set `default_digest_method` on `Signer` but not on `HMACAlgorithm`, which ends up with a mismatched pair.
- **Downstream libraries are affected without being asked.** Flask's `SecureCookieSessionInterface` already pins `hashlib.sha1` explicitly, so it is unaffected. Other libraries that rely on the itsdangerous default are not, and neither are services in different languages that check tokens with SHA-1.
- **Mixed versions during a rolling deploy.** Upgraded nodes issue SHA-256 tokens that older nodes reject.
- **Removing the fallback too early or too late.** Removing it too early recreates the outage. Keeping it forever means SHA-1 is never actually retired.
- **Test and doc drift.** `test_digests` and `test_iter_unsigners` fail, and the docs keep saying SHA-1 is the default.

## Plan

1. In `signer.py`, add a `_lazy_sha256` helper. Point both `HMACAlgorithm.default_digest_method` and `Signer.default_digest_method` at it, and keep `_lazy_sha1` for the fallback.
2. In `serializer.py`, set `default_fallback_signers = [{"digest_method": _lazy_sha1}]` so `Serializer` and its subclasses still accept old tokens. Document that passing your own `fallback_signers` replaces this list.
3. Leave the `Signer` and `TimestampSigner` API unchanged. Document in CHANGES how direct users pin `digest_method=hashlib.sha1` or add their own fallback.
4. Update the tests:
   - `test_digests`: the default now equals SHA-256; add a new pinned SHA-256 token.
   - `test_iter_unsigners`: expect `_lazy_sha256` first and the SHA-1 fallback after it.
   - New test: a token made by the old default still loads through `Serializer`.
   - New test: the SHA-1 fallback still doesn't touch `hashlib.sha1` at import time.
5. Update the docs: the docstrings, `docs/concepts.rst` "Digest Method Security" (new default, token length, migration), and a CHANGES 2.3.0 entry marked as a breaking change with migration steps.
