The plan is to add UUIDs next to the integer IDs first. Then a new `/v2/summaries` API uses the UUID as its only ID, and integer access is retired later, once nobody uses it. I haven't edited any repo files; the plan is saved at `claude-home/plans/replace-the-integer-ids-goofy-nest.md`.

**What exists today:** a FastAPI app with Tortoise ORM, Aerich migrations and Postgres 17. The table `textsummary` has an auto-incrementing integer key (`id SERIAL`). That number appears in the URLs (`/summaries/{id}/`, which rejects 0) and in every response body. It is also passed to the background job in `summarizer.py`.

**Assumptions**
- Existing clients read `id` as a number and send numbers in URLs, so changing `id` to a UUID in place would break them.
- Nothing outside the API depends on the integer key. It stays as the internal database key; only the public identifier changes.
- A version prefix in the URL (`/v2/summaries`) is acceptable.

**Phase 1: add UUIDs without breaking anything**
1. **Model:** add `uuid = fields.UUIDField(unique=True, default=uuid4)` and keep `id`. `SummarySchema` is generated from the model, so it picks up the new field automatically.
2. **Migration (Aerich, adjusted by hand):**
   - add a nullable `uuid` column;
   - fill existing rows with `gen_random_uuid()`, in batches if the table is large;
   - set the column's default to `gen_random_uuid()` and make it `NOT NULL`;
   - add a unique index;
   - write a real `downgrade`, since the existing one is empty.

   The database default makes sure rows inserted by older app versions still get a UUID.
3. **v1 responses:** add `uuid` alongside `id: int` in `SummaryResponseSchema`. Adding a field doesn't break clients that ignore unknown fields.
4. **v1 URLs:** change the path parameter to `Union[PositiveInt, UUID]`, with the integer type first. Add a lookup helper in `crud.py` that searches by `id` or by `uuid` depending on what it receives. `crud.post` returns both values.
5. **Background job:** `summarizer.py` keeps using the internal integer.

**Phase 2: `/v2/summaries`**
- A new router where `id` is the UUID, both in URLs and in responses. URLs accept only UUIDs, and the integer never appears. It reuses the same `crud` functions and gets its own schemas.

**Phase 3: retire integer access (a later release)**
- v1 responses carry `Deprecation` and `Sunset` headers, and integer-URL hits are logged and counted.
- When those hits reach zero, remove v1 or have integer URLs return 410 Gone. The integer stays as the internal key.

**Files to change:** `app/models/tortoise.py`, `app/models/pydantic.py`, `app/api/crud.py`, `app/api/summaries.py`, a new `app/api/summaries_v2.py`, `app/main.py` and a new migration. Tests: `tests/test_summaries.py`, `tests/test_summaries_unit.py` and a new v2 test file.

**How to check it**
- Run the migration against a database already holding integer-ID rows. Every row should get a unique UUID, and a raw SQL insert should get one from the default.
- The current tests should pass with one intentional change: the 422 error body for `id=0`.
- New tests:
  - v1 returns the same row whether looked up by integer or by UUID;
  - v1 responses include both `id` and `uuid`;
  - v2 create/read/update/delete works end to end with UUIDs;
  - v2 rejects integers with 422;
  - an unknown UUID returns 404.
- Downgrading and re-upgrading the migration works on a copy of the database.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Some clients break when `id` changes type | `id` is an integer in every response today | Keep v1 `id` as an integer; UUID-only `id` goes in v2 |
| 2 | Filling existing rows locks the table | One `UPDATE` across `textsummary` | Fill in batches; add the index with `CONCURRENTLY` |
| 3 | Rows created during deploy have no UUID | Old app instances don't set `uuid` | Database default `gen_random_uuid()` |
| 4 | v1 error bodies change | The union type changes the 422 detail that tests and clients check for `id=0` | Update tests; mention it in the changelog |
| 5 | `"123"` parsed as the wrong type | Union parsing order | Integer type first; test both kinds of input |
| 6 | Rollback is impossible | The existing migration's `downgrade` is empty | Write and test a real downgrade |
| 7 | IDs still guessable through v1 | v1 still accepts integers | Deprecation headers, usage metrics, then 410 |
| 8 | Two ID schemes drift apart in the code | `crud` and schemas must handle both | One lookup helper; tests for both paths |
| 9 | Background job updates the wrong row | `generate_summary` gets an ID from the request handler | Always pass the internal integer key |
| 10 | Test database differs from the migrated one | Tests use `generate_schemas=True`, not the migrations | Run `aerich upgrade` in CI on seeded data |

Riskiest: #1. Changing the type of the existing `id` field is the one mistake that silently breaks every current client.
