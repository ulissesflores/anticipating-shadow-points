I've written the plan to `<config>/plans/make-every-to-do-list-golden-gadget.md` and haven't changed any repo files.

**Current state:** there's no tenant concept anywhere. The current user only carries `Id` and `Roles` (`src/Application/Common/Interfaces/IUser.cs`). `GetTodosQueryHandler` returns every list in the database. The rule that list titles must be unique applies across the whole database (`CreateTodoListCommandValidator.cs:22`). An item can be created in any list by its ID (`CreateTodoItem.cs:25`). The database is rebuilt at startup, so there are no migrations. This repo is also a template that builds in 3 database × 3 front-end variants (`#if UsePostgreSQL/UseSqlServer/UseApiOnly`).

**Assumptions** (non-interactive run):
- Each user belongs to exactly one tenant, stored on `ApplicationUser` and passed as a `tenant_id` claim.
- Each self-registration creates a new tenant. Inviting users into an existing tenant is out of scope.
- Isolation is done in one shared database with EF Core filters, not separate databases.

**Plan:**
1. **Domain:** add a `Tenant` entity and an `ITenantOwned` interface. Put `TenantId` on both `TodoList` and `TodoItem`; storing it on items too lets them be filtered directly.
2. **Infrastructure:**
   - `ApplicationDbContext` gets a global filter that reads the current tenant from the context at query time. If there's no tenant, it returns nothing.
   - A new `TenantInterceptor` stamps `TenantId` on save. It rejects saves with no tenant, a mismatched tenant, or a changed `TenantId`.
   - A claims factory adds `tenant_id` at sign-in.
   - Registration creates a new tenant.
   - Seeding creates a "Default" tenant and gives it to the admin user and the sample list.
   - The database gets indexes on `TenantId` and a unique `(TenantId, Title)` index on lists.
3. **Application:**
   - `CreateTodoItem` loads the list through the filter, so another tenant's list comes back as 404.
   - Handlers that use `FindAsync` switch to filtered `FirstOrDefaultAsync`.
   - The unique-title check becomes per-tenant through the filter.
4. **Web:** `CurrentUser.TenantId` reads the claim.
5. **Tests:**
   - The test helpers (`WebApiFactory` and `TestApp`) become tenant-aware.
   - New isolation tests cover reads, updates, deletes, creating items in another tenant's list, and titles per tenant.
   - A model test fails if any tenant-owned entity lacks a filter.
6. **Docs:** a new ADR (ADR-004) that also explains how to backfill existing databases.

**Verification:** `dotnet test`, the template matrix (`test-templates.yml`) across every variant, and a manual check with two users in two tenants. Each should see only their own lists, and a cross-tenant `PUT` should return 404.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Data leaks across tenants through an unfiltered path | `FindAsync` and any future raw SQL or `IgnoreQueryFilters` skip filtering | Filtered `FirstOrDefaultAsync`, model test, isolation tests |
| 2 | Cross-tenant item creation | `CreateTodoItem` trusts `ListId` blindly | Load the list through the filter; interceptor checks tenant match |
| 3 | Null tenant shows all or no data | Seeding has no HTTP context; old sessions lack the claim | Return nothing when null; explicit tenant for seeding; force re-login |
| 4 | Filter frozen to one tenant | EF caches the model; a captured local value is reused for every request | Filter reads a context property, not a local |
| 5 | Title check leaks or blocks other tenants | `BeUniqueTitle` is global today | Per-tenant via the filter plus a unique `(TenantId, Title)` index |
| 6 | Client sets or changes `TenantId` | Commands map onto entities | Never accept it as input; interceptor stamps it and rejects changes |
| 7 | Registration leaves users without a tenant | Built-in `MapIdentityApi` `/register` can't be extended easily | Create the tenant on user creation; reject users without one |
| 8 | Tests break or pass without testing isolation | Mocked `IUser` has no tenant | Tenant-aware helpers; two-tenant tests |
| 9 | A template variant fails to build | 3 DBs × 3 clients, `#if` blocks | Run the `test-templates.yml` matrix |
| 10 | Existing apps' data becomes unreachable | Rows without a tenant are hidden once the filter is on | Backfill migration guidance in the ADR |

Riskiest: #1, a query that skips the tenant filter and returns another company's data.
