## What the code does now

- `index.js:109`: `var rollingSessions = Boolean(opts.rolling)`, so rolling defaults to `false`.
- `index.js:483-492` (`shouldSetCookie`): for an existing session, the cookie is re-sent only if `rollingSessions` is on, or if the cookie has an expiry and the session was modified. When the cookie is re-sent, `req.session.touch()` (`index.js:251-255`) resets `expires` to now + `maxAge`.
- The store side already rolls for unmodified sessions when the store has a `touch` method: `shouldTouch` (`index.js:472-480`) does not check `rolling`. So in practice only the browser cookie's expiry fails to roll today.
- Docs and tests that state the old default: `README.md:295-312` ("The default value is `false`"), the JSDoc at `index.js:78`, and `test/session.js:1159` (`'should default to false'`).

## Assumptions

1. "Roll by default" means `rolling` becomes `true` when the option is not given. An explicit `rolling: false` still turns it off.
2. Unlike `resave` and `saveUninitialized`, the old default gets no deprecation warning. It just changes, and this ships as a semver-major release with a HISTORY.md entry.
3. Nothing else about cookie or store behaviour changes.

## Ways this could go wrong (before planning)

- It is a breaking change. Every app that never set `rolling` starts sending `Set-Cookie` on every response that goes through the middleware.
- CDNs and proxies usually won't cache responses that carry `Set-Cookie`. Apps that mount session middleware before static assets or cacheable GETs would lose caching.
- With the default `maxAge: null` (a browser-session cookie), rolling resends a cookie that has no expiry. That costs bytes and gains nothing.
- Security: active users effectively never time out. Teams relying on the old fixed expiry lose that limit without being told.
- `Boolean(opts.rolling)` is the wrong way to apply the new default. `rolling: 0` or `rolling: ''` should still mean off, so only `undefined` should map to `true`.
- Many existing tests use the default options and assert there is no `Set-Cookie` header (about 34 such assertions in `test/session.js`). They will fail, and the fix is to set `rolling: false` explicitly in those tests, not to delete them.
- How rolling interacts with `saveUninitialized: false` (no cookie for uninitialized sessions) and with secure cookies over plain HTTP (`index.js:245`) must stay the same.
- The README, JSDoc and external typings (`@types/express-session`) would still say "default false".

## Plan

1. **`index.js:108-109`**: change to
   `var rollingSessions = opts.rolling === undefined ? true : Boolean(opts.rolling)`
   and update the JSDoc at line 78 to "(default: true)". The rest of the logic in `shouldSetCookie` and `touch()` stays as it is.
2. **`README.md` `##### rolling`**: change to "The default value is `true`", add how to opt out (`rolling: false`), and add a note that it does nothing useful when `maxAge` is unset and that it stops caching of responses carrying `Set-Cookie`. Keep the existing `saveUninitialized` note.
3. **`HISTORY.md`**: add an "unreleased" major entry: "Change default `rolling` to `true`".
4. **`test/session.js`**:
   - Rename `'should default to false'` to `'should default to true'` and assert `Set-Cookie` on the second, unmodified request.
   - Add `'should not force cookie when rolling: false'`.
   - Add `rolling: false` to existing tests that rely on there being no `Set-Cookie` header. The real behaviour they check doesn't change.
   - Add a test that, by default, `Expires` moves forward between two requests when `maxAge` is set.
5. **Verify**: run `npm test` (full mocha suite) and `npm run lint`. Then manually check one app on defaults with `maxAge: 60000`: make two requests a few seconds apart and confirm the second response has a later `Expires`. Run the same check with `rolling: false` and confirm there is no `Set-Cookie`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Silent breaking change | Every app without `rolling` set starts sending `Set-Cookie` on each response | Semver-major release, HISTORY entry, README opt-out note |
| 2 | Caching stops working | CDNs/proxies skip responses with `Set-Cookie`; middleware often runs before static files | Document it; advise mounting sessions after static files or setting `rolling: false` |
| 3 | Idle timeout becomes endless | Active users never hit the fixed expiry anymore | Document it; point to app-level absolute timeouts |
| 4 | Wasted work when `maxAge` is null | The default cookie has no expiry, so re-sending it changes nothing | Document it; optionally roll only when `maxAge` is set |
| 5 | Falsy values handled wrong | `Boolean()` with a new default could misread `0` or `''` | Default only on `=== undefined` |
| 6 | Mass test failures | About 34 assertions assume no `Set-Cookie` under defaults | Add explicit `rolling: false` to those tests, not delete them |
| 7 | Edge cases change behaviour | Must keep the `saveUninitialized: false` and secure-over-HTTP rules | Keep existing tests for both; add a default-rolling variant |
| 8 | Outside docs and typings out of date | `@types/express-session` and tutorials say the default is false | Note it in the release; file an issue on DefinitelyTyped |

Riskiest: #2, because `Set-Cookie` on every response quietly stops CDN and proxy caching for apps that never asked for rolling.
