I've written a plan for the UUID change and edited no project code. The plan is in `claude-home/plans/replace-the-integer-ids-velvety-music.md`, the only file I wrote. This is a non-interactive run, so I'm presenting the plan here rather than asking for approval.

## What I found
- The only resource is `TextSummary`, whose integer ID is `SERIAL` (`project/app/models/tortoise.py`, migration `0_..._init.py`). That integer shows up in every `/summaries` path and response, as `id: int` with a `gt=0` check.
- The response schema is generated from the model (`pydantic_model_creator`), so any new model field automatically appears in responses.
- The background summarizer (`project/app/summarizer.py`) looks rows up by the integer ID.
- CI runs the test suite against **SQLite**, not Postgres. Integration tests build tables straight from the models instead of running the migrations.
- Deploying to Heroku (`release.sh`) does not run `aerich upgrade`, so the production database schema is updated by hand.

## Assumptions
- The integer stays as the internal primary key, and a unique, non-null `uuid` column is added next to it. Changing the primary key itself would rewrite the table and every lookup, and clients gain nothing from that.
- "Keep existing clients working" means that, for a deprecation period, old clients see no change in path type, `id` type or status codes.
- Only `/summaries` is in scope.

## Ways this could go wrong
1. **Changing `id` from a number to a string breaks clients.** Clients that store the ID as an integer, compare numbers or sort by it would break. Old URLs like `/summaries/42/` would also return 404 or 422.
2. **Existing rows would get no UUID.** The model's `uuid4` default only runs in Python, so rows that already exist would be `NULL` and adding `NOT NULL` would fail.
3. **Code ships before the schema changes.** Deploys don't run migrations, so the new code would query a missing `uuid` column and return 500s.
4. **Tests pass on SQLite but production fails on Postgres.** SQLite stores UUIDs as text and lacks `gen_random_uuid()`, and the migration is never tested.
5. **Ambiguous path parameter.** Accepting either form (`Union[UUID, int]`) needs care. A malformed UUID should give a clear 422, `0` should still be rejected, and the existing error-format tests check exact field names and messages.
6. **Partial switchover.** If one function still filters by the integer while the route passes a UUID, you get silent 404s or an update that touches the wrong row.
7. **The old integer IDs are still guessable.** As long as integer lookups work, the information leak UUIDs were meant to close stays open.
8. **The rollback can't undo anything.** The init migration's `downgrade` is empty.

## Plan (summary)
1. **Model:** add `uuid = UUIDField(default=uuid4, unique=True)`.
2. **Migration in three steps:** add a nullable column, backfill it with `gen_random_uuid()`, then add `SET NOT NULL` and a unique index. Write a real `downgrade` that drops the column.
3. **Lookups:** add one `crud._lookup(ident)` helper that finds a row by UUID or by integer. The summarizer keeps using the integer internally.
4. **Existing `/summaries`:** the path accepts either a UUID or an integer, `id` stays an integer (marked deprecated), and a new `uuid` field is added.
5. **New `/v2/summaries`:** here `id` *is* the UUID, and the integer never appears.
6. **Later:** remove integer support once logs show it's no longer used.
7. **Release order:** run the migration first, then deploy the code.
8. **Tests:**
   - The existing integer-ID tests must pass unchanged, since they are the compatibility check.
   - Add tests for UUID paths and for v2.
   - Run the tests and `aerich upgrade` against Postgres with rows that already exist.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Changing the type of `id` breaks old clients | `id: int` is in every response, and tests assert `{"id": 1, ...}` | Keep `id` as an integer on `/summaries`, add a `uuid` field, put UUID-as-`id` only in `/v2` |
| 2 | Old integer URLs return 404 or 422 | The path is `id: int = Path(gt=0)` | Accept UUID or integer in the path for the deprecation period |
| 3 | Existing rows have no UUID | The `uuid4` default only runs in Python | Add a nullable column, backfill it with SQL, then `SET NOT NULL` |
| 4 | Code goes live before the schema changes | `release.sh` doesn't run migrations | Run `aerich upgrade` before releasing, or as a Heroku release step |
| 5 | Tests pass but production fails | CI uses SQLite, and the tests skip migrations | Run the tests and the migration against Postgres 17 |
| 6 | Unclear errors for path values | Order of UUID/integer parsing and the `gt=0` rule; error formats are asserted exactly | Try UUID first, keep the `gt=0` check, add tests for malformed input |
| 7 | Lookups switched only partly | `crud`, `summaries`, `summarizer` and the delete endpoint each filter on `id` | One shared `_lookup()` helper; the summarizer keeps the integer |
| 8 | The integer IDs can still be guessed | The compatibility period keeps integer lookups working | Log integer usage, set a date, then remove it |
| 9 | Rollback can't undo the migration | The init `downgrade` is empty | Write a real `downgrade` and test it |

Riskiest: #4: the deploy pipeline never runs migrations, so new code querying a `uuid` column that doesn't exist yet would return 500s for every client, old and new.
