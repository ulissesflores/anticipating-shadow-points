Changing the title already changes the slug. `ArticleUpdate` in `articles/routers.go:152-173` builds a new slug from the new title and retries if two requests race for the same one. What's missing is any record of the old slug. After a rename, every shared link to `/api/articles/<old-slug>` returns 404. So the work is to keep old slugs resolving to the same article. I only read the code: nothing was edited except the plan file, and nothing was run.

## Ways this could go wrong (before planning)
1. **Deleting through an old link does nothing but reports success.** `ArticleDelete` deletes using the slug from the URL (`DeleteArticleModel(&ArticleModel{Slug: slug})`). If that slug is an old one, no row matches and it still returns 204.
2. **An old link starts pointing at someone else's article.** The duplicate check `makeUniqueSlug` only looks at current article slugs. Another article whose title produces the freed slug would take it over.
3. **Renaming back to an earlier title.** The article's own old slug must not count as taken, or the author gets `foo-2` instead of `foo`.
4. **Old slugs that point to other old slugs.** If each old slug points to the next one, a chain builds up over several renames and can loop.
5. **Unneeded slug changes.** If the current slug is `foo-2` and the title is set to "Foo" again, `makeUniqueSlug` counts the article itself as a clash and moves it to `foo-3`.
6. **Partial writes.** If saving the old-slug record and updating the article aren't in one transaction, a failure can leave a renamed article whose old links don't work.
7. **Empty lookups.** GORM ignores empty fields in struct conditions, so a lookup with an empty slug would return the first article in the table.
8. **Redirects instead of direct answers.** A 301 turns POST/DELETE into GET in many clients and could break the RealWorld spec suite (hurl + bruno).
9. **Some routes not updated.** Eight handlers look articles up by slug. Missing one means old links work on some routes and 404 on others.
10. **Reserving slugs.** Renaming repeatedly reserves more and more slugs. This is minor.

## Assumptions
- Old slugs are answered directly: 200, with the new slug in the response body. No redirect.
- Old slugs work on every `/:slug` route. The author check still runs on the article they resolve to.
- Old slugs stay reserved forever, the same way slugs of soft-deleted articles already are.
- The API shape doesn't change.

## Plan
The full plan is in `plans/let-authors-change-an-valiant-haven.md`.
1. **New table** in `articles/models.go`: `ArticleSlugAliasModel{Slug (unique), ArticleID}`. Every old slug points straight at the article's ID, so there are no chains.
2. **New lookup** `FindArticleBySlug`: try the current slug first, then the old-slug table. An empty slug is rejected.
3. **Update `makeUniqueSlug`** so old slugs count as taken, except old slugs belonging to the article being renamed and its own current slug.
4. **Rename in one transaction**: record the old slug, remove any old-slug record matching the new slug for this article, then apply the update. The existing retry on duplicate slugs stays.
5. **Use the new lookup in all 8 slug handlers.** `ArticleDelete` deletes by article ID instead of the URL slug.
6. **Register the new table** with `AutoMigrate` in `hello.go` and in the test setup.
7. **Tests**:
   - after a rename, the old slug returns 200;
   - after two renames, both old slugs work;
   - renaming back reclaims the original slug;
   - another author's article with the same title gets `-2`;
   - delete, favorite and comments through an old slug act on the right article;
   - a non-author using an old slug gets 403.

   Then run `go test ./...` and `scripts/run-spec-tests.sh`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Delete through an old slug silently does nothing | `ArticleDelete` deletes by URL slug; no match still returns 204 | Delete by the article's ID |
| 2 | Old link taken over by another article | `makeUniqueSlug` only checks current slugs | Reserve old slugs in the duplicate check |
| 3 | Renaming back can't reclaim the original slug | Its own old slug counts as taken → `-2` | Skip old slugs owned by the same article; remove that record on rename |
| 4 | Chains or loops of old slugs | Old slugs pointing to other old slugs | Point every old slug at the article ID |
| 5 | Renamed article with no old-slug record | Update and record written separately | One `db.Transaction` for both |
| 6 | Some routes still 404 on old slugs | 8 handlers each look up by slug | One shared lookup, tested on every route |
| 7 | Redirect breaks POST/DELETE and the spec suite | 301 turns writes into GETs in clients | Answer directly with 200 |
| 8 | Empty slug matches an arbitrary article | GORM ignores empty struct fields | Reject empty slugs in the lookup |
| 9 | Unneeded slug change (`foo-2` → `foo-3`) | `makeUniqueSlug` counts the article itself | Exclude the article's own current slug |
| 10 | Duplicate slugs from concurrent requests | Check-then-write race (SQLite) | Unique index on old slugs plus the existing retry |

Riskiest: #2, an old link taken over by another article. It sends people who follow a shared link to an unrelated article without any error, which is worse than the 404 this change is meant to fix.
