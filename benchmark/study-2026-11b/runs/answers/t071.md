## Assumptions
- This is django-axes, and the default today comes from `axes/conf.py:51`, which falls back to `["ip_address"]`.
- "Username and IP together" means the nested form `[["username", "ip_address"]]`. That is one combined key, the same as the old `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP`. It does not mean the OR form `["username", "ip_address"]`.
- Explicit settings keep priority: an explicit `AXES_LOCKOUT_PARAMETERS` and the legacy flags still win. Only the no-configuration fallback changes.
- This is a breaking default change that ships in the next release after 9.0.0, with a changelog entry and an updated migration note in `docs/2_installation.rst`.

## How this could go wrong
- **Protection gets weaker.** Failures are counted per (user, IP) pair, so there is no per-IP total. One IP can try many usernames, and one username can be tried from many IPs, without ever hitting the limit.
- **Silent upgrade for existing sites.** Anyone who relied on the IP-only default changes behavior without touching their settings. Counters restart, and existing `AccessAttempt` rows no longer line up with the new key.
- **Missing or odd usernames.** Logins without a username (API or token auth, a custom `USERNAME_FIELD`, a wrong `AXES_USERNAME_FORM_FIELD`) give a `None` or empty username. These attempts could all share one bucket, or skip lockout entirely.
- **Username variants.** Without normalization, `Admin`, `admin` and `admin ` each get a fresh counter. This needs a check against `AXES_USERNAME_CALLABLE` and case handling.
- **Interaction with `AXES_USE_USER_AGENT`.** The block at `axes/conf.py:53-60` edits the first entry of the list. With a nested default it appends `user_agent` to the combination, so the key becomes username, IP and user agent. That is narrower than before.
- **Legacy flag combinations.** `AXES_ONLY_USER_FAILURES`, `AXES_LOCK_OUT_BY_USER_OR_IP` and the others must still resolve exactly as they do now. Because the default now sits in the final `else`, the branch order has to stay intact.
- **Storage growth.** Each (user, IP, user agent) combination makes its own DB row or cache key. A spraying attack inflates the table or cache faster, and cleanup and reset commands such as `axes_reset_ip` and `axes_reset_username` act on different slices.
- **Tests and docs.** Many tests assume the IP-only default. Docs that call IP-only "the default" go stale.
- **Behind a proxy.** A wrong or absent client-IP setup makes every user share one IP. Lockout then effectively becomes per-username only, so it may not be the protection people think they have.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Weaker brute-force defense | No per-IP total, so one IP can spray many usernames freely | Document it. Recommend pairing with rate limiting or the OR form `["username","ip_address"]` |
| 2 | Silent breaking default | `conf.py` fallback applies to every unconfigured site | Changelog and release-note warning, and consider a system-check warning |
| 3 | Empty or `None` username | A combined key with a missing part may share one bucket or skip lockout | Handle missing values explicitly. Add tests for API and custom-field logins |
| 4 | Username case or whitespace variants | Each variant starts a new counter | Normalize in `AXES_USERNAME_CALLABLE` or by default. Test it |
| 5 | `AXES_USE_USER_AGENT` mutation | `conf.py:53-60` edits the default list in place | Test the combination. Copy the list instead of mutating it |
| 6 | Legacy flag regression | Branch order in `conf.py` is easy to break | Parametrized test for every flag combination |
| 7 | Storage and cache growth | One record per combination under spraying | Check handler key size and the cleanup command |
| 8 | Reset commands and tooling mismatch | `axes_reset_ip` and `axes_reset_username` act on a different slice | Verify and document their behavior under the combined key |
| 9 | Stale tests and docs | Existing tests assume the IP-only default | Update the tests and the docs in `2_installation.rst` and `3_usage.rst` |

Riskiest: #1, because the new default lowers the lockout protection for every site that never set `AXES_LOCKOUT_PARAMETERS`.
