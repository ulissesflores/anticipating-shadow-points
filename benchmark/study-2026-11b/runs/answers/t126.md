**Assumptions:** This repo is `express-session` 1.19.0. "Roll by default" means flipping the default of the existing `rolling` option from `false` to `true` in `index.js:109`. That is `Boolean(opts.rolling)` today, and it would become `opts.rolling === undefined ? true : Boolean(opts.rolling)`. Explicit `rolling: false` keeps working. I'm treating this as a semver-major or opt-in-by-release change, and I haven't edited anything, as you asked. I also didn't write the plan file, because that would break your no-edit rule.

**What could go wrong**
- **Cookie on every response.** `shouldSetCookie` (`index.js:491`) returns true whenever `rolling` is on. That changes caching and `Set-Cookie` behaviour for static assets, health checks, CDNs and shared caches.
- **`saveUninitialized` interaction.** Rolling only applies when the cookie ID matches `req.sessionID`, so empty sessions are not newly created. Anonymous traffic with an existing cookie still gets its cookie refreshed.
- **Store write load.** `shouldTouch` triggers `store.touch` on unmodified sessions, or a full `save` if the store has no `touch` (`index.js:364`). Every request becomes a store write, which hurts Redis/DB-backed stores.
- **Stores without `touch`.** With `resave: true` or no `touch` method, rolling means a full re-save per request. That raises the risk of lost updates in concurrent requests.
- **Session never expires.** Polling clients, health checks and tabs with background XHR keep sessions alive forever. That quietly weakens idle-timeout security policy and compliance assumptions.
- **Absolute-lifetime expectations.** Apps that relied on a fixed expiry, such as a forced re-login every N hours, stop working.
- **Session cookies with no `maxAge`.** For `expires: null` cookies, rolling is mostly a no-op, but it still re-sends the cookie. Behaviour differs from the `maxAge` case and is easy to misjudge.
- **Existing tests.** Tests that assert no `Set-Cookie` on unchanged sessions, and the `rolling` describe block at `test/session.js:1158`, will break. Many other tests probably assume the old default.
- **Docs and deprecation.** README `rolling` (line 295) and HISTORY need updating. The default flip needs a migration note, and ideally a deprecation warning first, like the existing `resave` deprecate call.
- **Third-party wrappers and tests.** Downstream code that depends on the default will change silently, because no option is undefined-checked.

**Main risks**

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Sessions never expire for active/polling clients | `rolling` extends expiry on every request, including background polls | Document it, and offer an absolute max-age option |
| 2 | Store write amplification | Every request calls `touch` or a full `save` | Keep `touch` support, and warn for stores without it |
| 3 | Silent breaking change for existing users | The default flips with no code change on their side | Semver-major, deprecation warning first, migration note |
| 4 | `Set-Cookie` on every response breaks caching | `shouldSetCookie` is true whenever rolling is on | Skip cookie refresh for static or cacheable routes |
| 5 | Lost updates from concurrent saves | Without `touch`, each request re-saves the whole session | Prefer `touch`, and document `resave: false` |
| 6 | Existing tests fail or go stale | Tests assume the old default, for example at `test/session.js:1158` | Update tests, and add default-on and explicit-off cases |
| 7 | Security and compliance drift | Idle-timeout policies change without anyone deciding to | Release notes and a security note in the README |
| 8 | Docs out of sync | README `rolling` section and HISTORY describe the old default | Update both in the same change |

Riskiest: #3. It is a silent default flip in a widely-depended-on library, and it triggers #1 and #2 for every downstream user at once.
