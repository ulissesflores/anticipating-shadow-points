## Assumptions
- **Where the change goes:** the defaults in `SessionMiddleware.__init__` in `starlette/middleware/sessions.py` change. `same_site` goes from `"lax"` to `"strict"`, and `https_only` goes from `False` to `True`.
- **Opting out stays possible:** callers can still pass `same_site="lax"` or `https_only=False` explicitly. I'm not adding any new parameters.
- **Backwards compatibility:** this counts as a breaking default change, so it needs a release note. The upstream release notes live in `docs/release-notes.md`.
- **Other files that need updating:**
  - `docs/middleware.md` documents both defaults (lines 235 and 237).
  - `tests/middleware/test_session.py` and `tests/middleware/test_middleware.py` assume the current defaults.
  - `README.md`, `docs/index.md` and `docs/config.md` mention `SessionMiddleware`, so I'd check them for examples that depend on the old defaults.
- **Code that stays as is:** the `Secure` flag is already appended whenever `https_only` is true, and it is applied to both the set and the clear cookie. No structural change is needed.

## Ways this could go wrong
1. **Plain-HTTP sessions stop working.** `Secure` cookies are not stored over `http://`. Local dev, test clients and internal HTTP services would silently lose their sessions. The Starlette `TestClient` uses `http://testserver`, and most existing tests would fail or lose their cookies.
2. **Sessions break behind a TLS-terminating proxy.** The browser sees HTTPS, so the cookie works there. But the app sees `http`, and any scheme-dependent logic gets confused. This is a smaller risk than #1, because `Secure` is a browser-side check and not a server-side one.
3. **`SameSite=Strict` breaks cross-site login flows.** OAuth and OIDC redirects back to the app, payment returns and links from email won't carry the cookie on the first navigation. The user appears logged out and OAuth `state` stored in the session is lost.
4. **Strict hurts ordinary UX.** A user following an external link into the site lands logged out until they navigate again.
5. **Embedded and third-party use breaks.** `partitioned` and `same_site="none"` setups need `https_only` and an explicit `none`. Because the defaults change, existing configs that relied on `lax` now behave differently.
6. **Silent failure.** No error is raised. Users just get logged out, so the breakage is hard to diagnose.
7. **Docs and tests drift.** The docs still say the defaults are `lax` and `False`. Tests that assert the exact `Set-Cookie` string will fail.
8. **Surprise for downstream users.** Anyone upgrading without reading the release notes gets different behavior with no warning.
9. **WebSocket sessions.** The middleware also covers `websocket` scopes, and Strict affects handshake cookies, which depend on how the page was reached.

|---|------|-------------------|------------|
| 1 | Sessions vanish over plain HTTP | `https_only` default flips to `True`, so dev and `TestClient` (`http://testserver`) drop the cookie | Use an `https://` base URL in tests and pass `https_only=False` for dev; document it |
| 2 | OAuth/OIDC callback loses the session | Strict omits the cookie on cross-site redirects, so `state` stored in the session is lost | Document `same_site="lax"` for login flows; consider a changelog warning |
| 3 | Users logged out via external links | Strict withholds the cookie on top-level cross-site navigations | Document the tradeoff; keep `lax` as an easy opt-out |
| 4 | Silent behavior change on upgrade | Defaults change with no error or warning | Release note marked breaking; possibly a deprecation cycle or a major version |
| 5 | Existing tests break | `test_session.py` and `test_middleware.py` assume the old defaults and exact cookie strings | Update the tests and add default-flag assertions |
| 6 | Docs lie | `docs/middleware.md` lines 235 and 237 state the old defaults | Update the docs in the same change |
| 7 | Partitioned/embedded setups misconfigured | They need `none` plus `https_only`, and `strict` conflicts | Document the combination; consider validating it |

| 9 | WebSocket handshake cookie dropped | Strict applies to handshakes initiated from cross-site pages | Test the WebSocket path |
