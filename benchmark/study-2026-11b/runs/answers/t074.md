# Plan: "Download my data" export for Flasky

This is the Flasky app (Flask + SQLAlchemy). The relevant models are `User`, `Post` and `Comment` in `app/models.py`. Web routes are in `app/main/views.py`, the profile page is `app/templates/user.html`, and the REST API is in `app/api/`. You asked me not to edit any files, so I haven't written the plan file. Everything is below.

## Assumptions (non-interactive)
1. **"Their data" means only what the user wrote:** their profile fields, posts they authored, and comments they authored (including comments a moderator disabled, marked with `disabled: true`). Comments other people left on their posts and follower lists are not included. Follower lists are easy to add later.
2. **Format:** one JSON file, `flasky-export-<username>-<YYYYMMDD>.json`, sent as a download. JSON fits a nested profile → posts → comments structure. ZIP or CSV would add dependencies for no real gain.
3. **Delivery:** a synchronous web route for the logged-in user only, linked from their own profile page. There's no background job and no API endpoint for now.
4. **Profile fields included:** `username`, `email`, `name`, `location`, `about_me`, `member_since`, `last_seen`, `role.name`, `confirmed`. Excluded: `password_hash`, `avatar_hash`, any tokens, and internal ids that mean nothing outside the app.

## Ways this could go wrong
- **Leaking another user's data (IDOR):** if the route takes `<username>` or `<id>`, anyone could change the URL and download someone else's data.
- **Leaking secrets:** serializing the whole `User` row (or `__dict__`) would include `password_hash`.
- **Reusing the existing `to_json()` methods:** they return API links and counts (`posts_url`, `comment_count`), not content. `User.to_json` has no `email`, `name` or `about_me`. The export would look complete but be missing data.
- **Dates:** `datetime` objects aren't JSON-serializable with `json.dumps`, and `jsonify` would turn them into RFC-1123 strings with no timezone. They need to be ISO-8601 UTC.
- **Memory and timeouts:** `user.posts` and `user.comments` are dynamic queries, so `.all()` on a heavy user loads everything into memory. Heroku cuts requests off at 30 seconds and Gunicorn has its own worker timeout.
- **Caching personal data:** without `Cache-Control: no-store`, a proxy or the browser could keep a copy of personal data.
- **Header injection or odd filenames:** the username goes into `Content-Disposition`, so it must be sanitized.
- **Unconfirmed users can't use it:** `auth.before_app_request` redirects unconfirmed users away from `main.*` routes. That's acceptable because they can't post anyway, but it should be a deliberate choice.
- **Comments disabled by moderators:** leaving them out would make the export incomplete. Including them is correct, but they need the flag.
- **Abuse:** there's no rate limiter, so the endpoint can be called over and over to load the database.
- **Stale export if fields are added later:** the field list is hand-written, so new columns won't show up unless the list is updated. Tests should pin the field list.

## Implementation
1. **`app/models.py`:** add export-specific serializers, kept separate from the API's `to_json()`:
   - `User.to_export_dict()`: an explicit allowlist of profile fields, with ISO-8601 UTC dates.
   - `Post.to_export_dict()`: `id`, `body` (the original Markdown), `body_html`, `timestamp`, `comment_count`.
   - `Comment.to_export_dict()`: `id`, `body`, `body_html`, `timestamp`, `disabled`, `post_id`, and `post_url` built with `url_for('main.post', id=..., _external=True)`.
2. **`app/main/views.py`:** add a new `@main.route('/export')` with `@login_required`. It takes no user id and always uses `current_user`.
   - Build the response as a generator, wrapped in `stream_with_context`. It writes the profile first, then iterates `current_user.posts.order_by(Post.timestamp)` and `current_user.comments.order_by(...)` with `.yield_per(500)`, encoding each item with `json.dumps`. Memory stays flat and the first bytes go out before Heroku's 30-second limit.
   - Response headers: `Content-Type: application/json; charset=utf-8`, `Content-Disposition: attachment; filename=...` (via `secure_filename`), and `Cache-Control: no-store`.
   - Add top-level metadata: `export_version: 1`, `generated_at`, and `counts`.
3. **`app/templates/user.html`:** inside the existing `{% if user == current_user %}` block, next to "Edit Profile", add a "Download my data" button that links to `url_for('.export')`.
4. **No migration and no new dependencies.**

## Verification
- **Add `tests/test_client.py::test_export`:**
  - Register and confirm a user, create a post and a comment (one of them disabled), then GET `/export`. Check the status is 200, the `Content-Disposition` is an attachment, `json.loads` succeeds, and the posts and comments are present.
  - Check that `password_hash` does not appear anywhere in the raw body.
  - Create a second user with their own post and check it's absent from the first user's export.
  - Check that an anonymous GET redirects to `/auth/login`.
- **Model unit test:** check that `to_export_dict()` returns exactly the expected set of keys, so the export can't drift silently.
- **Run** `flask test`. Then, with `flask fake` data (`app/fake.py`), do a manual run with `flask run`, click the button, and open the file.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Another user's data leaks (IDOR) | Existing routes are keyed by `<username>`/`<id>`, so copying that pattern is tempting | No URL parameter; use `current_user` only; test with a second user |
| 2 | `password_hash` or other secrets in the file | `User` stores `password_hash` and `avatar_hash` next to profile fields | Explicit allowlist serializer; test that the raw body lacks `password_hash` |
| 3 | Export misses data | Existing `to_json()` returns API links, not content, and has no email or about_me | Separate `to_export_dict()`; test the key set |
| 4 | Timeout or memory blow-up on heavy users | Dynamic relationships, Heroku 30 s limit, Gunicorn workers | Stream with `yield_per` and `stream_with_context` |
| 5 | Personal file cached by proxy or browser | Plain GET with no cache headers | `Cache-Control: no-store` |
| 6 | Disabled comments missing or unexplained | Moderators set `Comment.disabled` | Include them with a `disabled` flag |
| 7 | Bad or ambiguous dates | `jsonify` uses RFC-1123 with no timezone; `json.dumps` fails on datetime | ISO-8601 with `Z`, done in the serializers |
| 8 | Header injection via filename | Username goes into `Content-Disposition` | `secure_filename` plus a fixed prefix |
| 9 | Endpoint hammered to load the database | No rate limiter in the stack | Streaming keeps cost low; add Flask-Limiter later if needed |
| 10 | Unconfirmed users get redirected | `auth.before_app_request` blocks `main.*` for them | Accept and document (they have no posts or comments) |

Riskiest: #1. A route that serves another user's full data, including their email, would be a privacy breach, and it's the easiest mistake to make by copying the existing `/user/<username>` pattern.
