# Plan: let owners book visits online without double-booking a vet

I haven't changed any code. The plan is saved at `claude-home/plans/let-pet-owners-book-glowing-starfish.md`.

**How it works today:** a visit has only a date and a description. It has no vet and no time. Visits are created from `/owners/{ownerId}/pets/{petId}/visits/new` in `VisitController.java`, and there is no login.

## Assumptions (I couldn't ask)
- "Online" means the existing public web form. Adding user accounts and login is out of scope.
- Appointments are fixed 30-minute slots between 09:00 and 17:00, set as properties so they can be changed. The server's time zone applies.
- "Same time" means the same vet, the same date and the same slot start time.
- Old visits keep an empty vet and time, so they never conflict with anything.
- Existing MySQL and Postgres databases must keep working. On those profiles the app re-runs `schema.sql` at every startup.

## Steps
1. **Database rule:** add `vet_id` (linked to `vets`) and `visit_time` to the `visits` table, plus a uniqueness rule `uq_visits_vet_slot` on (vet, date, time). This rule is what actually stops double-booking, even when two people submit at the same moment.
   - **H2:** edit the table definition directly, since it's rebuilt at every startup.
   - **Postgres:** add the columns and index with "if not exists" statements, so existing databases upgrade safely.
   - **MySQL:** it has no "add column if not exists", so new installs get the columns in the table definition. Existing databases need a one-off `migrate_visit_booking.sql`, documented in the MySQL setup notes.
2. **Sample data:** the H2 and MySQL `data.sql` files insert visits by column position. Adding columns breaks that, so switch them to explicit column names.
3. **`Visit.java`:** add a `vet` field and a `time` field (`LocalTime`, format `HH:mm`), both required for new bookings. Load the vet eagerly, because the setting `open-in-view=false` would make a lazily loaded vet fail when a page displays it.
4. **Picking the vet on the form:** add a `VetFormatter`, copying the approach of `PetTypeFormatter`, plus `VetRepository.findById`. The form has to send the vet as `vet`, not `vet.id`, because the controller blocks every field named `*.id`.
5. **New `VisitRepository`:** one query to check whether a slot is taken (`existsByVetIdAndDateAndTime`) and one to list a vet's booked times on a date.
6. **Controller:** check that the slot is inside clinic hours and starts on a slot boundary. Check whether it's already taken, so the user gets a clear message. Then save with `saveAndFlush`. If two requests still race, catch the database's duplicate error for `uq_visits_vet_slot` and show it as "slot taken". This is the same pattern `PetController` already uses for duplicate pet names.
7. **Pages:**
   - On the booking form, add a vet dropdown and a time dropdown.
   - Show the vet and time in the pet's previous visits and on the owner details page.
8. **Translations:** add the new labels and messages to all 11 `messages*.properties` files. `I18nPropertiesSyncTest` fails if any file is missing a key.

## Verification
- **Controller tests:** a successful booking, missing vet or time, slot already taken, slot outside hours, and the duplicate-error path.
- **Concurrency test:** modelled on `PetClinicConcurrencyTests`. Several threads book the same vet and slot at once; exactly one succeeds and one row is stored.
- **Allowed cases:** a different vet in the same slot, or the same vet in the next slot, both succeed.
- **Real databases:** run the MySQL and Postgres integration tests. Also start the app against a database created with the old schema, to prove the upgrade works, and run the MySQL migration script on an old database.
- **Full build and manual check:** run `./mvnw verify`, then try booking the same slot from two browser tabs.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing MySQL/Postgres databases never get the new columns | `CREATE TABLE IF NOT EXISTS` skips existing tables, so the app fails when it touches `vet_id` | Postgres "if not exists" statements; MySQL migration script; test against an old-schema database |
| 2 | Two simultaneous submissions both pass the "is it free?" check | That check happens before the save, so it can't stop a race | Database uniqueness rule plus handling the duplicate error |
| 3 | Duplicate error matched by reading the error message | Wording and case differ between H2, MySQL and Postgres | Name the rule identically everywhere; lowercase match; test on all three databases |
| 4 | Sample data fails to load | H2 and MySQL inserts list values by position | Switch to explicit column lists |
| 5 | The vet field can't be filled from the form | The controller blocks fields named `*.id` | Bind `vet` through `VetFormatter` |
| 6 | Pages crash when showing the vet | `open-in-view=false` breaks lazy loading during page rendering | Load the vet eagerly |
| 7 | Old visits have no vet or time | Making the columns required would reject existing rows | Leave the columns optional in the database and enforce them only for new bookings |
| 8 | A translation file is missed | `I18nPropertiesSyncTest` fails the build | Add the keys to all 11 files |
| 9 | Anyone can book for any owner | The app has no login | Called out as out of scope; add login before going live |
| 10 | Time zone or clinic-hours mismatch | Uses the server clock (`LocalDate.now()`) | Make the zone and hours configurable |

Riskiest: #1. Existing MySQL/Postgres databases won't get the new columns from the startup scripts, so booking breaks after deploy unless the migration is handled.
