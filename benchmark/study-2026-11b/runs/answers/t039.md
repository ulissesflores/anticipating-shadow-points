## What the code does today

- **`Visit`** (`owner/Visit.java`) has only a date (`LocalDate`) and a description. It has no time and no vet. The `visits` table has `id, pet_id, visit_date, description` in all three schemas (`db/h2`, `db/mysql`, `db/postgres`).
- **`VisitController`** already lets anyone book through `POST /owners/{ownerId}/pets/{petId}/visits/new`. It checks that the date is in the future, then saves via `owners.save(owner)`, which cascades from Owner to Pet to Visit.
- **There is no Spring Security and no login.** Anyone who knows or guesses an owner ID can book for that owner.
- **Schema changes aren't applied automatically.** `ddl-auto=none` and `spring.sql.init.mode=always`. MySQL and Postgres use `CREATE TABLE IF NOT EXISTS`, so a database that already exists won't get new columns. There's no Flyway or Liquibase.
- **Seed data uses positional inserts**, e.g. `INSERT INTO visits VALUES (default, 7, '2013-01-01', ...)`.
- **The form binder blocks `*.id`**, so a nested `vet.id` field from the form would be silently dropped.
- **`I18nPropertiesSyncTest`** requires every new message key to exist in all 11 message files.

## Ways this could go wrong

1. **Race condition.** Two people submit the same vet and time at once. Both pass a "check, then insert" lookup and both bookings are saved. Only a database constraint prevents this.
2. **No time of day today.** "Same time" means nothing until visits have a start time. If visits can have different lengths, overlaps can't be caught by a simple unique constraint. Postgres can do it with an exclusion constraint, but H2 and MySQL can't.
3. **Existing MySQL/Postgres databases never get the new columns.** The app starts, then fails on the first insert or read.
4. **Seed data breaks.** The positional `INSERT INTO visits VALUES (...)` statements fail once the column count changes.
5. **Vet selection is silently ignored.** If the form posts `vet.id`, the `*.id` rule drops it, so the visit saves with no vet and no clash is ever detected.
6. **A clash shows as an HTTP 500.** The duplicate-key error (`DataIntegrityViolationException`) is thrown at save time, after validation has passed. It needs to be caught and turned into a form error.
7. **Old visits have no vet.** The new vet column must allow empty values. All three databases treat those as distinct in a unique constraint, so old rows won't block anything, but that needs a test.
8. **No owner check.** "Pet owners book online" implies a logged-in owner. Today any visitor can book for any owner's pet. Adding login is a much bigger change.
9. **Time zones.** `LocalDate.now()` uses the server's zone, so "tomorrow" and the slot times can be off for users elsewhere.
10. **Tests and translations.** `VisitControllerTests` will need a `VetRepository` mock, and every new message key must go into all 11 language files.

## Assumptions

- "Online" means the existing Thymeleaf form, which owners reach through the current owner and pet pages. Adding login is out of scope, but I flag it as a risk.
- Bookings use fixed 30-minute slots during clinic hours (09:00–17:00 to start with, set in config). With a fixed slot length, "same time" means "same slot", so one unique constraint on (vet, date, time) works on H2, MySQL and Postgres.
- The owner must pick a vet. There's no matching by specialty, and no cancel or reschedule in this change.

## Plan

1. **Schema, in all three `schema.sql` files.** Add a `vet_id` column (empty allowed, linked to `vets`) and a `visit_time TIME` column. Add the unique constraint `uk_visits_vet_slot (vet_id, visit_date, visit_time)` and an index on `vet_id`. For existing MySQL/Postgres databases, ship a one-off `ALTER TABLE` script in `db/*/` and document it, or introduce Flyway. I recommend Flyway if the app is deployed anywhere real.
2. **Seed data, in all three `data.sql` files.** Change the visit inserts to name their columns.
3. **`Visit.java`.** Add `@ManyToOne Vet vet` and `LocalTime time` with `@NotNull`, plus a check that the time falls on a slot boundary within clinic hours.
4. **`VisitController`.**
   - Inject `VetRepository`.
   - Expose a `vets` model attribute.
   - Bind the vet through a separate `vetId` request parameter (or a `Vet` formatter like `PetTypeFormatter`) to get around the `*.id` rule.
   - Before saving, check whether the slot is free (new method `VisitRepository.existsByVetIdAndDateAndTime`) to give a friendly error.
   - Also catch `DataIntegrityViolationException` around the save and turn it into `result.rejectValue("time", "slotTaken")`. That handles the race the first check can't.
   - Saving the visit through a small `VisitRepository` (or flushing inside a transaction) makes sure the error is thrown inside the controller, where it can be caught.
5. **Template `pets/createOrUpdateVisitForm.html`.** Add a vet dropdown (the `fragments/selectField` fragment) and a time input. Show vet and time in the "Previous Visits" table.
6. **Translations.** Add the `slotTaken`, `vet` and `time` keys to all 11 `messages*.properties` files.
7. **Tests.**
   - `VisitControllerTests`: the slot-taken path, the duplicate-key path, a missing vet, and a time off the slot grid.
   - A `@DataJpaTest`: inserting two visits with the same vet, date and time raises the duplicate-key error, while two old visits with no vet are both accepted.
   - A test that two simultaneous submissions produce exactly one booking.
   - Existing tests (`ClinicServiceTests`, `OwnerControllerTests`) must keep passing.

**How to check it:** run `./mvnw test`, and run against Postgres and MySQL through `docker-compose` (empty database and an upgraded one). Then book the same slot from two browser tabs: the second should get the form error, not a 500.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Race lets two bookings into one slot | Saving cascades through Owner, and a "check then insert" lookup isn't atomic | Unique constraint on (vet, date, time); keep the check only for a friendly message |
| 2 | Clash shows as HTTP 500 | Duplicate-key error is thrown at save time, after validation | Catch it around the save and turn it into a form error |
| 3 | Existing databases never get the new columns | `CREATE TABLE IF NOT EXISTS`, no migration tool | Ship `ALTER TABLE` scripts or adopt Flyway |
| 4 | Seed data fails at startup | Positional `INSERT INTO visits VALUES (...)` | Name the columns in all three `data.sql` files |
| 5 | Vet silently not saved, so no clash detection | Binder blocks `*.id` | Bind a separate `vetId` parameter or use a `Vet` formatter; `@NotNull` on vet |
| 6 | Overlapping visits slip past the constraint | Variable lengths can't be expressed as a portable unique constraint | Fixed 30-minute slots, checked on the server |
| 7 | Old visits with no vet break the constraint | Existing rows have no vet | Allow an empty vet; test that empty values are treated as distinct |
| 8 | Anyone can book for any owner | No login; owner ID is in the URL | Flag it; add Spring Security plus an ownership check as a follow-up |
| 9 | Slot and date shift by time zone | `LocalDate.now()` uses the server's zone | Use a configured clinic time zone via `Clock` |
| 10 | Build breaks on translations and mocks | `I18nPropertiesSyncTest`; `VisitControllerTests` | Add keys to all 11 files; mock `VetRepository` |

Riskiest: #1, the race between two simultaneous bookings. Unless a database unique constraint enforces it and the duplicate-key error becomes a form error, the core promise of no double bookings for a vet won't hold.
