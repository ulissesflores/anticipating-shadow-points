Most of this is already in the code. Commit a51468c ("modernize (#152)") made `src/Conduit/Infrastructure/Security/PasswordHasher.cs` produce ASP.NET Core Identity's PBKDF2-HMAC-SHA512 hashes at 210,000 iterations. It still accepts the old 64-byte HMAC-SHA512 hashes, whose key is the fixed string "realworld". `Features<home>:79-84` replaces an old hash with a new one when a user logs in successfully, and `PasswordHashingTests` covers that.

**What's missing:** users who never log in again keep the old hash forever, and that hash is fast to brute-force if the database leaks. The plan closes this without anyone resetting a password. I haven't edited any files; the plan is saved at `claude-home/plans/store-passwords-with-a-synthetic-frost.md`.

**The plan: wrap the old hashes**
1. **One-time rewrap:** for every row with an old hash `L`, store `0xF1 + PBKDF2(L)` instead. The 16-byte salt column is kept because it's needed to recompute `L` at login. This needs no plaintext and no schema change.
2. **Login check in `PasswordHasher.Verify`:** checks run in this order:
   - old raw hash (64 bytes, 16-byte salt);
   - wrapped hash (first byte `0xF1`, 16-byte salt): recompute `L` from the password, check it against the PBKDF2 hash, and report "success, rehash needed";
   - normal Identity hash (first byte `0x01`).

   The existing login path then upgrades wrapped rows to normal hashes without any change.
3. **`LegacyPasswordRewrapper`:** run once by an operator via a `Program.cs` flag (e.g. `--rewrap-legacy-passwords`), not at startup. It works in batches and only writes a row if its hash hasn't changed since it was read (`... WHERE PersonId = id AND Hash = oldHash`). That makes it safe to rerun and stops it overwriting a hash a concurrent login just upgraded.
4. **Tests:**
   - a wrapped hash verifies and gets upgraded on login;
   - a second rewrap run changes nothing;
   - the rewrap doesn't overwrite a hash changed by a concurrent login;
   - a normal hash made with fewer iterations reports "rehash needed", so future iteration increases also upgrade on login;
   - the existing `LoginTests` keeps passing.
5. **Docs:** add an operator step to `docs/database-migrations.md`. Check everything with `dotnet run --project build/build.csproj -- test`.

**Assumptions**
- Keep PBKDF2 at 210k iterations rather than adding Argon2id: it meets current OWASP guidance and needs no new package.
- Tell hash types apart with a marker byte instead of a new column, so no migrations are needed for SQLite and SQL Server.
- Only the rewrap step needs an operator; logins keep working the same way throughout.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Misreading the hash format | Formats are told apart only by byte length, first byte and salt length; `LoginTests` already stores a normal hash next to a 16-byte salt | Check the old format first, then `0xF1`; test every combination |
| 2 | Rewrap overwrites a hash a login just upgraded | Login can update the same row at the same moment | Only write if the hash is unchanged (`WHERE Hash = old`); add a race test |
| 3 | Rewrap is slow or locks the table | 210k iterations per row; large user tables | Run as a separate command in batches, not at startup |
| 4 | Accounts locked out by a bug in the wrapping | Wrapping can't be undone without the plaintext | Back up first; test on a copy; check a login after the run |
| 5 | Old hashes still there after the run | Rows added during the run or from restored backups | Safe to rerun; check that the old-hash count is 0 |
| 6 | Timing differences reveal the hash format | Wrapped rows compute HMAC plus PBKDF2, normal rows only PBKDF2 | Small, acceptable difference; the unknown-email path is unchanged |
| 7 | Slower login | 210k iterations on every login | Already the case today; watch latency |
| 8 | Hashes appear in logs | The new job touches every row | Log only counts |

Riskiest: #1, misreading the hash format. Because there's no explicit format column, one wrong length or marker check could quietly lock users out or accept a hash it shouldn't.
