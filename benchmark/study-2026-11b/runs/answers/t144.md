I've written the plan to `claude-home/plans/require-new-users-to-stateful-nest.md`. I edited no repo files. This is the Remix Blues stack (Prisma, Postgres, sessions stored in a cookie).

## What I found
- `app/routes/join.tsx` logs the new user in straight away: it calls `createUser` and then `createUserSession`.
- `verifyLogin` in `app/models/user.server.ts` checks only the password.
- `requireUser` and `getUser` in `app/session.server.ts` only check that the user exists.
- The repo has no email-sending code. MSW (`mocks/index.js`) is already wired in for dev and e2e, so it can intercept outbound email calls.
- The seed user `rachel@remix.run`, `cypress/support/create-user.ts` and the sign-up test in `cypress/e2e/smoke.cy.ts` all assume a new account can log in immediately.

## Ways this could go wrong
1. **Existing users get locked out.** A new `emailVerifiedAt` column starts as null for every existing row, including the seed user.
2. **Sign-up still creates a session.** If join keeps calling `createUserSession`, the check at login is pointless.
3. **Old sessions bypass the check.** Sessions store only `userId`, so an unverified user with a session from another path would never be checked.
4. **Unverified accounts block the real owner.** Someone signs up with another person's address and never verifies. The real owner then gets "A user already exists".
5. **Email scanners use up the link.** Corporate mail scanners open links to check them, which would consume a single-use token sent as a plain GET link.
6. **Leaked tokens.** Storing tokens in plain text, or tokens that never expire or can be reused, makes them usable by anyone who sees them.
7. **Revealing which emails exist.** Saying "please verify" before the password is checked, or a resend form that answers differently for unknown emails, tells an attacker which addresses have accounts.
8. **Poisoned links.** Building the link from the request's Host header lets an attacker point it at their own site.
9. **Sending failures.** If the email API fails or is down, or no key is set on Fly, sign-up throws an error or leaves accounts stuck. Unlimited resends can also be used to spam people.
10. **Tests break.** The smoke test and `create-user.ts` assume instant login. The seed script needs updating too.

## Plan
**Assumptions:**
- "New users" means accounts created after deploy; existing users are marked verified by a backfill.
- Tokens are random 32-byte values, stored as SHA-256 hashes, last 24 hours and work once.
- The email provider is called over HTTP, with its key and the app URL set as env variables.

**Steps:**
1. **Database:** add `User.emailVerifiedAt` and an `EmailVerificationToken` table. The same migration sets `emailVerifiedAt = createdAt` for existing users.
2. **Sign-up:** `join.tsx` creates the token, sends the email and goes to a "check your email" page, with no session. Signing up again with an unverified email resends the link.
3. **Verify page:** a new `verify-email.tsx` route. Opening the link shows a "Confirm" button, and only the button press uses up the token (so scanners don't) and logs the user in.
4. **Login:** check `emailVerifiedAt` only after the password matches, and offer a resend at that point.
5. **Session check:** `requireUser` and `getUser` treat unverified users as logged out.
6. **Resend:** rate-limited, and the reply is the same whether or not the email exists.
7. **Email:** a new `email.server.ts` builds links from the configured app URL, not the Host header.
8. **Tests and seed:** the seed user and Cypress test users are created verified. The e2e sign-up test reads the token through a small helper script and follows the link. Unit tests cover token expiry and reuse.

**How to check it:** run `npm run setup` on a fresh database and confirm the seed user still logs in. Then sign up in dev and confirm login is refused until the link is used. Finally run `npm run validate`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Existing users locked out | New column is null for every current row, including the seed user | Backfill `emailVerifiedAt = createdAt` in the same migration; update seed |
| 2 | Check bypassed | `join.tsx` logs users in at once; `requireUser` only checks the user exists | Remove the session from join; check verification in `requireUser`/`getUser` |
| 3 | Unverified accounts block real owner | Join rejects any existing email | Re-signup of an unverified email resends the link |
| 4 | Link scanners use up tokens | Single-use token in a plain link | Link opens a page; only the Confirm button uses the token |
| 5 | Weak tokens | No token system exists yet | 32 random bytes, stored hashed, 24h expiry, deleted once used |
| 6 | Reveals which emails exist | Login and resend could answer differently | Check verification only after the password; same resend reply for all |
| 7 | Poisoned links | Link built from the Host header | Build it from the configured app URL |
| 8 | Email sending fails | No email setup in repo or on Fly | Add env vars to `.env.example` and Fly; handle errors; MSW in dev/test |
| 9 | Resend used to spam | Endpoint needs no login | Limit per user and per address |
| 10 | Tests and deploy break | Smoke test expects instant login | Mark test users verified; token helper for the e2e sign-up flow |

Riskiest: #2, the check bypassed through the session created at sign-up (closely followed by #1, locking out existing users if the backfill is missed).
