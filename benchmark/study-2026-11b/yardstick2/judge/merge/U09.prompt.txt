Three reviewers independently listed ways a software change could go wrong.

Change request: Store passwords with a stronger hashing scheme without forcing existing users to reset their passwords.

Items (the letter is the reviewer):
A1. In PasswordHasher.cs, algorithm detection currently relies on a fragile byte-length check (hash.Length == 64 && salt.Length == 16) for HMAC-SHA512 before passing payloads to ASP.NET Core Identity's VerifyHashedPassword. Introducing a third hashing format risks decoding errors or format collisions unless an explicit format discriminator is established to distinguish HMAC, Identity PBKDF2, and the new scheme.
A2. Transparent rehashing upon authentication is implemented only in Login.Handler, whereas Edit.Handler updates password hashes only when a new password is explicitly submitted. Users who authenticate exclusively through existing JWT tokens without logging in via /api/users/login will continue using legacy password hashes indefinitely.
A3. The Person entity lacks concurrency tokens or row-versioning, leaving rehash operations vulnerable to race conditions. Simultaneous login requests for the same account, or a login concurrent with a profile update in Edit.cs, could overwrite newer user data or trigger concurrency exceptions under SQL Server's ReadCommitted isolation.
A4. Password hashing in PasswordHasher executes synchronously on thread-pool threads via Task.FromResult. Upgrading to a computationally heavier or memory-intensive algorithm doubles the execution overhead during an existing user's first login (verifying the legacy hash and generating the new hash), risking thread-pool starvation and request timeouts under peak login traffic.
A5. If the new hashing scheme requires alterations to Person.Hash, Person.Salt, or the addition of algorithm metadata columns, migrations must be synchronized across both SqliteConduitContext and SqlServerConduitContext. Any discrepancy between the providers will immediately cause MigrationTests.cs to fail its HasPendingModelChanges() assertion and break CI.
A6. ConduitMapper.cs uses Riok.Mapperly code generation with explicit [MapperIgnoreSource] attributes on Person.Hash and Person.Salt. Adding any new domain properties to Person (such as an algorithm version indicator) will produce compilation errors under the repository's strict <WarningsAsErrors>true</WarningsAsErrors> build configuration until the mapper is updated.
A7. The IPasswordHasher interface enforces Hash(string password, byte[] salt) and Verify(string password, byte[] hash, byte[] salt), and multiple test classes (CreateTests, LoginTests, EditTests) instantiate new PasswordHasher() directly rather than resolving it from DI. Altering this signature or adding constructor dependencies will break compilation across numerous integration test fixtures.
A8. Because Login.Command does not implement IReadOnlyRequest, every login is wrapped in an explicit transaction by DBContextTransactionPipelineBehavior, which uses Serializable isolation for SQLite. Converting every active user's initial login from a read operation into an immediate database write will significantly increase database lock contention on SQLite deployments.
A9. The project enforces centralized package management via Directory.Packages.props and locked restores via RestorePackagesWithLockFile. Introducing third-party cryptographic dependencies (such as an Argon2 or BCrypt library) requires updating locked package files and risks introducing cross-platform native runtime issues between macOS, Linux, and containerized deployments.
A10. Existing integration tests in PasswordHashingTests.cs explicitly assert legacy HMAC rehash semantics and verify that upgraded records have empty salt arrays (Assert.Empty(upgraded.Salt)). Changing the hashing strategy, payload representation, or rehash lifecycle without updating these tests will cause the test suite to fail.
A11. Sequential fallback verification across multiple algorithm generations (HMAC-SHA512, Identity PBKDF2, and the new scheme) introduces execution timing variances during authentication. Without constant-time mitigation across all branches, differences in verification duration could leak whether an account is on a legacy format or facilitate account enumeration.
B1. Legacy hash compatibility – Existing users still have HMAC‑SHA‑512 hashes (64 bytes + 16 byte salt); switching to a stronger scheme must retain verification for these legacy hashes, otherwise logins will fail for all current accounts.
B2. Database schema changes – A stronger hash (e.g., Argon2id) will produce longer encoded strings; the PasswordHash column may need length adjustment, and any hard‑coded size checks in the code or migrations could cause truncation errors.
B3. Re‑hash trigger logic – The current Verify method returns SuccessRehashNeeded for legacy hashes; introducing a new scheme requires updating the login flow to automatically re‑hash the password on successful verification, which may be missed and leave old hashes unchanged.
B4. Performance impact – Increasing the work factor (e.g., higher iteration count or memory‑hard Argon2 parameters) can significantly raise CPU/memory usage during login, potentially causing time‑outs or degraded user experience under load.
B5. Salt handling – The existing implementation expects a separate salt byte array; a modern scheme often embeds the salt in the stored hash. Mismatched expectations may lead to null‑reference errors or incorrect verification if the API surfaces the salt incorrectly.
B6. Testing coverage gaps – The test suite only includes a PasswordHashingTests for the current logic; without new tests for the upgraded algorithm, regressions (e.g., failure to verify or re‑hash) may go undetected.
B7. Dependency version lock – The PasswordHasher relies on Microsoft.AspNetCore.Identity with a specific IterationCount; upgrading to a different algorithm may require adding a new NuGet package (e.g., Isopoh.Cryptography.Argon2) and updating the lock file, risking build failures if the package is not pinned.
B8. Error handling and exception safety – Converting the new hash to Base64 and storing it could throw FormatException or OutOfMemoryException; the current Dispose method does nothing, so any new resources (e.g., native libs) must be disposed to avoid leaks.
B9. Migration strategy – Performing an in‑place migration without forcing password resets demands a “lazy” re‑hash on next successful login; failing to implement this correctly could lock users out or leave a mixed‑state of hash versions that complicates future maintenance.
B10. Security policy compliance – The change must be reflected in ADRs, CHANGELOG, and any external security audit documentation; omission could result in non‑compliant releases and audit failures.
B11. Concurrency race conditions – If multiple login attempts trigger re‑hashing simultaneously, the user record could be updated concurrently, leading to lost updates or inconsistent PasswordHash values.
B12. Impact on token generation – The JwtTokenGenerator may embed password‑related claims or rely on hash verification timing; altering the hashing algorithm could affect token issuance latency or validation logic if not reviewed.
C1. PasswordHasher.Verify picks the algorithm by shape: a 64-byte Hash with a 16-byte Salt is HMAC-SHA512 over UTF-8(password) || salt using the literal key "realworld", and every other non-empty Hash is Convert.ToBase64String'd into Identity's PBKDF2 verifier at 210,000 iterations. A new encoding that is 64 bytes long, or that leaves Salt at 16 bytes, is checked as that HMAC; LoginTests already stores a current hash beside a 16-byte Guid salt because Hash() ignores the salt argument it is given.
C2. Rows already written as Identity PBKDF2 (registration, password edit, and any login that took the SuccessRehashNeeded path) have to keep verifying after the change. PasswordHashingTests builds the HMAC fixture in memory and round-trips whatever Hash() emits now, so there is no pinned payload (format marker, PRF, iteration count 210000) of a hash already sitting in Persons.Hash.
C3. Create, Edit, and the login upgrade all persist Hash() immediately, and the readme already says an older process cannot verify an upgraded password. A rolling deploy therefore locks a user out as soon as one new instance rehashes them on login, signup, or password change, and rolling the app back has the same result because the plaintext cannot be restored to the previous blob.
C4. Login is not an IReadOnlyRequest, so DBContextTransactionPipelineBehavior holds the SQLite write transaction or the SQL Server connection across synchronous Verify and Hash (Task.FromResult around the KDF). Login rejects only an empty password, while create and edit only require 8 characters, so a higher work factor lets one oversized password stall writers, and the unknown-email path returns 401 before any hashing, which widens the timing gap between missing users, fast HMAC rows, and upgraded rows.
C5. Accounts that never log in cannot be upgraded, because the plaintext exists only at login, so their HMAC under the hardcoded "realworld" key and their Salt stay offline-crackable for as long as reset is off the table. Removing the 64-byte branch or the Salt column locks those rows out; docs/database-migrations.md says neither password column changes, and both the SQLite BLOB and SQL Server varbinary(max) snapshots have to keep reading the old salt.
C6. Person has no concurrency token, and the SuccessRehashNeeded branch in Login loads the row and later overwrites Hash and sets Salt to empty. A concurrent Edit that sets a new password, without checking the previous one, can be overwritten by an in-flight login that still holds the old password, and that write happens on every login if the new verifier keeps returning SuccessRehashNeeded after the row is already on the new scheme.
C7. The salt contract is split across the interface and the column: Hash(password, salt) currently discards salt and Identity embeds its own, while HMAC verification requires Person.Salt.Length == 16, and Create, Edit, and Login each pass [] and clear person.Salt themselves. A replacement that consumes the argument, or that stops clearing Salt, either stores passwords that can never verify or recreates the 16-byte salt that selects the HMAC branch.
C8. Login upgrades a row only when Verify returns PasswordVerificationResult.SuccessRehashNeeded and treats any other non-failure as success, so the new verifier has to map "recognized but weaker" onto that value and garbage onto Failed. Identity already runs PBKDF2 with the iteration count stored inside Hash; a scheme whose memory or time cost is also taken from the row will run those parameters inside the open transaction, and a throw from the parser becomes a 500 from ErrorHandlingMiddleware after rollback, so a correct password still fails the request.
