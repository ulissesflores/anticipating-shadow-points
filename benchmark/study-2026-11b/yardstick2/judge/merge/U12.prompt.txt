Three reviewers independently listed ways a software change could go wrong.

Change request: Make the session middleware's cookie Secure and SameSite=Strict by default.

Items (the letter is the reviewer):
A1. In starlette/testclient.py, TestClient defaults to baseurl="http://testserver". Because HTTPX does not transmit Secure cookies over insecure HTTP connections, enabling Secure by default will break the majority of existing test cases in tests/middleware/testsession.py that rely on sessions persisting across requests.
A2. Applications running in local development or test environments over plain HTTP (such as http://127.0.0.1:8000 or non-TLS containers) will fail to persist sessions because browsers drop Secure cookies on unencrypted origins. Developers would encounter broken session behavior out of the box without clear diagnostic errors.
A3. Setting SameSite=Strict by default prevents browsers from sending the session cookie on top-level cross-site GET navigations, such as following an external link or opening a bookmark. Users navigating to the application from external sites will appear unauthenticated on their initial landing page until an internal navigation occurs.
A4. Authentication workflows that rely on third-party redirects—such as OAuth2 callbacks, OpenID Connect logins, or SAML identity provider flows—will break because incoming redirects will not carry the session cookie under SameSite=Strict. This will cause state parameter validation failures and loss of pre-authenticated session context.
A5. SessionMiddleware.init configures the cookie's secure attribute via the parameter httpsonly: bool = False, unlike Response.setcookie which uses secure: bool = False. Changing the default value or renaming the parameter to match the rest of the codebase risks breaking existing keyword arguments and callers across the ecosystem.
A6. In starlette/responses.py, Response.setcookie and Response.deletecookie default to secure=False and samesite="lax". Changing SessionMiddleware to default to Secure and Strict introduces inconsistent cookie defaults across Starlette's API surface.
A7. In SessionMiddleware.call, sessions are initialized as empty if no valid cookie is received in connection.cookies. Under SameSite=Strict, a cross-site GET request to a route that modifies session data will create and overwrite the session, inadvertently destroying or replacing the user's existing authenticated state.
A8. SessionMiddleware handles scope["type"] == "websocket", extracting cookies during the initial connection handshake. Marking the cookie Secure by default will block browsers from sending the session cookie over unencrypted WebSocket connections (ws://), breaking WebSocket endpoints during local development or in non-TLS environments.
A9. SessionMiddleware supports partitioned cookies for embedded contexts (partitioned: bool = False), which explicitly requires samesite="none" and HTTPS as documented in docs/middleware.md. Defaulting to SameSite=Strict will silently break embedded or iframe use cases unless developers explicitly override both parameters.
A10. docs/middleware.md explicitly instructs users that httpsonly defaults to False and samesite defaults to 'lax', with specific recommendations for production configuration. Modifying these defaults without synchronizing the documentation, release notes, and migration guides will cause user confusion and unexpected breaking changes for downstream frameworks like FastAPI.
B1. Breaks non‑HTTPS deployments – The middleware will always set the Secure flag, so browsers will refuse to send the session cookie over plain HTTP, causing authentication to fail in local development or any environment that does not serve traffic over TLS.
B2. Disrupts existing cross‑site flows – Switching the default SameSite from Lax to Strict will prevent the cookie from being sent on legitimate cross‑origin POSTs (e.g., OAuth redirect callbacks, embedded payment forms), leading to login or payment failures.
B3. Incompatible with legacy browsers – Older browsers (e.g., Safari 12, Internet Explorer) do not understand SameSite=Strict or the Secure attribute on cookies and may drop the cookie entirely, breaking sessions for users on those platforms.
B4. Test suite mismatches – Several tests in tests/middleware/testsession.py assume the default SameSite=Lax and Secure=False; changing the defaults will cause those tests to fail until they are updated to reflect the new cookie policy.
B5. Cookie‑clearing inconsistencies – The code that clears a session (elif session.modified and not initialsessionwasempty) re‑uses self.securityflags. If the defaults are changed, stale cookies set with the old flag combination may remain, causing ambiguous session state after a logout.
B6. Potential domain‑scope issues – The Secure flag is added regardless of the optional domain parameter. Deployments that rely on cross‑subdomain cookies may encounter unexpected restrictions when the cookie is forced to be sent only over HTTPS and with SameSite=Strict.
B7. Unexpected header size growth – Adding ; secure; samesite=strict to every Set‑Cookie header increases its length; on edge cases with many cookies this could push the header over typical size limits, resulting in dropped cookies.
B8. Breaking third‑party integrations – External services that set their own session‑related cookies (e.g., analytics, SSO providers) may clash with the stricter defaults, leading to duplicated or rejected cookies.
B9. Reduced flexibility for advanced users – The httpsonly flag becomes redundant, and developers who previously relied on toggling it to enable Secure only in production will lose that granular control, possibly requiring code changes elsewhere.
B10. Documentation drift – The docs in docs/middleware.md currently describe the default behavior (samesite="lax" and httpsonly=False). Changing the code without updating the documentation will create misinformation for downstream users.
B11. Potential security regression in mixed‑content setups – Some applications deliberately serve mixed HTTP/HTTPS content and rely on the cookie being sent over HTTP for certain internal API calls; the new default will block those calls, unintentionally exposing the application to CSRF if developers fall back to insecure workarounds.
B12. Compatibility with HTTP‑only health checks – Health‑check endpoints that hit the application over plain HTTP (common in Kubernetes readiness probes) will now receive a 401/403 due to missing session cookies, possibly causing false‑negative health reports.
C1. TestClient defaults to baseurl="http://testserver", and testsecuresession already shows that a Secure session cookie is dropped there: the update returns the new session, and the next request sees {"session": {}}. Most of tests/middleware/testsession.py builds SessionMiddleware with only secretkey on that HTTP client, so the new default fails those round-trips with no exception.
C2. docs/middleware.md publishes samesite default 'lax' and httpsonly default False ("set this to True in production"), and docs/config.md installs SessionMiddleware with only secretkey. Flipping both defaults is a breaking change for every caller that omitted those arguments, and those pages plus docs/release-notes.md stay wrong until they are updated in the same change.
C3. SameSite=Strict withholds the cookie on a cross-site top-level GET, which the current 'lax' default still sends. The session lives only in that signed cookie, so the landing request gets a new empty Session and the app cannot tell it from a logged-out user. samesite is already the opt-in for strict.
C4. partitioned=True is documented to require samesite="none" as well as Secure. The constructor only concatenates flags, so SessionMiddleware(..., partitioned=True) would emit samesite=strict; secure; partitioned, which browsers discard. testpartitionedsession only covers the explicit samesite="none", httpsonly=True pair, so it stays green.
C5. Callers who already pass samesite="none" and leave httpsonly at its current default get a cookie browsers reject. With Secure on by default, that same call starts storing a real cross-site session cookie, which is a wider send than today, and the middleware does not warn.
C6. Write and clear share one securityflags string, and Response.deletecookie still defaults to secure=False, samesite="lax". A Secure expiry is ignored on plain HTTP, so clearsession stops deleting the pre-change cookie, and a deletecookie("session") that follows docs/responses.md no longer matches the middleware cookie because path, Secure, SameSite, and Partitioned have to match.
C7. The middleware reads the cookie on websocket scopes but only writes Set-Cookie on http.response.start. A Secure cookie is not sent on a ws:// handshake, and HTTPSRedirectMiddleware answers ws with a 307 to wss without carrying the session. No session test opens a websocket.
C8. httpsonly=False has to remain a real override. The comment in starlette/middleware/sessions.py says the Secure flag is for HTTPS only, and testsessioncookiesubpath pins baseurl="http://testserver/secondapp". Always appending secure, instead of changing the default, removes the only HTTP path this repo supports.
C9. The break is silent. testsecuresession expects {"session": {}} after a successful update on http://testserver, not an error, so the documented app and its tests look as if the session was never saved.
