Three reviewers independently listed ways a software change could go wrong.

Change request: Let authors change an article's title, and its URL slug with it, without breaking links that were already shared.

Items (the letter is the reviewer):
A1. FindOneArticle(&ArticleModel{Slug: slug}) is hardcoded across all article endpoints (ArticleRetrieve, ArticleFavorite, ArticleCommentCreate, etc.) in articles/routers.go to query ArticleModel by Slug directly. Supporting historical slugs requires decoupling this lookup into an alias-aware resolution layer so that all handlers consistently locate the current article without breaking existing query signatures.
A2. In ArticleDelete (articles/routers.go), the handler executes DeleteArticleModel(&ArticleModel{Slug: slug}) using the raw URL parameter rather than the resolved article's primary key or current slug. If an article is accessed and deleted via a historical slug, GORM will attempt to delete a non-existent slug on ArticleModel, returning HTTP 204 while leaving the article intact in the database.
A3. makeUniqueSlug in articles/models.go only counts collisions against ArticleModel.Slug and ignores historical slug aliases. A newly created or retitled article could claim an old slug that was previously shared, leading to routing ambiguity or hijacking existing links unless makeUniqueSlug and its retry loop validate against both current and historical slugs.
A4. ArticleUpdate executes articleModel.Update(updates) without a database transaction and relies on an optimistic retry loop for unique index collisions. Updating the current slug on ArticleModel while simultaneously inserting or updating a historical alias record across multiple steps risks partial failures and database inconsistency during concurrent requests.
A5. Endpoints such as PUT /api/articles/:slug, POST /:slug/comments, and POST /:slug/favorite share the same /:slug path parameter as retrieve operations. If historical slugs are allowed on mutation endpoints, users might modify articles under obsolete identities; if disallowed, interactive widgets on shared links may break with 404 errors.
A6. An author may rename an article back to an earlier title or swap titles between multiple articles, creating circular references or duplicate key errors in the alias history. The design must explicitly define how historical aliases are pruned, reclaimed, or redirected when a slug reverts to its original owner.
A7. ArticleModel embeds gorm.Model and uses soft deletes (DeletedAt), whereas historical slugs must be properly scoped to active articles. If an article is deleted, its slug history must either be soft-deleted or invalidated so that old links properly return 404 and historical slugs do not leak or permanently block reuse.
A8. Returning HTTP 301/308 redirects for historical slugs can break strict RealWorld API clients that do not follow redirects or that strip the Authorization: Token ... header on redirection. Conversely, serving 200 OK directly causes canonical URL duplication and may confuse clients because ArticleResponse omits the database ID (json:"-") and only returns the new slug.
A9. If historical slugs are permanently reserved to prevent breaking shared links, an author could hoard high-value slugs simply by repeatedly updating an article's title. The team must determine whether historical aliases ever expire or if original slugs can be reclaimed or reassigned across different authors.
A10. Database migrations in hello.go and test resets in articles/unittest.go (resetDBWithMock) rely on GORM's AutoMigrate over SQLite. Introducing a new alias table or modifying constraints requires updating migration lists across application entry points and all test fixtures, while SQLite's limited ALTER TABLE capabilities complicate schema evolution on existing databases.
B1. Updating the slug may break existing foreign‑key or relational constraints if any other tables (e.g., comments, favorites) reference the article by its slug instead of a stable ID.
B2. URL routing logic (articles/routers.go) currently matches on the slug; changing it could cause ambiguous routes or collisions with other resources if uniqueness checks are not enforced.
B3. Cached responses (e.g., in Redis or in‑memory structures) keyed by the old slug may become stale, leading to 404s or serving incorrect data.
B4. Search indexes or full‑text lookup tables that store the slug as a searchable field will need re‑indexing to avoid missing results after a title change.
B5. Client‑side code (e.g., frontend links) may hard‑code the slug in navigation components; a silent change could break navigation without a server‑side redirect.
B6. Existing API clients or third‑party services that store the article URL may continue using the old slug, resulting in broken links unless a redirect mechanism is added.
B7. Potential race conditions: simultaneous title updates could produce duplicate slugs or overwrite each other if slug generation isn’t atomic.
B8. Validation logic (articles/validators.go) may not currently enforce slug immutability; allowing edits could bypass length or character restrictions leading to malformed URLs.
B9. The common/database.go migration schema may lack a unique constraint on the slug column, causing duplicate entries after edits.
B10. Audit logging and change tracking (if any) may not capture slug changes, making it hard to trace link breakage after deployment.
B11. SEO metadata generation may rely on the original slug; changing it without updating sitemap entries could hurt search engine indexing.
B12. Unit and integration tests that assert fixed slug values will start failing unless they are updated to accommodate dynamic slug changes.
C1. FindOneArticle matches only ArticleModel.Slug, and retrieve, update, delete, favorite, unfavorite, and both comment routes each call it on their own. A shared URL is also the editor path (/#/editor/<slug>), the comment route, and the favorite route, so preserving the link only on GET /api/articles/:slug still leaves those handlers returning the {"errors":{"article":["not found"]}} body the tests assert.
C2. hello.go sets RedirectTrailingSlash to false because a redirect drops the body. A 301/302 from an old slug changes the status codes the pinned Hurl suite checks, and the hash clients in FRONTENDINSTRUCTIONS.md (/#/article/<slug>) will not rewrite that hash from an API Location.
C3. scripts/run-spec-tests.sh pins realworld-apps/realworld at 25588846c314b15a5e427ffe816e6b4af7be68c7 with a sha256, and that Hurl suite is the CI source of truth. It expects PUT to return 200 with the new slug in the article JSON and has no alias rule, so answering 200 for a slug that is no longer current can fail hurl-api-test or the weekly spec-drift run unless both pin constants move together.
C4. Slug is a uniqueIndex, delete is a GORM soft delete, and makeUniqueSlug counts Unscoped() rows, so a deleted article keeps its slug forever while FindOneArticle will not return it. makeUniqueSlug never looks at any other table, so a later POST /api/articles can take a slug that is still a shared link, and a soft-deleted row can block a rename onto a slug no live GET serves.
C5. makeUniqueSlug does not exclude the row being edited. An article already on base-2 whose new title slugifies to base is bumped to base-3 because its own current slug counts as taken, and a rename back onto a slug this article just released does the same, so the helper mints a suffix instead of reclaiming the shared URL.
C6. ArticleUpdate writes the new slug with Update, then ReplaceTags, then re-fetches, with no transaction. The retry loop only regenerates updates["slug"] twice, and only on gorm.ErrDuplicatedKey. TestArticleUpdateSlugRaceRetries already shows a concurrent insert taking the destination slug. The same window lets a create grab the old slug the moment the UPDATE frees it, before any alias row exists.
C7. Comments and favorites already point at the numeric article id (CommentModel.ArticleID, FavoriteModel.FavoriteID), so they survive a slug change. An alias stored as "previous slug string to next slug string" breaks on the second rename (A to B to C) once B is no longer on the row. TestArticleUpdateDescriptionAndCollidingTitle expects the colliding retitle to land on slugA-2, which stops being true once old slugs stay reserved.
C8. ArticleDelete checks AuthorID, then calls DeleteArticleModel with the path slug rather than the primary key. Resolving an alias for the read and then deleting by the raw param can return 204 and leave the row, and an alias that outlives the soft delete makes a later GET of that slug find the article again, against the test that a deleted slug is 404.
C9. Schema changes exist only as AutoMigrate in Migrate (hello.go) and again in TestMain (articles/unittest.go). A history table added in one place and not the other splits the test database from ./data/gorm.db, and AutoMigrate will not rebuild the existing unique index or record the current slug of rows already stored, so links shared before the deploy still 404.
C10. The slug moves only when makeSlug(title) != articleModel.Slug. github.com/gosimple/slug folds case and punctuation, so a real title edit can leave the slug unchanged, and a title that passes min=4 but is only symbols becomes an empty slug. An empty slug collides with GET /api/articles/, and makeUniqueSlug would then issue -2 and -3. The update validator checks the title string and never the generated slug.
