Three reviewers independently listed ways a software change could go wrong.

Change request: Make sessions roll by default, so that every request extends the session's expiry.

Items (the letter is the reviewer):
A1. In index.js, unmodified sessions rely on store.touch() rather than store.save(); if a session store does not implement touch(), the backend session TTL will not be extended, causing sessions to expire prematurely in the store while the client-side cookie continues to renew.
A2. Enabling rolling by default causes shouldSetCookie() to return true on every request for an active session, injecting a Set-Cookie header on all responses and breaking downstream HTTP caching and CDN edge caching.
A3. Because store.touch() is executed during res.end() on every request, rolling by default transforms all read-only HTTP traffic into write operations on the session store, risking severe I/O bottlenecks and connection pool exhaustion in external stores like Redis or MongoDB.
A4. When a session is configured without a maxAge (a browser-session cookie where expires is null), shouldSetCookie() still evaluates to true, repeatedly sending redundant Set-Cookie headers on every response even though there is no cookie expiration to extend.
A5. Because express-session only resets cookie.maxAge and lacks a built-in absolute expiration ceiling, rolling sessions by default allows sessions to remain active indefinitely through periodic background requests, significantly increasing the window of exposure for hijacked sessions.
A6. Concurrent requests from the same user will trigger simultaneous invocations of store.touch() (or store.save()) and res.setHeader('Set-Cookie', ...), creating race conditions, out-of-order cookie expirations, and potential session data overwrites.
A7. In index.js, res.end() is monkey-patched to defer response completion until store.touch() finishes, meaning every HTTP response will incur the latency of an asynchronous session store roundtrip before completing.
A8. When resave is true (or left undefined and defaulted to true), unmodified requests satisfy shouldSave() instead of shouldTouch(), triggering full session serialization and store.set() calls on every request rather than lightweight touches.
A9. Numerous unit tests in test/session.js explicitly assert that rolling defaults to false and that unmodified requests do not send a Set-Cookie header via shouldNotHaveHeader('Set-Cookie'), causing immediate, widespread test suite failures.
A10. Changing the default value of opts.rolling from false to true alters default HTTP header behavior and session lifecycles for all consumers, representing a breaking API change that requires a major version bump.
B1. Unintended session prolongation – Enabling rolling for all requests will continuously extend the cookie’s expiry, preventing sessions from naturally timing out and potentially keeping stale authenticated sessions alive indefinitely.
B2. Increased cookie traffic – Every response will now set a Set‑Cookie header, adding overhead to network traffic and increasing the size of HTTP responses, which may affect performance on high‑traffic services.
B3. Compatibility with saveUninitialized: false – When saveUninitialized is false, rolling by default may cause cookies to be sent even though no session data has been persisted, breaking the intended “no‑session‑cookie‑until‑data‑saved” semantics.
B4. Store‑specific side effects – Custom session stores that rely on explicit touch calls (e.g., Redis with TTL updates) may receive unnecessary touch operations, leading to higher write load and potential race conditions in distributed environments.
B5. Security exposure – Continuously refreshed session IDs increase the window for session hijacking attacks, especially if secure cookie flags (secure, httpOnly, sameSite) are misconfigured elsewhere in the code.
B6. Memory‑leak risk in MemoryStore – The default in‑memory store will retain more active sessions because they never expire, potentially exhausting server memory in long‑running processes.
B7. Breakage of tests expecting non‑rolling behavior – The test suite contains explicit checks for rolling: false (e.g., in test/session.js); changing the default may cause those assertions to fail and hide regressions.
B8. Interaction with cookie.maxAge reset – The Session.prototype.touch method resets maxAge to originalMaxAge; with rolling always on, this reset may be invoked more frequently, potentially overriding custom per‑request max‑age adjustments.
B9. Potential denial‑of‑service – Malicious clients can keep a session alive indefinitely by making frequent requests, denying legitimate users the ability to obtain fresh sessions when the server enforces concurrent session limits.
B10. Unexpected side effects for APIs – Stateless API endpoints that rely on short‑lived sessions may unintentionally keep sessions alive, leading to stale authentication contexts and harder debugging of token expiration bugs.
B11. Impact on load balancer sticky sessions – If the application is deployed behind a load balancer using sticky sessions tied to cookie expiry, constantly rolling cookies can interfere with session affinity and cause uneven request distribution.
B12. Compliance and audit concerns – Certain regulatory regimes require session lifetimes to be bounded; default rolling could violate policies that mandate fixed session expiration windows.
C1. rolling is documented as default false and test/session.js locks that in ('should default to false', and 'should Set-Cookie only once for browser-session cookies'). Changing Boolean(opts.rolling) in index.js breaks every caller that omits the option; resave and saveUninitialized only warn through depd and keep the old default on this 1.x line.
C2. The default cookie is { maxAge: null }, and Session.resetMaxAge only assigns cookie.maxAge = cookie.originalMaxAge, so there is no expiry to extend. MemoryStore.get deletes a record only when cookie.expires is already in the past, and rolling still forces Set-Cookie on every response by skipping the expires != null check in shouldSetCookie.
C3. rollingSessions is read only by shouldSetCookie. The stored expiry moves only in shouldSave (the deprecated resave: true default, or a real modification) or in store.touch. With the README’s recommended resave: false and a store that has no touch (SyncStore in the tests), the browser Expires slides while the store keeps the old date, the next get misses, and generate() replaces the sid.
C4. With resave left at its default true, every request already store.sets the whole session, which the README warns can let a parallel request overwrite the other. Default rolling also sends Set-Cookie from each of those responses, and MemoryStore.touch replaces currentSession.cookie wholesale, so the response that finishes last can publish an Expires taken from the copy loaded at the start of that request.
C5. Nothing in Session or Cookie caps an absolute lifetime; touch puts maxAge back to originalMaxAge on every finished response, and the middleware runs for every path rfcPathMatch accepts (default /). A short maxAge then never elapses while the client polls or loads assets with the cookie, and generateSessionId runs only when the cookie is missing or the store misses, so a stolen connect.sid stays valid for that same activity window.
C6. A fixed cookie.expires is turned into a duration by the expires setter (originalMaxAge = this.maxAge) and resetMaxAge rebuilds it as Date.now() + originalMaxAge. Once that value is written on every response, a calendar Expires (still documented, and covered by the epoch assertion Thu, 01 Jan 1970 00:00:00 GMT) keeps moving forward, and each save can drop originalMaxAge by a millisecond because the getter is expires - Date.now() and Store.createSession persists that number.
C7. cookie may be a function of req, but that function is applied in store.generate and in the path gate, while a rolled response sends the loaded req.session.cookie.data. A later request does not recompute maxAge, path, secure: 'auto', or sameSite: 'auto', so the middleware can renew a cookie whose stored Path no longer matches the callback, or skip renewal when the live callback path does not match.
C8. shouldSetCookie ignores status code, and setcookie appends a signed connect.sid to whatever Set-Cookie is already on the response, including 304s and bodies the app expected a cache to store. on-headers calls touch and setcookie when the first byte flushes (res.write and the Content-Length split in res.end); touched then blocks a second reset, so a slow body freezes Expires at header time (the slow-write test covers this only with rolling: true). If store.touch fails after that, the client already has the new cookie and the error is only handed to next via defer.
C9. shouldSetCookie still refuses a cookie for a new sid when saveUninitialized is false, which the README, the test 'should not force cookie on uninitialized session if saveUninitialized option is set to false', and the HISTORY note for rolling: true all require. Treating “every request” as an unconditional Set-Cookie would emit connect.sid on anonymous requests; with the deprecated saveUninitialized: true default, rolling also rewrites the cookie on every later hit to a session that was saved empty.
