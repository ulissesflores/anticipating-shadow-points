Three reviewers independently listed ways a software change could go wrong.

Change request: Change the default signing digest from SHA-1 to SHA-256.

Items (the letter is the reviewer):
A1. Existing production tokens and signatures (such as session cookies or password reset links) signed under the current SHA-1 default will fail validation with BadSignature, reproducing the severe backward-incompatibility issue that led to yanking release 1.0.0.
A2. Standalone Signer and TimestampSigner classes lack any fallback verification mechanism, meaning callers using them directly rather than through Serializer will immediately reject existing SHA-1 signatures unless custom multi-signer verification logic is manually added.
A3. Because Serializer.defaultfallbacksigners currently defaults to an empty list, even Serializer.loads() will fail to validate existing SHA-1 tokens by default unless SHA-1 is explicitly added to defaultfallbacksigners.
A4. In Signer.derivekey(), digestmethod is used for key derivation across concat, django-concat, and hmac modes, meaning switching to SHA-256 changes both the derived signing key material and the signature, breaking external compatibility with systems expecting Django-compatible SHA-1 key derivation.
A5. A SHA-256 HMAC digest produces 32 raw bytes (43 base64 characters) instead of SHA-1's 20 bytes (27 characters), increasing overall token length by 16 characters and risking payload overflow in size-constrained environments like HTTP cookie limits or compact URLs generated by URLSafeSerializer.
A6. Class-level defaultdigestmethod is declared independently on both HMACAlgorithm and Signer in src/itsdangerous/signer.py, creating a desynchronization risk if both attributes are not updated uniformly or if downstream subclasses override only one of them.
A7. The lazy loading pattern implemented via lazysha1 to prevent import-time exceptions on FIPS-compliant systems must be evaluated for SHA-256, and any retained SHA-1 fallback must preserve lazy resolution so it does not trigger errors on FIPS builds where SHA-1 is disabled.
A8. If SHA-1 is added as a default fallback signer to preserve backward compatibility, Serializer.iterunsigners() will run multiple key derivations and HMAC comparisons on invalid or legacy tokens, doubling CPU overhead per failed verification and potentially introducing timing side-channels.
A9. In distributed architectures and rolling deployments (such as multi-server Flask deployments), upgraded nodes will emit SHA-256 tokens that older nodes cannot parse, leading to session drops and authentication failures across the deployment window.
A10. Existing unit tests in tests/testitsdangerous/testserializer.py assert explicit equality against SHA-1 output (including testdigests checking the hardcoded signature [42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM and testiterunsigners checking for lazysha1), which will fail immediately without test updates.
A11. Documentation throughout docs/concepts.rst, docs/signer.rst, and class docstrings explicitly details hashlib.sha1 as the default, justifies its security properties in HMAC, and provides hardcoded SHA-1 examples that will become incorrect and misleading.
B1. Existing signed data becomes invalid – All signatures generated with the current SHA‑1 default (e.g., session cookies, CSRF tokens, URL‑signed values) will fail verification after the change, causing immediate authentication breaks for users with stored tokens.
B2. Backward‑compatible clients may reject SHA‑256 – External services or older client libraries that explicitly use itsdangerous.Signer(..., digestmethod=hashlib.sha1) will receive signatures they cannot validate, leading to integration failures.
B3. Test suite will break – Tests that assert exact signature lengths or compare against hard‑coded SHA‑1 digests (e.g., in tests/testsigner.py) will fail, requiring updates to expected values or fixtures.
B4. Potential performance impact – SHA‑256 is computationally heavier than SHA‑1; high‑throughput signing (e.g., per‑request signing of API tokens) may experience measurable latency increases, especially on low‑power environments.
B5. Migration strategy required – Changing the default without a migration path forces a “all‑or‑nothing” rollout; a staged approach (e.g., versioned signer or explicit digestmethod override) is needed to avoid service disruption.
B6. Documentation and public API mismatch – The library’s docs (e.g., docs/signer.rst) state SHA‑1 as the default; failing to update them will mislead users and cause confusion during debugging.
B7. Interoperability with other languages – Systems that verify signatures in other languages (Java, JavaScript, etc.) expecting SHA‑1 must be updated to use SHA‑256, otherwise cross‑service validation will break.
B8. Key‑derivation assumptions – Some key‑derivation functions may have implicit size expectations tied to SHA‑1 output length; switching to SHA‑256 may alter derived key lengths, affecting downstream cryptographic operations.
C1. Signer.defaultdigestmethod is also the hash in derivekey for the default django-concat scheme (salt + b"signer" + secretkey) and the HMAC inside HMACAlgorithm.getsignature. Existing tokens, including the pinned vector [42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM in tests/testitsdangerous/testserializer.py, will fail verification. Release 1.0.0 was yanked for a default-digest change, and 1.1.0 put the default back on SHA-1.
C2. Signer.unsign and TimestampSigner.unsign never consult fallbacksigners. Only Serializer.loads and TimedSerializer.loads do. Callers of the signer classes lose every existing signature, and those classes have no migration argument.
C3. defaultfallbacksigners is [] since 2.0, when the old SHA-512 compatibility fallback was removed. Serializer, TimedSerializer, URLSafeSerializer, and URLSafeTimedSerializer all inherit that empty list and do not set their own digest, so a default swap rejects their existing cookies and URL tokens.
C4. In iterunsigners, a dict fallback becomes the whole signerkwargs. A SHA-1 entry of {"digestmethod": hashlib.sha1} drops a caller's keyderivation or sep, so tokens signed with the old digest plus a non-default derivation such as "hmac" still fail.
C5. A new default SHA-1 fallback starts accepting SHA-1 again for applications that already passed digestmethod=hashlib.sha256 or sha512 and relied on the empty default. fallbacksigners=None copies defaultfallbacksigners, and TimedSerializer.loads never expires an algorithm: SignatureExpired stops the loop only after a digest has already matched.
C6. lazysha1 exists so FIPS builds that lack SHA-1 fail at first use, not at import (2.2.0). loads catches only BadSignature. A SHA-1 fallback that calls hashlib.sha1 on FIPS raises a different error and aborts the rest of iterunsigners.
C7. The default lives on both HMACAlgorithm.defaultdigestmethod and Signer.defaultdigestmethod. Signer passes the digest into HMACAlgorithm only when algorithm is omitted. Callers who pass a custom algorithm still derive the key with Signer.digestmethod, so updating one attribute and not the other mixes a SHA-256 key with a SHA-1 MAC.
C8. The signature is the raw HMAC, then base64encode strips padding, so the signed tail grows from 20 bytes to 32. URLSafeSerializerMixin compresses only the payload, and docs/concepts.rst already treats that growth as material for cookies and URLs.
C9. The tree is 2.3.0.dev, and the 2.3.0 changelog only drops Python 3.8/3.9 and removes deprecated code. A wire-incompatible default on that minor line breaks the compatibility 2.x has kept since 1.1.0, and the docstrings, docs/concepts.rst, and docs/serializer.rst still say the default is SHA-1 and that HMAC-SHA1 is acceptable.
