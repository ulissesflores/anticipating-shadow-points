Three reviewers independently listed ways a software change could go wrong.

Change request: Let pet owners book visits online, without two visits being booked for the same vet at the same time.

Items (the letter is the reviewer):
A1. VisitController.processNewVisitForm loads the Owner and persists visits in memory without transaction locking or concurrency checks, creating a race condition where concurrent booking requests for the same vet and time will result in duplicate bookings.
A2. The Visit entity and the visits tables across h2/schema.sql, mysql/schema.sql, and postgres/schema.sql lack any association or foreign key to Vet, requiring schema changes and coupling the currently independent owner and vet domain packages.
A3. Visit.java records visits using java.time.LocalDate (DATE in SQL) without a time-of-day, duration, or time-zone concept, requiring a temporal model redesign and migration of existing seed data in data.sql to support "at the same time" checks.
A4. The codebase contains no authentication or authorization layer, which leaves endpoints like /owners/{ownerId}/pets/{petId}/visits/new publicly exposed and allows anonymous users to book appointments on behalf of arbitrary owners.
A5. Visits are currently persisted exclusively through cascade saves on the Owner aggregate root (this.owners.save(owner)) rather than a dedicated VisitRepository, preventing independent locking or direct querying of a vet's booked schedule.
A6. VetRepository annotates vet lookups with @Cacheable("vets"), which risks serving stale availability data if appointment booking logic is coupled to cached vet entity state.
A7. The application maintains separate DDL scripts for H2, MySQL, and PostgreSQL without a database migration tool (such as Flyway or Liquibase), making simultaneous additions of foreign keys and unique constraints prone to dialect drift and CI test failures.
A8. Unlike PetController, VisitController does not catch DataIntegrityViolationException, meaning any database-level unique constraint violation triggered by a booking collision will bubble up to CrashController and show a 500 error page instead of a form validation message.
A9. VisitController explicitly configures dataBinder.setDisallowedFields("id", ".id"), which will silently drop incoming vet identifiers during form submission unless binder rules are updated carefully to avoid mass assignment risks.
A10. I18nPropertiesSyncTest fails the build if new template text or message keys are added without synchronizing all ten localized messages.properties files, making UI additions for vet and slot selection a failure point for automated verification.
B1. Missing Vet Availability Model – The current domain lacks an entity representing a vet’s schedule; adding booking will require new tables and relationships, risking mismatches with existing JPA mappings and migrations.
B2. Race Conditions on Concurrent Requests – VisitController.processNewVisitForm saves the owner with a new visit without transactional locking, so parallel bookings could create duplicate appointments for the same vet time slot.
B3. Insufficient Validation of Overlap – No existing service checks for overlapping visits per vet; a naïve date‑time comparison could miss edge cases (e.g., time‑zone differences or appointments spanning midnight).
B4. Database Transaction Isolation – The default save on OwnerRepository uses a simple EntityManager persist; without explicit @Transactional and appropriate isolation level, duplicate rows may be committed under high load.
B5. UI and Form Integration Risks – The HTML templates (createOrUpdateVisitForm.html) only capture pet‑visit data; extending them to include vet selection may break existing form bindings or introduce client‑side validation gaps.
B6. Security/Authorization Gaps – The application currently has no authentication layer around visit creation; exposing an online booking endpoint could allow unauthenticated users to create or modify appointments.
B7. Impact on Existing Tests – Numerous integration tests (e.g., VisitControllerTests, PetClinicConcurrencyTests) assume visits are created without vet constraints; the new logic will likely cause them to fail unless updated.
B8. Performance of Availability Queries – Retrieving a vet’s free slots will add database joins on visits and possibly vetspecialties; without pagination or caching, page‑load times could degrade.
B9. Data Migration Complexity – Introducing a new appointment table and foreign keys will require schema migration scripts (schema.sql); errors here could break the H2, MySQL, and PostgreSQL in‑memory databases used for testing.
B10. Time‑Zone Handling – The Visit entity stores a LocalDate only; adding time‑of‑day for bookings will need LocalDateTime or ZonedDateTime, and failure to handle zones could produce incorrect double‑booking detection.
B11. Potential Duplicate Business Logic – Existing VetController lists vets but does not expose scheduling; duplicating scheduling logic across controllers could lead to inconsistent rules.
B12. Rollback and Compensation – If a booking fails after the owner is saved, there is no compensating transaction to revert the partially persisted visit, risking orphaned records.
C1. Visit and the visits table in the H2, MySQL, and Postgres schemas store only petid, visitdate (LocalDate), and description. There is no vet and no time of day, so "the same time" cannot be enforced until a slot (start plus duration, or a discrete slot) is defined and added to all three schemas and their data.sql files.
C2. Visits are not an aggregate root: Pet.visits is an eager CascadeType.ALL collection saved only by OwnerRepository.save, and there is no VisitRepository or @Version. Two owners booking one vet are two separate owner saves, so a check-then-insert in VisitController races under read committed. Only a database unique key that spans owners closes it, the same way uniqueownerpetname closed the pet-name race in PetClinicConcurrencyTests.
C3. VisitController.processNewVisitForm never catches DataIntegrityViolationException. Copying PetController.isDuplicatePetNameViolation, which looks for the text uniqueownerpetname, will miss MySQL, whose pet unique key is an unnamed UNIQUE (ownerid, name), and will turn a real slot collision into the generic error page.
C4. ddl-auto=none and there is no Flyway or Liquibase. MySQL and Postgres schema.sql use CREATE TABLE IF NOT EXISTS, so an existing docker-compose volume or the Kubernetes demo-db database will not gain a vetid column or a unique index, while H2 drops and recreates its tables and the tests can pass against a rule production never has.
C5. Seed visits are inserted without a vet (positional INSERTs in H2, WHERE NOT EXISTS in Postgres). A NOT NULL vetid breaks startup on every database. A nullable vetid lets Postgres treat nulls as distinct, so a booking that omits the vet bypasses the unique slot, and there is no cancel or reschedule path to free a slot once it is taken.
C6. Nothing authenticates the caller. Owner is a public clinic record, not a login, and POST /owners/{ownerId}/pets/{petId}/visits/new has no Spring Security and no CSRF protection. Anyone who knows the ids can book that pet or fill a vet's calendar, and setDisallowedFields only blocks id, so a new vet field is mass-assignable.
C7. VetRepository is read-only, and both findAll() and findAll(Pageable) share the local Caffeine cache named vets. The vet HTML list is paged at 5, and selectField.html binds th:value="${item}" as text the way pet types do, which will not bind a Vet id. The availability read from that per-pod cache goes stale as soon as k8s/petclinic.yml runs more than one replica.
C8. Visit() defaults to tomorrow, and the controller rejects any date that is not after LocalDate.now() in the JVM zone, with no hours, duration, or timezone set on the Kubernetes container. A unique key on the date alone blocks the whole day. Different start times on that day still double-book the vet, and "today" shifts if the pod runs in UTC.
C9. VisitControllerTests is a @WebMvcTest with OwnerRepository mocked, so it never touches a constraint. The only concurrency test books duplicate pet names on H2. The Postgres profile used in Kubernetes, the MySQL Testcontainers tests, and src/test/jmeter/petclinictestplan.jmx will not show two concurrent bookings of one vet. I18nPropertiesSyncTest will fail if the conflict text is hardcoded instead of added to all eleven message bundles.
