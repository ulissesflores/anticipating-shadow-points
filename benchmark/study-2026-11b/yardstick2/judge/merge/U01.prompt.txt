Three reviewers independently listed ways a software change could go wrong.

Change request: Require new users to verify their email address before they can log in.

Items (the letter is the reviewer):
A1. The User model in prisma/schema.prisma currently lacks an email verification field, meaning adding an unverified check to verifyLogin without a backfill migration will immediately lock out existing users and break prisma/seed.ts (e.g., rachel@remix.run).
A2. app/routes/join.tsx currently calls createUserSession to issue a session cookie immediately upon registration, requiring a significant architectural change to withhold authentication until confirmation without leaving the user flow broken.
A3. Automated Cypress tests (cypress/e2e/smoke.cy.ts) and test helpers (cypress/support/create-user.ts) rely on immediate user creation and login sessions, which will fail continuous integration pipelines unless tests and fixtures are adapted to mock or bypass verification.
A4. The application completely lacks an email delivery service, SMTP transport, and related configuration in package.json and .env.example, requiring net-new third-party infrastructure and credential management before verification messages can be sent.
A5. In server.ts, multi-region database replays via fly-replay are configured only for non-GET requests, meaning an email verification link visited via a standard GET request will fail when attempting to write verification status against a read-only database replica.
A6. Because User.email is enforced with a unique constraint in prisma/schema.prisma and join.tsx rejects existing emails, unverified registrations created maliciously or with typos will permanently block the legitimate owners from creating accounts unless an account cleanup or expiration process is implemented.
A7. Protected route guards getUser and requireUser in app/session.server.ts check only user existence by ID, which would allow unverified users with existing session cookies to continue accessing protected /notes routes.
A8. The development setup relies on MSW in mocks/index.js without any local email interception or mailbox testing tooling, creating developer friction and making local verification testing difficult.
A9. The codebase currently possesses no mechanism or schema for generating, hashing, expiring, and invalidating single-use tokens, risking vulnerabilities if verification tokens are stored insecurely or lack expiration limits.
A10. Informing users of unverified status in app/routes/login.tsx risks introducing account enumeration vulnerabilities if error handling distinguishes between non-existent accounts and unverified registered users.
B1. Database schema change – Adding an emailVerified column and related token tables requires a migration; if the migration fails or is applied inconsistently, existing user data could become corrupted or inaccessible.
B2. Login logic regression – Modifying login.tsx to reject unverified accounts may unintentionally block legitimate users (e.g., existing accounts without the new flag) and could introduce a silent failure path if the verification check is omitted or mis‑wired.
B3. Email verification token security – Storing or transmitting verification tokens must use cryptographically secure generation and expiration; weak tokens or long‑lived links could be guessed or abused to hijack accounts.
B4. Email delivery reliability – The new verification flow depends on external email delivery; bounced or delayed emails could lock users out, creating a denial‑of‑service risk and requiring robust retry/resend mechanisms.
B5. User experience & edge cases – New users who never receive the verification email or lose access to it need a safe “resend” or “change email” path; lacking this can lead to abandoned registrations and support overhead.
B6. Potential enumeration attacks – Exposing “account not verified” vs “invalid credentials” messages can allow attackers to discover which emails are registered; responses must be uniform to avoid leaking user existence.
B7. Impact on existing authentication flows – Password‑reset, account‑deletion, and OAuth‑based login may assume a verified email; introducing the flag without updating those flows could cause inconsistent states or security gaps.
B8. Compliance and data privacy – Storing verification timestamps and tokens introduces personal data that may be subject to GDPR/CCPA; appropriate retention, deletion, and audit logging must be ensured to avoid regulatory violations.
C1. join.tsx calls createUserSession immediately after createUser, and requireUserId (used by notes.tsx) treats any session userId as logged in. A check added only in verifyLogin still lets a new account open /notes before the address is confirmed, and the login loader redirects away whenever that cookie is already set.
C2. This app cannot send mail. package.json has no mail client, mocks/index.js only passes through /ping with MSW onUnhandledRequest: "bypass", and the Fly config documents SESSIONSECRET but no mail secret or public origin. npm run validate boots through start:mocks, so a real provider call either escapes CI or fails with no captured message.
C3. User has no verified flag, token, or expiry, and both the Fly releasecommand and npm run setup run prisma migrate deploy before prisma/seed.ts creates rachel@remix.run with only email and password. A required column with no default breaks that seed, while @default(false) migrates cleanly, does not trip autorollback, and locks the seed user plus every existing row, with no admin screen to mark them verified.
C4. getUser destroys the cookie only when the user row is missing, and "Remember me" sets session maxAge to 7 days. Enforcing verification there also rejects the cookie from cypress/support/create-user.ts, which never calls verifyLogin. Leaving the check only on the login action keeps every session that signup already issued.
C5. User.email is a case-sensitive unique column, and a duplicate signup returns "A user already exists with this email". If the message never arrives, that address stays reserved: login has no resend, deleteUserByEmail is only used by Cypress, and nothing expires unverified rows, so a signup can squat an inbox the real owner can no longer register.
C6. Login currently returns one string, "Invalid email or password", for both a missing user and a bad password. A separate "verify your email" response after bcrypt.compare succeeds tells the caller that the address is registered and that the password was correct. validateEmail only requires length greater than 3 and an @, and the value is stored unchanged, so Rachel@Remix.run and rachel@remix.run are different users and a token lookup can miss.
C7. getUser returns the whole Prisma User, and the root loader puts that object in the document JSON on every page. A token column on User is therefore sent to the browser. morgan("tiny") in server.ts logs the request URL, so a token in the query string is written to the Fly logs, and the trailing-slash middleware 301s while keeping that query string.
C8. Outside PRIMARYREGION, app/db.server.ts points Prisma at port 5433, and server.ts replays only non-GET methods to the primary. A verification link that writes from a loader will try to mark the user verified on a read replica and fail in every secondary region.
C9. cypress/e2e/smoke.cy.ts submits "Create Account" and then follows "View Notes for {email}" in the same session, which only renders when useOptionalUser is set. cy.login() depends on create-user.ts inserting a user and a session cookie. Both assume createUser already grants access to notes, and that is what npm run validate runs.
C10. fly.toml publishes the app on internal port 8080 behind forcehttps and sets no public base URL, and Express never enables trust proxy. A link built from request.url can point at the internal port or at plain http, so the message confirms an address the recipient cannot open.
