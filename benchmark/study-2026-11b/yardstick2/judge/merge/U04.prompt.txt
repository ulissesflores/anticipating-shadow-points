Three reviewers independently listed ways a software change could go wrong.

Change request: Lock users out by username and IP address together instead of by IP address alone, as the new default.

Items (the letter is the reviewer):
A1. Under the current ["ipaddress"] default, an IP attempting passwords against multiple accounts is blocked after AXESFAILURELIMIT attempts, but switching to [["username", "ipaddress"]] enables attackers to execute horizontal password spraying across unlimited usernames from a single IP without triggering lockout.
A2. In axes.helpers.makecachekeylist, cache keys are generated by concatenating parameter values without a delimiter via "".join(...), causing hash collisions in AxesCacheHandler between distinct username and IP combinations (such as username "admin1" with IP "0.0.0.1" versus "admin" with IP "10.0.0.1").
A3. In AxesCacheHandler.resetattempts, cache keys are computed only from the provided arguments, meaning management commands axesresetip and axesresetusername will silently fail to clear lockout keys because neither passes both username and IP together.
A4. In AxesDatabaseHandler.userloginfailed, the guard to avoid creating records when username is None strictly checks lockoutparameters == ["username"]; under [["username", "ipaddress"]], requests missing a username will record username=None attempts in the database that will not protect actual accounts.
A5. In AccessAttempt, queries filter on exact username matches without normalization, which allows attackers to bypass lockout thresholds against case-insensitive authentication backends (such as email-based logins) by varying character casing unless AXESUSERNAMECALLABLE is configured.
A6. Existing integration tests in tests/testlogin.py (including testlockoutbyipblockswhendiffusersameipwithoutcache and its cached equivalent) explicitly assert default lockout by IP across different usernames, causing multiple test suite failures without a major test overhaul.
A7. AccessAttempt defines a unique constraint on (username, ipaddress, useragent) and individual indexes on username and ipaddress, but lacks a composite index on (username, ipaddress); making this pair the default query pattern will increase row volume and could degrade query performance during getfailures.
A8. The public utility function axes.utils.resetrequest inspects request.GET.get("username") to satisfy usernamerequired, which fails to extract usernames from POST request bodies or custom form fields when handling reset requests under the new default.
A9. When AXESRESETONSUCCESS is enabled, a successful login previously cleared all failure records for the originating IP, but under the new default, resetuserattempts will only clear records matching that specific username and IP combination.
A10. In axes/admin.py, IsLockedOutFilter and status evaluate lockout thresholds against an individual AccessAttempt row's failuressincestart rather than aggregating failures across rotating user agents for a (username, IP) pair as getfailures does, causing false negative lockout displays in the admin.
B1. Migration complexity and data integrity – Changing the uniquetogether constraint to include username means a new migration must enforce uniqueness across three fields. Existing rows with null usernames or duplicate IP‑only entries could cause migration failures or silent data loss if not cleaned beforehand.
B2. Breakage of existing queries and reports – Many parts of the codebase (e.g., admin list filters, custom ORM queries, analytics dashboards) assume lockouts are keyed solely by IP. Adding username will alter query semantics and may return empty results or duplicate rows unless all callers are updated.
B3. Performance overhead – The AccessAttempt table is indexed on ipaddress and username separately, but the new composite unique index adds an additional index lookup on three columns for every login attempt, potentially increasing DB load under high traffic.
B4. Inconsistent lockout behavior for shared IPs – Users behind NAT or corporate proxies share an IP address. With the new default, a malicious actor could lock out a specific username only from that IP, but legitimate users from the same IP using other usernames remain unaffected, which may be unexpected for teams relying on IP‑wide lockout as a DoS mitigation.
B5. Compatibility with reverse‑proxy IP extraction – Axes relies on django-ipware to resolve the client IP. If the proxy count (AXESIPWAREPROXYCOUNT) is mis‑configured, the wrong IP may be stored, breaking the new combined lockout rule and causing false positives/negatives.
B6. Impact on existing tests – The test suite expects lockouts to trigger on IP alone (see tests/testlogin.py). Updating the default will cause those tests to fail and require extensive fixture changes to include usernames in mock requests.
B7. Potential for accidental lockouts due to missing usernames – When username is None (e.g., anonymous login attempts), the composite uniqueness check may treat all such attempts as a single entity, leading to a single IP locking out all anonymous users.
B8. Admin UI and audit log confusion – The admin listfilter currently displays lockedout and attempttime but not the new composite key. Administrators may find it harder to trace which username/IP combination caused a lockout without UI enhancements.
B9. Backward‑compatibility for existing deployments – Projects that have customized AXESLOCKOUTPARAMETERS to lock out by IP only will need to merge the new default or explicitly override it, otherwise they may unintentionally inherit the stricter rule and experience unexpected lockouts.
B10. Risk of race conditions during concurrent login attempts – With three fields in the uniqueness constraint, two rapid login failures for the same username from the same IP could trigger a IntegrityError if the database does not handle the composite index atomically, potentially crashing the authentication flow.
B11. Data migration downtime – Adding the composite unique constraint may require a table lock on axesaccessattempt during migration, leading to temporary unavailability of login endpoints for large datasets.
B12. Documentation drift – The project’s ADRs, changelog, and README currently describe IP‑only lockouts. Updating the default without synchronizing these artifacts will create misinformation for future developers and operators.
C1. AXESLOCKOUTPARAMETERS already has two different shapes, and this request fits only the nested one. [["username", "ipaddress"]] (the old AXESLOCKOUTBYCOMBINATIONUSERANDIP branch in axes/conf.py) locks that pair, while the flat ["username", "ipaddress"] is an OR: getfailures takes the max of the separate filters, so one address locks every username from it and one username is locked from every address. The flat form also makes AxesCacheHandler.resetattempts raise NotImplementedError when resetrequest sets iporusername=True.
C2. A pair filter makes AxesDatabaseHandler.getfailures sum failuressincestart only for rows that match both username and IP. A guess that changes the username, or the IP, never reaches the default AXESFAILURELIMIT of 3, and axeslockoutparamscheck (axes.W006) stays quiet because ipaddress is still in the list.
C3. getclientusername keeps the raw posted string, truncated to 255, with no case folding and no check that the user exists. Admin, admin, and a random name are separate counters. AxesTestCase.login already posts a new random username on every failure, and those attempts only add up today because the default filter ignores the username. checkhandler and lockout() depend on that.
C4. Both handlers skip writing a failure only when lockoutparameters == ["username"]. A nested pair does not match, so a missing name is stored as NULL and later filtered with username IS NULL. makecachekeylist drops that falsy value and hashes the IP alone, which is the same key the current IP-only default already wrote, so the cache handler and the database handler lock different requests.
C5. Cache keys are the SHA-256 of the parameter values joined with no separator. With a pair default, ("admin", "1.2.3.4") and ("admin1.2.3", ".4") share one AxesCacheHandler counter and stay different AccessAttempt rows.
C6. Sites that never set AXESLOCKOUTPARAMETERS receive ["ipaddress"] from the fallback in axes/conf.py. Changing that fallback does not trip axesdeprecationcheck, which warns only when a deprecated flag is present, and it reinterprets existing rows: an address that is locked only because several usernames were summed together falls under the limit on the next request, with no data migration.
C7. That same fallback still rewrites the list when AXESUSEUSERAGENT or the deprecated lockout flags are set. Setting the new default on the getattr before that branch drops AXESONLYUSERFAILURES, AXESLOCKOUTBYUSERORIP, and AXESLOCKOUTBYCOMBINATIONUSERANDIP. AXESUSEUSERAGENT=True would append useragent onto the inner list, producing [["username", "ipaddress", "useragent"]] where the upgrade notes in docs/2installation.rst document [["ipaddress", "useragent"]].
C8. axes.utils.reset(ip=...), axesresetip, and resetrequest with only REMOTEADDR delete every database attempt for that IP, because AxesDatabaseHandler.resetattempts applies the username filter only when a username was passed (tests/testattempts.py expects the count to drop from 5 to 3). The cache handler builds its key from username=None and leaves the pair keys that login wrote in place. One unlock path clears every account on the address, and the other clears none.
C9. IsLockedOutFilter marks a row locked only when that row's own failuressincestart reaches AXESFAILURELIMIT. Rows are unique on (username, ipaddress, useragent), and the lock decision sums across user agents, so a locked pair can show as open in the admin.
C10. The published default becomes false in the same change. docs/4configuration.rst still says the default is ["ipaddress"] and "only use IP address", and docs/2installation.rst tells existing installs to set ["ipaddress"] to keep current behavior. userlockedout still carries only username and ipaddress, so a receiver that bans the IP bans an address Axes would still allow for every other username.
