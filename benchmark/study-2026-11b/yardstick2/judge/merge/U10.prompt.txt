Three reviewers independently listed ways a software change could go wrong.

Change request: Make every to-do list and item belong to a tenant, so that each company only sees its own data.

Items (the letter is the reviewer):
A1. Because authentication uses ASP.NET Core's built-in MapIdentityApi<ApplicationUser>() and CurrentUser only exposes Id and Roles, there is currently no tenant concept in the identity model or token claims. Without defining how tenants are registered, stored, and resolved per request, the application cannot securely authenticate a tenant context.
A2. Handlers such as GetTodosQueryHandler query context.TodoLists directly across the entire database without tenant scoping. If tenant filtering is implemented ad hoc in individual queries rather than centrally via EF Core Global Query Filters in ApplicationDbContext, future queries or navigation property traversals are prone to cross-tenant data leaks.
A3. CreateTodoItemCommand and UpdateTodoItemDetailCommand accept an arbitrary ListId without verifying that the target TodoList belongs to the current tenant, allowing users to insert items into or reparent items into another company's list. Furthermore, commands using FindAsync([request.Id]) will permit cross-tenant mutations or deletions if tenant ownership checks are omitted.
A4. CreateTodoListCommandValidator and UpdateTodoListCommandValidator enforce unique titles across the entire TodoLists table using context.TodoLists.AnyAsync. Without scoping this check to the current tenant, companies will encounter collisions on common list titles like "Work" or "Personal", while validation errors could leak the existence of other tenants' lists.
A5. If TenantId is stored on both TodoList and TodoItem, the database risks data inconsistency where an item's tenant differs from its parent list unless composite foreign keys or domain invariants are enforced. Conversely, if TodoItem omits TenantId and relies solely on TodoList, item-level lookups in UpdateTodoItem and DeleteTodoItem will require extra joins to verify tenant boundaries.
A6. If tenant assignment relies on incoming request payloads rather than being established server-side from authenticated claims, clients could forge a foreign TenantId and create resources in other companies. Tenant assignment must be enforced systematically across entities, such as through an interceptor alongside AuditableEntityInterceptor.
A7. ApplicationDbContextInitialiser uses EnsureCreatedAsync() rather than EF Core migrations and seeds hardcoded default users and todo lists without any tenant association. Introducing a required TenantId will break database initialisation, corrupt seed workflows, and fail on existing databases unless a migration and data backfill strategy is planned.
A8. The test infrastructure in Application.FunctionalTests (WebApiFactory, TestApp, and DatabaseResetter) mocks IUser without tenant context and executes against a shared, unpartitioned database state. Introducing tenant requirements will break existing functional test runs and give a false sense of security unless multi-tenant test fixtures and cross-tenant boundary assertions are created.
A9. The frontend Angular and React applications rely on generated API clients via NSwag (nswag.json). If tenant context alters API route parameters, registration contracts, or request payloads instead of being handled transparently via authentication claims or session headers, the generated client and UI components will experience breaking changes across the board.
B1. Database schema breakage – Adding a TenantId column to TodoItem.cs and TodoList.cs (and related EF configurations) will require migration scripts; existing data and tests that assume no tenant field may fail.
B2. Query leakage – Current queries (e.g., src/Application/TodoLists/Queries/GetTodos/GetTodos.cs) do not filter by tenant, so without adding tenant predicates every tenant could see other companies’ todo data.
B3. Command authorization gaps – Commands such as CreateTodoItem, UpdateTodoItem, and DeleteTodoList (in src/Application/TodoItems/Commands/ and src/Application/TodoLists/Commands/) lack explicit tenant ownership checks; a malicious user could modify another tenant’s records.
B4. Missing tenant propagation – The IUser interface (src/Application/Common/Interfaces/IUser.cs) provides user information but no tenant info, so services like CurrentUser (src/Web/Services/CurrentUser.cs) must be extended; otherwise tenant context will be null, causing runtime errors.
B5. EF Core configuration oversights – The entity configurations (src/Infrastructure/Data/Configurations/TodoItemConfiguration.cs and TodoListConfiguration.cs) need global query filters for TenantId; forgetting this will leave the database unprotected.
B6. Cascade delete side effects – Introducing tenant‑scoped foreign keys may trigger cascade deletes across tenants if not configured with OnDelete restrictions, risking data loss when a tenant is removed.
B7. Testing suite mismatches – Unit and functional tests (e.g., tests/Application.FunctionalTests/TodoLists/Commands/CreateTodoListTests.cs) assume a single‑tenant model; they will break unless tenant setup is added to test fixtures.
B8. Performance regression – Adding a tenant filter to every query can affect query plans; without proper indexing on TenantId, the TodoItems and TodoLists tables may experience latency spikes under multi‑tenant load.
B9. API contract changes – Controllers/endpoint definitions (src/Web/Endpoints/TodoLists.cs) currently return DTOs without tenant fields; exposing or omitting them inconsistently will break client contracts and Swagger documentation.
B10. Security rule enforcement – The AuthorizationBehaviour (src/Application/Common/Behaviours/AuthorizationBehaviour.cs) only checks roles; it must also enforce tenant isolation, otherwise role‑based access may inadvertently grant cross‑tenant visibility.
B11. Data migration complexity – Existing production data must be backfilled with correct TenantId values; an incomplete migration could leave orphaned records accessible to the wrong tenant.
B12. Caching and concurrency hazards – Any in‑memory caches (e.g., MediatR pipelines) that store todo data without tenant keys could serve stale data to the wrong tenant after the change.
C1. ApplicationUser is an empty IdentityUser, IUser and CurrentUser carry only the user id and role claims, and IdentityService.CreateUserAsync plus MapIdentityApi<ApplicationUser>() never assign a company. The seeded administrator@localhost and the global Roles.Administrator are the same, so a tenant id has no server-side source, and putting it on a command record would let the caller choose it because the todo endpoints bind those records from the body.
C2. GetTodosQueryHandler is the only read and it projects every TodoList. UpdateTodoList, UpdateTodoItem, UpdateTodoItemDetail, and DeleteTodoItem load with FindAsync on the integer id, DeleteTodoList matches only Id, and CreateTodoItem writes request.ListId without loading the list. UpdateTodoItemDetail then copies that ListId onto the item, and the foreign key is only ListId, so an item can be hung on another company's list; create returns that same database-wide id.
C3. [Authorize] sits only on GetTodosQuery. The other todo commands have no attribute, and AuthorizationBehaviour only checks that IUser.Id is set and that a role or named policy matches; IIdentityService.AuthorizeAsync never receives the list or item id. RequireAuthorization() on the TodoLists and TodoItems groups lets any authenticated account through.
C4. A query filter does not fit the mapping that exists today. OnModelCreating only runs ApplyConfigurationsFromAssembly, and TodoListConfiguration and TodoItemConfiguration are parameterless, so they cannot see a per-request tenant; a value captured while the model is built is shared by every request. TodoItem.List is required, so a filter on the list alone makes EF inner-join and drop items whose list is hidden, while FindAsync in the four update/delete handlers and in TestApp.FindAsync still resolves the integer key.
C5. CreateTodoListCommandValidator and UpdateTodoListCommandValidator reject a title when any TodoList already has it, so one company can learn that another company used that name. TodoListConfiguration has no unique index: an index on Title alone collides with the seeded "Tasks" list and with two companies using the same title, and a LINQ check with no (TenantId, Title) constraint stays racy once a filter hides the other company's rows.
C6. AuditableEntityInterceptor stamps CreatedBy from IUser.Id and does not stamp a company. TrySeedAsync inserts the "Tasks" list and its four items with no owner, and TestApp.AddAsync inserts straight into ApplicationDbContext, so both paths skip the handlers. A required tenant column fails that seed; a null tenant is either invisible or visible to every company. Development startup only does EnsureDeleted/EnsureCreated, there is no migration, and the PostgreSQL and SQL Server AppHost databases use a persistent container, so an existing database will not grow the column.
C7. The tests describe one shared database. WebApiFactory replaces IUser with a mock of Id and Roles only, TestApp keeps a single static user, GetTodosTests.ShouldReturnAllListsAndItems expects every inserted list, and DeleteTodoListTests creates a list with no signed-in user. After a filter is added, TestApp.FindAsync and CountAsync run with an empty tenant, so a hidden row and a deleted row look the same, and Respawn does not create a second company.
C8. Both ClientApp and ClientApp-React already post UpdateTodoItemDetailCommand with a new listId when the item-details dialog moves an item. Treating every list change as illegal breaks that flow; accepting the id without proving the destination list is in the same company keeps the cross-tenant write that TodoItems.UpdateTodoItemDetail already exposes.
