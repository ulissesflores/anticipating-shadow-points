Three reviewers independently listed ways a software change could go wrong.

Change request: Replace the integer IDs that the API exposes with UUIDs, while keeping existing API clients working.

Items (the letter is the reviewer):
A1. In app/api/summaries.py, the readsummary, updatesummary, and deletesummary endpoints strictly enforce id: int = Path(..., gt=0). Replacing this parameter type with UUID will immediately reject existing clients' integer requests with 422 Unprocessable Entity unless the routes accept a union type or custom path converter.
A2. In app/models/pydantic.py, SummaryResponseSchema defines id: int, and app/models/tortoise.py generates SummarySchema dynamically via pydanticmodelcreator(TextSummary). Replacing id with a UUID string in API responses will break JSON deserialization and schema validation in existing clients that expect an integer.
A3. The TextSummary model in app/models/tortoise.py relies on Tortoise's default auto-incrementing serial primary key defined in migration 020250421234125init.py. Altering the primary key column to a UUID in PostgreSQL using Aerich risks table locks, migration failure, and data loss unless legacy integer IDs are preserved alongside a new UUID column.
A4. In app/api/crud.py, query methods filter records directly using TextSummary.filter(id=id). Querying an integer column with a UUID string or querying a PostgreSQL UUID column with an integer through asyncpg will raise an unhandled DataError, resulting in 500 Internal Server Errors instead of 404 responses.
A5. In app/summarizer.py, generatesummary(summaryid: int, url: str) expects an integer and queries TextSummary.filter(id=summaryid) as an asynchronous task scheduled by BackgroundTasks in createsummary. Changing the exposed ID to UUID without coordinating this background task's signature and query logic will cause asynchronous summarization jobs to fail.
A6. Maintaining backward compatibility requires app/api/crud.py to support dual lookups by either legacy integer ID or UUID. Introducing a secondary UUID column without an enforced unique constraint and index will lead to slow full table scans and could allow duplicate UUID assignments.
A7. The readallsummaries endpoint in app/api/crud.py uses TextSummary.all().values(), which defaults to PostgreSQL's natural primary key order. Shifting the exposed identifier to non-sequential UUIDs without adding an explicit orderby("createdat") clause risks disrupting the expected listing order for existing clients.
A8. The test suites in tests/testsummaries.py and tests/testsummariesunit.py heavily assert integer IDs, mock integer returns from crud, and test boundary validation such as id=0 expecting gt: 0 error details. Changing route types and payload schemas will break existing unit and integration tests unless the test suite is refactored to verify both legacy integer and UUID client paths.
A9. The release script in release.sh deploys Docker containers directly to Heroku without a zero-downtime migration strategy. If the database migration alters or drops the integer primary key while old container instances are running, in-flight client requests will fail due to schema mismatches.
B1. Database schema migration – Tortoise’s default primary key is an integer; switching to a UUID column requires a migration that adds a new uuid field, back‑fills existing rows, and updates all foreign‑key constraints, which can be error‑prone and may lock the tables during the change.
B2. Data loss during back‑fill – Converting existing integer IDs to UUIDs (or generating new UUIDs) risks orphaned records if the migration does not correctly map old IDs to new ones across all tables and relationships.
B3. Performance impact – UUID primary keys are larger (16 bytes) and less cache‑friendly than 4‑byte integers, potentially degrading query performance and index size for the TextSummary table and any future joins.
B4. API contract breakage – The OpenAPI schema, Pydantic models (SummaryResponseSchema.id: int), and route definitions (Path(..., gt=0)) all assume an integer; changing the type to UUID will cause validation errors for existing clients unless the response schema is versioned or both types are supported.
B5. Test suite failures – Unit and integration tests (testsummaries.py, testsummariesunit.py) currently assert integer IDs; they will fail unless the tests are updated to generate and compare UUIDs.
B6. External client compatibility – Any downstream services, scripts, or SDKs that parse the id field as an integer (e.g., for sorting, pagination, or constructing URLs) will break unless they are updated to handle UUID strings.
B7. URL routing and path validation – FastAPI routes use /{id}/ with int path parameters; replacing with UUID strings requires updating the path converters and validation (Path(..., gt=0) will no longer be appropriate).
B8. Cache key collisions – In‑memory caches or Redis keys that embed the integer ID (e.g., summary:{id}) will need to be refactored to accommodate the longer UUID strings, otherwise cached lookups may miss or collide.
B9. Backward‑compatibility strategy – Providing a migration path that preserves the old integer ID for existing clients (e.g., dual‑field response or header) adds complexity and must be carefully designed to avoid ambiguous identifiers.
C1. SummaryResponseSchema.id is typed as int, and SummarySchema is produced by pydanticmodelcreator(TextSummary), so the implicit integer primary key is the id on GET, PUT, POST, and DELETE. Replacing that field with a UUID string on the only router (/summaries, no version prefix) breaks clients that parse id as an integer unless the integer is still returned next to the UUID.
C2. readsummary, updatesummary, and deletesummary declare id: int = Path(..., gt=0), so a UUID in the path is rejected with 422 before crud runs. The tests lock the exact 422 body for /summaries/0/ (type: greaterthan, ctx.gt == 0) on GET, PUT, and DELETE, so a compatibility parser still has to accept existing positive integer paths and has to decide what happens to that error body.
C3. The only Aerich migration creates "id" SERIAL NOT NULL PRIMARY KEY1. SummaryResponseSchema.id is an int, and SummarySchema is generated by pydanticmodelcreator(TextSummary) from Tortoise's implicit integer primary key. POST /summaries/, GET /summaries/, GET/PUT/DELETE /summaries/{id}/ all publish that integer as id on one unversioned router, so swapping the field to a UUID string breaks clients that already parse id as an integer unless a second field or a second route is chosen first.
C4. readsummary, updatesummary, and deletesummary declare id: int = Path(..., gt=0). A UUID in the path is rejected with 422 before crud runs, and testsummaries.py locks the current body for /summaries/0/ (greaterthan, ctx.gt == 0) and requires /summaries/999/ to hit the database and return 404.
C5. project/migrations/models/020250421234125init.py creates textsummary.id as a SERIAL primary key, and its downgrade returns an empty string. initdb sets generateschemas=False, so production can change only through Aerich. Postgres will not turn that SERIAL column and textsummaryidseq into a UUID in place. Existing rows need a new UUID column and a backfill, and the aerich table's own SERIAL id has to stay out of that migration.
C6. webdev (DATABASEURL) is the database Aerich migrates. webtest is created in project/db/create.sql and rebuilt in testappwithdb by registertortoise(..., generateschemas=True) on DATABASETESTURL. That flag does not alter an existing SERIAL primary key and does not run the Aerich file. entrypoint.sh only waits for Postgres, and release.sh only patches the Heroku image, so the app can deploy while both databases are still on the init migration.
C7. createsummary passes the value from crud.post (summary.id after save()) into backgroundtasks.addtask(generatesummary, summaryid, ...). generatesummary is typed summaryid: int and updates TextSummary.filter(id=summaryid), and the insert stores summary="". A UUID primary key that is not written back onto the in-memory model, or a public id that is not the filter key, leaves the summary empty. Dockerfile.prod runs Gunicorn, so during the Heroku formation swap old workers can still be holding the integer.
C8. crud.get, put, and getall return QuerySet.values(), which includes every column. GET and PUT are shaped by SummarySchema. POST builds {"id": summaryid, "url": payload.url} by hand, and DELETE validates that dict against SummaryResponseSchema (id and url only). A second identifier column will surface in one of these responses and be dropped or rejected in the others unless the mapping is explicit in all four.
C9. Integer paths stay an enumeration oracle: /summaries/999/ is a legal request and 404s only after the lookup. Keeping stored integer ids working leaves that lookup available. One path parameter has to treat "1" as the legacy key and a UUID string as the new key. The current int converter rejects the UUID before any lookup.
C10. TextSummary.all().values() has no orderby. The SERIAL primary key currently lines up with insertion order. A random UUID primary key changes the order of GET /summaries/. createdat is stored and returned, and nothing in the list query sorts by it.
C11. testsummariesunit.py asserts the POST body is exactly {"id": 1, "url": "https://foo.bar/"} and calls /summaries/1/ and /summaries/999/. The integration tests only compare the id just returned with the path they call next. testappwithdb generates a fresh schema and never loads a pre-existing SERIAL row or the Aerich migration, so a green UUID-only suite would not show that an old integer still gets, updates, and deletes the same row.
