1. **Migration complexity and data integrity** – Changing the `unique_together` constraint to include `username` means a new migration must enforce uniqueness across three fields. Existing rows with `null` usernames or duplicate IP‑only entries could cause migration failures or silent data loss if not cleaned beforehand.  

2. **Breakage of existing queries and reports** – Many parts of the codebase (e.g., admin list filters, custom ORM queries, analytics dashboards) assume lockouts are keyed solely by IP. Adding `username` will alter query semantics and may return empty results or duplicate rows unless all callers are updated.  

3. **Performance overhead** – The `AccessAttempt` table is indexed on `ip_address` and `username` separately, but the new composite unique index adds an additional index lookup on three columns for every login attempt, potentially increasing DB load under high traffic.  

4. **Inconsistent lockout behavior for shared IPs** – Users behind NAT or corporate proxies share an IP address. With the new default, a malicious actor could lock out a *specific* username only from that IP, but legitimate users from the same IP using other usernames remain unaffected, which may be unexpected for teams relying on IP‑wide lockout as a DoS mitigation.  

5. **Compatibility with reverse‑proxy IP extraction** – Axes relies on `django-ipware` to resolve the client IP. If the proxy count (`AXES_IPWARE_PROXY_COUNT`) is mis‑configured, the wrong IP may be stored, breaking the new combined lockout rule and causing false positives/negatives.  

6. **Impact on existing tests** – The test suite expects lockouts to trigger on IP alone (see `tests/test_login.py`). Updating the default will cause those tests to fail and require extensive fixture changes to include usernames in mock requests.  

7. **Potential for accidental lockouts due to missing usernames** – When `username` is `None` (e.g., anonymous login attempts), the composite uniqueness check may treat all such attempts as a single entity, leading to a single IP locking out all anonymous users.  

8. **Admin UI and audit log confusion** – The admin `list_filter` currently displays `locked_out` and `attempt_time` but not the new composite key. Administrators may find it harder to trace which username/IP combination caused a lockout without UI enhancements.  

9. **Backward‑compatibility for existing deployments** – Projects that have customized `AXES_LOCKOUT_PARAMETERS` to lock out by IP only will need to merge the new default or explicitly override it, otherwise they may unintentionally inherit the stricter rule and experience unexpected lockouts.  

10. **Risk of race conditions during concurrent login attempts** – With three fields in the uniqueness constraint, two rapid login failures for the same username from the same IP could trigger a `IntegrityError` if the database does not handle the composite index atomically, potentially crashing the authentication flow.  

11. **Data migration downtime** – Adding the composite unique constraint may require a table lock on `axes_accessattempt` during migration, leading to temporary unavailability of login endpoints for large datasets.  

12. **Documentation drift** – The project’s ADRs, changelog, and README currently describe IP‑only lockouts. Updating the default without synchronizing these artifacts will create misinformation for future developers and operators.
