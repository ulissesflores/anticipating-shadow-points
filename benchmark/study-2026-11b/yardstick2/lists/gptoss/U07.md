1. **Database schema migration** – Tortoise’s default primary key is an integer; switching to a UUID column requires a migration that adds a new `uuid` field, back‑fills existing rows, and updates all foreign‑key constraints, which can be error‑prone and may lock the tables during the change.  

2. **Data loss during back‑fill** – Converting existing integer IDs to UUIDs (or generating new UUIDs) risks orphaned records if the migration does not correctly map old IDs to new ones across all tables and relationships.  

3. **Performance impact** – UUID primary keys are larger (16 bytes) and less cache‑friendly than 4‑byte integers, potentially degrading query performance and index size for the `TextSummary` table and any future joins.  

4. **API contract breakage** – The OpenAPI schema, Pydantic models (`SummaryResponseSchema.id: int`), and route definitions (`Path(..., gt=0)`) all assume an integer; changing the type to `UUID` will cause validation errors for existing clients unless the response schema is versioned or both types are supported.  

5. **Test suite failures** – Unit and integration tests (`test_summaries.py`, `test_summaries_unit.py`) currently assert integer IDs; they will fail unless the tests are updated to generate and compare UUIDs.  

6. **External client compatibility** – Any downstream services, scripts, or SDKs that parse the `id` field as an integer (e.g., for sorting, pagination, or constructing URLs) will break unless they are updated to handle UUID strings.  

7. **URL routing and path validation** – FastAPI routes use `/{id}/` with `int` path parameters; replacing with UUID strings requires updating the path converters and validation (`Path(..., gt=0)` will no longer be appropriate).  

8. **Cache key collisions** – In‑memory caches or Redis keys that embed the integer ID (e.g., `summary:{id}`) will need to be refactored to accommodate the longer UUID strings, otherwise cached lookups may miss or collide.  

9. **Backward‑compatibility strategy** – Providing a migration path that preserves the old integer ID for existing clients (e.g., dual‑field response or header) adds complexity and must be carefully designed to avoid ambiguous identifiers.
