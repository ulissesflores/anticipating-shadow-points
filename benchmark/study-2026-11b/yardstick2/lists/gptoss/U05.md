1. **Unintended session prolongation** – Enabling rolling for all requests will continuously extend the cookie’s expiry, preventing sessions from naturally timing out and potentially keeping stale authenticated sessions alive indefinitely.  

2. **Increased cookie traffic** – Every response will now set a `Set‑Cookie` header, adding overhead to network traffic and increasing the size of HTTP responses, which may affect performance on high‑traffic services.  

3. **Compatibility with `saveUninitialized: false`** – When `saveUninitialized` is false, rolling by default may cause cookies to be sent even though no session data has been persisted, breaking the intended “no‑session‑cookie‑until‑data‑saved” semantics.  

4. **Store‑specific side effects** – Custom session stores that rely on explicit `touch` calls (e.g., Redis with TTL updates) may receive unnecessary touch operations, leading to higher write load and potential race conditions in distributed environments.  

5. **Security exposure** – Continuously refreshed session IDs increase the window for session hijacking attacks, especially if secure cookie flags (`secure`, `httpOnly`, `sameSite`) are misconfigured elsewhere in the code.  

6. **Memory‑leak risk in `MemoryStore`** – The default in‑memory store will retain more active sessions because they never expire, potentially exhausting server memory in long‑running processes.  

7. **Breakage of tests expecting non‑rolling behavior** – The test suite contains explicit checks for `rolling: false` (e.g., in `test/session.js`); changing the default may cause those assertions to fail and hide regressions.  

8. **Interaction with `cookie.maxAge` reset** – The `Session.prototype.touch` method resets `maxAge` to `originalMaxAge`; with rolling always on, this reset may be invoked more frequently, potentially overriding custom per‑request max‑age adjustments.  

9. **Potential denial‑of‑service** – Malicious clients can keep a session alive indefinitely by making frequent requests, denying legitimate users the ability to obtain fresh sessions when the server enforces concurrent session limits.  

10. **Unexpected side effects for APIs** – Stateless API endpoints that rely on short‑lived sessions may unintentionally keep sessions alive, leading to stale authentication contexts and harder debugging of token expiration bugs.  

11. **Impact on load balancer sticky sessions** – If the application is deployed behind a load balancer using sticky sessions tied to cookie expiry, constantly rolling cookies can interfere with session affinity and cause uneven request distribution.  

12. **Compliance and audit concerns** – Certain regulatory regimes require session lifetimes to be bounded; default rolling could violate policies that mandate fixed session expiration windows.
