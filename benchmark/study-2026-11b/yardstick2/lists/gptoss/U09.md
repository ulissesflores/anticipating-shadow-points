1. **Legacy hash compatibility** – Existing users still have HMAC‑SHA‑512 hashes (64 bytes + 16 byte salt); switching to a stronger scheme must retain verification for these legacy hashes, otherwise logins will fail for all current accounts.  

2. **Database schema changes** – A stronger hash (e.g., Argon2id) will produce longer encoded strings; the `PasswordHash` column may need length adjustment, and any hard‑coded size checks in the code or migrations could cause truncation errors.  

3. **Re‑hash trigger logic** – The current `Verify` method returns `SuccessRehashNeeded` for legacy hashes; introducing a new scheme requires updating the login flow to automatically re‑hash the password on successful verification, which may be missed and leave old hashes unchanged.  

4. **Performance impact** – Increasing the work factor (e.g., higher iteration count or memory‑hard Argon2 parameters) can significantly raise CPU/memory usage during login, potentially causing time‑outs or degraded user experience under load.  

5. **Salt handling** – The existing implementation expects a separate `salt` byte array; a modern scheme often embeds the salt in the stored hash. Mismatched expectations may lead to null‑reference errors or incorrect verification if the API surfaces the salt incorrectly.  

6. **Testing coverage gaps** – The test suite only includes a `PasswordHashingTests` for the current logic; without new tests for the upgraded algorithm, regressions (e.g., failure to verify or re‑hash) may go undetected.  

7. **Dependency version lock** – The `PasswordHasher` relies on `Microsoft.AspNetCore.Identity` with a specific `IterationCount`; upgrading to a different algorithm may require adding a new NuGet package (e.g., `Isopoh.Cryptography.Argon2`) and updating the lock file, risking build failures if the package is not pinned.  

8. **Error handling and exception safety** – Converting the new hash to Base64 and storing it could throw `FormatException` or `OutOfMemoryException`; the current `Dispose` method does nothing, so any new resources (e.g., native libs) must be disposed to avoid leaks.  

9. **Migration strategy** – Performing an in‑place migration without forcing password resets demands a “lazy” re‑hash on next successful login; failing to implement this correctly could lock users out or leave a mixed‑state of hash versions that complicates future maintenance.  

10. **Security policy compliance** – The change must be reflected in ADRs, CHANGELOG, and any external security audit documentation; omission could result in non‑compliant releases and audit failures.  

11. **Concurrency race conditions** – If multiple login attempts trigger re‑hashing simultaneously, the user record could be updated concurrently, leading to lost updates or inconsistent `PasswordHash` values.  

12. **Impact on token generation** – The `JwtTokenGenerator` may embed password‑related claims or rely on hash verification timing; altering the hashing algorithm could affect token issuance latency or validation logic if not reviewed.
