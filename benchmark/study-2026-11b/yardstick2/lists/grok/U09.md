Vou ler o código de senha e autenticação deste repositório para listar os riscos reais da troca de hash sem reset.1. `PasswordHasher.Verify` picks the algorithm by shape: a 64-byte `Hash` with a 16-byte `Salt` is HMAC-SHA512 over `UTF-8(password) || salt` using the literal key `"realworld"`, and every other non-empty `Hash` is `Convert.ToBase64String`'d into Identity's PBKDF2 verifier at 210,000 iterations. A new encoding that is 64 bytes long, or that leaves `Salt` at 16 bytes, is checked as that HMAC; `LoginTests` already stores a current hash beside a 16-byte `Guid` salt because `Hash()` ignores the salt argument it is given.

2. Rows already written as Identity PBKDF2 (registration, password edit, and any login that took the `SuccessRehashNeeded` path) have to keep verifying after the change. `PasswordHashingTests` builds the HMAC fixture in memory and round-trips whatever `Hash()` emits now, so there is no pinned payload (format marker, PRF, iteration count 210000) of a hash already sitting in `Persons.Hash`.

3. `Create`, `Edit`, and the login upgrade all persist `Hash()` immediately, and the readme already says an older process cannot verify an upgraded password. A rolling deploy therefore locks a user out as soon as one new instance rehashes them on login, signup, or password change, and rolling the app back has the same result because the plaintext cannot be restored to the previous blob.

4. `Login` is not an `IReadOnlyRequest`, so `DBContextTransactionPipelineBehavior` holds the SQLite write transaction or the SQL Server connection across synchronous `Verify` and `Hash` (`Task.FromResult` around the KDF). Login rejects only an empty password, while create and edit only require 8 characters, so a higher work factor lets one oversized password stall writers, and the unknown-email path returns 401 before any hashing, which widens the timing gap between missing users, fast HMAC rows, and upgraded rows.

5. Accounts that never log in cannot be upgraded, because the plaintext exists only at login, so their HMAC under the hardcoded `"realworld"` key and their `Salt` stay offline-crackable for as long as reset is off the table. Removing the 64-byte branch or the `Salt` column locks those rows out; `docs/database-migrations.md` says neither password column changes, and both the SQLite `BLOB` and SQL Server `varbinary(max)` snapshots have to keep reading the old salt.

6. `Person` has no concurrency token, and the `SuccessRehashNeeded` branch in `Login` loads the row and later overwrites `Hash` and sets `Salt` to empty. A concurrent `Edit` that sets a new password, without checking the previous one, can be overwritten by an in-flight login that still holds the old password, and that write happens on every login if the new verifier keeps returning `SuccessRehashNeeded` after the row is already on the new scheme.

7. The salt contract is split across the interface and the column: `Hash(password, salt)` currently discards `salt` and Identity embeds its own, while HMAC verification requires `Person.Salt.Length == 16`, and `Create`, `Edit`, and `Login` each pass `[]` and clear `person.Salt` themselves. A replacement that consumes the argument, or that stops clearing `Salt`, either stores passwords that can never verify or recreates the 16-byte salt that selects the HMAC branch.

8. `Login` upgrades a row only when `Verify` returns `PasswordVerificationResult.SuccessRehashNeeded` and treats any other non-failure as success, so the new verifier has to map "recognized but weaker" onto that value and garbage onto `Failed`. Identity already runs PBKDF2 with the iteration count stored inside `Hash`; a scheme whose memory or time cost is also taken from the row will run those parameters inside the open transaction, and a throw from the parser becomes a 500 from `ErrorHandlingMiddleware` after rollback, so a correct password still fails the request.
