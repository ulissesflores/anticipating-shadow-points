POST `/summaries/`, GET `/summaries/`, GET/PUT/DELETE `/summaries/{id}/` all publish that integer as `id` on one unversioned router, so swapping the field to a UUID string breaks clients that already parse `id` as an integer unless a second field or a second route is chosen first.

2. `read_summary`, `update_summary`, and `delete_summary` declare `id: int = Path(..., gt=0)`. A UUID in the path is rejected with 422 before `crud` runs, and `test_summaries.py` locks the current body for `/summaries/0/` (`greater_than`, `ctx.gt == 0`) and requires `/summaries/999/` to hit the database and return 404.

3. `project/migrations/models/0_20250421234125_init.py` creates `textsummary.id` as a `SERIAL` primary key, and its `downgrade` returns an empty string. `init_db` sets `generate_schemas=False`, so production can change only through Aerich. Postgres will not turn that `SERIAL` column and `textsummary_id_seq` into a UUID in place. Existing rows need a new UUID column and a backfill, and the `aerich` table's own `SERIAL` id has to stay out of that migration.

4. `web_dev` (`DATABASE_URL`) is the database Aerich migrates. `web_test` is created in `project/db/create.sql` and rebuilt in `test_app_with_db` by `register_tortoise(..., generate_schemas=True)` on `DATABASE_TEST_URL`. That flag does not alter an existing `SERIAL` primary key and does not run the Aerich file. `entrypoint.sh` only waits for Postgres, and `release.sh` only patches the Heroku image, so the app can deploy while both databases are still on the init migration.

5. `create_summary` passes the value from `crud.post` (`summary.id` after `save()`) into `background_tasks.add_task(generate_summary, summary_id, ...)`. `generate_summary` is typed `summary_id: int` and updates `TextSummary.filter(id=summary_id)`, and the insert stores `summary=""`. A UUID primary key that is not written back onto the in-memory model, or a public id that is not the filter key, leaves the summary empty. `Dockerfile.prod` runs Gunicorn, so during the Heroku formation swap old workers can still be holding the integer.

6. `crud.get`, `put`, and `get_all` return `QuerySet.values()`, which includes every column. GET and PUT are shaped by `SummarySchema`. POST builds `{"id": summary_id, "url": payload.url}` by hand, and DELETE validates that dict against `SummaryResponseSchema` (`id` and `url` only). A second identifier column will surface in one of these responses and be dropped or rejected in the others unless the mapping is explicit in all four.

7. Integer paths stay an enumeration oracle: `/summaries/999/` is a legal request and 404s only after the lookup. Keeping stored integer ids working leaves that lookup available. One path parameter has to treat `"1"` as the legacy key and a UUID string as the new key. The current `int` converter rejects the UUID before any lookup.

8. `TextSummary.all().values()` has no `order_by`. The `SERIAL` primary key currently lines up with insertion order. A random UUID primary key changes the order of `GET /summaries/`. `created_at` is stored and returned, and nothing in the list query sorts by it.

9. `test_summaries_unit.py` asserts the POST body is exactly `{"id": 1, "url": "https://foo.bar/"}` and calls `/summaries/1/` and `/summaries/999/`. The integration tests only compare the `id` just returned with the path they call next. `test_app_with_db` generates a fresh schema and never loads a pre-existing `SERIAL` row or the Aerich migration, so a green UUID-only suite would not show that an old integer still gets, updates, and deletes the same row.
