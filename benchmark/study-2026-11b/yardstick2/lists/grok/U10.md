Vou ler o repositório para localizar como listas, itens e tenant estão modelados hoje, e só então listar os riscos específicos dessa mudança.O projeto é o template Clean Architecture. Vou ler entidades, consultas, autorização e testes para ver onde o isolamento por empresa ainda não existe.1. `ApplicationUser` is an empty `IdentityUser`, `IUser` and `CurrentUser` carry only the user id and role claims, and `IdentityService.CreateUserAsync` plus `MapIdentityApi<ApplicationUser>()` never assign a company. The seeded `administrator@localhost` and the global `Roles.Administrator` are the same, so a tenant id has no server-side source, and putting it on a command record would let the caller choose it because the todo endpoints bind those records from the body.

2. `GetTodosQueryHandler` is the only read and it projects every `TodoList`. `UpdateTodoList`, `UpdateTodoItem`, `UpdateTodoItemDetail`, and `DeleteTodoItem` load with `FindAsync` on the integer id, `DeleteTodoList` matches only `Id`, and `CreateTodoItem` writes `request.ListId` without loading the list. `UpdateTodoItemDetail` then copies that `ListId` onto the item, and the foreign key is only `ListId`, so an item can be hung on another company's list; create returns that same database-wide id.

3. `[Authorize]` sits only on `GetTodosQuery`. The other todo commands have no attribute, and `AuthorizationBehaviour` only checks that `IUser.Id` is set and that a role or named policy matches; `IIdentityService.AuthorizeAsync` never receives the list or item id. `RequireAuthorization()` on the `TodoLists` and `TodoItems` groups lets any authenticated account through.

4. A query filter does not fit the mapping that exists today. `OnModelCreating` only runs `ApplyConfigurationsFromAssembly`, and `TodoListConfiguration` and `TodoItemConfiguration` are parameterless, so they cannot see a per-request tenant; a value captured while the model is built is shared by every request. `TodoItem.List` is required, so a filter on the list alone makes EF inner-join and drop items whose list is hidden, while `FindAsync` in the four update/delete handlers and in `TestApp.FindAsync` still resolves the integer key.

5. `CreateTodoListCommandValidator` and `UpdateTodoListCommandValidator` reject a title when any `TodoList` already has it, so one company can learn that another company used that name. `TodoListConfiguration` has no unique index: an index on `Title` alone collides with the seeded "Tasks" list and with two companies using the same title, and a LINQ check with no `(TenantId, Title)` constraint stays racy once a filter hides the other company's rows.

6. `AuditableEntityInterceptor` stamps `CreatedBy` from `IUser.Id` and does not stamp a company. `TrySeedAsync` inserts the "Tasks" list and its four items with no owner, and `TestApp.AddAsync` inserts straight into `ApplicationDbContext`, so both paths skip the handlers. A required tenant column fails that seed; a null tenant is either invisible or visible to every company. Development startup only does `EnsureDeleted`/`EnsureCreated`, there is no migration, and the PostgreSQL and SQL Server AppHost databases use a persistent container, so an existing database will not grow the column.

7. The tests describe one shared database. `WebApiFactory` replaces `IUser` with a mock of `Id` and `Roles` only, `TestApp` keeps a single static user, `GetTodosTests.ShouldReturnAllListsAndItems` expects every inserted list, and `DeleteTodoListTests` creates a list with no signed-in user. After a filter is added, `TestApp.FindAsync` and `CountAsync` run with an empty tenant, so a hidden row and a deleted row look the same, and Respawn does not create a second company.

8. Both `ClientApp` and `ClientApp-React` already post `UpdateTodoItemDetailCommand` with a new `listId` when the item-details dialog moves an item. Treating every list change as illegal breaks that flow; accepting the id without proving the destination list is in the same company keeps the cross-tenant write that `TodoItems.UpdateTodoItemDetail` already exposes.
