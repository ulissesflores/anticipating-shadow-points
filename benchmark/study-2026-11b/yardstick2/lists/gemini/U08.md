1. Existing production tokens and signatures (such as session cookies or password reset links) signed under the current SHA-1 default will fail validation with `BadSignature`, reproducing the severe backward-incompatibility issue that led to yanking release 1.0.0.
2. Standalone `Signer` and `TimestampSigner` classes lack any fallback verification mechanism, meaning callers using them directly rather than through `Serializer` will immediately reject existing SHA-1 signatures unless custom multi-signer verification logic is manually added.
3. Because `Serializer.default_fallback_signers` currently defaults to an empty list, even `Serializer.loads()` will fail to validate existing SHA-1 tokens by default unless SHA-1 is explicitly added to `default_fallback_signers`.
4. In `Signer.derive_key()`, `digest_method` is used for key derivation across `concat`, `django-concat`, and `hmac` modes, meaning switching to SHA-256 changes both the derived signing key material and the signature, breaking external compatibility with systems expecting Django-compatible SHA-1 key derivation.
5. A SHA-256 HMAC digest produces 32 raw bytes (43 base64 characters) instead of SHA-1's 20 bytes (27 characters), increasing overall token length by 16 characters and risking payload overflow in size-constrained environments like HTTP cookie limits or compact URLs generated by `URLSafeSerializer`.
6. Class-level `default_digest_method` is declared independently on both `HMACAlgorithm` and `Signer` in `src/itsdangerous/signer.py`, creating a desynchronization risk if both attributes are not updated uniformly or if downstream subclasses override only one of them.
7. The lazy loading pattern implemented via `_lazy_sha1` to prevent import-time exceptions on FIPS-compliant systems must be evaluated for SHA-256, and any retained SHA-1 fallback must preserve lazy resolution so it does not trigger errors on FIPS builds where SHA-1 is disabled.
8. If SHA-1 is added as a default fallback signer to preserve backward compatibility, `Serializer.iter_unsigners()` will run multiple key derivations and HMAC comparisons on invalid or legacy tokens, doubling CPU overhead per failed verification and potentially introducing timing side-channels.
9. In distributed architectures and rolling deployments (such as multi-server Flask deployments), upgraded nodes will emit SHA-256 tokens that older nodes cannot parse, leading to session drops and authentication failures across the deployment window.
10. Existing unit tests in `tests/test_itsdangerous/test_serializer.py` assert explicit equality against SHA-1 output (including `test_digests` checking the hardcoded signature `[42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM` and `test_iter_unsigners` checking for `_lazy_sha1`), which will fail immediately without test updates.
11. Documentation throughout `docs/concepts.rst`, `docs/signer.rst`, and class docstrings explicitly details `hashlib.sha1` as the default, justifies its security properties in HMAC, and provides hardcoded SHA-1 examples that will become incorrect and misleading.
