1. In `index.js`, unmodified sessions rely on `store.touch()` rather than `store.save()`; if a session store does not implement `touch()`, the backend session TTL will not be extended, causing sessions to expire prematurely in the store while the client-side cookie continues to renew.
2. Enabling rolling by default causes `shouldSetCookie()` to return `true` on every request for an active session, injecting a `Set-Cookie` header on all responses and breaking downstream HTTP caching and CDN edge caching.
3. Because `store.touch()` is executed during `res.end()` on every request, rolling by default transforms all read-only HTTP traffic into write operations on the session store, risking severe I/O bottlenecks and connection pool exhaustion in external stores like Redis or MongoDB.
4. When a session is configured without a `maxAge` (a browser-session cookie where `expires` is `null`), `shouldSetCookie()` still evaluates to `true`, repeatedly sending redundant `Set-Cookie` headers on every response even though there is no cookie expiration to extend.
5. Because `express-session` only resets `cookie.maxAge` and lacks a built-in absolute expiration ceiling, rolling sessions by default allows sessions to remain active indefinitely through periodic background requests, significantly increasing the window of exposure for hijacked sessions.
6. Concurrent requests from the same user will trigger simultaneous invocations of `store.touch()` (or `store.save()`) and `res.setHeader('Set-Cookie', ...)`, creating race conditions, out-of-order cookie expirations, and potential session data overwrites.
7. In `index.js`, `res.end()` is monkey-patched to defer response completion until `store.touch()` finishes, meaning every HTTP response will incur the latency of an asynchronous session store roundtrip before completing.
8. When `resave` is `true` (or left undefined and defaulted to `true`), unmodified requests satisfy `shouldSave()` instead of `shouldTouch()`, triggering full session serialization and `store.set()` calls on every request rather than lightweight touches.
9. Numerous unit tests in `test/session.js` explicitly assert that `rolling` defaults to `false` and that unmodified requests do not send a `Set-Cookie` header via `shouldNotHaveHeader('Set-Cookie')`, causing immediate, widespread test suite failures.
10. Changing the default value of `opts.rolling` from `false` to `true` alters default HTTP header behavior and session lifecycles for all consumers, representing a breaking API change that requires a major version bump.
