1. `FindOneArticle(&ArticleModel{Slug: slug})` is hardcoded across all article endpoints (`ArticleRetrieve`, `ArticleFavorite`, `ArticleCommentCreate`, etc.) in `articles/routers.go` to query `ArticleModel` by `Slug` directly. Supporting historical slugs requires decoupling this lookup into an alias-aware resolution layer so that all handlers consistently locate the current article without breaking existing query signatures.
2. In `ArticleDelete` (`articles/routers.go`), the handler executes `DeleteArticleModel(&ArticleModel{Slug: slug})` using the raw URL parameter rather than the resolved article's primary key or current slug. If an article is accessed and deleted via a historical slug, GORM will attempt to delete a non-existent slug on `ArticleModel`, returning HTTP 204 while leaving the article intact in the database.
3. `makeUniqueSlug` in `articles/models.go` only counts collisions against `ArticleModel.Slug` and ignores historical slug aliases. A newly created or retitled article could claim an old slug that was previously shared, leading to routing ambiguity or hijacking existing links unless `makeUniqueSlug` and its retry loop validate against both current and historical slugs.
4. `ArticleUpdate` executes `articleModel.Update(updates)` without a database transaction and relies on an optimistic retry loop for unique index collisions. Updating the current slug on `ArticleModel` while simultaneously inserting or updating a historical alias record across multiple steps risks partial failures and database inconsistency during concurrent requests.
5. Endpoints such as `PUT /api/articles/:slug`, `POST /:slug/comments`, and `POST /:slug/favorite` share the same `/:slug` path parameter as retrieve operations. If historical slugs are allowed on mutation endpoints, users might modify articles under obsolete identities; if disallowed, interactive widgets on shared links may break with 404 errors.
6. An author may rename an article back to an earlier title or swap titles between multiple articles, creating circular references or duplicate key errors in the alias history. The design must explicitly define how historical aliases are pruned, reclaimed, or redirected when a slug reverts to its original owner.
7. `ArticleModel` embeds `gorm.Model` and uses soft deletes (`DeletedAt`), whereas historical slugs must be properly scoped to active articles. If an article is deleted, its slug history must either be soft-deleted or invalidated so that old links properly return 404 and historical slugs do not leak or permanently block reuse.
8. Returning HTTP 301/308 redirects for historical slugs can break strict RealWorld API clients that do not follow redirects or that strip the `Authorization: Token ...` header on redirection. Conversely, serving 200 OK directly causes canonical URL duplication and may confuse clients because `ArticleResponse` omits the database ID (`json:"-"`) and only returns the new slug.
9. If historical slugs are permanently reserved to prevent breaking shared links, an author could hoard high-value slugs simply by repeatedly updating an article's title. The team must determine whether historical aliases ever expire or if original slugs can be reclaimed or reassigned across different authors.
10. Database migrations in `hello.go` and test resets in `articles/unit_test.go` (`resetDBWithMock`) rely on GORM's `AutoMigrate` over SQLite. Introducing a new alias table or modifying constraints requires updating migration lists across application entry points and all test fixtures, while SQLite's limited ALTER TABLE capabilities complicate schema evolution on existing databases.
