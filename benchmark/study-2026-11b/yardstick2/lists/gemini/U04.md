1. Under the current `["ip_address"]` default, an IP attempting passwords against multiple accounts is blocked after `AXES_FAILURE_LIMIT` attempts, but switching to `[["username", "ip_address"]]` enables attackers to execute horizontal password spraying across unlimited usernames from a single IP without triggering lockout.
2. In `axes.helpers.make_cache_key_list`, cache keys are generated by concatenating parameter values without a delimiter via `"".join(...)`, causing hash collisions in `AxesCacheHandler` between distinct username and IP combinations (such as username "admin1" with IP "0.0.0.1" versus "admin" with IP "10.0.0.1").
3. In `AxesCacheHandler.reset_attempts`, cache keys are computed only from the provided arguments, meaning management commands `axes_reset_ip` and `axes_reset_username` will silently fail to clear lockout keys because neither passes both username and IP together.
4. In `AxesDatabaseHandler.user_login_failed`, the guard to avoid creating records when username is `None` strictly checks `lockout_parameters == ["username"]`; under `[["username", "ip_address"]]`, requests missing a username will record `username=None` attempts in the database that will not protect actual accounts.
5. In `AccessAttempt`, queries filter on exact username matches without normalization, which allows attackers to bypass lockout thresholds against case-insensitive authentication backends (such as email-based logins) by varying character casing unless `AXES_USERNAME_CALLABLE` is configured.
6. Existing integration tests in `tests/test_login.py` (including `test_lockout_by_ip_blocks_when_diff_user_same_ip_without_cache` and its cached equivalent) explicitly assert default lockout by IP across different usernames, causing multiple test suite failures without a major test overhaul.
7. `AccessAttempt` defines a unique constraint on `(username, ip_address, user_agent)` and individual indexes on `username` and `ip_address`, but lacks a composite index on `(username, ip_address)`; making this pair the default query pattern will increase row volume and could degrade query performance during `get_failures`.
8. The public utility function `axes.utils.reset_request` inspects `request.GET.get("username")` to satisfy `username_required`, which fails to extract usernames from POST request bodies or custom form fields when handling reset requests under the new default.
9. When `AXES_RESET_ON_SUCCESS` is enabled, a successful login previously cleared all failure records for the originating IP, but under the new default, `reset_user_attempts` will only clear records matching that specific username and IP combination.
10. In `axes/admin.py`, `IsLockedOutFilter` and `status` evaluate lockout thresholds against an individual `AccessAttempt` row's `failures_since_start` rather than aggregating failures across rotating user agents for a (username, IP) pair as `get_failures` does, causing false negative lockout displays in the admin.
