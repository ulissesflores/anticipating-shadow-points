1. Because authentication uses ASP.NET Core's built-in `MapIdentityApi<ApplicationUser>()` and `CurrentUser` only exposes `Id` and `Roles`, there is currently no tenant concept in the identity model or token claims. Without defining how tenants are registered, stored, and resolved per request, the application cannot securely authenticate a tenant context.

2. Handlers such as `GetTodosQueryHandler` query `_context.TodoLists` directly across the entire database without tenant scoping. If tenant filtering is implemented ad hoc in individual queries rather than centrally via EF Core Global Query Filters in `ApplicationDbContext`, future queries or navigation property traversals are prone to cross-tenant data leaks.

3. `CreateTodoItemCommand` and `UpdateTodoItemDetailCommand` accept an arbitrary `ListId` without verifying that the target `TodoList` belongs to the current tenant, allowing users to insert items into or reparent items into another company's list. Furthermore, commands using `FindAsync([request.Id])` will permit cross-tenant mutations or deletions if tenant ownership checks are omitted.

4. `CreateTodoListCommandValidator` and `UpdateTodoListCommandValidator` enforce unique titles across the entire `TodoLists` table using `_context.TodoLists.AnyAsync`. Without scoping this check to the current tenant, companies will encounter collisions on common list titles like "Work" or "Personal", while validation errors could leak the existence of other tenants' lists.

5. If `TenantId` is stored on both `TodoList` and `TodoItem`, the database risks data inconsistency where an item's tenant differs from its parent list unless composite foreign keys or domain invariants are enforced. Conversely, if `TodoItem` omits `TenantId` and relies solely on `TodoList`, item-level lookups in `UpdateTodoItem` and `DeleteTodoItem` will require extra joins to verify tenant boundaries.

6. If tenant assignment relies on incoming request payloads rather than being established server-side from authenticated claims, clients could forge a foreign `TenantId` and create resources in other companies. Tenant assignment must be enforced systematically across entities, such as through an interceptor alongside `AuditableEntityInterceptor`.

7. `ApplicationDbContextInitialiser` uses `EnsureCreatedAsync()` rather than EF Core migrations and seeds hardcoded default users and todo lists without any tenant association. Introducing a required `TenantId` will break database initialisation, corrupt seed workflows, and fail on existing databases unless a migration and data backfill strategy is planned.

8. The test infrastructure in `Application.FunctionalTests` (`WebApiFactory`, `TestApp`, and `DatabaseResetter`) mocks `IUser` without tenant context and executes against a shared, unpartitioned database state. Introducing tenant requirements will break existing functional test runs and give a false sense of security unless multi-tenant test fixtures and cross-tenant boundary assertions are created.

9. The frontend Angular and React applications rely on generated API clients via NSwag (`nswag.json`). If tenant context alters API route parameters, registration contracts, or request payloads instead of being handled transparently via authentication claims or session headers, the generated client and UI components will experience breaking changes across the board.
