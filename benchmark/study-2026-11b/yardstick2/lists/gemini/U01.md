1. The `User` model in `prisma/schema.prisma` currently lacks an email verification field, meaning adding an unverified check to `verifyLogin` without a backfill migration will immediately lock out existing users and break `prisma/seed.ts` (e.g., `rachel@remix.run`).
2. `app/routes/join.tsx` currently calls `createUserSession` to issue a session cookie immediately upon registration, requiring a significant architectural change to withhold authentication until confirmation without leaving the user flow broken.
3. Automated Cypress tests (`cypress/e2e/smoke.cy.ts`) and test helpers (`cypress/support/create-user.ts`) rely on immediate user creation and login sessions, which will fail continuous integration pipelines unless tests and fixtures are adapted to mock or bypass verification.
4. The application completely lacks an email delivery service, SMTP transport, and related configuration in `package.json` and `.env.example`, requiring net-new third-party infrastructure and credential management before verification messages can be sent.
5. In `server.ts`, multi-region database replays via `fly-replay` are configured only for non-GET requests, meaning an email verification link visited via a standard `GET` request will fail when attempting to write verification status against a read-only database replica.
6. Because `User.email` is enforced with a unique constraint in `prisma/schema.prisma` and `join.tsx` rejects existing emails, unverified registrations created maliciously or with typos will permanently block the legitimate owners from creating accounts unless an account cleanup or expiration process is implemented.
7. Protected route guards `getUser` and `requireUser` in `app/session.server.ts` check only user existence by ID, which would allow unverified users with existing session cookies to continue accessing protected `/notes` routes.
8. The development setup relies on MSW in `mocks/index.js` without any local email interception or mailbox testing tooling, creating developer friction and making local verification testing difficult.
9. The codebase currently possesses no mechanism or schema for generating, hashing, expiring, and invalidating single-use tokens, risking vulnerabilities if verification tokens are stored insecurely or lack expiration limits.
10. Informing users of unverified status in `app/routes/login.tsx` risks introducing account enumeration vulnerabilities if error handling distinguishes between non-existent accounts and unverified registered users.
