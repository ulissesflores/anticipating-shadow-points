1. **Broken inbound links** – After a slug change the old URL (`/api/articles/:old‑slug`) will no longer resolve, resulting in 404 errors for any previously shared links unless a redirect or slug‑history table is added.  

2. **Missing redirect handling** – The current code does not create a permanent redirect (301) from the old slug to the new one, so browsers, search engines, and social platforms will not automatically update cached URLs.  

3. **Race conditions on slug uniqueness** – `makeUniqueSlug` is retried only a few times; concurrent updates to different articles with the same title could still cause a duplicated‑key error that bubbles up as a 422 response.  

4. **In‑place slug update without transaction** – The update of the article row and the subsequent `ReplaceTags` call are performed in separate DB calls; a failure after the slug is saved (e.g., tag replacement error) leaves the article in an inconsistent state.  

5. **Cache‑stale references** – Any in‑memory caches (e.g., article lists, feed pagination) that index by slug will retain the old slug, causing duplicate entries or missing articles until the cache is explicitly refreshed.  

6. **Foreign‑key lookups that rely on slug** – Although comments and favorites use the article ID, some helper queries (e.g., favorited‑by‑user) may still filter by slug; after the change those queries will miss the article.  

7. **SEO impact without canonical handling** – Changing the slug without updating the `canonical` link or providing a `rel="alternate"` header can dilute search‑engine ranking for the original URL.  

8. **Client‑side URL generation** – Front‑end code that builds article URLs from a cached title may generate mismatched URLs if the title is updated but the client has not refreshed its state.  

9. **Potential loss of slug‑based uniqueness constraints** – If the new title yields a slug identical to another article’s existing slug, the unique index will reject the update, but the error message (`database` error) may be confusing to the user.  

10. **Absence of audit trail** – Changing the slug silently overwrites the previous identifier; without logging or an audit table it is impossible to trace which URL was originally used.  

11. **Incorrect slug regeneration logic** – The code checks `if base := makeSlug(title.(string)); base != articleModel.Slug` which compares the new base slug to the *current* slug, not the old one; if the title changes but results in the same base slug (e.g., punctuation differences) the slug will not be updated, leading to inconsistent title/slug pairs.  

12. **Missing validation for title‑to‑slug mapping** – No constraints ensure the generated slug conforms to URL‑safe characters; a malicious title could produce an invalid or unsafe slug, breaking routing or opening injection vectors.
