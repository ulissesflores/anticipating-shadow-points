1. **Missing `isVerified` flag in the `User` model** – without adding a boolean column and updating Prisma migrations, the code cannot reliably determine whether a user’s email is verified, leading to runtime errors when the flag is accessed.  

2. **Login flow still calls `verifyLogin` unchanged** – the existing `verifyLogin` function returns a user object regardless of verification status, so users could still obtain a session cookie unless every login endpoint is updated to check the new flag.  

3. **Email‑verification token storage & expiration** – if a token is stored in‑memory or in an insecure table without expiry, stolen tokens could be reused to validate any account, bypassing the intended verification step.  

4. **Race condition between account creation and verification** – a user could submit a login request before the verification email is processed, and the server might create a session for an unverified account if the verification check is not atomic.  

5. **Database migration impact on existing data** – adding a non‑nullable `isVerified` column without a default or back‑filling existing rows will cause the Prisma client to fail on startup, breaking all endpoints that query `User`.  

6. **Email enumeration vulnerability** – the sign‑up API may now return different error messages for “email already exists” vs. “verification pending”, allowing attackers to probe which addresses are registered.  

7. **Broken test suites** – the Cypress utility `cy.login()` assumes that a newly created user can log in immediately; after introducing verification, all existing end‑to‑end and unit tests that create a user and log in will fail unless they are updated to handle the verification step.  

8. **Forgot‑password / password‑reset flow** – password reset emails typically rely on the user’s verified email address; if verification status isn’t checked, reset links could be sent to unverified accounts, exposing a vector for account takeover.
