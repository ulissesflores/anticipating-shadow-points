1. **`touch` may not be invoked automatically** – if request handlers or middleware don’t call `req.session.touch()`, merely extending the expiry in the code won’t actually roll sessions on each request.  

2. **Race conditions with concurrent requests** – resetting `cookie.maxAge` without persisting the new value to the store could cause stale expiration times when multiple requests modify the same session simultaneously.  

3. **Inconsistent behavior across session stores** – some stores (e.g., Redis, MongoDB) may ignore the `maxAge` change unless `save()` is called; blindly resetting `maxAge` could leave the underlying store unchanged, resulting in premature expiration.  

4. **Performance impact** – invoking `touch` on every request adds an extra write to the session store, which can degrade throughput for high‑traffic services if the store isn’t optimized for frequent updates.  

5. **Cookie size limits** – continuously resetting `cookie.maxAge` without clearing other cookie attributes may eventually push the serialized cookie beyond browser limits, causing request failures.  

6. **Security‑related side effects** – extending the session lifetime by default may violate security policies (e.g., short‑lived auth tokens) and increase exposure to session fixation or hijacking attacks.  

7. **Potential loss of original `maxAge` semantics** – the current `resetMaxAge` restores `originalMaxAge`; making sessions roll by default could unintentionally hide configuration errors where `originalMaxAge` is set incorrectly.  

8. **Compatibility with `express-session` options** – the library supports `rolling: true` in its config; duplicating that logic here could create conflicting behaviors or double‑increment expiration, leading to erratic session lifetimes.  

9. **Testing suites may break** – existing unit tests (e.g., in `test/session.js`) assume non‑rolling behavior; changing the default will cause assertions about expiration timestamps to fail.  

10. **Memory leak risk in in‑memory stores** – constantly resetting expiration without a corresponding cleanup may keep idle sessions alive indefinitely, exhausting memory in development or low‑capacity environments.  

11. **Unexpected side effects for API clients** – clients that rely on a fixed session timeout (e.g., mobile apps) may experience prolonged sessions, affecting token refresh logic and potentially causing stale authentication data to persist.  

12. **Misaligned documentation** – the README and code comments describe “resetMaxAge” as an explicit operation; making it automatic would render those docs inaccurate, leading to confusion for future maintainers.
