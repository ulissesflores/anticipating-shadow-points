1. Adding a TenantId property to `TodoList` and `TodoItem` entities will require updating EF Core configurations and migrations; forgetting to create the migration or apply it will cause runtime database errors.  

2. Existing queries (e.g., in `GetTodos.cs`) do not filter by tenant, so without explicit tenant scoping every company could retrieve all other tenants’ data.  

3. The `AuthorizationBehaviour` and `AuthorizeAttribute` currently enforce role‑based checks but not tenant isolation; omitting tenant validation could allow privileged users to bypass tenant boundaries.  

4. Seed data in `ApplicationDbContextInitialiser` creates default `TodoList`/`TodoItem` records without a tenant reference, leading to null `TenantId` values and potential constraint violations after the schema change.  

5. Unit and functional tests (e.g., `CreateTodoListTests.cs`, `GetTodosTests.cs`) assume a single‑tenant context; they will fail or pass incorrectly if tenant filtering is not mocked or injected.  

6. The `CurrentUser` service in `src/Web/Services/CurrentUser.cs` only provides user identity; extending it to expose the tenant ID may require additional DI registration and could break existing consumers.  

7. Caching layers (if any) or in‑memory collections that store `TodoItem` objects may not consider tenant segregation, causing stale cross‑tenant data to be returned after the change.  

8. Soft‑delete or audit interceptors (`AuditableEntityInterceptor.cs`) currently log only user ID; they must be enhanced to capture tenant context, otherwise audit trails become ambiguous.  

9. Multi‑tenant support may introduce N+1 query performance issues when loading related `TodoItems` for each `TodoList`; failing to add appropriate indexes on `TenantId` could degrade query performance dramatically.
