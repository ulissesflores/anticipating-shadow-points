1. **Login failures for existing users** – the new hasher will produce a different hash format, but `PasswordHasher.Verify` still expects the legacy HMAC‑SHA512 or the current Identity format; without a migration path, verification will always return `Failed`.  

2. **Database column size mismatch** – `Person.Hash` and `Person.Salt` are stored as `byte[]`; a stronger algorithm (e.g., Argon2id) can generate longer byte arrays, potentially exceeding the current column length and causing truncation or runtime exceptions.  

3. **Empty‑salt handling** – the current `Create` command stores `Salt = []` and the hasher ignores the supplied salt; a scheme that requires an external salt will break because the empty array is persisted and later used for verification.  

4. **Re‑hash‑needed flag not acted on** – `PasswordVerificationResult.SuccessRehashNeeded` is returned for legacy hashes, but no code updates the stored hash after a successful login, leaving users stuck with the weaker hash indefinitely.  

5. **DI registration incompatibility** – replacing `PasswordHasher` with a custom implementation may break the existing service registration (e.g., lifetime, interface expectations), causing runtime resolution errors for `IPasswordHasher`.  

6. **Unit‑test breakage** – tests such as `PasswordHashingTests.cs` assert specific hash lengths or verification outcomes; a new algorithm will invalidate those expectations, leading to failing CI pipelines.  

7. **Performance regressions** – increasing the iteration count or switching to a memory‑hard algorithm may introduce noticeable latency in user registration and login, potentially triggering request timeouts in the API.  

8. **Incorrect disposal of cryptographic resources** – the current `Dispose` method is empty; a stronger hasher may allocate unmanaged memory that must be cleared, otherwise sensitive material could linger in memory.  

9. **Legacy verification path becomes dead code** – if the new scheme no longer supports the 64‑byte HMAC hashes, the conditional block in `Verify` becomes unreachable; removing it without thorough testing could expose hidden bugs for any remaining legacy accounts.  

10. **Migration ordering issues** – applying a schema migration that enlarges the hash column before migrating existing records could cause temporary data inconsistency, especially if the migration runs concurrently with live traffic.  

11. **Incorrect handling of `Hash` return type** – the current `Hash` method converts the Identity hash string back to a byte array; a new hasher that already returns raw bytes will cause `Convert.FromBase64String` to throw, breaking user creation.  

12. **Missing backward‑compatibility flag** – without a way to indicate which hashing algorithm was used per user, future code may misinterpret newer hashes as legacy, leading to incorrect verification results.
