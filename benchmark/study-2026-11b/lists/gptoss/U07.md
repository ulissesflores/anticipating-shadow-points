1. **Database schema mismatch** – Changing primary key columns from `INTEGER` to `UUID` may break existing migrations, raw SQL scripts, and the SQLite/PostgreSQL schema defined in `project/db/create.sql` and migration files, causing migration failures or data loss.  

2. **ORM model incompatibility** – Tortoise‑ORM models in `project/app/models/tortoise.py` expect integer fields for IDs; switching to `UUIDField` requires updates to model definitions, default value generation, and possibly the `pydantic` schemas that serialize these IDs.  

3. **CRUD endpoint expectations** – API routes in `project/app/api/crud.py` and `summaries.py` parse request/response bodies assuming integer IDs; converting to UUID strings will break request validation, URL routing (`/items/{id}`), and downstream client code that expects numeric IDs.  

4. **Serialization / validation errors** – Pydantic models (`project/app/models/pydantic.py`) may still type IDs as `int`, leading to validation errors when UUID strings are returned or accepted, and causing mismatched OpenAPI docs.  

5. **Foreign‑key relationships** – Any relationships that reference the primary key (e.g., foreign key columns in other tables or models) must also be migrated to `UUID`; otherwise referential integrity constraints will fail and queries will raise errors.  

6. **Existing test suite** – Tests in `project/tests/` (e.g., `test_summaries.py`, `test_ping.py`) use hard‑coded integer IDs; after the change they will fail or pass incorrectly, masking real bugs.  

7. **Data migration strategy** – Introducing UUIDs on a live database requires a data migration path; without a proper migration script, existing rows with integer IDs will become orphaned or duplicated.  

8. **Performance considerations** – UUID primary keys can impact index size and query performance; the codebase may not account for this, leading to slower API responses and higher storage usage.  

9. **Client compatibility layer** – To keep existing API clients working, a compatibility shim must translate between integer and UUID representations; lacking this will cause backward‑compatibility breakage for external consumers.  

10. **Environment configuration** – Deployment scripts (`docker-compose.yml`, `Dockerfile`, `release.sh`) may include commands that assume integer auto‑increment behavior (e.g., seeding data with numeric IDs); these need to be updated to generate UUIDs.  

11. **Logging and monitoring** – Log statements and metrics that format IDs as integers will break or produce unreadable output when IDs become UUID strings.  

12. **Security and validation** – UUIDs can be supplied in various formats (with/without hyphens); insufficient validation may allow malformed IDs to reach the database, causing errors or potential injection vectors.
