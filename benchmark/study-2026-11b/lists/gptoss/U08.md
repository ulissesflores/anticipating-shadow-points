3. Tests that assert specific signatures or lengths (e.g., in `tests/test_signer.py`) will fail because the expected SHA‑1‑based signatures will no longer match the new SHA‑256 output.  
4. Documentation strings and examples refer to `hashlib.sha1` as the default; they will become misleading unless updated, increasing the risk of future misuse.  
5. The lazy import helper `_lazy_sha1` is hard‑coded; replacing the default without providing a comparable `_lazy_sha256` could re‑introduce import‑time failures on platforms lacking SHA‑256 (unlikely but a regression risk).  
6. Users explicitly passing `digest_method=None` rely on the class‑level default; changing it silently may break backward‑compatible APIs that expected SHA‑1, especially in libraries that pin the default for interoperability.  
7. The `derive_key` method builds the HMAC key using `self.digest_method(self.salt + …).digest()`. Switching to SHA‑256 changes the key length, which could affect downstream callers that assume a 20‑byte SHA‑1 digest (e.g., custom key‑derivation implementations).  
8. The `Signer` constructor allows overriding `digest_method`; if the default is changed but older code still passes `digest_method=hashlib.sha1`, inconsistent digests may appear within the same application, leading to hard‑to‑debug signature mismatches.
