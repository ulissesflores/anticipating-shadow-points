1. **Database schema mismatch** – `axes/migrations/0007_alter_accessattempt_unique_together.py` creates a unique constraint on `(username, ip_address, user_agent)`. Switching the default to lock out by *both* username **and** IP will make the existing constraint too strict for cases where only one of the fields is set (e.g., anonymous login attempts with no username), causing `IntegrityError` on record insertion.  

2. **Missing username handling** – `axes/handlers/database.py` and `axes/handlers/cache.py` contain a guard that aborts record creation when `lockout_parameters == ["username"]` and `username is None`. After the change, the code will still hit this guard for attempts that lack a username, resulting in **no lockout record** being stored for IP‑only attacks.  

3. **Cache key divergence** – `helpers.get_client_parameters()` builds filter kwargs based on `settings.AXES_LOCKOUT_PARAMETERS`. Changing the default to a combined `[["username", "ip_address"]]` will generate a **different cache‑key list** (`make_cache_key_list`) than the current IP‑only key, causing cache misses and allowing attackers to bypass lockout until the cache is repopulated.  

4. **Management commands out of sync** – The `axes_reset_ip_username` command (and its help text) assumes a lockout by both parameters, but the other reset commands (`axes_reset_ip`, `axes_reset_username`) still operate on *single* fields. If the default changes without updating those commands, administrators may inadvertently reset only one dimension, leaving the other still locked out.  

5. **Query‑filter logic breakage** – `helpers.get_client_parameters()` creates a list of dicts for each lockout parameter. When a combined parameter list is used, the resulting `filter_kwargs` become a **single dict with both fields**, which some downstream code (e.g., `AccessAttempt.objects.filter(**filter_kwargs)`) may not expect, potentially raising `FieldError` or generating incorrect SQL.  

6. **Existing tests will fail** – The test suite (`tests/test_*`) contains fixtures that lock out by IP only (e.g., `test_login.py`). Without adjusting the test data to include usernames, those tests will either raise exceptions or incorrectly assert lockout behavior, leading to widespread test failures.  

7. **Deduplication migration may delete needed rows** – `0007_alter_accessattempt_unique_together.py` deduplicates attempts by grouping on `(username, user_agent, ip_address)`. If many records have `username=None`, the new combined lockout will treat them as *different* lockouts, but the deduplication still removes duplicates, potentially deleting legitimate attempt records that should remain distinct for IP‑only tracking.  

8. **Performance regression** – Adding `username` to the lockout key expands the cardinality of the unique‑together index. In high‑traffic environments this can **slow down** lookups and insertions in the `AccessAttempt` table, especially when usernames are long or not indexed, increasing query time for every authentication attempt.  

9. **Backward‑compatibility of settings** – `settings.AXES_LOCKOUT_PARAMETERS` can be a list or callable. Existing projects may still configure it as `["ip_address"]`. Changing the default without a migration step will cause a **silent mismatch** where the code uses the old list while docs and defaults assume the new combined lockout, leading to inconsistent lockout behavior across deployments.  

10. **Signal handling may double‑lock** – The `axes/signals.py` module emits lockout signals based on the result of `get_lockout_parameters`. When both username and IP are considered, a single failed attempt could trigger two separate lockout signals (one for each field) if the signal listeners are not updated, potentially causing duplicate log entries or race conditions in custom lockout callables.  

11. **User‑agent edge case** – The unique‑together constraint includes `user_agent`. If a user logs in from the same IP with different browsers, the combined lockout will treat them as distinct, **defeating the intended stricter lockout** by username + IP. This nuance must be addressed in the migration or documentation to avoid unexpected security gaps.  

12. **Admin UI confusion** – The Django admin (`axes/admin.py`) displays lockout entries grouped by IP. After the change, administrators may misinterpret the UI, thinking a user is only locked out by IP when in fact the username factor is also part of the lockout, leading to **incorrect manual unlock attempts**.
