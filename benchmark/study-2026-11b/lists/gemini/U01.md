1. In `app/routes/join.tsx`, the action currently calls `createUserSession` immediately after `createUser`, which would automatically log new users in upon registration and bypass email verification unless sign-up is explicitly decoupled from session creation.
2. Adding a non-nullable `emailVerified` boolean defaulting to `false` in `prisma/schema.prisma` would cause `npx prisma migrate deploy` to treat all existing users as unverified, locking them out of production contrary to the requirement that this only applies to new users.
3. In `server.ts`, the multi-region Fly.io replay middleware only replays non-GET requests to `PRIMARY_REGION`; if email verification links are handled via a `GET` request in a route loader that updates PostgreSQL, users routed to read-only replica regions will encounter database write errors.
4. The smoke test in `cypress/e2e/smoke.cy.ts` submits the registration form in `join.tsx` and immediately asserts access to authenticated routes (`/notes`), which will break once registration stops creating an active session.
5. In `cypress/support/create-user.ts`, test user creation directly calls `createUser` and `createUserSession` for `cy.login()`; if `verifyLogin` or session checks enforce verification without updating this script, authenticated Cypress tests will fail across the suite.
6. The database seed in `prisma/seed.ts` provisions `rachel@remix.run` via `prisma.user.create` without verification metadata, which would prevent developers from logging in with the default test credentials after running `npm run setup`.
7. If a new Prisma model is added to store verification tokens without `onDelete: Cascade` referencing `User`, calling `prisma.user.delete` in `cypress/support/delete-user.ts` and `app/models/user.server.ts` will throw foreign key constraint errors during cleanup.
8. Because `app/routes/join.tsx` rejects existing emails with `"A user already exists with this email"`, creating an unverified user record on signup allows abandoned or malicious unverified accounts to permanently squat on email addresses without an account-reclaiming or token-resend mechanism.
9. In `app/routes/login.tsx`, authentication failures currently return a generic `"Invalid email or password"` error, so returning `null` from `verifyLogin` for unverified users will mislead them into thinking their credentials are wrong instead of directing them to verify their email.
10. If verification emails are dispatched synchronously within the `join.tsx` action without transactional error handling, external email API failures or timeouts will leave orphaned unverified users in PostgreSQL who cannot log in or re-register.
11. The application has no email service dependencies in `package.json`, no email environment variables in `.env.example`, and no mock handlers in `mocks/index.js`, which will cause local development and offline CI runs (`npm run test:e2e:run` with MSW) to fail unless mail transport is properly mocked.
