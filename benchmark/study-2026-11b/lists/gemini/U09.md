1. In `PasswordHasher.cs`, verification currently branches between 64-byte legacy HMAC-SHA512 hashes and ASP.NET Core Identity PBKDF2 hashes. If the new verifier replaces existing logic without supporting both historical formats or lacks an algorithm discriminator, users with legacy HMAC hashes or intermediate PBKDF2 hashes will fail authentication and be locked out.

2. In `Login.cs`, password migration relies on `passwordHasher.Verify` returning `PasswordVerificationResult.SuccessRehashNeeded` to trigger updating `person.Hash` and saving changes to the database. If the new implementation returns `PasswordVerificationResult.Success` for valid older hashes, users will authenticate successfully but their stored hashes will never be upgraded to the stronger scheme.

3. `PasswordHasher.cs` currently converts password hashes to and from Base64 strings using `Convert.FromBase64String` and `Convert.ToBase64String`. If the stronger scheme uses standard text formats like PHC or modular crypt strings containing non-Base64 characters (such as Argon2 or bcrypt formats with `$`), runtime `FormatException` crashes will occur during verification instead of returning `PasswordVerificationResult.Failed`.

4. The `Person.Salt` column is configured as a non-nullable `BLOB` in SQLite and `varbinary(max)` in SQL Server, populated with an empty byte array `[]` when using self-salting schemes. If the new implementation attempts to set `Salt` to null when rehashing or creating users, `SaveChangesAsync` will throw database constraint violations.

5. If storing the new hash format requires modifying `Person` (such as changing column data types, nullability, or adding an algorithm discriminator column), migrations must be created for both `SqliteConduitContext` and `SqlServerConduitContext`. Omitting migrations for either provider will break `MigrationTests` because `HasPendingModelChanges()` is asserted against both database contexts.

6. While `Login.cs` handles opportunistic rehashing, `Edit.cs` also updates passwords using `passwordHasher.Hash(message.User.Password, [])` when a user updates their profile. If the hashing scheme upgrade is not consistently applied across both `Create.cs` and `Edit.cs`, or if existing salt clearing is mishandled during profile updates, users could store mismatched hash formats that fail subsequent logins.

7. Because opportunistic rehashing converts `POST /api/users/login` from a read into a database write via `context.SaveChangesAsync`, concurrent login requests for the same unmigrated user could cause race conditions. Under SQLite, where transactions run at `IsolationLevel.Serializable` via `DBContextTransactionPipelineBehavior`, simultaneous hash calculations and writes risk database locking failures.

8. In `Login.cs`, requests for non-existent users immediately abort with a 401 before any cryptographic work is performed. With a computationally heavier hashing scheme, the significant latency discrepancy between non-existent emails (~1ms) and valid accounts (~hundreds of ms) enables user enumeration and exposes the unauthenticated login endpoint to denial-of-service attacks.

9. Although `IPasswordHasher.Hash` returns a `Task<byte[]>`, `PasswordHasher.cs` executes hashing synchronously via `Task.FromResult`, and `Verify` is entirely synchronous. Introducing a compute- or memory-heavy algorithm (such as Argon2id or bcrypt) synchronously on Kestrel request threads could exhaust the .NET ThreadPool under concurrent login or registration traffic.

10. The test suite in `tests/Conduit.IntegrationTests` contains numerous integration tests (such as `CreateTests`, `LoginTests`, and `ApiTests`) that repeatedly create and authenticate users. If the work factor for the stronger hashing scheme is hardcoded high without an environment-specific or configurable work factor for tests, build and test execution via `dotnet run --project build/build.csproj -- test` will suffer severe performance degradation or time out in CI.

11. `PasswordHashingTests.cs` contains explicit integration tests that construct legacy HMAC-SHA512 hashes using the hardcoded `"realworld"` key, verify lazy rehashing on login, and assert hash and salt states. Altering the `IPasswordHasher` contract or changing how legacy HMAC hashes and upgraded hashes are verified will break these tests unless the migration path preserves backward-compatible verification.
