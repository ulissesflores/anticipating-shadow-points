1. In `axes/handlers/cache.py`, `AxesCacheHandler.reset_attempts` hashes `AccessAttempt(username=username, ip_address=ip_address)`, but commands like `axes_reset_ip` supply `username=None`. This produces an IP-only hash that fails to match the combined `(username + ip)` key in cache, leaving locked-out users unable to be unlocked via IP-based reset commands.

2. In `tests/base.py`, `AxesTestCase.login(is_valid_username=False)` generates a random username on each attempt to test IP lockout. Under a combined default, attempts are split across unique usernames and never accumulate toward `AXES_FAILURE_LIMIT`, causing `self.lockout()` and dozens of dependent tests across `test_login.py` and `test_handlers.py` to fail.

3. In `axes/utils.py`, `reset_request` inspects combined lockout parameters and sets `username_required=True`, reading the username strictly from `request.GET.get("username")`. This hardcodes the query parameter name and ignores `AXES_USERNAME_FORM_FIELD` or custom user model fields, breaking reset workflows for applications using non-standard username fields or POST requests.

4. Defaulting to `[["username", "ip_address"]]` fundamentally changes the security model by allowing an attacker at a single IP address to spray passwords across unlimited distinct usernames without triggering an IP lockout. This removes the repository's default protection against horizontal credential stuffing and user enumeration attacks.

5. In `axes/handlers/database.py`, `user_login_failed` contains a guard for `lockout_parameters == ["username"]` when `username is None`, but has no corresponding handling for combined parameters. Requests without a username (such as malformed payloads or views decorated with `@axes_dispatch`) will record rows with `username=None`, which fail to lock out named accounts or aggregate properly with credentialed attempts.

6. Because `AccessAttempt.objects.filter` and `AxesCacheHandler` key generation perform exact, case-sensitive matching, projects with case-insensitive authentication (e.g. email logins) will become vulnerable to lockout bypasses. Attackers from the same IP can evade the failure limit simply by alternating the letter casing of the submitted username unless `AXES_USERNAME_CALLABLE` is explicitly configured.

7. In `axes/conf.py`, deprecated flags like `AXES_ONLY_USER_FAILURES` and `AXES_LOCK_OUT_BY_USER_OR_IP` are checked only if `settings.AXES_LOCKOUT_PARAMETERS is None`. Setting the new default directly on line 39 instead of in the fallback block will silently bypass and break backward compatibility for existing deployments relying on those legacy settings.

8. In `axes/admin.py`, `AccessAttemptAdmin.status` and `IsLockedOutFilter` evaluate lockout thresholds on single `AccessAttempt` records rather than aggregating across records sharing the same `(username, ip_address)`. Because different user agents generate distinct rows under the model's `unique_together` constraint, the admin panel will report users as unlocked even when their aggregated attempts exceed the failure limit.

9. In `axes/models.py`, `AccessAttempt` has single-column indexes on `ip_address` and `username`, but lacks a composite index on `(username, ip_address)`. Shifting the default query in `AxesDatabaseHandler.filter_user_attempts` to always filter by both fields simultaneously will cause database query degradation on large tables without an accompanying migration.

10. In `axes/apps.py` and `axes/helpers.py`, changing the default alters startup log messages in `AppConfig.initialize()` and changes formatted client strings in `get_client_str()` when `AXES_VERBOSE=False`. This will directly break existing tests such as `test_axes_config_log_ip_only` and `test_non_verbose_ip_only_client_details`, and may break downstream log-monitoring systems that parse Axes output.
