1. `CreateTodoListCommandValidator` and `UpdateTodoListCommandValidator` enforce unique titles using global queries across `_context.TodoLists`. Without scoping these validation queries to the current tenant, different companies will be blocked from creating lists with common names (such as "Tasks"), and users could probe other companies' list titles through validation errors.

2. `CreateTodoItemCommandHandler` assigns `request.ListId` and `UpdateTodoItemDetailCommandHandler` updates `entity.ListId` without validating that the target `TodoList` belongs to the caller's tenant. Without explicit tenant checks on list associations, users could inject or move to-do items into another company's lists by supplying foreign list IDs.

3. Item command handlers (`UpdateTodoItemCommandHandler`, `DeleteTodoItemCommandHandler`, and `UpdateTodoItemDetailCommandHandler`) look up entities directly by primary key using `_context.TodoItems.FindAsync([request.Id])`. If `TodoItem` lacks a tenant identifier or relies solely on parent-list navigation for scoping without global query filters, a user could manipulate or delete any company's items simply by guessing integer IDs.

4. If `TenantId` is denormalized and added to both `TodoList` and `TodoItem` without database-level composite foreign keys, an item's tenant could diverge from its parent list during updates or moving items. This would cause data integrity violations where an item appears in one tenant's list while belonging to another tenant.

5. `ApplicationDbContextInitialiser.TrySeedAsync` inserts default `TodoList` and `TodoItem` records on application startup without any tenant association. If a required, non-nullable tenant property or foreign key is introduced, application startup in `Program.cs` will crash during initialization or create orphaned entities that are invisible to all tenants.

6. `IUser` and `CurrentUser` only expose `Id` and `Roles` from `ClaimsPrincipal`, and `Users.MapIdentityApi<ApplicationUser>()` uses standard ASP.NET Core Identity endpoints that do not capture, store, or issue tenant claims. Without establishing a clear tenant resolution mechanism (such as subdomain, tenant header, or JWT claim), handlers cannot securely identify which company the authenticated user belongs to.

7. `ApplicationDbContext` inherits `IdentityDbContext<ApplicationUser>`, which enforces global unique constraints on `NormalizedEmail` and `NormalizedUserName`. In a multi-tenant environment where multiple companies might share the database, users with identical email addresses across distinct companies will collide and fail registration.

8. If tenant assignment is handled implicitly within `AuditableEntityInterceptor` alongside `CreatedBy`, modifying entities outside an active HTTP request context (such as background jobs, database seeders, or integration tests) will fail or overwrite tenant values with null.

9. `WebApiFactory` and `TestApp` in the functional test suite mock `IUser` with only a user ID and roles, and helper methods like `TestApp.AddAsync` persist entities directly to `ApplicationDbContext` without tenant context. Introducing mandatory tenant constraints or query filters will silently hide data from assertions or break existing functional tests across the suite.

10. If the tenant identifier is introduced into API route templates or command contracts rather than resolved transparently on the server, existing OpenAPI specifications and generated NSwag clients in both `ClientApp` (Angular) and `ClientApp-React` will break and require coordinated client-side refactoring.
