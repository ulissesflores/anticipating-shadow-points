Vou ler o repositório e mapear onde perfil, posts e comentários vivem, para listar os riscos concretos desse download único.1. `GET /api/v1/users/<id>`, `/users/<id>/posts/`, and `/users/<id>/timeline/` never check that `g.current_user` is that id, and `user.html` shows `email` only to administrators. An export copied from those routes lets any confirmed account download another user's `email`, `name`, `location`, and `about_me` by changing the integer.

2. The API and the HTML app use different identities: `verify_password` sets `g.current_user` and does not call `login_user`, while pages use Flask-Login's `current_user`. Reading the wrong one builds the file for `AnonymousUser` or crashes. `api.before_request` returns 403 when `confirmed` is false, and `auth.before_app_request` redirects every non-auth endpoint to `auth.unconfirmed`, so a registered but unconfirmed account cannot reach a new `main` or `api` route.

3. `User.to_json` leaves out `email`, `name`, `location`, `about_me`, `confirmed`, and `role`. `Comment.to_json` leaves out `disabled`, and `Post.to_json` returns `comment_count` plus `comments_url` instead of the comment rows, so a file built from these serializers is not the user's archive.

4. `user.comments` is what that user wrote, including comments on other people's posts. `post.comments` is every comment on that post, and `get_comments` runs `Comment.query` with no author filter. Reusing the `_comments.html` test `moderate or not comment.disabled` also drops the owner's own moderator-hidden comments.

5. `user.followed_posts` joins `follows` and returns posts by everyone that user follows. Their own posts show up there only because `User.__init__` inserts a self-follow (`add_self_follows` exists for older rows). The list routes paginate at `FLASKY_POSTS_PER_PAGE` (20) and `FLASKY_COMMENTS_PER_PAGE` (30) with `error_out=False`, so one page silently drops the rest. `fake.posts` already generates enough rows to hit the cap.

6. A column dump of `User` includes `password_hash`. `generate_confirmation_token`, `generate_reset_token`, `generate_email_change_token`, and `generate_auth_token` are itsdangerous payloads signed with `SECRET_KEY` (the default in `Config` is `'hard to guess string'`). Writing a fresh token into the file hands the holder a confirm, reset, or email-change link, and the API already accepts the one-hour auth token as the Basic username with an empty password.

7. `auth.before_app_request` skips its check when `request.endpoint == 'static'`. Saving the archive under `app/static/` makes it fetchable with no login. The only background pattern in the app is `send_email`'s `Thread`, and running this query there crosses SQLite's thread check on the default `sqlite:///...data.sqlite` connection.

8. Session cookies have no `Secure` or `SameSite` setting (Flask 0.12.2 and Flask-Login 0.4.0, nothing in `config.py`), and sensitive actions such as `/moderate/disable/<id>` are already plain GET links. A GET download on `main` is sent with the session cookie on a cross-site request. Flask-WTF does not attach a CSRF token to that link, and `remember_me` keeps the cookie.

9. `json.dumps` of `member_since`, `last_seen`, or `timestamp` raises `TypeError`. Only Flask's `JSONEncoder` accepts `datetime`, and `fake.past_date()` stores a `date` in those `DateTime` columns. The editable source is `body`. `body_html` is the bleach HTML that `_posts.html` and `_comments.html` inject with `|safe`, so an HTML file built the same way is a live document of the stored markdown.

10. `SQLALCHEMY_RECORD_QUERIES` is on in the base `Config`, and `main.after_app_request` logs the SQL text and bound parameters of any query slower than `FLASKY_SLOW_DB_QUERY_TIME` (0.5s). One query that loads every `Text` body crosses that line and writes the posts and comments into the log. `ProductionConfig` also emails ERROR tracebacks to `FLASKY_ADMIN`. The same request runs `current_user.ping()`, which sets `last_seen` on the shared session, so a `commit` in the handler stores the export time as `last_seen`.
