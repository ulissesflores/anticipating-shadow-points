I'll review how signing digests are chosen and used in this repository, then list the concrete failure modes of switching the default from SHA-1 to SHA-256.The library is itsdangerous. I'll read the signer, serializers, and tests that pin SHA-1 signatures so the risks stay specific.1. Tokens already signed with the implicit SHA-1 default will fail to verify. Release 1.0.0 was yanked for the same kind of default change, `Serializer.default_fallback_signers` has been empty since 2.0, and `Signer.unsign` / `TimestampSigner.unsign` never try fallbacks, so only `Serializer.loads` and `TimedSerializer.loads` can still accept old tokens.

2. `digest_method` is also the key-derivation hash. The default `django-concat` path, plus `concat` and `hmac`, hashes `salt + b"signer" + secret_key` in `derive_key`, so the derived key changes from 20 bytes to 32 bytes along with the MAC. `key_derivation="none"` is the only mode that leaves the secret unhashed.

3. `Signer.default_digest_method` and `HMACAlgorithm.default_digest_method` are separate copies of `_lazy_sha1`. `Signer` passes its digest into `HMACAlgorithm` only when `algorithm` is omitted, so `algorithm=HMACAlgorithm()` (see `test_algorithm`) can MAC a SHA-256-derived key with SHA-1 if only one attribute is updated.

4. A custom `SigningAlgorithm` still receives its key from `derive_key()`. `_ReverseAlgorithm` and any other algorithm that ignores `digest_method` still emits different signatures once the default digest changes.

5. In `iter_unsigners`, a dict fallback replaces `signer_kwargs` instead of merging. A default fallback of `{"digest_method": sha1}` drops a caller's `sep`, `key_derivation`, or `algorithm`, and a bare `Signer` entry uses the new SHA-256 default, so neither form actually verifies those old tokens.

6. Restoring SHA-1 on `default_fallback_signers` makes every serializer that omitted `fallback_signers` accept SHA-1 again, including callers who already passed `signer_kwargs={"digest_method": hashlib.sha256}` and relied on the empty list from 2.0 (issue 155).

7. `_lazy_sha1` exists so FIPS builds that lack SHA-1 do not touch `hashlib.sha1` at import (2.2.0, issue 375). A SHA-1 fallback that calls `hashlib.sha1()` during unsign raises an exception `loads` does not catch (`BadSignature` only; `TimedSerializer` also aborts the loop on `SignatureExpired`), so a missing SHA-1 becomes a crash instead of a rejected token.

8. Both call sites need a constructor: `derive_key` calls `digest_method(data).digest()`, and `HMACAlgorithm.get_signature` passes that same object as `hmac.new(..., digestmod=)`. It must stay a `staticmethod`. A plain function on the class is bound to the instance, and a hash name string satisfies only one of the two call sites.

9. The signature grows from a 20-byte SHA-1 digest (27 url-safe base64 characters, padding stripped) to 32 bytes (43 characters), the cookie and URL growth `docs/concepts.rst` already warns about. That also invalidates the pinned strings in `README.md` (`6YP6T0BaO67XP--9UzTrmurXSmg`), `docs/signer.rst` (`wh6tMHxLgJqB6oY1uT73iMlyrOA`), and `test_digests` (`[42].-9cNi0CxsSB3hZPNCe9a2eEs1ZM`), and `test_iter_unsigners` asserts the first signer's digest is `_lazy_sha1`. Sphinx is not configured with doctest, so the docs can go stale without a CI failure.
