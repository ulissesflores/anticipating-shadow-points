Vou ler o código da sessão e de onde o cookie é emitido, para listar falhas concretas desse padrão Secure e SameSite=Strict neste repositório.1. `SessionMiddleware` appends `; secure` only when `https_only` is true, and `TestClient` defaults to `base_url="http://testserver"`. `test_secure_session` already shows an HTTP client returning the new session in the POST body and an empty session on the next GET, because the cookie jar drops `Secure` cookies on `http://`; making that the default breaks `test_session`, `test_session_persists_mutations`, `test_set_cookie_only_on_modification`, `test_vary_cookie_on_access`, and the `docs/config.md` app that builds `SessionMiddleware` with only `secret_key`.

2. The flag is fixed in `__init__` (`security_flags += "; secure"`) and the send path never reads `scope["scheme"]`. A write served over plain HTTP, including uvicorn's default and any request that reaches the middleware before an optional `HTTPSRedirectMiddleware`, still emits `Set-Cookie` with `Secure`, which browsers discard while the endpoint returns 200 and the in-request session.

3. Deriving `Secure` from `scope["scheme"] == "https"` instead of `https_only` misses the proxy layout this repo documents: TLS usually stops in front of the app, and `scheme` stays `http` until Uvicorn's optional `ProxyHeadersMiddleware` applies `X-Forwarded-Proto`. Those deployments would keep issuing a non-Secure session cookie.

4. `same_site` defaults to `"lax"`, which is still sent on a cross-site top-level GET. `SameSite=Strict` is not, so a login, OAuth/OIDC `state`, or `next` URL stored in `request.session` is missing when the browser returns from an identity provider, a payment page, or an emailed link. `AuthenticationMiddleware` does not fill that in; it only inspects `Authorization`.

5. `docs/middleware.md` says `partitioned=True` needs `https_only=True` and, for a cross-site embed, `same_site="none"`. Browsers reject `Partitioned` without `Secure` (`docs/responses.md`) and reject it unless `SameSite=None`, so a default of `Strict` plus `Secure` makes `partitioned=True` alone a cookie that is dropped both on write and on clear, since both headers are built from the same `security_flags` string. `test_partitioned_session` only stays green because it passes `same_site="none"` and `base_url="https://testserver"` itself.

6. Logout writes `session=null; expires=Thu, 01 Jan 1970 00:00:00 GMT` plus those same flags, and does not go through `Response.delete_cookie` (`Max-Age=0`, and defaults `secure=False`, `samesite="lax"`). A `Secure`/`SameSite=Strict` expiry does not remove the non-Secure `SameSite=Lax` cookie already stored, and `cookie_parser` keeps whichever `session=` value appears last, so a stale valid signature still loads. Reads do not reissue the cookie either: `test_set_cookie_only_on_modification` asserts `Set-Cookie` is omitted unless `session.modified`, so existing cookies keep the old attributes for the default 14-day `max_age`.

7. The middleware loads `scope["session"]` for `websocket` connections, but `send_wrapper` only rewrites `http.response.start`, so a socket can never update the cookie. A `Secure` cookie is not sent on a `ws://` handshake; `TestClient` with the default `http://testserver` base opens `ws://`, and `HTTPSRedirectMiddleware` rewrites `ws` to `wss` only when it is installed outside.

8. The attributes are one concatenated string (`httponly; samesite=` plus optional `; secure`, `; domain=`, and `; partitioned`), and unlike `Response.set_cookie` there is no runtime check of `same_site`. Hardcoding `samesite=strict; secure` and still appending the constructor value emits two SameSite attributes, so an explicit `same_site="none"` can lose. Rebuilding the header with `Response.set_cookie` raises `ValueError` for `partitioned=True` on Python before 3.14 (this middleware writes the token raw, and `test_partitioned_session` does not skip versions) and `SimpleCookie` can quote the `TimestampSigner` value (`=` from `b64encode`, `.` separators) so `unsign` fails.

9. `domain` is appended to that same string (`test_domain_cookie` expects `domain=.example.com`). With `Secure` set, only HTTPS hosts in that parent domain store or clear the shared cookie; an HTTP host in the `Domain` keeps the old one. Callers and tests that pass `https_only=False` or `same_site="lax"`/`"none"` rely on those parameters overriding the default; `docs/middleware.md` still documents the defaults as `lax` and `https_only=False`, with `https_only=True` only as a production choice.
