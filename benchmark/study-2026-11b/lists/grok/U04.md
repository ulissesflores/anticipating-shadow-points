Vou ler o código de bloqueio atual para listar os riscos concretos desta mudança, sem alterar nada.O padrão atual é bloqueio só por IP. Vou cruzar configuração, handlers e testes para ver onde a combinação username+IP quebra.1. `["username", "ip_address"]` is OR lockout (`get_failures` takes the max of the two counters, the old `AXES_LOCK_OUT_BY_USER_OR_IP` path). "Together" is the nested `[["username", "ip_address"]]`. The flat list locks that username from every other IP after failures from one address, which `test_lockout_by_user_and_ip_allows_when_same_user_diff_ip_without_cache` treats as allowed.

2. A nested pair gives each username its own counter, so one IP can try `AXES_FAILURE_LIMIT` (default 3) passwords on every account and never trip. `axes.W006` only checks that `ip_address` appears somewhere, so this stays silent, and the default tests `test_lockout_by_ip_blocks_when_diff_user_same_ip_*` currently require the other user on that IP to be blocked.

3. In `axes/conf.py`, a missing `AXES_LOCKOUT_PARAMETERS` still runs the deprecated-flag block, and `AXES_USE_USER_AGENT` appends onto element 0. Turning the implicit default into a nested list changes a user-agent-only project from `[["ip_address", "user_agent"]]` to `[["username", "ip_address", "user_agent"]]`. Replacing that whole block also drops `AXES_ONLY_USER_FAILURES`, `AXES_LOCK_OUT_BY_USER_OR_IP`, and `AXES_LOCK_OUT_BY_COMBINATION_USER_AND_IP`.

4. `make_cache_key_list` concatenates values with no separator and skips falsy ones, so `root` at `10.0.0.1` hashes the same as `root1` at `0.0.0.1`. An empty username collapses to the old IP-only digest, so omitted-username attempts share one bucket and can hit leftover IP keys. The database handler stores real columns; the cache handler would be wrong for every default install.

5. `AxesCacheHandler.reset_attempts` hashes a single synthetic `AccessAttempt`. `axes_reset_ip` and `axes_reset_username` pass only one field, so they delete a different key than the pair that was incremented, and `ip_or_username=True` already raises `NotImplementedError`. The database handler still filters by whichever column is set, so the same command clears every username on that IP in the database and clears nothing in cache.

6. The "do not record" guard in both handlers matches only `lockout_parameters == ["username"]` when the username is `None`. A combination still inserts `username` NULL, and `filter(username=None)` is `IS NULL`, distinct from `""`, so a missing field and a blank field are two extra counters that do not add to the real account. `get_client_username` does not casefold, and it truncates to 255 characters, so `Admin`/`admin` and long emails that share a prefix become separate or merged buckets.

7. Rows already store the username, but today's count is the sum of every username on that IP. After the filter change, a shared address that is over the limit unlocks per pair with no migration. Cache entries move from `sha256(ip)` to `sha256(username + ip)`, so existing cache lockouts stop matching. Any project that never set the flag picks this up on upgrade, while `docs/4_configuration.rst` and `docs/2_installation.rst` still say the default is `["ip_address"]`.

8. Non-verbose `get_client_str` logs exactly the lockout parameters, then `cleanse_parameters` masks `AXES_SENSITIVE_PARAMETERS`, whose default is `["username", "ip_address"]`. The lockout warning no longer shows either half of the new key.

9. `AccessAttempt` is unique on `(username, ip_address, user_agent)`, and `get_failures` sums every user-agent row for the pair, but `AccessAttemptAdmin` marks a row locked only when that row's own `failures_since_start` reaches the limit. A lock spread across browsers never shows as locked in the admin.
