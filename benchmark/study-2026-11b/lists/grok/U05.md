Vou ler o código de sessão deste repositório para achar onde a expiração é decidida e o que quebraria se cada pedido passasse a renovar o prazo.1. `rolling` is `Boolean(opts.rolling)`, so the default is false, and the tests `should default to false`, `should only set-cookie when modified`, and `should Set-Cookie only once for browser-session cookies` require an unmodified later response to send no `Set-Cookie`. A silent flip in 1.19.x skips the deprecation path already used for an omitted `resave` or `saveUninitialized`, and an explicit `rolling: false` has to keep the absolute cookie deadline.

2. The default cookie is `{ maxAge: null }` (no `Expires`). `Session.resetMaxAge` writes `originalMaxAge` back, which stays null, so a roll only repeats `Set-Cookie` and does not extend a lifetime. Inventing a `maxAge` would turn those browser-session cookies into persistent ones; `should not reset cookie` covers the case where the handler sets `expires` to null.

3. `shouldSetCookie` honors `rolling` only when `cookieId === req.sessionID`. With `saveUninitialized: false`, a new unmodified session must not be stored and must not get a cookie (`should not force cookie on uninitialized session…`, `should prevent uninitialized session from being touched`). Rolling inside `generate()` would set `connect.sid` before any session data exists.

4. `rolling` only forces `Set-Cookie`. Store expiry is a separate `res.end` path: `session.touch()`, then `save` if `shouldSave`, or `store.touch` when the store has that method. A store without `touch` and with `resave: false` keeps its own TTL (the README already says those stores need `resave: true`), so the browser cookie slides while `MemoryStore.getSession` still drops the record at the old `cookie.expires` and the next `get` calls `generate()` with a new id.

5. `MemoryStore.touch` reloads through `getSession`, which deletes the record when `expires <= Date.now()` and then does nothing. A request still in flight when that deadline passes loses the session, while `onHeaders` still `setcookie`s the same id. `set` would have written it back; the recommended `resave: false` path does not.

6. `hash()` skips `cookie`, so a rolled expiry is not a modification and `resave: false` must not `set` the whole session. Treating the new `Expires` as a change makes every request save and brings back the parallel-request overwrite the `resave` option exists to avoid.

7. An overlapping request that still holds the old id will `Set-Cookie` that id if rolling is on, and `regenerate()`'s new id loses if that response is applied last. Today that unmodified response sends no `Set-Cookie`, so it cannot put the old id back. This is separate from the `resave` data race described in the README.

8. `onHeaders` calls `touch()` and then `setcookie` on the first write, and the `touched` flag stops `res.end` from touching again. A `res.write` before `regenerate()`, a `maxAge` change, or `res.end` (the slow-write case) commits the rolled cookie early; stamping expiry only at `res.end` after that flush leaves the browser on the pre-touch `Expires`.

9. For `cookie.secure` on a non-secure request, `onHeaders` returns before `setcookie` (`should not set-cookie when insecure`) while `res.end` still updates the store. Rolling that HTTP response either sends `connect.sid` in cleartext or extends the store while the HTTPS cookie's `Expires` stays put. `secure: 'auto'` and `sameSite: 'auto'` run only in `store.generate`, so a rolled `Set-Cookie` repeats `cookie.data` from the store, not a new result of a `cookie` function.

10. The `expires` setter sets `originalMaxAge` from the `maxAge` getter (`expires - Date.now()`). `resetMaxAge` assigns that back through `maxAge`, which builds a new `Date` and can store a smaller value (the tests allow 1999 versus 2000). `createSession` restores `originalMaxAge` after `new Cookie` because that setter clobbers it; the touch/save path persists the clobber, so every rolled request ratchets the window down.

11. Nothing sets `Cache-Control` or `Vary`, and `setcookie` appends `Set-Cookie`. Rolling puts the signed id on responses that currently omit it, including matches under `cookie.path` (`rfcPathMatch`, so `/admin` matches `/admin/users` and not `/administrator`). A shared cache can replay one client's `connect.sid`, and subresource requests keep sliding `maxAge` so it never elapses while the page loads. Requests that fail the path check must not extend the session.
