Vou ler o código do repositório para apontar falhas concretas de multi-tenant em listas e itens, sem alterar nada.1. `ApplicationUser`, `IUser`, and `CurrentUser` only expose the identity user id and role claims, and `Users` calls `MapIdentityApi<ApplicationUser>()`, so a newly registered account has no company. A `TenantId` accepted from the command body can be set to another company, and storing the caller's user id instead means two people in the same company never see the same lists.

2. `UpdateTodoList`, `UpdateTodoItem`, `DeleteTodoItem`, and `UpdateTodoItemDetail` load the row with `FindAsync` on the shared integer id. EF Core ignores a global query filter inside `Find`/`FindAsync`, so a filter in `OnModelCreating` still lets another company's user update or delete that row. `DeleteTodoList` uses LINQ `Where`, so the same filter would hide the list there and the handlers would disagree.

3. `CreateTodoItem` writes `ListId` from the command without loading the list, and `UpdateTodoItemDetail` sets `entity.ListId = request.ListId` with no ownership check. The Angular and React detail editors already move an item by posting a new `listId`, so an item can be attached to or moved onto another company's list, and a `TenantId` stored on both entities can diverge. `TodoItemConfiguration` does not set delete behavior, so the required `ListId` foreign key cascades item deletes with the list and never checks the item's tenant.

4. `CreateTodoListCommandValidator` and `UpdateTodoListCommandValidator` reject a title when any `TodoList` already has it, and the seeder inserts "Tasks". Two companies then cannot use the same title, and the "'Title' must be unique" error reveals that some other company already has it. A unique index on `Title` alone collides across companies, and scoping only the LINQ check still lets two concurrent creates in one company both pass unless the index is `(TenantId, Title)`.

5. The only MediatR `[Authorize]` is on `GetTodosQuery`. Create, update, and delete commands skip `AuthorizationBehaviour`, and the endpoint groups only call `RequireAuthorization()`, which checks that some user is signed in. `GetTodos` then runs `ProjectTo<TodoListDto>` over every `TodoLists` row, so filtering that query alone still leaves every mutation keyed by the global `BaseEntity.Id`, which the create endpoints return in the `Location` URL.

6. `InitialiseDatabaseAsync` runs only in Development and calls `EnsureDeletedAsync` then `EnsureCreatedAsync`. There is no migration, `PendingModelChangesWarning` is ignored, and Aspire picks one shared SQLite, SQL Server, or PostgreSQL database. A required `TenantId` will not alter an existing non-development database, and the seeded "Tasks" list and its four items have no company. A nullable column puts that seed, plus every self-registered user with a null tenant, in one shared bucket. Seed runs with no `HttpContext`, and `AuditableEntityInterceptor` already stores a null `CreatedBy` in that case, so the same hook would store a null tenant.

7. `WebApiFactory` replaces `IUser` with a mock of `Id` and `Roles` only, and `TestApp.AddAsync`, `FindAsync`, and `CountAsync` use `ApplicationDbContext` directly. `GetTodosTests.ShouldReturnAllListsAndItems` expects the signed-in user to see every inserted list. Those tests stay green when the mock's tenant is null and every row shares that null, and `TestApp.FindAsync` uses `DbContext.FindAsync`, which also skips query filters.

8. The only role is the global `Roles.Administrator`, given to `administrator@localhost` by the seeder and checked in `AuthorizationBehaviour` with no company. Bypassing the tenant filter for that role shows every company's lists to that account. Applying the filter leaves the seeded admin in no tenant, so the seeded "Tasks" list is invisible to every user who does have a company.

9. `ClientApp/src/app/todo/todo.component.ts`, `ClientApp-React/src/components/Todo.jsx`, and their NSwag clients load one catalog from `getTodoLists()` and address every row by numeric id. The OpenAPI summary for that route still says it retrieves all todo lists. Putting the tenant id on the command body leaves it under the caller's control, and leaving the clients unchanged makes them render and move any row an unfiltered query still returns.
