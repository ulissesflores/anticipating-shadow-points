Vou ler o código de senha deste repositório para apontar falhas concretas da troca de hash sem reset.1. `PasswordHasher.Verify` treats a 64-byte `Hash` plus a 16-byte `Salt` as HMAC-SHA512 under the UTF-8 key `realworld`, and every other length as an ASP.NET Identity payload. A new digest that is 64 bytes, or that leaves the existing 16-byte salt in place, is checked with that HMAC and then either rejects the real password or accepts a password that happens to match the old construction.

2. Rows already exist in two forms: legacy HMAC (`UTF-8(password)` concatenated with the salt) and Identity PBKDF2-HMAC-SHA512 at 210,000 iterations, stored as the decoded v3 payload with `Salt` empty. Replacing the Identity hasher and special-casing only HMAC locks out every account that registered or already logged in under the current code, and no migration can rebuild those hashes because the plaintext is gone.

3. `Login` rewrites `Hash` and clears `Salt` only when verification returns `SuccessRehashNeeded`. Identity already returns that whenever the embedded iteration count is below `IterationCount`, so a new hasher that always reports rehash needed rewrites the hash on every login, while one that returns `Success` for old rows never upgrades them. `CreateTests` expects a freshly stored hash to verify as `Success`. Rewriting on `Failed`, or clearing `Salt` before the new hash is saved, makes the only remaining verifier unusable.

4. `Hash` stores `Convert.FromBase64String` of Identity's string, and `Verify` turns those bytes back with `Convert.ToBase64String`. Passing an Argon2 PHC string through `FromBase64String` throws `FormatException`, which `ErrorHandlingMiddleware` turns into HTTP 500. The transaction then rolls back, so every later login by a not-yet-upgraded user fails the same way. Storing the base64 text itself in the `Hash` blob double-encodes current Identity rows, and `VerifyHashedPassword` returns `Failed`.

5. `Login.Command` is not `IReadOnlyRequest`, so `DBContextTransactionPipelineBehavior` opens the transaction before `Verify`: `Serializable` on SQLite and `ReadCommitted` on SQL Server. The KDF runs synchronously inside `Task.FromResult` and ignores `CancellationToken`. A heavier function holds that transaction for a failed password too, and for a second hash when an upgrade is written. On deploy, every first login is a write. SQLite lock failures become HTTP 500 even when the password was correct. Unknown emails return 401 before any hash, so the slower function widens the timing gap on `POST /api/users/login`.

6. `Login` only rejects an empty password. `Create` and `Edit` also require length 8. Adding that minimum to login stops shorter existing passwords from reaching `Verify`, so those accounts can never take the upgrade path.

7. `Salt` is a required `BLOB` / `varbinary(max)` on two independent migration chains, and startup applies migrations by default. Dropping or nulling it makes `salt.Length` throw, or pushes 64-byte HMAC rows into the Identity verifier, which rejects them. `docs/database-migrations.md` leaves these columns unchanged because `Salt` is what legacy verification uses. Databases created with `EnsureCreated()` are not adopted automatically, so a new required column is missing there and login throws.

8. `Hash` ignores its `salt` argument, and `HashPassword` is invoked with the scoped `PasswordHasher` instance as the user, which Identity's hasher ignores. Keying the new digest with that salt argument breaks `Create`, the login upgrade, and `Edit`, which all pass an empty salt. Mixing the user argument into the hash binds it to a per-request object, so the next request fails verification. `LoginTests` saves a 16-byte `Guid` salt beside an Identity hash. Treating "salt length is 16" as legacy rejects that row and any upgrade that did not assign `Salt = []`.

9. Dormant HMAC accounts stay recoverable from a database copy because the key is the literal UTF-8 bytes of `realworld` in source, until that user logs in successfully. A SQL backfill cannot rehash them. After this change, the process that is running today also cannot verify the new format. The readme already warns that a rollback rejects upgraded hashes, so a rolling deploy or a rollback returns 401 for anyone who has logged in once since the release.
