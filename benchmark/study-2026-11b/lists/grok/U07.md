Vou ler o repositório para achar onde a API expõe IDs inteiros e o que quebra se eles virarem UUID sem cuidar dos clientes atuais.1. `GET`, `PUT`, and `DELETE` type the path as `id: int = Path(..., gt=0)`, so a UUID is rejected with 422 before `crud` runs, and the single `/{id}/` route cannot also be registered as a UUID. Switching that annotation so only UUIDs parse turns `/summaries/999/` from 404 `"Summary not found"` and `/summaries/0/` from the `greater_than` / `gt: 0` 422 (the bodies locked in `test_summaries.py` and `test_summaries_unit.py`) into a UUID-parse 422.

2. `POST` and `DELETE` serialize `id` with the hand-written `SummaryResponseSchema` (`id: int` and `url` only), while `GET`, `PUT`, and the list use `SummarySchema` from `pydantic_model_creator(TextSummary)`, whose `id` follows Tortoise’s implicit integer primary key. Changing only one of those two types makes that set of routes fail response validation with 500 while the others still emit integers.

3. `crud.post` inserts the row before `SummaryResponseSchema` checks the response, and `delete_summary` calls `crud.delete` before returning the pre-delete dict through that same schema. A UUID that still has to satisfy `id: int` becomes a 500 after the insert or delete has committed, and because `url` is not unique a retry of the failed create writes a second `textsummary` row.

4. `create_summary` feeds `crud.post`’s return value to `generate_summary`, which does `TextSummary.filter(id=summary_id).update(...)`. A zero-row update is success, so passing the public UUID while `id` is still the serial key (or the serial key while the column is already `uuid`) leaves `summary` as `""` after the 201, and that error is raised inside the background task, outside `add_exception_handlers=True`.

5. `TextSummary` never declares `id`; Tortoise adds an autoincrement integer primary key, and `crud.get`, `put`, `delete`, and `generate_summary` all filter that field. An extra non-primary-key UUID column is never looked up, and a `UUIDField` primary key with no stored default leaves `summary.id` as `None` after `save()`, so the 201 body and the background update both miss the row.

6. The applied column is `"id" SERIAL` in `migrations/models/0_20250421234125_init.py`. PostgreSQL will not cast that serial to `uuid`, `downgrade` is empty, and `CREATE TABLE IF NOT EXISTS` means editing this file does not change databases that already ran it. That migration also creates `aerich.id` as `SERIAL`, and with no `/v2` prefix the integers clients already stored from `POST /summaries/` stay valid only if a unique legacy column is backfilled before the serial key is dropped.

7. The running app uses `register_tortoise(..., generate_schemas=False)`, the tests use `generate_schemas=True` on `DATABASE_TEST_URL`, and `db.generate_schema()` imports `models.tortoise` rather than `app.models.tortoise`. `entrypoint.sh` only waits for Postgres, and `Dockerfile.prod` starts gunicorn with no `aerich upgrade` (`release.sh` only swaps the Heroku image), so an empty `web_test` can get a UUID primary key from the model while `web_dev` and production stay on the serial column and fail with an asyncpg type error.

8. Both suites call `PUT /summaries/1/` with an invalid URL and expect the 422 `detail` to be the URL-scheme message, which happens only because `1` passes `Path(gt=0)` and the body fails afterward. Once `1` is an invalid UUID, a client that still sends a stored integer together with a bad body gets a path `uuid_parsing` error in place of the body error it handles today.

9. On this unversioned `/summaries` API the JSON `id` is a number: `POST` returns `{"id": summary_id, "url": ...}`, `DELETE` echoes that pair, and `GET`/`PUT`/list return `id` from `.values()` under `SummarySchema`. Replacing that field with a UUID string breaks clients generated from the current OpenAPI integer (and `test_create_summary`’s exact `{"id": 1, ...}` body) even if the path still accepts the old integer, and a `GET` schema that drops or renames `id` no longer matches the `id` the client just received from `POST`.
