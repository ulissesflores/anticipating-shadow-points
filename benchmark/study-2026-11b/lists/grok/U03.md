Vou mapear o repositório e o fluxo atual de comentários para listar falhas concretas desta mudança.Não há papel de moderador hoje; vou ler modelos, rotas, auth e o ciclo de vida dos comentários.1. `users` has no role column, JWT `getJWTCustomClaims()` is empty, and `AuthServiceProvider` only maps a nonexistent `ModelPolicy`; putting `is_moderator`/`role` on `User::$fillable` lets any logged-in user grant it via `UserController@update`, which mass-assigns `$request->get('user')` while `UpdateUser` validates only profile fields.

2. `RegisterUser` is public and `DummyDataSeeder` creates 25 identical users with no staff flag, so after migrate/seed (including the Docker flow) every account is equal and there is no existing write path that can appoint the first moderator.

3. `CommentController@index` is `auth.api:optional` and returns `$article->comments()->get()` with no query constraint; hidden rows stay in the public RealWorld list unless filtered, and a global scope on `Comment` would also hide them from the author and from moderators because there is no `show` action to load one comment.

4. `destroy` hard-deletes (`$comment->delete()`, no `SoftDeletes`) and `DeleteComment` allows only `user_id == auth()->id()`; folding hide into that action lets the author erase the row (and any appeal) after a hide, and widening `authorize()` so moderators can call it lets them destroy evidence instead of hiding it.

5. `routes/api.php` registers comments as `only: index, store, destroy`, so a successful appeal has no existing update/unhide endpoint; copying `DeleteArticle`/`UpdateArticle` (`$article->user_id == auth()->id()`) would make the article owner the hider rather than a moderator.

6. The comments table only has `created_at`/`updated_at`, so a 7-day check on `created_at` closes appeals for old comments hidden today, while a check on `updated_at` resets whenever hide saves the model; `Console\Kernel::schedule` is empty and Docker only runs `artisan serve`, so a scheduled expiry command would never run.

7. `destroy(DeleteComment $request, $article, Comment $comment)` leaves `$article` untyped (the slug string, unused) and binds `Comment` by id only, so a hide or appeal under `/api/articles/{any-slug}/comments/{id}` mutates any comment regardless of article.

8. `CommentTransformer` always emits `body` plus author, and `Comment::$with = ['user']` always eager-loads that author; returning a hidden comment through the current transformer leaks the abusive text and profile, which `CommentTest::it_returns_all_the_comments_of_the_article` currently requires for every row.

9. The author has no way to learn of a hide in time to appeal: `User` is `Notifiable` with no notification classes, mail defaults to Mailgun SMTP, the queue driver is `sync` with no jobs, and the only GET is the public index, so after a hide they cannot obtain the comment id or remaining window from the API.

10. Both `comments.user_id` and `comments.article_id` are `onDelete('cascade')`, and `ArticleController@destroy` already hard-deletes the article, so deleting the article or the author’s user wipes hidden comments and any appeal rows keyed to them.

11. `Comment::$fillable` already includes `user_id`; adding hide/appeal columns there and following `ArticleController@update`’s `$model->update($request->get(...))` pattern lets the author unhide themselves or forge `hidden_at`/`appealed_at`.

12. The `api` middleware group is only `cors` + `bindings` (`throttle` is registered and unused), and `config/auth.php`’s `api` guard is the token driver rather than jwt-auth, so Gate/policy checks on the `api` guard can ignore the user that `auth.api` set, while unthrottled hide/appeal routes stay callable from any CORS origin.
