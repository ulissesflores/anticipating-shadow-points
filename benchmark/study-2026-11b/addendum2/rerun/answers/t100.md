# Plan: tenant isolation for to-do lists and items

I read the code only and edited nothing. The repo is the Clean Architecture .NET template with Angular and React clients.

## What I found

- **Entities:** `TodoList` and `TodoItem` (`src/Domain/Entities/`) inherit `BaseAuditableEntity`. Neither has any tenant concept.
- **Current user:** `IUser` exposes only `Id` and `Roles`. `Web/Services/CurrentUser.cs` reads them from claims.
- **Identity:** `ApplicationUser` is a bare `IdentityUser`. There is no company or tenant model.
- **Data access:** handlers use `IApplicationDbContext` directly. `GetTodos` reads `_context.TodoLists` with no filter. The item and list commands use `FindAsync(id)`, which would let a user reach another company's row by guessing an id.
- **Schema:** there are no migrations. `ApplicationDbContextInitialiser` runs `EnsureDeleted` and then `EnsureCreated`, so the schema is rebuilt on every start.
- **Tests:** functional tests log in through `TestApp.RunAsUserAsync`.

## Assumptions

1. A user belongs to exactly one tenant (company). Multi-tenant membership is out of scope.
2. The tenant comes from a `tenant_id` claim issued at login, never from client input.
3. The shared-database, shared-schema model is enough, with a `TenantId` column.
4. The database is disposable, so there are no production rows to backfill. The `EnsureDeleted` and `EnsureCreated` setup supports this. If production data exists, a migration and backfill step is needed.
5. Tenant creation and admin UI are out of scope. I'll seed two demo tenants.
6. `TenantId` is a `Guid`, in a new `Tenant` entity.

## Plan

1. **Domain.**
   - Add a `Tenant` entity (`Id`, `Name`).
   - Add an `ITenantScoped { Guid TenantId }` interface. Implement it on `TodoList` and `TodoItem`, with `TenantId` set once and never exposed on update commands.
   - Keep `TodoItem.TenantId` in step with its list's tenant.
2. **Application.**
   - Add `ITenantProvider { Guid? TenantId }` in `Common/Interfaces`, or extend `IUser`. I prefer a separate interface.
   - Handlers need no per-query filter if the global filter below is in place.
   - Create handlers get `TenantId` stamped automatically, not set per handler.
3. **Infrastructure.**
   - Add a `TenantId` column on `ApplicationUser`, a foreign key to `Tenant`, and a `tenant_id` claim, added through a claims principal factory in Identity.
   - In `ApplicationDbContext.OnModelCreating`, apply an EF global query filter to every `ITenantScoped` entity: `e.TenantId == _tenantProvider.TenantId`.
   - Inject `ITenantProvider` into the context.
   - Extend `AuditableEntityInterceptor`, or add a sibling interceptor, to stamp `TenantId` on Added entries. It should also throw if a Modified entry's `TenantId` changed, or if an Added entry has a different tenant than the current one.
   - Add indexes on `(TenantId, …)`.
   - Make `TodoItem` and `TodoList` configurations require `TenantId`.
   - Index `TodoItem` on `(TenantId, ListId)`.
4. **Web.**
   - Implement `ITenantProvider` over `HttpContext.User` and register it scoped.
   - Fail closed. An authenticated user with no tenant claim gets 403, and an unauthenticated request gets no data.
5. **Seed.**
   - Create two tenants, one user per tenant, and sample lists.
   - Seeding must bypass the filter with `IgnoreQueryFilters()` and set `TenantId` explicitly. The `Any()` check in `TrySeedAsync` would otherwise see nothing.
6. **Clients.**
   - No API contract change is needed, because the tenant is implicit. Regenerate the NSwag clients only if a DTO changes.
7. **Tests.**
   - Update `TestApp.RunAsUserAsync` to create or accept a tenant.
   - Add a cross-tenant suite. Tenant B must not be able to read, update, delete or add items to tenant A's list, and must get NotFound rather than Forbidden.
   - Add a test that a create stamps the caller's tenant.
   - Add a test that a missing tenant claim fails closed.
   - Update the existing functional tests for the new setup.

## Verification

- Run `dotnet build`, then `dotnet test` for the Domain, Application, Infrastructure and Functional projects.
- Run the app. Log in as the user in tenant A and the user in tenant B. Confirm each sees only their own lists, and that requesting the other tenant's list id returns 404.
- Check the generated SQL for the `TenantId` predicate on every query.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Filter bypass through `FindAsync` | The handlers use `FindAsync`, which can skip query filters if the entity is already tracked | Switch to `FirstOrDefaultAsync`, or add a cross-tenant test per handler |
| 2 | Tenant taken from client input | An id in a request body or header can be forged | Read it only from the signed claim |
| 3 | Missing tenant fails open | A null `TenantId` compared in a filter can match nothing, or in the wrong setup everything | Fail closed with a 403 and a test for the null case |
| 4 | `IgnoreQueryFilters` misuse | Seeding and admin code have to bypass the filter | Restrict its use to seeding and review every call |
| 5 | Item and list tenant drift | `TodoItem` has its own `TenantId` and `ListId`, so they can disagree | Stamp from the parent list and assert in the interceptor |
| 6 | Existing data has no tenant | The rebuild hides this in dev, but a real database would break | Use a backfill migration if production data exists |
| 7 | Stale claim after tenant change | Cookie claims persist until re-login | Short cookie lifetime, or re-validate against the user record |
| 8 | Test fixtures break | `TestApp` creates tenant-less users | Update the test helpers first |
| 9 | Cross-tenant leaks outside the filter | Domain events, logs and caches are not filtered | Review `LogTodoItemCompleted` and any caching |
| 10 | Tenant filter cost | Every query gains a predicate | Composite indexes on `TenantId` |

Riskiest: #1, because the id-based handlers can let a user reach another company's rows unless each one is tested for cross-tenant access.
