Here's the plan. Nothing in the repo was edited; the plan is written to `~/.../plans/replace-the-integer-ids-lovely-hanrahan.md`. The approach is to add a UUID next to the integer ID rather than swap one for the other, so every existing URL, status code and response body stays the same.

**Assumptions:**
- "Keep clients working" means existing URLs, status codes, 422 error bodies and response fields stay exactly the same. Removing the integer later is a separate breaking release that gets announced in advance.
- The integer `SERIAL` primary key stays as the internal key. A new `uuid` column becomes the public identifier, so the primary key never needs rewriting.
- The database is Postgres 17 (`project/db/Dockerfile`), so `gen_random_uuid()` is built in.
- Migrations are run by hand with aerich (`entrypoint.sh` doesn't run them).
- The API has no versioning, and no other table points at `textsummary`.

## Steps
1. **Model** (`app/models/tortoise.py`): add `uuid = fields.UUIDField(unique=True, default=uuid.uuid4)`. `SummarySchema` is generated from the model, so it picks up the new field automatically.
2. **Migration**: write a new aerich migration by hand. Don't trust the auto-generated one: it adds a NOT NULL column with no database default, which fails on existing rows. The column definition should be `ADD COLUMN uuid UUID NOT NULL DEFAULT gen_random_uuid()`, which also fills in existing rows. Add a unique index and a real `downgrade` that drops the column.
3. **Schemas** (`app/models/pydantic.py`): add `uuid: UUID` to `SummaryResponseSchema`. Keep `id: int` and mark it `deprecated`.
4. **CRUD** (`app/api/crud.py`): add new functions `get_by_uuid`, `put_by_uuid` and `delete_by_uuid`. Leave `get`, `put` and `delete` as they are, because the unit tests replace them by name.
5. **Routes** (`app/api/summaries.py`): add `/{summary_uuid:uuid}/` routes (GET, PUT, DELETE) using Starlette's built-in UUID path converter, registered **before** the existing `/{id}/` routes.
   - Anything that isn't a UUID falls through to the existing integer routes, which stay exactly as they are. That includes the exact 422 response for `/summaries/0/`, which a test checks.
   - A single `Union[int, UUID]` parameter would be simpler, but it changes the shape of that 422 error.
   - Mark the integer routes `deprecated` in the OpenAPI docs.
   - POST returns `{id, uuid, url}` plus a `Location: /summaries/{uuid}/` header.
6. **Background task** (`app/summarizer.py`): pass the UUID and look the row up by it.
7. **Tests**:
   - Mocks in `test_summaries_unit.py` must now return a `uuid`, because the response model will require it.
   - Add tests for the UUID routes: found, unknown UUID gives 404, and a malformed UUID falls back to the integer route.
   - Keep every existing integer-ID test unchanged; they are the compatibility check.
8. **Later, separate release**: remove the integer routes and the `id` field, or rename `uuid` to `id` under `/v2`, once logs show nobody uses the integers.

## Verification
- **Migration:** run `aerich upgrade` on a database that already has rows, and check each row gets its own non-null UUID.
- **Tests:** the full `pytest` suite should pass, with existing tests unchanged apart from the mocks that now need `uuid`.
- **Manual checks with curl:**
  - GET by integer and GET by UUID return the same record.
  - `/summaries/0/` and `/summaries/not-a-uuid/` still return the same 422 bodies as today.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Auto-generated migration fails on existing rows | aerich writes NOT NULL with no database default, and Tortoise's `uuid4` default only applies in Python | Write the migration by hand with `DEFAULT gen_random_uuid()` |
| 2 | Migration bugs never show up in tests | `conftest.py` builds the schema with `generate_schemas=True`, so pytest never runs migrations | Run `aerich upgrade` on a seeded copy of the database |
| 3 | UUID requests caught by the integer route | `/{id}/` is matched first and returns 422 for UUID strings | Register the `:uuid` routes before the `/{id}/` routes |
| 4 | Error responses change for old clients | A union-typed path parameter changes the 422 error fields that tests (and clients) check | Keep the integer routes as they are and add separate routes |
| 5 | Unit-test mocks break | The response model requires `uuid`, and the mocks return dicts without it | Add `uuid` to the mocks and keep the crud function names |
| 6 | Clients that parse `id` as an integer break | Changing what `id` holds would break typed clients | Add a new `uuid` field and leave `id` as an integer until a later release |
| 7 | IDs can still be guessed | The integer routes stay open, so IDs can still be enumerated | Log integer-route use, announce a cutoff date, then remove them |
| 8 | Background task updates the wrong row | `generate_summary` looks rows up by integer ID | Pass the UUID and look up by it, then test that path |
| 9 | Locking during the migration | Filling in UUIDs rewrites the whole table under a lock | Fine for this small table; on a large table, backfill in batches |

Riskiest: #1, the hand-written migration that fills in UUIDs for existing rows, because no test exercises it (#2).
