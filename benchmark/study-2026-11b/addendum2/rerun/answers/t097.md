This change is already on `master`. It came in with commit `a51468c` ("modernize (#152)"), so what's left is a short hardening follow-up rather than a rewrite. I didn't edit anything in the repo; the plan is saved in `plans/store-passwords-with-a-logical-kahn.md`.

## What's already in place
- **New hashes:** `src/Conduit/Infrastructure/Security/PasswordHasher.cs` uses ASP.NET Core Identity's `PasswordHasher` (PBKDF2-HMAC-SHA512, 210,000 iterations, random salt). The stored value records its own salt and iteration count.
- **Old hashes:** the old HMAC-SHA512 hashes (64-byte hash plus 16-byte salt) are still checked, using a constant-time comparison. A correct password returns `SuccessRehashNeeded`.
- **Upgrade on login:** `Features<home>` rehashes the password after a successful login and clears `Salt`. `Create.cs` and `Edit.cs` only ever write the new format.
- **No database change:** `Hash` and `Salt` are `varbinary(max)` (SQL Server) and BLOB (SQLite), and the new hash is 61 bytes, so no migration is needed.
- **Tests:** `PasswordHashingTests.cs` covers random salts, wrong passwords, and the upgrade on login.

## Assumptions
- Keep Identity's PBKDF2. Argon2 would add a package for little extra security.
- No forced resets. Users who never log in again keep their old hashes.
- The RealWorld API contract stays the same.

## Follow-up steps
1. **Even out login timing** (`Login.cs`): an unknown email currently returns 401 straight away, while a known one takes about 100 ms to check. That difference shows which emails are registered. Fix: when the email isn't found, still check the password against a fixed dummy hash.
2. **Make the rehash safe against a password change** (`Login.cs`): replace the plain save with a conditional `ExecuteUpdateAsync(... where PersonId == id && Hash == oldHash)`. A login's rehash then can't overwrite a password the user changed at the same moment. If the rehash fails, the login should still succeed.
3. **Optional, configurable iteration count:** read `PasswordHasherOptions.IterationCount` from config in `ServicesExtensions.cs`, defaulting to 210,000. Identity already flags hashes with fewer iterations for rehashing, so raising the number later upgrades users as they log in.
4. **Tests:**
   - A hash made with fewer iterations gets upgraded on login.
   - An old-format user can log in over HTTP and gets a 200 and a token.
   - Changing the password (Edit) after an old-format login stores the new format.
   - An unknown email still returns 401.
5. **Optional:** add a query to `docs/` that counts remaining old-format rows (`LENGTH(Hash)=64 AND LENGTH(Salt)=16`).

**Verification:** run `dotnet run --project build/build.csproj -- test` and `make test-hurl-with-managed-server`. Then add an old-format user to SQLite by hand, log in, and check that `Hash` is now 61 bytes and `Salt` is empty.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Login timing reveals which emails exist | Checking a known email now costs ~100 ms; an unknown one returns at once | Check against a dummy hash when the email isn't found |
| 2 | Rehash overwrites a new password | Login saves the whole tracked user, so the last save wins | Conditional update on the old `Hash` value |
| 3 | Old hashes stay forever for inactive users | Upgrades only happen on login | Track the count; optional reset campaign later |
| 4 | Old-format detection goes by byte length only | `64 && 16` is a guess from the stored shape | New hashes are 61 bytes so they can't match; add a test that locks this in |
| 5 | Higher CPU per login and signup | 210k iterations on every login and signup | Load-test; configurable iterations; rate limiting |
| 6 | Rollback breaks logins | The old code can't read the new format | Ship forward-only; don't roll back past #152 |
| 7 | Rehash write fails and blocks login | `SaveChangesAsync` error returns a 500 | Catch and log; still return the token |
| 8 | Weak old HMAC key | Fixed key `"realworld"`; a leaked database can be attacked offline until users upgrade | Upgrade quickly; consider resetting high-value accounts |

Riskiest: #2, a login rehash racing a password change can bring back the old password.
