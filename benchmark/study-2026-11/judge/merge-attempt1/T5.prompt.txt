Three reviewers independently listed ways a software change could go wrong.

Change request: Deploy new versions with zero downtime: run the database migrations automatically on every deploy and keep the site up while the new container starts.

Items (the letter is the reviewer):
A1. In app/entrypoint.sh, migrations are preceded by python manage.py flush --no-input; mistakenly copying or adapting this development logic into app/entrypoint.prod.sh will wipe the production PostgreSQL database on every deployment.
A2. Running python manage.py migrate automatically while the old web container is still serving traffic will crash the live application whenever a migration introduces backward-incompatible changes, such as renaming or dropping columns and tables.
A3. Placing python manage.py migrate inside app/entrypoint.prod.sh will cause concurrent migration race conditions and table lock deadlocks if multiple replicas of the web container are launched simultaneously during rollout.
A4. Migrations requiring ACCESS EXCLUSIVE table locks (such as adding non-null columns or altering constraints) will block concurrent read and write queries from the running web container, causing request timeouts on the live site.
A5. In nginx/nginx.conf, the upstream is hardcoded to server web:8000;, which Nginx resolves via Docker DNS only at startup; starting a new side-by-side container under a different name or IP will not receive traffic without dynamic DNS re-resolution or an explicit Nginx reload.
A6. Neither app/Dockerfile.prod nor docker-compose.prod.yml defines container health checks; without readiness checks, incoming traffic will be routed to the new container while migrations are still executing or before Gunicorn has finished binding to port 8000, triggering 502 Bad Gateway errors.
A7. The web and nginx services share staticvolume at /home/app/web/staticfiles; running collectstatic for the new version while the old container is live will overwrite existing assets in place, causing cache mismatches and 404 errors for active user sessions.
A8. Standard docker-compose commands do not natively support zero-downtime rolling replacements; attempting to start a new web container alongside the existing one will fail due to container name and network alias conflicts unless a blue-green orchestration strategy is introduced.
A9. If an automatic database migration fails midway due to a constraint violation or invalid SQL, the deployment script may crash without an automated rollback strategy, leaving the database partially migrated and both container versions in a broken state.
A10. Running old and new Gunicorn worker processes simultaneously alongside active migration transactions against the single db container (postgres:15) risks exhausting PostgreSQL's maxconnections limit, rejecting live user connections.
A11. When the old web container is terminated after the new one is up, in-flight operations—such as image uploads processed by upload/views.py—will be abruptly severed if Docker does not allow Gunicorn sufficient graceful shutdown time.
B1. The entrypoint.sh script always runs python manage.py flush --no-input before migrations, which will delete all data on every container start, causing catastrophic data loss in production.
B2. Running python manage.py migrate on every deploy can lock database tables; if the existing (old) container is still handling requests, those locks will block reads/writes and produce intermittent downtime or request failures.
B3. With Docker‑Compose there is no rolling‑update or health‑check mechanism, so a new web container may be started before the previous one has finished serving traffic, leading to a brief period where both containers are operating on the same database schema version and may encounter incompatibilities.
B4. The migration step is triggered unconditionally for all environments (including docker-compose.prod.yml), so a failed migration in a staging or CI run will automatically bring down the production service when the same image is promoted.
B5. No database backup or snapshot is performed prior to migrations; if a migration script contains a destructive operation (e.g., dropping a column), there is no automated way to roll back, increasing the risk of irreversible schema changes.
B6. The dependson clause in docker-compose.prod.yml only guarantees container start order, not readiness; nginx may begin routing traffic to the web service before the migration has completed, causing 502/504 errors for users.
B7. Because the entrypoint runs migrations each time the container starts, scaling the service (e.g., multiple replicas) will cause concurrent migration attempts, resulting in race conditions and potential migration failures.
B8. The script uses a simple nc loop with no timeout to wait for PostgreSQL; if the database never becomes reachable, the container will hang indefinitely, preventing new deployments from completing.
B9. Static assets are mounted from a shared volume, but there is no collectstatic step in the entrypoint; new code that adds or modifies static files may not be served, breaking the UI after a zero‑downtime deploy.
B10. Environment variables for database connection (SQLHOST, SQLPORT, etc.) are read from .env.prod files that are not version‑controlled in the repo, making the migration step brittle and prone to failures when those files differ between environments.
B11. The docker-compose.prod.yml does not define any restart policy or graceful shutdown (stopgraceperiod), so when the old container is stopped for the zero‑downtime swap, in‑flight requests can be terminated abruptly.
B12. There is no explicit versioning or tagging of migration scripts; adding a new migration that depends on a later code change could cause the old container to crash after the database schema has already been upgraded.
C1. app/entrypoint.sh runs python manage.py flush --no-input before migrate. Reusing that script as the production boot path empties hellodjangoprod on every container start. app/entrypoint.prod.sh today only waits for Postgres.
C2. nginx/nginx.conf sets upstream hellodjango { server web:8000; } and proxypass http://hellodjango with no Docker DNS resolver. docker-compose -f docker-compose.prod.yml up -d --build gives the new web container a new IP while the already-running nginx keeps the old one, so port 1337 stays on 502 until the nginx container is recreated as well.
C3. Production is a single web service with no healthcheck, and dependson only waits until the container has been created. The documented up -d --build stops the old container before entrypoint.prod.sh finishes and before gunicorn hellodjango.wsgi:application --bind 0.0.0.0:8000 is listening. A deploy.updateconfig block in this Compose file is ignored outside Swarm.
C4. The entrypoint reaches exec "$@" only after the shell script returns, and the database wait is an unbounded nc -z $SQLHOST $SQLPORT that never checks that SQLUSER from .env.prod can log in. A migrate added there holds the new container off port 8000 for the whole migration, and a Postgres that accepts TCP but rejects the role leaves this container as the only upstream while gunicorn is still not running.
C5. entrypoint.prod.sh has no set -e, so a failed migrate still starts gunicorn against the migrations that already committed. Each Django migration is one Postgres transaction, but migration N+1 can fail after N is committed, and the compose service sets no image: tag, so --build overwrites the previous web image and leaves nothing to start when the new code and the half-applied schema disagree.
C6. Keeping the old container up means a second web replica, and both would run migrate on boot against hellodjangoprod. Those two runs can deadlock on the same CREATE or ALTER, or both write djangomigrations and then abort because the relation already exists, so neither replica reaches gunicorn.
C7. Every container shares one database. upload/migrations/ contains only init.py, and the production entrypoint has never applied migrations, so the first automated migrate builds the contrib auth, admin, and session tables under live /admin/ traffic. A later migration that drops, renames, or adds a NOT NULL column is applied while the previous container is still serving the old models.
C8. Nginx serves /static/ and /media/ from staticvolume and mediavolume, which outlive the web container, so a collectstatic in the same entrypoint as migrate rewrites or, with --clear, deletes files another container is still using. imageupload stores the upload on mediavolume via FileSystemStorage, and with no stopgraceperiod Docker’s 10s SIGKILL cuts gunicorn’s 30s graceful stop and leaves a partial file.
C9. The only migrations that run are the files Dockerfile.prod copies in with COPY . $APPHOME. migrate will not invent the missing upload migration, and a makemigrations in the entrypoint writes that file only in the container’s writable layer. The next recreate boots an image without it and hits InconsistentMigrationHistory against the rows already stored on postgresdata.
C10. db is in the same compose project, with no healthcheck, and POSTGRESPASSWORD from .env.prod.db is honored only when postgresdata is first created. Recreating db or changing that password leaves the old role password in the volume, migrate cannot authenticate, and the web entrypoint never reaches gunicorn. A deploy that uses down -v also deletes postgresdata, staticvolume, and mediavolume.
C11. settings.py falls back to a sqlite file at BASEDIR / "db.sqlite3" when SQLENGINE is unset, and both entrypoints run their database steps only when DATABASE=postgres. Dropping either variable from the env file migrates a sqlite file that disappears with the container, or skips migrate and boots gunicorn against an unmigrated hellodjangoprod.
