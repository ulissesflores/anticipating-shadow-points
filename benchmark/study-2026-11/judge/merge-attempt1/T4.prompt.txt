Three reviewers independently listed ways a software change could go wrong.

Change request: Make ky retry POST and PATCH requests by default when the network fails, so that flaky mobile connections stop failing.

Items (the letter is the reviewer):
A1. Adding post and patch to defaultRetryOptions.methods in source/utils/normalize.ts would cause Ky to retry on retry.statusCodes (such as 500, 502, 503, and 504) as well as network failures, violating the request to only retry when the network fails. This would re-execute failed server-side mutations for HTTP error responses that should have failed immediately.
A2. Because POST and PATCH are non-idempotent methods, retrying on a NetworkError introduces duplicate server-side side effects if the connection was interrupted after the server received and processed the initial mutation. Ky has no way of discerning whether a network failure occurred before the request reached the server or after the server began handling it.
A3. In source/core/Ky.ts, connection drops produce a NetworkError whereas request timeouts throw a TimeoutError, which is governed separately by retry.retryOnTimeout (defaulting to false). Flaky mobile connections frequently fail via timeouts, meaning the change would either fail to resolve mobile drops or, if retryOnTimeout is broadened, unsafely retry requests that the server is still actively executing.
A4. In source/core/Ky.ts, #fetch() calls this.request.clone() whenever retry.limit > 0, which invokes ReadableStream#tee() on streaming bodies. Enabling retries for POST and PATCH by default will force every streaming upload to buffer unconsumed chunks in memory, risking excessive memory consumption or out-of-memory crashes on resource-constrained mobile devices.
A5. If a POST or PATCH request body is a ReadableStream that was disturbed or locked during an interrupted initial attempt, Request.clone() in #fetch() will throw an unhandled TypeError on the retry attempt rather than recovering cleanly. This would cause flaky mobile requests to crash with native stream errors rather than surfacing a clean NetworkError.
A6. When using onUploadProgress, streamRequest in source/utils/body.ts pipes the request body through a progress-tracking transform stream. Retrying an interrupted POST or PATCH upload will cause progress events to restart from 0%, triggering confusing progress regressions or duplicate completion events in client UIs.
A7. Existing custom retry.shouldRetry hooks that return undefined rely on Ky falling through to default method checks that reject POST and PATCH. Enabling POST and PATCH retries by default would alter this fallback behavior, silently triggering retries for existing applications that expect undefined to reject non-idempotent requests.
A8. This change directly breaks existing test assertions in test/retry.ts—specifically tests like 'not on POST' and 'NetworkError is not retried for non-retriable method (POST)'—which enforce that POST requests fail fast without retrying. Changing this default represents a breaking change in Ky's core HTTP semantics for existing consumers.
A9. POST and PATCH mutations frequently carry headers such as Idempotency-Key or authorization nonces generated for a single attempt. Retrying automatically without re-running beforeRequest hooks or providing a mechanism to refresh request-specific tokens will cause backends to reject retried requests as duplicate or invalid submissions.
A10. Across heterogeneous mobile JS runtimes (such as React Native or older WebKit), calling Request.clone() on requests containing FormData or multipart bodies has known runtime bugs where boundaries or Content-Type headers are stripped. Retrying POST and PATCH requests by default exposes all multipart form submissions to these runtime cloning defects on every attempt.
B1. Non‑idempotent side effects – POST and PATCH usually modify server state; automatically retrying them can cause duplicate writes or unintended state changes if the original request actually succeeded but the client didn’t receive a response.
B2. Request body consumption – Ky streams request bodies (e.g., ReadableStream, FormData, file blobs). After a failed attempt the body may be exhausted, making a retry impossible or resulting in a corrupted payload.
B3. Hook interactions – Existing beforeRetry/afterResponse hooks may rely on the original request object; blindly retrying could bypass custom logic, mutate shared state, or invoke hooks multiple times unexpectedly.
B4. Timeout semantics – retryOnTimeout is currently false by default. Enabling retries for POST/PATCH may unintentionally retry when a timeout occurs after the server has started processing, again risking duplicate operations.
B5. Header side‑effects – Some APIs require one‑time authentication or nonce headers (e.g., CSRF tokens) that become invalid after the first attempt; automatic retries would send stale headers and trigger authentication failures.
B6. Back‑off and jitter defaults – The library’s default exponential back‑off may be too aggressive for mobile networks, leading to long delays or throttling; without tuning, retries could degrade the user experience.
B7. TypeScript typings – The retry.methods option currently excludes POST/PATCH by default. Changing defaults requires updating the MutableRetryOptions and related type definitions, else developers may see type errors or mismatched IntelliSense.
B8. Compatibility with existing retry config – Projects may already specify a custom retry object that omits methods. Overriding the default could unintentionally extend the retry set, breaking assumptions in tests or CI pipelines.
B9. Network‑error detection – Ky decides whether an error is “network” via isNetworkError. Certain mobile edge cases (e.g., DNS‑lookup failures) may be classified differently, causing inconsistent retry behavior for POST/PATCH versus GET.
B10. Memory‑leak risk – Repeated retries of large upload payloads without proper stream cancellation can accumulate buffered data, potentially exhausting memory on constrained mobile devices.
B11. Server‑side rate limiting – Automatic retries on POST/PATCH may repeatedly hit rate‑limit responses (429) and ignore afterStatusCodes handling, leading to rapid back‑off loops and possible bans.
B12. Testing coverage – The current test suite focuses on GET/DELETE retry paths; adding POST/PATCH retries may expose untested code paths, causing false‑positive test passes or hidden regressions.
C1. retry.methods is checked in #calculateRetryDelay before the error type, so adding post and patch to retryMethods in source/utils/normalize.ts also retries the default status codes 408, 413, 429, 500, 502, 503, and 504. The test not on POST currently requires a 500 to be sent once, and a 500 on POST often means the server already committed the write.
C2. Ky never sends an Idempotency-Key. isRawNetworkError only matches TypeError messages such as Failed to fetch, fetch failed, and terminated, which is the same signal when the socket dies before the POST is sent and after the server has already processed it, and the default limit of 2 means the body can go out three times.
C3. PATCH is not idempotent, and this repo already retries PUT and DELETE while leaving POST and PATCH out of retryMethods on purpose. Replaying a JSON Patch add or any other non-idempotent PATCH duplicates the change, so treating PATCH like PUT is unsafe.
C4. A stalled mobile connection hits the per-attempt timeout of 10000 ms and becomes a TimeoutError, which is not retried because retryOnTimeout defaults to false. A drop while .json() or .text() is reading is wrapped in NetworkError inside #raceBodyRead and thrown through #throwProcessedError, so it is also not retried. totalTimeout defaults to false, so turning those paths on would resend a POST the server may already have answered, with no overall deadline.
C5. isRawNetworkError treats every Chrome Failed to fetch and every Undici fetch failed or terminated as retriable, including CORS, CSP, mixed-content, and blocker failures, plus Chromium streaming uploads over HTTP/1.1, which source/types/options.ts documents as a network error even on plain HTTP. Those retries cannot succeed. The beforeRetry escape of clearing onUploadProgress runs only after the method is allowed, and it does nothing for a stream POST that failed without a progress handler.
C6. A throw inside onUploadProgress fails the upload stream and is documented as a NetworkError that is retried, with the callback running again. The sample call is ky.post, but the method check currently stops that, so once POST is retriable a buggy progress callback duplicates the upload instead of failing once.
C7. A retry resends the clone taken in #fetch with Request.clone() and tee(), then cancelBody() cancels the upload that just failed. The test that a network error resends a complete POST stream only covers an explicit methods: ['post'] list, and it reads the whole body before throwing. A drop while the tee source is still live can error the saved branch, so the next attempt throws a stream TypeError that is not a NetworkError and the original failure disappears. Large uploads are then held in memory and transmitted up to three times.
C8. fetch follows redirects inside a single attempt. A POST the server already accepted, answered with 301, 302, or 303, or followed with 307 or 308 onto a hop that then failed, is reported as a network error on the original request, and the retry sends that POST and its body to the original URL again.
C9. 408 is in the default statusCodes, and the readme says Chromium already retries 408 on keep-alive connections. POST is outside methods today, so it avoids that second replay. Adding it makes Ky and the browser both resend the POST. A 429 or 503 also uses retry-timing headers with maxRetryAfter of Infinity, so the cloned POST body can sit in memory for as long as Retry-After says.
C10. Callers who pass retry: 2 or {limit: n} do not pin methods. normalizeRetryOptions fills them from defaultRetryOptions, and methods: undefined is specified to reset to that same list. replaceOption(3) is tested as restoring the default where POST is not retried. All of those callers would start retrying POST and PATCH unless they pass an explicit methods array.
C11. shouldRetry and beforeRetry never run for a failing POST today, because the method check happens first. A shouldRetry that returns undefined to keep the default logic would start allowing POST status-code retries, and a beforeRetry that returns a new Request (used as-is, and unable to change retry.methods) can drop the body or mint a fresh idempotency header on each attempt.
