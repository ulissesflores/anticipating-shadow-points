Three reviewers independently listed ways a software change could go wrong.

Change request: Add soft delete for users: deleting a user hides the account but keeps their items, and an admin can restore it within 30 days.

Items (the letter is the reviewer):
A1. In backend/app/models.py, UserBase.email enforces a strict database-level unique constraint (Field(unique=True)). If a user is soft-deleted, their email remains in the table, meaning subsequent registration or signup attempts with that email will fail in crud.getuserbyemail or trigger an unhandled database IntegrityError.
A2. In backend/app/api/routes/users.py, the admin deleteuser endpoint explicitly executes statement = delete(Item).where(col(Item.ownerid) == userid) before deleting the user. If an engineer converts user deletion to a soft delete but overlooks this query, the user's items will still be permanently deleted, directly violating the requirement to preserve them.
A3. In backend/app/models.py and migration 1a31ce608336, Item.ownerid is defined with nullable=False and ondelete="CASCADE". If a soft-deleted user is eventually purged from the database after 30 days while keeping their items, PostgreSQL will cascade-delete those items anyway or throw a foreign key violation unless the column is made nullable or ownership is transferred.
A4. In backend/app/api/deps.py, getcurrentuser retrieves the user by primary key and only verifies if not user.isactive. If soft deletion is introduced with a new timestamp or boolean flag without deactivating the user or updating getcurrentuser, soft-deleted users with valid JWT tokens will remain authenticated until their tokens expire up to 8 days later.
A5. The codebase contains two deletion routes in backend/app/api/routes/users.py: admin deletion (deleteuser) and self-deletion (deleteuserme). If soft delete is implemented on only one endpoint, the other endpoint will continue performing hard deletes and wiping user records and items inconsistently.
A6. In backend/app/api/routes/users.py, the readusers endpoint executes unfiltered queries for both the total count (select(func.count()).selectfrom(User)) and the retrieved batch (select(User)). Without adding filtering for soft-deleted records, deleted accounts will continue to appear in the admin user list and distort pagination counts.
A7. Neither compose.yml nor the backend/ application defines any background task worker or scheduler (such as Celery, ARQ, or a cron runner). Without introducing infrastructure to periodically check and permanently purge accounts older than 30 days, expired accounts will remain in a soft-deleted state indefinitely.
A8. In backend/app/api/routes/login.py, recoverpassword fetches users using crud.getuserbyemail without filtering by deletion status. This allows soft-deleted users to request recovery emails and potentially reset their passwords to regain active access without admin intervention.
A9. There is currently no restore endpoint in the API or UI, and creating one without validation could allow admins to restore accounts beyond the 30-day cutoff or cause state conflicts if the email address was reused in the interim. It must also be defined whether restoring an account should reinstate isactive for users who were explicitly deactivated prior to deletion.
A10. Existing unit and integration tests in backend/tests/api/routes/testusers.py (such as testdeleteuserme and testdeleteusersuperuser) explicitly query the database after deletion to assert that result is None. Modifying deletion behavior without updating these assertions and adding test coverage for item retention and the 30-day restore window will break the test suite in CI.
A11. The frontend dialogs in frontend/src/components/Admin/DeleteUser.tsx and frontend/src/components/UserSettings/DeleteConfirmation.tsx display hardcoded warning text stating that items will be permanently deleted and cannot be undone. Without updating these descriptions, updating the TypeScript client via openapi-ts, and adding a restore action in UserActionsMenu.tsx, the admin UI will provide no mechanism to restore users and will show contradictory warnings.
B1. isactive flag overload – the UserBase model already defines isactive, which is used for account activation/login; repurposing it for soft‑delete may break existing authentication checks that treat a non‑active user as never‑registered.
B2. Cascade delete on items – User.items is defined with cascadedelete=True and Item.ownerid uses ondelete="CASCADE". If a soft‑delete implementation mistakenly performs a hard DELETE, all related Item rows will be removed, contradicting the requirement to keep a user's items.
B3. Missing deletedat timestamp – without a dedicated deletedat column, restoring a user within 30 days is ambiguous (the system cannot tell whether a user was soft‑deleted or simply never activated), and the purge job cannot reliably identify records to delete after the retention window.
B4. Authentication bypass – crud.authenticate fetches the user by email and returns it if the password verifies, but it does not check whether the user has been soft‑deleted. A deleted account could still obtain a valid JWT and access protected resources.
B5. Admin permission enforcement – the current API routes (backend/app/api/routes/users.py) lack an explicit “restore user” endpoint and do not verify that the requester has admin privileges, risking unauthorized restoration or accidental deletion of other accounts.
B6. Unique‑email conflict on restore – if a soft‑deleted user’s email is reused by a new account, restoring the original record would violate the unique=True constraint on User.email, causing a database error and potentially orphaning the original user's items.
B7. Query filters not updated – many list‑or‑detail endpoints (GET /users, GET /items) query User or join on User without filtering isactive/deletedat. After soft‑delete, stale endpoints could still expose hidden users or silently skip them, leading to inconsistent UI behavior.
B8. Background purge reliability – implementing a scheduled job to permanently delete users after 30 days must handle time‑zones and clock drift; using datetime.now(UTC) without proper truncation may cause records to be removed earlier or later than intended.
B9. Test suite breakage – existing tests (backend/tests/api/routes/testusers.py) assume hard deletion semantics (e.g., expecting items to be removed). Introducing soft‑delete will cause those tests to fail unless they are updated to assert that items remain.
B10. Database migrations – adding a deletedat column requires a new Alembic migration. Forgetting to mark the column as nullable or to set a default can block existing deployments or cause migration conflicts on production environments.
B11. Auditing and audit logs – the project currently does not log user deletion or restoration events. Without proper audit entries, compliance and debugging will be impossible, especially when an admin restores a user after the 30‑day window.
B12. Potential race condition on restore – if two admins attempt to restore the same soft‑deleted user simultaneously, the restoration code must be idempotent; otherwise, one admin could inadvertently reactivate a user that the other has already permanently purged, leading to data loss or duplicate entries.
C1. DELETE /users/{userid} runs delete(Item) for that ownerid before session.delete(user), and DELETE /users/me deletes only the user, which still removes items because User.items sets cascadedelete=True and migration 1a31ce608336 made item.ownerid ON DELETE CASCADE and NOT NULL. Soft-deleting through either call, or hard-purging the row after 30 days, destroys the items this change must keep, and the column cannot be nulled to detach them.
C2. User.email is unique=True, and crud.getuserbyemail is the lookup for POST /users/, POST /users/signup, PATCH /users/me, PATCH /users/{userid}, login, and password recovery. A hidden row keeps the address, so the same person cannot sign up again during the window, and rewriting the email to free the index makes a reset JWT (sub is the email, valid for EMAILRESETTOKENEXPIREHOURS = 48) apply to whoever owns that address next.
C3. isactive already blocks login, getcurrentuser, and resetpassword, and the admin Edit User form toggles it on its own. Using isactive=False as the delete mark makes a manually deactivated account identical to a deleted one, and the existing PATCH /users/{userid} (UserUpdate carries isactive, password, email, and issuperuser) turns the account back on with no 30-day check.
C4. Access tokens last 8 days (ACCESSTOKENEXPIREMINUTES), store only sub = user id, and sit in localStorage. getcurrentuser loads by id and only rejects isactive=False, and authenticate has no deletion check, so a hidden user keeps calling /users/me and /items and can obtain a fresh token until something on those paths reads a deletion timestamp.
C5. POST /password-recovery/{email} sends a reset mail whenever getuserbyemail finds a row and never looks at isactive. POST /reset-password/ only rejects an inactive user, so a hidden account can set a new password and log back in for the whole 30 days.
C6. Nothing in this process expires rows: prestart migrates, and initdb only inserts FIRSTSUPERUSER when that email is absent. The 30-day limit has to be a deletedat compared in UTC (same DateTime(timezone=True) as createdat from migration fe56fa70289e) on the restore handler, or hidden rows and their emails stay forever.
C7. GET /users/ counts and lists every User (skip/limit 100, ordered by createdat) with a separate count query, and the admin table (columns.tsx, UserActionsMenu) only offers Edit and Delete. Filtering deleted users out of that list removes the only screen an admin could restore from; leaving them in means the account is not hidden. UserPublic has no deletion field, and frontend/src/client will not grow a restore call until scripts/generate-client.sh is rerun.
C8. initdb looks up settings.FIRSTSUPERUSER by email and skips creation when the row exists. Another superuser can hide that account (DELETE /users/{userid} only blocks user == currentuser), after which startup will not recreate it and login fails, so nobody left can restore accounts.
C9. A superuser's GET /items/ returns every item, and PUT/DELETE /items/{id} do not care that the owner is hidden. The items screen shows title and description, not the owner's email, so the kept items stay editable and deletable during the 30 days and cannot be tied back to the hidden account.
C10. testdeleteuserme and testdeleteusersuperuser assert the User row is None, and Playwright admin.spec.ts asserts the email row disappears after "The user was deleted successfully". Code that satisfies those tests still hard-deletes, and DeleteUser.tsx plus DeleteConfirmation.tsx tell the operator that items are permanently deleted and cannot be undone.
C11. In development, POST /private/users/ inserts a User with no email-exists check, and Playwright's createUser uses that route. A soft-deleted email hits the unique constraint as an unhandled integrity error instead of the 400 returned by POST /users/signup.
