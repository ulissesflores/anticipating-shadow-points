Three reviewers independently listed ways a software change could go wrong.

Change request: Allow an article to have several co-authors, while keeping existing article URLs and API responses working for current clients.

Items (the letter is the reviewer):
A1. In src/app/routes/article/article.mapper.ts, articleMapper explicitly formats author: authorMapper(article.author, id). If this is replaced with an authors array rather than retaining the singular author field, existing Conduit API clients expecting a single author object will break.
A2. In src/app/routes/article/article.service.ts, updateArticle generates newSlug as ${slugify(article.title)}-${id} using the authenticated user's ID. If a co-author edits the title, the slug will incorporate the co-author's ID instead of the original author's ID, mutating the slug and breaking existing article URLs.
A3. In src/app/routes/article/article.service.ts, updateArticle and deleteArticle enforce permissions via existingArticle.author.id !== id. Without careful refactoring, this logic will either reject legitimate co-authors with a 403 Forbidden error on updates or naively allow any co-author to permanently delete an article without the primary author's consent.
A4. In src/app/routes/article/article.service.ts, buildFindAllQuery filters by author using author: { AND: [{ username: { equals: query.author } }] }. If the underlying Prisma model transitions to multiple authors without updating this filter to inspect relation lists (e.g., authors: { some: ... }), querying GET /articles?author=:username will fail at runtime or omit co-authored articles.
A5. In src/prisma/schema.prisma, Article currently defines a scalar authorId Int foreign key referencing User. Replacing authorId with a many-to-many relation without a careful migration script to backfill existing records into the new join table will corrupt foreign keys or cause permanent loss of existing authorship data.
A6. In src/app/routes/article/article.service.ts, getFeed fetches articles matching author: { followedBy: { some: { id } } }. If this query is expanded to check multiple authors without applying distinct selection, users who follow more than one co-author of the same article will receive duplicate articles and corrupted pagination counts.
A7. In src/app/routes/tag/tag.service.ts, getTags queries articles: { some: { author: { OR: queries } } } to restrict tag counts to demo or user-accessible articles. Changing the author relation on Article without updating this nested relation filter will trigger a Prisma runtime validation failure and break the GET /tags endpoint.
A8. In src/app/routes/article/article.service.ts, favoriteArticle and unfavoriteArticle build response payloads directly using profileMapper(article.author, id) rather than articleMapper. Updating the Prisma include statements and response models only in articleMapper will cause runtime crashes during favorite/unfavorite operations due to referencing undefined article.author.
A9. In src/prisma/schema.prisma, Article.author specifies onDelete: Cascade, which purges the article if the author's user account is deleted. In a multi-author model, maintaining naive cascade deletion on author accounts could delete an article entirely when one co-author leaves or is removed, rather than simply disconnecting that co-author.
A10. In src/app/routes/article/article.service.ts, createArticle only connects a single author via the authenticated user's ID. Introducing co-authors in the creation payload without validating user existence, preventing duplicate IDs, or establishing an authorization/invitation mechanism could allow arbitrary author impersonation or unhandled database constraint exceptions.
B1. Prisma schema incompatibility – the current Article model likely contains a singular authorId foreign key; adding a many‑to‑many relationship requires a new join table and migration, which could break existing generated client code and cause compile‑time errors.
B2. API contract breakage – endpoints such as GET /articles/:slug and the article.model.ts DTO probably serialize a single author field; expanding to an array may cause TypeScript type errors and break consumers that still expect a single object.
B3. URL generation and uniqueness – article URLs may be built from the author’s username (e.g., /articles/:author/:slug); introducing multiple authors could produce duplicate URLs or require a redesign of the routing logic.
B4. Authorization checks – existing permission checks (author.id === req.user.id) will no longer be sufficient; they must be updated to verify that the requesting user is one of the co‑authors, otherwise unauthorized edits could be allowed or legitimate edits rejected.
B5. Database migration data loss – converting from a single authorId column to a join table needs a data migration script to copy existing author references; if omitted, existing articles could lose their author association.
B6. Validation and input parsing – request validation (e.g., in article.controller.ts or DTOs) currently validates a single authorId; adding an array requires new schema validation rules, and missing validation could let malformed payloads pass, resulting in runtime exceptions.
B7. Caching and CDN keys – any caching layer keyed by the author ID (e.g., Redis or HTTP cache) will become incorrect, potentially serving stale data or mixing content between co‑authors.
B8. Search and indexing – full‑text search or tag indexing may rely on a single author field; expanding to multiple authors may require re‑indexing and updates to the search queries to include all co‑authors.
B9. Existing unit/integration tests – many tests (e.g., article.service.test.ts) assume a single author object; they will fail or give false positives unless updated, which could hide regressions.
B10. OpenAPI/Swagger documentation – the generated OpenAPI spec currently describes author as an object; without updating the spec, API consumers will receive mismatched documentation and may generate incorrect client code.
B11. Performance impact on joins – retrieving articles now requires joining through a new many‑to‑many table; unoptimized queries could cause N+1 problems or slow responses, especially for list endpoints.
B12. Backward‑compatible response shape – legacy clients may crash if the author field changes from an object to an array; you need to decide whether to keep the original field for backward compatibility (e.g., primaryAuthor) or version the API.
C1. articleMapper and the favorite/unfavorite handlers both emit a single author profile (username, bio, image, following). Replacing that with an array, or renaming it, breaks every current list, slug, create, update, and favorite response; extra co-authors have to be added beside the existing object, which must stay the original primary author.
C2. favoriteArticle and unfavoriteArticle spread the raw Prisma row (id, authorId, favoritedBy) and then overwrite author with profileMapper, while list and slug routes go through articleMapper. Including co-authors without the same explicit select used today will leak password and email, and the two response shapes will diverge.
C3. The public URL is Article.slug, built as  ${slugify(title)}-${authenticatedUserId} , and updateArticle recomputes it with the caller’s id. A co-author title edit changes that suffix and the old GET/PUT/DELETE /articles/:slug 404s; dropping the user-id suffix instead makes two users’ identical titles hit the unique slug check and return 422 title must be unique.
C4. Update and delete authorize with existingArticle.author.id !== id. Once author is a list, that comparison throws or always returns 403, so today’s owners can no longer edit. Whether any co-author may update or delete must be decided separately from Comment.authorId, which is a different required foreign key and must stay a single commenter.
C5. buildFindAllQuery and getTags only return an article when its one author is demo: true or is the viewer, and ?author= is a username match on that same relation. Applying the demo check to any co-author either publishes a non-demo article as soon as a demo co-author is added, or hides a demo article when a non-demo co-author is added, and GET /articles?author=<primary username> stops matching the rows current clients already get.
C6. getFeed keeps only articles whose author.followedBy contains the viewer. Treating a followed co-author as enough changes /articles/feed for current clients; leaving the check on the primary only means followers of a co-author never see the article, and articlesCount will disagree with the list if the count query and the findMany query do not use the same predicate.
C7. authorId is NOT NULL with ON DELETE CASCADE in the initial migration, so deleting the primary user deletes the article and its comments. An implicit many-to-many like ArticleToTag has no order, so the profile emitted as author can change between requests, and repeating that migration’s drop-without-copy would wipe authorship. prisma migrate deploy runs only the SQL files, so a schema.prisma edit alone does not migrate existing rows or keep User.articles (UserArticles) pointing at a stable primary.
C8. Every article PUT calls disconnectArticlesTags and then reconnects tags only when tagList is a non-empty array. Copying that onto authors means a current client body of {title, description, body} removes the primary author. createArticle today connects only req.auth.user.id and ignores unknown fields, so a required co-author list would 422 those clients, and seed.ts (createArticle with just the creator id) would fail the same way.
C9. authorMapper and profileMapper call followedBy.some, and every article include selects followedBy on the single author. If author arrives as an array, or a co-author select omits followedBy, GET /articles, /articles/feed, GET /articles/:slug, create, and update all 500. Each profile’s following flag is per viewer, and the hand-built comment author objects are filtered by the commenter’s demo flag, not the article author.
C10. A missing username, a duplicate co-author, or the primary listed again surfaces as an unhandled Prisma error (P2025 / P2002). The handler in src/main.ts turns that into HTTP 500 err.message instead of the 422 { errors: ... } body that blank title, description, and body already use.
