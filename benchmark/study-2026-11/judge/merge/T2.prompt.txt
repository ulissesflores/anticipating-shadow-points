Three reviewers independently listed ways a software change could go wrong.

Change request: Send every user a weekly email digest of the new posts written by the people they follow.

Items (the letter is the reviewer):
A1. In app/models.py, User.followingposts() explicitly includes the user's own posts via Author.id == self.id; reusing this query directly will erroneously include the recipient's own posts in their digest.
A2. In app/email.py, sendemail() defaults to spawning a separate unmanaged background Thread for each email (sync=False); iterating over all users in a loop will launch hundreds or thousands of threads simultaneously, exhausting system memory and overwhelming the SMTP server.
A3. The codebase lacks a recurring task scheduler, as the infrastructure in Procfile and deployment/supervisor/microblog-tasks.conf only runs a standard rq worker for on-demand user tasks; without introducing a scheduler like rq-scheduler or cron, there is no mechanism to trigger the digest weekly.
A4. Generating absolute URLs for posts and profiles within email templates using urlfor(..., external=True) will fail or produce broken links in a background worker because SERVERNAME defaults to None in config.py and no HTTP request context is active.
A5. In app/models.py, the User model contains no fields for email notification preferences or opt-out tokens; sending unsolicited digests without an unsubscribe mechanism violates CAN-SPAM/GDPR regulations and requires a database migration to track preferences.
A6. Localization in app/init.py determines language via request.acceptlanguages inside getlocale(), which is unavailable inside background tasks; rendering localized email templates will fail or default arbitrarily without a stored user language preference.
A7. Reusing the post rendering pattern from app/templates/post.html will fail in emails because it relies on moment(post.timestamp).fromNow() and client-side JavaScript, which email clients do not execute.
A8. Iterating through all users and querying their followed authors' recent posts will produce an O(N) database query bottleneck that will exhaust database connections and exceed the default execution timeout of the single configured RQ worker.
A9. Filtering posts using a naive relative window like datetime.now(timezone.utc) - timedelta(days=7) without persisting a per-user lastdigestsent timestamp will cause posts to be duplicated or skipped whenever scheduled runs drift, fail, or are retried.
A10. If emails are sent synchronously (sync=True), a single SMTP failure or invalid email address will raise an unhandled exception that aborts the batch job midway, leaving the remaining users unprocessed without a retry tracking mechanism.
B1. Missing or incomplete email templates – The repository only contains exportposts email templates; there are no dedicated templates for a weekly digest, so rendering email/digest.html/.txt would fail at runtime.
B2. No scheduled job for weekly execution – The codebase uses RQ tasks (app/tasks.py) but lacks a cron‑style scheduler (e.g., Celery beat, APScheduler). Without adding a periodic task, the digest would never be sent.
B3. Potential N+1 query explosion – Retrieving “new posts written by people they follow” may require joining followers and posts tables per user; the current followingposts query is lazy and could cause many separate DB trips when iterating over all followers, leading to performance degradation on large networks.
B4. Timezone and date‑range mismatches – The Post.timestamp field is stored as UTC, but the digest must include only posts from the last week; failing to convert to the user’s local timezone could result in missing or duplicated entries.
B5. No user opt‑out or preference handling – The User model has no column for “emaildigestenabled”. Sending unsolicited weekly emails could violate privacy policies and trigger spam complaints.
B6. Email delivery limits and back‑pressure – Sending a digest to every active user could exceed SMTP provider limits; the current sendemail function does not implement rate‑limiting, retries, or bounce handling, risking dropped messages and a blocked mail server.
B7. Large attachment risk – If a user follows many active accounts, the generated JSON payload could become huge, exceeding typical email attachment size limits; the code currently attaches the entire posts list without size checks.
B8. Task progress tracking misuse – tasks.settaskprogress expects a Task entry per RQ job; the digest job would need its own Task record, otherwise the progress updates will raise AttributeError when task is None.
B9. Failure to handle empty result sets – When a user has no new posts, the digest generator must still send a meaningful email (or skip sending). The current export logic assumes at least one post and may raise a division‑by‑zero error in settaskprogress(100  i // totalposts).
B10. Missing ADMINS configuration for sender address – sendemail relies on app.config['ADMINS'][0] as the sender; if ADMINS is not defined in the config for the production environment, the email send will raise a KeyError.
B11. Concurrency race conditions on follower updates – While the digest job reads follower relationships, concurrent follow/unfollow actions could cause stale or missing posts in the digest unless the query is performed in a repeatable‑read transaction.
B12. No test coverage for the new feature – The repository’s tests.py does not include tests for scheduled email generation, so regressions (e.g., broken templates or query errors) could go unnoticed until production.
C1. User.followingposts() also returns the recipient's own posts: the filter is Follower.id == self.id OR Author.id == self.id, and testfollowposts expects that (John receives his own post; David, who follows nobody, still receives his). Dropping the groupby(Post) that collapses that self-join repeats each of those posts once per follower.
C2. Nothing here fires weekly. The installed rq is only a consumer (Procfile worker and deployment/supervisor/microblog-tasks.conf with numprocs=1), and app/cli.py only implements translate. Starting a scheduler inside createapp() runs it once per Gunicorn worker and again in the worker process, because app/tasks.py calls createapp() at import, so the same week is mailed more than once.
C3. User has no digest cursor. lastseen is overwritten on every authenticated request in beforerequest, and lastmessagereadtime tracks private messages. A rolling seven-day cutoff resends posts when the job overlaps or is retried, and skips posts when the single worker is down longer than the window. followers stores only the current edge, so a Friday follow includes that author's whole week and an unfollow before the job drops posts written while the follow existed.
C4. Post.timestamp is a timezone-naive DateTime filled with aware datetime.now(timezone.utc). Comparing those values, once read back from Postgres or SQLite, with an aware cutoff in the worker raises or puts boundary posts in the wrong week. No user timezone is stored, so the week boundary is only the server clock.
C5. A worker cannot render mail the way password reset does. getlocale() reads request.acceptlanguages, and User has no locale column, so () has neither a request nor a language (LANGUAGES is only en and es). urlfor(..., external=True) needs SERVERNAME, an optional env var that is empty outside a request. Running each body through app.translate.translate calls Microsoft once per post, calls () itself, and when MSTRANSLATORKEY is missing or post.language is '' (the LangDetectException path) returns the error sentence as the post text.
C6. sendemail defaults to a detached thread; only exportposts passes sync=True. An async send from an RQ job returns before SMTP finishes and dies with the job. A synchronous send for every user occupies the only worker, queued behind exportposts, which sleeps five seconds per post. RQ's default job timeout is 180 seconds, so a long digest is killed mid-loop. The sender is ADMINS[0], hardcoded to your-email@example.com, and MAILSERVER is optional, so the message raises or is rejected.
C7. Task.userid is required, and launchtask always enqueues app.tasks.{name} with that user id. The only dedupe is gettaskinprogress. exportposts sets progress to 100 in both except and finally, so a failed run is stored as complete and is not retried. With no per-recipient send record, a retry after a partial SMTP failure mails a second copy to everyone already sent.
C8. Posts are unlimited apart from Length(max=140), while the home page stops at POSTSPERPAGE (25). Paginating the digest the same way drops the rest. Loading every followed post in the worker's long-lived session never calls db.session.remove(), so the identity map grows for the life of the process. The default database is SQLite, and every page view commits lastseen, so a long digest write lock stalls the site.
C9. Addresses are never confirmed, and there is no opt-out. POST /api/users is unauthenticated, PUT /api/users/<id> can replace email with no verification, and the profile form does not edit email. The digest would send post bodies, which the app only shows behind loginrequired, to whatever inbox was typed. Message has the same body, timestamp, and author shape as Post, so a sweep of "activity from people I follow" would put private messages in the mail.
