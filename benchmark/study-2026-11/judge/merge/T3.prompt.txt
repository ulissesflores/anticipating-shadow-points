Three reviewers independently listed ways a software change could go wrong.

Change request: Let a user sign in with Google or with their password on the same account, linking the two by email address.

Items (the letter is the reviewer):
A1. In styleguideexample/blogexamples/googleloginserverflow/sdk/apis.py and raw/apis.py, the callback reads idtokendecoded["email"] without checking the emailverified claim. If an attacker registers an unverified Google account using a target's email address, automatic linking will grant unauthorized access to an existing password-authenticated account.
A2. GoogleAccessTokens.decodeidtoken in sdk/services.py and raw/service.py explicitly disables JWT verification with verifysignature: False and leaves GOOGLEAUTHPROVIDERCERTURL empty. Accepting forged or unverified ID tokens allows malicious actors to impersonate any user's email and compromise their account.
A3. When a user signs up via Google first, BaseUserManager.createuser assigns an unusable password via user.setunusablepassword(). Because UserCreateApi rejects existing emails and no password-setting or reset endpoints exist, that user will be permanently unable to set a password or authenticate through UserSessionLoginApi or UserJwtLoginApi.
A4. While UserJwtLoginApi and UserSessionLoginApi return JWT tokens and session keys respectively, GoogleLoginApi only calls login(request, user) and returns raw Google tokens without returning a session key or generating a JWT. Clients relying on JSONWebTokenAuthentication or SessionAsHeaderAuthentication via ApiAuthMixin will be unable to authenticate subsequent API requests after Google sign-in.
A5. GoogleLoginApi directly invokes Django's login(request, user) immediately upon finding a matching user, bypassing the isactive check that Django's authenticate() enforces during password logins. This allows inactive or deactivated accounts (isactive=False on BaseUser) to regain access simply by authenticating through Google.
A6. BaseUserManager.createuser normalizes emails with self.normalizeemail(email.lower()), but GoogleLoginApi filters with userlist(filters={"email": useremail}), which performs a case-sensitive exact match. If Google returns an email with differing capitalization, the lookup will fail to link the account, triggering unexpected 404 errors or duplicate registration attempts.
A7. Auto-provisioning missing accounts during Google login without atomic transactions or locking will race with concurrent password registrations (UserCreateApi) for the same email. This will crash the callback with an unhandled database IntegrityError due to the unique constraint on BaseUser.email.
A8. BaseUser links identity exclusively via the mutable email string and contains no field or model to track Google's immutable subject identifier (sub). If a user changes their primary email address in either service, account linking breaks or risks associating a recycled email with an unintended user.
A9. authlogout in styleguideexample/authentication/services.py invalidates JWT tokens by rotating user.jwtkey, but session logout only clears the Django session without touching the JWT key. Linking both authentication methods without a coordinated session and token revocation strategy means revoking access or logging out from one method leaves the other active.
A10. GoogleLoginApi logs in any matching user without checking administrative privileges or enforcing the two-factor authentication implemented in styleguideexample/customadmin/sites.py. A compromised Google account belonging to an admin (isadmin=True) could bypass admin 2FA verification entirely.
A11. Google OAuth logic is currently split between two separate sample packages (blogexamples/googleloginserverflow/sdk and raw) rather than integrated into styleguideexample/authentication/. Implementing linking across or between these demonstration modules without consolidating into a single domain service creates divergent, hard-to-maintain authentication flows.
B1. Duplicate accounts due to unverified email – Google OAuth may return an unverified email address; linking it directly to an existing password‑based account could let an attacker create a second login for the same address without proving ownership.
B2. Case‑sensitivity mismatch – BaseUserManager.createuser lower‑cases the email, but the OAuth payload may contain mixed‑case values; if linking logic compares case‑sensitively, the same email could be stored twice, violating the unique constraint.
B3. Race condition when linking accounts – Simultaneous sign‑in attempts (Google and password) could both create a new BaseUser record before the linking step runs, resulting in orphaned duplicate rows and broken session handling.
B4. Password‑less accounts breaking existing auth flow – Users created via Google will have setunusablepassword(); later attempts to log in with a password will always fail, and the API (UserSessionLoginApi) does not check for hasusablepassword(), leading to confusing “invalid credentials” responses.
B5. JWT key invalidation on logout – authlogout rotates jwtkey for any user; if a Google‑linked account logs out via the JWT endpoint while a session‑based login is still active, subsequent JWT‑based requests will be rejected, causing inconsistent logout behavior.
B6. Missing CSRF / state verification in OAuth flow – The repository currently has no OAuth view (googleloginserverflow only contains placeholder SDK files). Adding a Google sign‑in endpoint without proper state token handling could expose the flow to CSRF attacks or token replay.
B7. Inconsistent authentication back‑ends – The project mixes session‑based login (UserSessionLoginApi) and JWT (UserJwtLoginApi). Introducing Google OAuth without a unified backend may cause users to receive a JWT but still rely on session cookies, leading to “not authenticated” errors on protected endpoints.
B8. Data loss when merging profiles – Linking two accounts by email will likely require merging related data (e.g., UserProfile, 2FA settings). The current code has no migration or merge logic, so naive linking could overwrite or discard existing fields, violating GDPR‑style data integrity.
C1. Both Google callbacks identify the user from idtokendecoded["email"] after jwt.decode(..., options={"verifysignature": False}), and neither the raw nor the SDK flow checks emailverified, aud against GOOGLEOAUTH2CLIENTID, or iss. The userinfo payload is fetched and then ignored for identity, so an unverified or substituted email claim becomes the link to an existing BaseUser.
C2. UserCreateApi is open: DEFAULTAUTHENTICATIONCLASSES is empty, the view sets no permissions, and usercreate never confirms the address. The emails app is only an outbox. Anyone who POSTs /api/users/create/ with a victim's email owns that row, and a later Google sign-in that links on email enters the attacker's account while the attacker still has the password.
C3. The reverse path is the same hole. userupdate has an empty field list, so there is no way to add a password to a Google-created user. Changing UserCreateApi so that an existing email "links" by storing the posted password lets anyone who knows the address set that password.
C4. BaseUserManager.createuser stores normalizeemail(email.lower()), and testuserwithcapitalizedemailcannotbecreated treats the other casing as the same user via ValidationError from fullclean. The callbacks look up userlist(filters={"email": useremail}) through BaseUserFilter, which is an exact, case-sensitive match, so a mixed-case Google email misses the row and a follow-up usercreate lowercases it and raises instead of signing in. Inserting without createuser can store a second row, because the Postgres unique index is case-sensitive.
C5. BaseUser has no Google sub or other provider id, and email is the username. A Google account that changes its address misses the old row and usercreate inserts another user, or hits unique if that address is already taken. The password, jwtkey, UserTwoFactorAuthData one-to-one, File.uploadedby, and group permissions stay on the old row, and there is no merge path.
C6. usercreate with no password calls setunusablepassword(), which testuserwithoutpasswordiscreatedwithunusableone already locks in. UserSessionLoginApi and UserJwtLoginApi both use authenticate, so that user can never sign in with a password. Linking must not call setunusablepassword on a user who already has one, and AUTHPASSWORDVALIDATORS never run inside usercreate, so a new "set password" path can store a password the validators would reject.
C7. Password login goes through authenticate, so ModelBackend rejects isactive=False. Both Google callbacks call login(request, user) and never read isactive or UserTwoFactorAuthData. A deactivated account, including an isadmin user, gets a session that UserMeApi and the file APIs accept through ApiAuthMixin. The admin OTP check runs only inside AdminSite. Adding a second auth backend makes this login() call raise ValueError, because the queryset user has no .backend.
C8. The Google callbacks return idtokendecoded and userinfo. They do not return {session, data} or the JWT {token} and JWTAUTHCOOKIE that UserJwtLoginApi sets. ApiAuthMixin accepts a session cookie, Authorization: Session <key>, or a Bearer token signed with that user's jwtkey. A client that only keeps the JWT stays logged out, and a token minted with any other secret fails JSONWebTokenAuthentication. UserSessionLogoutApi does not rotate jwtkey, and authlogout does not clear the session, so one side stays signed in.
C9. The live routes are callback-raw in raw/apis.py and callback-sdk in sdk/apis.py. raw/views.py and sdk/views.py repeat the same email lookup and login() but are not on the urlconf. Linking in only one of the four copies leaves the others matching or creating accounts under different rules. Both redirect views also share the single session key googleoauth2state.
C10. The callbacks do a non-locking userlist and would then create. A concurrent POST /api/users/create/ for the same address can pass the same empty check. The loser gets ValidationError from fullclean, or IntegrityError if that check is skipped. The DRF handler turns the former into a 400 and the latter into a 500, and neither signs the winner in. ATOMICREQUESTS rolls the request back, so there is no retry onto the row that won.
C11. Exact matching on the Google email string treats jane.doe@gmail.com, janedoe@gmail.com, and plus-aliases as different people. Google delivers one mailbox for those. The link then splits one person across two BaseUser rows, each with its own password and jwtkey.
