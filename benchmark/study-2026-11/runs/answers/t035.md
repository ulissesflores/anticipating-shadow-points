## What the code does today

- **`BaseUser`** (`styleguide_example/users/models.py`) has a unique `email`. `create_user` lowercases the email and gives the user an unusable password when none is passed. There's no field recording whether an email has been verified, and nothing links a user to an outside login provider.
- **Password login** goes through `UserSessionLoginApi` and `UserJwtLoginApi` in `styleguide_example/authentication/apis.py`. Both use Django's standard `authenticate()`, which also rejects inactive users.
- **Google login exists only as a blog demo**, under `blog_examples/google_login_server_flow/{raw,sdk}`. It has several problems:
  - It decodes the Google ID token with `verify_signature: False`. It never checks `aud`, `iss` or `email_verified`.
  - It finds the user with an exact, case-sensitive email match (`user_list(filters={"email": ...})`).
  - It calls `login()` directly, so **inactive users can log in**.
  - It returns 404 if no user exists, and sends the decoded token and user info back to the client.
- Nothing stores Google's stable user ID (`sub`), so a user is matched only by email on every login.

## Ways this could go wrong

1. **Pre-account hijacking.** Password signup never checks that the person owns the email. An attacker signs up with the victim's address. The victim later signs in with Google, gets linked to that account, and the attacker's password still works.
2. **Unverified Google email.** Without checking `email_verified`, someone could take over an account using a Google identity for an email they don't own.
3. **Unchecked ID token.** Skipping the signature, `aud` and `iss` checks is fine for a demo. In a real login path it could accept a token issued for another app.
4. **Matching by email alone.** Users can change their Google email, and Workspace admins can reassign an address to someone else (for example, a former employee's). Logins can then land on the wrong account. After the first link, the stable `sub` should be the key.
5. **Case mismatch.** Stored emails are lowercased but the lookup is exact. `John@X.com` from Google won't match `john@x.com`, which leads to a failed login or a duplicate-account attempt.
6. **Inactive users** get past the Google path because it never goes through `authenticate()`.
7. **Google-first users can't use a password.** Their password is unusable, so password login always returns 400 unless they get a way to set one.
8. **Race on first login.** Two callbacks at once can both try to create the user or link, and one fails on a unique constraint (IntegrityError).
9. **Data leaks.** The demo returns the decoded token and user info to the client, and the error message reveals whether an email has an account.
10. **Mixing the demo with the real flow.** If the blog example is changed in place, the demo and production behaviour become tangled. The two existing demo flows (raw and sdk) would also drift apart.

## Assumptions

- This is the HackSoft Django Styleguide Example. The real feature goes in `authentication`/`users`, and the blog examples stay as they are, apart from reusing `GoogleSdkLoginFlowService`.
- Google sign-in uses the existing server-side flow and the existing `GOOGLE_OAUTH2_*` settings. It produces a session login, like `UserSessionLoginApi`.
- A Google login for an email with no account creates the account (sign-up through Google).
- Password signup has no email verification today. Existing users are treated as verified when the migration runs; that's an accepted legacy risk.
- `google-auth` is already installed as a dependency of `google_auth_oauthlib`, so `google.oauth2.id_token.verify_oauth2_token` can be used.

## Plan

**1. Data model** (`styleguide_example/users/models.py`, plus a new migration)
- Add a `UserIdentity(BaseModel)` model with: `user` (foreign key, cascade delete), `provider` (choices; `"google"` for now), `provider_uid` (Google's `sub`), and `email_at_link`. Make `(provider, provider_uid)` unique, and allow only one identity per user per provider.
- Add `BaseUser.email_verified_at` (a nullable datetime). The migration fills it in for existing users (see the assumption above).

**2. Selectors and services**
- Add `user_get_by_email(email)` in `users/selectors.py`, matching with `email__iexact` after lowercasing.
- In `authentication/services.py`, add `auth_google_verify_id_token(id_token) -> dict`. It uses `verify_oauth2_token` with `audience=settings.GOOGLE_OAUTH2_CLIENT_ID` and requires `email_verified is True`. Otherwise it raises `ApplicationError`.
- Add `auth_google_get_or_link_user(*, sub, email) -> BaseUser`, wrapped in `@transaction.atomic`:
  1. If a `UserIdentity` exists for this `sub`, use its user. Don't fall back to email.
  2. Otherwise, if a user has this email:
     - If their email is verified, link the identity.
     - If not, this is the pre-hijack case. Link the identity, call `set_unusable_password()`, rotate `jwt_key` with the existing `auth_logout`, and set `email_verified_at`. The legitimate owner can set a new password; whatever an attacker set is gone.
  3. Otherwise, create the user with `user_create(email=..., password=None)`, mark the email verified, and create the identity.
  4. Use `select_for_update` on the user. If an IntegrityError happens, re-read and return the existing link.
  5. If `not user.is_active`, raise `ApplicationError`.
- Add `auth_set_password(*, user, password)` using Django's password validators. If the user already has a usable password, require the current one.

**3. APIs** (`authentication/apis.py` and `authentication/urls.py`)
- Add `GoogleLoginRedirectApi` and `GoogleLoginCallbackApi` under `auth/google/`. Reuse `GoogleSdkLoginFlowService` (move it to `authentication/` or import it from the blog module) and keep the existing state/CSRF session check.
- The callback calls `get_tokens`, then `auth_google_verify_id_token`, then `auth_google_get_or_link_user`, then `login(request, user, backend=...)`. Call `request.session.cycle_key()` (`login()` already does this). It returns the same `{"session", "data": user_get_login_data(...)}` shape as the password login. It doesn't return tokens and doesn't reveal whether an email has an account.
- Add `UserSetPasswordApi` (requires login) under `auth/password/set/`, so Google-first users can then log in with a password.
- Optionally add `has_usable_password` and `providers` to `user_get_login_data`, so the frontend knows which options to offer.

**4. Leave alone**
- Password login stays unchanged. A Google-only user's unusable password already returns 400 correctly.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Pre-account hijack via email linking | Password signup never checks email ownership | On link to an unverified account: wipe the password, rotate `jwt_key`, mark verified |
| 2 | Linking on an unverified Google email | Demo never checks `email_verified` | Reject unless `email_verified is True` |
| 3 | Unchecked ID token accepted | Demo uses `verify_signature: False`, no `aud`/`iss` check | `verify_oauth2_token` with our client ID |
| 4 | Changed or reassigned email reaches wrong account | Matching is by email only; `sub` isn't stored | `UserIdentity` keyed on `sub`; check it first |
| 5 | Case mismatch causes duplicate or failed login | Stored email lowercased, lookup exact | Lowercase plus `iexact` lookup |
| 6 | Inactive users log in via Google | `login()` called without `authenticate()` | Check `is_active` in the service |
| 7 | Google-first users can't use a password | `create_user` sets an unusable password | Set-password endpoint with validators |
| 8 | Concurrent first logins collide | Unique email/identity, no locking | Atomic transaction, `select_for_update`, handle IntegrityError |
| 9 | Token or account-existence leak | Demo returns decoded token; 404 names the email | Return only login data; neutral errors |
| 10 | Existing users wrongly trusted as verified | Backfill marks all legacy users verified | Accept and document it, or backfill with null and require re-verification |

Riskiest: #1, pre-account hijacking when a Google sign-in is linked by email to a password account whose email was never verified.
