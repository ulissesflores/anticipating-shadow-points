## How retries decide today

- The default `retry.methods` list is `get put head delete options trace query` (`source/utils/normalize.ts:17`). POST and PATCH are left out on purpose, and there is a test for it (`test/retry.ts:3766`, "NetworkError is not retried for non-retriable method (POST)").
- The method check happens before any other retry check (`Ky.ts:703`). After it passes, a request is retried on a network error, on statuses 408/413/429/500/502/503/504, and on a timeout if `retryOnTimeout` is set.
- So adding `'post'` and `'patch'` to the default list would not mean "retry when the network fails". It would also retry every 500, 502, 503, 504 and 429 response.
- The readme already warns about this exact case (line 581): "a network error does not tell whether the server got the request."

## Ways this can go wrong

1. **Duplicate side effects.** A `NetworkError` can happen after the server already processed the request, for example when the connection drops before the response arrives. Retrying a POST can then charge a card twice or create a record twice. On mobile, where connections drop mid-response, this is the most common way the "network fails".
2. **Retrying more than network errors.** Because of the shared method check, a one-line change would also retry 5xx and 429 responses for POST and PATCH.
3. **It breaks existing users without warning.** This changes behaviour for everyone on the default, so it is a semver-major change, not part of the 2.2.x line.
4. **Users can't easily remove it.** Method lists are combined, not replaced, when you use `.extend()` (`test/retry.ts:1732`). A user who wants the old behaviour on an extended instance would need `replaceOption`.
5. **Some bodies can't be sent twice.** A `ReadableStream` body can only be read once, and upload-progress bodies are streamed. Existing tests at `test/retry.ts:1925–2006` cover this path, but making it the default exposes it far more often.
6. **Uploads run again.** `onUploadProgress` and `beforeRetry` hooks would now fire for POST and PATCH, and upload progress would restart from zero.
7. **Many existing tests and docs assume no POST retries** (`retry.ts:322`, `:3766`, `:1569`). They have to change on purpose, not be loosened to make them pass.
8. **Project rule on `null`.** `AGENTS.md` says `null` is never a valid value. Any new option must throw a clear error that names the option when given `null`, and must not quietly treat it as unset.

## Plan

I assumed you want this specific behaviour change and that a major version bump is acceptable. Given risk 1, my recommendation is to keep POST/PATCH retries opt-in rather than default. If it must be the default, make it as narrow as possible:

1. **Add a separate default for network errors only.** In `source/utils/normalize.ts`, add a new option, `retry.networkErrorMethods`, defaulting to `[...retryMethods, 'post', 'patch']`. Validate it the same way `methods` is validated (strings only, arrays only, reject `null` with a named error). Leave `methods` unchanged so POST and PATCH are still not retried on status codes or timeouts.
2. **Change the retry decision.** In `#calculateRetryDelay` (`source/core/Ky.ts:703`), use `networkErrorMethods` for the method check when the error is a `NetworkError`, and keep `methods` for everything else. Run `shouldRetry` after whichever check applies, as now.
3. **Skip retries that can't be replayed.** Don't retry a POST or PATCH by default when the body was a caller-supplied `ReadableStream`.
4. **Types and docs.** Add the option to `source/types/retry.ts`, `test-d`, and the readme `retry` section. Include a clear warning about duplicate requests and how to turn it off (`networkErrorMethods: replaceOption([...])`), and suggest sending an `Idempotency-Key` header from `beforeRequest`.
5. **Tests.** Update the tests that assert "no POST retry" so they cover status codes instead. Add tests showing that:
   - a POST/PATCH network error is retried;
   - a POST that gets a 500 or 429 is not retried;
   - a streamed POST body is not retried;
   - `extend` and `replaceOption` can turn it off;
   - passing `null` throws an error that names the option.
6. **Verify.** Run `npm test` (the full suite plus types). Then do a manual check with a server that drops the socket after reading a POST body, and confirm it is retried exactly `limit` times.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate writes (double charge or record) | `NetworkError` can't tell whether the server already processed the request; mobile drops often happen mid-response | Keep it opt-in, or document an `Idempotency-Key` recipe |
| 2 | POST also retried on 5xx and 429 | The single `methods` check gates every kind of retry (`Ky.ts:703`) | Separate `networkErrorMethods`; leave `methods` unchanged |
| 3 | Silent breaking change | It changes behaviour for every default user | Semver-major release with a release note |
| 4 | Hard to turn off | Method arrays are combined on `.extend()` | Document `replaceOption`; add a test for it |
| 5 | Stream bodies can't be replayed | A `ReadableStream` can only be read once | Skip the default retry for caller-supplied streams |
| 6 | Hooks and upload progress fire again | `beforeRetry` and `onUploadProgress` now run for writes | Document it; test the hook call counts |
| 7 | Tests changed just to make them pass | Several tests assert there is no POST retry | Rewrite them to cover status codes, not delete them |
| 8 | New option accepts `null` | `AGENTS.md` forbids `null` values | Throw an error that names `retry.networkErrorMethods` |
| 9 | Load spikes on servers | More write retries during outages | Keep `limit: 2` with backoff and optional jitter |

Riskiest: #1, because retrying POST/PATCH after a network error can repeat a write that has real consequences, such as a payment, and Ky can't detect when that happens.
