# Co-authors for articles: validated plan (ASP `--standard`, stopped after Phase 6)

I didn't edit any repo files. The plan is saved at `claude-home/plans/standard-allow-an-article-breezy-sundae.md`. The entry check passed. The repo is small, so I read the code myself instead of sending out research subagents. I skipped web research because a join table is the well-known pattern here. The repo has no record of past project lessons to consult.

## Assumptions (stated instead of asking)
- **The current `author` stays the owner.** In responses it stays a single profile object. Co-authors are extra users on top of it.
- **One new response field.** Article responses gain `coAuthors: Profile[]`, always present, `[]` by default and kept in a fixed order.
- **Input:** `article.coAuthors` is optional on POST and PUT.
  - If the key is missing on PUT, the list stays as it is.
  - Items can be usernames or `{username}` objects.
- **Permissions:**
  - Only the owner can change the co-author list or delete the article.
  - Co-authors can edit title, description, body and tags.
- **List endpoints don't change.** `?author=` and `/articles/feed` still match only the owner, so counts don't move for current clients. A new optional `?contributor=` filter matches the owner or a co-author.
- **URLs don't change.** The slug format `slugify(title)-<ownerId>` stays, and adding co-authors never changes a slug. Renaming the slug when the title changes already happens today and is out of scope.

## Main facts from the code
- **Slug bug that co-authors would expose:** `updateArticle` builds the new slug from the **caller's** id (`src/app/routes/article/article.service.ts:317`). That only works because today the caller is always the author. If a co-author renamed an article, its URL would end in their id.
- **Favorite responses leak data:** `favoriteArticle` and `unfavoriteArticle` return the raw database row (`article.service.ts:597-603`). That row includes `favoritedBy` user rows with password hashes. This leak already exists.
- **Repeated query block:** the same `include` block appears 7 times. Article visibility ("author is a demo user or me") is decided at `article.service.ts:8-67` and repeated in `tag.service.ts`.

## Validator result
An independent subagent saw only the plan and returned **REVISE** with 3 high-severity issues. All of them are fixed in revision 1:
- **Clients that send articles back would break.** Many Conduit clients PUT back the article they got from GET, which would now include `coAuthors`. Those edits would fail with 422 or 403. Fix: accept both input shapes, and treat an unchanged list as no change.
- **The favorite-endpoint leak contradicted the no-password test.** The leak is now recorded as an accepted, existing issue for a follow-up, so the test is scoped to `coAuthors` and the endpoints that use the mapper.
- **Mock-based tests can't catch a wrong database select**, because the mock returns whatever it's given. Fix: assert on the arguments passed to the mock instead.

It also flagged two medium points, now recorded as risks:
- **Consent:** an owner can name any user as a co-author.
- **Tags get wiped:** a PUT without `tagList` clears the tags. This already happens today, and co-authors now inherit it.

Standard mode allows one validator round, so revision 1 has not been re-validated.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Clients that send articles back break | Many Conduit clients PUT back the GET body, which will now include `coAuthors` | Accept both input shapes; unchanged list = no change; test sending GET back as PUT |
| 2 | Co-author edit changes the URL | Slug is built from the caller's id (`:317`) | Build it from `authorId`; test |
| 3 | Password hashes leak through co-authors | Favorite endpoints return the raw row | Select only profile fields; map co-authors through `profileMapper` |
| 4 | Permissions too wide or too narrow | Every check today compares only `author.id` | `canEdit`/`isOwner` helpers; test each role |
| 5 | Article counts change for current clients | `?author=` and feed counts would include co-authored articles | Keep owner-only meaning; new `?contributor=` |
| 6 | Tests pass but real queries are wrong | Database is fully mocked | Assert on query arguments and the shared include |
| 7 | Migration isn't purely additive | It runs automatically at container start | Only creates a table; diff checked without a database; old code ignores the table |
| 8 | Partial co-author list after an error | Remove and re-add done as separate steps | Do both inside one `update` |
| 9 | Users named as co-authors without consent | Owner can add anyone | Accepted and documented; self-removal endpoint as follow-up |
| 10 | Co-author edit wipes tags | A PUT without `tagList` clears tags (`:335-343`) | Already happens today; documented, not changed |

Riskiest: #1, current clients sending the GET response back as a PUT. Once `coAuthors` appears in responses, those clients' content edits would fail unless the API ignores an unchanged co-author list.
