## Plan: soft delete for users with a 30-day admin restore

**Current behaviour:** both delete endpoints remove the user permanently. `DELETE /users/{id}` (`backend/app/api/routes/users.py:214`) also bulk-deletes the user's items. `DELETE /users/me` deletes the user, and the cascade setting on `User.items` and on `Item.owner_id` then deletes the items.

### Assumptions (stated, since I couldn't ask)
- A deleted user is marked with a new `User.deleted_at` field (a timezone-aware date, indexed). `is_active` stays a separate admin switch, so restoring puts the user back exactly as they were.
- Both the admin delete and self-delete (`/users/me`) become soft deletes. Superusers still can't delete themselves.
- A user's items are not changed when the user is deleted. Superusers still see those items in `GET /items/`.
- Email stays unique. A deleted user's email can't be used to sign up again until the account is purged, so a restore never collides with a new account.
- After 30 days, a purge job permanently deletes the user and their items, which matches what delete does today. The restore endpoint checks the 30 days itself, so it doesn't depend on when the purge last ran.
- The repo has no scheduler, so the purge is a standalone script run from cron or a one-off compose service.

### Steps
1. **Model and migration:** add `deleted_at` to `User` and to `UserPublic`. Add a new Alembic migration after `fe56fa70289e` that creates the nullable column and its index.
2. **Config:** add `USER_RESTORE_WINDOW_DAYS = 30` in `core/config.py`.
3. **`crud.py`:**
   - `get_user_by_email` gets an `include_deleted=False` parameter. The duplicate-email checks (signup, admin create, email changes) and `init_db` pass `True`.
   - `authenticate` rejects deleted users but keeps the dummy-hash path that protects against timing attacks.
   - Add `soft_delete_user`, `restore_user` and `purge_deleted_users`.
4. **`deps.get_current_user`:** a deleted user gets "User not found". This shuts out existing login tokens, which last 8 days.
5. **`login.py`:** password recovery sends no email for a deleted user, and reset-password rejects them with the same "Invalid token" message.
6. **`users.py`:**
   - Both DELETE endpoints do a soft delete, and the `delete(Item)` statement goes.
   - `GET /users/` gets a `?deleted=` filter, applied to both the list and the count.
   - Only superusers can fetch a deleted user by id.
   - Editing a deleted user returns 404.
   - New `POST /users/{id}/restore` for superusers: 404 if the user isn't deleted, 410 if the 30 days have passed.
7. **Purge script:** `app/purge_deleted_users.py`, following the pattern of `app/initial_data.py`, plus docs on how to schedule it.
8. **Frontend:**
   - Regenerate the API client.
   - Change the wording in `DeleteUser.tsx` to say the user can be restored within 30 days.
   - Add a "Deleted" view to the admin page with a Restore action in `UserActionsMenu.tsx`.

### Verification
- **`test_users.py`:**
  - After delete, the user is gone from the list, can't log in, and their old token fails, but their items are still in the database.
  - Restore within 30 days brings back login and items; after 30 days it returns 410.
  - A non-admin trying to restore gets 403.
  - Signing up with a deleted user's email is rejected.
- **`crud/test_user.py`:** the purge removes only users (and their items) past the 30 days.
- **`test_login.py`:** password recovery and reset for deleted users.
- **Commands:** run `alembic upgrade head` and `downgrade -1`, `scripts/test.sh`, and the Playwright admin tests.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Some code path still lets a deleted user in | Users are loaded in about 12 places, e.g. `session.get(User, …)` in deps and routes and `get_user_by_email` in login and reset | Put the check in `crud` and `deps`; test each auth path |
| 2 | Old tokens keep working | Tokens last 8 days; `get_current_user` only checks `is_active` | Check `deleted_at` in `get_current_user` |
| 3 | Password reset brings a deleted account back | `reset_password` finds the user by email and sets a new password | Reject deleted users with the same "Invalid token" response |
| 4 | Email collisions on sign-up | `email` has a unique index; sign-up checks without filtering | Duplicate checks include deleted users; document the 30-day block |
| 5 | Data is never purged | There is no scheduler in the repo, so deleted users and items pile up (a privacy and GDPR issue) | Purge script, cron or compose job, a test, and docs |
| 6 | Purge removes items admins expect to keep | The cascade on `User.items` and `Item.owner_id` deletes items with the user | Agree on what happens to items after 30 days; purge in one transaction |
| 7 | User list counts are wrong | `read_users` counts and lists in two separate queries | Apply the same filter to both; add a test |
| 8 | The first superuser is soft-deleted, which can lock admins out | `init_db` won't recreate an email that still exists, and admins can delete other superusers | Block deleting the last active superuser |
| 9 | Timezone mistakes in the 30-day check | Mixing timezone-aware and naive dates breaks the comparison | Use timezone-aware UTC (`get_datetime_utc`) only; test the boundary |
| 10 | Frontend out of sync | The generated client and admin screens assume users are gone for good | Regenerate the client; add a Deleted view and Restore; update Playwright tests |

Riskiest: #1. If even one way of loading a user skips the `deleted_at` check, a "deleted" account can still log in, reset its password or use the API.
