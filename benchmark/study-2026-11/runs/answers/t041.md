I recommend against simply adding `post` and `patch` to the default retry methods. That change would retry them on server errors too, not just network failures. It could also repeat writes the server already received. I wrote a plan for a narrower change and edited no source files.

## What could go wrong
1. **One check covers every kind of retry.** The method check at `source/core/Ky.ts:703` runs before any retry decision. If `post`/`patch` go into the default list (`source/utils/normalize.ts:17`), they would also be retried on 408, 429, 5xx and timeouts.
2. **Ky can't tell whether the server got the request.** A network error looks the same whether the request never left or the response was lost on the way back (undici reports `terminated`, Safari `Load failed`). Mobile connections often drop after the server has already done the work, so retrying can mean double payments or duplicate records.
3. **PATCH isn't safe to repeat either.** Patches like "add to a list" or "increment" apply twice if retried.
4. **Some bodies can't be re-sent.** A `ReadableStream` body or a `Request` input's body can only be re-sent where request streams are supported (`Ky.ts:556`).
5. **Existing users' behaviour changes silently.** The `'not on POST'` test (`test/retry.ts:322`) and other tests depend on POST not retrying. Apps that wrote their own retry logic would now retry twice over: up to 3× the calls, more with `limit` raised.
6. **Hooks run more often.** `beforeRetry`, `shouldRetry` and the delay/jitter settings would now run for POST, so hooks that assumed GET-only retries may misbehave.
7. **The `null` rule.** Any new option must reject `null` with a clear error, not treat it as absent (AGENTS.md).

## Recommended plan
- Keep the default method list as it is.
- In `#calculateRetryDelay`, add one narrow case. Retry a POST or PATCH by default only when all of these hold:
  - the error is a network error (`isNetworkError`), not a timeout or HTTP status;
  - the request has an `Idempotency-Key` header;
  - the body can be re-sent.
- `shouldRetry`, `limit`, `totalTimeout`, delay and jitter still apply to these retries.
- Update the docs in `source/types/retry.ts`, `source/types/options.ts:186` and the `readme.md` retry section. They should explain the header rule and show how to opt in fully with `retry: {methods: [..., 'post', 'patch']}`.
- Tests:
  - POST without the key is still not retried.
  - POST with the key is retried on a network error and sends the same key and body each time.
  - POST with the key is not retried on a 500.
  - Same cases for PATCH, plus a streamed body (not retried).
  - `shouldRetry` returning `false` still stops the retry.
- Ship it as a major version, or a minor one since it only affects requests that set the header.

**Assumptions:**
- "Network fails" means errors that `isNetworkError` recognises, not timeouts or 5xx.
- Requiring the `Idempotency-Key` header is an acceptable meaning of "by default". If you want POST and PATCH retried with no conditions, it's a one-line default change plus docs, and you accept risk 2 below.

The plan is in `claude-home/plans/make-ky-retry-post-purrfect-cascade.md`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate writes (double charge or record) | A network error can come after the server already handled the request | Retry only when an `Idempotency-Key` header is present |
| 2 | Retries on 5xx, 429 and timeouts too | The method check covers every retry reason | Add a separate network-error-only case; don't touch `methods` |
| 3 | PATCH isn't safe to repeat | Patches that add or increment apply twice | Same header rule; say so in the docs |
| 4 | Streamed bodies can't be re-sent | Stream bodies only replay where request streams are supported | Don't retry non-replayable bodies |
| 5 | Existing behaviour changes silently | Tests and users rely on POST not retrying | Major version or header-only rule; changelog |
| 6 | Retries stack up | Apps with their own retry logic now retry twice over | Keep `limit` at 2; document how to turn it off |
| 7 | Hooks run where they didn't before | `beforeRetry`/`shouldRetry` assumed GET-only retries | Tests showing `shouldRetry` can still veto |
| 8 | `null` gets accepted by mistake | AGENTS.md forbids accepting `null` | Validate any new option as a boolean |

Riskiest: #1. Retrying a POST that the server already processed causes duplicate side effects, and Ky has no way to detect it.
