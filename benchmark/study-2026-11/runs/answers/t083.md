**What the repo does today.** This is the FastAPI + SQLModel full-stack template. Items are destroyed in three places:
- `DELETE /users/{id}` explicitly deletes the user's items, then the user (`backend/app/api/routes/users.py:221-233`).
- `DELETE /users/me` calls `session.delete`.
- The model cascades deletes to items (`cascade_delete=True`), and the database foreign key from items to users is `ON DELETE CASCADE`.

Logins issue 8-day tokens, and `get_current_user` (`backend/app/api/deps.py`) only checks `is_active`.

**Assumptions (no questions were asked):**
- Both delete paths become soft deletes.
- "Hidden" means the user can't log in, existing tokens stop working, they drop out of the user list and its count, and `GET`/`PATCH /users/{id}` return 404.
- Items stay unchanged under the same owner, and admins still see them.
- A deleted user's email stays reserved.
- A user can be restored while `now < deleted_at + 30 days`, set in config. After that, restore returns 410.
- An automatic purge is out of scope. The repo has no scheduler, and a hard delete would cascade-delete the items. I'm treating this as an accepted risk with a follow-up.
- There was no lessons store to consult and no web research.

**Plan (D01–D06), in order:**
1. **Model:** add a timezone-aware `deleted_at` column with a partial index, plus a retention-days setting.
2. **Migration:** `down_revision = "fe56fa70289e"`, which is the real head.
3. **Auth and lookups:** reject deleted users in login, token checks, password recovery, reset-password and the admin recovery-HTML endpoint. Deleted users get the generic "Incorrect email or password", with the password check still run so timing doesn't change.
4. **Endpoints:**
   - Delete becomes a conditional update that only touches rows not already deleted.
   - The user list excludes deleted users from both list and count.
   - New superuser-only `GET /users/deleted` and `POST /users/{id}/restore` (also a conditional update; 410 after the window).
   - The first superuser can't be deleted.
   - The `/private/users/` route gets an email-exists check.
5. **Tests:** update the existing delete tests, which currently assert the user row is gone. Add negative tests for each endpoint and for the window boundaries. There's no time-freezing library, so tests set `deleted_at` directly or pass `now` in.
6. **Frontend:** regenerate the API client, fix the "permanently deleted" dialog text, add a deleted-users tab with a Restore button, and update the admin Playwright test.

**Validation:** the independent validator returned REVISE with 11 issues, and all were taken into the revision. I checked the two high-severity ones against the code myself:
- The Alembic head is `fe56fa70289e`, not `1a31ce608336`. Getting this wrong would create two migration heads and break `alembic upgrade head` at startup.
- `/private/users/` inserts users with no email check, so a reserved email would cause a 500 error there.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Deleted user keeps access | Tokens last 8 days; `get_current_user` only checks `is_active` | Reject `deleted_at` in `get_current_user` and `authenticate`; test with a live token |
| 2 | Items still destroyed | Explicit item delete, ORM cascade and DB `ON DELETE CASCADE` all exist | Remove both delete calls; test that item count is unchanged |
| 3 | Deleted users leak through other endpoints | Many paths look users up by id or email (list count, by-id, update, recovery, reset) | Shared filter; a negative test per endpoint |
| 4 | Wrong migration parent | Head is `fe56fa70289e`, not the cascade revision | Set `down_revision`; check `alembic heads` shows one head |
| 5 | Timezone bug in the 30-day check | Model fields have no `sa_type`, so autogenerate makes a naive timestamp | `DateTime(timezone=True)`; timezone-aware UTC comparisons |
| 6 | Restore or delete race | Current delete reads then writes | Conditional updates with a rowcount check |
| 7 | Email locked forever | Email stays reserved and there's no purge | Accepted risk; the follow-up purge job anonymises the email |
| 8 | Retention/GDPR gap | Deleted accounts are kept forever; hard delete would cascade to items | Write down the decision; plan the purge and item-ownership policy |
| 9 | 500 on `/private/users/` | It inserts without checking the email | Add the email check, return 400 |
| 10 | Frontend misleads admins | Dialog says "permanently deleted"; API client is generated code | Regenerate the client, fix the text, update Playwright |

Riskiest: #1, a deleted user's existing 8-day token still working, because `get_current_user` only checks `is_active` and the account would stay fully usable after "deletion".
