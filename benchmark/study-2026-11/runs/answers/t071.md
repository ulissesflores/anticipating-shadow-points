I've planned the change but not built it; nothing in the repo was edited. One validator review found 12 issues, and all are folded into revision 1 of the plan. The plan is at `claude-home/plans/standard-let-a-user-linked-clock.md`.

## What the code does today
- **Password login works:** session and JWT endpoints in `styleguide_example/authentication/apis.py`.
- **Google login exists only as a blog example** (`blog_examples/google_login_server_flow/{raw,sdk}`), and it has four flaws:
  - it reads the Google ID token without checking its signature (`verify_signature=False`);
  - it ignores whether Google has verified the email;
  - it matches users by exact email;
  - it returns the raw token contents in the response.
- **Anyone can sign up with any email and a password** through `UserCreateApi`, and the email is never verified.
- **`BaseUser.is_staff` is a method, not a property.** So `user.is_staff` is always truthy, and any check written that way passes for every user.

## Assumptions (no one was available to ask)
1. A new `authentication/google/` area; the blog examples are left alone.
2. After the first sign-in, the account is tied to Google's permanent user ID (`sub`), not the email. Email is only used for the first match.
3. A Google sign-in with no matching account creates a user with no usable password.
4. A Google-only user can add a password later through a "set password" endpoint.
5. Both session and JWT sign-in work after Google.
6. Google is the only outside sign-in provider.

## Plan (revision 1)
| ID | Deliverable | Acceptance |
|---|---|---|
| D01 | `UserAuthIdentity` model (user, provider, `sub`); each Google ID maps to one user and each user has at most one Google ID; migration | Migration applies; a duplicate `sub` raises an error |
| D02 | Check the Google ID token properly (`verify_oauth2_token`: signature, audience, issuer, expiry), allow 10 s of clock difference, and require `email_verified` and the nonce | Tests reject a wrong audience, an expired token, an unverified email, and a missing or wrong nonce |
| D03 | Find the user: by `sub` first, then by email ignoring case. If the email matches an existing password account: link it, kill the old password, rotate the JWT key, end all the user's sessions, log it and email the user. New users are created. Refused: inactive users, admins/superusers, and a second Google account | Tests for each branch; the race test uses `TransactionTestCase` |
| D04 | Endpoints: Google redirect (with state, PKCE and nonce kept in the session), Google callback (session login or the existing JWT cookie; no token in the URL or body), and an authenticated "set password" (runs `validate_password` and `update_session_auth_hash`) | API tests; a session from before a link gets 403 on `/me/`; a Google session can't reach `/admin/` |
| D05 | Check the Google settings aren't empty and return a 503 if they are; add log events | `capture_logs` shows the event names and no token fields |

Gates: the `pytest` suite and `mypy` must pass. A manual test against real Google is useful but not required to ship.

## Validator round
The first round came back REVISE with 12 issues, all fixed. The biggest change was the linking rule. The draft asked the user to confirm the existing password before linking. But if an attacker had squatted the email, the real owner could never know that password and would be locked out for good, and the confirm step also allowed unlimited password guessing. Now the verified Google mailbox owner wins and the old password is killed. The validator also caught that rotating the JWT key does not end Django sessions, so sessions are now deleted explicitly. One thing is still unconfirmed: drf-jwt isn't installed here, so whether it has the token-creation helpers the plan relies on has to be checked when building.

## Main risks
| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Someone registers the victim's email first and keeps their password after the victim links Google | Public signup with no email verification | When a verified Google email links, kill the old password, end all sessions, rotate the JWT key, email the user |
| 2 | Fake Google identity accepted | The example reads the token without checking its signature | Use `verify_oauth2_token` with audience, issuer, expiry and nonce checks |
| 3 | Linking to an email Google hasn't verified | The example never checks `email_verified` | Refuse unless `email_verified` is true |
| 4 | Old sessions survive a link | Rotating the JWT key leaves Django sessions alive | Delete the user's sessions; test that an old cookie gets 403 |
| 5 | Admin accounts get in through Google without 2FA | `is_staff` is a method, so it is always truthy | Check `is_admin` and `is_superuser` explicitly and refuse them |
| 6 | Duplicate accounts or a missed match on email case | Google may send mixed case; the lookup is exact | Lowercase the same way as `create_user` and match ignoring case |
| 7 | Identity hijacked or lost after a Google email change | No Google ID (`sub`) is stored today | Look up by `sub` first; use email only for the first link |
| 8 | Two first sign-ins at the same moment | Nothing stops two link rows being created together | Atomic transaction with uniqueness rules; on a clash, read the row again |
| 9 | JWT leaks or the callback can be forged | The callback is a GET from a redirect; no PKCE or nonce yet | Send the token only in an HttpOnly cookie; keep PKCE and the nonce in the session |
| 10 | A real user loses their password when Google links | The fix for risk 1 kills the password | Email the user and let them set a new password |

Riskiest: #1. Anyone can register any email with a password and the email is never verified, so careless linking by email hands the account to whoever registered first.
