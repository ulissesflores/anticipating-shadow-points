## What exists today
- **Users:** `BaseUser` (`styleguide_example/users/models.py:49`) has a unique `email`. `create_user` lowercases the email and sets an unusable password when `password=None`.
- **Password login:** `UserSessionLoginApi` and `UserJwtLoginApi` (`styleguide_example/authentication/apis.py`) use `authenticate()`, which already rejects inactive users.
- **Google login:** there are two copies of the same flow, `blog_examples/google_login_server_flow/{raw,sdk}/apis.py`. Each looks the user up by exact email, returns 404 if no user exists, then calls `login()`. So email "linking" already happens implicitly, but it's unsafe:
  - it never checks `email_verified` or `is_active`;
  - it stores no Google identity (`sub`);
  - it decodes the ID token with `verify_signature: False`;
  - the email match is case-sensitive, so it misses users whose stored email is lowercased.
- **Signup:** `UserCreateApi` (`users/apis.py:63`) creates a password account for any email without verifying it. This is what makes linking by email dangerous.

## Assumptions (non-interactive)
1. The Google flow moves from `blog_examples` into the `authentication` app as the real login path. I'll base it on the SDK variant; the raw variant stays as a blog example.
2. Signing in with Google when no account exists creates one, with an unusable password.
3. There's no email-verification feature, so a password account's email counts as **unverified**. Google's `email_verified=true` is the only proof that someone owns an email address.
4. Only Google is in scope, but the link table is keyed by provider so others can be added later.
5. Once linked, an account stays linked to that Google identity even if the user later changes their Gmail address.

## Plan
1. **Model:** add `UserExternalIdentity(user FK, provider, subject, email_at_link, created_at)` in `users`, with a unique constraint on `(provider, subject)`. Add the migration.
2. **Case-insensitive email:** add a functional unique constraint on `Lower("email")` (plus a data check for existing case-duplicates before migrating). Add a selector `user_get_by_email(email)` that uses `email__iexact`.
3. **Verified ID token:** replace `decode_id_token` with `google.oauth2.id_token.verify_oauth2_token(token, Request(), audience=client_id)`. This checks the signature, `aud`, `iss` and `exp`. Reject the login unless `email_verified` is true.
4. **New service `auth_google_login(*, id_token_claims) -> BaseUser`** (`authentication/services.py`), run as `@transaction.atomic`:
   - **Known Google `sub`:** return the linked user. Never re-match by email.
   - **Unknown `sub`, but a user has the same verified email:** lock the row with `select_for_update`, then link. Linking must also clear any pre-existing password the account owner never proved they had: call `set_unusable_password()`, rotate `jwt_key` (reuse `auth_logout`), and flush that user's sessions. Optionally skip this if the account is already proven via a password login in the same session (it's a judgement call; the default is to reset).
   - **No user with that email:** create one with `user_create(email=..., password=None)` plus the identity row. Catch `IntegrityError` from concurrent first logins and retry the lookup.
   - **User is inactive:** raise `ApplicationError` and don't log them in.
5. **API:** add `GoogleLoginRedirectApi` and `GoogleLoginCallbackApi` in `authentication/apis.py`. Keep the session `state` check and add PKCE/nonce. Call the service, then `login(request, user)` (or issue a JWT, matching the existing pair). Stop returning raw token and claims in the response; return `user_get_login_data` instead. Wire them up in `authentication/urls.py`.
6. **Password for Google-only users:** they log in with Google and can add a password through a set-password flow, which needs a separate email-reset service (out of scope here). Note: `authenticate()` already fails safely for unusable passwords.
7. **Unlink:** add a service that refuses to remove the last way to log in (no usable password and only one identity left).
8. **Admin:** add an inline on `BaseUser` admin to view and revoke identities.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Pre-account hijack: an attacker signs up with the victim's email and a password, and the victim's later Google login links to that account | `UserCreateApi` never verifies emails, so the attacker keeps a working password | Reset password, rotate `jwt_key` and flush sessions on first link |
| 2 | Unverified Google email gets linked | The callback never checks `email_verified` | Hard-reject unless `email_verified` is true |
| 3 | Forged or replayed ID token | `jwt.decode(..., verify_signature=False)` | `verify_oauth2_token` with `aud`/`iss`/`exp`, plus nonce/PKCE |
| 4 | Email case mismatch causes missed links or duplicate accounts | Stored emails are lowercased, lookup is exact, uniqueness is case-sensitive | `iexact` lookup + `Lower(email)` unique constraint |
| 5 | Matching by email instead of `sub` | Google emails can change or be reassigned; the current code is email-only | Store `(provider, sub)`; email is only used for the first link |
| 6 | Deactivated users can still log in with Google | `login()` skips the `is_active` check that `authenticate()` does | Explicit `is_active` check in the service |
| 7 | Race on first Google login creates duplicates or a 500 | Two callbacks run at once, and there's no unique constraint on the identity | Unique `(provider, sub)`, atomic block, retry on `IntegrityError` |
| 8 | Google-only users get locked out after unlinking or losing Google access | They have an unusable password | Block removing the last login method; offer a set-password flow |
| 9 | Old sessions/JWTs survive a security-relevant link | JWTs are tied to `jwt_key` and sessions aren't cleared | Rotate `jwt_key` (`auth_logout`) and delete the user's sessions |
| 10 | Migration fails on existing case-duplicate emails | The new `Lower(email)` constraint conflicts with existing data | Run a pre-migration duplicate audit and merge script |

Riskiest: #1, pre-account hijack. Because signup never verifies email ownership, linking by email can give an attacker who pre-registered the victim's address a working password on the victim's account.
