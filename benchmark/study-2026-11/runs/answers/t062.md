## What could go wrong
1. **Nothing triggers the weekly send.** The worker library in use (`rq` 1.15) has no recurring scheduler. The `Procfile` and supervisor config only start a worker, and the Docker boot script (`boot.sh`) doesn't even start that.
2. **Duplicate or missed digests.** If cron runs twice, the job is retried, or a run is skipped, users get two emails or a gap. A fixed "last 7 days" window makes this worse.
3. **The wrong posts get included.** `User.following_posts()` (`app/models.py`) deliberately includes the user's own posts, so a digest built on it would list them.
4. **Time zone bugs at the window edges.** Post times are saved as timezone-aware UTC, but SQLite returns them without a time zone. Mixing the two can raise errors or shift the window, which is why the code calls `.replace(tzinfo=…)`.
5. **Templates break in the worker.** `get_locale()` reads `request`, which doesn't exist in a background job, so `_()` and `url_for` fail there. `SERVER_NAME` is unset by default, so `_external` links can't be built.
6. **Sending to everyone at once.** `send_email` without `sync=True` starts one thread per message. A single loop over all users means SMTP rate limits, long jobs and partial failures.
7. **Spam and privacy problems.** There is no opt-out or unsubscribe today. Unsolicited bulk mail can hurt how reliably the site's email gets delivered and may break CAN-SPAM/GDPR rules.
8. **Bad content in the email.** Post bodies are user-written. They have to be HTML-escaped, and posts from deleted or blocked authors shouldn't be sent.
9. **Database load.** One follow query per user, run across every user at once, can be slow on SQLite or Postgres.

## Assumptions
- A "new" post is one written since that user's last digest, or in the last 7 days on their first digest. The user's own posts are left out.
- Users with no new posts get no email.
- Everyone is opted in by default, with a setting on the profile page and an unsubscribe link in each email.
- The weekly trigger is a system cron job (or Heroku Scheduler) running a new `flask send-digests` command. No new libraries.

## Plan
1. **Database:** add two user fields, `digest_enabled` and `last_digest_sent`, plus a migration. Add `User.digest_posts(since, until)`. It works like `following_posts` but only includes people the user follows, never the user, only posts inside the window, and at most about 20 posts.
2. **Background job:** add `send_weekly_digest(user_id, since, until)` in `app/tasks.py`. It renders `email/digest.{txt,html}` with the language fixed to the user's, sends with `send_email(..., sync=True)`, and only then sets `last_digest_sent`. Errors are logged the same way `export_posts` does.
3. **Weekly command:** `flask send-digests [--dry-run]` in `app/cli.py` goes through opted-in users in batches. It skips anyone who already got a digest in the last 6 days and queues one job per user with a fixed ID like `digest-{user}-{week}`. That ID stops a second cron run from sending twice.
4. **Opt-out:** a checkbox on the edit-profile form, a signed unsubscribe link (same JWT approach as the password reset), and a `List-Unsubscribe` email header.
5. **Deployment:** set `SERVER_NAME` in the worker's environment, and document the cron entry for Procfile/Docker/supervisor setups.
6. **Testing:** add tests to `tests.py` for:
   - the window edges
   - own posts excluded
   - people the user doesn't follow excluded
   - no email when there's nothing new
   - opt-out respected
   - a second run sending nothing

   Then run end to end against a local `aiosmtpd` debug mail server.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Weekly send never runs | No scheduler in `rq` 1.15; Docker only starts gunicorn | `flask send-digests` from cron, documented per deployment |
| 2 | Duplicate digests | Cron overlap or retries; no record of what was sent | `last_digest_sent` guard + fixed job IDs |
| 3 | User's own posts in digest | `following_posts()` includes them | New query that excludes the user |
| 4 | Posts missed or repeated at window edges | Saved UTC times come back from SQLite without a time zone | Window from `last_digest_sent` → now, all in UTC |
| 5 | Worker crashes rendering templates | `get_locale` needs `request`; `SERVER_NAME` unset | Set the language explicitly in the job; require `SERVER_NAME` |
| 6 | Email provider throttling, half-finished runs | One-thread-per-email sending, one big loop | One queued job per user, `sync=True`, batches |
| 7 | Spam complaints, legal exposure | No opt-out exists | Opt-out setting, unsubscribe link and header |
| 8 | Unsafe content in emails | Post bodies are user-written | Escaping in HTML templates; limit posts per email |
| 9 | Database load spikes | One follow query per user | Batched loading, index on post time already exists |

Riskiest: #2, duplicate digests to every user, because a double cron run or a retried job emails everyone twice and that can't be undone.
