**What the code does today**
- **Signup:** `UserCreateApi` (`styleguide_example/users/apis.py`) is open to anyone and never checks that the user owns the email address.
- **Google callbacks:** both are live at `blog_examples/google_login_server_flow/{raw,sdk}/apis.py`. They read the ID token without checking its signature or `email_verified`, find the user by exact email match, and call `login()` without checking `is_active`. They also send the raw token claims back in the response.
- **Sessions and CSRF:** sessions are stored in the database (the default). `ApiAuthMixin` turns off the CSRF check (`api/mixins.py:53-75`).
- **Small trap:** `BaseUser.is_staff` is a method, so `if user.is_staff` is always true.
- **Rest of the repo:** there is no lessons file or CLAUDE.md, and no password reset or "set password" feature.

**Assumptions (no questions were asked in this run)**
1. Google sign-in uses sessions only; JWT login for Google is out of scope.
2. A Google account is identified by its `sub` claim, and email is used only for the first link. Linking happens automatically only when the token's signature checks out and Google is authoritative for the address: it ends in `@gmail.com`, or `email_verified` is true and the token has an `hd` (Workspace) claim.
3. Admin and superuser accounts are never linked automatically.
4. If nobody has that email yet, a new account is created with no usable password.
5. When Google links to an account whose email was never verified, that account's password is removed, which also logs out old sessions, and its `jwt_key` is rotated. The user sets a new password through a new endpoint that enforces CSRF.
6. The unsafe `raw` callback is taken out of the URLs. There is no unlink feature.

**Deliverables**
- **D01:** a `GoogleIdentity` model (unique `sub`) and a new `email_verified_at` field on the user, in migration `0004`.
- **D02:** the ID token is checked with `verify_oauth2_token`.
- **D03:** a new `auth_google_login` service that links accounts safely when two requests arrive at once.
- **D04:** the `sdk` callback uses the new service and the `raw` route is removed.
- **D05:** a "set password" API.
- **D06:** tests, written first: the attacker's old cookie, session header and JWT stop working after a link; unverified emails and admin accounts are refused; email case differences match; two simultaneous first logins don't create duplicates.
- **D07:** a README section explaining the flow and the trade-off below.

**What the validator changed**
- **`raw` route:** it is now removed from the URLs, not just commented as unsafe.
- **Logging out old sessions:** the plan relies on the password change instead of deleting session rows, which the database store can't do per user.
- **Admin check:** it uses `is_admin or is_superuser`, not `is_staff`.
- **Account creation:** it runs inside a nested transaction so a duplicate-key error can be recovered from.
- **Set-password endpoint:** it enforces CSRF.
- **Issuer check:** the extra hand-written check is dropped, since `verify_oauth2_token` already does it.
- **Email enumeration:** the plan now only claims to stop it on the Google callback; the user list and signup still reveal which emails exist.

**Trade-off you should decide on:** no existing user has a verified email yet. So a legitimate password user's password is removed the first time they sign in with Google, and the response says a new password is needed. The safer alternative is to ask for the existing password before linking, but that is not the "link by email" you asked for.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Account pre-hijacking (attacker's password survives the merge) | Signup is public and never verifies email | Remove the password on link; rotate `jwt_key`; password change logs out old sessions |
| 2 | `raw` callback bypasses all checks | It's routed and reads the token without checking it | Remove its route; test that it's gone |
| 3 | Forged ID token or wrong audience | `decode_id_token` doesn't check the signature | `verify_oauth2_token` with our client ID |
| 4 | Linking on an email Google can't vouch for | `email_verified` alone isn't enough outside Gmail and Workspace | Gmail or `hd` only; otherwise sign in with password first |
| 5 | Admin takeover through a compromised Google account | Admin rows match by email like anyone else's | Refuse auto-link for `is_admin` and `is_superuser` |
| 6 | Forged request sets a password | `ApiAuthMixin` skips CSRF | CSRF-checked session auth; recent Google sign-in required |
| 7 | Legitimate users lose their password | Every existing row counts as unverified | Response says a new password is needed; documented in README |
| 8 | Duplicate account or crash when two first logins race | Two callbacks for the same new user | Unique `sub`; nested transaction; re-read on duplicate error |
| 9 | Email case or lookalike mismatch | Stored email is lowercased, token email isn't | Same normalization, `iexact` lookup, then exact check in Python |
| 10 | Inactive user gets logged in | Callback calls `login()` directly | Check `is_active`; same generic error |

Riskiest: #1, account pre-hijacking. Anyone can sign up with someone else's email today, and linking by email would hand that account over to the attacker unless the link removes the old password.
