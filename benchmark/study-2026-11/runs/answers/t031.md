**Why the site goes down today:** `docker compose -f docker-compose.prod.yml up -d --build` stops the old `web` container before the new one is ready. On top of that, nginx looks up the address of `web` only once, at startup (`nginx/nginx.conf:1-3`). So once `web` is replaced, nginx keeps sending requests to an old address and users get 502 errors. Also, `app/entrypoint.prod.sh` never runs migrations, and nothing in prod runs `collectstatic`.

**Assumptions:**
- One Docker host using Compose v2, with no orchestrator.
- Deploys run from a script on that host, either by hand or from CI over SSH.
- Postgres and nginx stay up; only `web` is replaced.
- Old and new code briefly run side by side, so migrations must be backward compatible: add new columns first, remove old ones in a later release.

**Plan:**
1. **Migrations as a separate one-off job.** Add a `migrate` service to `docker-compose.prod.yml`. It uses the same image as `web` and runs `migrate --noinput && collectstatic --noinput`. It sits in a `tools` profile, so a normal `up` never starts it. The deploy script runs it once before any new web container starts. Migrations stay out of the web entrypoint so that two replicas can't race to migrate.
2. **Health checks.** Add a `/healthz/` view that runs `SELECT 1`, and a Docker health check that calls it with Python (the slim image has no curl). Add a `pg_isready` check to `db` and make `web` wait until it passes.
3. **Graceful shutdown.** Set gunicorn's `--graceful-timeout 25` and `stop_grace_period: 30s`, so in-flight requests finish before the old container stops.
4. **nginx follows container changes.** Point nginx at Docker's internal DNS (`resolver 127.0.0.11 valid=5s`) and route through a variable `proxy_pass`, so it finds new containers. Add `proxy_next_upstream error timeout http_502` so a failed request is retried on the other container.
5. **Static files that old and new versions can share.** Switch to `ManifestStaticFilesStorage`, which adds a content hash to each filename. Old and new files can then sit side by side in the shared `static_volume`. Never run `collectstatic --clear`.
6. **A `deploy.sh` script.** Steps in order:
   1. Build an image tagged with the git commit.
   2. Run the migrate job. If it fails, stop; the old version keeps serving.
   3. Start a second `web` alongside the old one.
   4. Wait until the new container is healthy; on timeout, remove it and exit with an error.
   5. Reload nginx.
   6. Stop the old container with a 30-second grace period, then go back to one `web`.
7. **Guards.** Cap how long a migration waits for a table lock (5 seconds) during the migrate job. Add `makemigrations --check` to CI so code never ships without its migrations. Update the README to use `./deploy.sh`, and explain the backward-compatible migration rule and how to roll back.

**Bug to fix first:** `DEBUG = bool(os.environ.get("DEBUG", 0))` is True even when `DEBUG=0`, because any non-empty string is True. That means **prod currently runs with DEBUG on**. It also changes how the hashed static-file setup behaves, so fix it first with `int(...)`.

**How to verify:** During a deploy, send steady requests to `/healthz/` and check that none return a non-2xx status. Then test three failure paths: a migration that fails, a migration that adds a nullable column while under load, and a new build whose health check fails. In each, the old version should keep serving.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Migration breaks the old code still running | Old and new containers share one DB during the overlap | Backward-compatible migrations only; drop columns a release later |
| 2 | Migration locks a table and requests hang | Postgres `ALTER TABLE` takes heavy locks | 5s lock timeout on the migrate job; deploy fails instead of hanging |
| 3 | nginx keeps the old container's address | The `upstream` block resolves `web` only once | Docker DNS resolver plus variable `proxy_pass`, plus `nginx -s reload` |
| 4 | Static files overwritten by the new version | Shared `static_volume` with unhashed filenames | Hashed filenames (`ManifestStaticFilesStorage`); never `--clear` |
| 5 | Prod already runs with DEBUG on | `bool("0")` is True | Fix with `int()` before switching static storage |
| 6 | Unhealthy new container gets traffic | No health check exists today | `/healthz/` check; script waits for healthy and removes the container on timeout |
| 7 | In-flight requests cut off | Old container killed too quickly | Graceful shutdown: gunicorn 25s, `stop_grace_period` 30s |
| 8 | Migration failed halfway | Postgres runs each migration in a transaction, but data migrations may not | Script aborts before rollout; take a DB backup before risky migrations |
| 9 | Rollback after a destructive migration | Changing the image tag doesn't undo schema changes | Add-only schema changes; separate cleanup releases |
| 10 | Running containers by hand bypasses the script | The README still documents the old `up --build` | Update the README; `migrate` stays in the `tools` profile |

Riskiest: #1. A migration that isn't backward compatible breaks the old container while it is still serving traffic, which causes the very downtime this change is meant to remove.
