**Assumptions** (you weren't asked, so these are my calls):
- Both admin delete and self-delete become soft deletes.
- Items stay as they are and are still visible to admins.
- The deleted user's email stays reserved, so nobody can sign up with it.
- After 30 days, restore returns 410 (Gone). There is **no** automatic purge job, because a purge would delete the items through the database link.
- Only admins can restore.
- The 30-day window is measured in UTC and set in config (`USER_RESTORE_WINDOW_DAYS`).

## Phases 2–4: risks, scope and plan
- **D01 Database migration:** add a nullable `user.deleted_at` timestamp with an index. Rolling the migration back is refused while any user is soft-deleted, so deleted users can't silently come back.
- **D02 Model:** add `deleted_at`, and remove the ORM setting that deletes items along with the user. After that, a hard delete of a user who has items raises an error instead of wiping their items, which acts as a safety net.
- **D03 Blocking deleted users:** they are rejected by token checks, login, password recovery, password reset and the admin HTML recovery page.
- **D04 Delete and restore logic:** `soft_delete_user` and `restore_user` use conditional updates, so a delete and a restore happening at the same moment can't clash. The 30-day cutoff is computed in one place in Python, and a user deleted exactly 30 days ago can still be restored. Email lookups are split in two: one that includes deleted users (for "email already taken" checks) and one that excludes them (for login and recovery).
- **D05 API:** both delete routes do a soft delete and leave items alone.
  - The user list leaves deleted users out of both the results and the total count; `?deleted=true` lists them.
  - New `POST /users/{id}/restore` returns 200, 404 if the user isn't deleted, or 410 if the window has passed.
  - Deleting the last active admin is blocked.
  - Deletes and restores are logged with who did them.
  - The local-only user-creation route now checks the email first.
- **D06 Frontend:** regenerate the API client, add a "Deleted users" admin view with Restore and days left, and fix the two delete dialogs that still say "permanently deleted".
- **D07 Tests:**
  - Rewrite the existing delete tests to check that the row and items survive.
  - Add login, token and recovery tests for deleted users.
  - Check the user count.
  - Test restore at 30 days minus 1 second, exactly 30 days, and 30 days plus 1 second.
  - Test that the hard-delete safety net raises.
  - Add a Playwright test for delete then restore.

## Phases 5–6: independent check
An independent reviewer, given only the plan, returned **REVISE** with 10 issues; I accepted all 10. The main ones:
- **No admin left:** nothing stopped deleting the last admin.
- **Startup setup:** `init_db` finds a deleted first admin, doesn't recreate it, and leaves it unable to log in.
- **Test helper:** `authentication_token_from_email` reuses deleted rows.
- **Two clocks:** the plan used the database clock in one place and the app clock in another.
- **Admin recovery page:** it wasn't covered.
- **Error on reserved email:** the local-only user-creation route crashed (500) on a reserved email instead of giving a clear 400.

Round 1 of the allowed 3 brought the plan in line with all ten issues. `--standard` runs only one review round, so the revised plan has not been re-checked.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Items still deleted | Three separate delete paths (route, ORM setting, database link) | Remove the route delete and the ORM setting; test that items survive |
| 2 | Deleted user keeps access | Tokens last 8 days; `get_current_user` only checks `is_active` | Reject `deleted_at` in `get_current_user`, login and password recovery |
| 3 | Password reset brings the account back | `reset_password` only checks `is_active` | Separate email lookup that excludes deleted users |
| 4 | No admin left | Only self-delete is blocked; `init_db` won't recreate a deleted first admin | Block deleting the last admin; warning in `init_db` |
| 5 | Wrong 30-day boundary | Mixing database and app clocks; timezone mistakes | One UTC cutoff helper; boundary tests |
| 6 | Rollback brings deleted users back | Dropping the column erases the deleted marker | Rollback refused while any user is soft-deleted |
| 7 | A later purge wipes items | The database link to the owner still deletes items | Purge out of scope; hard delete now raises; tests lock that in |
| 8 | Deleted users leak into lists | Count and paging are queried separately from the results | Filter both; tests check the count |
| 9 | Clash on reserved email | Email must be unique; the local-only route has no check | Email check first in every create path |
| 10 | Shared test user breaks other tests | Test helper reuses rows by email | Use random users; helper checks `deleted_at` |

Riskiest: #1. Items being deleted anyway, through the ORM setting or the database link to the owner, can't be undone, and it breaks the main promise of the feature.
