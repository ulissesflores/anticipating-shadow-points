## Why not just add `post` and `patch` to `retry.methods`
The method check at `source/core/Ky.ts:703` decides whether any retry can happen. If POST and PATCH were added to the default `retry.methods` (`source/utils/normalize.ts:17`), they would also be retried on 408/413/429/5xx responses, not just when the network fails. A 500 or 503 on a write often means the server already acted, so that would be worse than what you asked for.

## Plan
1. **New option `retry.networkErrorMethods`**, default `['post', 'patch']`, typed in `source/types/retry.ts`. These methods are retried **only** when the error is a `NetworkError`.
2. **Validation in `normalizeRetryOptions`:**
   - Add the key to the existing "must be an array" and "must only contain strings" checks, and normalise entries with `normalizeRetryMethod`.
   - Per AGENTS.md, `null` is not allowed: it throws an error that names `retry.networkErrorMethods` and is never treated as empty.
3. **Retry decision in `#calculateRetryDelay`:**
   - A method passes the method check if it is in `methods` or in `networkErrorMethods`.
   - For a method that is only in `networkErrorMethods`, any error that isn't a network error is thrown before `shouldRetry` is called.
   - `shouldRetry` can still block a retry by returning `false`, but returning `true` can't extend these methods to HTTP errors or timeouts.
   - Forced retries (`ky.retry()`) work as before.
4. **Merge:** no code change. `merge.ts` already merges retry arrays this way (`methods` is combined across `extend()`). I'd add tests for combining across `extend()` and for `replaceOption`.
5. **Docs:** update the readme retry and `NetworkError` sections, the `options.ts` JSDoc and the `NetworkError.ts` doc comment. Show how to opt out with `networkErrorMethods: []` and recommend an `Idempotency-Key` header.
6. **Release:** ship as **3.0.0**, because a default behaviour changes. Include a migration note.

**Tests:**
- POST and PATCH network failures are retried, and the body arrives intact on every attempt (JSON, FormData, stream).
- POST 5xx, 429 and timeout are not retried.
- The opt-out works, and `methods: ['post']` still means full retries.
- `shouldRetry` can block a POST network retry but can't widen it.
- `null` and other bad values throw.
- Existing tests that expect a POST network error not to be retried are updated.

To verify: `npm test`, the browser tests in CI, and a manual run against a server that drops the socket on the first POST.

## Assumptions
- "Network fails" means errors that `isNetworkError` recognises. Timeouts and HTTP statuses stay as they are.
- The existing `limit: 2` and backoff apply to POST and PATCH too.
- An explicit `methods: ['post']` keeps its current meaning.
- Ky won't add idempotency keys automatically.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate writes (double orders or payments) | A `NetworkError` can happen after the server already received and processed the POST; Ky can't tell | Document it loudly, recommend an `Idempotency-Key`, easy opt-out |
| 2 | Silent behaviour change for current users | Apps that rely on POST failing fast now get up to 3 attempts | Major version, migration note, `networkErrorMethods: []` |
| 3 | Body can't be resent | Stream bodies and `Request` inputs depend on `request.clone()` (line 1225) and runtime stream support | Tests per body type; fail cleanly instead of sending an empty body |
| 4 | Network errors detected wrongly | `isNetworkError` guesses per runtime; a false positive retries a write | Keep the existing detection; add runtime tests for POST |
| 5 | `shouldRetry` unexpectedly ignored | Users expect `true` to always force a retry | Document that `true` can't widen network-only methods |
| 6 | Accidental retries on 5xx or 429 | A mistake in the new method check could treat POST like `methods` | Explicit tests that POST 5xx, 429 and timeout aren't retried |
| 7 | Confusing option merging | Arrays are combined across `extend()`, so an instance can't remove `post` without `replaceOption` | Document it and test `replaceOption([])` |
| 8 | `null` accepted by mistake | Easy to add a `?? []` fallback, which AGENTS.md forbids | Test that `null` throws an error naming the option |
| 9 | Longer waits on a dead connection | Up to 2 extra attempts plus backoff on mobile | Respect `totalTimeout`; document `limit` |

Riskiest: #1 Duplicate writes. A network error on POST doesn't prove the server didn't act, so retrying by default can repeat non-idempotent operations.
