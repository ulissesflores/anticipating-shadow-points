I've written a plan for soft-deleting users with a 30-day admin restore. Nothing in the repo was edited; the plan is saved to `claude-home/plans/add-soft-delete-for-spicy-knuth.md`.

**Where things stand:** both delete endpoints currently remove the user for good. `DELETE /users/{id}` explicitly deletes their items first (`backend/app/api/routes/users.py`), and `DELETE /users/me` removes them through the database cascade (`Item.owner_id ondelete=CASCADE`).

## Assumptions
- **Marker:** a new nullable `User.deleted_at` timestamp marks a deleted account. It is separate from `is_active`, which stays as the admin "disable" switch.
- **Items:** soft delete doesn't touch items. Superusers still see them in `/items`; the owner can't, because they can no longer log in.
- **Email:** stays reserved for the 30 days (the unique constraint stays), so signing up again with it fails with the existing "already exists" error.
- **After 30 days:** the account can't be restored. A separate purge command, meant to run daily, deletes it for good, and its items go with it through the existing cascade.
- **Restore:** only a superuser can restore. Users can't undelete themselves.

## Plan
1. **Model and migration:** add `deleted_at` (indexed) to `User` and show it in `UserPublic`. Add an Alembic migration (nullable column plus index, no backfill) and a `USER_RESTORE_WINDOW_DAYS = 30` setting in `core/config.py`.
2. **Data helpers (`crud.py`):** add `soft_delete_user`, `restore_user`, `is_restorable` and `purge_expired_users`. `authenticate` treats a deleted user as not found but still runs the dummy password check, so response timing doesn't reveal that the account exists.
3. **Login check (`deps.get_current_user`):** reject deleted users. This matters because login tokens stay valid for 8 days.
4. **Routes (`users.py`):**
   - Both delete endpoints set `deleted_at` instead of deleting, and stop deleting the items.
   - The user list hides deleted users by default; `?deleted=true` lists only them, and the count uses the same filter.
   - Looking up or editing a deleted user returns 404 (superusers can still read them).
   - New `POST /users/{id}/restore` for superusers: 404 if the user doesn't exist or isn't deleted, 410 once the 30 days have passed.
5. **Login routes (`login.py`):** password recovery and reset skip deleted users; recovery still returns the generic message.
6. **Purge job:** `app/purge_deleted_users.py`, following the `initial_data.py` pattern, documented in `deployment.md`.
7. **Frontend:**
   - Regenerate the API client.
   - Change the warning text in `DeleteUser`, `DeleteAccount` and `DeleteConfirmation` from "items permanently deleted" to "can be restored by an admin for 30 days".
   - On the admin page, add an Active/Deleted toggle; the Deleted view shows days left and a Restore action.
8. **Tests:**
   - Rewrite the delete tests in `test_users.py`, which currently expect the user row to be gone.
   - Add tests for restore: success, user not deleted, window expired (using a backdated `deleted_at`), and a non-superuser getting 403.
   - Add login tests: a deleted user can't log in, old tokens are rejected, and no recovery email is sent.
   - Add a test that the purge removes only expired users.
   - Add a Playwright flow: delete → restore → log in.

**To verify:** run `backend/scripts/test.sh`, apply and roll back the migration on a dev database, and run the Playwright admin and settings specs.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Deleted user keeps access | Login tokens last 8 days, and `get_current_user` only checks `is_active` | Reject `deleted_at` users in `get_current_user` and add a test |
| 2 | A query misses the new filter | Every query uses plain `select(User)` or `session.get` with no central filter | Add one shared "not deleted" helper; check every `User` query |
| 3 | Items lost on delete | The `delete(Item)` statement in `delete_user` and the database cascade both delete items today | Remove the statement; test that items survive |
| 4 | Email can't be reused | The unique email index still holds deleted users | Document it as intended; the purge frees the email |
| 5 | 30-day limit not enforced | The project has no scheduler | Check the 30 days in `restore` itself; purge only cleans up |
| 6 | Purge deletes items anyway | The cascade removes items when the user row is deleted | Confirm with product before turning on the purge job |
| 7 | Account existence leaks | Login and recovery are built to resist enumeration | Return the same errors and timing for deleted users as for unknown ones |
| 8 | Existing tests break | Current tests expect the user row to be gone after delete | Update them in the same change |
| 9 | Frontend client out of sync | The client is generated from the API schema | Regenerate it and update the delete warning texts |

Riskiest: #1 — if only login is changed, a deleted user's existing token keeps working for up to 8 days.
