## What's there today (FastAPI + SQLModel template)
- `User` has no deletion marker. `items` uses `cascade_delete=True`, and `Item.owner_id` uses `ondelete="CASCADE"` (`backend/app/models.py`).
- Two hard-delete paths:
  - `DELETE /users/me` calls `session.delete(current_user)` (`backend/app/api/routes/users.py:132`).
  - Admin `DELETE /users/{id}` explicitly runs `delete(Item)` first, then deletes the user (`users.py:214-232`).
- `email` is `unique=True`, so a soft-deleted row keeps its email.
- Every place that looks up a user goes through `session.get(User, …)` or `crud.get_user_by_email`, with no filter. That covers `deps.get_current_user`, `crud.authenticate`, `/login/password-recovery`, `/reset-password`, `/signup`, admin `read_users`, `read_user_by_id` and `update_user`.
- JWTs are stateless and checked only by `user.is_active`.
- There is no scheduler (cron, celery and so on) in the stack, so nothing exists yet that could purge rows after 30 days.

## Assumptions (no one to ask in this run)
1. Hidden means: can't log in, existing tokens are rejected, the user is left out of the admin user list by default, and password recovery and reset quietly do nothing for them.
2. "Keeps their items" means the items stay in the DB unchanged and still owned by the user. Superusers still see them in `/items`, and they come back on restore. Nothing is reassigned.
3. Both delete endpoints become soft deletes. After 30 days the account is purged for real (user and items), which keeps the existing hard-delete code as the purge path.
4. Only superusers can restore, and only while `deleted_at > now − 30d`.
5. The email stays reserved during the 30 days, so signup with that email returns the existing "already exists" error. After the purge it's free again.

## The ways this could go wrong
1. **Missed filter.** Some lookup keeps returning deleted users. The worst case is `get_current_user`: an old JWT keeps working.
2. **Hard delete still happens.** Either path, the ORM cascade or the explicit `delete(Item)`, is left in place and destroys the items we promised to keep.
3. **Email collision.** Signup with a soft-deleted user's email fails, or the check gets relaxed and a later restore breaks the unique constraint.
4. **Overloading `is_active`.** If deletion just sets `is_active=False`, a restore can't tell "admin deactivated" apart from "self-deleted", and the restore re-enables someone an admin had banned.
5. **The 30-day window never closes.** Without a purge job, "restore within 30 days" quietly becomes "restore forever" (with GDPR and erasure implications). Or the check uses naive vs. aware datetimes and fails in an off-by-timezone way.
6. **Migration drift.** The new `deleted_at` column needs an Alembic migration, and an index if it's filtered on. Someone might be tempted to drop the FK `ON DELETE CASCADE`, but the purge needs it.
7. **Items leaking out.** Superuser `/items` lists, or `read_item` by id, show items from hidden accounts. That may or may not be intended (assumption 2). Owners can't reach them anyway because they can't log in.
8. **Account enumeration or restore abuse.** Different responses for deleted vs. missing users leak information. A non-superuser could reach the restore endpoint. A deleted superuser could restore themselves.
9. **Frontend and client drift.** The generated OpenAPI client, the admin table, `DeleteUser.tsx` wording ("permanently deleted") and the Playwright tests all assume hard delete.
10. **Tests assert hard delete.** The existing tests in `tests/api/routes/test_users.py` check that the user and items are gone. They need rewriting rather than deleting.

## Plan
1. **Model and migration.** Add `deleted_at: datetime | None` (indexed) to `User`. Expose it on `UserPublic`. Add an Alembic revision under `backend/app/alembic/versions/`. Keep `cascade_delete` and `ondelete="CASCADE"`, which only fire on purge.
2. **One crud helper set** in `backend/app/crud.py`:
   - `soft_delete_user`
   - `restore_user` (raises if not deleted or if the window has passed)
   - `purge_expired_users(session, now)`, which reuses today's explicit hard-delete logic
   - Make `get_user_by_email` take `include_deleted: bool = False`. Signup, the admin create check and the `update_user` email-conflict check pass `True`, so the email stays reserved.
3. **Auth.**
   - `deps.get_current_user`: if `deleted_at` is set, return the same 404 "User not found" as a missing user.
   - `crud.authenticate`: treat a deleted user like a missing one, still running the `DUMMY_HASH` check so timing doesn't give it away.
   - `recover_password` and `reset_password` get this behaviour for free through the default `get_user_by_email`.
4. **Routes** (`users.py`):
   - Both DELETEs call `soft_delete_user`. Keep the rule that superusers can't delete themselves.
   - `read_users` gets an `include_deleted` query flag, default False, applied to both the count and the list.
   - Add `POST /users/{id}/restore`, superuser-only, returning 409 if the account isn't deleted and 410 if the window has expired.
   - `read_user_by_id` and admin `update_user` keep working on deleted users, so admins can inspect them.
5. **Purge.** Add `backend/app/scripts/purge_deleted_users.py` (or a hook in `backend/scripts/prestart.sh` plus a documented cron entry). The window comes from a new `settings.USER_SOFT_DELETE_RETENTION_DAYS = 30` in `core/config.py`.
6. **Frontend.**
   - Regenerate the client.
   - Admin table: a "Show deleted" toggle, a "Deleted" badge, and a Restore action in `UserActionsMenu.tsx`.
   - Change the `DeleteUser.tsx` and user-settings delete wording to say the account can be restored for 30 days.
7. **Tests.**
   - Rewrite the delete tests: user hidden, items still in the DB, old token rejected, login fails, signup with the same email gets 400.
   - Restore within the window works. Restore after 31 days returns 410, using a fixed `deleted_at`.
   - Purge removes the user and their items.
   - A non-superuser calling restore gets 403.

**Verification:** run `bash backend/scripts/test.sh`, run the Alembic upgrade and downgrade on a fresh DB, then run the Playwright admin specs after regenerating the client.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Deleted user's old JWT still works | `get_current_user` checks only `is_active`; tokens are stateless | Reject `deleted_at` in `get_current_user`; add a test |
| 2 | Items destroyed anyway | ORM `cascade_delete` + explicit `delete(Item)` in admin route | Replace both `session.delete` paths; assert items survive |
| 3 | Login, recovery or reset still work | `authenticate` / `get_user_by_email` are unfiltered | Default-exclude deleted in `get_user_by_email`; keep the dummy-hash timing |
| 4 | Email unique clash on signup or restore | `email` is `unique=True` at DB level | Keep the email reserved; signup checks with `include_deleted=True` |
| 5 | Restore re-enables a banned user | Using `is_active` as the delete flag loses the earlier state | Separate `deleted_at` column; restore never touches `is_active` |
| 6 | 30-day limit never enforced | No scheduler in the stack | Purge script + check the window in `restore_user` |
| 7 | Timezone or edge errors in the window | Mix of naive and aware datetimes | Store UTC-aware values via `get_datetime_utc`; test at the boundary |
| 8 | Admin list count/data mismatch | `read_users` counts and lists in separate queries | Apply the same filter to both |
| 9 | Restore endpoint misuse / enumeration | New endpoint; 404 vs. deleted responses differ | Superuser-only dependency; same 404 for deleted and missing in user-facing paths |
| 10 | Frontend/e2e break on the changed contract | Generated client and "permanent" delete UI | Regenerate the client; update the copy and Playwright specs |

Riskiest: #2. If either hard-delete path or the ORM cascade is left in place, the items are permanently lost.
