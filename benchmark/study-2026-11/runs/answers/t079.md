## What the repo has today

- **Production setup** (`docker-compose.prod.yml`): one `web` container (gunicorn on :8000), a `db` container (postgres:15), and an `nginx` container that publishes port 1337 and proxies to `web:8000`. None of the services has a healthcheck, `depends_on` doesn't wait for anything to be ready, and images are built from source with no version tag.
- **`app/entrypoint.prod.sh`**: waits for postgres with `nc` and then runs the main command. It does not migrate. Migrations and `collectstatic` are manual steps today.
- **`app/entrypoint.sh` (dev)**: runs `flush --no-input` and then `migrate`. That deletes all data and must never end up in the production path.
- **`nginx/nginx.conf`**: `upstream hello_django { server web:8000; }`. Nginx looks up `web` once, at startup, and keeps that address.
- **Data**: the `upload` app has no models of its own. Uploaded media goes to `media_volume`, which `web` and `nginx` share.

## Assumptions (I couldn't ask)

1. Single Docker host using Compose v2 (needed for `depends_on: condition:`). No Kubernetes or Swarm.
2. Deploys run from a script on the host or from CI over SSH, using `docker compose -f docker-compose.prod.yml`.
3. Postgres stays in Compose with its data volume. Uptime here means the web tier only; the database is not restarted during a deploy.
4. One web replica in normal running, with two only briefly during a deploy.
5. Zero downtime means no 5xx or refused connections at nginx while a deploy runs.

## Ways this could go wrong (before planning)

- **Migrating in the entrypoint**: it would run on every container start, restart and replica, so two containers can migrate at the same time.
- **Copying the dev entrypoint**: that would bring `flush` into production and wipe the database.
- **Old code against the new schema**: while two versions overlap, the old one keeps serving against the migrated schema. A dropped or renamed column, or a new NOT NULL column without a default, breaks it.
- **Table locks**: a migration that takes a long lock (ALTER on a big table, adding an index without `CONCURRENTLY`) blocks requests. That is downtime even though containers stay up.
- **Plain `docker compose up -d`**: it stops the old `web` before the new one is ready, so nginx returns 502.
- **Stale nginx address**: nginx keeps the old container's IP after `web` is replaced, which gives 502s even when a healthy new container exists.
- **No healthchecks**: "started" is treated as "ready". Gunicorn may still be booting, or the app may crash on bad settings.
- **Failed migration**: if the deploy carries on, new code runs against the old schema.
- **No rollback**: images aren't tagged, so rebuilding overwrites the previous image.
- **Healthcheck tooling**: the slim image has no `curl`, and a probe that doesn't send an allowed Host header gets a 400 from Django.
- **Abrupt shutdown**: gunicorn stopped without a grace period drops in-flight requests, including uploads.

## Plan

**1. One-shot `migrate` service in `docker-compose.prod.yml`**
- It uses the same image as `web`, with `command: python manage.py migrate --noinput` and `restart: "no"`.
- `web` gets `depends_on: migrate: condition: service_completed_successfully`, so a failed migration means the new web never starts.
- `db` gets a `pg_isready` healthcheck, and `migrate` waits for `service_healthy`. The `nc` loop in `entrypoint.prod.sh` stays as a harmless fallback.
- The migrate service gets a Postgres `lock_timeout` (for example 5s, through `DATABASES["default"]["OPTIONS"]` driven by an env var). A migration that would block traffic then fails fast instead of hanging requests.
- `collectstatic --noinput` can run in the same one-shot step, since the static volume is shared.

**2. Healthcheck on `web`**
- Use Python's built-in `urllib`, not `curl`, and request `http://localhost:8000/` with a host that is in `DJANGO_ALLOWED_HOSTS`. A tiny `/healthz/` view in `hello_django/urls.py` is cleaner.
- Add `stop_grace_period: 30s` and gunicorn `--graceful-timeout 30` so in-flight requests finish.

**3. Nginx re-resolves `web` and retries failed requests**
- Add `resolver 127.0.0.11 valid=5s;` and `proxy_next_upstream error timeout http_502;`.
- Add a `deploy.sh` step that runs `nginx -s reload` after containers change.

**4. Rolling swap in `deploy.sh`**
1. Tag the image with the git SHA (`image: app:${TAG}`) and keep the previous tag for rollback.
2. Back up with `pg_dump` before migrating.
3. Run `docker compose run --rm migrate`. If it fails, stop; the old web keeps serving.
4. Run `docker compose up -d --no-deps --no-recreate --scale web=2 web` to start the new container next to the old one.
5. Wait until the new container's health is `healthy`, then reload nginx.
6. Stop the old container gracefully (`docker stop` sends SIGTERM and gunicorn drains), remove it, and reload nginx again.

`wowu/docker-rollout` is an off-the-shelf version of steps 4–6. I'd keep the logic in the script and avoid the extra dependency.

**5. Rules for writing migrations (expand/contract)**
- Each migration must stay compatible with the code version before it: add nullable columns or ones with defaults, and drop or rename only one release after the code stops using them. Indexes use `AddIndexConcurrently` with `atomic = False`.
- CI runs `python manage.py makemigrations --check --dry-run`, so model changes can't ship without migrations. Never run `makemigrations` during a deploy.
- Review the SQL with `sqlmigrate` for anything that touches large tables.

**6. Docs**
- Update the README's production section to say "deploy with `./deploy.sh`" and add the migration rules.

**Files involved:** `docker-compose.prod.yml`, `nginx/nginx.conf`, a new `deploy.sh`, `app/hello_django/settings.py` (lock timeout), `app/hello_django/urls.py` (health view), `README.md`. Leave `app/entrypoint.prod.sh` without migrations.

## Verification

1. **Downtime probe:** run `while true; do curl -s -o /dev/null -w '%{http_code}\n' localhost:1337/; sleep 0.1; done | sort | uniq -c` during a deploy. Expect only 200s.
2. **Additive migration:** deploy one that adds a nullable column. Expect no non-200 responses and the column present afterwards.
3. **Failing migration:** deploy a deliberately broken one. The deploy should stop, the old container should keep serving, and no new `web` should start.
4. **Rollback:** redeploy the previous SHA tag and confirm it serves.
5. **Large upload:** upload a big file during the swap and confirm it completes.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Migration breaks the old code still serving | Old and new containers overlap during the swap | Expand/contract rules; drop or rename one release later |
| 2 | `flush` copied into production | Dev `entrypoint.sh` runs `flush` before `migrate` | Separate migrate service; never reuse the dev entrypoint |
| 3 | Long table lock stalls requests | Postgres ALTERs block reads and writes | `lock_timeout`; concurrent indexes; `sqlmigrate` review |
| 4 | 502s during the swap | Nginx keeps `web`'s old IP; plain `up -d` stops the old container first | Resolver plus reload; scale to 2, wait healthy, then stop old |
| 5 | New code starts after a failed migrate | Today's `depends_on` waits for nothing | `service_completed_successfully`; script exits on error |
| 6 | Concurrent migrations | Migrating in the entrypoint runs once per replica or restart | Single one-shot `migrate` service |
| 7 | Traffic sent before the app is ready | No healthchecks exist | Python healthcheck on `/healthz/` |
| 8 | Healthcheck always fails | Slim image has no curl; Host header must be allowed | Use `urllib` with an allowed host |
| 9 | No rollback path | Untagged builds overwrite the previous image | Tag images by git SHA; `pg_dump` before migrating |
| 10 | Uploads cut off mid-request | Container stopped without draining | `stop_grace_period` plus gunicorn graceful timeout |

Riskiest: #1. A migration that isn't backward-compatible breaks the old container while it's still serving, and the containers staying up won't prevent it.
