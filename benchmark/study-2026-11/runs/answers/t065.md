## How it works today
- A prod deploy is `docker-compose -f docker-compose.prod.yml up -d --build`. That stops the old `web` container before gunicorn in the new one is ready, so nginx returns 502s in between.
- Migrations never run in prod: `app/entrypoint.prod.sh` only waits for Postgres. The dev `entrypoint.sh` runs `flush` before migrating, which wipes the database, so it must never be copied to prod.
- nginx looks up `web:8000` only when it starts or reloads (`nginx/nginx.conf`).
- There is no healthcheck and no health endpoint.

## Assumptions
- One Docker host with Compose v2; no Swarm or Kubernetes.
- Only `web` is replaced; `db` and `nginx` stay up during a deploy.
- Migrations are written "expand/contract": each schema change must still work with the old code.

## Plan
1. **Health endpoint:** add `/healthz/` in `app/hello_django/urls.py`. It runs `SELECT 1` against the database and returns 200 or 503.
2. **`docker-compose.prod.yml`:**
   - Tag the `web` image with the git commit (`hello_django_web:${TAG}`) so you can roll back to a previous build.
   - Give `web` a healthcheck using Python's `urllib`, since the image has no curl. Add `stop_grace_period: 30s` and `--graceful-timeout 25` for gunicorn.
   - Give `db` a `pg_isready` healthcheck and make `web` wait for it.
   - Add a one-shot `migrate` service (`profiles: [deploy]`) that runs `migrate --noinput` and `collectstatic --noinput`.
   - Keep `web` free of `ports` and `container_name`, because either one blocks running two copies at once.
3. **`nginx/nginx.conf`:** add `proxy_next_upstream error timeout http_502` with 2 tries, so a request refused by the old container is retried on the new one.
4. **`entrypoint.prod.sh`:** leave it unchanged. Migrations run once per deploy, not in every container.
5. **New `scripts/deploy.sh`:** a lock (`flock`) stops two deploys running at once, and each step aborts on failure.
   1. Build the image tagged with the commit.
   2. Run the `migrate` service. If it fails, stop here; the old version keeps serving.
   3. Start a second `web` container alongside the old one.
   4. Wait up to 60s for the new one to pass its healthcheck. If it doesn't, remove it and exit; the old one keeps serving.
   5. Reload nginx so it sends traffic to both.
   6. Stop the old container with a 30s grace period; gunicorn finishes its in-flight requests.
   7. Scale back to one `web` and reload nginx again.
   8. Smoke-test `/healthz/`.
6. **README:** replace the prod instructions with `deploy.sh`, and document the migration rule and how to roll back (redeploy the previous tag with `--skip-migrate`).

**How to check it works:**
- Run a load generator such as `hey` against `:1337` while deploying twice; expect zero non-2xx responses.
- Deploy a new model field under load and confirm the migration is applied.
- Force a broken migration and a failing healthcheck; in both cases the old version should keep serving.
- Roll back to the previous tag and confirm the site serves.

**Separate bug:** in `settings.py`, `bool(os.environ.get("DEBUG", 0))` is `True` when `DEBUG=0`, because `bool("0")` is `True`. Prod is currently running with DEBUG on. This plan doesn't fix that.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | A migration breaks the old code still serving | The old and new containers share one database during the swap | Expand/contract rule; make the column change first, remove the old one in a later deploy |
| 2 | Migrations run concurrently | Putting `migrate` in the entrypoint would run it in both replicas | A single one-shot `migrate` step plus a deploy lock |
| 3 | nginx keeps routing to the old container | It looks up `web` only at start or reload | Reload after scale-up and after scale-down; retry via `proxy_next_upstream` |
| 4 | In-flight requests are cut off | Stopping the container kills gunicorn workers | Graceful SIGTERM with `stop_grace_period` 30s and `--graceful-timeout` |
| 5 | The new container is never marked healthy | No curl in the image; `ALLOWED_HOSTS` may reject the Host header the check sends | Python urllib check sending an allowed Host; 60s timeout, then remove the new container |
| 6 | No database rollback | Migrations only move forward | Back up before migrating; roll back code with `--skip-migrate` and the previous tag |
| 7 | Shared static files change under the old version | `collectstatic` overwrites the shared volume in place, with no hashed filenames | Use `ManifestStaticFilesStorage`; accept a brief mismatch |
| 8 | Someone runs the old `up --build` command | The README tells them to, and it still causes downtime | Update the README so `deploy.sh` is the only documented path |
| 9 | A long migration locks tables | Postgres takes heavy locks for some schema changes, which blocks requests | Set `lock_timeout`; use concurrent index creation; review migration SQL with `sqlmigrate` |

Riskiest: #1. A migration that isn't backward-compatible breaks the old container while it is still serving traffic.
