# ASP plan: co-authors for articles (stopped after Phase 6, nothing executed)

The plan is ready but not yet approved: the independent validator said REVISE, and I applied all 10 of its fixes but did not send the revised plan back for a second check. No project file was edited. The only file written is the plan at `claude-home/plans/standard-allow-an-article-goofy-karp.md`. The entry check passed. The repo has no `CLAUDE.md` or lessons file, so no past lessons were available.

**Assumptions (no one to ask in this run):**
- **Owner:** the existing `author` field stays as the article's owner (primary author) and its JSON shape doesn't change.
- **Response:** co-authors appear in a new extra field, `coAuthors: Profile[]`, which is `[]` for every existing article.
- **Writes:** `POST` and `PUT` accept an optional `article.coAuthors` list of usernames.
  - On `PUT`, leaving the field out changes nothing; `[]` removes all co-authors.
  - At most 10 co-authors. Duplicates and the owner are dropped. Unknown usernames return 422.
- **Permissions:** the owner and co-authors can edit the content. Only the owner can delete the article or change the co-author list; a co-author who tries gets 403.
- **Slugs:** a slug is always built from the owner's id, never from the id of whoever is editing.
- **Lists and feed:** `?author=X` and the feed also match co-authors. Viewers also see articles they co-author in lists. The `demo`-based visibility rule stays tied to the owner.

**What the code review found:**
- **Slug bug:** `updateArticle` builds the new slug from the caller's id (`article.service.ts:317`). Today only the owner can edit, so it's harmless. Once co-authors can edit, a co-author renaming an article would change its URL. This is the main way the change could break existing URLs.
- **Raw responses:** favorite and unfavorite return the raw database row instead of going through `articleMapper` (`:597-651`). If the new relation is just added to them, raw link-table rows would show up in their JSON.
- **Repeated query setup:** the same `include` block is copied 7 times in `article.service.ts`.
- **List visibility:** a list only shows an article if its owner is `demo` or is the viewer (`:13-40`). Registered users are always created with `demo: false` (`auth.controller.ts:16`).

**Plan (deliverables):**
- **D01 – schema and migration.**
  - Add a new link table `ArticleCoAuthor`: primary key `(articleId, userId)`, a `position` column, an index on `userId`, and deletes cascading from both sides.
  - Add a back-relation on `User`.
  - The migration only creates the table and adds keys; `authorId` is untouched and no data is copied.
- **D02 – read side.**
  - Pull the copied `include` block into one shared `articleInclude(viewerId)`.
  - Extend `articleMapper` to output `coAuthors`, defaulting to `[]`.
  - Map `coAuthors` explicitly in favorite and unfavorite.
  - Load only the viewer's own follow row for each co-author, not the full follower list.
  - Make the `?author=` filter, the feed and the visibility rule also match co-authors.
- **D03 – write side.**
  - Add a `resolveCoAuthors` helper that applies the validation rules above.
  - Make the update one transaction covering the permission check, tag reset, co-author replacement and the update itself.
  - Build the slug from the owner's id.
- **D04 – tests.**
  - The new 403, slug and visibility tests are the real check, since no existing test covers update or delete.
  - A golden test compares every key of the GET, list, feed, favorite and unfavorite responses.
  - The Prisma test mock needs a `$transaction` mock.
- **D05 – docs.** Add a "Co-authors" section to `README.md`.

**Validator round 1 – REVISE.** It found 2 blockers, both of which I confirmed in the code:
1. Co-authors would never see their own co-authored articles in lists, because visibility depended only on the owner.
2. The planned curl check would have returned nothing, because of the same `demo` rule.

It also raised 8 minor issues. Two matter most:
- A Prisma filter whose `id` is `undefined` matches everything.
- The permission check ran outside the transaction.

All 10 were applied in the plan's "Phase 6 revisions" section.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Slug changes when a co-author edits the title | `updateArticle` uses the caller's id for the slug (`:317`) | Always build the slug from `authorId`; regression test |
| 2 | Response shape drifts | favorite/unfavorite return the raw row; adding the relation would leak link rows | Map `coAuthors` explicitly; full-key golden tests |
| 3 | Co-author gets too much power | Update and delete share one ownership check | Owner-only delete and co-author changes; 403 tests |
| 4 | List results or visibility change | Author filter sits inside the demo/self rule | Separate clause; extend only the viewer's own match; count/list parity test |
| 5 | Follower data loaded too broadly | `authorMapper` loads every follower row; Prisma drops a filter with `undefined` | Load the viewer's row only, and only when there is a viewer |
| 6 | Partial writes or race | Tag reset and update are separate writes; the check runs outside them | One interactive `$transaction` |
| 7 | Migration breaks a rolling deploy | Old code runs against the new schema | Additive table only; `authorId` untouched |
| 8 | Weak test coverage | No existing tests cover update or delete; mocked rows lack `coAuthors` | New tests are the real check; mapper defaults to `[]`; `$transaction` mock |
| 9 | Bad co-author input | Duplicates, the owner, unknown users, very long lists | Validation, max 10, 422 with `errors.coAuthors` |

Riskiest: #1. A co-author renaming an article silently changes its URL, which breaks the existing links you asked to keep working.
