## Assumptions
- "The network fails" means errors that `isNetworkError` recognises, such as `Failed to fetch`, `fetch failed`, `terminated` or `Load failed`. It does not include HTTP 5xx/429 responses or timeouts.
- The behaviour change is acceptable in a semver-major release. The last release was 2.2.0, so this would be 3.0.0.

## How the code works today
- The default list of methods that get retried is `['get','put','head','delete','options','trace','query']`, in `source/utils/normalize.ts:17`.
- In `#calculateRetryDelay` (`source/core/Ky.ts:688-763`), the method check at line 703 runs before anything else. It is the only thing that stops a POST from being retried, whether the failure is a network error, a retryable status code or a timeout.
- Ky clones the request ahead of time for retries whenever `retry.limit > 0` (`Ky.ts:1225`), whatever the method. So POST bodies are already copied, and a streamed body is already buffered in memory through `tee()`. Making POST retryable doesn't add that cost.

## Ways this could go wrong (before planning)
1. **The naive fix retries far more than network errors.** The obvious change is adding `'post','patch'` to `retryMethods`. That also makes POST and PATCH retry on 408/413/429/500/502/503/504, and with `shouldRetry` and `retryOnTimeout`, because one `methods` list controls every kind of failure.
2. **A network error doesn't mean the server never got the request.** `terminated` (Undici), Safari's `Load failed` and Chrome's `Failed to fetch` can all happen after the server has committed the write and the response was lost. On flaky mobile networks this is the common case. A retry then creates a duplicate order, payment or message.
3. **PATCH isn't idempotent in general.** For example, JSON Patch `add` to an array, or an increment, applied twice gives a different result.
4. **Silent change for existing users.** Code that relied on POST never being retried starts firing `beforeRetry` hooks, upload-progress restarts and the backoff delays without anyone opting in.
5. **Existing tests and docs say the opposite.** `test/retry.ts` and `test/main.ts` assert that POST is not retried, and readme lines 265, 281 and 304 document the current list.
6. **Upload progress jumps backwards.** On a retry, `onUploadProgress` restarts from 0 for a large POST body.
7. **The AGENTS.md rule on `null`.** Any new option must throw a named `TypeError` when given `null`, not treat it as `undefined`.

## Recommended plan
Add a separate, narrow path that retries only network errors, instead of widening `retry.methods`:

1. **`source/types/retry.ts` and `source/utils/normalize.ts`:** add `retry.networkErrorMethods`, which defaults to `['post','patch']`. It is checked only after the error is confirmed to be a network error. Validate it the same way the loop at `normalize.ts:55-70` does (an array of strings, run through `normalizeRetryMethod`), and throw `` `retry.networkErrorMethods` must be an array `` for `null` or any other non-array.
2. **`source/core/Ky.ts:703`:** if the method is in `retry.methods`, keep the current flow. Otherwise, if it is in `networkErrorMethods` and `isNetworkError(error)`, call `shouldRetry` (still allowed to veto with `false`) and then return `#calculateDelay`. Everything else for these methods still throws, so no status-code or timeout retries.
3. **Safety gate (recommended):** for POST and PATCH, only retry by default when the request has an `Idempotency-Key` header. This follows the IETF httpapi draft. Users who accept the risk can set `networkErrorMethods` with no gate, or add the methods to `retry.methods`. If you want an unconditional default instead, drop the gate. That gives up mitigation for risk 2 and still needs the major version bump.
4. **Tests (`test/retry.ts`):**
   - POST and PATCH are retried on a network error, both with and without the gate.
   - They are not retried on 500, 503 or 429, or on a timeout.
   - `networkErrorMethods: []` turns the feature off.
   - `null` throws a named error.
   - `shouldRetry` returning `false` still vetoes.
   - The existing tests that assert POST isn't retried are updated.
5. **Docs (readme Retry section and the `NetworkError` section):** explain the new option, that a lost response can mean the write already happened, and the idempotency-key advice.

**Verification:** run `npm test` (ava, the browser tests and the `tsd` type tests in `test-d/`). Also run a manual check against a local server that destroys the socket after reading the POST body. That reproduces the "write committed, response lost" case, and confirms the gate prevents the duplicate.

## Main risks of this change

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate writes | `terminated`, `Load failed` and `Failed to fetch` can fire after the server has committed the write | Require an `Idempotency-Key` header by default; document the risk |
| 2 | POST also retries on 5xx/429/timeout | One `methods` check at `Ky.ts:703` controls every failure type | Separate `networkErrorMethods` path that only handles network errors |
| 3 | PATCH isn't idempotent | Increments and array appends double when replayed | Same gate; call out PATCH in the docs |
| 4 | Silent behaviour change | Existing apps start getting retries, `beforeRetry` calls and delays they didn't ask for | Major version bump, changelog, `networkErrorMethods: []` to opt out |
| 5 | `shouldRetry` gets called for POST | Users' predicates were written assuming GET-like methods | Keep the `false` veto; document the new callers |
| 6 | Upload progress restarts | `onUploadProgress` drops back to 0 on a retry | Document it; consider adding the attempt number to progress events |
| 7 | `null` accepted quietly | AGENTS.md forbids treating `null` as absent | Validate it and throw a named `TypeError` |
| 8 | Stale tests and docs | Tests and readme say POST isn't retried | Update `test/retry.ts`, `test/main.ts` and the readme in the same change |

Riskiest: #1. Retrying a POST whose response was lost on a flaky mobile connection can double-charge or double-submit, and from the network error alone the client can't tell whether the server already applied the write.
