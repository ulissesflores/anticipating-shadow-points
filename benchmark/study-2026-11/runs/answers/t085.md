# Zero-downtime deploys with automatic migrations: failure modes and plan

## Assumptions
- Production is a single Docker host running `docker-compose.prod.yml` (nginx → gunicorn `web` → Postgres 15) with Compose v2. There is no Kubernetes, Swarm or load balancer in front.
- Deploys happen on the host, by a person or a CI job over SSH. Today a deploy is `docker compose -f docker-compose.prod.yml up -d --build`.
- "Keep the site up" means no 502s or refused connections on port 1337 while the new container starts. A few seconds where old and new code both serve requests is acceptable.
- You said not to edit any file, so I haven't written one, not even the plan file. Everything below is a plan.

## What the repo does today (and why it matters)
- **`up -d --build` causes downtime.** Compose stops the old `web` container before the new one is ready, and nothing checks that the new one is healthy.
- **nginx resolves `web` only once, at startup** (`nginx/nginx.conf:1-3`, a static `upstream`). A recreated `web` container gets a new IP, so nginx keeps sending traffic to the old, dead address and returns 502s until it is reloaded. This is the biggest hidden trap.
- **The production entrypoint doesn't migrate** (`app/entrypoint.prod.sh`). The dev entrypoint (`app/entrypoint.sh:14`) runs `manage.py flush --no-input` and then migrates. Copying that file "to get migrations" would wipe the production database on every deploy.
- **Migrating from each container's entrypoint is unsafe** once more than one `web` container runs during the overlap: they race each other, and the app starts even if the migration failed.
- **Static files share one volume and have no hashed names.** `STATIC_ROOT` is on `static_volume`, used by both containers and nginx, and nothing runs `collectstatic` today. Running it overwrites the old version's assets while old pages are still being served.
- **No health signal:** there's no healthcheck in the compose file and no health URL. `depends_on: db` doesn't wait for Postgres to be ready (the entrypoint polls with `nc`).
- **Shutdown can cut requests:** Docker's default stop timeout is 10 s, after which in-flight gunicorn requests are killed.
- **Unrelated bug, but it raises the stakes:** `settings.py` has `DEBUG = bool(os.environ.get("DEBUG", default=0))`. `bool("0")` is `True`, so production runs with DEBUG on. Any error during a deploy would show stack traces to visitors.

## Plan (recommended approach)
1. **Health endpoint and healthcheck**
   - Add a tiny `/healthz/` view that runs `SELECT 1`.
   - Add a `healthcheck` to `web` in `docker-compose.prod.yml` (python/urllib or curl).
   - Add `stop_grace_period: 30s`, and set gunicorn `--graceful-timeout 25` so in-flight requests finish.
2. **nginx re-resolves `web` and retries**
   - Use `resolver 127.0.0.11 valid=5s;` with `set $upstream web:8000; proxy_pass http://$upstream;`. Alternatively, keep the upstream block and run `nginx -s reload` as part of every deploy.
   - Add `proxy_next_upstream error timeout http_502;` so a request that lands on a container being removed is retried.
3. **Migrations as a separate, one-off step**
   - Create a new `scripts/deploy.sh` with `set -euo pipefail`. It will:
     1. Build and tag the image with the git SHA.
     2. Run `docker compose run --rm --no-deps web python manage.py migrate --noinput` using the **new** image, before any traffic moves.
     3. Abort the deploy if that fails. The old containers keep serving.
   - Leave the entrypoints unchanged. Never reuse `entrypoint.sh`.
   - Set the Postgres `lock_timeout` (e.g. `SET lock_timeout='5s'` through DB `OPTIONS`/env for the migrate run) so a blocked `ALTER TABLE` fails fast instead of freezing the site.
4. **Static files**
   - Switch to `ManifestStaticFilesStorage` (hashed filenames; old files stay).
   - Run `collectstatic --noinput` in the deploy script after migrating and before the swap.
5. **Rolling swap on a single host** (the pattern used by the `docker-rollout` plugin)
   1. `docker compose up -d --no-deps --no-recreate --scale web=2 web` starts a new-image container next to the old one. This works because `web` has no `container_name` and no published host port, only `expose`.
   2. Wait until the new container reports `healthy`, with a timeout. If it never does, remove it and stop. The old container is untouched.
   3. Stop the old container gracefully, then `--scale web=1`.
   4. If you kept the static upstream, run `docker compose exec nginx nginx -s reload`.
6. **Migration rule (expand/contract)**
   - Every migration must work with both the old and the new code, because both run during the overlap and after a rollback.
   - Add or rename columns in two releases. Make new columns nullable or give them DB defaults. Drop columns one release after the code stops using them.
   - Write this down in the README and check for it in PR review.
7. **Rollback**
   - Redeploy the previous SHA tag with the same script; it skips the swap if migrations are a no-op.
   - Don't reverse migrations automatically.
8. **Fix the `DEBUG` parsing** (`int(os.environ.get("DEBUG", 0))`) in the same change.

**Files to change:** `docker-compose.prod.yml`, `nginx/nginx.conf`, `app/hello_django/settings.py`, `app/hello_django/urls.py` (and a small health view), new `scripts/deploy.sh`, and `README.md`. `app/upload/migrations/` is currently empty, so the first real migration should be tested on a copy of the database.

## How to check it works
- Run a load loop against the site during a deploy, e.g. `while true; do curl -s -o /dev/null -w '%{http_code}\n' localhost:1337/healthz/; done | sort | uniq -c`. Expect only 200s.
- Repeat with a deliberately broken migration: the deploy must abort, the old version must keep serving, and there must be no 5xx.
- Repeat with an image whose healthcheck fails: the new container must be removed and the old one kept.
- Check `docker compose ps` afterwards: there should be exactly one `web` container, on the new image.
- Check that an old page's hashed CSS URL still returns 200 after the deploy.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Migration breaks the old code still running | Old and new containers share one DB during the overlap and after a rollback | Expand/contract migrations; never drop or rename in the same release |
| 2 | nginx keeps the dead container's IP and returns 502s | Static `upstream web:8000` is resolved once at startup | `resolver 127.0.0.11` with a variable `proxy_pass`, or `nginx -s reload`; `proxy_next_upstream` |
| 3 | `flush` wipes the production DB | Dev `entrypoint.sh` runs `flush` before `migrate`; it's tempting to copy | Separate `migrate`-only step; leave the entrypoints alone |
| 4 | Concurrent migrations | Migrating in the entrypoint runs it once per replica during the scale-up | One `run --rm` migrate step before the swap |
| 5 | Long table lock freezes the site | `ALTER TABLE` takes an exclusive lock; requests queue behind it | `lock_timeout`; rehearse on a DB copy; split large migrations |
| 6 | Traffic moves to a broken container | No healthcheck exists; Compose has no readiness gate | `/healthz/` with a DB check, plus a health-wait in the deploy script |
| 7 | In-flight requests killed | 10 s default stop timeout; abrupt container removal | `stop_grace_period`, gunicorn graceful timeout, drain before stopping |
| 8 | Static assets mismatch between versions | One shared `static_volume`, unhashed files | `ManifestStaticFilesStorage`; collectstatic before the swap |
| 9 | Failed migration still deploys | Script or entrypoint keeps going after an error | `set -e`; swap only after migrate succeeds |
| 10 | Errors shown to visitors during the deploy | `bool("0")` makes `DEBUG=True` in production | Parse `DEBUG` as an int |

Riskiest: #1. A migration that isn't backward-compatible breaks the old containers during the overlap and makes rollback impossible, even when every other step works.
