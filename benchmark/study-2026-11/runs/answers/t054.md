I've written a plan for the weekly digest and haven't changed any code.

**What could go wrong (listed before planning):**
- **Duplicate or missed emails.** A schedule that fires twice, a retried job or a crash partway through could send a digest twice or skip one.
- **The existing feed query includes the user's own posts.** `following_posts()` in `app/models.py` returns them, so the digest can't reuse it as it is.
- **Date comparisons can fail.** SQLite gives back dates without a timezone, so comparing them with the current UTC time can raise an error or shift the week's window.
- **Emails can be lost in background jobs.** `send_email` sends from a separate thread by default, and a background job can finish before that thread does.
- **Email templates break with no web request.** Absolute links need `SERVER_NAME`, the post template uses `moment()` (which needs JavaScript), and the translation setup reads the current request.
- **Volume.** Thousands of emails at once can overload the mail server, and the error handler that emails ADMINS would send one alert per failure.
- **Consent and security.** Existing users never asked for this email, so it needs an unsubscribe link that works without logging in and can't be forged.
- **Database change.** Adding a yes/no column to a live database needs a default value.

**Assumptions (no one to ask in this run):**
- An external cron job or Heroku Scheduler runs a new `flask digest send` command each week. The installed version of `rq` (the background-job library) has no scheduler.
- Digests are on by default for everyone, and each email has a signed unsubscribe link.
- No email is sent to a user when the people they follow posted nothing that week.
- Emails are in English only for now.

**Plan:**
1. **`User` model:** add `digest_enabled` (with a database default) and `last_digest_sent`. Add `followed_posts_since(since)`, which leaves out the user's own posts and caps the list at about 50. Add an unsubscribe token that reuses the password-reset token code with a separate key.
2. **Migration:** generate one with `flask db migrate` and check it sets the default.
3. **Job in `app/tasks.py`:** `send_weekly_digest(user_id)`.
   - Skip the user if they've unsubscribed or got a digest in the last 6 days.
   - Set the window start to the last send time, or 7 days ago.
   - Skip if there are no posts.
   - Send synchronously (`sync=True`).
   - Record `last_digest_sent` only after the send succeeds.
   - Log failures as warnings so admins don't get an email per failure.
4. **CLI in `app/cli.py`:** `flask digest send` goes through opted-in users in batches and queues one job per user. It has `--dry-run` and `--user` options for testing.
5. **Templates:** `email/weekly_digest.txt` and `.html`, with plain timestamps, absolute links and the unsubscribe link.
6. **Route:** `GET /unsubscribe/<token>` turns the digest off. Optionally add an opt-back-in checkbox on the edit-profile page.
7. **Deploy:** set `SERVER_NAME` and a real sender address in `ADMINS[0]`, and add the cron line `0 8 * * 1 flask digest send`.
8. **Tests:** check the post filter, that running the job twice sends one email (with sending mocked), and that unsubscribe tokens work and expire.

**How to check it:** run `python -m unittest tests`. Then start the `aiosmtpd` debugging mail server and an `rq worker`, and run `flask digest send --user susan`. Confirm the email prints, that a second run sends nothing, and that the unsubscribe link turns the digest off.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate or missed digests | No scheduler is in place, and the schedule or job can run twice or crash partway | Check and update `last_digest_sent` per user, writing it only after a successful send |
| 2 | Users see their own posts | `following_posts()` includes the user's own posts | New `followed_posts_since()` query that leaves them out |
| 3 | Date comparison errors | SQLite returns dates without a timezone, compared against the current UTC time | Convert both sides to UTC without timezone before comparing |
| 4 | Emails silently dropped | `send_email` sends from a separate thread by default | Use `sync=True` inside the job |
| 5 | Template fails outside a web request | `url_for` external links need `SERVER_NAME`; `moment()` and the translation setup read the request | Separate plain email templates, require `SERVER_NAME`, English only |
| 6 | Mail server or admin inbox flooded | Error handler emails ADMINS on every error; one email per user | Log failures as warnings, queue jobs in batches |
| 7 | Unwanted email / spam complaints | Existing users never opted in | Signed unsubscribe link plus a `digest_enabled` setting |
| 8 | Forged unsubscribe links | The link has to work without logging in | Signed, expiring token with its own key |
| 9 | Migration fails on existing rows | New required yes/no column on a populated table | Set a database default in the migration |
| 10 | Wrong sender address | `ADMINS[0]` is `your-email@example.com` | Set a real sender before launch |

Riskiest: #1, duplicate or missed digests. Emailing every user twice can't be undone and erodes trust right away.
