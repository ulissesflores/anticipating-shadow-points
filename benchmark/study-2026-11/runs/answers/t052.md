## Ways this could go wrong
1. **Nothing runs it on a schedule.** The app has an RQ worker (`Procfile` `worker:`), but no cron or scheduler, so a weekly job never fires unless something outside the app starts it.
2. **Wrong posts in the digest.** `User.following_posts()` (`app/models.py:166`) also returns the user's own posts. Reusing it as-is would put your own posts in your digest.
3. **Sending twice or skipping a week.** Without a stored "last sent" time, a retried or overlapping run resends, and a missed run loses a week's posts.
4. **Spam and legal exposure.** There's no opt-out field, so this would be bulk email with no unsubscribe link (CAN-SPAM / GDPR).
5. **Broken links in the email.** The worker calls `create_app()` at import (`app/tasks.py`). Building full URLs (`url_for(..., _external=True)`) without a request needs `SERVER_NAME` to be set.
6. **Translated text fails in the worker.** `get_locale()` reads `request.accept_languages`. Any `_()` call in the digest templates would fail in the worker, where there's no request.
7. **Mail volume.** `send_email` sends on a background thread by default. Looping over every user from one place opens one thread and SMTP connection per email, which can hit provider rate limits and leave half the users without their email.
8. **Slow database queries.** One query per user on the followers join, with no limit on posts per digest. That's an N+1 pattern and can produce very large emails.
9. **One bad user stops the batch.** `export_posts` puts its whole body in one try/except, so a single bad address or user would end the run for everyone after them.
10. **Time zone mistakes.** Stored timestamps are naive UTC, while `last_seen` uses `.replace(tzinfo=utc)` handling. Mixing aware and naive datetimes in the time-window filter raises errors or misses posts.

## Assumptions (no one to ask in this run)
- **"New" posts:** posts from accounts you follow, written since your last digest (default: the last 7 days). Your own posts are left out.
- **Who gets it:** everyone by default, with an opt-out checkbox on the profile page and a one-click unsubscribe link. Users with no new posts get no email.
- **Trigger:** a new `flask digest send` command, run weekly by an external cron or scheduler. It splits users into batches and puts one RQ job per batch on the queue. No new dependency.
- **Size:** at most about 20 posts per email, plus an "and X more" link.

## Plan
1. **Database:** add `digest_opt_in` (default true) and `last_digest_sent_at` to `User`, with an Alembic migration.
2. **Query:** add `User.digest_posts(since, until)`. It covers followed authors only, filters by the time window, and is capped.
3. **Worker job:** add `send_weekly_digests(user_ids, until)` in `app/tasks.py`. It sends with `send_email(..., sync=True)`, handles errors one user at a time, and saves `last_digest_sent_at` after each send.
4. **Command:** add `flask digest send [--dry-run] [--user ID]` in `app/cli.py`. It skips users whose last digest was sent less than 6 days ago, so a second run doesn't resend.
5. **Email templates:** `email/weekly_digest.{txt,html}` with full URLs and a signed unsubscribe link (same JWT approach as the password-reset token), written without `_()` calls.
6. **Opt-out:** an unsubscribe route and a checkbox in `EditProfileForm`.
7. **Ops docs:** document the weekly cron entry and that `SERVER_NAME` is required.

**Verification:**
- Tests in `tests.py` cover: own and old posts excluded, opted-out users skipped, and running twice sends only once.
- A `--dry-run` run, then a real run against a local debugging SMTP server (`aiosmtpd`) with `rq worker` running, to check the actual emails.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Nothing triggers the job | Only an RQ worker exists, with no scheduler | External weekly cron runs `flask digest send` |
| 2 | Duplicate or missed digests | Retries and overlapping runs, no record of what was sent | `last_digest_sent_at` saved per user; skip if sent in the last 6 days |
| 3 | Unwanted bulk email, legal exposure | No opt-out field today | Opt-out flag plus signed unsubscribe link |
| 4 | Own posts in digest | `following_posts()` includes them | New followed-only query |
| 5 | Broken links in email | Worker has no request, so full URLs need `SERVER_NAME` | Require and document `SERVER_NAME` |
| 6 | Translated text fails in worker | `get_locale()` reads `request` | No `_()` in digest templates, or force a locale |
| 7 | SMTP throttling and half-finished runs | Default send uses one thread per email | `sync=True` inside batched RQ jobs |
| 8 | Slow queries, huge emails | One query per user, no post limit | Limit posts, batch user IDs |
| 9 | One failure ends the batch | `export_posts`-style single try/except | try/except and commit per user |
| 10 | Wrong time window | Naive UTC timestamps mixed with aware ones | Compare in naive UTC consistently |

Riskiest: #2, duplicate or missed digests from retries or overlapping runs, because a resend reaches every user's inbox and can't be undone.
