## Assumptions (non-interactive)

1. **The current `author` stays as the "primary author" (owner).** `Article.authorId` and the `author` object in responses don't change shape or meaning.
2. **Co-authors are an additional list.** Responses get a new field, `coAuthors: Profile[]` (`[]` when there are none). Clients that ignore unknown JSON fields won't notice.
3. **Permissions:** co-authors can edit the content (`PUT`). Only the primary author can delete the article or change the co-author list.
4. **Input format:** `POST/PUT /articles` accept an optional `article.coAuthors: string[]` of usernames.
5. **Existing filters keep their meaning:** `?author=` keeps meaning "primary author" and `/articles/feed` keeps following primary authors only. Co-author filtering goes behind a new query param.
6. **Postgres + Prisma 4.16.** The migration only adds things, so no backfill is needed.

## Ways this could go wrong (found in this code)

- **Slugs depend on whoever is editing.** `updateArticle` builds `newSlug = slugify(title)-${id}`, where `id` is the person making the request (`article.service.ts`, inside `updateArticle`). Today only the owner can edit, so that's harmless. Once co-authors can edit, a co-author changing the title gives the article a new URL ending in *their* user id. The old URL breaks, and the result can collide with a slug the co-author already has.
- **The favorite/unfavorite responses are built by hand.** They do `...article` on the raw Prisma result instead of using `articleMapper`, and they already leak `favoritedBy: true`, which is full User rows including `password` and `email`. Adding `coAuthors` to that include would also leak each co-author's raw `followedBy` lists, and those responses would look different from every other endpoint.
- **The include block is copied 7 times** (list, feed, create, get, update, favorite, unfavorite). If one copy misses `coAuthors`, `articleMapper` either crashes on `undefined.map` or returns inconsistent data.
- **`authorMapper` calls `author?.followedBy.some(...)`.** It throws if the co-author select leaves out `followedBy`.
- **Who can see what.** `buildFindAllQuery` only shows articles where the primary author is `demo` or the person asking. A non-demo co-author wouldn't see articles they co-wrote unless the OR is extended. Extending it changes `articlesCount` for nobody else, but it needs care.
- **Widening `?author=` or the feed to include co-authors** would silently change list contents and counts for current clients.
- **The authorization check only knows the owner.** `existingArticle.author.id !== id` is used for both update and delete. Changing it too broadly would let co-authors delete or reassign the article.
- **PUT semantics.** The existing `tagList` update wipes tags when the field is left out (`disconnectArticlesTags` always runs). Copying that pattern would wipe co-authors on every edit that doesn't mention them.
- **Input validation:** unknown usernames, duplicates, the owner listing themselves, or very large lists.
- **Deleting users.** A deleted co-author should drop out of the join table (cascade). A deleted owner still cascade-deletes the whole article, so co-authors lose it. That should be a documented decision.
- **Tests and seed** use a Prisma mock with hand-written article objects. Those fixtures need `coAuthors`, or the mapper will throw in tests.

## Plan

1. **Schema** (`src/prisma/schema.prisma`). Add an implicit many-to-many relation:
   - on `Article`: `coAuthors User[] @relation("ArticleCoAuthors")`
   - on `User`: `coAuthoredArticles Article[] @relation("ArticleCoAuthors")`
   
   This follows the pattern already used by `tagList` and `favoritedBy`. Generate it with `prisma migrate dev --name article_coauthors`. It only creates the join table `_ArticleCoAuthors` with cascade foreign keys and doesn't touch `authorId`.
2. **One shared include** in `article.service.ts`. Pull the repeated include into a single `articleInclude` const and add `coAuthors: { select: { username, bio, image, followedBy } }`. Use it in all 7 places.
3. **Mapper** (`article.mapper.ts`). Add `coAuthors: (article.coAuthors ?? []).map(u => authorMapper(u, id))`. Leave `author` exactly as it is.
4. **Favorite/unfavorite.** Switch them to `articleMapper` so they return the same shape as other endpoints. This also stops the leak of `favoritedBy`, `id` and `authorId`. Strictly that's a response change, so call it out in the PR. If you want zero change there, at minimum add a mapped `coAuthors` to their hand-built result.
5. **Create.** Validate `coAuthors`: it must be an array of strings, every username must exist (otherwise 422), remove duplicates, drop the owner, and cap the length (e.g. 10). Then `connect: [{ username }]`. The slug stays `slugify(title)-${ownerId}`.
6. **Update.**
   - Select `author.id` plus `coAuthors.id`. Allow the request if the user is the owner or a co-author.
   - Build the slug from `existingArticle.author.id`, not the requester's id.
   - Change the co-author list only if `coAuthors` is present in the body, and only if the requester is the owner (otherwise 403). Use `set: [...]` for that.
   - Don't copy the tag-wiping pattern.
7. **Delete.** Unchanged: owner only.
8. **Listing.** In `buildFindAllQuery`:
   - Add an OR branch so the person asking also sees articles where they're a co-author: `coAuthors: { some: { id } }`.
   - Add a new `?coauthor=username` filter.
   - Leave `?author=` and `getFeed` as they are.
9. **Docs.** Update the JSDoc on the controller routes and the README API notes. Routes and URLs don't change.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Slug rewritten with the co-author's id | `updateArticle` uses the requester's `id` in `newSlug` | Build the slug from `existingArticle.author.id`; add a test |
| 2 | Leaking user data in favorite responses | The `...article` spread already leaks `favoritedBy` rows (password, email); raw `coAuthors` adds more | Route favorite/unfavorite through `articleMapper` |
| 3 | Inconsistent or crashing responses | The include block is copied 7 times; `authorMapper` needs `followedBy` | One shared `articleInclude`; `?? []` in the mapper |
| 4 | Changed list results for current clients | Widening `?author=` or the feed changes contents and `articlesCount` | Keep their meaning; add a new `?coauthor=` param |
| 5 | Too much power for co-authors | A loosened owner check could cover delete or co-author changes | Separate checks: edit = owner or co-author; delete and co-author list = owner |
| 6 | Co-authors wiped on edit | Copying the `tagList` "always reset" pattern | Change the list only when `coAuthors` is in the body |
| 7 | Hidden co-authored articles | The visibility filter only looks at the primary author's `demo`/id | Add an OR on `coAuthors.some.id` |
| 8 | Bad input | Unknown, duplicate or self usernames; huge lists | Validate, dedupe, cap; return 422 |
| 9 | Slow queries | Each co-author loads their full `followedBy` list | Cap the list; later select only the requester's follow relation |
| 10 | Unit tests and seed break | Mock fixtures have no `coAuthors` | Update fixtures; default to `[]` in the mapper |

Riskiest: #1 — a co-author renaming the title gives the article a new URL with their user id, which breaks the existing article URL that the change has to preserve.
