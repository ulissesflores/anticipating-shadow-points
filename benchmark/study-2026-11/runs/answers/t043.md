I've written a plan for co-authored articles and edited no repo files. The plan is in `claude-home/plans/allow-an-article-to-validated-nautilus.md`. Nothing was run or tested.

## Assumptions (no one to ask in this run)
- **Who the `author` is:** the existing `author` / `authorId` stays as the article's **owner**. Co-authors are added on top of it.
- **API changes only add things:** responses gain `article.coAuthors: Profile[]`, and POST/PUT accept an optional `coAuthors: string[]` of usernames. `article.author` keeps its current shape and meaning.
- **Who can do what:** only the owner can delete the article or change the co-author list. Co-authors can edit the title, body, description and tags.
- **Slugs:** the slug suffix always uses the owner's id.

## Ways this could go wrong (found in the code)
1. **URLs change when a co-author renames.** `updateArticle` builds the new slug from the *editor's* id (`${slugify(title)}-${id}`). If a co-author renames the article, the slug changes and old links break.
2. **Deleting a co-author could delete the article.** `Article.author` uses `onDelete: Cascade`. If co-authors are modelled the same way, deleting a co-author's account deletes the article.
3. **Raw database fields leak into responses.** `favoriteArticle` and `unfavoriteArticle` copy the whole database row into the response (`...article`). Any new include would appear in those responses, and their shape already differs from `articleMapper`.
4. **Edits are owner-only today.** Update and delete check `existingArticle.author.id !== id`, so co-authors would get 403 unless the update check changes.
5. **Article visibility.** `buildFindAllQuery` only shows articles whose author is `demo` or the current user. Without a change, co-authors can't see their own co-authored articles in listings.
6. **Article counts can stop matching the list.** `getArticles` and `getFeed` count with one query and fetch with another. If only one of them gets the co-author filter, the totals won't match the returned articles.
7. **The `?author=` filter.** Making it also match co-authors would quietly change which articles existing clients get back.
8. **Duplicated query code.** The same author `include` block is copy-pasted 7 times in `article.service.ts`, so it's easy to miss one.
9. **Slower, bigger responses.** The include loads each author's full `followedBy` list, and a co-author list multiplies that per article.
10. **Database migration.** The migration must only add a new table. Changing `authorId` (dropping it or making it nullable) would break every existing query.

## Approach (summary)
- **Database:** add an explicit join table `ArticleCoAuthor(articleId, userId, position)`. It cascades on both sides, so deleting a co-author only removes the link. It's a new table only, so no backfill.
- **Shared query:** replace the 7 copied include blocks with one `articleInclude`.
- **Responses:** `articleMapper` adds `coAuthors`. Favorite/unfavorite get cleaned up so they keep exactly their current output keys.
- **Create/update:** check that co-author usernames exist, and remove duplicates and the owner. Owner or co-author may edit. Only the owner may change the co-author list. The slug always uses the owner's id.
- **Filters:** `?author=` keeps matching the owner only. Add an optional new `?coauthor=` filter.
- **Tests:** a migration dry-run on a copy of the data, the unchanged e2e suite as the compatibility check, and new unit tests for slug stability and owner-only delete.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Slug changes on a co-author's edit | Slug is built from the editor's `id` in `updateArticle` | Build it from `existingArticle.author.id` |
| 2 | Article deleted with a co-author | Author relation uses `onDelete: Cascade` | Join table cascades only the link row |
| 3 | Favorite responses change shape | `...article` spread returns raw rows | Use the mapper, keep current keys |
| 4 | `author` field changes meaning | Clients expect one profile object | Keep `author`, add `coAuthors` |
| 5 | Co-authors get 403 on edit | Owner-only `author.id !== id` check | Allow owner or co-author; delete stays owner-only |
| 6 | Counts don't match lists | Count and fetch use separate queries | One shared `where` per endpoint |
| 7 | `?author=` results change | Clients filter by owner username | Keep it owner-only; add `?coauthor=` |
| 8 | One query path missed | 7 copied include blocks | Single `articleInclude` const |
| 9 | Slower, bigger responses | Full `followedBy` loaded per author | Select only `id`; cap co-authors |
| 10 | Migration breaks existing rows | Touching `authorId` breaks queries | Add a table only; test on a data copy |

Riskiest: #1. A co-author renaming an article changes its slug, which silently breaks existing article URLs.
