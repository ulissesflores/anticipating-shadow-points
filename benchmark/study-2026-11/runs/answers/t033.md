This is the FastAPI + SQLModel app. Right now, deleting a user removes the row for good and takes their items with it, both in `backend/app/api/routes/users.py` and through cascade settings in `models.py`.

## Ways this could go wrong (checked against the code)
1. **Deleted users can still use the app.** The current "is this user allowed in" checks in `deps.get_current_user`, `crud.authenticate` and `login.py` only look at whether the account exists and is active. A hidden account still exists, so its login tokens (valid for 8 days) and its password would keep working.
2. **Password reset brings the account back.** Password recovery (`login.py` around lines 58, 85 and 109) looks users up by email without checking for deletion. A reset link would let a deleted user back in without an admin.
3. **Items still get deleted.** The delete endpoint explicitly deletes the user's items, and the database cascades item deletes from users. If any code path still truly deletes a user, the items go too, which breaks "keeps their items".
4. **Restore gets mixed up with "inactive".** Reusing the existing `is_active` flag as "deleted" would collide with admins deactivating accounts. A restore could then reactivate a user an admin had deliberately turned off.
5. **The email address stays taken.** Email must be unique. While the hidden account exists, nobody can sign up again with that address. If we freed the address, a restore could later clash with the new account.
6. **Lists and counts are wrong.** The admin user list and its total count need the same filter, or the pages and numbers won't match. Looking up a deleted user by id should return "not found" to normal users.
7. **The 30-day window is fuzzy.** Mixing local and UTC times, or deciding whether day 30 counts, can make the cutoff off by a day. Nothing purges accounts after 30 days, because the app has no scheduler.
8. **Migrations, tests and the frontend.** It needs a new database migration. Existing tests that check items are gone will fail. The frontend's generated API client and the admin delete wording also need updating.

## Assumptions
- I'll add a nullable `deleted_at` timestamp to the user record instead of reusing `is_active`.
- Items stay unchanged in the database. Admins still see them; the owner can't log in to see them.
- After 30 days, restore returns 410 (gone). There's no automatic purge.
- The email address stays reserved while the account is hidden.
- Superusers still can't delete themselves.

## Plan
1. Add `User.deleted_at` with an Alembic migration, and include it in what the API returns about a user.
2. Block deleted users in one shared place, `get_current_user`, and also in `authenticate` and the three password-recovery paths.
3. Change both delete endpoints to set `deleted_at` instead of deleting the user and their items.
4. Add `POST /users/{id}/restore` for superusers. It returns 404 if the user isn't deleted and 410 after the window, which is set in config as `USER_RESTORE_WINDOW_DAYS=30`.
5. Hide deleted users from the admin list and its count, with an `include_deleted` option for admins. Return 404 for deleted users on read and update unless the caller is a superuser.
6. Frontend: regenerate the API client, add a Restore action and a "show deleted" filter, and update the delete confirmation text.
7. Tests: login blocked, old token rejected, items kept, restore inside and outside the window, email reserved, password reset ignored, list filtering.

To check it works: run `scripts/test.sh`, apply and roll back the migration, run the Playwright admin tests, and do a manual delete → restore run, including setting `deleted_at` back 31 days to see restore refused.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Deleted user keeps access | Login and token checks only look at existence and `is_active`; tokens last 8 days | Check `deleted_at` in `get_current_user` and `authenticate` |
| 2 | Password reset revives account | Recovery and reset look up by email with no deletion check | Treat deleted users as not found in `login.py` |
| 3 | Items still deleted | Explicit item delete plus database cascade | Remove the hard delete; add a test that items survive |
| 4 | Restore clobbers admin's deactivation | `is_active` is already set by admins | Separate `deleted_at` field; restore only clears it |
| 5 | Email locked or clashing | Email must be unique | Keep it reserved during the window; signup returns 400 |
| 6 | Wrong user lists and counts | List and count are separate queries | Same filter on both; `include_deleted` option |
| 7 | 30-day cutoff off by a day | Mixed time zones; unclear boundary | UTC only, a config constant, a test at the boundary |
| 8 | Tests and frontend out of sync | Existing tests expect items gone; generated API client | Update the tests and regenerate the client |

Riskiest: #1. Deleted users would keep working access through their existing tokens and passwords unless `get_current_user` and `authenticate` check `deleted_at`.
