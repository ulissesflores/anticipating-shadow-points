## Plan: weekly digest of followed users' posts

**Context:** this is the Microblog app at Chapter 23. It already has followers, Flask-Mail (`app/email.py`) and an RQ worker (`app/tasks.py`). It has no scheduler and no email preferences.

**Assumptions** (non-interactive run, so I chose these rather than asking):
- **Trigger:** an external weekly cron (or Heroku Scheduler) runs `flask digest send`. No new scheduler dependency.
- **Default and opt-out:** the digest is on by default. Users can turn it off in Edit Profile or with a one-click unsubscribe link in the email.
- **Empty weeks:** a user with no new posts from people they follow gets no email.
- **Own posts excluded:** `User.following_posts()` (`app/models.py:173`) includes your own posts, so it can't be reused as is.
- **Language:** emails are in English. Babel's `get_locale` reads `request`, which doesn't exist in the worker, and the app stores no per-user language.
- **Length:** each email shows at most 20 posts, plus "and N more".

**Steps:**
1. **Database and model** (`app/models.py`, plus one migration):
   - Add `User.digest_enabled` (on by default) and `User.last_digest_sent_at`.
   - Add a new query, `User.digest_posts(since)`: posts by people the user follows, newer than `since`, not by the user.
   - Add unsubscribe token helpers, copied from the JWT pattern in `get_reset_password_token`.
2. **Job** (`app/tasks.py`): add `send_digest(user_id)`.
   - It works out the window as `last_digest_sent_at`, or 7 days ago if never sent.
   - It skips the user if they opted out or have no new posts.
   - Otherwise it renders the email, sends it with `send_email(..., sync=True)`, then records the send time and commits.
   - It uses the same error logging as `export_posts`, but not `launch_task` or `_set_task_progress`, because those would create Task rows and progress bars in the UI.
3. **Command** (`app/cli.py`): add `flask digest send [--dry-run] [--user]`. It queues one `send_digest` job per eligible user (enabled, and last sent more than 6 days ago) on `app.task_queue`.
4. **Templates:** add `email/digest.txt` and `email/digest.html`, modelled on the `export_posts.*` emails. They include profile links and an unsubscribe link, and don't use `_()`.
5. **Preferences:**
   - Add a "Weekly digest email" checkbox to `EditProfileForm` and the `edit_profile` route (`app/main/routes.py:97`).
   - Add a public `/unsubscribe/<token>` route.
   - Run `flask translate update` and add the Spanish strings.
6. **Operations:**
   - Document the weekly cron line in the README.
   - Set `SERVER_NAME` and `PREFERRED_URL_SCHEME` wherever the worker and cron run.

**Verification:**
- **New tests in `tests.py`:**
  - The digest query excludes your own posts, posts by people you don't follow, and posts older than the window.
  - `send_digest` sends one email, and skips users with no posts or who opted out. Checked with `mail.record_messages()`.
  - The command queues only eligible users, using a mocked queue.
  - The unsubscribe token round-trips.
- **Manual run:**
  1. Start the RQ worker and a local `aiosmtpd` debugging server.
  2. Run `flask digest send --user susan` twice and check the second run sends nothing.
  3. Click the unsubscribe link.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate or missed digests | Cron reruns, worker retries or a crash between sending and committing can resend, and a silent skip can lose a week | Window based on `last_digest_sent_at`; only queue users last sent more than 6 days ago; commit right after sending |
| 2 | Broken links in the email | `url_for(_external=True)` in the worker has no request, so it needs `SERVER_NAME` | Set `SERVER_NAME` and `PREFERRED_URL_SCHEME` in the worker env; test it |
| 3 | Babel crash in the worker | `get_locale()` reads `request.accept_languages` | No `_()` in digest templates, or wrap rendering in `force_locale('en')` |
| 4 | Own posts in the digest | `following_posts()` includes the user's own posts | New `digest_posts()` that excludes them; unit test it |
| 5 | Spam complaints or blacklisting | Emails are never verified, it's on by default, and nothing could opt out before | Opt-out link in every email, a preference toggle, skip empty digests |
| 6 | Timezone mismatch in the time window | Timestamps come back from SQLite naive but are compared with timezone-aware values | Compare as UTC consistently; test against SQLite and Postgres |
| 7 | Load spike on SMTP and the worker | One email per user in one burst through the single `microblog-tasks` worker; export jobs wait behind it | Send in batches or throttle, use a separate queue, run off-peak |
| 8 | Unsubscribe token can be forged or reused | Reusing the reset-password JWT style without its own key name lets one token type pass as the other | A separate claim name (`unsubscribe`); the token only flips one flag |
| 9 | The schedule never runs | Nothing in Procfile or supervisor schedules jobs, so a missing cron means silent failure | Document the cron, log a run summary, add `--dry-run` |
| 10 | Migration default for existing users | A new non-null boolean column breaks existing rows without a server default | `server_default=sa.true()` in the migration |

Riskiest: #1. A resent or silently skipped weekly email is the failure users will notice and complain about.
