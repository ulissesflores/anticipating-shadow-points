I've written the plan to `claude-home/plans/let-a-user-sign-compiled-bengio.md`; no other files were changed. The current Google login code has two security holes that block safe linking, so the plan fixes them first. It reads Google's sign-in token without checking its signature and never checks Google's `email_verified` flag. Separately, anyone can create a password account for any email address without proving they own it.

**What I found**
- **Two login paths, not connected.** Password login lives in `styleguide_example/authentication/apis.py`. Google login exists only as blog demos in `blog_examples/google_login_server_flow/{raw,sdk}/apis.py`. That callback looks up the user by exact email and returns 404 if there is none.
- **Token not checked.** Both `decode_id_token` copies use `jwt.decode(..., verify_signature=False)` and nothing checks `email_verified`.
- **Open signup.** `UserCreateApi` is public and never verifies the email.
- **Email case.** `create_user` stores emails in lower case, but the email filter matches exactly, so a Google email in different case won't match.

**Assumptions**
- Google login uses sessions, as in the demos; JWT login stays password-only.
- The real flow moves into the `authentication` app, and the blog demos call it.
- Only Google accounts with a verified email can link or create accounts.
- Every existing password account counts as "email unverified", since there is no verification flow.

**Plan**
1. **Model and migration `0004`:** add a `UserGoogleIdentity` table (user, unique Google account ID `sub`, email when linked). Add `BaseUser.email_verified_at`.
2. **`google_id_token_verify`:** check the token with `google.oauth2.id_token.verify_oauth2_token` (the `google-auth` library is already installed), with our client ID as the audience. Reject when `email_verified` is not true. This replaces both unsigned decodes.
3. **`user_get_or_create_from_google`**, in one transaction:
   - Look up the user by Google `sub` first.
   - Otherwise match by email, ignoring case.
   - If that account has a password and an unverified email: disable the password, invalidate existing JWT tokens (`auth_logout`), and tell the client to prompt "set a password". This stops someone who pre-registered the victim's email from keeping access.
   - If there is no matching account, create one with no password.
   - Save the Google link, set `email_verified_at`, and retry once if two first logins collide.
4. **Google callback:** call the service, then `login()`. Return `user_get_login_data` instead of the raw token, and drop the 404 that reveals whether an email has an account.
5. **`UserPasswordSetApi` (`auth/password/set/`):** requires login, and the current password if one exists. It checks password rules, then invalidates JWT tokens and refreshes the session. This lets Google-created users add a password.
6. **Password login:** no change needed; it already fails cleanly for accounts with no password.
7. **Admin:** show Google links inline on the user page, and show `email_verified_at` as read-only.

**Verification:** add tests with mocked Google token checks for:
- a new Google user;
- linking an unverified password account (old password and JWT stop working);
- linking a verified account (password still works);
- a forged token, wrong client ID, or `email_verified=false` being rejected;
- emails that differ only in case;
- a Google email change still matching by `sub`;
- setting a password, then logging in both ways.

Then run `pytest` and `mypy`, and do one manual sign-in with real Google credentials.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Account pre-hijacking | Anyone can register any email with a password, and auto-linking would keep the attacker's password | Disable the password and invalidate JWTs on first link to an unverified account |
| 2 | Forged sign-in token | Signature checking is turned off in both demos | `verify_oauth2_token` with audience check |
| 3 | Unverified Google email | `email_verified` is never checked | Reject unless `email_verified` is true |
| 4 | Legit users lose their password | No email verification exists, so all current accounts count as unverified | "Set password" endpoint and prompt; tell users before launch |
| 5 | Email case mismatch | Exact match against lower-cased stored emails | Lower-case and match ignoring case |
| 6 | Google email changes or is reused | Matching only by email can attach to the wrong account | Key on Google `sub` after the first link |
| 7 | Duplicate accounts from concurrent logins | Two first logins at once | Unique constraints, transaction, retry on conflict |
| 8 | Old sessions and JWTs stay valid | Password changes don't invalidate tokens on their own | Invalidate JWT tokens and refresh the session on link and on password set |
| 9 | Revealing whether an account exists | The current 404 names the email | Remove it; use generic errors |
| 10 | Blog demos break | They share the changed decode code | Point demos at the new service; cover them with tests |

Riskiest: #1, account pre-hijacking. The public signup has no email verification, so linking by email alone would let an attacker keep a password on the victim's account.
