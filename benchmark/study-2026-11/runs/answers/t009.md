## Assumptions
- **Who gets it:** every user with an email address. The repo has no opt-out today, so I'd add a `digest_opt_in` flag that defaults to on and a one-click unsubscribe link. Sending to everyone with no way to stop it is the biggest problem with the request as written.
- **What's in it:** posts written in the last 7 days by people the user follows. The user's own posts are left out. Users with no new posts get no email.
- **Schedule:** once a week, started by a `flask digest send` CLI command. Cron, Heroku Scheduler or a systemd timer runs it. `rq==1.15.1` has no built-in scheduler, and adding `rq-scheduler` would be another process to run.
- **Sending:** through the existing RQ worker queue (`microblog-tasks`), as one job per small batch of users. The emails are sent with `sync=True`.

## Ways this could go wrong (checked against the code)
1. **`User.following_posts()` (`app/models.py:166`) includes the user's own posts** through the `Author.id == self.id` branch. If it's reused as-is, every digest contains your own posts.
2. **`get_locale()` (`app/__init__.py:17`) reads `request.accept_languages`.** A cron job or worker has no request, so any `_()` in a template raises an error. The digest needs its own locale (English, or a new per-user language field).
3. **`url_for(..., _external=True)` needs `SERVER_NAME`** when there's no request. It's optional in `config.py`, so links break or the call fails.
4. **`send_email` starts a thread by default** (`app/email.py`). In a short-lived CLI or worker process those threads can die before they send, or open hundreds of SMTP connections. Use `sync=True` inside a job, as `export_posts` already does.
5. **Duplicate or missed sends.** Cron retries, overlapping runs or worker restarts can send twice. A failed run can skip a week. This needs a `last_digest_sent_at` per user, used both as the start of the window and as a send-once guard.
6. **Timezones:** `Post.timestamp` is naive UTC. The window has to use UTC consistently or posts get counted twice or dropped.
7. **Cost and SMTP limits:** one job per user, or N+1 queries per user, against an SMTP server with no rate limit. That leads to throttling, spam-folder placement and blocked senders. Batch the jobs and limit posts per email (for example the top 20, then "and N more").
8. **Privacy and compliance:** unsolicited bulk email with no unsubscribe link. That can break CAN-SPAM/GDPR and annoy users. The unsubscribe token must be signed (reuse the JWT pattern in `get_reset_password_token`) and must not expire too quickly.
9. **Do not reuse `launch_task`.** It creates a `Task` row for the user and `_set_task_progress` sends notifications, so users would see digest progress pop-ups in the UI.
10. **Untested scheduling:** nothing in the repo runs on a schedule (`Procfile`, supervisor, Docker `boot.sh`). It's easy to ship the code and never actually trigger it in one of those three deploy targets.

## Plan
1. **Model and migration** (`app/models.py`, new Alembic revision):
   - Add `User.digest_opt_in` (bool, default True, server_default true) and `User.last_digest_sent_at` (datetime, nullable).
   - Add `User.followed_posts_since(since)`: join followers on `follower_id == self.id`, `Post.timestamp > since`, ordered by newest first, with a limit. The own-posts branch is excluded.
2. **Task** (`app/tasks.py`):
   - Add `send_weekly_digest(user_ids)`. For each user, take the window start from `last_digest_sent_at` (or now − 7 days), query posts, skip if there are none, render and send with `sync=True`, then set `last_digest_sent_at` and commit per user.
   - Wrap each user in try/except so one bad address doesn't stop the batch. It doesn't use `_set_task_progress`.
3. **CLI** (`app/cli.py`): add `flask digest send [--dry-run] [--batch-size 100]`.
   - Select opted-in users whose `last_digest_sent_at` is null or more than about 6.5 days ago.
   - Enqueue batches with `current_app.task_queue.enqueue('app.tasks.send_weekly_digest', ids)`.
4. **Templates:**
   - Add `app/templates/email/weekly_digest.{txt,html}`, based on `reset_password.*`.
   - Include post author, body, a link to the profile and an unsubscribe link.
   - Avoid `_()`, or force English with `flask_babel.force_locale('en')`.
5. **Unsubscribe:**
   - Add a token route in `app/main/routes.py` that turns the flag off, a signed JWT like the password reset token, and a checkbox in `EditProfileForm` (`app/main/forms.py`) plus the `edit_profile` handler.
   - Optionally add a `List-Unsubscribe` header.
6. **Config and deploy:**
   - Require `SERVER_NAME` (and `PREFERRED_URL_SCHEME`) for digest runs. The CLI should fail fast if it's missing.
   - Document a weekly cron entry, e.g. `0 8 * * 1 flask digest send`. Add a Heroku Scheduler note and a supervisor or systemd timer example in `deployment/`.
7. **Tests** (`tests.py`):
   - Unit test `followed_posts_since`: it excludes own posts, unfollowed authors and posts outside the window.
   - Test the task with mail suppressed (`MAIL_SUPPRESS_SEND`, `mail.record_messages()`): no email for an empty digest, opted-out users are skipped, and running twice sends once.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Own posts in digest | `following_posts()` ORs in `Author.id == self.id` | New `followed_posts_since()` query |
| 2 | Crash outside request | `get_locale()` reads `request` | `force_locale` / per-user lang; no request-bound code |
| 3 | Broken links | `url_for(_external)` needs `SERVER_NAME`, which is optional | Require it; fail fast in CLI |
| 4 | Duplicate/missed sends | Cron/RQ retries, no send record | `last_digest_sent_at` guard + window |
| 5 | Lost emails | `send_email` defaults to daemon thread | `sync=True` inside worker |
| 6 | Spam/compliance | Bulk mail to "every user", no opt-out exists | Opt-in flag, signed unsubscribe, List-Unsubscribe |
| 7 | SMTP throttling / slow run | One SMTP send per user, no batching | Batched jobs, cap posts, skip empty digests |
| 8 | UI notification noise | `launch_task`/`_set_task_progress` create Task rows and notifications | Enqueue directly, no progress tracking |
| 9 | Never runs in prod | No scheduler in Procfile/supervisor/Docker | Documented cron/timer per deploy target |
| 10 | Timezone window errors | Naive UTC timestamps | UTC everywhere; window from stored timestamp |

Riskiest: #6, bulk email to every user with no opt-out or unsubscribe. That breaks compliance rules and hurts sender reputation for all of the app's mail, including password resets.
