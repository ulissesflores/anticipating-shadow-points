I didn't edit any files. This is a plan only. The repo is the standard Django + Postgres + Gunicorn + Nginx Docker Compose setup. The files that matter are `docker-compose.prod.yml`, `app/entrypoint.prod.sh` and `nginx/nginx.conf`.

## Assumptions
- Production runs on a single Docker host with `docker compose -f docker-compose.prod.yml`, not Swarm or Kubernetes.
- "On every deploy" means a deploy script, run by hand or by CI on the host, carries out every step. Nobody runs commands by hand.
- Postgres stays in the same Compose project, and its data volume is kept between deploys.
- Running two copies of `web` for a short time on one host is acceptable (blue/green by scaling).

## How it works today (the causes of downtime)
1. **Updating the app restarts it with a gap.** `docker compose up -d --build` stops the old `web` container before the new one is ready, so the site is down while it starts.
2. **Nginx keeps using the old container's address.** `upstream { server web:8000; }` in `nginx/nginx.conf` looks up the address once, when Nginx starts. A new container gets a new IP, so Nginx keeps returning 502 errors until it is reloaded.
3. **There's no health check.** No endpoint and no Compose `healthcheck`, so nothing can tell when the new container is ready.
4. **Production never runs migrations.** `app/entrypoint.prod.sh` only waits for the database. The dev `app/entrypoint.sh` runs `flush --no-input` before `migrate`, which deletes all data. That file must never be copied into production.
5. **Static files go stale.** The `static_volume` named volume is filled from the image only when the volume is first created. New static assets won't reach Nginx unless `collectstatic` runs on each deploy.
6. **Shutdown cuts off requests.** Docker gives a container 10s to stop by default, then kills it. Requests still in progress can be dropped.
7. **Rollback isn't possible.** Images are rebuilt with no tag, so there's no previous image to go back to.
8. **Debug mode is probably on in production.** In `settings.py`, `DEBUG = bool(os.environ.get("DEBUG", default=0))` turns `DEBUG=0` into `True`, because the text `"0"` counts as true. This is a separate bug, but during a failed deploy, debug error pages would show internal details.

## Plan

**1. Readiness signal**
- Add a `/healthz` view in `app/hello_django/urls.py` that runs `SELECT 1` and returns 200.
- Add a `healthcheck` to `web` in `docker-compose.prod.yml` using `python -c "urllib.request.urlopen('http://localhost:8000/healthz')"`, because the image has no curl.

**2. Versioned images**
- Set `image: hello_django_web:${TAG}` next to `build:`, with `TAG` = the git SHA. This makes rollback a redeploy of the previous tag.

**3. Migrations: one step per deploy, not in every container's startup**
- Run them in a new `deploy.sh` with `docker compose run --rm web python manage.py migrate --noinput`. They should run once, before any traffic moves to the new version.
- Don't put them in `entrypoint.prod.sh`. With two web containers starting together, they would race each other.
- Before migrating, take a `pg_dump` backup and set a short lock timeout (`PGOPTIONS='-c lock_timeout=5s'`) so a blocked `ALTER TABLE` fails quickly instead of stalling the site.
- If the migration fails, stop the deploy. The old container keeps serving.
- In CI, add `makemigrations --check` so missing migrations are caught before deploy.

**4. Static files**
- Run `collectstatic --noinput` in `deploy.sh` after migrating. It writes into the shared `static_volume` and only adds or overwrites files, so the old version's assets are still served during the switch.

**5. Rollout in `deploy.sh`**
1. Build the new image.
2. Back up the database, then migrate.
3. Run `collectstatic`.
4. Start a second web container: `docker compose up -d --no-deps --no-recreate --scale web=2 web`.
5. Wait until the new container reports healthy (with a timeout; on timeout, remove it and stop the deploy).
6. `nginx -s reload`, so Nginx sends traffic to both containers.
7. `docker stop` the old container (with a grace period), then remove it.
8. `nginx -s reload` again, then return the scale to 1.

**6. Graceful shutdown**
- Add `--graceful-timeout 30` to the Gunicorn command and `stop_grace_period: 40s` to `web`.
- In `nginx.conf`, add `proxy_next_upstream error timeout http_502` so a request that hits a container while it is stopping is retried on the other one.

**7. Migration rules (written in the README)**
- Every migration must work with both the old and the new code: add first, remove later.
- Renaming or dropping a column takes two deploys.
- Indexes on large tables use `AddIndexConcurrently` with `atomic = False`.

**8. Debug fix**
- Fix it as a separate one-line change: `DEBUG = os.environ.get("DEBUG", "0") == "1"`.

**Files touched:** `docker-compose.prod.yml`, `nginx/nginx.conf`, `app/hello_django/urls.py`, `app/hello_django/settings.py`, a new `deploy.sh`, and `README.md`. `app/entrypoint.prod.sh` stays as it is.

## Verification
1. Run `while true; do curl -s -o /dev/null -w '%{http_code}\n' localhost:1337/; done | sort | uniq -c` during a deploy. Expect only 200s.
2. Deploy a migration that adds a nullable column while that loop is running. Expect zero errors.
3. Deploy a migration that is deliberately broken. The script should stop and the old version should keep serving.
4. Deploy an image whose `/healthz` fails. The script should time out, remove the new container and leave traffic on the old one.
5. Roll back by deploying the previous `TAG` and confirm it works.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Migration breaks the old code still serving traffic | Old and new containers run together on one database | Add first, remove later; two deploys for drops and renames |
| 2 | Migration takes table locks and stalls the site | Postgres `ALTER TABLE` / `CREATE INDEX` block reads and writes | `lock_timeout`; build indexes concurrently |
| 3 | Dev entrypoint copied into production | `entrypoint.sh` runs `flush` before `migrate` | Migrate only in `deploy.sh`; never reuse the dev entrypoint |
| 4 | Nginx keeps sending traffic to the old container | `upstream web:8000` is looked up once, at startup | Reload Nginx after each switch; retry on 502 |
| 5 | Two containers run migrations at once | Migrating in the entrypoint plus `--scale web=2` | One `run --rm` migrate step before the rollout |
| 6 | Traffic switches before the new app is ready | No health endpoint or `healthcheck` today | `/healthz` + `healthcheck`; wait for healthy |
| 7 | Requests dropped while the old container stops | Docker's 10s stop limit, Gunicorn's defaults | `graceful-timeout` + `stop_grace_period` |
| 8 | Static files stale or missing | The named volume is only filled when first created | Run `collectstatic` on each deploy; it only adds files |
| 9 | No way back after a bad release | Images are untagged and rebuilt in place | Tag images with the git SHA; back up before migrating |
| 10 | Errors show debug pages to visitors | `bool("0")` is `True`, so `DEBUG` is on | Fix the parsing of `DEBUG` |

Riskiest: #1, a migration that the old container still serving traffic can't run against. Zero-downtime deploys always run the old and new code against the same database for a while.
