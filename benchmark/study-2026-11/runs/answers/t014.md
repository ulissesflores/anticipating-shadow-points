## Assumptions
- **Response shape:** current clients use the RealWorld API, which expects one `author` profile object. That field stays exactly as it is. A new `authors: Profile[]` array is added alongside it, with the primary author first.
- **Primary author:** the creator stays the primary author in the existing `Article.authorId` column. Co-authors go in a new join table. So there is no destructive migration and no backfill of the old column.
- **Co-author permissions:** co-authors can edit the article. Only the primary author can delete it or change the author list.
- **Where co-authors appear:** filtering by `?author=` and the feed both match any co-author, not just the primary author.
- **Slugs:** an existing slug never changes just because co-authors are added or removed.

## Ways this could go wrong (found in the code)
1. **Slugs depend on whoever edits the title.** Slugs are built as `${slugify(title)}-${id}` in both `createArticle` and `updateArticle`. In `updateArticle`, `id` is the person editing. If a co-author changes the title, the slug's suffix switches to their user id, and old URLs and bookmarks break.
2. **Deleting the primary author still deletes the article.** `Article.author` has `onDelete: Cascade`, so the article disappears for every co-author too.
3. **List visibility is tied to the primary author.** `buildFindAllQuery` only shows articles whose `author` is a demo user or the caller. Co-authored articles would stay hidden from co-authors unless the filter becomes `author OR coAuthors.some`.
4. **Edit and delete checks.** Both use `existingArticle.author.id !== id`. Loosening this carelessly would let co-authors delete the article or remove the owner.
5. **Some responses leak raw fields.** `favoriteArticle` and `unfavoriteArticle` spread `...article` into the response instead of using `articleMapper`. Adding a `coAuthors` include would leak raw user rows (including their `followedBy` lists), and these responses already leak `id`/`authorId`.
6. **Slower queries.** Every query copies the same large `include` block, and `followedBy` loads every follower for each author. Multiplying that by N authors makes list endpoints much heavier.
7. **Bad co-author input.** Duplicate co-authors, the owner listed as their own co-author, unknown usernames, or no limit on list size.
8. **Feed and count mismatches.** `getFeed` and `getArticles` both run `count` and `findMany`. If the `where` is changed in one but not the other, `articlesCount` and the returned page won't match. Adding OR across co-authors can also return duplicates.
9. **Tests.** The tests in `src/tests/services/article.service.test.ts` mock Prisma with fixed shapes. They'll fail, or pass misleadingly, unless the mocks include `coAuthors`.

## Plan
1. **Schema:** add an explicit `ArticleAuthor` join model (`articleId`, `userId`, `createdAt`, unique on `(articleId, userId)`, cascade on both sides). Add `coAuthors` to `Article` and `coAuthoredArticles` to `User`. Create a new migration under `src/prisma/migrations/` that only adds things. Leave `authorId` alone.
2. **Shared include:** put the duplicated include block in one constant in `article.service.ts` and use it everywhere, including favorite/unfavorite.
3. **Mapper:** in `article.mapper.ts`, keep `author` unchanged and add `authors: [author, ...coAuthors]`, reusing `authorMapper`. Switch favorite/unfavorite over to `articleMapper` too. That stops the field leak, but it does remove those leaked fields from those two responses.
4. **Writes:** `createArticle` and `updateArticle` accept an optional `article.coAuthors: string[]` of usernames. Inputs are de-duplicated, the owner is excluded, unknown usernames get a 422, and the list is capped (for example at 10). Only the owner may change the list.
5. **Authorization:** add a `canEdit(article, userId)` helper (owner or co-author) for updates. Deletes stay owner-only.
6. **Slugs:** on a title change, build the new slug with the original `authorId`, not the editor's `id`.
7. **Queries:** `buildFindAllQuery` and `getFeed` use `OR: [{author: …}, {coAuthors: {some: {user: …}}}]`, and `count` and `findMany` share the same `where`.
8. **Owner deletion:** leave the cascade as it is for now and document it. Promoting a co-author is out of scope.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Slugs change when a co-author edits the title | `updateArticle` builds the slug from the editor's `id` | Build it from the stored `authorId` |
| 2 | Breaking current clients' `author` field | RealWorld clients expect one `author` object | Keep `author`, add `authors[]` |
| 3 | Co-authors can delete the article or remove the owner | The single `author.id !== id` check gets loosened | Separate edit and delete rights |
| 4 | Article lost when the primary author is deleted | `onDelete: Cascade` on `author` | Document it now, handle it later |
| 5 | Co-authored articles hidden from co-authors | `buildFindAllQuery` filters on `author` only | Add an OR over `coAuthors` |
| 6 | Favorite responses leak raw user rows | They spread `...article` instead of using the mapper | Route them through `articleMapper` |
| 7 | Slower list queries | `followedBy` loaded fully for every author | Shared include; select only ids |
| 8 | Count doesn't match the page | `count` and `findMany` built separately | One shared `where` |
| 9 | Migration fails on production data | First explicit join table in this project | Add-only migration; test on a copy |
| 10 | Tests pass but miss bugs | Prisma mocks have fixed shapes | Update mocks and add e2e cases |

Riskiest: #1. A co-author changing the title silently rewrites the slug with their own user id, which breaks existing article URLs.
