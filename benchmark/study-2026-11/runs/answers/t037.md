I've written the plan to `claude-home/plans/let-a-user-sign-lucky-orbit.md`. No repo files were edited.

**How things stand:** password login (session and JWT) is in `styleguide_example/authentication/apis.py`. Google login exists only as a blog example in `blog_examples/google_login_server_flow/sdk/apis.py`. That example looks the user up by exact email and returns a 404 if none is found. It never creates or links an account, never checks `email_verified`, and reads the ID token without verifying its signature.

**Assumptions:**
- Build on the existing SDK Google flow (`GoogleSdkLoginFlowService`); the `raw` example stays as it is.
- Link only when Google reports `email_verified=true`.
- Save Google's stable account id (`sub`), so later logins don't depend on the email staying the same.
- A first Google login with no matching user creates one with no usable password.
- A first Google login that matches an existing password user links automatically. The app has no email verification, so the old password is disabled and existing sessions and JWTs are revoked at that point (the user can set a new password).
- Google-only users can add a password later through a new endpoint.

**Plan:**
1. **New `GoogleAccount` model** in `users/models.py`: a one-to-one link to `BaseUser`, a unique `sub`, and the last email seen. Add migration `0004` and an admin inline.
2. **New service `user_get_or_link_google(sub, email, email_verified)`** in `users/services.py`, run in one transaction:
   - If `sub` is already linked, return that user.
   - Reject unverified emails.
   - Otherwise find the user by lowercased email (`email__iexact`), locking the row with `select_for_update`.
     - If found, disable the password, rotate `jwt_key` (reusing `auth_logout`) and link the account.
     - If not found, create the user with `user_create(password=None)` and link it.
   - If two first logins race, retry the lookup on `sub`.
3. **Google callback** (`GoogleLoginApi`): replace the email lookup and 404 with the new service and keep the state/CSRF check. Then call `login()` with an explicit backend and return `user_get_login_data`. Also verify the ID token's signature, `aud` and `iss` with `google.oauth2.id_token.verify_oauth2_token`. Optionally move the callback out of `blog_examples` into `authentication/`.
4. **Password login:** `authenticate()` already rejects users with no usable password, so that part needs no change. One fix: lowercase the email in the login serializer, because stored emails are lowercase but login input isn't normalized.
5. **New `UserSetPasswordApi`** at `auth/password/set/`, backed by `user_set_password`. It requires the current password if one exists, runs `validate_password` and rotates `jwt_key`. Optionally add `has_password` / `has_google` to the login data.
6. **Tests:** service tests for create, link, lookup by `sub` after the email changes, unverified email, mixed-case email, and a race. API tests for the callback with the Google calls mocked, checking that `/auth/me/` returns the same user id after Google login and after password login.

**Verification:** `makemigrations --check`, then `pytest`. Then a manual round trip: sign in with Google, set a password, log out, sign in with the password, and confirm `/api/auth/me/` returns the same `id`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Someone registers the victim's email with a password first, then the victim's Google login links to that account | The app never verifies emails, so the matching password account could belong to anyone | Disable the password and rotate `jwt_key` when linking |
| 2 | Linking on an unverified Google email | The current code reads `email` and ignores `email_verified` | Reject unless `email_verified` is true |
| 3 | Forged or swapped ID token | `decode_id_token` uses `verify_signature: False` | Use `verify_oauth2_token` and check `aud` and `iss` |
| 4 | Email case mismatch causes missed links or duplicates | Emails are stored lowercase, but the filter and login input aren't normalized | Lowercase input and look up with `iexact` |
| 5 | Two first logins at once create two links | No lock or unique handling in the flow today | Unique `sub`, `select_for_update`, retry on `IntegrityError` |
| 6 | Google email changes, so the user can't log in or gets the wrong account | Matching by email only | Match on `sub` first; use email only for the first link |
| 7 | A Google session or JWT survives a password change | JWTs depend on `jwt_key` | Rotate `jwt_key` on set-password and on link |
| 8 | `login()` fails or picks the wrong auth backend | `login()` can't tell which backend to use when more than one is configured | Pass `backend=` explicitly |
| 9 | Existing users are surprised when their password stops working | Risk 1's mitigation disables passwords on link | Explain it in the UI and offer the set-password and reset flows |
| 10 | Moving the callback URL breaks the OAuth redirect | `API_URI` reverses a named route that Google has registered | Keep the route, or update the reverse name and the Google console together |

Riskiest: #1. Because nobody verifies emails, a password account created by an attacker could be linked to the victim's Google sign-in unless linking disables the old password and revokes its sessions and tokens.
