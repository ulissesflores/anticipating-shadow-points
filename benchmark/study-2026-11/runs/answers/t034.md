The plan is finished and checked through Phase 6, and I stopped there as you asked. The only file written is the plan file, `claude-home/plans/standard-deploy-new-versions-vivid-blum.md`; nothing in the repo was changed.

## What the repo does today
- Production deploys with `docker-compose -f docker-compose.prod.yml up -d --build`. That replaces the `web` container, so the site is down while the new one boots.
- Even after the new container starts, nginx keeps sending traffic to the old container's address. `nginx/nginx.conf` looks up `web:8000` once at startup and caches it, so visitors get 502 errors until nginx is reloaded.
- Migrations never run in production: `app/entrypoint.prod.sh` only waits for Postgres. The dev `app/entrypoint.sh` runs `flush` (wipes the database) and then `migrate`, so it must never be reused for production.
- Nothing runs `collectstatic` in production, and the static files live in a shared Docker volume that only gets filled from the image when it is empty.
- There are no healthchecks or `/health` route.
- `settings.py` turns DEBUG on whenever the variable is set, including `DEBUG=0` (`bool("0")` is True). So production currently runs with DEBUG on.

## Assumptions (no questions were possible)
- One Docker host with Compose v2.
- Deploys go through a script, `scripts/deploy.sh <git-sha>`.
- "Zero downtime" means no 5xx errors at nginx and in-flight requests finish.
- Migrations follow "expand/contract": the old code must keep working on the new schema, and destructive changes are split across two deploys.
- Rollback means switching back to the previous image; the database schema is never rolled back automatically.

## Plan after revision 1
**Two app containers, switched by nginx.** Production gets two app services, `web_blue` and `web_green`, with images tagged by git SHA. Only one serves traffic at a time. nginx reads the active one from a small included file and finds the container through Docker's internal DNS, so it starts even after a host reboot.

**Deploy sequence:**
1. Take a lock so two deploys can't overlap.
2. Build the image for the new SHA.
3. Back up the database with `pg_dump`; if the backup fails, stop here.
4. Run migrations once as a separate container, never in the entrypoint. A 3-second Postgres lock timeout makes a migration that can't get its lock fail fast instead of blocking live traffic.
5. Run `collectstatic`, using hashed static file names so old and new versions can coexist.
6. Start the idle container and wait up to 90 seconds for its health check to pass.
7. Point the include file at the new container (written atomically), check the config, then reload nginx gracefully.
8. Wait 35 seconds for in-flight requests to finish, then stop the old container.

If anything fails before the nginx reload, the new container is stopped and the old one keeps serving. Compose commands use `--no-deps` so a deploy never restarts `db` or nginx.

**Other pieces:**
- A `/healthz` route that checks the database and returns `ok <sha>`.
- Healthchecks every 2 seconds, gunicorn `--graceful-timeout 30`, and a 35-second stop grace period.
- The DEBUG fix moves into scope, because hashed static file names don't work while DEBUG is on.
- README sections on the migration policy and on rollback (`deploy.sh <prev-sha> --skip-migrate`).

**Proof it works:** a load script runs concurrent GETs and POSTs across each deploy, records which SHA answered, and checks that responses switch from old to new with zero errors. Three failure drills follow:
- A migration blocked by a held table lock: migrate should time out after about 3 seconds and the old version keeps serving.
- A deliberately unhealthy image: same expected result.
- A host reboot.

**Validation:** an independent reviewer that saw only the plan file returned REVISE with 10 issues, and all 10 were addressed in revision 1. The two most important:
- The original load test would have passed even if traffic never switched, which is why each response now reports its SHA.
- A bare `compose up` could have recreated the database container.

`--standard` allows one review round, so the revision was not reviewed again.

**One planned blip:** moving nginx to the new config needs a single nginx rebuild and restart, a few seconds of downtime. Every deploy after that is zero-downtime.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Migration breaks the old code still serving | Old and new run together during every deploy | Expand/contract policy; `makemigrations --check` plus a migration linter |
| 2 | Database migration blocks live queries | Postgres table changes take exclusive locks | `lock_timeout=3s`; the deploy fails and the old version keeps serving |
| 3 | nginx keeps sending traffic to the old container | The current upstream is looked up once and cached | Docker DNS lookup plus atomic config swap and graceful reload |
| 4 | nginx crash-loops after a host reboot | Containers restart in no particular order, so `web_*` may not exist yet | Look up the container per request; reboot drill |
| 5 | Migrations race or rerun | Migrating in the entrypoint would run in both containers | One separate migrate run, under a deploy lock |
| 6 | Dev entrypoint's `flush` reaches prod | `app/entrypoint.sh` wipes the database | Never reuse it; a test fails if `flush` appears in prod paths |
| 7 | In-flight requests are killed | Compose waits 10s by default, gunicorn 30s | 35s grace period, drain after the nginx switch, concurrent POST drill |
| 8 | Static files missing or mismatched | The shared volume isn't refreshed, and DEBUG is effectively on | Hashed static file names, DEBUG fix, `collectstatic` before the switch |
| 9 | Rollback becomes impossible | Forward-only schema; partial migration runs | `pg_dump` before migrate, kept 7 days; documented restore |
| 10 | Test passes while the switch is broken | A load loop on `/` gets 2xx from the old version anyway | Each response reports its SHA; assert old→new with 0 errors |

Riskiest: #1 — a migration that isn't backward-compatible breaks the old version during the overlap and makes rollback impossible, and only a team policy plus a linter guards against it.
