## What the code does now
- `Article` has one `authorId` (`src/prisma/schema.prisma`). Every response returns `author` as a single profile object.
- The slug is `${slugify(title)}-${userId}`. In `updateArticle` (`article.service.ts:317`) that id is the **editor's** id, not the owner's.
- Update and delete only allow the owner: `existingArticle.author.id !== id` at `article.service.ts:310` and `:404`.
- `favoriteArticle` and `unfavoriteArticle` don't use `articleMapper`. They build the response by hand with `profileMapper` (`:599`, `:645`).
- The `?author=` filter and `getFeed` both look only at `author`.

## Ways this could go wrong
1. **Slugs change when a co-author edits.** If co-authors can edit, a co-author who changes the title gives the article a slug with their own id. Old URLs then return 404.
2. **The response shape changes.** Turning `author` into an array, or removing it, breaks every RealWorld client.
3. **Schema migration.** Dropping or renaming `authorId`, or backfilling it, risks losing data and needs code and database changes deployed at the same moment.
4. **Permissions.** Co-authors might be able to delete the article or remove the owner. Or the 403 checks miss them and they can't edit at all.
5. **Endpoints disagree.** If `authors` is added only in `articleMapper`, the favorite and unfavorite endpoints won't return it.
6. **Filter and feed changes.** Including co-authors changes `?author=` results and the article counts used for pagination.
7. **Slow queries.** Loading co-authors with their followers adds nested includes to every list request.
8. **Bad input.** Unknown usernames, duplicates, the owner listing themselves, or very long lists.
9. **Deleting users.** With cascade deletes, deleting the owner's account still deletes the article for all co-authors.
10. **Tests.** The Prisma-mock unit tests and e2e tests encode the single-author shape.

## Assumptions
I couldn't ask, so I assumed:
- `authorId` stays as the owner.
- Co-authors can edit the article. Only the owner can delete it or change the co-author list.
- `?author=` and the feed match both the owner and co-authors.
- The response keeps `author` and adds `authors`.

## Plan
1. **New table only.** Add an `ArticleCoAuthor(articleId, userId, position)` join table with cascading foreign keys and an index on `userId`. Nothing existing changes and no backfill is needed.
2. **Response.** `articleMapper` adds `authors: Profile[]`, owner first, built with the existing `authorMapper`. One shared Prisma `include` replaces the block that is currently repeated about 8 times. The favorite and unfavorite endpoints switch to `articleMapper`.
3. **Requests.** POST and PUT accept an optional `article.coAuthors: string[]` of usernames, checked and written in the same transaction as the article. Unknown usernames return 422; duplicates and the owner's own name are dropped; the list is capped.
4. **Permissions.** A new `canEdit` check (owner or co-author) is used for updates. Deleting stays owner-only.
5. **Slug fix.** `updateArticle` builds the slug from `existingArticle.authorId` instead of the editor's id.
6. **Filter and feed.** `?author=` and `getFeed` use an OR over the owner and co-authors, and the count query uses the same condition.
7. **Tests.** Unit tests for the new rules, plus an e2e snapshot that a single-author article has the same keys as before plus `authors` of length 1.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Slug changes when a co-author edits | Update builds the slug from the editor's id (`service.ts:317`) | Build it from `existingArticle.authorId` |
| 2 | Clients break on the `author` shape | All RealWorld clients read `article.author` as an object | Keep `author`; add `authors` |
| 3 | Data loss in the migration | `authorId` is required and cascades | Only add a join table; no backfill |
| 4 | Co-author can delete or take over | Owner checks at `:310` and `:404` are used for everything | `canEdit` for updates; owner-only delete and co-author changes |
| 5 | Endpoints return different shapes | Favorite and unfavorite build responses with `profileMapper` | Send all endpoints through `articleMapper` |
| 6 | `?author=` results and counts change | The filter only looks at `author` | OR over owner and co-authors; same condition for the count |
| 7 | Slower article lists | Nested `followedBy` loads for every co-author | Cap co-authors; index `userId`; one shared include |
| 8 | Bad co-author input | Usernames come from client JSON | Check usernames, dedupe, drop owner, cap, return 422 |
| 9 | Owner deletion removes shared work | `onDelete: Cascade` on `authorId` | Document it; possibly promote a co-author later |
| 10 | Tests encode a single author | Prisma mocks and e2e assume one `author` | Update mocks; add a shape snapshot |

Riskiest: #1, because a co-author renaming an article would move its slug to their id, so existing URLs return 404.
