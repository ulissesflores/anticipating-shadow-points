I've written the plan to `<config>/plans/make-ky-retry-post-sleepy-allen.md`. No project files were changed.

**Assumptions** (non-interactive, so these aren't confirmed):
- "When the network fails" means a `NetworkError` only. A POST that gets a 5xx, a 429 or a timeout should still not be retried.
- Callers must still be able to turn this off.
- Because this changes default behavior, it should ship as a major release (3.0.0).

**Approach**
1. **New option `retry.networkErrorMethods`, default `['post', 'patch']`.** It lists methods that are retried only on network errors. I'd rather not add them to `retry.methods`, because that would also retry POST on 500/502/503/504/408/429 — well beyond what was asked.
   - Type and docs: `source/types/retry.ts`.
   - Default and validation: `source/utils/normalize.ts`. Add the new key to the existing array and string-entry checks and to `normalizeRetryMethod`. Per `AGENTS.md`, passing `null` should throw an error that names `retry.networkErrorMethods`, with no fallback.
2. **Retry decision in `#calculateRetryDelay`** (`source/core/Ky.ts:703`). A request is retryable if its method is in `methods`, or if it's in `networkErrorMethods` and `isNetworkError(error)`.
   - The forced-retry path (`ky.retry()` from a hook) still comes first and doesn't change.
   - `shouldRetry` still runs after this check, so it can still block a retry by returning `false`.
3. **Merging.** Check that `source/utils/merge.ts` (around line 426) and the copy of `retry` given to init hooks handle the new array the same way as `methods`. `retry: 3` should keep the default, and `extend({retry: {networkErrorMethods: []}})` should replace the list.
4. **Docs.** Update the readme retry section (around line 260) and the JSDoc in `options.ts`:
   - how to opt out (`networkErrorMethods: []` or `retry: 0`)
   - a recommendation to send an `Idempotency-Key` header
   - a note that streaming POST bodies are now buffered in memory by default
5. **Tests.**
   - Keep the existing `not on POST` 500 test in `test/retry.ts`.
   - Add tests that POST and PATCH are retried on a network error, and not on a timeout or 429.
   - Add tests for opting out, for the body being re-sent on retry (JSON and stream), and for `shouldRetry` being called on a POST network error but still not on a POST 500 (`test/retry-decisions.ts:241`).
   - Add validation tests (including `null`) and type tests in `test-d/retry.ts`.
6. **Verify** with `npm test`, focusing on `test/retry.ts`, `test/retry-decisions.ts` and `test/network-error.ts`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate side effects (double charge, double order) | A connection can drop after the server has already processed a POST, and ky still sees a `NetworkError` | Document an `Idempotency-Key` header; easy opt-out with `networkErrorMethods: []` |
| 2 | Silent behavior change for existing users | Upgraders get POST retries without asking for them | Major version bump and a prominent release note |
| 3 | Memory spike on large streaming uploads | When retries are on, ky buffers the request body (`readme.md:399`), and POST uploads now count | Document it; suggest `retry: 0` for big streams |
| 4 | `shouldRetry` semantics shift | It's currently never called for POST (`test/retry-decisions.ts:241`); now it is for network errors | Keep that test for 500s; add one for network errors; document it |
| 5 | Wrong error-type match | Network errors are detected per runtime (`NetworkError.ts:9`), so an unrecognized error might be mis-classified | Retry only on `isNetworkError`; test in the browser and in Node |
| 6 | Merge/extend mistakes | `merge.ts` has special handling for `retry` arrays and numeric shorthand | Explicit tests for `create().extend()` with the new key |
| 7 | `null` accepted by accident | `AGENTS.md` forbids accepting `null` | Rely on the array check; test that `null` throws a named error |
| 8 | Longer time before failure on mobile | Two extra attempts with backoff while offline | Keep `limit: 2` and the existing backoff; mention `totalTimeout` |

Riskiest: #1. Retrying non-idempotent POST/PATCH after a network failure can repeat side effects the server has already applied.
