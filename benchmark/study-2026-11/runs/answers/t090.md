**Assumptions (instead of asking):**
- Digests are on by default and users can opt out with an unsubscribe link.
- Emails are English only.
- One UTC week for everyone, starting Monday 00:00; no per-user send day or timezone.
- At most 20 posts per email, followed by "and N more".
- A user gets at most one digest a week. If a send fails, they miss that week rather than risk getting it twice.
- No mail is sent when there are no new posts.

**What the code already has (Phase 1).** The app is the Flask Mega-Tutorial microblog at v0.23.
- **Reusable pieces:**
  - `User.following_posts()` in `app/models.py`; it also returns the user's own posts.
  - `send_email(..., sync=True)` in `app/email.py`.
  - The RQ queue `microblog-tasks`.
  - The JWT pattern from `get_reset_password_token`.
- **What's missing:** a scheduler, email preferences, unsubscribe, and email verification.
- **No project lessons were found** (no `CLAUDE.md` or lessons file), and I did not run the web prior-art search.

**The plan (Phases 3–6):**
1. **D01 – Database:** add two user fields, `digest_opt_out` and `last_digest_at` (the time of the user's last digest), with an Alembic migration. A scripted test runs upgrade and downgrade on a temporary SQLite file.
2. **D02 – Post selection:** `User.digest_posts(since, until)` returns only posts by people the user follows, never their own, with `since < timestamp <= until`, oldest first.
3. **D03 – Unsubscribe:**
   - A signed link with no expiry.
   - The link opens a confirm page and only a POST changes anything, so link scanners can't unsubscribe people.
   - A separate one-click POST endpoint for mail providers, which needs no form token (CSRF) and is safe to repeat.
   - `send_email` gains an `extra_headers` option so each mail carries a `List-Unsubscribe` header.
4. **D04 – Sending:**
   - The logic lives in `app/digest.py::send_user_digest(user_id, until)`, so tests can run it against the test database. `app/tasks.py` is only a thin wrapper, because importing it starts the app with the production config.
   - Before sending, the job claims the user with one conditional database update and only proceeds if exactly one row changed. That is what stops duplicates; RQ job IDs don't.
   - All times are compared as UTC without a timezone, and post times are formatted on the server (the app's `moment()` helper is JavaScript and won't work in email).
   - It needs `SERVER_NAME` and a real `DIGEST_SENDER`; `ADMINS[0]` is only a placeholder.
5. **D05 – Trigger:** a `flask digest send [--dry-run]` command fixes the week boundary, so running it twice in the same week does nothing. It queues one job per user who follows at least one person, and stops early if mail or `SERVER_NAME` settings are missing. It's tested with Flask's CLI test runner and a mocked queue.
6. **D06 – Deployment:** document a weekly cron or Heroku Scheduler entry, since the app has no scheduler. This one is checked by hand.

**How it gets checked:** `python tests.py` covers own posts excluded, opt-out respected, a second run sending nothing, an empty week sending nothing, unsubscribe working, and one recipient per message. An end-to-end run against a local `aiosmtpd` server is optional and manual.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Duplicate digests | Cron plus a manual run, RQ retries, and RQ 1.15 re-queues jobs with the same ID | Conditional database claim per user; week boundary fixed so a rerun does nothing |
| 2 | User's own posts in the digest | `following_posts()` includes the user's own posts | Separate query that excludes them, plus a test |
| 3 | Posts missed or repeated at the week edge | Posts are saved with a timezone but the column stores none; SQLite and Postgres treat this differently | Compare in UTC without timezone everywhere; `since < ts <= until`; boundary tests |
| 4 | Job crashes building links | `url_for(_external=True)` outside a web request needs `SERVER_NAME`, which isn't set in tests or by default | Require it and stop early if missing; set it in `TestConfig` |
| 5 | Tests hit the production database | Importing `app/tasks.py` starts the app with the production config | Put the logic in `app/digest.py`; keep the task a thin wrapper |
| 6 | Spam or legal complaints | Mailing everyone by default, with no email verification and a placeholder sender | Opt-out link, `List-Unsubscribe` header, real `DIGEST_SENDER`, no mail for empty weeks |
| 7 | Unsubscribes nobody asked for | Mail scanners open links in emails | Link shows a confirm page; only a POST unsubscribes; one-click endpoint is safe to repeat |
| 8 | Digest never sent | There is no scheduler and the worker may not be running | Document cron or Heroku Scheduler; log enqueued/sent/skipped/failed counts per run |
| 9 | Mail server throttling | Hundreds of messages go out in a single burst | One job per user, posts capped per email, sending rate can be tuned |
| 10 | Migration fails on SQLite | Alembic isn't set up for SQLite's limited table changes | Only add columns, each with a default; scripted upgrade/downgrade test |

Riskiest: #1, duplicate digests — overlapping runs and RQ re-queuing jobs with the same ID can email users twice, so the database claim plus the fixed week boundary must be right.
