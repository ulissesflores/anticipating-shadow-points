The plan is a single `./deploy.sh` script. It builds the new image, runs migrations once, starts the new container next to the old one, sends traffic to it once it's healthy, then shuts the old one down gracefully. The full plan is in `claude-home/plans/deploy-new-versions-with-jolly-adleman.md`; I haven't changed any project files.

## What happens today
- Production runs on one host: nginx → one gunicorn `web` container → postgres 15. Running `docker-compose -f docker-compose.prod.yml up -d --build` stops `web` and then starts the new one, so nginx returns 502s in between.
- `app/entrypoint.prod.sh` only waits for postgres; it never runs `migrate`. The dev `app/entrypoint.sh` does migrate, but it also runs `flush`, which wipes the database, so it must not be copied to production.
- There are no healthchecks, no `collectstatic` step in production, and no CI.
- `app/upload/migrations/` has no migration files yet.

## Assumptions
- One Docker host with Compose v2; no Swarm or Kubernetes, and the image is built on the host.
- Postgres stays in compose and deploys never recreate it.
- Migrations follow expand/contract: each release's schema still works with the previous release's code.
- Old and new code briefly serving requests at the same time is acceptable.

## Steps
1. **Health endpoint and healthchecks**
   - Add a `/healthz/` view that runs `SELECT 1` against the database.
   - Give `web` a compose healthcheck that calls `/healthz/`, and give `db` a `pg_isready` healthcheck. Make `web` wait for a healthy `db` (`depends_on` with `service_healthy`).
   - Set `stop_grace_period: 30s` and gunicorn `--graceful-timeout 25` so in-flight requests finish before a container stops.
   - Tag each image with the git commit (`image: hello_django:${TAG}`) so you can roll back to a previous tag.
2. **Migrations as a one-off step, not in the entrypoint**
   - Before any traffic moves, the script runs `docker compose run --rm --no-deps web python manage.py migrate --noinput && python manage.py collectstatic --noinput` using the new image.
   - If that fails, the deploy stops and the old container keeps serving.
   - Add an optional `lock_timeout` for the migrate run, so a migration fails fast instead of blocking live queries.
   - Add `makemigrations --check` to the builder stage of `Dockerfile.prod`, so a build fails if a migration is missing.
3. **Static files**
   - Switch to `ManifestStaticFilesStorage`, which puts a content hash in each file name.
   - New files are then added next to the old ones in the shared `static_volume`, so pages served by the old container still find their assets.
4. **nginx**
   - Keep `upstream web:8000`, but have the script run `nginx -s reload` after each scale change so nginx picks up the current containers.
   - Add `proxy_next_upstream error timeout http_502 http_503` with 2 tries, so a request that hits a stopping container is retried on the other one.
5. **`deploy.sh`** runs these steps in order:
   1. Build the image with `TAG=$(git rev-parse --short HEAD)`.
   2. Make sure `db` and `nginx` are up, without recreating them.
   3. Run migrate and collectstatic.
   4. Scale `web` to 2 with `--no-recreate`.
   5. Wait up to 90s for the new container to be healthy. If it isn't, remove it and exit; the old one keeps serving.
   6. Reload nginx.
   7. Stop the old container (`docker stop -t 30`) and remove it.
   8. Reload nginx again and set the scale back to 1.

   On the very first deploy there is no old container, so the script just runs `up -d`. To roll back, run `TAG=<prev> ./deploy.sh --no-build`, which skips the build and migrations. Migrations are never reversed automatically.
6. **README**: replace the `up --build` instructions with `./deploy.sh` and write down the expand/contract migration rules.

**Files to change:** `docker-compose.prod.yml`, `app/Dockerfile.prod`, `app/hello_django/settings.py`, `app/hello_django/urls.py` (plus the healthz view), `nginx/nginx.conf`, a new `deploy.sh`, and `README.md`.

## How to verify
1. Run `./deploy.sh` after a trivial code change while a curl loop or `hey -z 60s` hits `localhost:1337`. Expect only 200s, no 502 or 504.
2. Deploy a model change that adds a nullable field under the same load, and check that `showmigrations` shows it applied with no errors.
3. Deploy a migration that raises: the deploy should stop and the old container should keep serving.
4. Deploy with `/healthz/` returning 503: the new container should be removed and the old one should stay.
5. Roll back to the previous tag and confirm there is no downtime.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Migration breaks the old code still serving | The old container runs against the new schema during the overlap | Expand/contract rules; drops and renames only in a later release |
| 2 | Migration takes a lock and stalls live traffic | Only one Postgres; `ALTER TABLE` can block queries | `lock_timeout` on the migrate run; review migrations before merging |
| 3 | nginx keeps sending traffic to the removed container | It looks up `web` addresses only at reload | Reload after each scale change; `proxy_next_upstream` retries |
| 4 | `collectstatic` overwrites assets the old pages use | `static_volume` is shared by both versions | `ManifestStaticFilesStorage` (hashed file names) |
| 5 | New container never becomes healthy | No healthcheck exists today | `/healthz/` check, 90s timeout, remove the new container on failure |
| 6 | In-flight requests are cut off when the old container stops | Default stop timeout is 10s | Gunicorn graceful timeout plus a 30s `stop_grace_period` |
| 7 | The dev `flush` gets copied into the production entrypoint | `entrypoint.sh` already does migrate and flush | Keep migrations in `deploy.sh`; add a warning in the README |
| 8 | Missing migration files are deployed unnoticed | `upload/migrations` is empty today | `makemigrations --check` in the build |
| 9 | Rolling back the code doesn't roll back the schema | Migrations only move forward | Backward-compatible schema; take a DB backup before deploy |
| 10 | The script's container-ID handling is fragile | Compose scaling with `--no-recreate` is easy to get wrong | Test on a staging host; use `set -euo pipefail` |

Riskiest: #1. A migration that isn't backward-compatible breaks the old container while it is still serving traffic.
