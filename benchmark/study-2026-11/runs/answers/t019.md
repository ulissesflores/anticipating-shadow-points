I've written a plan for co-authors that adds to the existing data and API and doesn't change anything current clients rely on. I didn't edit any project files; the plan is in `claude-home/plans/allow-an-article-to-graceful-dove.md`.

## Assumptions
- `Article.authorId` stays as the **primary author** (the owner). Co-authors are extra users stored in a new join table, so no existing rows change.
- **API responses:** `article.author` stays exactly as it is. A new field, `authors`, lists every author's profile, primary first.
- **Slugs never change because of co-authors.** The number at the end of a slug stays the primary author's id.
- **Permissions:** co-authors can edit an article. Only the primary author can delete it or change who the co-authors are.
- **Filters:** `?author=` and the feed match the primary author or any co-author.

## Plan
1. **Schema and migration** (`src/prisma/schema.prisma`, new migration): add a model `ArticleCoAuthor { articleId, userId, position, createdAt }`.
   - The primary key is `(articleId, userId)`.
   - Rows are deleted automatically when the article or the user is deleted.
   - This only adds a table, so no backfill is needed.
2. **One shared include** (`article.service.ts`): the same `include { tagList, author, favoritedBy, _count }` block is repeated 7 times. Replace it with one constant and add `coAuthors`, ordered by `position`, with each user's profile fields.
3. **Mapper** (`article.mapper.ts`): build `authors` by running the existing `authorMapper` over the primary author plus the co-authors. `author` stays unchanged.
4. **Favorite/unfavorite:** these two currently build their response by hand with `profileMapper`, which also exposes `id` and `authorId`. Switch them to `articleMapper` so `authors` is returned everywhere. Check that the response still contains every field it has today.
5. **Create/update input:** accept an optional `article.coAuthors: string[]` of usernames.
   - Return 422 for an unknown username.
   - Remove duplicates and the primary author, and cap the list (e.g. 10).
   - Write the article and its co-authors in one `$transaction`. If the field is missing on update, leave the co-authors as they are.
6. **Authorization** in `updateArticle` and `deleteArticle`: allow updates from the primary author or a co-author. Deleting the article or changing the co-author list stays limited to the primary author.
7. **Slug fix:** `updateArticle` builds the new slug as `slugify(title)-${id}`, where `id` is whoever is making the request. It must use `existingArticle.authorId` instead, or a co-author's title edit would change the URL.
8. **Queries** (`buildFindAllQuery`, `getFeed`):
   - The `author` filter becomes "primary author OR some co-author has this username".
   - The feed includes articles where the primary author or any co-author is someone you follow.
   - The existing demo/self visibility rule stays on the primary author only.
   - `count` and `findMany` must use the same `where`.
9. **Docs:** update the comments in `article.controller.ts` and the README.

## Verification
- **Migration:** run `prisma migrate dev` on a copy of production-like data and confirm existing rows are untouched.
- **Unit tests** (`src/tests/services/article.service.test.ts`):
  - `author` is unchanged and `authors` is added.
  - A co-author can edit but not delete.
  - The slug stays the same when a co-author changes the title.
  - An unknown co-author returns 422.
- **e2e:** snapshot the list, single-article and favorite responses before and after. The only difference should be the added `authors` field.
- **Build:** run `nx test` and `nx build`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Co-author edit changes the slug, breaking URLs | `updateArticle` builds the slug from the requester's `id` | Use `existingArticle.authorId` and add a test for it |
| 2 | Response shape changes for current clients | favorite/unfavorite build their response by hand and differ from `articleMapper` | Only add fields; compare e2e snapshots before and after |
| 3 | `?author=` results now include co-authored articles | Clients may expect only articles the user wrote alone | Document it, or put it behind a separate `coauthor=` parameter |
| 4 | `articlesCount` doesn't match the returned list | Counting and fetching use separate `where` clauses | Build one `where` and use it for both |
| 5 | Co-author gains too much power | The current check is a simple `author.id !== id` | Separate the edit check from the delete/manage check and test both |
| 6 | Slower queries (N+1, joins) | Every query will also load co-authors and their followers | Index `userId`, cap co-author count, check query plans |
| 7 | Migration problems in production | Prisma migrations run at deploy | Keep it to adding a table only; test on a data copy |
| 8 | Partial writes | Saving the article and its co-authors are separate steps | Wrap them in `prisma.$transaction` |
| 9 | A deleted co-author leaves a stale reference | Users can be deleted | Delete co-author rows automatically on user deletion |
| 10 | Feed or visibility leaks | The demo/self rule only applies to `author` | Keep the rule on the primary author only and test it |

Riskiest: #1, a co-author's title edit changing the slug and silently breaking existing article URLs.
