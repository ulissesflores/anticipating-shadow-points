# Zero-downtime deploys with automatic migrations: validated plan

I stopped after Phase 6 as you asked. No project files were edited; the plan is saved at `claude-home/plans/standard-deploy-new-versions-squishy-ocean.md`.

**Assumptions** (non-interactive run, so I didn't ask):
- One host, Compose v2.
- Deploys are started by a script, run by a person or over SSH.
- A few seconds of extra latency during the swap is fine; failed requests are not.

**Lessons consulted before acting:** none. The repo has no lessons store and no `CLAUDE.md`. I read the repo directly (it's only about 30 files) and didn't spawn exploration agents.

## How it works today
- Every deploy runs `docker compose -f docker-compose.prod.yml up -d --build`. That stops the old `web` container before the new one starts, so the site is down during the swap.
- Production never runs migrations. `app/entrypoint.prod.sh` only waits for the database.
- The nginx config is baked into its image (`nginx/Dockerfile`), and nginx looks up the address of `web` only once, at start.

## Plan (after validator revision round 1)
1. **D01 Health check and DEBUG fix.**
   - Add `GET /healthz/`, which runs `SELECT 1` against the database.
   - Fix `app/hello_django/settings.py:25`. The setting reads `bool("0")`, which is `True`, so production currently runs with DEBUG on.
2. **D02 Compose changes.**
   - Tag each `web` image with the git commit.
   - Add a fast healthcheck (every 3s) and give containers 30s to shut down cleanly.
   - Run gunicorn with 3 workers and a 25s graceful timeout.
   - Make `web` wait until Postgres reports ready (`pg_isready`).
   - Load the nginx config from the repo (bind mount) instead of baking it into the image.
3. **D03 nginx.** The deploy script writes the list of `web` container addresses into a file nginx reads. nginx gets a 2s connect timeout and retries a different container on connection errors.
4. **D04 `scripts/deploy.sh`**, in this order:
   1. Take a lock so two deploys can't run at once, then build the new image.
   2. Pre-flight checks: fail if a model change has no migration, print the migration plan, and confirm DEBUG is off.
   3. Back up the database (`pg_dump`).
   4. Run `migrate` once, as a one-off container. Lock waits are capped at 5s, with up to 3 retries. If it fails, the deploy stops and the old version keeps serving.
   5. Run `collectstatic`.
   6. Start a second `web` container and wait until it is healthy.
   7. Point nginx at both containers, then at the new one only. Wait for in-flight requests to finish.
   8. Stop and remove the old container by its ID.
   9. Save the current tag and run a smoke test through port 1337.

   `--rollback <tag>` repeats the swap with an older image and never runs migrations backwards. Migrations never run in the entrypoint, and the dev `entrypoint.sh` must never be used in production because it runs `flush`.
5. **D05 README.** Document deploy and rollback, the one-time cutover, and the migration rules: each migration must still work with the code that's currently running. That rules out several Django 4.2 patterns within a single release; they are listed in the plan.
6. **D06 Zero-downtime check.** A probe sends 20 requests per second through nginx: plain page loads plus image-upload POSTs carrying a valid CSRF token. It records three deploys: one with a new migration, one where the second of several migrations fails, and a rollback. Each must show 0 errors.

## What the validator changed (round 1: REVISE)
The independent validator found 11 problems. I checked the most important ones against the code, they held, and all are now in the plan:
- **nginx would keep sending traffic to the stopped container.** Fixed by removing it from nginx before stopping it.
- **Changing the nginx config would itself cause an outage**, because the config is baked into the image. Fixed with the bind mount; the one-time cutover still has a short gap.
- **The upload test couldn't pass as first written.** A POST to `/` fails without a CSRF token, and fails with a server error (`KeyError`) without `image_file`.
- **Smaller fixes:** default healthcheck timing was too slow, the image tag wasn't saved between deploys, there was no first-run (bootstrap) step, rollback didn't check the image exists, the list of unsafe Django 4.2 migrations was missing, a failed deploy can leave some migrations applied, and the DEBUG bug matters in production.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | New schema breaks the old code during the swap | Both versions serve traffic at once; on Django 4.2 a NOT NULL column with a default, or a rename, breaks the old code's inserts | Expand/contract rules; ban these patterns within a single release |
| 2 | nginx sends traffic to a dead container | nginx looks up `web` only once; the default connect timeout is 60s | Generated address list; remove the old container before stopping it; 2s connect timeout |
| 3 | A migration lock stalls the whole site | `ALTER TABLE` blocks every query on that table while it waits for its lock | `lock_timeout=5s` with limited retries |
| 4 | Migrations run twice at the same time | Running them in the entrypoint would repeat them in every container | One-off `migrate` step plus a deploy lock |
| 5 | Dev `flush` reaches production | `entrypoint.sh` runs `flush --no-input` | Explicitly forbidden; prod uses its own entrypoint only |
| 6 | Partial migration after a failure | Each migration commits separately | Old code stays up; `pg_dump` first; failing-migration test |
| 7 | Rollback loses data or can't run | Reverse migrations drop data; the old image may have been deleted | Rollback never migrates; keep the last 5 images; check the image exists first |
| 8 | The cutover itself causes downtime | nginx has to be recreated once to load the mounted config | Planned short window, documented in the README |
| 9 | Someone bypasses the script | A plain `compose up -d` recreates `web` with a stop-then-start | Save the tag; forbid it in the README |
| 10 | Production runs with DEBUG on | `bool("0")` is `True` | Fix in D01; the pre-flight check blocks the deploy otherwise |

Riskiest: #1. New-schema migrations that break the old code, because they cause errors during every swap and no infrastructure change can catch them; only the migration rules can.
