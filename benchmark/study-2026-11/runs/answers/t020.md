## What the code shows
- The default retry methods (`source/utils/normalize.ts:17`) don't include `post` or `patch`.
- The method check in `#calculateRetryDelay` (`source/core/Ky.ts:703`) gates every reason to retry: status codes, timeouts and network errors alike. So just adding `post`/`patch` to `retry.methods` would also retry POST on 500/502/503/504/429. The server certainly received those requests, so retrying them is the wrong fix.
- Retrying won't cost extra memory. Ky already copies the request body (`Ky.ts:1225`) for POST whenever `limit > 0`.
- The project's own docs already say the core risk out loud (`readme.md:581`): "a network error does not tell whether the server got the request."

## Assumptions (no one to ask in this run)
- **A1:** "Network fails" means a `NetworkError` while the request is being sent (`Ky.ts:1268`). It excludes HTTP status errors, timeouts, and a connection that drops while the response body is being read (`Ky.ts:905`), where the response has already arrived.
- **A2:** `retry.methods` stays unchanged.
- **A3:** This changes default behaviour, so it ships as 3.0.0 with a migration note.
- **A4:** The project keeps no lessons file; AGENTS.md (no `null` anywhere) is the only rule that applies.

## Plan
- **New option:** `retry.networkErrorMethods`, default `['post', 'patch']`.
  - For a method only in this list, any error that isn't a network error is rethrown *before* `shouldRetry` runs, so POST behaviour on HTTP errors and timeouts doesn't change.
  - On a network error, `shouldRetry` can still veto by returning `false`.
  - Retries forced with `ky.retry()` work as today.
  - Opting out is `[]`. Passing `null` throws "retry.networkErrorMethods must be an array" through the existing check.
- **Deliverables:**
  - **D01:** types and their docs in `source/types/retry.ts`.
  - **D02:** default value and validation in `normalize.ts`.
  - **D03:** split the method check in `Ky.ts`.
  - **D04:** tests and type tests.
  - **D05:** readme, migration note, and an Idempotency-Key example.
- **Verify:** `npm test`, plus the browser tests in CI.

**Independent validator (one round): APPROVE.** I folded in its five fixes:
- **`.extend()` can't opt out:** it merges retry arrays by joining them (I checked `merge.ts:353`), so a child's `networkErrorMethods: []` doesn't clear a list the parent set. Only `replaceOption([])` does. This gets documented and tested.
- **Docs that need rewording:** they say `shouldRetry` runs "after method checks pass" (`types/retry.ts:143`, `readme.md:281`, `readme.md:304`).
- **Types:** add a mutable field to `MutableRetryOptions` and update the strict type test in `test-d/normalized-options.ts`.
- **Copying:** copy the array during normalization so hooks can't change it for other requests.
- **Extra test:** POST + `shouldRetry: () => true` + a 500 response must still send exactly one request.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Side effects run twice (double charge or double create) | A network error doesn't prove the server didn't commit: undici's `terminated`, `Network connection lost` and Safari's `Load failed` can all happen after the server processed the request | Loud docs, an Idempotency-Key example, `shouldRetry` as a veto; accepted on purpose |
| 2 | POST also retried on 5xx/429 | The method check gates every reason to retry (`Ky.ts:703`) | Separate option; tests that 5xx/429 POST isn't retried |
| 3 | Existing users' behaviour changes silently | New default in a library on 2.2.0 | 3.0.0 plus a migration note |
| 4 | `.extend()` can't turn it off | Retry arrays are joined when merged (`merge.ts:353`) | Document `replaceOption([])`; test it |
| 5 | `null` config quietly accepted | AGENTS.md forbids `null` | The existing array check throws; add a test |
| 6 | `shouldRetry: true` brings back retries on HTTP errors | Today `shouldRetry` overrides the default checks | Rethrow non-network errors before `shouldRetry`; test it |
| 7 | Streamed uploads fail again on every retry | Chromium sends streamed bodies only over HTTP/2+; upload progress restarts at 0 | Docs; the existing `beforeRetry` `{options}` escape hatch |
| 8 | Retry storm against a server that's recovering | Many mobile clients reconnect at the same time | Existing backoff and `limit: 2`; recommend jitter |
| 9 | Type definitions drift | `NormalizedRetryOptions` is derived from `MutableRetryOptions` | Update the strict type test |
| 10 | Docs contradict the code | Several places say "after method checks pass" | Reword all four places |

Riskiest: #1. A retried POST/PATCH after a network failure can run a non-idempotent write twice, and no code-level check can rule that out.
