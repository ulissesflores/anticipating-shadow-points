## Assumptions
- Production is `docker-compose.prod.yml` (nginx → one gunicorn `web` → postgres) running on a single host with Docker Compose v2. There's no Kubernetes or Swarm, and the database isn't managed elsewhere.
- Today a deploy is `docker compose -f docker-compose.prod.yml up -d --build`. That stops the old `web` container before the new one is ready, so the site goes down during every deploy.
- "Zero downtime" here means no 5xx errors and no dropped requests during a normal deploy. It does not cover failover if the whole host goes down.

## Ways this could go wrong (from reading the repo)
1. **`flush` copied into prod.** `app/entrypoint.sh:16` runs `python manage.py flush --no-input` before `migrate`. That's fine in dev, but if someone "adds migrations" to `entrypoint.prod.sh` by copying it, every deploy wipes the production database.
2. **Migrations in the entrypoint run on every replica.** Starting two containers during a rollout means two `migrate` processes at once. Django doesn't lock migrations, so they can race and fail halfway through.
3. **Old code meets the new schema.** During the overlap, the old container serves traffic against the migrated database. Renaming or dropping a column, or adding a NOT NULL column without a default, breaks the old version.
4. **nginx keeps the old container's IP.** `nginx/nginx.conf:2` has `server web:8000;`, and nginx looks that name up only once, at startup. After `web` is recreated it keeps sending traffic to a dead IP and returns 502s.
5. **Nothing checks that the new container is ready.** No service has a healthcheck, and nginx has no `depends_on: condition: service_healthy`. Traffic can switch to a gunicorn that is still booting or has crashed.
6. **Waiting for the database only checks the port.** `nc -z` passes as soon as postgres is listening, even if it can't accept queries yet. A migration started at that moment can fail.
7. **Static files go stale.** `static_volume` is a named volume, and Docker only fills it from the image when the volume is empty. Nothing runs `collectstatic`, so new CSS and JS never reach nginx.
8. **Gunicorn shutdown cuts requests.** The default `stop_grace_period` (10s) and gunicorn's default graceful timeout can kill requests that are still running when the old container stops.
9. **No rollback once a migration has run.** If the new image fails its health check after migrating, rolling back the code still leaves the new schema in place.
10. **Long table locks.** Adding an index or rewriting a table on postgres 15 can lock it long enough to stall every request. That's downtime even though the container swap went fine.
11. Unrelated but nearby: `settings.py:26` has `DEBUG = bool(os.environ.get("DEBUG", default=0))`, so `DEBUG=0` from the env file becomes the string `"0"`, which is True. Production may already be running with DEBUG on.

## Plan

**1. Make migrations a single deploy step, not part of container startup.**
- Leave `entrypoint.prod.sh` with no `migrate` and no `flush`.
- Add a `migrate` service (or `docker compose run --rm web …`) to `docker-compose.prod.yml` that runs `python manage.py migrate --noinput && python manage.py collectstatic --noinput` once. It uses the new image and mounts `static_volume`.
- Wrap the command in a postgres advisory lock (a small management command or `psql -c "select pg_advisory_lock(…)"`), so a second deploy started by accident waits instead of racing.
- Replace the `nc` wait with a `pg_isready` or `manage.py check --database default` retry loop.

**2. Health checks.**
- Add a `/healthz/` view in `app/hello_django/urls.py` that runs `SELECT 1`.
- Add a `healthcheck:` to `web` in the compose file (curl or a Python one-liner, since the slim image has no curl). Give `db` a `pg_isready` healthcheck and switch `web` to `depends_on: db: condition: service_healthy`.

**3. Make nginx pick up new containers.**
- In `nginx/nginx.conf`, add `resolver 127.0.0.11 valid=5s;` and set `set $upstream http://web:8000; proxy_pass $upstream;` so the name is looked up again.
- Add `proxy_next_upstream error timeout http_502;` so a request that hits a dying container gets retried on another one.

**4. Blue/green rollout on one host.** Add a new `scripts/deploy.sh`:
1. `docker compose build web`
2. `docker compose run --rm migrate` (runs the migrations and `collectstatic`; stop on failure, before any traffic moves)
3. `docker compose up -d --no-deps --no-recreate --scale web=2 web` (starts the new container next to the old one)
4. Wait until the new container's health status is `healthy`, with a timeout. If it never gets there, remove the new container and exit non-zero.
5. `docker compose exec nginx nginx -s reload`
6. Stop the old container gracefully (`docker stop -t 30 <old>`, then `docker rm`), then `--scale web=1`.

This can be replaced by the `docker rollout` CLI plugin, which does the same steps. Also set `stop_grace_period: 35s` on `web` and pass `--graceful-timeout 30` to gunicorn.

**5. Migration policy (expand/contract).** Document in the README that every migration must keep working with the previous release:
- Add new columns as nullable or with a default.
- Do renames and drops in two releases.
- Build large indexes with `AddIndexConcurrently` (`atomic = False`).
- Take a `pg_dump` before step 4.2.

**6. Fix the `DEBUG` parsing** while touching settings (`os.environ.get("DEBUG", "0") == "1"`).

**Files:** `docker-compose.prod.yml`, `app/entrypoint.prod.sh`, `nginx/nginx.conf`, `app/hello_django/urls.py` (and a small health view), `app/hello_django/settings.py`, new `scripts/deploy.sh`, `README.md`.

## Verification
- Run `hey` or `while curl -fsS localhost:1337/healthz/; do :; done` in a loop while running `deploy.sh` for a code-only change. Expect zero non-2xx responses.
- Repeat with an additive migration (a new nullable field on `upload`). Expect zero errors and confirm the old container keeps serving during the overlap.
- Deploy an image whose healthcheck fails. Expect the script to abort, the old container to keep serving, and no 502s.
- Run two `deploy.sh` at the same time. Expect the second `migrate` to block on the advisory lock.
- Check that a changed static file shows up at `/static/…` after the deploy.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Prod data wiped | Dev `entrypoint.sh` runs `flush --no-input` before `migrate`; easy to copy into prod | Separate migrate step that runs no `flush`; check for `flush` in CI |
| 2 | Migration incompatible with the old version | Old and new containers share one database during the overlap | Expand/contract rule, two-release drops and renames |
| 3 | 502s after the swap | nginx looks up `web:8000` only at startup | `resolver 127.0.0.11` + variable `proxy_pass` + reload |
| 4 | Concurrent migrations | Migrating in the entrypoint runs on every replica, and Django has no lock | One-shot migrate job + pg advisory lock |
| 5 | Traffic sent to a container that isn't ready | No healthchecks anywhere | `/healthz/` + compose healthcheck + wait in script |
| 6 | Long table locks | Postgres DDL on large tables blocks reads and writes | `AddIndexConcurrently`, `lock_timeout`, small steps |
| 7 | Stale static files | Named volume never refreshes from the image | `collectstatic` in the migrate step |
| 8 | Requests cut on shutdown | Default 10s stop and no gunicorn graceful timeout | `stop_grace_period` + `--graceful-timeout` |
| 9 | Can't roll back | Schema already migrated when the new image fails | Back-compat migrations + `pg_dump` before deploy |
| 10 | DEBUG on in prod | `bool("0")` is True | Compare explicitly to `"1"` |

Riskiest: #1. If the dev entrypoint's `flush --no-input` ends up in the prod migration path, every deploy wipes the production database.
