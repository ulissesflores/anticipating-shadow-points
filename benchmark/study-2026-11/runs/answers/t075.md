## What's in the code now
- **Password sign-in** goes through `authenticate()` on `BaseUser.email` (`styleguide_example/authentication/apis.py`).
- **Google sign-in** exists only as a blog example (`blog_examples/google_login_server_flow/sdk/apis.py:73-79`). It has three problems:
  - It reads the ID token with `verify_signature: False` (`sdk/services.py:27`).
  - It never checks `email_verified` or `aud`.
  - It looks users up by exact email, which is case-sensitive in Postgres, and returns 404 when no user matches.
- **Sign-up checks nothing**: `UserCreateApi` creates an account for any email and password. So the email on a password account proves nothing about who owns it.

## Assumptions
- One `BaseUser` per email, on Postgres.
- Users who sign up with Google get an unusable password and can set one later.
- The main target is session login; JWT login reuses the same service.
- The Google flow moves into `authentication/`, and the blog example stays as it is.

## Plan
1. **New `GoogleIdentity` model**: links a user to Google's permanent account ID (`sub`, unique) and records the email at linking time.
2. **Case-insensitive email lookup**: look users up with `email__iexact`, or lowercase stored emails and add a unique constraint on the lowercased value.
3. **Verify the Google token properly** with `google.oauth2.id_token.verify_oauth2_token` against our client ID, and reject it unless `email_verified` is true.
4. **New `auth_google_sign_in` service**, run in one transaction:
   - If the `sub` is already linked, return that user.
   - Otherwise find the user by email, locking the row (`select_for_update`):
     - **No user:** create one with no password, and link it.
     - **Password user, not yet linked:** link it. Because that email was never verified, also disable the existing password, rotate `jwt_key` (reuse `auth_logout`), delete the user's sessions, and email them a notice.
     - **User already linked to a different `sub`:** return 409.
   - Reject inactive users, and handle two first-time sign-ins arriving at once.
5. **New `google/redirect/` and `google/callback/` endpoints** in `authentication`. They reuse the existing CSRF state check and return `user_get_login_data`, not the raw tokens.
6. **Password login stays as it is**, with a generic 400 so it doesn't reveal that an account uses Google.

**Verification:** unit tests for each branch, with token verification mocked. Then API tests, the existing test suite, and a manual end-to-end run: sign in with Google, set a password, sign in with the password, and confirm `/me` returns the same `id`.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Someone takes over an account by registering it first | `UserCreateApi` accepts any email with no verification. An attacker registers the victim's email with a password, and later linking by email joins the victim to the attacker's account. | When Google first links to a password account, disable the password, rotate `jwt_key`, clear sessions and send a notice |
| 2 | Forged or reused ID token | The token's signature is never verified (`verify_signature: False`), and `aud` isn't checked | Use `verify_oauth2_token` with our client ID as the audience |
| 3 | Email not actually owned | Google can return addresses it hasn't verified (`email_verified=false`) | Require `email_verified is True` |
| 4 | Case mismatch creates duplicates or misses links | The email filter is an exact match on Postgres | Look up with `iexact`, or lowercase emails and add a unique constraint |
| 5 | User loses access when their Gmail address changes | Matching only by email | Match by `sub` once linked; use email only the first time |
| 6 | Duplicate users or an `IntegrityError` from two simultaneous first sign-ins | The create and link steps race each other | Lock the row, make `sub` unique, retry once |
| 7 | Old password sessions or JWTs still work after linking | Sessions and `jwt_key` are left as they are | Reuse `auth_logout` and delete the user's sessions |
| 8 | Login errors reveal which emails exist or how they sign in | Different responses for "no password" and "wrong password" | Keep the generic 400 and don't return raw tokens or `user_info` |
| 9 | Google-only users can't use password login and there's no path to set one | `create_user` gives them an unusable password | Add a set-password flow for signed-in users and document it |
| 10 | Callback breaks in production | The redirect URI moves, and the Google Console must list it | Update the allowed URIs in the Console and add a smoke test |

Riskiest: #1. Because sign-up never verifies emails, linking by email lets an attacker who registers someone's email first get into that person's account unless the first Google link wipes the existing password and logs out its sessions.
