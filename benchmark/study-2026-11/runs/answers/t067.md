One independent validator round returned REVISE with 10 findings. I checked them against the code, and the plan now addresses all of them. A second validator round has not been run.

**Assumptions (no questions asked):**
- "When the network fails" means a `NetworkError` only. It does not include HTTP 5xx/408/429 responses or timeouts.
- This changes default behaviour of a published library, so it is a semver-major change. Releasing it is out of scope.
- ky will not add an `Idempotency-Key` header itself, because a custom header triggers a CORS preflight. The readme gets a recipe instead.
- The repo has no lessons file; `AGENTS.md`'s rule against `null` applies.
- The prior art on how other HTTP clients handle this came from memory. I did not verify it online in this run.

**Key finding:** the obvious one-line change is to add `'post','patch'` to the default `retry.methods` (`source/utils/normalize.ts:17`). That is wrong. In `#calculateRetryDelay` (`source/core/Ky.ts:703`), the method check comes before any error-type check. So that change would also retry POSTs on 500, 502, 503, 504, 408 and 429, which often arrive after the server has already written the data.

**Chosen design:** a new option, `retry.networkErrorMethods`, defaulting to `['post', 'patch']`.
- A method that is in this list but not in `methods` is retried only on a `NetworkError`.
- `shouldRetry` can veto that retry by returning `false`. Returning `true` cannot turn an HTTP error on a POST into a retry.
- Timeouts on these methods are not retried, even with `retryOnTimeout: true`.
- `ky.retry()` from a hook works as before.
- Setting the option to `null` or a non-array throws a `TypeError` that names the option.

**What the validator caught:**
- ky concatenates nested arrays when merging options. So a request-level `networkErrorMethods: []` does not cancel an instance-level `['post']`. The working opt-outs are `replaceOption([])` or `retry: 0`.
- An existing test, "NetworkError is not retried for non-retriable method (POST)" (`test/retry.ts:3766`), contradicts the new default and has to be converted.
- Users who set `methods: ['get']` currently get "only GET retries". After the change, POST and PATCH would still retry on network errors.
- In Chromium, streaming uploads over HTTP/1.1 always fail with a network error. Every POST with `onUploadProgress` would use up its retries on an upload that cannot succeed.

**Deliverables:**
- **D01:** types and validation for the new option
- **D02:** the retry decision change in `Ky.ts`
- **D03:** test updates, including a check that the new tests fail when the change is reverted
- **D04:** readme and doc-comment updates
- **D05:** a breaking-change note

**This may not meet the stated goal.** The default timing gives about 1 s of retries (2 retries, 300 ms then 600 ms). Mobile dropouts often last longer, so the plan documents `limit`, `delay` and `backoffLimit` rather than changing them.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Duplicate writes (double order or payment) | "Failed to fetch" and Undici's `terminated` also fire when the server committed the write and only the response was lost; browsers can't tell the two apart | Prominent warning, `Idempotency-Key` recipe, release as a major version |
| 2 | POST retried on 5xx | The method check runs before the error-type check (`Ky.ts:703`) | Separate option limited to `NetworkError`; tests that 500/503/408/429 are not retried |
| 3 | Opt-out silently doesn't work | Nested arrays are concatenated on merge (`merge.ts:441`) | Document `replaceOption([])` or `retry: 0`; test both |
| 4 | Silent change for `methods: ['get']` users | That setting used to mean "only GET retries" | Breaking-change note and readme text |
| 5 | `shouldRetry` contract changes | Its docs and a test say it is never called for POST | Call it only for network errors; `true` can't turn an HTTP error into a retry |
| 6 | Uploads that can't succeed use up all retries | Chromium streaming uploads over HTTP/1.1 always fail with a network error | Document the `beforeRetry` workaround; add a test |
| 7 | Tests changed just to pass | Existing tests assume POST is never retried (`test/retry.ts:322`, `:3766`) | Convert them, keep default-POST counterparts, check the new tests fail when the change is reverted |
| 8 | `null` handled inconsistently | `AGENTS.md` bans `null`; sibling array options throw a plain `Error` | Throw a `TypeError` that names `retry.networkErrorMethods` |
| 9 | Goal not met | About 1 s of default backoff is shorter than most mobile outages | Document `limit`, `delay`, `backoffLimit` |
| 10 | Hidden effect on `Request` objects and hooks | The check reads `this.request.method`; retry options are re-read on every decision | Tests for a `Request` input with a stream body and for a hook changing the option |

Riskiest: #1. Retrying a POST whose write already happened duplicates side effects, and no client-side check can prevent that without server-side idempotency keys.
