**What the code does today**
- Both `DELETE /users/me` and `DELETE /users/{id}` permanently remove the user row (`backend/app/api/routes/users.py:141`, `:235`).
- The admin delete also removes the user's items explicitly (`users.py:233`). The database and ORM cascades would remove them anyway.
- Login tokens last 8 days, and `get_current_user` only checks `is_active` (`backend/app/api/deps.py:41-45`).
- The frontend only logs a user out on a 401 or 403 response (`frontend/src/main.tsx:22-29`).
- The existing tests assert that the row is gone after a delete.

**Assumptions (not confirmed with you)**
- Both delete paths become soft deletes, and only a superuser can restore.
- The marker is a new `deleted_at TIMESTAMPTZ` column. `is_active` is left alone so admins can still toggle it separately.
- The email stays reserved while the account is deleted, so a restore can never clash with a new signup.
- A restore is allowed if less than 30 days have passed. After that it returns `410`.
- **Nothing purges accounts after 30 days.** That's out of scope and is a follow-up.
- Items are left exactly as they are, and admins still see them.
- There's no hard-delete option in the API any more.

**The plan**
1. **Data model:** add the `User.deleted_at` field, indexed, and show it in `UserPublic` only. It can't be set through `UserUpdate` or `UserUpdateMe`. One new Alembic migration with a working downgrade.
2. **Lookups:** every place that loads a user gets an explicit rule (12 places, listed in the plan):
   - login returns 400 and still runs the dummy password check, so timing doesn't reveal deleted accounts;
   - an existing token gets **403**, so the frontend logs the user out (a 404 would leave them stuck in a broken session);
   - password recovery sends nothing, and reset returns 400;
   - the admin user list and its count both exclude deleted users unless `?deleted=true`;
   - editing a deleted user returns 409;
   - startup doesn't recreate the first superuser if it's deleted, and logs a warning instead.
3. **Delete and restore:** delete sets `deleted_at` and no longer removes items. The new `POST /users/{id}/restore` returns 404, 409 or 410 as appropriate, and only clears `deleted_at` if it is still set, so two simultaneous restores can't both succeed.
4. **Frontend:** regenerate the API client, rewrite the delete dialogs (which currently say "permanently deleted") in `DeleteUser.tsx`, `DeleteAccount.tsx` and `DeleteConfirmation.tsx`, and add a deleted-users view, a restore action and a days-left column.
5. **Tests:** rewrite the hard-delete tests and add the edge cases:
   - the restore window at 29 days 23 hours and at 30 days plus one second;
   - a token issued before the delete;
   - items kept and still visible to admins;
   - a check that fails if `session.delete(user)` comes back;
   - a Playwright test that deletes and then restores.

|---|---|---|---|
| 1 | Deleted user's token still works | Tokens last 8 days; `get_current_user` only checks `is_active` | Check `deleted_at` in deps and return 403; test with a token issued before the delete |

Riskiest: #2, a lookup that ignores `deleted_at`. With 12 separate places, missing one quietly lets a "deleted" user log in, reset their password or stay signed in.
