# ASP `--standard`: weekly follow digest for microblog v0.23

I stopped after Phase 6 as you asked. No files were edited, not even the plan-mode plan file. The entry check passed: `ASP_IN_GOAL` is not set.

## Phase 0a: assumptions (stated instead of asking)
1. A post is "new" if its `Post.timestamp` falls in the window `(since, until]`. `since` is the later of the user's last digest send and `until − 7 days`. The user's own posts are left out.
2. A user with no new posts gets no email. Every user is opted in by default, can unsubscribe in one click, and can turn the digest on or off from their profile.
3. Scheduling uses an external cron (system cron or Heroku Scheduler) that runs a Flask CLI command. RQ 1.15.1 has no built-in scheduler. The run time is Monday 08:00 UTC; there is no per-user timezone.
4. Each email lists at most 50 posts plus "and N more". The email is English only, matching the existing email templates.

## Phase 1: research
**Codebase findings that matter:**
- `User.following_posts()` (`app/models.py`) includes the user's own posts (`Author.id == self.id`), so it can't be reused here.
- `send_email` (`app/email.py`) starts one thread per message unless `sync=True` is passed.
- `app/tasks.py` calls `create_app()` when it is imported. Its `_set_task_progress` expects a matching `Task` row to exist.
- `get_locale()` (`app/__init__.py`) reads `request` without any guard.
- `Config.SERVER_NAME` is read from the environment, and Flask is pinned at 3.0.0.
- All 6 recent migrations use `batch_alter_table`.
- Tests are `unittest` in `tests.py` with in-memory SQLite.
- In `Procfile`, only `web` runs `db upgrade`.

**Prior art:** the RQ-plus-cron pattern, and RFC 8058 one-click `List-Unsubscribe`. I did this from what I already know; no web-search subagent was run.

**Consulted lessons before acting:** the repo has no `CLAUDE.md` and no lessons store, so none were consulted.

**Phase 0b:** nothing ambiguous came out of the research, so no further questions.

## Phase 2: shadow points (pre-mortem + MAST categories)
| Category | Shadow point | Mitigation |
|---|---|---|
| contract | Duplicate sends when cron re-runs or a job retries | Task checks the watermark and a minimum gap (skip if last send > `until − 6d`), plus a Redis `SET NX digest:{week}` lock in the CLI |
| data | The first run sends the whole history | Window starts no earlier than `until − 7d` |
| time-tz | SQLite returns naive datetimes; new posts get timezone-aware defaults | Convert everything to naive UTC before comparing; test the window boundaries |
| integration | Using `SERVER_NAME` for `url_for` breaks web routing on Flask 3.0 | Add a separate `DIGEST_BASE_URL`, or set `SERVER_NAME` only in the worker or CLI environment |
| integration | Babel's `get_locale` crashes outside a request | Return a default when `has_request_context()` is false |
| op-ex | A thread per email; SMTP rate limits | Use `sync=True` in the worker, one job per user, enqueue in batches |
| security / compliance | Bulk mail to unverified addresses; unsubscribe token mixed up with reset token | Dedicated `{'unsub': id}` token, long or no expiry; RFC 8058 POST endpoint exempt from CSRF; kill switch |
| security | HTML injection through post bodies | Jinja autoescaping in the `.html` template |
| concurrency | Crash partway through a run | Per-user jobs; the watermark is written only after a successful send |
| observability | Failed sends go unnoticed | Log one summary line per run; keep the RQ failed-job registry; logs from `--dry-run` |
| op-ex | Cron fires before the migration has run or before the worker restarts | Deploy order: upgrade, restart worker, then enable cron; `DIGEST_ENABLED` defaults to off |
| testing | `app.tasks` binds to the production app when imported | Put the logic in `app/digest.py` and keep the RQ task as a thin wrapper |

**Accepted risk:** if the send succeeds but the commit of the watermark fails, that user may get one duplicate.

## Phases 3–4: charter, macro plan and deliverables (revision 2)
- **D01 Migration** (batch mode): add `digest_opt_in` (`server_default=sa.true()`) and `last_digest_sent_at` (nullable). Run upgrade and then downgrade on SQLite.
- **D02 `app/digest.py`:**
  - `digest_posts(user, since, until)` returns posts by followed users only, newest first, capped, with a total count.
  - `send_digest(user_id, until)` runs the checks (kill switch, opt-in, minimum gap, empty list), renders `email/digest.{txt,html}`, sends with `sync=True`, then sets the watermark and commits.
- **D03** `app/tasks.py`: `send_weekly_digest` is a thin wrapper that does not use `_set_task_progress`.
- **D04 CLI** `flask digest send [--dry-run]`: computes `until` once, takes the Redis week lock, and enqueues jobs for opted-in users in id batches. `--dry-run` enqueues nothing.
- **D05 Unsubscribe:**
  - a GET confirmation page;
  - an RFC 8058 POST endpoint, exempt from CSRF;
  - `List-Unsubscribe` and `List-Unsubscribe-Post` headers;
  - an `EditProfileForm` toggle. The API keeps the field private.
- **D06 Config and ops:** `DIGEST_ENABLED` (default off), `DIGEST_MAX_POSTS`, `DIGEST_BASE_URL`, a cron example, and the deploy-order note in `README` or `deployment/`.
- **D07 Tests:**
  - the query leaves out own, unfollowed and old posts; a post at exactly `until` is included and one at exactly `since` is excluded;
  - one email per user, checked with `mail.record_messages`;
  - a re-run sends nothing; an opted-out user gets nothing; the kill switch blocks sending;
  - reset tokens and unsubscribe tokens are not interchangeable;
  - `--dry-run` enqueues nothing (mocked queue).

**Verification:** `python tests.py` passes. Then a manual run of `flask digest send --dry-run` followed by a real send against the aiosmtpd debug server, which is already in `requirements.txt`.

## Main risks
| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Duplicate or repeated digests | RQ 1.15 `job_id` doesn't de-duplicate; cron can re-fire | Watermark, 6-day minimum gap, Redis week lock |
| 2 | First run mails the whole history | `last_digest_sent_at` starts NULL | Window starts no earlier than `until − 7d` |
| 3 | Wrong posts at the window edges | SQLite returns naive datetimes; new posts are timezone-aware | Normalize to naive UTC; boundary tests |
| 4 | Web app returns 404s after deploy | `SERVER_NAME` restricts hosts on Flask 3.0 | Separate `DIGEST_BASE_URL` |
| 5 | Worker crashes on locale | `get_locale` reads `request` without a guard | `has_request_context()` guard |
| 6 | Spam complaints or blocklisting | Emails are unverified; all users are opted in | One-click unsubscribe, kill switch, skip empty digests |
| 7 | One thread per email; SMTP throttling | `send_email` uses a thread by default | `sync=True`, per-user jobs, batched enqueue |
| 8 | Unsubscribe token misuse | Only a 600s reset token exists today | Dedicated claim; tests that tokens don't cross over |
| 9 | Cron runs before the schema exists | Only `web` runs `db upgrade` | Deploy order; `DIGEST_ENABLED` off by default |
| 10 | Tests hit the production app | `app.tasks` calls `create_app()` on import | Logic in `app/digest.py`, thin task wrapper |

Riskiest: #1 — duplicate digests to the whole user base, because RQ's `job_id` doesn't prevent a cron re-run from sending everyone a second email.
