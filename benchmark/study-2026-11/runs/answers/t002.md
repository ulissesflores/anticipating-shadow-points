The weekly digest plan is finished and has passed one independent review round. I stopped at Phase 6 as asked: no project files were changed and nothing was run against the app. The full plan is in `claude-home/plans/standard-send-every-user-linked-dove.md`.

**What the code is missing today**
- **No scheduler.** The app only has an RQ worker (a background job queue). Something like a weekly cron job has to start each run.
- **No opt-out.** There is no email preference and no unsubscribe anywhere.
- **No email verification**, so the digest would also go to addresses nobody confirmed.

**Code facts that change the design**
- **`following_posts()` can't be reused.** It includes the user's own posts and has no date filter.
- **`app/tasks.py` creates the app as soon as it is imported**, so tests must not import it. The digest logic goes in a new `app/digest.py`.
- **`_set_task_progress()` would crash.** It expects a Task row, which a digest job doesn't have.
- **Rendering fails in the worker.** Both the translation function and absolute links (`url_for(_external=True)`) need a web request the worker doesn't have. Rendering inside a fake request built from a new `DIGEST_BASE_URL` setting fixes both.
- **Error logging could flood the admins.** In production every error log line is emailed to the admins, so a failure per user would mean thousands of emails.

**Assumptions I made instead of asking**
1. "Every user" means users who haven't opted out **and** have at least one new post that week. Empty digests are not sent.
2. The digest is on by default, with one-click unsubscribe and a profile toggle. Legal sign-off is needed before the first real send.
3. The window is a fixed UTC week, Monday to Monday. It is not "the last 7 days", so a late run or a rerun leaves no gaps or overlaps.
4. A digest shows at most 20 posts, then "and N more".
5. A weekly cron job calls a new `flask digest send` command. No new scheduler library is added.
6. English only for now.

**Plan in seven pieces**
- **D01:** a `digest_enabled` flag on users, a `DigestLog` table with one row per user per week, and the database migration.
- **D02:** `app/digest.py`, which finds eligible users and their posts and records the send as pending before sending.
- **D03:** the email templates and unsubscribe headers. `send_email` gets an optional `extra_headers` argument; existing callers are untouched.
- **D04:** the unsubscribe flow. Opening the link shows a confirm page, and only the confirm button changes anything, so link scanners can't unsubscribe people.
- **D05:** the background job and the `flask digest send/status` commands, with safety checks before anything is sent.
- **D06:** setup docs (cron line, settings, Postgres prerequisites).
- **D07:** tests for all of the above.

**Validator result:** it returned REVISE with 11 issues, and all 11 are now in the plan. The main ones:
- **Interrupted sends.** A crash mid-send would leave a user stuck as "pending" forever. The plan now sends at most once by default and adds an explicit `--retry-stale` option.
- **RQ job IDs don't prevent duplicates.** Re-queuing with the same job ID overwrites the old job, so the database record is the only guard.
- **Bad sender address.** Mail would go out from the placeholder `your-email@example.com`, which fails standard sender authentication checks (DMARC). A new `DIGEST_SENDER` setting is now required.
- **SQLite locking.** SQLite can't handle several workers writing at once. Production needs Postgres.
- **Missing Postgres test.** The migration is now tested on Postgres too.
- **Weak acceptance checks.** Several were too vague and now have specific automated tests.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Duplicate digests to every user | Cron double-fires, RQ retries, re-queuing a job ID overwrites it | `DigestLog` unique per user and week, recorded before sending; command skips users already logged; atomic retry |
| 2 | Silent non-delivery after a crash | A row stuck as pending is never retried | Send at most once; `status` reports stale rows; `--retry-stale` |
| 3 | Week window off by hours, or gaps | Post timestamps are stored without time zone; Postgres session time zone can shift times | Fixed UTC Monday weeks; compare without time zone; check `SHOW TimeZone` |
| 4 | Every job crashes in the worker | `get_locale` and `url_for(_external)` need a request | Fake request from `DIGEST_BASE_URL` + English locale; must match `SERVER_NAME` |
| 5 | Spam complaints, legal exposure | Mass mail with no opt-out today; on by default | One-click unsubscribe headers, profile toggle, legal gate, `DIGEST_ENABLED` off by default |
| 6 | Mail fails sender checks | Sender is placeholder `ADMINS[0]` | Required `DIGEST_SENDER`; set up SPF/DKIM/DMARC |
| 7 | Forged or accidental unsubscribes | Default `SECRET_KEY` is public; link scanners open GET links | Command refuses default key; token only valid for unsubscribe; only the confirm POST changes anything |
| 8 | Admin inbox flood | Every error log line is emailed to admins | Per-user failures logged as warnings; one summary error |
| 9 | Feature never actually runs | No scheduler exists | `flask digest send` + documented cron / Heroku Scheduler line |
| 10 | "Database is locked" | Command and RQ workers write to SQLite at the same time | Postgres for production; warn on SQLite |

Riskiest: #1, duplicate digests sent to the whole user base. Sent email can't be recalled, and the failure comes from ordinary retries and scheduling, not rare edge cases.
