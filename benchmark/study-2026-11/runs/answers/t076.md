Here's the plan for letting one account sign in with Google or with a password, linked by email. I changed no repo files; the plan is saved at `claude-home/plans/let-a-user-sign-curious-rocket.md`.

## What exists today
- **Password login:** `UserSessionLoginApi` and `UserJwtLoginApi` in `styleguide_example/authentication/apis.py`.
- **Google login:** only a blog demo, in `blog_examples/google_login_server_flow/sdk/`. It already finds the user by email, but:
  - it decodes Google's ID token **without checking its signature** (`jwt.decode(..., verify_signature=False)`);
  - it ignores Google's `email_verified` flag;
  - it does an exact-case email match;
  - it returns 404 if no user exists and never stores the Google ID (`sub`).
- **Signup:** `UserCreateApi` in `users/apis.py` creates password accounts for anyone, without checking that they own the email.

## Assumptions
- "Same account" means one `BaseUser` row, with the lowercased email as the link key.
- A first Google login with an unknown email creates the user, with no usable password.
- Google login creates a Django session, as the demo does. JWT for Google is out of scope.
- A Google-only user can add a password later through a new authenticated endpoint.

## Steps
1. **Model:** add two fields to `BaseUser` (`users/models.py`), plus a migration:
   - `google_sub`: nullable, unique;
   - `email_verified_at`: nullable.
2. **Verify the token properly:** add `verify_id_token()` to `GoogleSdkLoginFlowService`. It uses `google.oauth2.id_token.verify_oauth2_token` with our client ID as the audience; `google-auth` is already a dependency.
3. **Linking service:** add `auth_google_login(*, claims)` to `authentication/services.py`, run in one transaction:
   - Require `email_verified`.
   - If a user already has this `google_sub`, log them in.
   - Otherwise look up the email case-insensitively and lock the row. If that user is linked to a *different* `google_sub`, reject.
   - If found, link the account. If the email was never verified and the account has a password, wipe the password, rotate `jwt_key` (reuse `auth_logout`) and delete their sessions. This blocks someone who signed up with another person's email from keeping access.
   - If not found, create the user with `user_create(password=None)` and link.
   - Reject inactive users. On a unique-constraint race (two first logins at once), retry the lookup once.
4. **Endpoints:** add to `authentication/apis.py` and `authentication/urls.py`:
   - `google/redirect/` and `google/callback/`, reusing the demo's state/CSRF checks and logging in with an explicit `backend=`.
   - `password/set/`: login required; asks for the current password if one exists, validates the new one, rotates `jwt_key` and keeps the session.
   - Point `API_URI` at the new callback and register that redirect URI in the Google Console.
5. **Fix the demo:** switch the `sdk/apis.py` and `sdk/views.py` callbacks to the verified service. Otherwise the unverified email lookup stays exploitable.
6. **Password login:** lowercase the input email so it matches how emails are stored. `authenticate()` already rejects accounts without a usable password.
7. **Tests:**
   - Service tests: new user, linking an existing account, returning user, unverified email, case mismatch, conflicting `sub`, inactive user, password wipe on link.
   - API tests with Google mocked: state mismatch returns 400; after a Google login, a password login reaches the same user `id`.

**Verification:** run `pytest styleguide_example/authentication styleguide_example/users`, `mypy` and `makemigrations --check`. Then a manual run with real Google credentials: sign up with a password, log in with Google, and check `/api/auth/me/` returns the same `id`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Pre-signup account takeover | Anyone can sign up with someone else's email; when the real owner links Google, the squatter's password still works | Wipe the password, rotate `jwt_key` and drop sessions when linking an unverified account |
| 2 | Forged ID token | The current code skips signature checks, so a crafted token can claim any email | `verify_oauth2_token` with our client ID as audience |
| 3 | Unverified Google email | Linking on an email Google hasn't confirmed lets someone claim an account they don't own | Require `email_verified is True` |
| 4 | Demo endpoint left open | `blog_examples` callbacks still log in by unverified email | Route them through the shared service, or remove them |
| 5 | Email case mismatch | Stored emails are lowercased; the filter is exact-match | Lowercase the email and use `iexact` |
| 6 | Duplicate user on concurrent first login | Two callbacks for a new email can both try to create the user | Atomic transaction, `select_for_update`, unique constraints, retry once |
| 7 | Google-only user locked out of password login | They were created with no usable password and the repo has no reset flow | `password/set/` endpoint |
| 8 | Old sessions/JWTs survive a security change | JWTs stay valid until `jwt_key` changes | Rotate `jwt_key` and flush sessions on link and on password set |
| 9 | Redirect URI mismatch | The callback path changes and must be registered in the Google Console | Update the console and env config before deploying |
| 10 | Multiple-backend login error | `login()` needs an explicit `backend=` when the user didn't come from `authenticate()` | Pass `ModelBackend` explicitly |

Riskiest: #1, pre-signup account takeover. Signup here never checks email ownership, so linking by email alone hands the account to whoever registered first.
