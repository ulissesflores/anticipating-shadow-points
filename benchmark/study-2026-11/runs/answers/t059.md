The plan is ready (Phase 6) and no project files were changed. The independent validator answered REVISE. I checked its two main findings in the code, and the plan now includes every item it raised. I did not send the revised plan back for a second check.

**The obvious fix is the wrong one.** You could add `'post'` and `'patch'` to the default `retry.methods` list (`source/utils/normalize.ts:17`). But that list decides every kind of retry, not only network failures (`source/core/Ky.ts:703`). POST requests would then also be retried when the server answers 500, 502, 503, 504, 408 or 429, and an existing test that checks this doesn't happen (`test/retry.ts:322`) would start failing.

**Recommended design:** add a new option, `retry.networkErrorMethods`, with default `['post', 'patch']`. The retry check becomes: the method is in `methods`, or the error is a network error and the method is in `networkErrorMethods`. In practice:
- Only a failed connection triggers a retry for POST and PATCH. Status codes and timeouts still don't.
- `shouldRetry` can still veto a retry.
- The existing limit, backoff and jitter still apply.
- To turn it off: `retry: {networkErrorMethods: []}`, or `replaceOption([])` when using `.extend()`.

**Assumptions:**
- "The network fails" means the request itself was rejected with a network error. It does not include HTTP error statuses or timeouts.
- This changes default behavior, so it ships as a major version (3.0.0).
- Passing `null` for the new option throws a `TypeError` that names it, as `AGENTS.md` requires.
- The project has no lessons file, so `AGENTS.md` was the only one checked.

**Deliverables:**
- **D01 – types:** the new field in `source/types/retry.ts`, plus the matching type test.
- **D02 – validation:** defaults and checks in `normalize.ts`.
- **D03 – retry check:** the change at `Ky.ts:703`.
- **D04 – tests:** network failures, status codes, timeouts, turning it off, `null`, stream bodies, `onUploadProgress`, a custom `fetch`, and `.extend()`.
- **D05 – docs:** the readme, the doc comments that would become wrong, and a migration note recommending an `Idempotency-Key` header.

**What the validator caught:**
- `.extend()` joins arrays together instead of replacing them, so `networkErrorMethods: []` in a child client does not turn the feature off.
- `null` would currently produce a plain `Error` instead of a `TypeError`.
- The existing error message would wrongly say the new option "must only contain numbers".
- A callback that throws inside `onUploadProgress` now causes the POST body to be re-sent.
- Six doc comments would become wrong.

It also confirmed that `retry.methods` is read in only one place. Errors that happen while reading the response body never reach the retry logic.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Duplicate side effects (double charge or order) | Node's `'terminated'` and Safari's `'Load failed'` can fire after the server already handled the body | Docs warning, `Idempotency-Key` guidance, opt-out |
| 2 | Retrying on 5xx too | `retry.methods` decides every kind of retry | New `networkErrorMethods` option, not a change to `methods` |
| 3 | Silent change in behavior | Existing callers get POST retries without changing anything | Major version, migration note |
| 4 | Opt-out ignored in `.extend()` | Arrays are joined (`merge.ts:348-353`) | Document `replaceOption([])` and test it |
| 5 | `methods: ['get']` no longer means "never retry POST" | The new option applies regardless of `methods` | Document it; migration note shows the exact opt-out |
| 6 | `null` gives an unclear error | `normalize.ts:48` only filters out `undefined` | Explicit `TypeError` naming the option |
| 7 | Upload body sent again; progress callback runs again | A throwing `onUploadProgress` becomes a network error | Doc note and a test |
| 8 | `shouldRetry` and `beforeRetry` now run for POST | Before, POST was rejected before these ran | Update docs (`readme.md:304`, `retry.ts:143`) and test |
| 9 | Stale docs and type tests | Several docs say "retriable methods" and type tests list the exact fields | Update `NetworkError.ts:7`, `options.ts:186`, `test-d/normalized-options.ts` |
| 10 | Extra load on a recovering server | Many mobile clients replaying writes at once | Existing backoff, jitter and limit of 2 |

Riskiest: #1, duplicate side effects. A network error does not prove the server never received the POST, so any write without an idempotency key can be applied twice.
