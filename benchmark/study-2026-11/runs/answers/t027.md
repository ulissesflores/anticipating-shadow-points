## Assumptions (not asked, since this was a non-interactive run)
- The site runs on one Docker host with Docker Compose v2, using `docker-compose.prod.yml`. No Swarm or Kubernetes.
- "Zero downtime" means no 5xx responses or connection errors through nginx on port 1337. Postgres is not restarted by deploys.
- Old and new code briefly run side by side against the new schema, so every migration must work with the old code too: add first, remove in a later release.
- Switching to the new setup the first time needs one short nginx restart. Every deploy after that is zero-downtime.

## What I found in the repo
- **Downtime today:** `up -d --build` stops the old `web` container before the new one is ready. nginx also looks up `web:8000` only once, at startup or reload, so it won't find a new container on its own.
- **No automatic migrations:** `entrypoint.prod.sh` only waits for Postgres. The dev `entrypoint.sh` runs `flush --no-input`, which wipes the database, so it must never end up in the prod path.
- **No health checks** anywhere, and the image has no `curl`.
- **Old base image:** `python:3.11.4-slim-buster`. Debian buster is end-of-life and its package repos are archived, so the build may fail at `apt-get update`.
- **Prod debug mode is on:** `DEBUG = bool(os.environ.get("DEBUG", 0))` treats the string `"0"` as true, so prod currently runs with `DEBUG=True`.
- No project lessons, `CLAUDE.md` or memory were found. I skipped the web-research subagent and relied on well-known patterns instead.

## Validated plan (after Phase 6)
The independent validator returned **REVISE** with 9 issues. I checked them against the repo and accepted all of them. Only one validator round was run (the `--standard` setting), so the revised plan was not checked again.

1. **Health check:** a small middleware placed first in `MIDDLEWARE` answers `/healthz/` with a `SELECT 1` check, before Django checks the host name. The Compose health check uses Python's urllib with a 20-second start period.
2. **One image for app and migrations:** the image is tagged with the git commit and shared by `web` and a one-off `migrate` service. That service runs `migrate` and `collectstatic`, mounts the static volume, and sits in the `tools` profile so a plain `up` never runs it.
3. **nginx:** the upstream comes from an included file mounted from the host. Add `proxy_connect_timeout 2s` and pass an `X-App-Version` response header through.
4. **`scripts/deploy.sh`**, in this order:
   - take a lock with `flock` so two deploys can't overlap;
   - build and tag the image;
   - fail if `makemigrations --check` finds model changes without a migration;
   - back up the database with `pg_dump -Fc` and check the dump is non-empty;
   - run `migrate` with a 5-second lock timeout (passed via `PGOPTIONS`);
   - start a second `web` container with `--no-deps --no-recreate --scale web=2`, and find its ID by comparing container lists before and after;
   - wait until the new container is healthy;
   - write the new container's name into the upstream file, run `nginx -t`, then reload nginx;
   - check that responses on port 1337 carry the new version header;
   - wait 5 seconds, then stop the old container with a 30-second grace period.

   On any failure, the script removes only the new container by its ID and never scales down. Add `restart: unless-stopped` to the services.
5. **Migration policy** written into the README, with Django 4.2 specifics:
   - New columns must start out nullable. `AddField(default=…)` drops the database default, so inserts from the old code would fail.
   - Removing a field takes two releases: first remove it from Django's state with `SeparateDatabaseAndState`, then drop the column.
6. **Failure drills:** a broken migration, a new image that never becomes healthy, and an `nginx -t` failure. All of them run with `scripts/probe.sh` sending about 10 requests per second; it must record zero errors.
7. **Separate changes:** the base image moves to bookworm (`netcat-openbsd`), and the `DEBUG` parsing fix ships as its own deploy.

**Rollback:** run `APP_TAG=<previous sha> scripts/deploy.sh`. The schema is not rolled back. It stays compatible with the old code under the policy in step 5, and the `pg_dump` backup is the last resort.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | A migration breaks the old code still running | Old and new containers share the schema during the switch; in Django 4.2, `AddField(default)` drops the DB default | Add-first/remove-later policy, nullable new columns, review migrations before deploy |
| 2 | A migration locks a table and the site hangs | `migrate` runs against live prod traffic | `lock_timeout=5s` via `PGOPTIONS`; flag `atomic=False` and `RunSQL` migrations |
| 3 | nginx keeps sending traffic to the old or removed container | Docker DNS lists every running replica, and nginx caches the address | Explicit container name in the upstream file → `nginx -t` → reload → wait → stop old |
| 4 | Traffic reaches the new container before it is ready | Started is not the same as ready, and there are no health checks today | `/healthz/` check plus waiting for `healthy` before switching |
| 5 | Every deploy aborts on the health check | A real `ALLOWED_HOSTS` usually lacks `localhost`, so Django returns 400 | Health middleware runs before the host check |
| 6 | Migrations run from the old code or run twice | A separate build of the `migrate` service, or migrating at container startup | One commit-tagged image; single `migrate` run under `flock` |
| 7 | A failed deploy brings the broken image back up | `:latest` points at the new build; scaling down can remove the wrong container | Commit tags, remove the new container by ID, never scale down |
| 8 | The dev flush script wipes prod data | `entrypoint.sh` runs `flush --no-input` | Prod path never uses it; a test checks prod files for `flush` |
| 9 | The build fails during a deploy | The buster package repos are archived | Build before changing anything; move the base image to bookworm |
| 10 | A bad migration cannot be undone | Django migrations are not rolled back automatically | Checked `pg_dump` before migrating; abort before switching containers |

Riskiest: #1 — a migration that isn't compatible with the old code will cause 500 errors during the switch even if everything else in the deploy works, and no script can catch that; only the migration policy and review can.
