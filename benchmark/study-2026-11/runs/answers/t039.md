## What I found in the code
- **Delete wipes items three ways today.**
  - `models.py` has `cascade_delete=True` on `User.items` and `ondelete="CASCADE"` on `Item.owner_id`.
  - `users.delete_user` also runs an explicit `delete(Item)` before `session.delete(user)`.
- **Old logins stay valid.** Tokens last 8 days (`ACCESS_TOKEN_EXPIRE_MINUTES`). `deps.get_current_user` only checks `is_active`.
- **Many places look users up by email.** These are in `crud.py`, `login.py` (login, password recovery and reset) and `users.py` (email uniqueness checks).
- **Existing timestamps are timezone-aware** (`DateTime(timezone=True)`), so a new deletion timestamp should be too.
- **There is no job scheduler.** The deploy only runs `prestart.sh`.
- **Two frontend texts promise permanent deletion.** One is the admin delete dialog. The other is `UserSettings/DeleteConfirmation.tsx`, which says "permanently deleted".

## Assumptions
- **Separate field.** A new `deleted_at` marks deletion. It is kept apart from `is_active`, which admins already use to suspend accounts.
- **Who can do what.** Both self-delete and admin delete become soft deletes. Only a superuser can restore.
- **Email stays taken.** While an account is deleted, its email can't be reused. Signup shows the same "already exists" error as for any other taken email.
- **No audit table.** Deletes and restores are written to the log only.
- **What happens after 30 days (changed after validation).** "Keeps their items" means the items are never deleted. So after 30 days the account is anonymized instead of deleted:
  - A purge script scrubs the email, password and name, and sets a `purged_at` timestamp.
  - The user row stays, so the database never cascades the delete to items, and the email becomes free again.
  - Ops has to schedule the script. The 30-day limit is checked at restore time anyway, so behaviour is correct even if the purge never runs.

## Plan (after revision 1)
1. **Model and migration.**
   - Add timezone-aware `deleted_at` and `purged_at` columns with an index, plus a `RESTORE_WINDOW_DAYS=30` setting.
   - The downgrade first sets `is_active=false` on deleted users. Without that, dropping the column would silently bring them back.
2. **Login and token checks.**
   - `get_current_user` returns 404 for deleted users.
   - Login and password reset treat a deleted user exactly like an unknown email, with the same error message and the same timing.
   - Password recovery sends nothing for deleted users.
   - One helper does this: `get_user_by_email(include_deleted=False)` by default; the email uniqueness checks pass `True`.
3. **Shared logic in `crud.py`.**
   - `soft_delete_user`, `restore_user(now)` and `purge_expired_users(now)`.
   - Restore and purge use one shared check for "within 30 days", with exactly 30 days counting as restorable.
4. **Routes.**
   - Both delete endpoints soft-delete, and the explicit `delete(Item)` statement is removed.
   - Deleting an already-deleted user returns 404 and leaves `deleted_at` unchanged.
   - The admin user list hides deleted users unless `?include_deleted=true` is passed.
   - New `POST /users/{id}/restore` returns 404 if the user isn't deleted and 410 if the window has passed or the account was purged.
   - Editing a deleted user returns 409.
5. **Purge script.** It anonymizes expired accounts, has a `--dry-run` option and is safe to run repeatedly.
6. **Tests.**
   - Rewrite `test_delete_user_me` and `test_delete_user_super_user` to check that items survive.
   - Add tests for login and token rejection, restore at exactly 30 days and at 30 days + 1 second (with the time passed in), a double delete, the list filter, the purge, and signup with a deleted user's email.
   - Add a test that restoring a superuser keeps superuser rights.
7. **Frontend.**
   - Regenerate the API client.
   - In the admin page, add a "Show deleted" toggle, a "Deleted" badge and a Restore action.
   - Fix the copy in both delete dialogs.
   - Update `admin.spec.ts` and `user-settings.spec.ts` to cover delete, then show deleted, then restore, then log in.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Items still get hard-deleted | ORM cascade, database cascade and an explicit `delete(Item)` all exist | Remove every `session.delete(user)`; purge only anonymizes; test that items survive |
| 2 | A deleted user's old login still works | Tokens last 8 days; `get_current_user` only checks `is_active` | Reject `deleted_at` in `get_current_user`; test it |
| 3 | Password reset or login revives a deleted account | `login.py` looks users up by email in 4 places | `get_user_by_email` hides deleted users by default |
| 4 | Error messages reveal that an account is deleted | Login returns "Inactive user" (400) | Same error and timing as an unknown email |
| 5 | Off-by-one or timezone bug at the 30-day mark | The comparison mixes stored and current times | Timezone-aware column, time passed in, one shared check, boundary tests |
| 6 | Admin can't find deleted users to restore them | The list hides them by default | `include_deleted` flag plus the "Show deleted" toggle |
| 7 | Downgrade brings deleted users back | Dropping the column makes them active again | Downgrade sets `is_active=false` first |
| 8 | Purge never runs, so personal data is kept forever | There is no scheduler | Document the cron; restore checks the 30 days on its own |
| 9 | Email stays taken or reveals the account | `email` must be unique | Same signup error; purge frees the email |
| 10 | Frontend breaks or says the wrong thing | Generated client; both dialogs say "permanently deleted" | Regenerate the client; update both Playwright specs |

Riskiest: #1. Three separate code paths delete items today, so missing any one of them silently breaks the core promise that a deleted user's items are kept.
