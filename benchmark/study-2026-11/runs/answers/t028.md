The plan is ready and has been through one validator round. I stopped at Phase 6 as you asked: nothing was approved or executed, and the only file written is the plan at `claude-home/plans/standard-let-a-user-inherited-teacup.md`.

## What the code does today
- **Password login** is in `styleguide_example/authentication/apis.py` and goes through Django's `authenticate()`.
- **Google login** exists only as a blog example in `blog_examples/google_login_server_flow/{sdk,raw}/apis.py`. It has four security gaps:
  - It reads the Google ID token without checking its signature (`verify_signature=False`).
  - It ignores Google's `email_verified` flag.
  - It finds the user by an exact, case-sensitive email match.
  - It calls `login()` directly, which skips the `is_active` check, so a disabled user could still sign in.
- **Anyone can create an account with a password.** `POST /api/users/create/` needs no login and sends no verification email, and no default permission class is set. This makes "link by email" open to account pre-hijacking: an attacker registers your email with a password first, you later sign in with Google, the two get linked, and the attacker still has a working password.
- **No lessons file:** the repo has no CLAUDE.md or lessons store to consult. I did not run web research this time; the Google guidance in the plan comes from what I already know.

## Assumptions (in place of questions)
1. This is production code, not a blog example. It goes in `authentication/` and `users/` and reuses `GoogleSdkLoginFlowService`.
2. Signing in with Google using an unknown, verified email creates a new account with no usable password.
3. Google sign-in links to an existing password account automatically only when both are true:
   - Google reports `email_verified=true`.
   - That account's email is verified on our side, or it has no usable password.
   
   Otherwise the user must sign in with their password and use "Connect Google".
4. A Google-only user can add a password through a logged-in endpoint. Email-based password reset is out of scope because the app has no mailer.

## Plan (revision 2)
- **D01 – Model:** add `BaseUser.email_verified` (defaults to False for existing rows, editable in admin). Add a `UserSocialIdentity` table holding the user, provider and Google's account ID (`sub`), with two uniqueness rules: one row per (provider, `sub`) and one per (user, provider). Migration is `users/0004`.
- **D02 – Token check:** verify the ID token with `google.oauth2.id_token.verify_oauth2_token` against our client ID, and check `email_verified`. This uses a subclass of the existing service that overrides `API_URI`, because the current one sends users back to the blog example's callback.
- **D03 – Services:** look up the user by Google `sub` first. If none, match on email ignoring case, but only under the assumption-3 conditions, and refuse when that user already has a different Google identity. If still none, create the user.
  - It all runs in one transaction and retries once if two first-time sign-ins race.
  - It refuses users with `is_active=False`.
  - Also included: connect, unlink (blocked if the user has no password) and set-password, which rotates `jwt_key` so other JWTs stop working and keeps the current session alive with `update_session_auth_hash`.
- **D04 – APIs:** one redirect endpoint and one callback, with the session storing `{state, mode: login|connect, user_id}`. "Connect Google" works with session login only. The callback redirects to the frontend with a generic result code, never the email or token claims. Link, create, refuse, unlink and password changes are logged with structlog.
- **D05 – Tests,** with the Google calls mocked:
  - The pre-hijack attempt is refused.
  - A Google account with `email_verified=false` is refused.
  - Email matching ignores case.
  - A returning user is found by `sub` after changing their Google email.
  - An inactive user is refused.
  - A second Google account with the same email is refused.
  - A token minted at login can't be reused to connect.
  - A token with the wrong audience is rejected.
  - Unlink is blocked when the user has no password.
  - After setting a password, old JWTs no longer work.

**Verification:** run `pytest` on `authentication` and `users`, run `mypy`, run `makemigrations --check`, plus one smoke test with real Google credentials.

**Validator:** it returned REVISE with 10 issues. All 10 are folded into revision 2, including the hard-wired redirect URI, the connect flow not being specified, and a second Google account with the same email crashing with a 500. One remains open: it suspects that google-auth-oauthlib 1.2.2 adds PKCE automatically, so the token exchange would fail with `invalid_grant`. I couldn't confirm this because the package isn't installed locally, so it is gated on the real-credentials smoke test.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Account pre-hijacking | Anyone can sign up with a password via `/users/create/`, and no email is verified | Link automatically only if our side has verified the email or the account has no password; otherwise use "Connect Google" |
| 2 | Forged or replayed ID token | The blog example skips the signature check | `verify_oauth2_token` with our client ID; test a token with the wrong audience |
| 3 | Unverified Google email used to log in | `email_verified` is never read | Refuse unless it is true |
| 4 | Duplicate account when the Google email changes | Lookup is by email only | `UserSocialIdentity` keyed by `sub`, looked up first |
| 5 | Email case mismatch | Stored emails are lower-case; the filter is exact | Case-insensitive lookup plus lower-casing |
| 6 | Disabled user signs in via Google | `login()` skips `is_active` | Check it explicitly, with a test |
| 7 | Forced linking via a crafted callback | Login and connect would share one callback | Store the mode and user in the session alongside the state; test cross-mode reuse |
| 8 | Old JWTs survive a password change or unlink | `jwt_key` is not rotated | Rotate it, keep the current session, test that the old JWT fails |
| 9 | Token exchange fails (PKCE) | Library may add a code verifier the current code drops | Store the verifier in the session; real-credentials smoke test |
| 10 | Locked out after unlinking Google | A Google-only user has no password | Block unlink without a password |

Riskiest: #1, account pre-hijacking. Combined with open, unverified password signup, linking by email lets an attacker keep access to the victim's account.
