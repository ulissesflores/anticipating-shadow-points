I've written the plan for the weekly digest; no project files were changed. The plan is saved at `claude-home/plans/send-every-user-a-eventual-aurora.md`.

**What the codebase gives us:** this is the Flask Mega-Tutorial app at chapter 23. It already has follows, a background worker (RQ, the `microblog-tasks` queue), an email helper (`send_email` in `app/email.py`) and a background-task pattern to copy (`export_posts` in `app/tasks.py`). It has nothing that runs on a schedule. The existing feed query, `User.following_posts()` at `app/models.py:166`, includes the user's own posts, so the digest needs its own query.

**Assumptions (no one to ask in this run):**
- "People they follow" excludes the user's own posts.
- Each digest covers the posts since the last digest, going back at most 7 days.
- Users with no new posts get no email.
- Everyone is subscribed by default and can opt out, both in their profile settings and through a link in every email.
- Each email shows at most 50 posts, with an "and N more" link.
- The weekly schedule comes from outside the app: cron or Heroku Scheduler running a new `flask digest send` command.
- Emails are English-only for now.

**Plan:**
1. **Database:** add two fields to `User`: `digest_enabled` (on by default, including for existing users) and `last_digest_sent`. This needs one new migration after `834b1a697901`. Add a `followed_posts_since(since)` query that covers only followed users, plus an unsubscribe token built the same way as the password-reset token.
2. **Background job:** add `send_weekly_digest(user_id)` to `app/tasks.py`. It re-checks the opt-out and skips anyone sent a digest in the last 6 days, so running it twice does no harm. It builds the email and sends it, and only records `last_digest_sent` after the send succeeds. It won't use `User.launch_task`, because that would show progress notifications in the user's UI.
3. **Trigger:** `flask digest send` in `app/cli.py` goes through opted-in users in batches. It queues one job per user with up to 3 retries and a job id per user per week, so a second run in the same week doesn't queue duplicates. It also has a dry-run option.
4. **Email templates:** `email/weekly_digest.txt` and `.html`, with full links and an unsubscribe link.
5. **Opt-out:** a checkbox in `EditProfileForm` and the `edit_profile` route. A token-based unsubscribe page that needs no login: opening the link shows a confirm page and only the button unsubscribes, so email scanners that open links can't unsubscribe anyone. The new text also goes into the Spanish translation file.
6. **Config and deploy:** add a `DIGEST_MAX_POSTS` setting, require `SERVER_NAME` to be set for the worker, and document the cron or Heroku Scheduler entry.

**How to verify:**
- Unit tests in `tests.py`:
  - The new query leaves out your own posts, people you don't follow, and old posts.
  - The job skips opted-out users, users with no new posts, and users who just got a digest.
  - The unsubscribe token works both ways.
  - These capture emails with `mail.record_messages()` and run without Redis.
- Manual run: a local `aiosmtpd` debug mail server, an RQ worker and `flask digest send`, then run it a second time and check that no new emails go out.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate digests | No scheduler exists yet, so cron runs overlap and RQ retries resend | 6-day guard on `last_digest_sent`, one job id per user per week, record the send only after it succeeds |
| 2 | Links break in the worker | `url_for(_external=True)` has no request to build from, so it needs `SERVER_NAME` | Require `SERVER_NAME`; fail early in the CLI if it's missing |
| 3 | Translation calls crash | The locale is read from the request, which doesn't exist in the worker | Plain English strings, or `force_locale('en')` |
| 4 | Wrong posts in the date window | SQLite stores naive datetimes but the code mixes in timezone-aware ones | Compare in naive UTC; add a boundary test |
| 5 | Wrong recipients | `following_posts()` includes your own posts | New `followed_posts_since` query, with tests |
| 6 | Bulk mail without an opt-out | Legal exposure and spam complaints | Opt-out by default, unsubscribe link in every email, confirm page before unsubscribing |
| 7 | SMTP limits or slow sends | One connection per email, one worker process | One job per user, retries with backoff, add more workers if needed |
| 8 | Huge emails | Users who follow very active accounts | Cap at 50 posts plus "and N more" |
| 9 | Users' email addresses leak into logs | The task's error logging already emails tracebacks to the admins | Log user ids only |
| 10 | Migration on existing rows | A new non-null column fails without a default | `server_default=true` in the migration |

Riskiest: #1 duplicate digests, because nothing in the app schedules or deduplicates jobs today, and resending to every user is very visible and can't be undone.
