I recommend a new default, `retry.networkErrorMethods: ['post', 'patch']`, so POST and PATCH are retried only when the network fails. Adding them to the existing `retry.methods` list would also retry them on 500/502/503/504/408/429 responses, where the server definitely ran the request. Nothing in the repo was edited; the only file written is the plan at `claude-home/plans/make-ky-retry-post-quiet-bonbon.md`.

## Assumptions
- "Network fails" means a `NetworkError` only. Timeouts and HTTP error statuses don't count, and `retryOnTimeout` stays `false`.
- The default retry count (2) and backoff stay the same.
- Ky won't add an `Idempotency-Key` header automatically, because that would trigger CORS preflight requests. The docs will recommend it instead.
- Changing a default like this is a breaking change, so it ships as **3.0.0** (the package is at 2.2.0).

## Changes
1. **`source/utils/normalize.ts`**: add the default `['post', 'patch']`. Run the new option through the same checks as `methods`: it must be an array, entries must be strings, and method names are lowercased. A `null` value already fails the array check with `retry.networkErrorMethods must be an array`, which names the option as `AGENTS.md` requires. No `null` fallback.
2. **`source/types/retry.ts`**: add `networkErrorMethods?: readonly HttpMethod[] | undefined` with docs (duplicate-write warning, how to opt out). Add it to the `MutableRetryOptions` overrides. The internal option type in `options.ts:521` picks it up automatically.
3. **`source/core/Ky.ts` `#calculateRetryDelay`** (around line 703): change the method check to `methods.includes(m) || (isNetworkError(errorObject) && networkErrorMethods.includes(m))`.
   - `shouldRetry` runs after this check, so it will now also be called for POST/PATCH network errors, but still not for their HTTP errors.
   - Retries forced with `ky.retry()` are unchanged.
   - Stream bodies need no new work: the retry copy is already made whenever the retry limit is above 0 (`Ky.ts:1225`).
4. **`readme.md`** (retry section around lines 265–330, and the NetworkError section around line 1415) and the JSDoc at `options.ts:186`: document the option, the duplicate-write caveat, the idempotency-key advice, and how to opt out with `networkErrorMethods: []` or `retry: 0`. Add a migration note for 3.0.0.

## Risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate writes (double orders or payments) | A network error can't tell whether the server already got and ran the POST; mobile drops often happen after it was sent | Document clearly; recommend an `Idempotency-Key` header; easy opt-out with `[]` |
| 2 | Silent breaking change for existing users | Code that relied on "POST is never retried" now resends without any code change | Major version 3.0.0, migration note, changelog |
| 3 | `shouldRetry` now runs for POST/PATCH | Existing callbacks may assume they only see safe methods and return `true` | Document; add a test; mention in the migration note |
| 4 | Upload progress callback runs again | `onUploadProgress` already restarts on retry; POST/PATCH carry most uploads | Document; retrying without progress via `beforeRetry` is already documented |
| 5 | Large stream bodies held in memory | Retry copies use `tee()`, which keeps the whole body in memory | Already the case when the limit is above 0; document `retry: 0` for big uploads |
| 6 | Confusing overlap with `methods` | Two method lists; users may not know which one applies | Clear docs: `methods` covers all errors, the new list covers network errors only |
| 7 | Retries when the network check guesses wrong | Network errors are detected from runtime-specific error messages | Retry only confirmed `NetworkError`s; existing tests cover detection |
| 8 | More server load during outages | Every mobile client resends POSTs with the same backoff | Keep the default limit at 2; suggest `jitter` in the docs |
| 9 | `null` slipping through as "use the default" | `AGENTS.md` forbids `null` fallbacks | Rely on the array check; add a test that the error names the option |

Riskiest: #1. Duplicate non-idempotent writes, because a network error can't show whether the server already ran the POST.
