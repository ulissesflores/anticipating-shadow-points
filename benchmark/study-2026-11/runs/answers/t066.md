## What the code does today

- **Two hard-delete paths, both removing items:**
  - `DELETE /users/me` (`app/api/routes/users.py:131`) calls `session.delete(user)`. Because of `cascade_delete=True` on `User.items`, the ORM deletes the items too.
  - `DELETE /users/{id}` (`users.py:217`) runs an explicit `delete(Item)` and then deletes the user.
  - The database also has `ondelete="CASCADE"` on `item.owner_id` (migration `1a31ce608336`). Items are removed at three separate levels.
- **Auth only checks `is_active`:** `get_current_user` (`app/api/deps.py:30`), `login_access_token` (`login.py:24`) and `reset_password` (`login.py:78`) all do this. `recover_password` sends an email to any matching user. JWTs are stateless and stay valid until they expire.
- **`email` is unique** (`models.py`), and `get_user_by_email` drives signup, create, update and login.
- **No scheduler** (no cron, Celery or APScheduler), so nothing can enforce or purge after 30 days automatically.
- **Frontend copy says "permanently deleted"** (`frontend/src/components/Admin/DeleteUser.tsx:70`, plus `UserSettings/DeleteAccount.tsx`).

## Ways this could go wrong

1. Items still get deleted, because one of the three cascade layers (route, ORM, database FK) is left in place.
2. A deleted user can keep working: an existing JWT passes `get_current_user`, or login or password reset still succeeds.
3. Re-signup with the same email fails with "already exists", and that also reveals the account existed.
4. Restore collides with a new account that has since taken the same email.
5. Restore brings back the wrong state, for example re-activating a user an admin had deliberately set `is_active=False` before deletion.
6. The 30-day limit is never enforced, or data is never purged (a GDPR / right-to-erasure problem).
7. Comparing a naive datetime with an aware one breaks the 30-day check.
8. Leaks: deleted users still show up in `read_users` (and its count) and `read_user_by_id`, or the password-recovery email still goes to them.
9. Items whose owner is deleted are still visible to superusers in `/items`. That may or may not be intended.
10. Existing tests assert hard deletion (`tests/api/routes/test_users.py`), and the generated frontend client goes stale.

## Assumptions (no questions asked, since this run is non-interactive)

- Soft delete means a nullable `deleted_at` timestamp on `user`. `is_active` is not reused; it stays the admin "deactivate" switch.
- Both delete endpoints become soft deletes. Items stay untouched in the database. Superusers can still see them in `/items`; the owner can't, because they can't log in.
- A deleted user's email stays reserved until purge. Signup with it is rejected with the existing generic message. This also means restore can never hit an email conflict.
- Restore is superuser-only and allowed only while `now - deleted_at <= 30 days`. After that it returns 410.
- Actual purging after 30 days is a separate manual script (`app/purge_deleted_users.py`, run by external cron). It hard-deletes, so the existing cascade applies. There's no in-app scheduler.

## Plan

1. **Model and migration**
   - Add `deleted_at: datetime | None = Field(default=None, sa_type=DateTime(timezone=True), index=True)` to `User`.
   - Expose `deleted_at` in `UserPublic`.
   - Add a new Alembic revision after `fe56fa70289e`.
   - Keep `cascade_delete`/`ondelete` for the purge path, and make sure no soft-delete path calls `session.delete`.
2. **CRUD** (`app/crud.py`)
   - Add `soft_delete_user`, `restore_user`, and a `RESTORE_WINDOW = timedelta(days=30)` constant, possibly as a setting in `core/config.py`.
   - Have `authenticate` return `None` for deleted users while still running the dummy hash check, so timing stays constant.
3. **Auth gates**
   - `get_current_user`: reject `deleted_at is not None` with the same response as "user not found". This also cuts off live JWTs.
   - `recover_password`: skip sending the email to deleted users.
   - `reset_password`: reject deleted users.
4. **Routes** (`users.py`)
   - Both DELETE endpoints set `deleted_at` instead of deleting.
   - `read_users`: add an `include_deleted: bool = False` filter, applied to both the count and the list.
   - `read_user_by_id`: return 404 for deleted users unless the caller is a superuser.
   - Add `POST /users/{id}/restore` for superusers: 404 if the user isn't deleted, 410 if the window has passed, otherwise clear `deleted_at`.
5. **Purge script**: hard-delete users where `deleted_at < now - 30d`.
6. **Frontend**
   - Regenerate the client.
   - Change the "permanently deleted" copy in `DeleteUser.tsx` and `DeleteAccount.tsx`.
   - In the admin table, add a "show deleted" toggle, a Deleted badge, and a Restore action in `UserActionsMenu.tsx`.
7. **Tests**
   - Update the hard-delete assertions.
   - Add cases for:
     - the deleted user's items are kept;
     - their token is rejected;
     - login fails for a deleted user;
     - recovery sends no email;
     - restore works at 29 days and returns 410 at 31 days (patch the clock);
     - re-signup with the same email is blocked;
     - a deleted user is hidden from the list by default.

**Verification:** run `bash scripts/test.sh` in the backend, `alembic upgrade head` followed by `downgrade -1`, and the frontend Playwright admin tests. Then check by hand: delete a user, confirm their items are still there and their old token gets 404, restore them, and log in again.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Items still hard-deleted | Cascade exists in three places: the route's `delete(Item)`, ORM `cascade_delete`, and the FK `ON DELETE CASCADE` | Remove every `session.delete` from the delete paths; add a test that items survive |
| 2 | Deleted user keeps access | `get_current_user` and login only check `is_active`; JWTs are stateless | Check `deleted_at` in `deps.py` and `authenticate`; test with an old token |
| 3 | Email uniqueness conflicts | `email` has a unique index; signup or create with a deleted user's email fails | Keep the email reserved until purge; use the generic error message |
| 4 | 30 days never enforced or purged | No scheduler in the stack | Check the window at restore time; add a purge script for external cron |
| 5 | Timezone bugs in the window check | `created_at` pattern; naive vs aware datetimes | Use `DateTime(timezone=True)` and UTC everywhere; test the boundary |
| 6 | Overloading `is_active` | Deactivation and deletion would be confused on restore | Separate `deleted_at` column |
| 7 | Deleted users leak via list, get or recovery | `read_users`, `read_user_by_id` and `recover_password` don't filter | Filter by default; superuser-only `include_deleted` |
| 8 | Orphaned items' visibility unclear | Superuser `/items` shows every item | Document it as intended; filter later if needed |
| 9 | Tests and frontend out of sync | Tests assert hard delete; the UI says "permanently" | Update tests, regenerate the client, fix the copy |
| 10 | Migration on existing data | New column on the `user` table | Nullable with no default; check the downgrade |

Riskiest: #1. Items are cascade-deleted in three places (route, ORM, database FK), so missing any one of them silently destroys the data this feature exists to keep.
