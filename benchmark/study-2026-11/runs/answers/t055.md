I mapped the code paths before planning. This is the FastAPI full-stack template (SQLModel + Alembic + a React admin UI). I didn't edit any files, and that includes the plan file, because you asked for no edits.

## What the code does today
- **Hard delete in three places:**
  - `delete_user` (`backend/app/api/routes/users.py:231`) runs an explicit `delete(Item)` and then `session.delete(user)`.
  - `delete_user_me` (`users.py:136`) calls `session.delete`.
  - The ORM `User.items` has `cascade_delete=True`, and the database foreign key is `ondelete="CASCADE"` (`backend/app/models.py:57,88`). So deleting a user wipes their items at both the ORM and the database level.
- **User lookups have no filtering:** `get_current_user` (`backend/app/api/deps.py:30`) uses `session.get(User, sub)`. `crud.get_user_by_email` is shared by login, signup, password recovery and reset, and admin create/update. `read_users` counts every row.
- **Email must be unique** at the database level (`models.py:14`).

## Assumptions
1. A new nullable column, `deleted_at` (timezone-aware). I won't reuse `is_active`, because restore has to bring back the previous active/inactive state.
2. Both admin delete and self-delete become soft deletes. Items stay in place. The owner can't reach them while deleted, and superusers can still see them.
3. Restore is admin-only (`POST /users/{id}/restore`). It's allowed only while `now - deleted_at <= 30 days`; after that the API returns 410.
4. No automatic purge job is part of this change. When and how to purge, and whether items survive a purge, is a separate decision.
5. A soft-deleted user keeps their email, so nobody can register with it during the window. The error message stays the same generic "already exists" text.

## Plan
1. **Model and migration.** Add `deleted_at: datetime | None` to `User`, with an index, and expose it on `UserPublic`. Write an Alembic migration modeled on `fe56fa70289e_add_created_at_to_user_and_item.py`. Leave the `CASCADE` foreign key in place so a future purge still works, but stop every code path from hard-deleting.
2. **CRUD.** Add `crud.soft_delete_user` and `crud.restore_user` (with the window check), plus a single `RESTORE_WINDOW = timedelta(days=30)`.
3. **Shut out deleted users everywhere:**
   - Make `get_current_user` reject them, which also kills existing JWTs (they last 8 days).
   - Make `crud.authenticate` and the recovery/reset routes in `login.py` treat them as nonexistent, while still running the dummy hash so response timing doesn't change.
4. **Admin API:**
   - `read_users` excludes deleted users by default and takes `include_deleted` / `deleted_only` flags.
   - `read_user_by_id` and `update_user` return 404 for deleted users unless the caller is a superuser using the restore path.
   - Add the restore endpoint.
5. **Frontend.** Regenerate the OpenAPI client. Update the wording in `frontend/src/components/Admin/DeleteUser.tsx`. Add a "Deleted" filter and a Restore action to `UserActionsMenu.tsx` / `columns.tsx`.
6. **Tests.** Update `backend/tests/api/routes/test_users.py`, whose delete tests currently expect the row to be gone. Add tests for:
   - items surviving a delete
   - login, token, and password reset failing for a deleted user
   - restore at 29 and 31 days
   - signup with a deleted user's email
   - list counts

**Verification:** run `bash scripts/test.sh` (backend pytest), then the Playwright admin tests in `frontend/tests`. Then do a manual check: delete a user, confirm their old token gets rejected and their items still exist, restore them, and confirm they can log in.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Items still get hard-deleted | Item deletion happens in three places: explicit `delete(Item)`, the ORM `cascade_delete`, and the database `ondelete=CASCADE` | Remove every `session.delete(user)` call and add a test that items survive |
| 2 | Deleted user can still log in or call the API | `get_current_user` uses `session.get`, and JWTs stay valid for 8 days | Check `deleted_at` in deps and in `authenticate` |
| 3 | Password reset brings the account back | `login.py` recovery/reset routes look users up with `get_user_by_email` | Treat deleted users as nonexistent there, keeping the dummy hash for timing |
| 4 | Email collisions | DB-level unique email: re-signup fails, and if reuse were allowed, a restore could clash | Keep the email reserved during the window and use a generic error |
| 5 | Missed query filters | Lists, counts, `read_user_by_id`, and admin update all read unfiltered | Use a shared "active users" helper and test each endpoint |
| 6 | Restore wipes the previous state | Reusing `is_active` loses whether the admin had disabled the user | Use a separate `deleted_at` column |
| 7 | Timezone bugs in the 30-day check | `get_datetime_utc` is timezone-aware; a column without timezone gives naive values and comparisons raise TypeError | Use a `DateTime(timezone=True)` column and test the boundary |
| 8 | Existing tests and UI assume a hard delete | `test_users` asserts the row is gone; the UI copy says "permanently" | Update tests and copy, and regenerate the client |
| 9 | "Keeps items" is unclear after day 30 | A future purge would cascade items through the foreign key | Decide what purge does before building it |

Riskiest: #2. A soft-deleted user's existing JWT still works for up to 8 days, because `get_current_user` doesn't check `deleted_at`.
