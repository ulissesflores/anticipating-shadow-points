I've written the plan to `claude-home/plans/send-every-user-a-golden-kernighan.md`; no project files were edited. The app is the Flask Mega-Tutorial microblog at v0.23. It already has follows, Flask-Mail (`app/email.py`) and an RQ worker (`app/tasks.py`), but no scheduler and no email preferences.

**Assumptions**
- "New posts" means posts from people the user follows, created since that user's last digest (or the last 7 days the first time). The user's own posts are left out.
- Users with nothing new get no email.
- Everyone is opted in by default, and each email has an unsubscribe link.
- A cron entry outside the app (cron, Heroku Scheduler or a k8s CronJob) runs a new `flask digest send` command once a week.
- Emails go out in English with UTC times, because the app doesn't store a language or timezone per user.

**Plan**
1. **`User` model** (`app/models.py`):
   - Add `digest_enabled` (on by default) and `last_digest_sent`, plus an Alembic migration.
   - Add `digest_posts(since)`, built from `following_posts()` but with an inner join so the user's own posts are left out.
2. **Worker task** `send_weekly_digest(user_id, period_end)` in `app/tasks.py`:
   - Skip users who turned digests off or have no new posts.
   - Otherwise build the email inside `test_request_context()` and `force_locale('en')`. This is needed because `get_locale()` reads `request`, and the links need `SERVER_NAME`.
   - Send with `send_email(..., sync=True)`, then save `last_digest_sent`.
   - Don't use `launch_task`; it creates `Task` rows and progress notifications the user would see.
3. **CLI command** `flask digest send [--dry-run] [--user X]` in `app/cli.py`:
   - Pick users who have digests on and haven't had one in the last 6 days.
   - Queue one job per user on `microblog-tasks`.
4. **Email templates** `email/weekly_digest.{txt,html}`, modelled on `export_posts.*`. They show at most `DIGEST_MAX_POSTS` posts, with "and N more" linking to `/index`, plus an unsubscribe link.
5. **Unsubscribe**:
   - Sign a token the same way `get_reset_password_token` does.
   - Add a page that works without login: it shows a confirm form, and confirming turns digests off.
   - Add a "weekly digest" checkbox to `EditProfileForm`.
6. **Config, translations and ops**:
   - Add `DIGEST_MAX_POSTS` to `config.py`.
   - Add Spanish translations for the new text.
   - Document the cron line and that `SERVER_NAME` must be set.
7. **Verification**:
   - Unit tests in `tests.py` for:
     - which posts are picked;
     - skipping users with digests off or nothing new;
     - updating `last_digest_sent`.
   - A manual run against a local aiosmtpd debug server plus `rq worker`. Running `flask digest send` a second time should send nothing.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate or missed digests | Cron retries and worker crashes, while `last_digest_sent` is written only after sending | Pass `period_end`; select only users with no digest in the last 6 days; commit right after sending |
| 2 | Rendering crashes outside a request | `get_locale()` reads `request`, and `url_for(_external)` needs `SERVER_NAME` | `test_request_context()` + `force_locale`; check config at startup |
| 3 | Spam complaints or legal exposure | Opt-in by default and no existing unsubscribe | Signed unsubscribe link, profile setting, `List-Unsubscribe` header |
| 4 | SMTP rate limits or blocklisting | Sending to every user in one burst | One job per user, throttling, batch through the provider |
| 5 | Wrong posts in the email | `following_posts()` includes the user's own posts (outer join) | Dedicated query with inner join; unit tests |
| 6 | Slow query or job pile-up at scale | Per-user join on `followers` plus `post.timestamp` | Existing indexes; select only ids; cap posts per email |
| 7 | Migration fails on existing rows | New non-null boolean column on `user` | `server_default=sa.true()` |
| 8 | Notification noise in the UI | `launch_task` and `_set_task_progress` create Task rows and notifications | Enqueue directly; don't use `Task` |
| 9 | Unsubscribe token misuse | No login required, and a long-lived token | Separate JWT claim, POST to confirm, only changes the digest setting |
| 10 | Scheduler isn't deployed | No scheduler exists in the Procfile, Docker or supervisor setup | Document and add a cron entry; `--dry-run` for a smoke test |

Riskiest: #1. Duplicate or missed digests from cron retries or worker crashes reach users directly and can't be undone.
