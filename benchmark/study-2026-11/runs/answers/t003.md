**What happens today:** both delete endpoints (`DELETE /users/me` and `DELETE /users/{id}`) remove the user row for good. The admin endpoint also deletes the user's items explicitly (`backend/app/api/routes/users.py:225`), and the database model is set to delete items whenever their owner is deleted (`backend/app/models.py`).

## Assumptions
- A deleted user is marked with a `deleted_at` timestamp instead of being removed. They can't log in, their existing tokens stop working, they can't reset their password, and they don't appear in the user list by default.
- Their items stay exactly as they are and admins still see them in `GET /items`. The items' link to the owner stays valid because the user row still exists.
- After 30 days, restoring returns 410 (Gone). Nothing deletes old accounts automatically; that can be a separate job later.
- A deleted user's email stays taken, so signing up again with it gets the existing "already exists" error.
- Both self-delete and admin delete become soft deletes. No hard-delete endpoint is added.

## Plan
1. **Model and migration:** add `deleted_at: datetime | None` (indexed) to `User` and return it in `UserPublic`. Add a 30-day restore-window setting to `core/config.py`. Write a new Alembic migration modelled on `fe56fa70289e_add_created_at...`.
2. **`crud.py`:** add `soft_delete_user` and `restore_user`. `authenticate()` returns `None` for deleted users but still runs the dummy password hash, so response times don't reveal which accounts exist. `get_user_by_email` keeps returning deleted users so the email stays taken.
3. **`deps.py` `get_current_user`:** reject deleted users, so tokens already issued stop working straight away.
4. **`routes/users.py`:**
   - Both delete endpoints set `deleted_at` and drop the `delete(Item)` and `session.delete` calls.
   - New superuser endpoint `POST /users/{id}/restore`: 404 if the user isn't deleted, 410 if the 30 days have passed, otherwise it clears `deleted_at`.
   - `read_users` gets an `include_deleted=False` option, applied to both the list and the count.
   - `read_user_by_id` and `update_user` treat deleted users as not found, except that a superuser can view them.
5. **`routes/login.py`:** password recover/reset and the recovery-email preview treat deleted users as if they don't exist.
6. **Frontend:** regenerate the API client. Update the wording in `Admin/DeleteUser.tsx` and the delete-account dialog. Add a "show deleted" toggle, a "Deleted" badge and a Restore action in `columns.tsx` / `UserActionsMenu.tsx`.
7. **Tests:**
   - Backend `tests/api/routes/test_users.py` and `tests/crud/test_user.py`:
     - deleting keeps the items
     - a deleted user can't log in and their token is rejected
     - deleted users are hidden from the list
     - restore works inside the window and returns 410 after it
     - signing up with a deleted user's email is rejected
     - only superusers can restore
   - Playwright: an admin deletes a user, then restores them.

**How to check it:** run `scripts/test.sh`, run the migration up and back down on a dev database, then run the Playwright tests.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Deleted users keep access | Logins and tokens look users up in several places (`session.get` in `get_current_user`, `get_user_by_email` in login and reset); one missed check leaves a deleted user able to log in | Check `deleted_at` in `authenticate`, `get_current_user` and the reset flows; add a test for each path |
| 2 | Cascade still deletes items | `cascade_delete=True` and `ondelete="CASCADE"` are still on the model | Never call `session.delete(user)` in delete paths; add a test that items survive |
| 3 | Re-signup blocked | Email is unique and the deleted user's row still exists | Document it as intended; add a clear error message or free the email later |
| 4 | Deleted users still counted | The `read_users` total is a separate query | Apply the same filter to the count query |
| 5 | Leaking whether an account exists | Login and recover-password responses could differ for deleted accounts | Use the same responses and timing as for unknown users |
| 6 | Clock and timezone mistakes | `created_at` uses aware UTC; a naive `deleted_at` would break the comparison | Use `get_datetime_utc` and a timezone-aware column |
| 7 | Frontend out of sync with API | The client is generated from the API definition | Regenerate the client and run the Playwright tests in CI |
| 8 | Superuser deletes and restores themselves | The self-delete guard only covers delete | Keep the guard; restore needs a different active superuser |
| 9 | Data kept forever | There's no purge after 30 days | Decide on retention or GDPR purging before release |

Riskiest: #1. A deleted user who can still log in or use an old token is a security hole, not just a display bug.
