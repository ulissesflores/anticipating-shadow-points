I've written the plan to `claude-home/plans/deploy-new-versions-with-wondrous-peacock.md`. No project files were changed. The plan is a deploy script that runs migrations once, starts the new container next to the old one, and only switches traffic when the new one is healthy.

**Current state.** Production is deployed with `docker-compose -f docker-compose.prod.yml up -d --build`. That restarts `web` in place, so nginx returns 502 errors until it is back. Production also never runs `migrate` or `collectstatic`: `app/entrypoint.prod.sh` only waits for Postgres.

**Assumptions:**
- Everything runs on one Docker host with Compose v2, and images are built on that host. There's no registry or CI in the repo.
- Postgres stays in Compose and is never recreated during a deploy.
- Migrations follow an "expand then contract" rule from now on: add things first, remove them in a later release. This is needed because the old code briefly runs against the new schema.
- A short window where the old and new code both serve traffic is acceptable.

**Plan:**
1. **Version every image.** Tag the `web` image as `hello_django_web:${APP_TAG}`, using the git commit hash, so rolling back means pointing at the previous tag.
2. **Add a one-off `migrate` service.** It uses the same image, runs `migrate --noinput && collectstatic --noinput` and then exits. Migrations stay out of the web container's startup so two web containers can't run them at the same time.
3. **Add a `/healthz` endpoint** that checks the database connection, and a Docker healthcheck that calls it with Python's `urllib`, since the slim image has no curl.
4. **Shut gunicorn down gracefully.** Add `--graceful-timeout 25` and set `stop_grace_period: 30s`. The entrypoint already uses `exec`, so the stop signal reaches gunicorn.
5. **Change nginx.** Point it at Docker's DNS (`resolver 127.0.0.11`) and retry a failed request on the other container (`proxy_next_upstream error timeout http_502`). The script reloads nginx after each switch so it picks up the current containers.
6. **Write `scripts/deploy.sh`:**
   1. Build the image. The existing flake8 step acts as a gate.
   2. Run `migrate`; if it fails, stop the deploy while the old container keeps serving.
   3. Start a second `web` container next to the old one.
   4. Wait up to 60s for it to report healthy; if it doesn't, remove it and exit.
   5. Reload nginx, stop the old container (30s grace), reload nginx again.
   6. Record the deployed tag for rollback.
7. **Update the README** with the new deploy command, first-time setup, the migration rule and how to roll back. Optionally add a CI check (`makemigrations --check`) so model changes can't ship without a migration.

**Verification:**
- Run a loop of `curl` requests while deploying; there should be no 502 or 504 responses.
- Deploy a harmless migration and confirm it was applied once.
- Break the health endpoint on purpose: the deploy should stop and the old container should keep serving.
- Ship a migration that fails: the deploy should stop before switching traffic, with the site still up.
- Roll back to the previous tag and confirm the old version is served.

**Separate bug:** `settings.py:25` does `bool(os.environ.get("DEBUG", 0))`. The value arrives as the string `"0"`, and `bool("0")` is `True`, so production is currently running with DEBUG on. It should be fixed separately from this change.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Migration not backward-compatible | Old and new containers serve traffic against the new schema at the same time | Expand/contract rule; drop or rename columns a release later |
| 2 | Migration fails or locks a table | Single Postgres; a long `ALTER` blocks old-container requests | Migrate before the switch; abort on failure; set `lock_timeout` for big tables |
| 3 | nginx keeps routing to stale containers | nginx resolves `web` once at startup | `resolver 127.0.0.11`, reload after each switch, `proxy_next_upstream` |
| 4 | Health check passes but the app is broken | `/healthz` only checks the DB connection | Smoke-test `/` before stopping the old container |
| 5 | In-flight requests cut off | Uploads can be slow; default stop sends SIGKILL after 10s | `stop_grace_period: 30s` and gunicorn `--graceful-timeout` |
| 6 | Rollback after a migration | Code rolls back but the schema doesn't | Expand-only migrations make old code safe; document `migrate <app> <n>` |
| 7 | `collectstatic` changes files the old version serves | Static files share one volume and aren't content-hashed | Use `ManifestStaticFilesStorage` (hashed filenames) |
| 8 | Accidental `db` recreate or `flush` | `up` without `--no-deps`; the dev entrypoint runs `flush` | Script always passes `--no-deps web`; dev entrypoint stays out of prod |
| 9 | Not enough memory for two containers | Single host runs two web containers during the switch | Check host headroom; keep the overlap short |
| 10 | DEBUG on in production | `bool("0")` is `True` in `settings.py:25` | Fix the parsing in a separate change |

Riskiest: #1. A migration that isn't backward-compatible breaks the old container while it is still serving traffic, which turns a zero-downtime deploy into errors.
