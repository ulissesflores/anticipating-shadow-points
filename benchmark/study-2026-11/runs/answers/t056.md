I've written the plan to `claude-home/plans/add-soft-delete-for-quirky-iverson.md`; nothing else was changed. Right now both delete endpoints (`DELETE /users/{id}` and `DELETE /users/me`) remove the user row and their items for good, and there's nothing in place that runs scheduled jobs.

## Assumptions
- **New field:** a nullable `deleted_at` timestamp marks a deleted user. It is separate from `is_active`, which admins already switch on and off for other reasons.
- **Items:** they stay in the database and admins can still see them. The owner can't reach them because they can no longer log in.
- **After 30 days:** a restore attempt is refused (HTTP 410). There's no automatic permanent delete, because deleting the user row would also delete their items at the database level.
- **Email:** deleting a user frees their email for a new signup. If someone has taken it before the restore, the restore is refused (HTTP 409).
- **Database:** Postgres, which the email rule above relies on.

## Plan
1. **Model:** add `User.deleted_at` (indexed) to `app/models.py` and show it in `UserPublic`. Add a `USER_RESTORE_WINDOW_DAYS = 30` setting.
2. **Migration:** add the column, and replace the unique email index with one that only applies to users that aren't deleted. Rolling back fails if two rows share an email.
3. **`app/crud.py`:**
   - `get_user_by_email` skips deleted users by default. Login, signup, password recovery/reset and the email checks all go through it.
   - Add `soft_delete_user` and `restore_user`; restore checks the 30-day window and email conflicts.
4. **Auth:** `get_current_user` in `app/api/deps.py` rejects deleted users. Without this, tokens issued before the delete keep working for up to 8 days.
5. **`app/api/routes/users.py`:**
   - Both delete endpoints set `deleted_at` instead of deleting, and the line that deletes the items goes.
   - The user list hides deleted users and takes `?deleted=true` for admins; the count matches.
   - Get-by-id and update return 404 or refuse for deleted users.
   - New admin endpoint `POST /users/{id}/restore` returns 404 if the user isn't deleted, 410 after the window, and 409 on an email conflict.
6. **Items routes:** no change. Admins still see items whose owner is deleted.
7. **Frontend:**
   - `DeleteUser.tsx` still says items are "permanently deleted"; fix that.
   - Add a deleted-users filter, a Restore action and a days-left label to the admin screens.
   - Regenerate the API client.
8. **Tests:**
   - Deleting keeps the user row and their items.
   - Login, existing tokens and password reset fail for deleted users.
   - The default list hides them and the deleted filter shows them.
   - Restore works on day 29, fails with 410 on day 31 and fails with 409 on an email conflict.
   - Signing up again with the same email works.

**How to check it:** run pytest, run the migration up and back down on a copy of the database, then do a manual pass: delete a user, confirm their old token stops working and an admin still sees their items, restore them, and log in again.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Deleted user's existing token keeps working | Tokens last 8 days and `get_current_user` only checks `is_active` | Check `deleted_at` in `get_current_user`; add a test |
| 2 | A lookup misses the deleted filter | `get_user_by_email` and `session.get(User)` are called from many places (login, password reset, private route) | Filter by default in crud; test every auth path |
| 3 | Items get deleted anyway | Database cascade plus `cascade_delete=True`; any leftover `session.delete(user)` wipes them | Remove all hard deletes; test that items survive |
| 4 | Email index migration fails or blocks writes | Swaps the original unique `ix_user_email` | Run on a copy first; rollback guard for duplicate emails |
| 5 | Restore hits an email that's been reused | The email is freed on delete | Return 409 on restore; admin changes the email first |
| 6 | Admin user count is wrong | The count query in `read_users` is separate from the list query | Apply the same filter to both |
| 7 | Data kept past 30 days without a purge | No job runner exists; a purge would also delete items | Decide what retention means; build the purge later |
| 8 | Delete screen gives the wrong message | `DeleteUser.tsx` still says "permanently deleted" | Update the text and add the Restore UI |
| 9 | Off-by-one at the 30-day edge | Mixing timezone-aware and naive dates | Use UTC throughout; test days 29 and 31 |

Riskiest: #1 — a deleted user's existing login token keeps working for up to 8 days unless `get_current_user` checks `deleted_at`.
