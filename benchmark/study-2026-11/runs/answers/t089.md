# ASP plan: multi-author articles that stay backward-compatible (stopped after Phase 6)

I edited no project files; the plan is saved at `claude-home/plans/standard-allow-an-article-fizzy-thunder.md`. It went through one independent validator round, which came back REVISE with 8 issues. I applied all 8 fixes; the revised plan has not been re-validated.

**Research (Phase 1).** The repo is small, so I read the code directly instead of starting research agents:
- **Prior lessons:** there is no lessons store (no `CLAUDE.md`). The only lesson in the history is the 2021 `implicit_tags` migration, which dropped a table.
- **Web research:** I skipped it. The prior art is the public RealWorld API spec, which defines `article.author` as a single object.

## Assumptions (in place of questions)
1. **Primary author stays:** `authorId` remains the owner. Co-authors go in a new table and existing rows need no backfill.
2. **Response shape:** `author` is unchanged. Every article response gets a new field, `coAuthors: Profile[]`, which is `[]` when there are none.
3. **Who can do what:** the primary author sets co-authors through an optional `article.coAuthors: [usernames]` on POST/PUT. Co-authors can edit content. Only the primary author can delete the article or change the co-author list.
4. **URLs:** the slug format stays `slugify(title)-<primaryAuthorId>`.
5. **Filters:** `?author=` keeps its current meaning. A new `?contributor=` matches the primary author or a co-author. The feed is unchanged.

## Plan (D01–D07)
- **D01 Schema:** an explicit `ArticleCoAuthor(articleId, userId, position)` table with a composite primary key and cascade deletes. The migration is purely additive, and its SQL is checked against a whitelist so any unexpected statement fails.
- **D02 Shared include and mapper:** one shared `articleInclude` replaces the 7 duplicated include blocks in `article.service.ts`. Co-authors are mapped with the existing `profileMapper`.
- **D03 Favorite/unfavorite:** these two endpoints return the raw database row. The plan keeps their current shape, and deep snapshot tests check that it stays that way.
- **D04 Create/update:** everything runs in one interactive transaction. The slug bug is fixed, and P2002 errors (duplicate key) return 422.
- **D05 Visibility:** the filter moves up to the article level: `OR[author demo/self, coAuthor = viewer]`. The new `contributor` filter is added.
- **D06 Tests:** responses for comments, profiles, feed and list must be unchanged. `npx nx test` and `npx nx build` must pass.
- **D07 Security (separate commit):** narrow the `favoritedBy` select. This fixes a leak in today's code, not one this feature adds.

## What the validator caught
- **Password hashes and emails leak today.** `favoritedBy: true` loads full User rows, and favorite/unfavorite send them back in the response (`src/app/routes/article/article.service.ts`, favorite/unfavorite functions). This is independent of the co-author work and worth fixing regardless.
- **Visibility filter placement:** the co-author condition can't go inside the existing `author` filter, which is where I had originally put it.
- **Race conditions:** the transaction was too narrow, and the check-then-write on the slug can race.
- **Migration check:** my original grep would have missed some unexpected statements, so it became a whitelist.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Slug changes when a co-author edits | `updateArticle` builds the new slug from the editor's id | Build it from `article.authorId` and add a test |
| 2 | `author` contract broken | Every client reads `article.author` as one object | Keep `author`; add `coAuthors` |
| 3 | Credential leak in favorite responses | Raw row spread with full `favoritedBy` users | D07 narrow select plus a "no `password` at any depth" test |
| 4 | Favorite/unfavorite shape drifts | Shared include changes the raw nested rows | Deep snapshot tests |
| 5 | Co-author hidden from their own article | Visibility filter is demo-or-self on `author` only | Article-level OR with a co-author branch |
| 6 | Migration touches existing tables | Prisma history includes an implicit-relation drop | Explicit model; whitelisted SQL |
| 7 | Co-author takes over the article | Authz only checks `author.id` | Delete and co-author changes are primary-only |
| 8 | Concurrent PUTs return 500 or half-written data | Tag reset and update run outside a transaction | One transaction; P2002 → 422 |
| 9 | `articlesCount` changes for current clients | Widening `?author=` alters the counts | Keep `?author=`; add `?contributor=` |
| 10 | Co-author PUT wipes tags | An omitted `tagList` clears all tags | Accepted and documented; follow-up fix |

Riskiest: #1. A co-author retitling an article would silently move it to a slug containing their own id, breaking existing article URLs, which is exactly what this change has to preserve.
