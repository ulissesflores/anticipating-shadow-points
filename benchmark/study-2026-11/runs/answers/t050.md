I've written and checked the plan for multi-author articles and stopped there, as asked. No project files were changed; the plan is in `claude-home/plans/standard-allow-an-article-eventual-popcorn.md`. One reviewer pass asked for revisions, and I applied all 7. I did not run a second review.

**What the codebase showed:**
- **Single author:** each article has exactly one author (`authorId` in `src/prisma/schema.prisma`).
- **Slugs:** a slug is the title plus the author's user id (`article.service.ts:178` and `:317`).
- **Duplicated queries:** the same database query setup is copied 7 times in `article.service.ts`.
- **Existing password leak:** `favoriteArticle` and `unfavoriteArticle` return the raw database row, including the full records of users who favorited the article. That means password hashes and emails are already exposed today (`:588-598`, `:634-644`).
- **List visibility:** article lists only show articles by demo users or by the logged-in user (`buildFindAllQuery`).

**Assumptions (no one to ask in this run):**
- The current `author` stays as the primary author and owner.
- Responses only gain a new field, `coAuthors` (a list of profiles, empty by default). `author` keeps its exact shape.
- Co-authors can edit an article. Only the primary author can delete it or add and remove co-authors; a co-author can remove themselves.
- `?author=` and the feed keep their current meaning. A new `?coAuthor=` filter covers co-authored articles.
- An article can have at most 10 co-authors, with no duplicates.

**Plan (D01–D08):**
- **D01 – database:** a new `ArticleCoAuthor` table, keyed on article and user, with an index on user and cascading deletes. The migration only adds things.
- **D02 – shared query and output:** replace the 7 copies with one shared query setup that also loads co-authors. The response mapper adds `coAuthors`, treating a missing value as an empty list.
- **D03 – favorite/unfavorite:** keep their current response shape and add `coAuthors` as clean profiles, not raw rows.
- **D04 – editing:** allow co-authors to edit, and always build the slug from the primary author's id, so an edit by a co-author never changes the URL.
- **D05 – co-author management:** add `POST /articles/:slug/co-authors` and `DELETE /articles/:slug/co-authors/:username`, plus optional `coAuthors` when creating an article. Restructure the list filter so `?author=` stays outside the visibility rule.
- **D06 – tests:** add unit tests for all of the above. Existing tests must pass without changes.
- **D07 – README:** document the new field, endpoints and deploy order.
- **D08 – password leak (separate commit, needs your OK):** have favorite/unfavorite return only the ids of users who favorited. This changes what those two endpoints return.

Every deliverable has its own test or command that proves it is done.

**Main risks**

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Slug changes when a co-author edits the title | Slug is the title plus the *editor's* id (`:317`) | Build it from the primary author's id; test it |
| 2 | New field leaks raw rows or password hashes | favorite/unfavorite return the raw row, and full user records already leak today | Map `coAuthors` explicitly; D08 trims user data to ids |
| 3 | Breaking the single-`author` contract | The public RealWorld spec defines `author` as one object | Leave `author` as is; only add `coAuthors` |
| 4 | One of the 7 copied queries misses co-authors and crashes | The same query setup is copy-pasted 7 times | One shared query; default to an empty list |
| 5 | `?author=` starts returning co-authored articles | The visibility rule is nested inside the author filter | Keep `?author=` outside it; add a test |
| 6 | Code ships before the database change and every article read fails | The new query reads a table that doesn't exist yet | Deploy runs `prisma migrate deploy` before starting the server (`README.md:73`); the migration only adds things |
| 7 | Permissions widened too far | Today only the author can edit or delete | Clear rules for who can do what; tests for refused (403) requests |
| 8 | Old clients sending an edit wipe the co-author list | An update request has no `coAuthors` field | Manage co-authors through their own endpoints only |
| 9 | Duplicates or more than 10 co-authors under concurrent requests | Count check and insert are separate steps | Database key blocks duplicates (returned as 422); check the cap in a transaction |
| 10 | Strict-schema clients reject the unknown `coAuthors` field | Some clients fail on fields they don't expect | Document it in the README; a version flag is possible if needed |

Riskiest: #2. The password-hash leak through favorite/unfavorite already exists, and loading co-authors through the same raw responses could expose more user records.
