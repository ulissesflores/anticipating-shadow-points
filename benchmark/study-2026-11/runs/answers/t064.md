The plan is ready, and I stopped after Phase 6 as you asked. I didn't change any project files; the only file I wrote is the plan itself, at `claude-home/plans/standard-deploy-new-versions-glimmering-lightning.md`.

**What I assumed (no one to ask):** one Docker host running Compose v2, with Postgres in the same Compose project. Deploys run from a git checkout on that host. For up to about 60 seconds the old and new app versions will both be running against the new database schema. "Zero downtime" means no failed page loads (GETs). An upload that's still in progress after a 30-second wait may be cut.

## What the repo does today
- **Deploys cause an outage.** `docker-compose up -d --build` stops the old `web` container before the new one is ready. On top of that, nginx looks up `web:8000` only once, when it starts, so it keeps sending traffic to the old container's address and returns 502 errors.
- **Production never migrates.** Neither migrations nor `collectstatic` run in prod (`app/entrypoint.prod.sh` only waits for Postgres).
- **The dev entrypoint wipes the database.** `app/entrypoint.sh` runs `flush --no-input`. Copying it into prod would delete all data.
- **Problems that exist already:**
  - The prod image is based on Debian buster, which is end-of-life, so the build may already fail.
  - In `settings.py`, `DEBUG=0` actually turns debug **on**, because `bool("0")` is `True`.
- **No rollback target.** Images aren't tagged, and there are no health checks.

## The plan, after one independent review round
1. **Pre-check:** confirm the prod image still builds. If not, move it to bookworm in a separate commit first.
2. **Health check:** add a `/healthz` page that also checks the database connection. It sits ahead of the allowed-hosts check so that check can't break it. Compose health checks poll it every 5 seconds, and the database gets a `pg_isready` check.
3. **Graceful shutdown:** gunicorn gets 30 seconds to finish open requests, and Compose waits 40 seconds before killing the container.
4. **nginx:**
   - Fail fast on connections (2-second connect timeout).
   - Retry the other container on 502/503.
   - Reload nginx after every container change so it sees the current addresses.
5. **A separate `migrate` step:**
   - It runs once per deploy, using the new image, before the new web container starts.
   - It never runs inside the web container's startup, so two containers can't race.
   - A 5-second lock timeout means a migration that needs a busy table fails instead of freezing the site.
6. **Image tags:** each image is tagged with the git commit, and the last good tag is saved for rollback.
7. **`deploy.sh`** takes a lock so two deploys can't overlap, then:
   1. Builds the image, or skips the build when rolling back to an existing tag.
   2. Aborts if a migration file is missing.
   3. Backs up the database.
   4. Runs the migrations (if this fails, the old version keeps serving).
   5. Starts a second web container.
   6. Waits up to 90 seconds for it to report healthy.
   7. Takes the old container out of nginx, reloads nginx, then stops and removes the old container.
   8. Checks through nginx that the new version is the one serving.
8. **`docs/DEPLOY.md` rule for migrations:** add new columns first and remove old ones in a later release. Never drop or rename something the previous release still reads.
9. **Test script:** `scripts/zd_check.sh` puts load on the site during three deploys in a row, plus one deliberately failing migration. It requires 0 failed GETs and reports any cut uploads.

The reviewer returned REVISE with 10 issues, and I applied all of them. The most serious:
- The health-check command was missing an `import`, so every deploy would have timed out.
- The rollback path rebuilt the image instead of reusing the old one.
- `TAG` wasn't exported, so every image would have been tagged `latest`.
- The missing-migration check ran after the migrations were already applied.
- The database backup command would have connected as the wrong user and failed.

There was no lessons file in the repo to check.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | A migration breaks the old version during the overlap | Old and new containers share one database for up to about 60 s | Add-then-remove rule in DEPLOY.md; review the migration plan before applying |
| 2 | A migration waits on a table lock and freezes the site | Every request queues behind the waiting `ALTER TABLE` | 5 s lock timeout; deploy fails fast and the old version keeps serving |
| 3 | nginx keeps sending traffic to the old container's address | `upstream web:8000` is looked up only when nginx starts | Reload nginx after each change; take the old container out first; 2 s connect timeout |
| 4 | The dev `flush` gets copied into prod | `entrypoint.sh` already does `flush --no-input` | Migrations live in their own step; test fails if `flush` appears in prod scripts |
| 5 | Migrations race each other | Running migrate on container startup with 2 containers | One-shot `migrate` step, never at startup |
| 6 | The new container never becomes healthy | Bad env file, DB unreachable, or a broken health check | 90 s timeout; remove the new container; exit with an error |
| 7 | Rollback has no image to go back to | Images are untagged, and `--build` overwrites `latest` | Tag by git commit; save the last tag; rollback skips the build |
| 8 | The first deploy fails at build time | Buster is end-of-life and its package mirrors are archived | Pre-check the build; move to bookworm if needed |
| 9 | Error pages leak details during a failed rollout | `bool("0")` means debug is on in prod | Fix the DEBUG parsing first (separate change) |
| 10 | Uploads in progress get cut | The app's main action is a POST to `/` | 40 s graceful shutdown; test reports any cuts |

Riskiest: #1. A migration that removes or renames something the still-running old version uses will cause 500 errors during the overlap. Scripting can't prevent it; only the add-then-remove rule for migrations does.
