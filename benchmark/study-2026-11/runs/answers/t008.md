I've planned the change but not built it. An independent reviewer read the first plan, asked for revisions, and I folded all of them in. No project file was changed; the only file written is the plan itself: `<config>/plans/standard-allow-an-article-iterative-stream.md`.

**Research shortcuts.**

- I skipped web research.
- There is no lessons file or `CLAUDE.md` to consult, so the "consulted lessons" step was empty.

## What the code does today that matters
- **Article URLs embed the author's user id.** The URL slug is `slugify(title)-<id>` (`src/app/routes/article/article.service.ts:166`). But when an article is edited, `updateArticle` uses the id of whoever is editing (`:312`). If a co-author changed the title, the URL would end in their id instead, breaking the URL pattern.
- **Edit and delete are owner-only.** Both check that the caller is the article's author (`:298`, `:426`).
- **Article lists are already filtered.** The `?author=` filter and a visibility rule ("demo users, or the caller") sit in the same query object (`:8-42`). A careless change here would alter what `?author=` returns.
- **Favorite and unfavorite return the raw database row** (`:597`) instead of going through the shared response mapper. Because of that, they already leak the email and password hash of every user who favorited the article.
- **Existing tests can't catch query mistakes.** They run against a mocked database, so they only check how results are shaped, not which rows are fetched.

## Assumptions (I couldn't ask)
- **A1:** `author` stays the current owner. Responses only gain a new `coAuthors: Profile[]` field.
- **A2:** Existing slugs are never rewritten. When a title changes, the new slug always uses the owner's id.
- **A3:** Co-authors can edit an article. Only the owner can delete it or change the co-author list.
- **A4:** Co-authors are set with an optional `article.coAuthors: string[]` (usernames) on create and edit, capped at 10. An unknown username returns 422.
- **A5:** `?author=` keeps its current meaning. A new `?coAuthor=` filter is added, and the personal feed is unchanged.
- **A6:** Deleting a co-author's account removes only their link to the article, not the article.

## The plan, in order
1. **Response snapshots first (D05a).** Record the exact current responses, with fixed dates, before touching anything.
2. **Database (D01).** Add-only migration creating an `ArticleCoAuthor` table (`articleId`, `userId`, `position`). Each article/user pair is unique, and the links are deleted if either side is deleted. A checksum over article id, slug and owner proves no existing row changed.
3. **Refactor (D02).** Replace the six copies of the same query block with one shared helper, with no change in behaviour.
4. **Reading (D03).** Return `coAuthors` everywhere, including favorite/unfavorite, through the existing profile mapper. For anonymous callers, don't load co-authors' follower lists.
5. **Writing and permissions (D04).**
   - Add "is owner" and "is owner or co-author" checks; the new slug always uses the owner's id.
   - The co-author list is replaced inside the same database update as the article, duplicates are skipped, and a conflict returns 409.
   - Usernames are validated before the article is created.
   - Add `?coAuthor=` without changing how `?author=` combines with the visibility rule.
   - Add an endpoint so a co-author can remove themselves: `DELETE /articles/:slug/co-authors/me`.
   - Only wipe an article's tags when the edit actually sends a tag list.
6. **Tests (D05b).** Co-author tests that also check the exact database queries the code makes.
7. **Real-database check (D06).**
   - Run the server against a throwaway Postgres; old slug URLs must return the same body plus `coAuthors: []`.
   - Test visibility, filters and two simultaneous edits there.
   - Update the README.

To deploy: run the migration first (the old code ignores the new table), then ship the code. Rolling back means reverting the code.

**Out of scope:** including co-authored articles in the feed, changing `?author=`, and an invite/consent flow. The password-hash leak in favorite/unfavorite is logged as a separate high-priority security follow-up.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | A co-author's title edit changes the slug's id suffix | Slug uses the editor's id (`:312`) | Always use the owner's id; unit test |
| 2 | `author` field changes shape | Every RealWorld frontend reads `article.author` | Keep `author` = owner; add `coAuthors` only; exact-key snapshots |
| 3 | `?author=` starts returning co-authored articles | Filter and visibility rule share one object | Separate `AND` term; test that it returns 0 |
| 4 | Favorite responses leak more data | They return the raw row, already exposing password hashes | Overwrite with mapped profiles; exact-key test; security follow-up |
| 5 | Authorization only half updated | Owner checks are copied in edit and delete | One shared helper; tests that delete and co-author changes return 403 for co-authors |
| 6 | Two simultaneous edits make one fail with a 500 | Delete-then-insert of the co-author list clashes on the unique pair | Do it inside the same update, skip duplicates, return 409; test on a real DB |
| 7 | Migration damages existing rows | Production data, no slug backfill allowed | Add-only table; checksum before and after |
| 8 | List pages get slow and heavy | Every follower is loaded for each co-author | Load only the caller's follow status; skip for anonymous callers; cap of 10 |
| 9 | Co-author edits wipe tags | Tags are reset on every edit (`:343`) | Reset only when a tag list is sent |
| 10 | Tests pass but production breaks | Mocked database ignores query shape | Check the exact queries; smoke test on a real database |

Riskiest: #1. A co-author editing the title would silently produce a slug ending in the wrong user id, which breaks the "URLs keep working" requirement in exactly the new flow this change adds.
