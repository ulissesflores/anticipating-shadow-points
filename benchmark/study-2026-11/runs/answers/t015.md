I haven't edited any files. Here is the plan, based on reading `source/utils/normalize.ts`, `source/core/Ky.ts` (`#calculateRetryDelay`, around lines 688–762) and `source/utils/is-network-error.ts`.

## How retries work today
- `retry.methods` defaults to `get put head delete options trace query` (`normalize.ts:17`). It controls every retry except forced ones (`ky.retry()`). That includes status-code retries (408/413/429/500/502/503/504), timeouts, and network errors (`Ky.ts:703`).
- A network error is a `NetworkError` that wraps a raw `TypeError`, recognised by its message (`is-network-error.ts`). Messages like `Failed to fetch`, `Load failed`, `terminated` and `Network connection lost` don't say whether the server already got and handled the request.
- The request is already cloned for retries whenever `retry.limit > 0`, whatever the method (`Ky.ts:1225`). So POST and PATCH bodies, including streams, can already be replayed. Nothing new is needed there.

## Ways this could go wrong
1. **Duplicate side effects.** A connection can drop after the server has committed a POST (for example `terminated` mid-response, or a mobile handoff before the response arrives). Retrying then creates a second order or payment. HTTP leaves POST and PATCH out of default retries for exactly this reason.
2. **Simply adding `post`/`patch` to `retry.methods` does far more than asked.** That list also controls status-code retries, so POST would start retrying on 500/502/503/504/429/408 too. A 500 or 504 often means the work was done or partly done.
3. **The error can't tell "never sent" from "sent but the reply was lost".** The message-based detection gives no signal either way, so we can't safely retry only the "never sent" case.
4. **It's a breaking change.** The repo is at 2.2.0. Users who rely on POST never repeating would get duplicates silently, so this needs a major version.
5. **It may not fix the actual complaint.** On mobile, flaky connections often end in a `TimeoutError`, not a `NetworkError`, and `retryOnTimeout` defaults to `false`.
6. **Side effects of the extra attempts.** `onUploadProgress` starts again from 0, large uploads are sent twice, and requests take longer up to `totalTimeout`.
7. **Setting conflicts.** If a user sets `methods: ['get']` explicitly, it's unclear whether the new POST/PATCH network retries still apply. `shouldRetry` docs say it runs "after method checks pass", and that becomes ambiguous.
8. **AGENTS.md rule.** Any new option must reject `null` with an error that names the option, not treat it as absent.
9. **Existing tests and docs assume POST is never retried.** `test/retry.ts`, `test/retry-decisions.ts`, `readme.md:265,281` and the JSDoc in `source/types/retry.ts` would all go stale.

## Recommended approach (assumptions stated, not asked)
- **Assumption:** "network fails" means only `NetworkError`. Timeouts and HTTP status codes keep today's behaviour for POST and PATCH.
- **Assumption:** you accept this as a breaking default and want it released as a major version.
- **New option:** `retry.networkErrorMethods` in `source/types/retry.ts`, defaulting to the current `methods` plus `post` and `patch`. Validate and normalise it with the same loops `normalize.ts` already uses for `methods` (lines 55–70, 95). `Array.isArray(null)` fails, so `null` already gets an error that names the option, as AGENTS.md requires.
- **`#calculateRetryDelay` (`Ky.ts:703`):**
  - If the method is in `methods`, keep the current path.
  - Otherwise, if the error is a network error and the method is in `networkErrorMethods`, use `#calculateDelay`.
  - Otherwise, don't retry.
  - Call `shouldRetry` on this new path too, so users can veto it.
- **Duplicates:** don't add an `Idempotency-Key` header automatically, because a custom header triggers a CORS preflight. Instead, document it as the way to make these retries safe, with a `beforeRequest` example.
- **Tests:**
  - POST and PATCH are retried on a network error.
  - They are *not* retried on 500 or 503, or on timeout.
  - `networkErrorMethods: []` turns the new behaviour off.
  - `null` throws.
  - `shouldRetry: () => false` blocks the retry.
  - Update the existing tests that assert POST is never retried.
- **Docs:** update the readme retry section and the JSDoc, with a clear warning about duplicate side effects.
- **Check:** `npm test` (ava plus the type tests in `test-d`), plus a manual run with a test server that drops the socket before and after it handles a POST.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate POST/PATCH side effects | The server may have committed before the socket dropped | Document `Idempotency-Key`; allow opt-out with `networkErrorMethods: []` |
| 2 | Retries spread to 5xx/429 | `retry.methods` controls status-code retries too | Use a separate `networkErrorMethods` that only applies to `NetworkError` |
| 3 | Can't tell "not sent" from "reply lost" | `isRawNetworkError` only matches messages | Accept and document it; don't promise exactly-once |
| 4 | Silent change for existing users | Default changes in a 2.x release | Release as a major version with a changelog warning |
| 5 | Flaky mobile still fails | Failures often show up as `TimeoutError`, and `retryOnTimeout` is false | Say so in the docs; leave timeouts alone for POST |
| 6 | Confusing interaction with `methods` / `shouldRetry` | Docs say `shouldRetry` runs after method checks | Define precedence clearly; run `shouldRetry` on the new path |
| 7 | `null` accepted silently | AGENTS.md forbids treating `null` as absent | Reuse the array validation; add a test that `null` throws |
| 8 | Uploads sent twice, progress resets | Every retry sends the whole body again | Document it; `beforeRetry` can drop `onUploadProgress` |
| 9 | Stale tests and docs | Tests and readme say POST is never retried | Update `test/retry*.ts`, the readme and the JSDoc together |

Riskiest: #1. A network error after the server has committed the request makes ky repeat it (a duplicate order or payment), and the client can't detect that.
