## What could go wrong
1. **URLs change after an edit.** A slug is `slugify(title)-<userId>`. `updateArticle` rebuilds it from the *caller's* id (`article.service.ts`, the `newSlug = ...-${id}` line). If a co-author renames an article, its URL would end in their id instead and old links would break.
2. **The response shape breaks.** Clients expect `article.author` to be a single profile object. Turning it into an array would break every current client.
3. **Raw database data leaks.** `favoriteArticle` and `unfavoriteArticle` copy the raw database row straight into the response. A new `coAuthors` relation would show up raw, and if it loaded full user records that would include password hashes. This already happens today with `favoritedBy: true`.
4. **Permissions get looser or tighter than intended.** Edit and delete both check `author.id !== id` only. Changing that without care either locks co-authors out or lets them delete the article.
5. **Listings and the feed behave unexpectedly.** `?author=X`, the feed and the visibility rule (demo user or yourself) all filter on the single author. They need extending, and `count` and `findMany` must use the same filter or the article count won't match the list.
6. **The migration hits old data.** Changing or removing `authorId` would mean backfilling data and could lose rows. A purely additive table avoids that.
7. **Deletes go wrong.** Deleting a user already deletes their articles, and that must stay true for the primary author. If a co-author account is deleted, only their co-author link should go, not the article.
8. **Some code paths get missed.** The same "include" block is copied 7 times in the service, so one could easily be left without co-authors.
9. **Tests give false confidence.** The unit tests mock the database layer, so they won't catch query mistakes.

## Assumptions (no clarification was possible)
- `authorId` stays as the primary author/owner, and co-authors are kept in a new join table.
- The response keeps `author` exactly as it is and gains a new `coAuthors: Profile[]` field, which is `[]` by default.
- POST and PUT accept an optional `coAuthors: [usernames]`. Only the primary author can change that list.
- Co-authors can edit an article. Only the primary author can delete it.
- `?author=` and the feed also match co-authored articles.
- Existing articles start with no co-authors, so no backfill is needed.

## Plan
1. **Database:** add an `ArticleCoAuthor(articleId, userId)` table with cascading deletes on both sides. This is an additive migration and leaves the `Article` columns unchanged.
2. **Shared include:** replace the 7 copies with one `articleInclude` constant. It loads co-authors with only `username`, `bio`, `image` and the ids of their followers.
3. **Mapper:** `article.mapper.ts` adds `coAuthors`, reusing the existing `authorMapper`.
4. **Create and update:** check the usernames exist, remove duplicates and the primary author, cap the list, and return 422 for bad input. Write the co-author list in the same transaction as the article.
5. **Permissions:** co-authors can edit; only the primary author can delete or change the co-author list.
6. **Slugs:** build them from the existing `authorId`, not from whoever is editing.
7. **Listings:** extend `buildFindAllQuery` and `getFeed` to match co-authors, using the same filter for the count and the list.
8. **Favorite/unfavorite:** map co-authors explicitly so raw rows aren't leaked. The existing password-hash leak through `favoritedBy` should be fixed separately.
9. **Checks:** run the migration on a copy of production-like data and confirm no slugs change. Add tests for co-author permissions and slug stability. Compare `GET /articles/:slug` before and after: the only difference should be the new `coAuthors` field.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | URL changes when a co-author edits the title | `updateArticle` builds the slug from the caller's id | Build it from `existingArticle.authorId`; add a test |
| 2 | Clients break on the response shape | `author` is a single object in the API spec | Leave `author` as is; only add `coAuthors` |
| 3 | User data / password hashes leaked | favorite/unfavorite copy raw rows into the response | Return only selected fields and map them explicitly |
| 4 | Co-author can delete or take over an article | Checks only look at `author.id` | Edit for co-authors; delete and co-author changes for the primary author only |
| 5 | Article count doesn't match the list | `count` and `findMany` build their filters separately | Use one shared filter for both |
| 6 | Co-authored articles hidden or wrongly shown | Visibility rule (demo or yourself) only checks the primary author | Also allow the viewer as a co-author; test as a demo and a non-demo user |
| 7 | Migration loses or corrupts data | Changing `authorId` would need a backfill | Additive join table only; `authorId` unchanged |
| 8 | One code path misses co-authors | The include block is copied 7 times | Extract one `articleInclude` constant |
| 9 | Bad co-author input | Unknown, duplicate or self usernames | Validate, remove duplicates, cap, return 422 |
| 10 | Tests pass but queries are wrong | Database layer is mocked in unit tests | Add e2e tests against a real Postgres |

Riskiest: #1, a co-author's title edit silently changes the slug's id suffix and breaks existing article URLs.
