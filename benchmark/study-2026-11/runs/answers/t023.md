The plan does **not** do exactly what you asked. As written, the change would let a failed POST or PATCH be sent twice, so the plan only retries them when the request carries an `Idempotency-Key` header. You need to decide whether that narrowing is acceptable before Phase 7.

## Why the literal request is risky
- **A network error doesn't prove the server never got the request.** A dropped connection, `fetch failed`, `terminated` or Safari's `Load failed` can happen after the server has already saved the write. Replaying the POST then creates a second order or a second charge. This is why HTTP (RFC 9110 §9.2.2) only allows automatic retries for idempotent methods, and why ky's default list leaves out POST and PATCH (`source/utils/normalize.ts:17`).
- **Adding them to `retry.methods` does more than you asked.** A single method check (`source/core/Ky.ts:703`) covers every retry reason, so POST would also start retrying on 408, 429 and 5xx responses. The existing "not on POST" test (`test/retry.ts:322`) would also fail.

## Recommended design
- **New option:** `retry.networkErrorMethods`, default `['post','patch']`. It is checked only when the method isn't already in `retry.methods`.
- **When it retries:** only on a connection error before any response arrives, and only if the request sent has an `Idempotency-Key` header. Timeouts, HTTP status codes and errors while reading the response body are excluded.
- **What still stops it:** `retry: 0`, `limit`, `totalTimeout`, and `shouldRetry` returning `false`. `ky.retry()` is unchanged.
- **`null` handling:** passing `null` for the new option fails with a clear error naming it, as AGENTS.md requires.
- **Memory:** no change. ky already copies the request body for retries whenever retries are on, whatever the method.

## Validator round (independent subagent): REVISE, all items folded into Revision 1
- The `null` case throws a plain `Error`, not a `TypeError`, to match `test/normalize.ts`.
- Method names in the new option need lowercasing, and the error message for a bad entry needs fixing.
- An empty list (`[]`) gets merged away by `extend`; opting out needs `replaceOption([])`.
- The header is read from the request after `beforeRequest`. A key added in `beforeRetry` is seen too late to unlock the first retry.
- More type files need updating: `MutableRetryOptions` and the `test-d` files.
- `Idempotency-Key` triggers a CORS preflight in browsers, so servers must allow the header.
- The repo has no changelog file, so the release note goes in the GitHub release text.
- Extra tests: PATCH without a key, `totalTimeout` running out, and a key added only in `beforeRetry`.

## Assumptions
- The goal is fewer visible failures without duplicate writes.
- "Network fails" means only a connection error before any response arrives.
- Explicit user configuration always wins over the new default.
- It ships as a minor version, because nothing changes for requests that don't send the header.

**Decision for you at Phase 7:**
- **Header-gated default (recommended):** mobile apps that don't send `Idempotency-Key` see no change.
- **Literal default without the gate:** retries every POST/PATCH on network failure, with the duplicate-write risk documented.
