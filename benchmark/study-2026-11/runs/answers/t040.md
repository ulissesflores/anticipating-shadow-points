I've written the plan to `claude-home/plans/make-ky-retry-post-rosy-moth.md` and changed nothing in the repo. One caution first: a network failure doesn't tell you whether the server already received the request. Retrying POST/PATCH by default will sometimes send a write twice, unless the server deduplicates (for example with an `Idempotency-Key` header). The plan narrows the change as far as it can to limit that.

**Assumptions:**
- "Network fails" means only what `isNetworkError` recognises. Timeouts and HTTP error statuses (5xx/429/408) are excluded, because on those the server has probably received the request.
- The existing `retry.methods` option keeps its current meaning. Adding `post`/`patch` to it directly would also retry them on 500/503/429.
- This changes the default behaviour of writes, so it ships as a major version (3.0.0).

**Approach:**
1. **New option** `retry.networkErrorMethods`, default `['post', 'patch']`. Methods in this list are retried only when the failure is a network error.
   - Add it to the types in `source/types/retry.ts` and `options.ts`.
   - Add the default in `source/utils/normalize.ts:17-35`. Reuse the existing array and string-entry checks and `normalizeRetryMethod`.
   - `null` stays an error that names the option, per AGENTS.md; no fallback is added.
2. **Retry decision** in `#calculateRetryDelay` (`source/core/Ky.ts:703`): a method passes if it is in `methods`, or if it is in `networkErrorMethods` and the error is a network error. `shouldRetry` can still veto with `false`, but returning `true` must not make a POST that got a 500 retry.
3. **Request body:** no change needed. Ky already copies the body for replay whenever retries are on, whatever the method (`Ky.ts:1225`). Tests should confirm that JSON, FormData and stream bodies replay identically.
4. **Docs:** update the `retry` section of `readme.md` with the new default, a duplicate-write warning, the opt-out (`networkErrorMethods: []`) and advice to send an `Idempotency-Key`. Add a release note.
5. **Tests:**
   - POST and PATCH retry on a mocked `TypeError('fetch failed')` up to the limit.
   - The existing `not on POST` test (500) keeps passing, and timeouts still don't retry.
   - Opt-out, the `shouldRetry` veto, and `null` being rejected.
   - `extend`/`replaceOption` merging, and changes made by a `beforeRetry` hook.
   - Update the defaults snapshot at `test/retry.ts:223` and add type tests.

**Verification:** run `npm test` plus the CI browser tests, and check that user aborts in Chromium (which also show up as "Failed to fetch") are still not retried.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate writes (double order or charge) | A connection reset after the server has processed the request looks the same as one that never arrived | Major version, readme warning, recommend `Idempotency-Key`, opt-out `[]` |
| 2 | Silent behaviour change for existing users | Code relying on POST never retrying gets retries after upgrading | 3.0.0 release, migration note |
| 3 | Mid-response drops counted as network errors | Node's `'terminated'` and `'Network connection lost'` can happen after the server finished | Exclude errors raised while reading the body; add a test |
| 4 | User abort retried as a network error | Chromium reports aborts as "Failed to fetch" | Keep the abort check at `Ky.ts:1276` first; run browser tests |
| 5 | `shouldRetry: true` widens retries | The override path could retry a POST on 500 | Network-error-only path ignores a `true` override; add a test |
| 6 | Mismatch with `methods` | A user with `methods: ['get']` still gets POST retries on network errors | Document clearly; opting out needs `networkErrorMethods: []` |
| 7 | Stream body replay | One-shot streams must be copied and buffered in memory to replay | Already done when `limit > 0`; test stream POST retries |
| 8 | Merge/extend regressions | The new key has to behave like `methods` under `extend` and `replaceOption` | Mirror the existing merge tests |
| 9 | Accepting `null` | Adding a lenient branch would break the project's conventions | Reuse the array check; test the error message |

Riskiest: #1, duplicate non-idempotent writes after an ambiguous network failure.
