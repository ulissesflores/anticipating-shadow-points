# Plan: soft delete for users with a 30-day admin restore

Right now both `DELETE /users/{id}` and `DELETE /users/me` permanently delete the user and their items (`backend/app/api/routes/users.py`). This plan turns both into soft deletes and adds a restore endpoint for admins. I didn't edit any project files; the plan is saved at `claude-home/plans/add-soft-delete-for-reactive-wreath.md`.

## Assumptions
- **New field, not `is_active`:** add a `deleted_at` timestamp instead of reusing `is_active`, because admins already use `is_active` for deactivating accounts.
- **Email stays taken:** while an account is soft-deleted, its email can't be used for a new signup or an email change. This keeps restore conflict-free.
- **Items are kept:** they stay in the database unchanged. Admins still see them in `/items`; the owner can't log in, so they can't.
- **After 30 days:** restore is refused. There's no permanent-purge job, because the project has no scheduler. Whether to purge later is a separate decision.
- **Both delete paths change:** admin delete and self-delete both become soft deletes.

## Backend
1. **`models.py`:**
   - Add `User.deleted_at: datetime | None` with an index, and include `deleted_at` in `UserPublic`.
   - Keep the existing cascade-delete settings; they only matter for a future purge.
2. **Alembic migration:** builds on `fe56fa70289e`. It adds the nullable, timezone-aware column and the index.
3. **`config.py`:** add `USER_RESTORE_WINDOW_DAYS = 30`.
4. **`crud.py`:**
   - Add `soft_delete_user` and `restore_user`.
   - `authenticate` returns None for a deleted user, but still runs the password check so response timing doesn't reveal anything.
5. **`deps.get_current_user`:** reject deleted users. Without this, existing login tokens (valid for 8 days) would keep working.
6. **`routes/users.py`:**
   - Both delete endpoints only set `deleted_at`. The `delete(Item)` call is removed.
   - `read_users` hides deleted users from both the count and the list by default. A new `include_deleted` parameter shows them.
   - `read_user_by_id` returns 404 for a deleted user unless the caller is an admin. `update_user` also refuses deleted users.
   - New `POST /users/{id}/restore` (admin only): 404 if the user doesn't exist or isn't deleted, 410 if the 30 days have passed, otherwise it clears `deleted_at`.
7. **`routes/login.py`:** password recovery and password reset treat a deleted user like an unknown user, so no email is sent.

## Frontend
- Regenerate the API client with `scripts/generate-client.sh`.
- Update the `DeleteUser.tsx` dialog text. It currently says items are "permanently deleted"; it should say items are kept and the account can be restored for 30 days.
- Add `RestoreUser.tsx` to `UserActionsMenu`, shown only for deleted users.
- Add a "Deleted" badge in `columns.tsx` and a "show deleted" toggle on the admin page.

## Tests
Add to `backend/tests/api/routes/test_users.py`, `test_login.py` and `backend/tests/crud/test_user.py`:
- After a delete, the items still exist, login fails, and an existing token is rejected.
- The deleted user is hidden from the user list by default and shown with `include_deleted`.
- Restore works at day 29 and returns 410 at day 31.
- Signup with the deleted user's email fails.
- Password recovery for a deleted user sends no email.
- A non-admin gets 403 on restore.

Also add a delete-then-restore test to `frontend/tests/admin.spec.ts`, then run `bash scripts/test.sh`.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Deleted user keeps access | Logins use stateless tokens that stay valid for 8 days | Check `deleted_at` in `get_current_user` |
| 2 | Missed filter on some query | Every query uses `session.get`/`select(User)` directly; there's no shared filter | Make one helper and grep every `User` lookup |
| 3 | Email still taken | Email must be unique, and the row stays in the table | Keep the email reserved on purpose and give a clear error |
| 4 | Accidental permanent delete | `cascade_delete=True` and the CASCADE foreign key are still there | Test that items survive both delete paths |
| 5 | Password reset reactivates the account | `recover-password` and `reset-password` look users up by email only | Treat deleted users as unknown in `login.py` |
| 6 | Restore clashes with `is_active` | Admins already use `is_active` for a different purpose | Keep the two fields separate; restore only touches `deleted_at` |
| 7 | Wrong 30-day calculation | `created_at` is timezone-aware, and naive datetimes cause comparison errors | Use `get_datetime_utc()` and test the boundary days |
| 8 | Data never purged | There's no scheduler, so deleted rows and items stay forever | Decide on a purge job and data-retention policy as a follow-up |
| 9 | Migration downgrade brings users back | Dropping the column makes every deleted user active again | Document it; hard-delete flagged rows before downgrading |
| 10 | User counts change | `read_users` count and pagination would include deleted users | Apply the same filter to both the count and the list queries |

Riskiest: #1. A soft-deleted user's existing login token keeps working unless `get_current_user` checks `deleted_at`.
