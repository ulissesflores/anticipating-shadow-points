I've written and validated the plan but not built anything, as asked. The plan is in `claude-home/plans/standard-let-a-user-polished-thunder.md`. One independent validator round returned REVISE with 10 issues, and all 10 are now in the plan.

## What I found in the code
- **Password sign-in already works**, with both sessions and JWT (`authentication/apis.py`).
- **Google sign-in exists only as a blog example** (`blog_examples/google_login_server_flow/`), and it isn't safe to build on as is:
  - it reads Google's ID token without checking its signature or intended audience;
  - it ignores whether Google has verified the email;
  - it never stores Google's permanent user ID (`sub`);
  - it sends the token contents back in the response.
- **Anyone can create a password account for any email** (`users/apis.py:63`), and nothing ever checks they own it. That makes automatic linking by email dangerous on its own: an attacker could register your email with a password before you ever sign in with Google, and keep access afterwards.

## Assumptions
I stated these instead of asking:
- Google sign-in uses sessions only; JWT stays password-only.
- Because email is never verified, every existing password account counts as unverified.
- The blog example is left untouched; the real code goes in the `authentication` and `users` apps.

## The plan
1. **Data model:**
   - add an `email_verified` flag to `BaseUser`;
   - add a `UserGoogleIdentity` table that stores Google's `sub` (unique), one per user;
   - write one additive migration.
2. **Google service:**
   - check the ID token properly using the `google-auth` library already in the requirements;
   - require that Google has verified the email.
3. **Sign-in with Google:**
   - Look the user up by `sub` first.
   - If there's no match, look them up by email, ignoring case. Link automatically only when all of these hold:
     - the email is a `@gmail.com` address or a Google Workspace domain;
     - the account isn't an admin;
     - the account isn't already linked to a different Google account (that case returns 409).
   - If the matched account's email was never verified, the person who proved they own it through Google wins. The old password is wiped, other sessions end and old JWTs stop working.
   - Inactive users are rejected before anything changes.
   - Two first-time sign-ins at once are handled without crashing or creating duplicates.
4. **Linking from a signed-in account:** the Google email must match the account email. This keeps the password, which is the gentle path for existing password users.
5. **Setting a password:** Google-only users can add one. The current password is required if one already exists.
6. **Endpoints:** one Google callback that acts only on what the current session started (sign-in or link). The response never includes tokens.
7. **Tests:** every one of these cases, plus a check that password sign-in is unchanged.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Attacker pre-registers the victim's email with a password | Account creation is public, with no email check | First Google sign-in wipes the old password, ends sessions, rotates the JWT key |
| 2 | Forged or misdirected ID token | The example skips signature and audience checks | Verify the token with `google-auth`; require a verified email |
| 3 | Attacker links their own Google account to someone else's account | The link flow could mark the email verified | Link only when the Google email equals the account email |
| 4 | Email used as the permanent key | Google emails can change or be reassigned | Store `sub`; use email only for the first link |
| 5 | Admin account taken over through Google | Auto-link would wipe the admin's password | Refuse auto-link for admins; require the explicit link |
| 6 | Non-Gmail address treated as proven | Google's "verified" flag is weaker for outside domains | Auto-link only `@gmail.com` or Workspace accounts |
| 7 | Legitimate user loses their password unexpectedly | Every existing account counts as unverified | Return a `password_was_reset` flag; offer link-while-signed-in and set-password |
| 8 | Set-password used to take over a stolen session | It's a new way to change credentials | Require the current password; rotate the JWT key; keep the user's own session |
| 9 | Two sign-ins at once cause errors or duplicate accounts | `sub` and email are both unique | Lock the row; retry inside a nested transaction |
| 10 | Inactive user gets in, or loses their password before being rejected | Google sign-in skips the usual inactive-user check | Check `is_active` before any change |

Riskiest: #1, the pre-registered password account. The other mitigations depend on wiping that password and ending its sessions at the first Google sign-in.
