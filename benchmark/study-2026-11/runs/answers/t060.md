# Plan: one account that can sign in with Google or with a password, linked by email

No code was changed. The plan is saved to `claude-home/plans/let-a-user-sign-bubbly-shamir.md`.

## What the code does now
- **Password login** goes through `authenticate()` in `styleguide_example/authentication/apis.py` (both session and JWT).
- **Google login** lives in two copies of `GoogleLoginApi`, in `blog_examples/google_login_server_flow/sdk/apis.py` and `raw/apis.py`. It looks the user up by email and returns 404 if there's no match. Three problems:
  - It decodes the Google ID token **without checking its signature** (`jwt.decode(..., options={"verify_signature": False})` in both `services.py` files).
  - It never checks whether Google says the email is verified (`email_verified`).
  - It doesn't record that the account is linked to a Google identity.
- The email lookup (`user_list(filters={"email": ...})`) is case-sensitive. Emails are stored lowercased (`create_user` lowercases them), so a Google email with capitals won't match.

## Assumptions
- Google login keeps using sessions, as it does today. JWT support can come later.
- An existing password account is linked automatically only when Google reports `email_verified=true`.
- If the email isn't found, a new user is created with no usable password (signing up via Google).
- Letting a Google-only user set a password through a set/reset flow is out of scope.
- No django-allauth. The plan follows the repo's existing services/selectors pattern.

## Steps
1. **New model `UserSocialAccount`**: fields `user` (FK to `BaseUser`), `provider` ("google"), `provider_uid` (Google's stable user ID, `sub`) and `email_at_link`. Unique on (`provider`, `provider_uid`) and on (`user`, `provider`). Plus a migration.
2. **Verify the ID token properly**: in both `decode_id_token` functions, use `google.oauth2.id_token.verify_oauth2_token(..., audience=settings.GOOGLE_OAUTH2_CLIENT_ID)`. That checks the signature, audience, issuer and expiry. `google-auth` is already in the requirements.
3. **New service `auth_google_login_or_link`** in `authentication/services.py`, run in one database transaction:
   - If a link already exists for this `sub`, return that user. After the first link, matching is by `sub`, never by email.
   - Otherwise, refuse unless the email is verified.
   - Lowercase the email and look the user up case-insensitively, locking the row.
   - If found, create the link. If not, call the existing `user_create(password=None)` and then link.
   - Reject inactive users.
4. **New selector `user_get_by_email`** that matches case-insensitively.
5. **Both `GoogleLoginApi` views**: replace the lookup-or-404 block with the service call. Keep the existing state (CSRF) check. Return `user_get_login_data` instead of echoing the raw token contents.
6. **Password login stays as it is**: `authenticate()` already fails for users with no usable password.
7. **Admin**: show linked Google accounts on the user page so staff can see and unlink them.

## Tests and verification
- **Service tests**:
  - An existing password user linked through a verified Google email ends up as the same user, and the password still works.
  - An unverified email is rejected.
  - A new email creates a user.
  - A repeat login matches by `sub` even after the email changes.
  - An email that differs only in case links to the existing user.
  - An inactive user is rejected.
- **API test** for the SDK callback with the Google calls mocked, checking that a state mismatch still returns 400.
- **Commands**: `makemigrations --check`, then `pytest styleguide_example/authentication styleguide_example/users`.
- **Manual check**: sign in with Google and with the password, and confirm `/api/auth/me/` returns the same user ID both times.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Account takeover through email linking | The ID token is currently decoded without a signature check and `email_verified` is ignored | Verify the token with `verify_oauth2_token` and require `email_verified` before linking |
| 2 | Someone pre-registers a victim's email with a password | Password signup doesn't confirm the email, so an attacker's password stays on the account after the real owner links Google | Require email confirmation before linking, or reset the password / notify the user when linking |
| 3 | Email changes or gets reused on Google's side | Matching only by email would follow the address, not the person | After the first link, match by `sub` only |
| 4 | Case mismatch | Lookup is case-sensitive; stored emails are lowercase | Lowercase the email and look up case-insensitively |
| 5 | Two simultaneous first logins create duplicate users or links | Lookup and create are separate steps | One transaction, a row lock, unique constraints, and handle `IntegrityError` |
| 6 | Logic duplicated across the sdk and raw flows | Two near-identical `GoogleLoginApi` copies | Both call one shared service |
| 7 | Sensitive token contents leaked in the response | Today's response returns the decoded token and user info | Return `user_get_login_data` instead |
| 8 | Google-only users get stuck | They have no usable password, so password login fails | Add a set/reset password flow later |
| 9 | JWT logout doesn't affect Google sessions | Google login is session-only; JWT logout rotates `jwt_key` | Document it; add JWT issuance later if needed |

Riskiest: #1, account takeover through linking on an unchecked or unverified Google token.
