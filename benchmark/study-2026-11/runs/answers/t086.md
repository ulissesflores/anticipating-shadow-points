**Assumptions (no questions asked):**
- One Docker host running Compose v2, with no orchestrator.
- "Zero downtime" means a client sending requests through nginx sees no errors and no dropped connections during a deploy.
- Migrations are written so the old and new code can both run against the new schema (add first, remove in a later release).
- Rolling back means redeploying the previous image; the database schema is not reversed.

**What the repo shows today:**
- A prod deploy (`docker compose ... up -d --build`) stops the old container before the new one is up, so the site goes down.
- Prod never runs `migrate` or `collectstatic`. `entrypoint.prod.sh` only waits for postgres.
- nginx looks up the `web` container's address once at start. A new container gets a new address, so nginx returns errors until it is reloaded.
- There are no health checks and no health endpoint.
- The dev `entrypoint.sh` runs `flush --no-input` before migrating, which wipes the database. It must never be reused for prod.
- Existing bug: `DEBUG = bool(os.environ.get("DEBUG", 0))` treats `"0"` as true, so prod currently runs with DEBUG on.

**Validated plan, in order:**
1. **D07 – fix DEBUG parsing.** Done first, because the static-file setup in D03 behaves differently once DEBUG is really off.
2. **D01 – health check.** Add a `/healthz` page that checks the database, a Compose health check written in Python (the image has no curl), and a 30s graceful shutdown for gunicorn with a 35s stop timeout.
3. **D02 – nginx.** Keep the current upstream but reload nginx at each swap step, and retry only on connection errors and timeouts.
4. **D03 – release step, run once before any container swap.** Back up the database, then `migrate` (with a lock timeout applied only to this run), then `collectstatic` into hashed file names. It runs in a one-off container (`docker compose run --rm --no-deps`). If it fails, the deploy stops and the old container keeps serving.
5. **D04 – `deploy.sh`:**
   - Take a lock so two deploys can't overlap, and tag the image with the git commit.
   - Record the old container's ID, then start a second `web` container.
   - Wait up to 120s for the new container to report healthy.
   - Disconnect the old container from the network, reload nginx, let in-flight requests finish, then stop and remove the old container.
   - A cleanup trap returns things to a known state if the script dies partway through the swap.
6. **D05 – migration gate.** A `makemigrations --check` step, written rules for migrations that old code can survive, and a check that blocks `flush` in the prod path.
7. **D06 – proof of zero downtime.** Three deploys, one of them with a new migration, under concurrent load plus a 5-second request started just before the old container is stopped. The pass condition is zero failed requests.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | New schema breaks the old container still serving | Old and new code share one DB during the swap | Add-then-remove migrations; review check; removals only in a later release |
| 2 | `migrate` runs in several places at once | Putting it in the entrypoint runs it in every container | One-off release step, never in the entrypoint |
| 3 | nginx keeps using the old container's address | It looks up `web` only at start or reload | Disconnect the old container, reload nginx, then stop it |
| 4 | In-flight uploads are cut off | Retries don't cover POSTs, and the default stop timeout is 10s | Drain first; 30s graceful shutdown under a 35s stop timeout |
| 5 | Migration locks a busy table or fails halfway | Postgres schema changes take exclusive locks | Lock timeout on the migrate run only; backup first; stop on failure |
| 6 | Dev entrypoint copied into prod wipes the DB | `entrypoint.sh` runs `flush --no-input` | Prod entrypoint never migrates; check blocks `flush` |
| 7 | Static files missing or mismatched between versions | Prod never ran `collectstatic`; the static volume is shared | Hashed file names; `collectstatic` without `--clear` in the release step |
| 8 | Script dies mid-swap and leaves two containers | No cleanup on failure | Cleanup trap, deploy lock, old container's ID recorded |
| 9 | Fixing DEBUG causes new errors (500s) | Hashed static files fail hard once DEBUG is off | Fix DEBUG first; run D06 with `DEBUG=0` |
| 10 | Disk fills with images and backups | Every deploy adds an image tag and a DB dump | Keep the last 3 images and 7 dumps |

Riskiest: #1. Automatic migrations on every deploy mean old code serves against a new schema during each swap, and with rollback not reversing the schema, one careless column drop or rename causes errors that rolling back can't fix.
