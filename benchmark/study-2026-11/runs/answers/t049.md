## What the code does now

- The list of HTTP methods ky retries by default is `get put head delete options trace query` (`source/utils/normalize.ts:17`). POST and PATCH are not on it.
- `retry.methods` is checked first and applies to every kind of retry (`source/core/Ky.ts:703`). If a method is on that list, it gets retried for network errors, for status codes 408/413/429/500/502/503/504, and, when enabled, for timeouts.
- So the obvious one-line change, adding `'post'` and `'patch'` to that list, would also retry POST and PATCH on 5xx and 429 responses. That goes beyond "when the network fails". A 500 or 502 often means the server already ran the write.
- You can already opt in today with `retry: {methods: ['post']}`. Tests use this (`test/resilience.ts:831` and onward), and those tests also show that every body type can be replayed.

## Assumptions

- "Network fails" means only errors that `isRawNetworkError` recognises and that ky wraps as `NetworkError`. Timeouts and HTTP status codes don't count.
- Existing behaviour stays the same: a user's explicit `retry.methods` still wins, a `shouldRetry` that returns `false` still blocks a retry, and `retry: 0` still disables retries.
- This changes behaviour in a way users will notice, so it ships as a major release (3.0.0), not as a 2.2.x patch.

## Ways this could go wrong (listed before planning)

1. **Duplicate writes.** A network error can't tell you whether the request reached the server. Undici's `terminated`, Safari's `Load failed` and Chrome's `Failed to fetch` can all happen after the server already processed the POST but before the response came back. Retrying then creates a second order or payment. Mobile connections, the case you're targeting, are where this happens most.
2. **Retrying on status codes too.** Widening `methods` alone retries POST on 500/502/503/429, as described above.
3. **Breaking existing callers.** Code that relies on POST being tried exactly once changes silently. For example, `test/retry.ts:322 "not on POST"` asserts the current behaviour.
4. **Extra memory and stream copies by default.** When retries are on, ky clones the request (`Ky.ts:1225`). For streamed bodies that copy holds the data in memory, so large POST uploads would roughly double their memory use by default.
5. **Upload progress.** Over HTTP/1.1 in Chromium, a streamed upload with `onUploadProgress` fails with a network error. That error would now be retried, and it will fail again the same way. The result is several attempts for every request, plus progress callbacks that reset.
6. **Uncertain-outcome errors not separated out.** `terminated` (connection dropped mid-flight) is treated the same as a DNS or connection-refused failure.
7. **Interaction with `shouldRetry` and hooks.** Users' `shouldRetry` and `beforeRetry` hooks will start firing for POST, and some of them assume they never will.
8. **Breaking the project's conventions.** Any new option must reject `null` with an error that names the option (AGENTS.md says `null` is never accepted), and it must be validated in `normalizeRetryOptions`.
9. **Docs out of sync.** The defaults are documented in `readme.md:265,281,1415` and in `source/types/options.ts` and `source/types/retry.ts`.

## Recommended approach

Add a separate default for network errors only, rather than widening `methods`:

1. **New option.** Add `retry.networkErrorMethods` to `RetryOptions` and `MutableRetryOptions` in `source/types/retry.ts`. It defaults to `[...retryMethods, 'post', 'patch']` in `normalize.ts`, and it goes through the same array, string and `null`-rejecting checks as `methods` (`normalize.ts:55-70`).
2. **Decision logic in `Ky.ts` (around line 700).**
   - A method on `retry.methods` behaves exactly as it does today.
   - A method only on `networkErrorMethods` can be retried only if the error is a `NetworkError`. Otherwise, or if `shouldRetry` returns `false`, the original error is thrown. Status-code and timeout retries stay blocked unless `shouldRetry` returns `true`, as it can today.
   - If the user sets `methods` but not `networkErrorMethods`, then `networkErrorMethods` should follow `methods`. Otherwise someone who wrote `methods: ['get']` would unexpectedly get POST retries.
3. **Don't make large or streamed uploads worse.** For a POST or PATCH that is only on `networkErrorMethods`, skip the retry clone when the body is a `ReadableStream` or `onUploadProgress` is set. Clone only when that method is eligible to be retried.
4. **Tests.**
   - Change `test/retry.ts:322` so it covers both cases: POST is not retried on a 5xx but is retried on a dropped connection.
   - Add PATCH cases.
   - Add cases for `networkErrorMethods: []`, for `null` throwing a `TypeError`, for `methods` without `networkErrorMethods` overriding the new default, and for a streamed body not being retried.
   - Check the type tests in `test-d/`.
5. **Docs and release.** Update the readme's retry section and the "Network errors" section, including a warning about duplicates and a recommendation to send an `Idempotency-Key` header from `beforeRequest`. Note it as a breaking change in the 3.0.0 release notes.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate side effects | `NetworkError` can't tell "never sent" from "response lost" (e.g. `terminated`) | Document it; recommend an `Idempotency-Key`; users can opt out with `networkErrorMethods: []` |
| 2 | POST retried on 5xx/429 | `retry.methods` covers status-code retries too | New `networkErrorMethods` option, limited to network errors |
| 3 | Silent breaking change | Callers and `test/retry.ts:322` assume POST is tried once | Release as 3.0.0 with a changelog entry |
| 4 | Explicit `methods` overridden | A new default could add POST for users who set `methods: ['get']` | `networkErrorMethods` follows `methods` when only `methods` is set |
| 5 | Memory blow-up on uploads | Retry clone copies streamed bodies (`Ky.ts:1225`) | No retry and no clone for streamed POST/PATCH bodies |
| 6 | Retry loop with `onUploadProgress` | Chromium on HTTP/1.1 always fails with a network error | Exclude it by default; the readme's `beforeRetry` workaround still applies |
| 7 | `null` quietly accepted | AGENTS.md forbids `null` fallbacks | Validate in `normalizeRetryOptions` with an error naming the option |
| 8 | Hooks firing unexpectedly | `shouldRetry` and `beforeRetry` now run for POST | Release notes; `shouldRetry` returning `false` still wins |
| 9 | Docs and types out of sync | Defaults listed in the readme, `options.ts` and `retry.ts` | Update all of them; add a `test-d` case |

Riskiest: #1 — automatically retrying a POST after a dropped connection can charge or create something twice, and on mobile networks that is exactly when connections drop.
