## What the code already does

- **User model** (`styleguide_example/users/models.py:49`): `BaseUser` has a unique email that is the login name. `create_user` lowercases the email (line 20). Users created without a password get an unusable one (line 28).
- **Password login** (`styleguide_example/authentication/apis.py`): session login uses `authenticate()`, and JWT login uses `ObtainJSONWebTokenView`. Logout rotates the user's JWT key (`authentication/services.py:18`).
- **Google login** exists only as blog examples: `blog_examples/google_login_server_flow/raw/apis.py` and the near-identical `sdk/apis.py`. Both already link by email:
  - they read `id_token["email"]`;
  - they look the user up with `user_list(filters={"email": ...})`, which is an exact, case-sensitive match;
  - they call `login()`;
  - they return 404 if no user is found.

So "linking by email" half-exists already, but it has these gaps:
- It never checks `email_verified` or `hd`.
- It decodes the ID token with `verify_signature=False` and doesn't check `aud` (`raw/service.py:30`).
- It doesn't store Google's stable user ID (`sub`).
- It doesn't check `is_active`.
- It doesn't create new users.
- Its email lookup can miss because of upper/lower case.

## Assumptions (no one to ask)

1. "Same account" means one `BaseUser` row, whichever method created it.
2. Signing in with Google for an unknown email creates a user with an unusable password. Such users can add a password later through a set-password flow (out of scope here, but the plan leaves room for it).
3. Auto-linking happens only when Google says `email_verified=true`.
4. There is no email verification for password sign-up today, so a password-only account's email counts as unverified.
5. The production Google endpoint moves out of `blog_examples` into `authentication/`, reusing the raw flow service. Both session and JWT login are supported.

## How this could go wrong (before planning)

- **Pre-hijack:** an attacker signs up with a password using the victim's email. Later the victim signs in with Google, gets linked, and the attacker's password still works.
- **Unverified email from Google:** linking on an email Google hasn't verified lets anyone claim any account.
- **Case mismatch:** the lookup is case-sensitive but stored emails are lowercase, so a mixed-case Google email fails or creates a duplicate.
- **Changed or reused emails:** without `sub`, a Google account that changes its email, or a recycled Workspace address, lands on the wrong user.
- **Deactivated users:** `login()` doesn't check `is_active`, so Google login would bypass deactivation.
- **Google-only users:** they have no password, so password login fails for them and needs a clear error and a set-password path.
- **Unverified tokens:** if the ID token is ever accepted from the client instead of the server-side code exchange, signature and audience checks become essential.
- **Race on first login:** two parallel callbacks can try to create the same user, and the unique email constraint raises a 500.
- **Account enumeration:** different errors for "no account", "Google-only account" and "wrong password" reveal which emails exist.
- **Duplicated code:** the raw and sdk examples are near-copies, so a fix in one can drift from the other.

## Plan

1. **Model:** add a `GoogleIdentity` model (`user` FK, unique `sub`, `email`, `linked_at`) in `users/` or `authentication/`, plus a migration. Also add `BaseUser.email_verified` (default False; existing Google-linked users stay False).
2. **Selector:** add `user_get_by_email(email)` that does `email__iexact` on the lowercased email. Reuse it everywhere instead of `user_list(filters={"email": ...})`.
3. **Service** `authentication/services.py::google_login_or_link(*, id_token_claims) -> BaseUser`, inside `@transaction.atomic`:
   - Check `iss`, `aud == GOOGLE_OAUTH2_CLIENT_ID` and `exp`, and turn on signature checking in `decode_id_token`. Reject if `email_verified` isn't true.
   - Look up by `sub` first.
   - Otherwise look up by email with `select_for_update`:
     - If the user exists and is unverified, link it, mark it verified, set an unusable password and rotate the JWT key. This kills the pre-hijack credentials; the owner can reset the password.
     - If the user exists and is verified, just link it.
   - If no user exists, call `user_create(email=..., password=None)`, catching `IntegrityError` and retrying the lookup.
   - Reject if `not user.is_active`.
4. **APIs:**
   - Move the redirect and callback views into `authentication/apis.py` and `urls.py`, keeping the session `state` CSRF check.
   - The callback calls the service, then either `login()` for sessions or issues a JWT with the existing `jwt_payload_handler` pattern.
   - Return generic errors that don't reveal whether an account exists.
5. **Password path:** `UserSessionLoginApi` and JWT login stay as they are. A Google-only user just gets the generic 400. Optionally add `POST /auth/password/set`, which needs a recent login.
6. **Cleanup:** point the blog example views at the new service, or leave them alone and mark them as demo-only.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Pre-hijack takeover | Password sign-up has no email verification; Google login auto-links by email | When linking an unverified account, set an unusable password and rotate the JWT key |
| 2 | Linking on an unverified Google email | The current code never checks `email_verified` | Reject unless `email_verified` is true |
| 3 | Forged or misdirected token | `decode_id_token` uses `verify_signature=False` with no `aud` check | Verify signature, `iss`, `aud` and `exp` |
| 4 | Changed or recycled email maps to the wrong user | No `sub` is stored; only email is matched | `GoogleIdentity.sub`, unique; look up by `sub` first |
| 5 | Duplicate or missed account from case | `user_list` matches exactly, while `create_user` lowercases | `email__iexact` and normalize before lookup |
| 6 | Deactivated users get in | `login()` skips the `is_active` check | Check explicitly in the service |
| 7 | 500 on first-login race | Unique email plus parallel callbacks | `select_for_update` and retry on `IntegrityError` |
| 8 | Google-only users locked out of password login | Unusable password is set at creation | Generic error plus a set-password or reset flow |
| 9 | Account enumeration | 404 "User with email X not found" today | Same generic error for every failure |
| 10 | Fixes drift between copies | Logic is duplicated in raw and sdk blog flows | One service that both call |

Riskiest: #1, pre-hijack takeover. Auto-linking by email onto password accounts whose email was never verified gives an attacker who registered first a lasting password into the victim's account.
