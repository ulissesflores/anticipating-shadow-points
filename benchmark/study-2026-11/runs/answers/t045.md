## Assumptions (no one to ask in this run)
1. **Trigger:** a new command, `flask send-digests`, run once a week by an outside scheduler such as cron or Heroku Scheduler. Nothing in the repo can schedule jobs today; it only has a queue (RQ) and a worker.
2. **What counts as new:** posts from the people the user follows, created since that user's last digest (or the last 7 days the first time), up to a cutoff fixed when the run starts. The user's own posts are left out.
3. **Who gets an email:** users with no new posts get nothing. Each email shows at most 50 posts plus an "and N more" link.
4. **Opt-out:** digests are on by default. Each email has a one-click unsubscribe link, and there is a checkbox on the edit-profile page.

## What the code showed
- **Own posts would leak in:** `User.following_posts()` (`app/models.py`) includes the user's own posts, so it can't be reused as is.
- **Timezone mismatch:** SQLite stores naive timestamps, and the code adds a timezone back in places, so date comparisons can silently mix naive and aware datetimes.
- **Not testable as is:** `app/tasks.py` builds a full app when it is imported, so tests can't import it.
- **Failures are hidden:** `export_posts` swallows its exceptions.
- **Emails can be lost:** `send_email` sends from a background thread by default, which dies with the worker.
- **Links and translations need a web request:** building absolute links and picking a language both fail inside the worker.
- **Wrong reuse target:** `launch_task` would create a `Task` row and progress notifications for every user.

## Plan (revision 2, after one review round)
1. Add two columns to `User` — `digest_enabled` (default true) and `last_digest_sent_at` — through a migration written with `batch_alter_table` so it also works on SQLite.
2. Add `User.digest_posts(since, until, limit)`, which returns only posts by followed users.
3. Put the logic in a new `app/digest.py`; `app/tasks.py` gets only a thin wrapper.
4. To prevent duplicates, each user is claimed in one transaction: read the old send time, then set the new one only if the old one is at least 6 days older than this run's cutoff. If sending fails, the old value is put back.
5. Emails are built with a new `DIGEST_BASE_URL` setting rather than by requiring `SERVER_NAME`. Requiring `SERVER_NAME` would make the web app return 404 for requests under other hostnames.
6. `send_email` gets an optional `extra_headers` argument, used for the `List-Unsubscribe` and `List-Unsubscribe-Post` headers.
7. The unsubscribe link opens a confirmation page and only the confirm button changes the setting, so mail scanners that follow links can't unsubscribe people.
8. Digests run on their own `microblog-digest` queue and worker so they don't hold up user-requested exports.
9. Tests call the send function directly and check sent mail with `mail.record_messages`, so they need no Redis. They cover the time boundaries, a post landing between two runs, opt-out, a tampered unsubscribe token, and the 50-post cap.

**Deliverables:** D01 model + migration, D02 query/builder, D03 job + command, D04 templates + headers, D05 opt-out, D06 ops docs.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Duplicate digests | No scheduler; cron retries or overlapping runs each pick a new cutoff | Per-user claim with a 6-day minimum gap, done in one transaction |
| 2 | Lost or doubled posts at the edges | Naive SQLite timestamps compared with timezone-aware ones | One fixed UTC cutoff passed to every job; boundary tests |
| 3 | Own posts in the digest | `following_posts()` includes the user's own posts | New `digest_posts()` query that excludes them |
| 4 | Broken links or crash in the worker | Absolute links and language choice need a web request | Render inside a request context built from `DIGEST_BASE_URL` |
| 5 | Web app returns 404s | Setting `SERVER_NAME` makes Flask reject other hostnames | Separate `DIGEST_BASE_URL`; leave `SERVER_NAME` alone |
| 6 | Accidental unsubscribes | Mail scanners open links in emails | Unsubscribe only on confirm (POST); one-click header |
| 7 | Mass mail with no opt-out | No preferences or email verification exist today | `digest_enabled` flag and signed unsubscribe token |
| 8 | User exports stuck behind digests | Single `microblog-tasks` queue and worker | Separate digest queue and worker; `result_ttl=0` |
| 9 | Silent send failures | `export_posts` swallows errors; background-thread sends | Send synchronously, let the job fail visibly, log counts |
| 10 | Digest never runs | Weekly trigger depends on outside cron | Cron sample, README section, `--dry-run` check |

Riskiest: #1, duplicate digests from overlapping or retried runs, because nothing in the app schedules jobs or guards against sending twice today.
