I've written a plan to add co-authors to articles; no code was changed. The plan file is `<config>/plans/allow-an-article-to-lexical-teacup.md`.

**Assumptions:**
- Each article keeps one primary author who owns it.
- Co-authors can edit an article's content, but only the primary author can delete it or change who the co-authors are.
- Adding new fields to JSON responses is fine for current clients.
- Co-authors are added without an invite or acceptance step in this first version.

## Approach
Keep `Article.authorId` as the primary author. Article URLs are built as `${slugify(title)}-${authorId}`, so leaving `authorId` alone keeps every existing URL, the `author` field in responses, and the current permission checks working. Co-authors are added alongside it, and nothing existing is removed.

1. **Database** (`src/prisma/schema.prisma` plus a new migration): add a link table `ArticleCoAuthor(articleId, userId, position, createdAt)`, with `@@id([articleId,userId])`, an index on `userId`, and cascade deletes in both directions. It only adds a table, so existing data needs no migration.
2. **Read model:** the same Prisma `include` block is copied 7 times in `article.service.ts`. Replace the copies with one shared `articleInclude` constant that also loads `coAuthors`, ordered by `position`.
   - `articleMapper` adds `coAuthors: Profile[]` and leaves `author` as it is.
   - `favoriteArticle`/`unfavoriteArticle` build their responses from the raw database row. They need to replace `coAuthors` with mapped profiles so the link-table rows don't show up in the response.
3. **Create and update:** accept an optional `article.coAuthors: string[]` of usernames.
   - Validation: remove duplicates, drop the primary author, allow at most 10, and return a 422 for any unknown username.
   - On update, replace the whole list inside `$transaction`. If the field is left out, nothing changes.
   - **Slug fix:** `updateArticle` currently builds the new URL from the *requesting user's* id (`-${id}`). Once co-authors can edit, a co-author changing the title would change the URL suffix. It must use the article's `authorId` instead.
4. **Lists and permissions:**
   - `PUT` is allowed for the primary author or a co-author. `DELETE` and changing co-authors stay primary-only.
   - In `buildFindAllQuery`, article lists only show articles whose primary author is a demo user or the logged-in user. Extend this so co-authors can also see articles they co-wrote.
   - `?author=` keeps meaning "primary author", and a new opt-in `?coauthor=username` filter is added. The feed is unchanged for now.
5. **Checks:**
   - Extend `src/tests/services/article.service.test.ts` to cover: creating with co-authors, the 422 case, a co-author's edit keeping the URL, a co-author being refused on delete, and an old article returning its previous fields plus `coAuthors: []`.
   - Run `prisma migrate` on a copy of production data.
   - Run the e2e smoke test.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | URL changes when a co-author edits the title | `updateArticle` builds the slug from the requester's `id` | Build it from the stored `authorId`; add a test |
| 2 | Raw database fields leak into responses | Favorite/unfavorite copy the whole database row into the response | Replace `coAuthors` with mapped profiles; add a response-shape test |
| 3 | Breaking strict clients | Clients that check the exact response shape may reject a new field | Only add the `coAuthors` field; keep `author` unchanged |
| 4 | `?author=` results change | Profile pages and article counts depend on it | Keep it primary-only; add opt-in `?coauthor=` |
| 5 | Co-authors can't see their own articles | List visibility only checks the primary author | Extend the visibility check to include co-authors |
| 6 | Permission mistakes | Edit, delete and co-author-list rights now differ by role | Put the checks in one helper and test each role |
| 7 | Slower queries | Each co-author's full `followedBy` list is loaded | Only load whether the current user follows them |
| 8 | Partial co-author updates | Replacing the list is several writes | Wrap them in `prisma.$transaction` |
| 9 | Co-authors added without consent | There is no invite or accept step | Cap the list size; consider an invite flow later |
| 10 | Migration problems | Prisma changes the production schema | The change only adds a table; run it on staging first |

Riskiest: #1 — if a co-author edits an article's title, its URL changes and existing links break.
