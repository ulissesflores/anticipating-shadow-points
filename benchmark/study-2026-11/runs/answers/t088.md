## Context
This repo is the Flask Mega-Tutorial microblog at chapter 23. It already has:
- the `followers` table in `app/models.py`
- an email helper, `send_email` in `app/email.py`
- a background job queue (RQ queue `microblog-tasks` with an `rq worker` process), and a job module at `app/tasks.py`

It has nothing that runs on a schedule. The feature: once a week, email each user the posts written in the last 7 days by the people they follow.

## Assumptions
- "New posts" means posts from the previous 7 days. Each run uses a fixed window, from 7 days before the run to the time of the run.
- Users who would get an empty digest receive no email.
- Users are opted in by default and can turn it off: a checkbox on the profile form plus an unsubscribe link in the email.
- The digest leaves out the user's own posts, even though the home timeline `following_posts()` includes them.
- The weekly trigger comes from outside the app (cron, Heroku Scheduler or a systemd timer), not from a new scheduling library.
- One email per user, showing at most about 20 posts plus a "and N more" link.

## Steps
1. **Model and migration** (`app/models.py`, new file in `migrations/versions/`)
   - Add `User.digest_opt_in` (true/false, defaults to true for new and existing users).
   - Add `User.last_digest_sent` (date-time, may be empty).
   - Add `User.digest_posts(since, until)`. It only matches posts by people the user follows, newest first, limited to about 20, and also returns the total count. It's a simpler version of `following_posts()`.
2. **Per-user job** (`app/tasks.py`): `send_weekly_digest(user_id, since, until)`.
   - Skip the user if they opted out, have no posts in the window, or `last_digest_sent >= until`.
   - Otherwise render new templates `email/weekly_digest.txt/.html` (modelled on `export_posts.*`) and send with `send_email(..., sync=True)`.
   - Then set `last_digest_sent = until` and save.
   - Don't create a `Task` row and don't call `_set_task_progress`, or every user would see a progress alert in the UI.
3. **Command that queues the jobs** (`app/cli.py`): `flask digest send [--dry-run]`.
   - Compute the window once.
   - Go through opted-in users who follow at least one person, in batches.
   - Queue one job per user on `current_app.task_queue`, with job id `digest-{user_id}-{ISO week}` so the same week can't be sent twice.
4. **Scheduling and deployment**
   - Add a weekly cron or supervisor/systemd example under `deployment/` and a Heroku Scheduler note to the README.
   - Require `SERVER_NAME` and `PREFERRED_URL_SCHEME`. Without them, building full links with `url_for(_external=True)` fails when there's no web request, as in a cron run or a worker.
5. **Opt-out**
   - Add a checkbox to `EditProfileForm` and handle it in the `edit_profile` route.
   - Add a signed one-click `/unsubscribe/<token>` route that needs no login. The token is a JWT, the same pattern as `get_reset_password_token`.
   - Extend `send_email` with an `extra_headers` option so the email can carry a `List-Unsubscribe` header.
6. **Translation**: wrap new strings in `_()`/`_l()`, then run `flask translate update` and fill in the Spanish strings.

## Verification
- **Unit tests in `tests.py`:**
  - `digest_posts` leaves out own posts, posts from people not followed, and posts outside the window.
  - The job skips opted-out users and empty digests.
  - Running it twice sends only once (capture mail with `mail.record_messages()`).
  - The unsubscribe token round-trips.
- **Manual:**
  1. `flask db upgrade`
  2. `flask digest send --dry-run`
  3. Start a local debug mail server with `aiosmtpd -n -c Debugging -l localhost:8025` and set `MAIL_SERVER=localhost MAIL_PORT=8025`.
  4. Run `rq worker microblog-tasks`, then `flask digest send`, and check the rendered email.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate digests | Cron retries, a re-run of the command, or RQ re-running a job can all send the same week again | `last_digest_sent` check plus one job id per user per week |
| 2 | No scheduler exists | RQ 1.15 has no built-in timer; nothing runs the command weekly | External cron/Scheduler plus documented deploy step |
| 3 | Broken links in email | `url_for` outside a web request needs `SERVER_NAME`, which isn't set by default | Require it in config; fail fast in the command |
| 4 | Email-provider limits / spam reputation | Bulk mail goes through the same SMTP account as password resets | Batch and throttle; consider a dedicated provider |
| 5 | Spam complaints and legal exposure (CAN-SPAM/GDPR) | Opting everyone in by default means existing users get unsolicited mail | One-click unsubscribe, `List-Unsubscribe` header, announce first |
| 6 | Slow queries at scale | Followers join per user, filtered by time | Use the existing `Post.timestamp` index; limit to about 20; batch users |
| 7 | Own posts included by mistake | Reusing `following_posts()` pulls in the user's own posts | Separate query plus a test for it |
| 8 | Worker side effects | `tasks.py` builds the app at import; existing jobs create `Task` rows and progress alerts | Digest job skips `Task` and notifications |
| 9 | Timezone mix-ups at the window edges | Some timestamps are stored without a timezone (code uses `.replace(tzinfo=utc)`) | Compute in UTC; window includes `until`, excludes `since` |
| 10 | Migration default | A new true/false column on existing rows needs a database-side default (SQLite/Postgres) | `server_default=sa.true()` in migration |

Riskiest: #1. Duplicate or repeated bulk emails to every user can't be undone and hurt both user trust and the mail account's reputation.
