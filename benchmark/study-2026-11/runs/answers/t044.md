# Plan (stopped after Phase 6): retry POST/PATCH on network failure by default

The plan is ready and has been through one independent review. I edited no files in the repo; the only file written is the plan itself, at `claude-home/plans/standard-make-ky-retry-ancient-ladybug.md`.

**Why POST/PATCH don't retry today:** the default retry methods (`source/utils/normalize.ts:17`) leave out `post` and `patch`. Ky checks the method (`source/core/Ky.ts:703`) before it looks at what kind of error happened, so a dropped connection on a POST fails at once.

## Assumptions (non-interactive run, so these were not confirmed with you)
- **A1** "Network fails" means a `NetworkError` only. It does not include timeouts, 5xx/429 responses, non-Error throws, or a connection that drops while the response body is being read.
- **A2** I don't add `post`/`patch` to the existing `retry.methods` list. That would also retry them on 408/413/429/5xx, which goes beyond what you asked.
- **A3** Changing a default breaks existing users, so this belongs in a major release (3.0.0) with a migration note. Releasing is out of scope.
- **A4** Ky will not add an `Idempotency-Key` header by itself. A custom header like that forces a CORS preflight on cross-origin calls. The readme gets a recipe instead.
- **A5** The project has no lessons store; the code and the readme were the only sources consulted. The readme already warns: *"a network error does not tell whether the server got the request"* (`readme.md:581`).

## The design
- **New option:** `retry.networkErrorMethods`, defaulting to `['post', 'patch']`.
- **Rule:** a request may retry if its method is in `methods`, or if the error is a `NetworkError` and its method is in `networkErrorMethods`.
- **Unchanged:** forced retries via `ky.retry()`.
- **`shouldRetry`:** for POST/PATCH it is now called on network errors, so you can veto a retry there. It is still not called when they get an HTTP error.
- **`null` for the new option** throws an error naming the option, as the project's conventions (AGENTS.md) require; it is not treated as "absent".
- **Opting out:** `networkErrorMethods: []` restores today's behaviour.
  - If a parent instance created with `ky.create` already set this option, a plain `[]` in a child instance or a single request doesn't remove anything, because nested arrays are concatenated (`source/utils/merge.ts:348-353`). Use `replaceOption([])` instead.
  - Without a parent setting, plain `[]` works.

**Files to change:**
- `source/utils/normalize.ts` and `source/core/Ky.ts:702-705` (the logic)
- `source/types/retry.ts` and `source/types/options.ts` (the retry docs are duplicated there)
- `source/errors/NetworkError.ts` and `readme.md` (docs)
- the tests

**Deliverables:**
- **D01:** the option's default and validation
- **D02:** the method-check change
- **D03:** types and type tests
- **D04:** runtime tests:
  - POST/PATCH are retried on a `NetworkError`, with the body resent byte for byte.
  - They are not retried on 500/429, on a timeout, or when the body read fails.
  - `shouldRetry` can veto a retry.
  - Both ways of opting out work.
  - Hooks and forced retries behave as before.
- **D05:** docs and the migration note

**Verification:** `npm test` must pass. The existing tests `'not on POST'` (`test/retry.ts:322`) and `'shouldRetry is not called…'` (`test/retry-decisions.ts:240`) should pass unchanged, because both use a 500 response.

## Independent review
**Round 1: REVISE.** I checked the reviewer's points against the code:
- **Confirmed:** retrying adds no new memory cost. The request body is already copied whenever retries are on, whatever the method (`Ky.ts:1225`).
- **Corrected:** my plan claimed that `[]` replaces the parent's list when instances are extended. It doesn't, as described above, so the opt-out now uses `replaceOption([])`.
- **Added:** the duplicated docs and `shouldRetry` docs to update; tests for forced retries, hooks, timeouts, uppercase methods, the numeric `retry` shorthand and non-Error throws; and an explicit position on whether this default is safe.

The design itself was not challenged, so I didn't run another round.

**My position:** the plan does what you asked. But if a POST charges a card, creates an order or sends a message, retrying it after a network error can repeat that action. If maintainers or users object, the fallback is the same option with an empty default, so retries become opt-in.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Duplicate side effects (double charge or order) | Some network errors (Node's "terminated", Safari's "Load failed") can happen after the server has already committed | Retry on `NetworkError` only; prominent readme warning; Idempotency-Key recipe; `shouldRetry` veto |
| 2 | Silent behaviour change for 2.x users | Every POST/PATCH caller changes behaviour with no code change on their side | Release as 3.0.0 with a migration note; `[]` opt-out |
| 3 | Opt-out silently does nothing in a child instance or per request | Nested arrays are concatenated when options merge | Document and test `replaceOption([])` |
| 4 | Retries spread to 5xx, 429 or timeouts | Easy to do by widening `methods` by mistake | Separate option; tests that POST is not retried on 500/429/timeout |
| 5 | `shouldRetry` behaves differently | It is now called for POST network errors | Exact wording in the docs; keep the existing HTTP-error test |
| 6 | `null` silently accepted | The project rule forbids treating `null` as absent | Existing array validation throws an error naming the option; add a test |
| 7 | Pointless retries of Chromium uploads with progress tracking | Over HTTP/1.1 these uploads always fail with a network error | Accept; document the existing `beforeRetry` recipe |
| 8 | Retry storm when many phones reconnect at once | Jitter is off by default | Accept; suggest `jitter: true` in the docs |
| 9 | Docs out of sync | Retry text is duplicated in the readme, `options.ts` and `retry.ts` | Update all three in D05 |

Riskiest: #1. Retrying a non-idempotent POST/PATCH after a network error that happened once the server had already committed repeats real side effects such as payments or orders, and fetch gives Ky no way to tell that case apart from a failure before the server received the request.
