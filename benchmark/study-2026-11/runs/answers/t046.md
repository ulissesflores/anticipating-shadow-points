I've written the plan for zero-downtime deploys with automatic migrations. I edited no repo files. The plan is saved at `claude-home/plans/deploy-new-versions-with-sprightly-papert.md`.

## Why the site goes down today
- **Old container stops first:** running `docker compose up -d --build` with `docker-compose.prod.yml` stops the old `web` container before the new one is ready.
- **nginx keeps the old address:** the `upstream { server web:8000; }` block in `nginx/nginx.conf` looks up `web` only when nginx starts. Once `web` is recreated with a new IP, nginx returns 502 errors until it is restarted.
- **Manual steps:** `app/entrypoint.prod.sh` only waits for the database port. `migrate` and `collectstatic` are run by hand.
- **No health or shutdown handling:** nothing checks container health, and the image has no curl. `docker stop` uses the default 10-second grace period.

## Assumptions
- Production stays on a single host running plain Docker Compose v2, with no Swarm or Kubernetes. It's deployed with a shell script, not a CI platform.
- Postgres runs in the same Compose project, and running two `web` containers for a short time is fine.
- Database changes will follow an "expand, then contract" rule: add the new things in one release and remove the old things in a later one. This is needed because the old code keeps running against the new database schema for a short time.

## Plan
1. **Separate migration step.** Add a `migrate` service to `docker-compose.prod.yml`, under `profiles: ["release"]` and using the same image as `web`. It runs `python manage.py migrate --noinput && python manage.py collectstatic --noinput` and mounts `static_volume`. It runs once per deploy, before any traffic moves. It is kept out of web's entrypoint so two web containers never run migrations at the same time.
2. **One shared image.** `web` and `migrate` both use `image: hello_django_web:${TAG:-latest}`, so each deploy builds once. Before switching, the current image is tagged `:prev` so you can roll back.
3. **Health checks.**
   - Add a `/healthz/` view in `app/hello_django/urls.py` that runs `SELECT 1` against the database.
   - Add a Compose healthcheck for `web` that uses Python's urllib, since the image has no curl.
   - Add a `pg_isready` healthcheck for `db`, and make `web` and `migrate` wait on `depends_on: condition: service_healthy`.
4. **Graceful shutdown.** Set `stop_grace_period: 30s` and run gunicorn with `--graceful-timeout 25`. The entrypoint already uses `exec`, so gunicorn receives the stop signal directly.
5. **nginx.** Add `proxy_next_upstream error timeout http_502;` and `proxy_connect_timeout 2s;`, so a request that hits a stopping container is retried on the other one. The deploy script reloads nginx gracefully (`nginx -s reload`) after each container change.
6. **New `scripts/deploy.sh`.** A lock (`flock`) stops two deploys from running at once. The steps:
   1. Build the image; stop if the build or flake8 fails.
   2. Tag the current image `:prev`.
   3. Run `docker compose --profile release run --rm migrate`; stop if it fails, leaving the old version serving.
   4. On a first deploy with no `web` running, just run `up -d` and finish.
   5. Run `--scale web=2 --no-recreate` and wait for the new container to report healthy. If it doesn't, remove it and stop.
   6. Reload nginx, stop the old container (letting in-flight requests finish), remove it, scale back to 1, and reload nginx again.
   7. Smoke-test `curl localhost:1337/healthz/`.
7. **README.** Update the production section to use `deploy.sh` and state the expand/contract rule.

**Files touched:** `docker-compose.prod.yml`, `nginx/nginx.conf`, `app/hello_django/urls.py`, new `scripts/deploy.sh`, and `README.md`. The existing `entrypoint.prod.sh` is reused unchanged for the database wait.

**How to verify it:**
- Run a curl and POST-upload loop during a deploy and expect no non-2xx responses.
- Deploy a deliberately broken migration: the deploy should stop and the old version keep serving.
- Deploy an image whose health check fails: it should be removed and the old version keep serving.
- Start two deploys at once: the lock should block the second.

**Unrelated bug in `settings.py`:** the line `DEBUG = bool(os.environ.get("DEBUG", default=0))` treats the text `"0"` as true. So `DEBUG=0` in `.env.prod` turns debug mode **on** in production. Fixing it is outside this change, but it should be fixed.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | New schema breaks the old code still serving | Migrations run before the switch, so old containers keep serving on the new schema | Expand/contract rule; no drop/rename in the same release |
| 2 | Migration can't be undone | `:prev` rolls back code only, not the database | Back up with `pg_dump` before migrating; write reversible migrations |
| 3 | nginx sends traffic to a dead IP | It looks up `web` only when it starts or reloads | Reload after each step, plus `proxy_next_upstream` |
| 4 | POSTs dropped while the old container stops | nginx won't retry a request already sent upstream | Graceful drain: 30s grace period and gunicorn graceful timeout |
| 5 | Health check fails because of `ALLOWED_HOSTS` | The check calls `localhost`, which must be in `DJANGO_ALLOWED_HOSTS` | Send an allowed Host header, or exempt `/healthz/` |
| 6 | Long migration locks tables | Postgres DDL can block reads and writes during the deploy | Keep migrations small; run backfills separately; set `lock_timeout` |
| 7 | Static files out of sync with running code | `collectstatic` overwrites the shared `static_volume` in place | Add new files before removing old; switch to hashed filenames later |
| 8 | Two deploys run at once | Both would migrate and scale at the same time | `flock` in `deploy.sh` |
| 9 | Compose version differences | `--scale --no-recreate` and health conditions need Compose v2 | Require Compose v2 and check the version in the script |
| 10 | Dev `entrypoint.sh` wipes the database | It runs `flush` on every start | Never point the dev stack at prod; leave dev as it is |

Riskiest: #1. The old code keeps serving against a schema that was migrated before the switch, and rolling back the image doesn't undo that.
