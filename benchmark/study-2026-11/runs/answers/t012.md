## What the code has today

This is the Flask Mega-Tutorial microblog app at Chapter 23. These parts matter for this change:

- **Followers:** the followers table and the `User.following` relationship are in `app/models.py`. `User.following_posts()` at `app/models.py:161` returns the user's **own** posts mixed in with the posts of people they follow.
- **Background jobs:** RQ queue `microblog-tasks`, set up in `app/__init__.py:44`. A worker runs from the Procfile and from `deployment/supervisor/microblog-tasks.conf`.
- **Email:** `send_email(..., sync=False)` in `app/email.py` sends from a separate thread by default. The existing example of a job that sends email is `export_posts` in `app/tasks.py`. It is tied to one user through `launch_task`/`Task` rows and in-app notifications.
- **Missing pieces:** nothing schedules jobs (RQ has no cron), there's no email preference or unsubscribe, there's no email verification, and the user's language isn't stored. `SERVER_NAME` is optional, and the email templates only build links when a web request is in progress.

## Ways this could go wrong (before planning)

1. It never sends, because nothing triggers a weekly run.
2. It sends twice, because two schedulers run, a job is retried, or a crash happens partway through.
3. The digest includes the user's own posts, because the code reuses `following_posts()`.
4. Users get email they never asked for and can't stop. There's no opt-out and no `List-Unsubscribe` header.
5. Mail goes to unverified addresses. Anyone can register with someone else's email, and a weekly mailing makes that worse.
6. Links in the email break or throw errors because no web request is in progress and `SERVER_NAME` isn't set.
7. One job loops over every user, hits RQ's default timeout of about 180 s, and stops partway through.
8. Email sent from a thread is lost when the worker process exits, so it has to use `sync=True`.
9. Posts are missed or counted twice at the week boundaries. `Post.timestamp` is stored without a timezone on SQLite and compared with timezone-aware datetimes.
10. Users with nothing new get an empty digest. Very active follow lists produce huge emails.
11. Reusing `launch_task`/`_set_task_progress` fills the database with `Task` rows and creates in-app notification noise.
12. Running it in dev or tests sends real email, because `MAIL_SERVER` is only an environment variable.

## Assumptions (non-interactive)

- "New posts" means posts by people the user follows created since their last digest (or the last 7 days if they've never had one). Their own posts aren't included.
- Opt-out: existing and new users are subscribed by default. Every email has a one-click unsubscribe link, and the profile page has a checkbox.
- Users with no new posts get no email. Each digest shows at most 20 posts (`DIGEST_MAX_POSTS`) plus a line like "and N more".
- The schedule is set outside the app: system cron, Heroku Scheduler, or a supervisor timer runs a CLI command weekly. I'm not adding an `rq-scheduler` dependency.
- Emails are in English or the default locale, since the user's language isn't stored.

## Plan

1. **Model and migration** (`app/models.py`, new migration in `migrations/versions/`):
   - Add `User.digest_enabled` (bool, `server_default=true`) and `User.last_digest_sent` (datetime, nullable).
   - Add a method `User.digest_posts(since, until)`: join the followers table on `followed_id`, filter `follower_id == self.id`, filter `since < Post.timestamp <= until`, order newest first. It doesn't include the user's own posts.
2. **Jobs** (`app/tasks.py`):
   - `send_weekly_digest(user_id, until_iso)` handles one user and is idempotent. It skips the user if they've opted out or if `last_digest_sent >= until`. If there are posts, it renders and sends with `sync=True` and a `List-Unsubscribe` header. Then it sets `last_digest_sent = until` and commits.
   - This job does **not** use `launch_task` or `_set_task_progress`.
3. **Trigger** (`app/cli.py`): add `flask digest send [--dry-run] [--user ID]`. It fixes one `until` timestamp for the run, pages through users who have `digest_enabled` set, and enqueues one job per user with an explicit `job_timeout`.
4. **Unsubscribe:**
   - A signed token made the same way as `get_reset_password_token`, but with a long expiry and its own claim name.
   - A route `main.unsubscribe_digest`.
   - A checkbox in `EditProfileForm` (`app/main/forms.py`, `edit_profile.html`).
5. **Templates:** `app/templates/email/digest.txt` and `digest.html`, using `_external=True` links.
6. **Config** (`config.py`): add `DIGEST_MAX_POSTS`. The CLI refuses to run if `SERVER_NAME` is unset.
7. **Deployment:**
   - Add a weekly cron entry, documented next to `deployment/supervisor/`, plus a Heroku Scheduler note.
   - Add any new strings to `messages.po` for translation.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate digests | Overlapping runs or RQ retries; no "already sent" record today | `last_digest_sent` per user, checked against a fixed `until` before sending |
| 2 | Never sent | RQ has no scheduler; nothing runs weekly | External cron calls `flask digest send`; log the run and alert on failure |
| 3 | Unwanted email, no opt-out | No preference field or unsubscribe exists | `digest_enabled` + one-click signed link + `List-Unsubscribe` header |
| 4 | Mailing unverified addresses | Signup never verifies email ownership | Announce first; consider verifying email or only mailing active users |
| 5 | Own posts included | `following_posts()` merges in the user's own posts | Separate `digest_posts()` query plus a test |
| 6 | Broken links in email | Worker has no web request; `SERVER_NAME` is optional | Require `SERVER_NAME` and build links with `_external=True` |
| 7 | Job timeout / partial run | One loop over all users plus one SMTP call each | One job per user with explicit `job_timeout` |
| 8 | Lost email | `send_email` sends from a thread by default; worker may exit first | `sync=True` |
| 9 | Missed or double-counted posts at boundaries | Timestamps stored without timezone vs. timezone-aware compare | One UTC `until` per run; `(since, until]` window; tests |
| 10 | Real email from dev/tests | Mail settings come only from environment | `MAIL_SUPPRESS_SEND` in tests; `--dry-run` flag |

Riskiest: #1, duplicate digests. A retried or overlapping run emails every user again, and that can't be undone.
