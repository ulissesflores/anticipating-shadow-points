## What's there now
- **User model:** `BaseUser` (`styleguide_example/users/models.py`) has a unique email that is stored lowercased, and `jwt_key` is rotated on logout. There's no email-verified flag and no record of which login provider a user came from.
- **Password login:** `authentication/apis.py` handles session and JWT login with `authenticate()`, matching the email exactly.
- **Google login:** it exists only as a blog demo (`blog_examples/google_login_server_flow/sdk/`). It:
  - decodes the ID token with `verify_signature: False`;
  - never checks `email_verified`, `aud` or `iss`;
  - looks up the user by exact email through `user_list()`, and returns 404 if no user has that email;
  - calls `login()`, which doesn't check `is_active`;
  - sends the raw token and profile back in the response.
- **Dependencies:** `google-auth` and `google-auth-oauthlib` are already in `requirements/base.txt`.

## Ways this could go wrong
1. **Pre-hijack takeover.** Password signup doesn't verify the email. An attacker can register `victim@gmail.com` with a password, and when the real owner later signs in with Google, both end up sharing one account.
2. **Forged or reused ID tokens.** The code skips the signature and audience checks. A token issued for another app, or a tampered one, could be accepted.
3. **Unverified Google email.** If `email_verified` isn't checked, someone could link to an address they don't own.
4. **Email is the wrong long-term key.** Google emails can change and be reused. Matching on email at every login, instead of Google's permanent user ID (the `sub` claim), can send a login to the wrong account.
5. **Case mismatch.** The exact-match lookup misses `Foo@Gmail.com` against the stored `foo@gmail.com`. That creates a duplicate user or hits an IntegrityError.
6. **Race on first Google login.** Two callbacks at once can both try to create the user, and the unique constraint turns one into a 500.
7. **Deactivated users get in.** `login()` doesn't check `is_active`, so the Google path would let them in.
8. **Google-only users can't set a password.** Their password is unusable and there's no endpoint to set one. Adding one without asking them to confirm who they are makes a stolen session permanent.
9. **Old sessions survive a link.** After an automatic link, sessions or JWTs created with the attacker's password stay valid.
10. **Leaks and enumeration.** The demo returns tokens and profile data, and its "user with email X not found" error reveals which emails have accounts.

## Assumptions (non-interactive)
- A Google sign-in with no matching account creates a new user with an unusable password.
- Linking is automatic, but only when Google says the email is verified.
- The first Google login counts as proof the user owns the email.
- Google login creates a session, like the existing session login. JWT can be added the same way later.
- The blog demo stays as it is. The production flow goes in the `authentication` app.

## Plan
1. **Model** (`authentication/models.py` plus a migration, as the app has no migrations yet):
   - Add `UserIdentity(user FK, provider, subject, email_at_link, created_at)`, with `unique(provider, subject)`.
   - Add `email_verified_at` (nullable) to `BaseUser` in a new users migration, `0004`.
2. **Token verification** (`authentication/google.py`):
   - Reuse `GoogleSdkLoginFlowService` for the authorization URL and the code exchange. Import it, or move it if keeping it under `blog_examples` feels wrong.
   - Replace `decode_id_token` with `google.oauth2.id_token.verify_oauth2_token(token, Request(), audience=settings.GOOGLE_OAUTH2_CLIENT_ID)`.
   - Reject the token unless `email_verified` is true.
3. **Service `google_login_resolve_user(claims)`** in `authentication/services.py`, inside `transaction.atomic`:
   1. Look up `UserIdentity` by `("google", sub)`. If found, return that user.
   2. Otherwise run `BaseUser.objects.select_for_update().filter(email__iexact=email)`. If a user matches:
      - create the identity link;
      - if `email_verified_at` is empty, call `set_unusable_password()`, rotate `jwt_key` and delete that user's sessions (this closes risks 1 and 9);
      - set `email_verified_at`.
   3. Otherwise create the user with `user_create(email=email.lower(), password=None)` plus the identity. Catch `IntegrityError` and retry the lookup once.
   4. Refuse if `not user.is_active`.
4. **APIs** (`authentication/apis.py` and `urls.py`):
   - `google/redirect/` and `google/callback/`, keeping the existing state check in the session. The callback calls the service and `login()`, then returns `user_get_login_data` only, with a generic error message on failure.
   - `password/set/` (requires login). If the user already has a usable password, it requires the current one. Otherwise it requires a Google login in the last N minutes (timestamp stored in the session). It uses `validate_password`.
5. **Password login:** switch the lookup to case-insensitive. Keep the generic 400 when someone tries a password on a Google-only account.
6. **Tests** (`authentication/tests/`), with Google's `verify_oauth2_token` and token exchange mocked:
   - new-user creation;
   - linking to an existing password account, which kills the old password and sessions;
   - a repeat login by `sub` after the Google email changes;
   - rejection when `email_verified` is false;
   - a mixed-case email;
   - an inactive user;
   - the concurrent-create path;
   - setting a password, both with and without a recent re-authentication.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Pre-hijack takeover | Password signup never verifies the email | When Google first links an unverified account, wipe the password, rotate `jwt_key` and delete sessions |
| 2 | Forged or reused ID token | Demo uses `verify_signature: False` and doesn't check audience | `verify_oauth2_token` with `audience=CLIENT_ID` |
| 3 | Unverified Google email links an account | No `email_verified` check | Reject unless the claim is true |
| 4 | Email changes or gets reused | Lookup is by email only | Store `sub` in `UserIdentity`; look up by `sub` first |
| 5 | Case mismatch creates a duplicate | `user_list` filter is an exact match | Use `email__iexact` and lowercase on write |
| 6 | First-login race causes a 500 | Unique email plus two callbacks at once | `select_for_update`, catch `IntegrityError` and retry |
| 7 | Inactive users get in | `login()` skips the `is_active` check | Check `is_active` explicitly in the service |
| 8 | Stolen session sets a password | Google-only users have no password to confirm | Require a recent Google login or the current password |
| 9 | Attacker's sessions survive the link | Sessions and JWTs aren't revoked | Flush sessions and rotate `jwt_key` on link |
| 10 | Data leak and account enumeration | Demo returns tokens and "email not found" | Return only `user_get_login_data`; generic errors |

Riskiest: #1, the pre-hijack takeover. Because signup never verifies email ownership, linking by email can hand the real owner's Google login to an account an attacker already controls.
