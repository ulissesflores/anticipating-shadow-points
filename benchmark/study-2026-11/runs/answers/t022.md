This is a plan for adding a weekly email digest to the Microblog app. Nothing has been edited apart from the plan file at `claude-home/plans/send-every-user-a-serene-river.md`.

## What the app already has
- **Follows:** a `followers` table, plus `User.following_posts()` at `app/models.py:166`. That query also returns the user's own posts, so the digest can't use it unchanged.
- **Background jobs:** an RQ queue (`app.task_queue`, set up in `app/__init__.py:44`), tasks in `app/tasks.py` (`export_posts` is the model to copy), and a `worker` process in `Procfile` and supervisor.
- **Email:** `send_email(..., sync=True)` in `app/email.py`, with emails rendered from templates in `app/templates/email/*.{txt,html}`.
- **Missing:** nothing runs on a schedule, and users have no email preferences.

## Assumptions
- "New posts" means posts written since that user's last digest, or in the last 7 days for a first digest. The user's own posts are left out.
- Users with no new posts get no email.
- Digests are on by default. Users can turn them off in their profile settings, or with a signed unsubscribe link that works without logging in.
- An external cron job (Heroku Scheduler or crontab) starts the weekly run by calling a new `flask digest send` command. No new scheduler library is added.
- Each email lists at most about 20 posts, with a link to the site for the rest. The text is translatable (English and Spanish), like the existing emails.

## Steps
1. **Model and migration:** add `User.digest_enabled` (on by default, with a database-side default so existing users get it) and `User.last_digest_sent`. Add `User.followed_posts_since(since, limit)`: only posts by people the user follows, newer than `since`, newest first, capped at `limit`.
2. **Task:** add `send_weekly_digest(user_id)` in `app/tasks.py`. It skips users who are opted out or have no new posts, then renders the email and sends it with `sync=True`. Only after sending does it set `last_digest_sent` and commit. Errors are logged the same way `export_posts` does it. It must not call `_set_task_progress`, because these jobs have no `Task` row.
3. **Command to queue the jobs:** add a `digest` group in `app/cli.py` with `flask digest send [--dry-run] [--user NAME]`. It goes through opted-in users whose last digest is older than about 6 days, in batches. Each job gets a fixed ID (`digest-{user_id}-{iso_week}`) so running the command twice in a week doesn't queue duplicates.
4. **Templates:** add `email/weekly_digest.txt` and `.html`, with posts grouped by author. Links are absolute (`_external=True`), so the worker needs `SERVER_NAME` set.
5. **Opting out:**
   - Add a checkbox to `EditProfileForm` and handle it in `edit_profile` (`app/main/routes.py:99`).
   - Add an `/unsubscribe/<token>` route. The token is a JWT signed like the password-reset token (`app/models.py:181`), marked for this one purpose.
   - Add an optional `extra_headers` argument to `send_email` so digests can carry a `List-Unsubscribe` header. Existing callers are unaffected.
6. **Config:** add `DIGEST_MAX_POSTS` and a `DIGEST_ENABLED` switch to turn the feature off.
7. **Deployment and translations:** document the cron line `0 8 * * MON flask digest send` in the README, and update the Spanish translations with `flask translate update`.

## How to check it works
- **Unit tests** in `tests.py`:
  - `followed_posts_since` leaves out the user's own posts and posts by people they don't follow, and respects the time window and the limit.
  - The task, checked with Flask-Mail's `record_messages()`: it sends when there are posts, sends nothing when there are none or the user opted out, updates `last_digest_sent`, and a second run sends nothing.
  - A valid unsubscribe token works and a tampered one is rejected.
- **Manual run:** start a local test mail server (`aiosmtpd`) and `rq worker microblog-tasks`, run `flask digest send --user susan`, and check the email. Run it again and confirm nothing is sent.
- **Migration:** run `flask db upgrade` on copies of an existing SQLite database and a Postgres one, and check that existing users get the default.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate or missed digests | Cron reruns or worker retries; nothing records what was sent today | Update `last_digest_sent` only after sending; fixed job ID per ISO week; skip users sent to in the last 6 days |
| 2 | User's own posts in the digest | `following_posts()` includes the user's own posts (`Author.id == self.id`) | New `followed_posts_since` that only joins on follows; add a test |
| 3 | Links fail or point to the wrong host | Emails are rendered in the RQ worker, outside any web request, so `url_for(_external=True)` needs `SERVER_NAME` | Require `SERVER_NAME` in the worker environment; check it at the start of the command |
| 4 | Slow or crashed weekly run | The existing pattern sends each email synchronously over SMTP from a single worker | One job per user; queue in batches; consider limiting the send rate |
| 5 | Spam complaints or legal exposure | Opt-out mail with no unsubscribe link; existing users never opted in | Signed unsubscribe link plus `List-Unsubscribe` header; profile checkbox; consider announcing it first |
| 6 | Migration fails on existing rows | A new required boolean without a database default breaks on SQLite and Postgres | Use `server_default=sa.true()`; test the upgrade on a copy of the database |
| 7 | Nothing ever triggers the run | The project has no scheduler; it's easy to forget the cron entry in Docker, Heroku or supervisor | Document it; add it to the deploy configs; log the time of each run |
| 8 | Slow queries for large accounts | Joins over follows and posts for every user each week | `Post.timestamp` and `user_id` are already indexed; cap the result with `LIMIT` |
| 9 | Unsubscribe token misuse | A token that never expires could be replayed or reused for another purpose | Add a purpose claim to the JWT; the token only sets the flag to off |

Riskiest: #1 — duplicate or missed digests, since a retried job or a re-run cron would email every user twice, or a failure could silently skip a week.
