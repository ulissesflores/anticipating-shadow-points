I've written and checked a plan for letting one account sign in with both a password and Google; I stopped after Phase 6 as asked and edited no repo files. The plan is at `<config>/plans/standard-let-a-user-squishy-sutherland.md`. An independent reviewer read it and returned **REVISE** with 11 issues; rev 2 addresses all of them.

I researched only the codebase. I ran no web search, and the project has no lessons file (`CLAUDE.md` is absent).

## What the code does today
- **Google login is a blog example.** It lives in `styleguide_example/blog_examples/google_login_server_flow/{raw,sdk}/apis.py`. It decodes Google's identity token **without verifying it** (`raw/service.py:30`) and ignores whether Google has verified the email.
- **The email lookup is exact and case-sensitive** (`user_list(filters={"email": ...})`). The flow also never checks `is_active` before calling `login()`, and an unknown email returns 404 with the email in the message.
- **Anyone can create a password account for any email.** `UserCreateApi` (`users/apis.py:63`) needs no login and never verifies the address. This is why matching on email alone is unsafe.
- **Admin 2FA still applies.** It is checked on every admin request (`custom_admin/sites.py:41`), so it doesn't matter how the session was created.

## Assumptions (stated instead of asking)
1. The email match only finds the candidate account. After the first link, the account is found by Google's stable user ID (`sub`), so later email changes don't break or move it.
2. If the account has a password, the link only completes after the user types that password once. Accounts without a password link automatically, but only for `@gmail.com` addresses or Google Workspace accounts (tokens with an `hd` claim).
3. No accounts are created automatically from Google. JWT login, unlinking, and "set a password for a Google-only user" are out of scope.
4. The callback URLs stay the same, so Google Cloud Console needs no changes.

## Plan (rev 2)
1. **D01 – link table:** a new `UserSocialIdentity` model storing the user, the provider and Google's user ID, unique per provider and ID and per user and provider. The migration only adds a table, and the model is registered in admin.
2. **D02 – token verification:** verify the token with `google.oauth2.id_token.verify_oauth2_token`, checking audience, issuer and expiry with a 10-second clock allowance set explicitly. Google's certificates are cached in memory with a 5-second fetch timeout. Tokens without `email_verified` are rejected. All four Google views use this, including the two that aren't routed today.
3. **D03 – account lookup service:** `auth_google_resolve_user` looks up the Google ID first, then the email case-insensitively. It then either links and logs in, returns "confirmation needed", or returns not found. Two accounts matching the same email give 409. Two simultaneous link attempts can't create duplicates or a server error.
4. **D04 – callbacks:** inactive users get 403. When confirmation is needed, the callback returns 409 with a one-time code and saves a pending link in the session for 10 minutes. Responses no longer echo the raw Google token, and the 404 no longer includes the email.
5. **D05 – confirm endpoint:** `POST api/auth/google/link/confirm/` takes the password and the one-time code. It is rate-limited per IP (5/min), and after 5 wrong passwords linking is locked for that user for an hour.
6. **D06 / D07:** a full test suite (forged, expired, wrong-audience and wrong-issuer tokens; inactive user; expired pending link; 6th attempt blocked; login still changes the session key; admin 2FA still enforced; password login unchanged), plus mypy, a migration check, and a README note.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Someone takes over a victim's account before the victim ever signs in | Anyone can sign up any email via the public `UserCreateApi`, with no verification | Password confirmation before linking; require Google's `email_verified` |
| 2 | Forged Google token | The blog flows decode the token with the signature check turned off | `verify_oauth2_token` with audience, issuer and expiry checks |
| 3 | Rate limit doesn't hold | No throttle rates are configured; the cache is per process outside tests; the confirm endpoint needs no login | Configure the rate, use a shared cache, and count failed attempts per user |
| 4 | `email_verified` is weak for non-Gmail Google accounts | Google only checked those emails when the account was created | Auto-link only for Gmail or Workspace accounts; everyone else confirms |
| 5 | Disabled user signs in through Google | `login()` doesn't check `is_active` | Check it explicitly, with a test |
| 6 | Cross-site request forgery on the confirm endpoint | DRF views skip CSRF checks, and no authentication classes are set | One-time code from the 409, compared in constant time |
| 7 | Case mismatch or duplicate emails | The current lookup is exact; emails were only lowercased when created | Case-insensitive lookup; duplicates give 409, never a silent pick |
| 8 | Duplicate link from two requests at once | A double callback creates the link twice | Unique constraints; catch the conflict inside a nested transaction |
| 9 | Google certificate fetch fails or is slow | google-auth re-downloads the certificates on every call | Cached session with a 5-second timeout; failure returns 503 |
| 10 | Callback response changes break callers | The token is no longer echoed back, and 409 is a new status | Document it (these are example endpoints) |

Riskiest: #1, takeover before the victim signs in. Signup is public and never verifies the email, so linking on an email match alone would let an attacker plant an account that the victim's Google login then joins.
