Here's the plan. I haven't edited any repo files; the full plan is at `claude-home/plans/make-ky-retry-post-parsed-muffin.md`.

**Why POST and PATCH aren't retried today:** `retry.methods` defaults to `get, put, head, delete, options, trace, query` (`source/utils/normalize.ts:17`). The method check in `source/core/Ky.ts:703` rejects anything else before Ky even looks at what kind of error happened.

**Main design choice:** don't just add `post` and `patch` to `retry.methods`. That one list controls every reason to retry, so POST would also be retried on 429, 5xx and 408 responses. That goes beyond what you asked for and would repeat work the server has already done. Instead:

1. **New option `retry.networkErrorMethods`**, defaulting to `['post', 'patch']`, in `source/types/retry.ts`. Methods in this list are retried only when `isNetworkError(error)` is true. Setting it to `[]` turns the new behaviour off.
2. **Validation** in `normalize.ts`: add the option to the existing array checks so that `null`, non-arrays and non-strings throw a `TypeError` that names `retry.networkErrorMethods`. There's no `null` fallback, as `AGENTS.md` requires. Entries go through `normalizeRetryMethod`, like `methods` does.
3. **Split the method check** in `Ky.ts:702-705`:
   - Methods in `methods` keep today's behaviour.
   - Methods in `networkErrorMethods` continue only when the error is a network error.
   - Anything else throws.

   `shouldRetry` can still return `false` to stop a retry. On this path, returning `true` can't make a non-network error retriable.
4. **Types and hooks:** add a mutable version to `MutableRetryOptions`, and make sure the array is copied per request and replaced (not merged) on `extend`, the same as `methods`.
5. **Docs:** update the readme retry section and the JSDoc in `options.ts:186`. Add a clear warning that a network error doesn't prove the server never processed the request, and recommend sending an `Idempotency-Key` header.
6. **Release:** this changes behaviour for every existing POST/PATCH caller, so it should be 3.0.0 with a migration note.

**Tests:**
- Keep the existing "not on POST" test (`test/retry.ts:322`) for HTTP 500.
- Add network-failure retry tests for POST and PATCH.
- Check that POST with 5xx, 429 or a timeout gets exactly one attempt.
- Cover the `[]` opt-out, `shouldRetry` stopping a retry, and rejection of `null` and other bad values.
- Check that JSON, FormData and stream request bodies are sent again intact.
- Add `extend`/`replaceOption` merge tests and type tests in `test-d`.
- Run `npm test` and the browser tests.

**Assumptions:**
- "Network fails" means `isNetworkError()`, not timeouts or 5xx responses.
- The retry limit (2), backoff and `totalTimeout` stay unchanged.
- A new option is better than changing what `methods` means for existing configs.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Duplicate side effects (double orders or payments) | Some errors that count as network errors (`terminated`, `Network connection lost`) can happen after the server got the request; on mobile, dropped responses are common | Document the risk loudly, recommend an `Idempotency-Key` header, make opting out easy |
| 2 | Silent behaviour change for current users | Every POST/PATCH caller gets retries without changing anything | Release as 3.0.0 with a migration note |
| 3 | Retries spreading to status codes | Adding to `methods` would also retry POST on 5xx and 429 | Separate `networkErrorMethods` that only applies to network errors |
| 4 | `shouldRetry: true` making POST retry on 500 | It currently overrides the default checks for allowed methods | On this path, `true` can't make a non-network error retriable |
| 5 | Stream bodies not re-sent correctly | Retries depend on `request.clone()` (`Ky.ts:1225`) splitting the stream | Tests for stream, FormData and JSON bodies on retry |
| 6 | `null` accepted quietly | `AGENTS.md` forbids `null` fallbacks | Validation loop throws a `TypeError` that names the option |
| 7 | Wrong merge on `extend` or in hooks | The new array must copy and replace like `methods` | Mirror the merge tests in `test/retry.ts:1443-1602` |
| 8 | Network errors not recognised on some platforms | Detection relies on matching error messages per runtime | Retries only run when detection succeeds, so the failure is just a missed retry |
| 9 | Extra load during outages | Up to 3 POSTs per action from many mobile clients | Keep the backoff; document `limit` and `totalTimeout` |

Riskiest: #1. Automatically retrying non-idempotent POST/PATCH after an ambiguous network failure can repeat real-world side effects like a second order or charge.
