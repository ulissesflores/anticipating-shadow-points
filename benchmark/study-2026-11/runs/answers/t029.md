I've written the plan to `claude-home/plans/let-a-user-sign-luminous-tarjan.md` and changed no repo files.

**What exists today.** Password login works through `UserSessionLoginApi` and `UserJwtLoginApi` in `authentication/apis.py`. Google login exists only as a blog example, in `blog_examples/google_login_server_flow/{sdk,raw}/apis.py`. That example has four gaps:
- It decodes the Google ID token without checking its signature.
- It ignores whether Google has verified the email (`email_verified`).
- It matches the email exactly, so case differences fail.
- It returns a 404 when no user matches, and stores no link to the Google identity.

**Assumptions** (non-interactive, so I didn't ask):
1. "Same account" means one row in the user table (`BaseUser`). Google is an extra identity attached to it, not a second user.
2. The first Google login matches the email, ignoring case, and only if Google says the email is verified. After that, the link uses Google's stable user ID (`sub`), so a later Gmail address change still works.
3. A Google login with no matching user creates a user with no usable password. A "set password" flow is out of scope. If you'd rather keep today's 404, it's a one-line switch.
4. Only the session-based login flow is in scope. The SDK and raw Google flows both get the same fix.
5. The repo has no public signup or email verification, so only users created by admins or internal code can be hijacked today.

**Plan:**
1. **Model:** add `UserGoogleIdentity` in `users/models.py`, with `user` (link to the user), `google_sub` (unique) and `email_at_link`. Migration `users/migrations/0004_usergoogleidentity.py`.
2. **Check the token properly:** in `sdk/services.py` and `raw/service.py`, replace the unchecked `jwt.decode` with `google.oauth2.id_token.verify_oauth2_token(..., audience=client_id)`. The `google-auth` package is already installed.
3. **Linking service:** add `auth_google_login_get_user(*, id_token_payload)` in `authentication/services.py`, inside one database transaction. It:
   - looks the user up by `sub` first;
   - otherwise requires a verified email and finds the user by email (ignoring case), locking the row so two logins can't link at once;
   - otherwise creates the user;
   - saves the link, rejects inactive users, and on a new link calls `auth_logout` to cancel tokens issued before the link.
4. **APIs:** in both `GoogleLoginApi` classes, replace the user lookup and 404 with the new service. Then `login(request, user)` and return `user_get_login_data` plus the session key, the same response as password login.
5. **Admin:** show a user's Google links in `users/admin.py` so support can remove one.
6. **Tests:**
   - Service tests: linking a password user, password still working afterwards, lookup by `sub` after an email change, unverified email rejected, case-insensitive match, creating a new user, inactive user rejected, `jwt_key` rotated on link.
   - API test: mock the Google calls and confirm the session works against `/api/auth/me/`.

**Verification:**
- Run `makemigrations --check` and `pytest`.
- Then by hand:
  1. Create a user with a password.
  2. Sign in through `/api/google-oauth2/login/sdk/redirect/` with the same Gmail address.
  3. Sign in through `/api/auth/session/login/` with the password.
  4. Confirm both give the same user ID.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Account pre-hijack: someone creates a password account under the victim's email before the victim uses Google | No email verification at signup, and linking by email trusts the old account | Link only verified Google emails; rotate `jwt_key` and the session on link; check signup email before any public signup ships |
| 2 | Forged or mis-targeted ID token | Current code uses `verify_signature: False` | `verify_oauth2_token` with the app's client ID as audience |
| 3 | Unverified Google email used to take over an account | `email_verified` is never read today | Reject the login when it's false |
| 4 | Case mismatch makes a duplicate user or a 404 | `create_user` lowercases emails, but the Google lookup matches exactly | Lowercase the email and match ignoring case |
| 5 | Two simultaneous first logins create two links or users | No locking today | One transaction, row lock, unique `google_sub` |
| 6 | Changed Gmail address no longer reaches the account | Matching is by email only | Match by `sub` after the first link |
| 7 | Google-created users can't use password login | They have no usable password and there's no reset or set-password API | Document it; add set-password later or keep the 404 |
| 8 | Old JWTs survive the link | Tokens are tied to `jwt_key` | Call `auth_logout` (rotate `jwt_key`) on a new link |
| 9 | Inactive users get in through Google | `login()` doesn't check `is_active` here | Check it in the service |
| 10 | Blog-example code becomes production login | It lives in `blog_examples/` and the raw and SDK flows differ | Point both flows at the one service; consider moving it to `authentication/` |

Riskiest: #1. Linking by email lets whoever registered that email with a password first share the Google user's account.
