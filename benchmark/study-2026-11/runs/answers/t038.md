## What's there now
- **`docker-compose.prod.yml`**: one `web` container (gunicorn on 8000), `db` (Postgres 15) and `nginx` (port 1337 → `web:8000`). There's no healthcheck, and `depends_on` only waits for the container to start, not for it to be ready.
- **`app/entrypoint.prod.sh`**: waits for Postgres, then runs the command. It doesn't run migrations or `collectstatic`.
- **`app/entrypoint.sh` (dev)**: runs `flush --no-input` and then `migrate`. Copying it into production would wipe the database on every deploy.
- **`nginx/nginx.conf`**: a static `upstream { server web:8000; }`. nginx looks up that name once at startup, so a replacement container with a new IP gets 502s until nginx reloads.
- Today, `docker compose up -d --build` stops the old `web` and then starts the new one, so the site goes down during every deploy.

## Ways this could go wrong (before planning)
1. **Concurrent migrations.** If `migrate` runs in the entrypoint and two containers start together, Django on Postgres doesn't lock against parallel runs.
2. **Old code against the new schema.** During the overlap, the old container serves traffic on the migrated database. Dropping or renaming a column breaks it.
3. **Postgres locks.** `ALTER TABLE` takes an exclusive lock. On a busy table, requests queue behind it, which is an outage even though no container restarted.
4. **A failed migration still cuts over.** If the deploy doesn't stop on a non-zero exit, traffic moves to a container whose code expects a schema that isn't there.
5. **nginx DNS caching** (see above). Traffic keeps going to a dead IP.
6. **No readiness signal.** Traffic reaches gunicorn before it has booted.
7. **Requests killed mid-flight.** Docker's default 10 s stop timeout plus SIGKILL cuts off long uploads.
8. **Stale or missing static files.** Nothing runs `collectstatic`, and the shared `static_volume` keeps old assets.
9. **No rollback target.** Images are built in place and never tagged, so there's nothing to switch back to.
10. **The build itself may fail.** `python:3.11.4-slim-buster` is on archived Debian buster, so `apt-get update` can fail at build time. A failed build blocks the deploy but doesn't take the site down.

## Assumptions
- One Docker host running `docker compose`, no Kubernetes or Swarm. Deploys run from a script on that host or from CI over SSH.
- Postgres stays in compose. One `web` replica normally, with two briefly during a deploy.
- "Zero downtime" means no failed requests through nginx, not "no slow requests."
- From now on, migrations follow expand/contract: add things first, remove them a release later.

## Plan
1. **Add `deploy.sh`** (new). It runs in order and stops at the first failure (`set -euo pipefail`):
   1. Build and tag the image as `web:<git-sha>`. Keep the previous tag for rollback.
   2. Run `docker compose run --rm web python manage.py migrate --noinput` once, as a one-off job before any new container takes traffic. This avoids the race with several replicas starting. Add a `lock_timeout` (e.g. via `PGOPTIONS='-c lock_timeout=5s'`) so a blocked `ALTER` fails fast instead of stalling the site.
   3. Run `collectstatic --noinput` the same way, into `static_volume`.
   4. Roll out (step 4 below).
   - Don't put `migrate` in `entrypoint.prod.sh`, and never reuse `entrypoint.sh` in production because of `flush`.
2. **Health check.** Add a tiny `/healthz` view in `hello_django/urls.py` that does a DB `SELECT 1`. Add a compose `healthcheck` on `web` that calls it with `python -c "urllib…"`, since the slim image has no curl. Set `start_period` to cover gunicorn's boot time.
3. **nginx.** Replace the static upstream with `resolver 127.0.0.11 valid=5s;`, `set $app http://web:8000;` and `proxy_pass $app;`. Add `proxy_next_upstream error timeout http_502;` so a request that hits a stopping container gets retried on the other one.
4. **Rollout.** Run `docker compose up -d --no-deps --no-recreate --scale web=2 web`, which keeps the old container and adds a new one. Poll until the new container is `healthy`, then remove the old one and scale back to 1. The `docker rollout` plugin does exactly this and could replace the hand-written step. `web` uses `expose`, not `ports`, so scaling to two works.
5. **Graceful shutdown.** Set `stop_grace_period: 30s` on `web` and `--graceful-timeout 25` on gunicorn, so the old container finishes its requests when it gets SIGTERM.
6. **Rollback.** If the health check fails, remove the new container and keep the old one. Migrations aren't rolled back automatically; with expand-only migrations, the old code still works against the new schema.
7. **Migration policy.** Write a short note in the README: never drop or rename in the same release as the code change; add columns as nullable or with a default; and since this is Django 4.2, prefer `AddIndexConcurrently` for indexes.
8. **Base image.** Move from `slim-buster` to `slim-bookworm` so builds keep working.

Files to change: `docker-compose.prod.yml`, `nginx/nginx.conf`, `app/hello_django/urls.py` (plus a small view), `app/Dockerfile.prod`, a new `deploy.sh`, and `README.md`.

**Unrelated bug found along the way:** in `settings.py`, `DEBUG = bool(os.environ.get("DEBUG", default=0))` evaluates `bool("0")`, which is `True`. Production is running with DEBUG on.

## Verification
- While `deploy.sh` runs, run `while true; do curl -s -o /dev/null -w '%{http_code}\n' localhost:1337/; done` and confirm it never prints anything other than 200.
- Deploy a release that adds a nullable column. The migration should apply once, and both old and new containers should serve during the overlap.
- Deploy a release with a deliberately broken migration. The script should exit non-zero, the old container should keep serving, and no new container should start.
- Deploy an image whose `/healthz` fails. The rollout should abort and the old container should stay up.
- Upload a large file during a deploy and confirm it isn't cut off.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Migration breaks old code during overlap | Old and new containers share one DB | Expand/contract migrations; drops a release later |
| 2 | Dev `flush` ends up in production | `entrypoint.sh` wipes the DB on start | Migrate only in `deploy.sh`; never reuse dev entrypoint |
| 3 | Concurrent `migrate` runs | Entrypoint migrations run once per replica | One-off `compose run` before rollout |
| 4 | Table lock stalls the site | `ALTER TABLE` takes an exclusive lock | `lock_timeout`; concurrent indexes |
| 5 | nginx sends traffic to a dead IP | Static `upstream web:8000` resolved once | `resolver 127.0.0.11` plus variable `proxy_pass` |
| 6 | Traffic before the app is ready | No healthcheck; `depends_on` ignores readiness | `/healthz` plus compose healthcheck gate |
| 7 | Cutover after a failed migration | No stop-on-error deploy step | `set -e`; migrate before scaling up |
| 8 | In-flight requests killed | 10 s default stop, then SIGKILL | `stop_grace_period`; gunicorn graceful timeout |
| 9 | No way back | Untagged in-place builds | Tag by git SHA; keep old container until healthy |
| 10 | Build fails | `slim-buster` apt repos archived | Move to `slim-bookworm` |

Riskiest: #1, a migration that isn't backward-compatible. It's the one failure that the health checks and the rollout won't catch, and new code can't undo a schema change it depends on.
