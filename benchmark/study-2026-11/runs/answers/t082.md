I've written the plan to `claude-home/plans/allow-an-article-to-rippling-orbit.md` and changed no repo files. The approach is purely additive: `Article.authorId`/`author` stays as the primary author (the owner), and co-authors are a new optional relation. No URL changes. The only response change is one new field, `coAuthors: Profile[]`, which is `[]` by default.

**Assumptions**
- "Current clients" means RealWorld-spec frontends, which ignore JSON keys they don't know.
- Co-authors can edit an article. Only the owner can delete it or manage co-authors.
- There's no ownership transfer, and co-author order doesn't matter.

**Steps**
1. **Schema:** add a join table, `ArticleCoAuthor(articleId, userId, createdAt)`, with a composite primary key and cascade deletes. The migration only creates this table: no backfill, and `Article` doesn't change.
2. **One shared query include:** `article.service.ts` repeats the same `include` block 6 times. Merge them into one shared `articleInclude` that also loads `coAuthors`. Then `article.mapper.ts` builds `coAuthors` with the existing `author.mapper.ts`.
3. **Favorite / unfavorite:** `favoriteArticle` and `unfavoriteArticle` (`article.service.ts:597`, `:643`) return the raw database row instead of going through the mapper. Switch them to `articleMapper`. Otherwise the new relation would go out as raw rows. This also fixes a leak that exists today: `favoritedBy: true` returns full User rows, including password hashes.
4. **Edit rights:** add a `canEdit` check (owner or co-author) and use it in `updateArticle`. Delete stays owner-only.
5. **Slugs:** `updateArticle` rebuilds the slug as `slugify(title)-${callerId}` (`article.service.ts:317`). If a co-author changed the title, their id would end up in the URL. Build it from the article's `authorId` instead.
6. **New endpoints:** `POST /articles/:slug/coauthors` and `DELETE /articles/:slug/coauthors/:username`. Also accept an optional `coAuthors` list of usernames on article create.
7. **Listing:** co-authors can see their non-demo articles (add an `OR` to the visibility filter). `?author=` keeps matching the primary author only, so existing counts and pagination stay the same; add a new `?coauthor=` filter. The feed stays primary-author only for now.
8. **Tests:**
   - Unit tests: mapper returns `[]` by default, a co-author can update, a co-author gets 403 on delete, the slug keeps the owner's id, and favorite responses contain no `password`.
   - e2e: the old response shape still matches.
   - Migration: dry run on a copy of prod data.

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Slugs drift when a co-author edits | The slug suffix is the editor's id (`service.ts:317`) | Build the suffix from the article's `authorId` |
| 2 | Raw rows leak into responses | Favorite/unfavorite return the database row unmapped | Send them through `articleMapper` and test that no `password` appears |
| 3 | Response shape changes for clients | `author` must stay a single object | Only add `coAuthors`, and pin the shape with an e2e test |
| 4 | `?author=` results change | Counts and pagination shift if co-authors start matching | Keep it primary-only and add `?coauthor=` |
| 5 | Co-authors gain too much power | Edit, delete and manage are separate rights today | Use `canEdit` for edits only; delete and manage stay owner-only |
| 6 | Slower queries | Each article now also loads co-authors and their followers | Add an index on `userId` and select only the needed fields |
| 7 | Migration problems | Prod is Postgres with existing data | Additive table only, rehearsed on a copy |
| 8 | Visibility filter changes | The demo/own filter decides what users see | Add co-author access only as an extra `OR` branch, with tests |
| 9 | Copies of the include block drift apart | It's copied 6 times today | Merge into one shared `articleInclude` |

Riskiest: #1. A co-author changing the title would silently change the article's URL and break existing links.
