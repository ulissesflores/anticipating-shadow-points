## What the code does today

- **Admin delete removes items explicitly.** `DELETE /users/{id}` (`users.py`, `delete_user`) runs `delete(Item).where(owner_id == user_id)` and then `session.delete(user)`.
- **Self-delete removes them through cascades.** `DELETE /users/me` runs `session.delete(current_user)`. Both `User.items` (`cascade_delete=True`) and `Item.owner_id` (`ondelete="CASCADE"`) are set to cascade.
- **Logged-in requests only check two things.** `get_current_user` (`deps.py`) looks the user up with `session.get` and checks `is_active`. Access tokens stay valid for 8 days (`ACCESS_TOKEN_EXPIRE_MINUTES`).
- **Email is a unique index.** Signup, admin create, update, password recovery and login all go through `crud.get_user_by_email`.
- **There is no job runner.** No scheduler, cron or worker exists, so nothing can run a purge after 30 days.

## Ways this could go wrong

1. **Items are still removed.** If `delete_user` keeps its explicit item delete, or any path still calls `session.delete(user)`, items vanish. Either one breaks the main requirement.
2. **The cascades fire later.** When the 30 days end and the account is purged for good, the ORM and database cascades delete the items. That contradicts "keeps their items" unless items are moved to another owner or the cascades are changed.
3. **Deleted users keep access.** A token issued before the delete keeps working for up to 8 days unless `get_current_user` rejects deleted users.
4. **Login and reset still work.** `authenticate` and `reset_password` only check `is_active`. A deleted user could log in or reset their password unless every path checks for deletion.
5. **The email can't be reused.** The unique index blocks signing up again with the same email. If uniqueness is relaxed to allow it, restoring the old account can create two live accounts with one email.
6. **Deleted users still show up.** The admin list, `read_user_by_id`, `update_user`, the user count and superuser item listings would all still include deleted users unless they are filtered.
7. **`is_active` gets mixed up with deletion.** Reusing `is_active` as the delete flag makes "deactivated" and "deleted" the same thing. A restore could then reactivate a user an admin had deliberately disabled.
8. **The 30-day window isn't enforced.** Without a job runner, nothing purges expired accounts. The restore endpoint also has to refuse restores after 30 days, with time zones handled correctly (`deleted_at` should be UTC).
9. **The migration is risky.** A new nullable `deleted_at` column is safe. Changing the foreign key's `ondelete` needs a hand-written Alembic migration and a check of what autogenerate produces.
10. **The frontend and tests don't match.** The generated client, `DeleteUser.tsx` wording, the admin "Deleted" view with a Restore button, and the existing delete tests all assume a hard delete.
11. **Concurrent restore and purge.** If an admin restores an account while the purge runs, the restore could report success on an account that was just removed.

## Assumptions (non-interactive run, so I didn't ask)

- **Scope:** both self-delete and admin delete become soft deletes. Only superusers can restore.
- **Items:** they stay in place with their `owner_id`, are hidden from the deleted user, and remain visible to superusers.
- **After 30 days:** the account is purged for good and its items are kept. The default would be to move them to the first superuser, so the cascades never fire. Restore returns 410 after the window.
- **Email:** a deleted user's email stays reserved until the account is purged, so restoring can't create a duplicate.
- **Purge runner:** a CLI script (`app/scripts/purge_deleted_users.py`) run by cron or a compose one-shot. No new scheduler dependency.
- **Superusers:** the existing rule that superusers can't delete themselves stays.

## Plan

1. **Model and migration.** Add `deleted_at: datetime | None` (indexed) to `User` in `models.py`. Add `deleted_at` to `UserPublic` for the admin view. Write an Alembic migration that adds the column.
2. **Delete routes.** Replace the hard deletes in `delete_user_me` and `delete_user` with `user.deleted_at = now(UTC)` and remove the item delete. Keep the superuser self-delete guard.
3. **Access checks.** In `get_current_user`, return the same response for a deleted user as for a missing one (404). In `crud.authenticate` and `reset_password`, treat deleted users as if they don't exist, including in password recovery, which still returns its generic message.
4. **Admin endpoints.**
   - `GET /users/` excludes deleted users by default and adds `?include_deleted` or `?deleted_only` for admins.
   - `read_user_by_id` and `update_user` return 404 for deleted users unless the admin asks for them explicitly.
   - Add `POST /users/{id}/restore` (superuser only). It returns 404 if the user doesn't exist or isn't deleted, and 410 if more than 30 days have passed. Otherwise it clears `deleted_at`.
5. **Purge.** Add a `purge_deleted_users` function in `crud` plus a script. It moves items to the first superuser, then hard-deletes users whose `deleted_at` is older than 30 days, in one transaction. It locks each user row (`SELECT … FOR UPDATE`) to avoid racing with a restore.
6. **Frontend.** Regenerate the client. Reword the `DeleteUser` dialog to say the account can be restored within 30 days. Add a deleted filter and a Restore action to the admin users table (`columns.tsx` / `UserActionsMenu.tsx`).
7. **Tests.** Update the delete tests so they check the user is hidden but its row and items remain. Add tests that:
   - an old token is rejected after delete,
   - login and password reset fail for a deleted user,
   - restore works within 30 days and returns 410 after,
   - signing up with the email of a deleted user fails,
   - the purge keeps the items.

## How to verify

- Run `bash scripts/test.sh`, or pytest in the backend container.
- Run the Playwright admin tests.
- Manually: delete a user who owns items, check their old token gets 404, restore them as an admin, then log in again and see the items. Backdate `deleted_at` to more than 30 days ago, run the purge script, and check the items still exist under the new owner.

## Main risks

| # | Risk | Why it bites here | Mitigation |
|---|------|-------------------|------------|
| 1 | Items still deleted | `delete_user` has an explicit `delete(Item)`, and both relationships cascade | Remove that line, never `session.delete(user)` before the purge, test item survival |
| 2 | Purge cascades the items away | `cascade_delete=True` plus FK `ondelete=CASCADE` | Move items to a new owner before the purge, or change the FK in the migration |
| 3 | Deleted user keeps API access | Tokens last 8 days; `get_current_user` only checks `is_active` | Reject `deleted_at` users in `get_current_user` |
| 4 | Login or password reset revives the account | `authenticate` and `reset_password` don't know about deletion | Treat deleted users as missing in `crud` lookups |
| 5 | Email conflicts | Unique index on `email`; restore vs re-signup | Keep the email reserved until purge; test re-signup |
| 6 | Deleted users leak into lists and counts | `read_users`, `read_user_by_id`, `update_user` query everyone | Default filter plus an explicit admin flag |
| 7 | Deactivated and deleted get mixed up | Tempting to reuse `is_active` | Separate `deleted_at` column; restore doesn't touch `is_active` |
| 8 | 30-day window never enforced | No scheduler in the repo | Purge script on cron; restore returns 410 after 30 days |
| 9 | Restore races the purge | Restore and purge run separately | Row lock or conditional update in one transaction |
| 10 | Frontend and tests drift | Generated client and `DeleteUser.tsx` assume a hard delete | Regenerate the client, update the wording, add a Restore UI and tests |

Riskiest: #2, because the database and ORM cascades on `Item.owner_id` will silently delete the user's items when the account is purged after 30 days, breaking "keeps their items" long after the feature looks finished.
