The independent validator returned REVISE with 13 issues; I checked them against the code and they hold. All are folded into the plan, and there was no second validator pass.

**The codebase.** This is the FastAPI + SQLModel + Alembic + React template. Today both delete endpoints remove the user row and every item they own:
- The admin delete (`backend/app/api/routes/users.py:214`) explicitly deletes the items, and the item table's foreign key cascades too.
- Self-delete (`users.py:132`) removes the row the same way.
- The login check (`deps.get_current_user`) only looks at `is_active`. Tokens last 8 days, so without a fix a deleted user's old token keeps working.

**Assumptions I made instead of asking:**
- Both admin delete and self-delete become soft deletes.
- A deleted user is treated as "not found" by login, existing tokens, password recovery and password reset.
- Their items stay untouched and still appear in the admin item list.
- The email stays taken during the 30 days (the unique constraint is unchanged).
- Restore is allowed only before `deleted_at + 30 days` (UTC, configurable); after that it returns 410.
- Permanent deletion after 30 days ships as a script; scheduling it is left to ops.
- `is_active` stays independent of `deleted_at`.

**What the plan builds:**
1. **Model and setting:** a nullable, indexed `deleted_at` column on users and a `USER_SOFT_DELETE_RETENTION_DAYS=30` setting. The normal user response (`UserPublic`) stays unchanged; a separate deleted-user response adds `deleted_at` and `restore_deadline`.
2. **Migration:** a timezone-aware column plus its index. Rolling back refuses if any soft-deleted rows exist, because otherwise it would silently bring those users back.
3. **Data functions:** soft delete, restore and purge. Restore and purge each run as a single conditional statement, and both use the same cutoff time computed in Python so they can't overlap. Login still runs the dummy password check for deleted users, so response timing doesn't reveal them.
4. **Login hardening:** fixed responses for deleted users. Old token → 404, login → 400 "Incorrect email or password", reset → 400 "Invalid token", recovery → the usual generic message with no email sent.
5. **Routes:** both deletes become soft deletes, and the user list and its count skip deleted users. New `GET /users/deleted` and `POST /users/{id}/restore` (200/404/410/403) are admin-only, and editing a deleted user returns 409. The new GET route must be declared before `/{user_id}`, or "deleted" gets parsed as a user ID and fails.
6. **Purge script:** `backend/app/purge_deleted_users.py`, dry-run by default, with `--apply` to delete.
7. **Frontend:** regenerate the API client and change the "permanently deleted" wording in three components. Add a Deleted users tab with a Restore button that refreshes both user lists, plus a Playwright test for delete → appears under Deleted → restore.

**Validator changes that mattered most:** the route-order bug in item 5, making the purge a single statement so it can't race a restore, and the boundary tests. There's no time-freezing library in the project, so those tests backdate `deleted_at` to 29d23h, exactly 30d and 30d+1s instead.

**Deviation:** I skipped the web research for prior art. No lessons file or `CLAUDE.md` exists, so there was nothing to consult there.

| # | Risk | Why it bites here | Mitigation |
|---|---|---|---|
| 1 | Deleted user's token still works | `get_current_user` checks only `is_active`; tokens last 8 days | Reject `deleted_at` in `deps.py`, return 404, add a test |
| 2 | Password reset or recovery brings a deleted user back | `login.py` recovery/reset paths only check `is_active` | Same deleted check; generic reply; no email |
| 3 | Items still hard-deleted | Admin delete explicitly deletes items; the foreign key cascades | Soft-delete the row only; test that items survive both deletes |
| 4 | Signup with a deleted user's email gives a 500 | The email stays unique; a filtered lookup would let the insert fail | Keep `get_user_by_email` unfiltered; regression test |
| 5 | Purge races a restore | Load-then-delete leaves a gap | One conditional DELETE/UPDATE sharing one Python cutoff |
| 6 | Off-by-one or timezone error at day 30 | Mixing naive and aware datetimes; no time-freezing library | Timezone-aware column; backdated boundary tests |
| 7 | `/users/deleted` returns 422 | `/{user_id}` is declared first and catches it | Declare the new route first; test it |
| 8 | Rolling back the migration revives deleted users | Dropping the column erases deletion state | Rollback refuses while deleted rows exist |
| 9 | Admin user lists go stale or drift from the API | One cache key; `UserPublic` change would leak fields | Leave `UserPublic` unchanged; refresh both caches; regenerate the client |
| 10 | Personal data kept forever | No scheduler, so the purge never runs | Ship the purge script; document a cron job as an ops follow-up |

Riskiest: #1. Without the `deps.py` check, a "deleted" user keeps full API access for up to 8 days.
