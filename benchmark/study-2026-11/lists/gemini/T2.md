1. In `app/models.py`, `User.following_posts()` explicitly includes the user's own posts via `Author.id == self.id`; reusing this query directly will erroneously include the recipient's own posts in their digest.
2. In `app/email.py`, `send_email()` defaults to spawning a separate unmanaged background `Thread` for each email (`sync=False`); iterating over all users in a loop will launch hundreds or thousands of threads simultaneously, exhausting system memory and overwhelming the SMTP server.
3. The codebase lacks a recurring task scheduler, as the infrastructure in `Procfile` and `deployment/supervisor/microblog-tasks.conf` only runs a standard `rq worker` for on-demand user tasks; without introducing a scheduler like `rq-scheduler` or cron, there is no mechanism to trigger the digest weekly.
4. Generating absolute URLs for posts and profiles within email templates using `url_for(..., _external=True)` will fail or produce broken links in a background worker because `SERVER_NAME` defaults to `None` in `config.py` and no HTTP request context is active.
5. In `app/models.py`, the `User` model contains no fields for email notification preferences or opt-out tokens; sending unsolicited digests without an unsubscribe mechanism violates CAN-SPAM/GDPR regulations and requires a database migration to track preferences.
6. Localization in `app/__init__.py` determines language via `request.accept_languages` inside `get_locale()`, which is unavailable inside background tasks; rendering localized email templates will fail or default arbitrarily without a stored user language preference.
7. Reusing the post rendering pattern from `app/templates/_post.html` will fail in emails because it relies on `moment(post.timestamp).fromNow()` and client-side JavaScript, which email clients do not execute.
8. Iterating through all users and querying their followed authors' recent posts will produce an O(N) database query bottleneck that will exhaust database connections and exceed the default execution timeout of the single configured RQ worker.
9. Filtering posts using a naive relative window like `datetime.now(timezone.utc) - timedelta(days=7)` without persisting a per-user `last_digest_sent` timestamp will cause posts to be duplicated or skipped whenever scheduled runs drift, fail, or are retried.
10. If emails are sent synchronously (`sync=True`), a single SMTP failure or invalid email address will raise an unhandled exception that aborts the batch job midway, leaving the remaining users unprocessed without a retry tracking mechanism.
