1. In `backend/app/models.py`, `UserBase.email` enforces a strict database-level unique constraint (`Field(unique=True)`). If a user is soft-deleted, their email remains in the table, meaning subsequent registration or signup attempts with that email will fail in `crud.get_user_by_email` or trigger an unhandled database `IntegrityError`.

2. In `backend/app/api/routes/users.py`, the admin `delete_user` endpoint explicitly executes `statement = delete(Item).where(col(Item.owner_id) == user_id)` before deleting the user. If an engineer converts user deletion to a soft delete but overlooks this query, the user's items will still be permanently deleted, directly violating the requirement to preserve them.

3. In `backend/app/models.py` and migration `1a31ce608336`, `Item.owner_id` is defined with `nullable=False` and `ondelete="CASCADE"`. If a soft-deleted user is eventually purged from the database after 30 days while keeping their items, PostgreSQL will cascade-delete those items anyway or throw a foreign key violation unless the column is made nullable or ownership is transferred.

4. In `backend/app/api/deps.py`, `get_current_user` retrieves the user by primary key and only verifies `if not user.is_active`. If soft deletion is introduced with a new timestamp or boolean flag without deactivating the user or updating `get_current_user`, soft-deleted users with valid JWT tokens will remain authenticated until their tokens expire up to 8 days later.

5. The codebase contains two deletion routes in `backend/app/api/routes/users.py`: admin deletion (`delete_user`) and self-deletion (`delete_user_me`). If soft delete is implemented on only one endpoint, the other endpoint will continue performing hard deletes and wiping user records and items inconsistently.

6. In `backend/app/api/routes/users.py`, the `read_users` endpoint executes unfiltered queries for both the total count (`select(func.count()).select_from(User)`) and the retrieved batch (`select(User)`). Without adding filtering for soft-deleted records, deleted accounts will continue to appear in the admin user list and distort pagination counts.

7. Neither `compose.yml` nor the `backend/` application defines any background task worker or scheduler (such as Celery, ARQ, or a cron runner). Without introducing infrastructure to periodically check and permanently purge accounts older than 30 days, expired accounts will remain in a soft-deleted state indefinitely.

8. In `backend/app/api/routes/login.py`, `recover_password` fetches users using `crud.get_user_by_email` without filtering by deletion status. This allows soft-deleted users to request recovery emails and potentially reset their passwords to regain active access without admin intervention.

9. There is currently no restore endpoint in the API or UI, and creating one without validation could allow admins to restore accounts beyond the 30-day cutoff or cause state conflicts if the email address was reused in the interim. It must also be defined whether restoring an account should reinstate `is_active` for users who were explicitly deactivated prior to deletion.

10. Existing unit and integration tests in `backend/tests/api/routes/test_users.py` (such as `test_delete_user_me` and `test_delete_user_super_user`) explicitly query the database after deletion to assert that `result is None`. Modifying deletion behavior without updating these assertions and adding test coverage for item retention and the 30-day restore window will break the test suite in CI.

11. The frontend dialogs in `frontend/src/components/Admin/DeleteUser.tsx` and `frontend/src/components/UserSettings/DeleteConfirmation.tsx` display hardcoded warning text stating that items will be permanently deleted and cannot be undone. Without updating these descriptions, updating the TypeScript client via `openapi-ts`, and adding a restore action in `UserActionsMenu.tsx`, the admin UI will provide no mechanism to restore users and will show contradictory warnings.
