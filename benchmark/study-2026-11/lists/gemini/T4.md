1. Adding `post` and `patch` to `defaultRetryOptions.methods` in `source/utils/normalize.ts` would cause Ky to retry on `retry.statusCodes` (such as 500, 502, 503, and 504) as well as network failures, violating the request to only retry when the network fails. This would re-execute failed server-side mutations for HTTP error responses that should have failed immediately.

2. Because POST and PATCH are non-idempotent methods, retrying on a `NetworkError` introduces duplicate server-side side effects if the connection was interrupted after the server received and processed the initial mutation. Ky has no way of discerning whether a network failure occurred before the request reached the server or after the server began handling it.

3. In `source/core/Ky.ts`, connection drops produce a `NetworkError` whereas request timeouts throw a `TimeoutError`, which is governed separately by `retry.retryOnTimeout` (defaulting to `false`). Flaky mobile connections frequently fail via timeouts, meaning the change would either fail to resolve mobile drops or, if `retryOnTimeout` is broadened, unsafely retry requests that the server is still actively executing.

4. In `source/core/Ky.ts`, `#fetch()` calls `this.request.clone()` whenever `retry.limit > 0`, which invokes `ReadableStream#tee()` on streaming bodies. Enabling retries for POST and PATCH by default will force every streaming upload to buffer unconsumed chunks in memory, risking excessive memory consumption or out-of-memory crashes on resource-constrained mobile devices.

5. If a POST or PATCH request body is a `ReadableStream` that was disturbed or locked during an interrupted initial attempt, `Request.clone()` in `#fetch()` will throw an unhandled `TypeError` on the retry attempt rather than recovering cleanly. This would cause flaky mobile requests to crash with native stream errors rather than surfacing a clean `NetworkError`.

6. When using `onUploadProgress`, `streamRequest` in `source/utils/body.ts` pipes the request body through a progress-tracking transform stream. Retrying an interrupted POST or PATCH upload will cause progress events to restart from 0%, triggering confusing progress regressions or duplicate completion events in client UIs.

7. Existing custom `retry.shouldRetry` hooks that return `undefined` rely on Ky falling through to default method checks that reject POST and PATCH. Enabling POST and PATCH retries by default would alter this fallback behavior, silently triggering retries for existing applications that expect `undefined` to reject non-idempotent requests.

8. This change directly breaks existing test assertions in `test/retry.ts`—specifically tests like `'not on POST'` and `'NetworkError is not retried for non-retriable method (POST)'`—which enforce that POST requests fail fast without retrying. Changing this default represents a breaking change in Ky's core HTTP semantics for existing consumers.

9. POST and PATCH mutations frequently carry headers such as `Idempotency-Key` or authorization nonces generated for a single attempt. Retrying automatically without re-running `beforeRequest` hooks or providing a mechanism to refresh request-specific tokens will cause backends to reject retried requests as duplicate or invalid submissions.

10. Across heterogeneous mobile JS runtimes (such as React Native or older WebKit), calling `Request.clone()` on requests containing `FormData` or multipart bodies has known runtime bugs where boundaries or `Content-Type` headers are stripped. Retrying POST and PATCH requests by default exposes all multipart form submissions to these runtime cloning defects on every attempt.
