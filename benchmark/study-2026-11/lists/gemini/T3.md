1. In `styleguide_example/blog_examples/google_login_server_flow/sdk/apis.py` and `raw/apis.py`, the callback reads `id_token_decoded["email"]` without checking the `email_verified` claim. If an attacker registers an unverified Google account using a target's email address, automatic linking will grant unauthorized access to an existing password-authenticated account.

2. `GoogleAccessTokens.decode_id_token` in `sdk/services.py` and `raw/service.py` explicitly disables JWT verification with `verify_signature: False` and leaves `GOOGLE_AUTH_PROVIDER_CERT_URL` empty. Accepting forged or unverified ID tokens allows malicious actors to impersonate any user's email and compromise their account.

3. When a user signs up via Google first, `BaseUserManager.create_user` assigns an unusable password via `user.set_unusable_password()`. Because `UserCreateApi` rejects existing emails and no password-setting or reset endpoints exist, that user will be permanently unable to set a password or authenticate through `UserSessionLoginApi` or `UserJwtLoginApi`.

4. While `UserJwtLoginApi` and `UserSessionLoginApi` return JWT tokens and session keys respectively, `GoogleLoginApi` only calls `login(request, user)` and returns raw Google tokens without returning a session key or generating a JWT. Clients relying on `JSONWebTokenAuthentication` or `SessionAsHeaderAuthentication` via `ApiAuthMixin` will be unable to authenticate subsequent API requests after Google sign-in.

5. `GoogleLoginApi` directly invokes Django's `login(request, user)` immediately upon finding a matching user, bypassing the `is_active` check that Django's `authenticate()` enforces during password logins. This allows inactive or deactivated accounts (`is_active=False` on `BaseUser`) to regain access simply by authenticating through Google.

6. `BaseUserManager.create_user` normalizes emails with `self.normalize_email(email.lower())`, but `GoogleLoginApi` filters with `user_list(filters={"email": user_email})`, which performs a case-sensitive exact match. If Google returns an email with differing capitalization, the lookup will fail to link the account, triggering unexpected 404 errors or duplicate registration attempts.

7. Auto-provisioning missing accounts during Google login without atomic transactions or locking will race with concurrent password registrations (`UserCreateApi`) for the same email. This will crash the callback with an unhandled database `IntegrityError` due to the unique constraint on `BaseUser.email`.

8. `BaseUser` links identity exclusively via the mutable `email` string and contains no field or model to track Google's immutable subject identifier (`sub`). If a user changes their primary email address in either service, account linking breaks or risks associating a recycled email with an unintended user.

9. `auth_logout` in `styleguide_example/authentication/services.py` invalidates JWT tokens by rotating `user.jwt_key`, but session logout only clears the Django session without touching the JWT key. Linking both authentication methods without a coordinated session and token revocation strategy means revoking access or logging out from one method leaves the other active.

10. `GoogleLoginApi` logs in any matching user without checking administrative privileges or enforcing the two-factor authentication implemented in `styleguide_example/custom_admin/sites.py`. A compromised Google account belonging to an admin (`is_admin=True`) could bypass admin 2FA verification entirely.

11. Google OAuth logic is currently split between two separate sample packages (`blog_examples/google_login_server_flow/sdk` and `raw`) rather than integrated into `styleguide_example/authentication/`. Implementing linking across or between these demonstration modules without consolidating into a single domain service creates divergent, hard-to-maintain authentication flows.
