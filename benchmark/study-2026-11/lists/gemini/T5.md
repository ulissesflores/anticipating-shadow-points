1. In `app/entrypoint.sh`, migrations are preceded by `python manage.py flush --no-input`; mistakenly copying or adapting this development logic into `app/entrypoint.prod.sh` will wipe the production PostgreSQL database on every deployment.
2. Running `python manage.py migrate` automatically while the old `web` container is still serving traffic will crash the live application whenever a migration introduces backward-incompatible changes, such as renaming or dropping columns and tables.
3. Placing `python manage.py migrate` inside `app/entrypoint.prod.sh` will cause concurrent migration race conditions and table lock deadlocks if multiple replicas of the `web` container are launched simultaneously during rollout.
4. Migrations requiring `ACCESS EXCLUSIVE` table locks (such as adding non-null columns or altering constraints) will block concurrent read and write queries from the running `web` container, causing request timeouts on the live site.
5. In `nginx/nginx.conf`, the upstream is hardcoded to `server web:8000;`, which Nginx resolves via Docker DNS only at startup; starting a new side-by-side container under a different name or IP will not receive traffic without dynamic DNS re-resolution or an explicit Nginx reload.
6. Neither `app/Dockerfile.prod` nor `docker-compose.prod.yml` defines container health checks; without readiness checks, incoming traffic will be routed to the new container while migrations are still executing or before Gunicorn has finished binding to port 8000, triggering 502 Bad Gateway errors.
7. The `web` and `nginx` services share `static_volume` at `/home/app/web/staticfiles`; running `collectstatic` for the new version while the old container is live will overwrite existing assets in place, causing cache mismatches and 404 errors for active user sessions.
8. Standard `docker-compose` commands do not natively support zero-downtime rolling replacements; attempting to start a new `web` container alongside the existing one will fail due to container name and network alias conflicts unless a blue-green orchestration strategy is introduced.
9. If an automatic database migration fails midway due to a constraint violation or invalid SQL, the deployment script may crash without an automated rollback strategy, leaving the database partially migrated and both container versions in a broken state.
10. Running old and new Gunicorn worker processes simultaneously alongside active migration transactions against the single `db` container (`postgres:15`) risks exhausting PostgreSQL's `max_connections` limit, rejecting live user connections.
11. When the old `web` container is terminated after the new one is up, in-flight operations—such as image uploads processed by `upload/views.py`—will be abruptly severed if Docker does not allow Gunicorn sufficient graceful shutdown time.
