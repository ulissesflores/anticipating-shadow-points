1. **Non‑idempotent side effects** – POST and PATCH usually modify server state; automatically retrying them can cause duplicate writes or unintended state changes if the original request actually succeeded but the client didn’t receive a response.  

2. **Request body consumption** – Ky streams request bodies (e.g., `ReadableStream`, `FormData`, file blobs). After a failed attempt the body may be exhausted, making a retry impossible or resulting in a corrupted payload.  

3. **Hook interactions** – Existing `beforeRetry`/`afterResponse` hooks may rely on the original request object; blindly retrying could bypass custom logic, mutate shared state, or invoke hooks multiple times unexpectedly.  

4. **Timeout semantics** – `retryOnTimeout` is currently `false` by default. Enabling retries for POST/PATCH may unintentionally retry when a timeout occurs *after* the server has started processing, again risking duplicate operations.  

5. **Header side‑effects** – Some APIs require one‑time authentication or nonce headers (e.g., CSRF tokens) that become invalid after the first attempt; automatic retries would send stale headers and trigger authentication failures.  

6. **Back‑off and jitter defaults** – The library’s default exponential back‑off may be too aggressive for mobile networks, leading to long delays or throttling; without tuning, retries could degrade the user experience.  

7. **TypeScript typings** – The `retry.methods` option currently excludes `POST`/`PATCH` by default. Changing defaults requires updating the `MutableRetryOptions` and related type definitions, else developers may see type errors or mismatched IntelliSense.  

8. **Compatibility with existing `retry` config** – Projects may already specify a custom `retry` object that omits `methods`. Overriding the default could unintentionally extend the retry set, breaking assumptions in tests or CI pipelines.  

9. **Network‑error detection** – Ky decides whether an error is “network” via `isNetworkError`. Certain mobile edge cases (e.g., DNS‑lookup failures) may be classified differently, causing inconsistent retry behavior for POST/PATCH versus GET.  

10. **Memory‑leak risk** – Repeated retries of large upload payloads without proper stream cancellation can accumulate buffered data, potentially exhausting memory on constrained mobile devices.  

11. **Server‑side rate limiting** – Automatic retries on POST/PATCH may repeatedly hit rate‑limit responses (`429`) and ignore `afterStatusCodes` handling, leading to rapid back‑off loops and possible bans.  

12. **Testing coverage** – The current test suite focuses on GET/DELETE retry paths; adding POST/PATCH retries may expose untested code paths, causing false‑positive test passes or hidden regressions.
