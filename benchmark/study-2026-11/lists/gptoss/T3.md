1. **Duplicate accounts due to unverified email** – Google OAuth may return an unverified email address; linking it directly to an existing password‑based account could let an attacker create a second login for the same address without proving ownership.  

2. **Case‑sensitivity mismatch** – `BaseUserManager.create_user` lower‑cases the email, but the OAuth payload may contain mixed‑case values; if linking logic compares case‑sensitively, the same email could be stored twice, violating the unique constraint.  

3. **Race condition when linking accounts** – Simultaneous sign‑in attempts (Google and password) could both create a new `BaseUser` record before the linking step runs, resulting in orphaned duplicate rows and broken session handling.  

4. **Password‑less accounts breaking existing auth flow** – Users created via Google will have `set_unusable_password()`; later attempts to log in with a password will always fail, and the API (`UserSessionLoginApi`) does not check for `has_usable_password()`, leading to confusing “invalid credentials” responses.  

5. **JWT key invalidation on logout** – `auth_logout` rotates `jwt_key` for any user; if a Google‑linked account logs out via the JWT endpoint while a session‑based login is still active, subsequent JWT‑based requests will be rejected, causing inconsistent logout behavior.  

6. **Missing CSRF / state verification in OAuth flow** – The repository currently has no OAuth view (`google_login_server_flow` only contains placeholder SDK files). Adding a Google sign‑in endpoint without proper `state` token handling could expose the flow to CSRF attacks or token replay.  

7. **Inconsistent authentication back‑ends** – The project mixes session‑based login (`UserSessionLoginApi`) and JWT (`UserJwtLoginApi`). Introducing Google OAuth without a unified backend may cause users to receive a JWT but still rely on session cookies, leading to “not authenticated” errors on protected endpoints.  

8. **Data loss when merging profiles** – Linking two accounts by email will likely require merging related data (e.g., `UserProfile`, 2FA settings). The current code has no migration or merge logic, so naive linking could overwrite or discard existing fields, violating GDPR‑style data integrity.
