1. **`is_active` flag overload** – the `UserBase` model already defines `is_active`, which is used for account activation/login; repurposing it for soft‑delete may break existing authentication checks that treat a non‑active user as never‑registered.  

2. **Cascade delete on items** – `User.items` is defined with `cascade_delete=True` and `Item.owner_id` uses `ondelete="CASCADE"`. If a soft‑delete implementation mistakenly performs a hard `DELETE`, all related `Item` rows will be removed, contradicting the requirement to keep a user's items.  

3. **Missing `deleted_at` timestamp** – without a dedicated `deleted_at` column, restoring a user within 30 days is ambiguous (the system cannot tell whether a user was soft‑deleted or simply never activated), and the purge job cannot reliably identify records to delete after the retention window.  

4. **Authentication bypass** – `crud.authenticate` fetches the user by email and returns it if the password verifies, but it does not check whether the user has been soft‑deleted. A deleted account could still obtain a valid JWT and access protected resources.  

5. **Admin permission enforcement** – the current API routes (`backend/app/api/routes/users.py`) lack an explicit “restore user” endpoint and do not verify that the requester has admin privileges, risking unauthorized restoration or accidental deletion of other accounts.  

6. **Unique‑email conflict on restore** – if a soft‑deleted user’s email is reused by a new account, restoring the original record would violate the `unique=True` constraint on `User.email`, causing a database error and potentially orphaning the original user's items.  

7. **Query filters not updated** – many list‑or‑detail endpoints (`GET /users`, `GET /items`) query `User` or join on `User` without filtering `is_active`/`deleted_at`. After soft‑delete, stale endpoints could still expose hidden users or silently skip them, leading to inconsistent UI behavior.  

8. **Background purge reliability** – implementing a scheduled job to permanently delete users after 30 days must handle time‑zones and clock drift; using `datetime.now(UTC)` without proper truncation may cause records to be removed earlier or later than intended.  

9. **Test suite breakage** – existing tests (`backend/tests/api/routes/test_users.py`) assume hard deletion semantics (e.g., expecting items to be removed). Introducing soft‑delete will cause those tests to fail unless they are updated to assert that items remain.  

10. **Database migrations** – adding a `deleted_at` column requires a new Alembic migration. Forgetting to mark the column as nullable or to set a default can block existing deployments or cause migration conflicts on production environments.  

11. **Auditing and audit logs** – the project currently does not log user deletion or restoration events. Without proper audit entries, compliance and debugging will be impossible, especially when an admin restores a user after the 30‑day window.  

12. **Potential race condition on restore** – if two admins attempt to restore the same soft‑deleted user simultaneously, the restoration code must be idempotent; otherwise, one admin could inadvertently reactivate a user that the other has already permanently purged, leading to data loss or duplicate entries.
