1. **Missing or incomplete email templates** – The repository only contains `export_posts` email templates; there are no dedicated templates for a weekly digest, so rendering `email/digest.html`/`.txt` would fail at runtime.  

2. **No scheduled job for weekly execution** – The codebase uses RQ tasks (`app/tasks.py`) but lacks a cron‑style scheduler (e.g., Celery beat, APScheduler). Without adding a periodic task, the digest would never be sent.  

3. **Potential N+1 query explosion** – Retrieving “new posts written by people they follow” may require joining `followers` and `posts` tables per user; the current `following_posts` query is lazy and could cause many separate DB trips when iterating over all followers, leading to performance degradation on large networks.  

4. **Timezone and date‑range mismatches** – The `Post.timestamp` field is stored as UTC, but the digest must include only posts from the last week; failing to convert to the user’s local timezone could result in missing or duplicated entries.  

5. **No user opt‑out or preference handling** – The `User` model has no column for “email_digest_enabled”. Sending unsolicited weekly emails could violate privacy policies and trigger spam complaints.  

6. **Email delivery limits and back‑pressure** – Sending a digest to every active user could exceed SMTP provider limits; the current `send_email` function does not implement rate‑limiting, retries, or bounce handling, risking dropped messages and a blocked mail server.  

7. **Large attachment risk** – If a user follows many active accounts, the generated JSON payload could become huge, exceeding typical email attachment size limits; the code currently attaches the entire posts list without size checks.  

8. **Task progress tracking misuse** – `tasks._set_task_progress` expects a `Task` entry per RQ job; the digest job would need its own `Task` record, otherwise the progress updates will raise `AttributeError` when `task` is `None`.  

9. **Failure to handle empty result sets** – When a user has no new posts, the digest generator must still send a meaningful email (or skip sending). The current export logic assumes at least one post and may raise a division‑by‑zero error in `_set_task_progress(100 * i // total_posts)`.  

10. **Missing `ADMINS` configuration for sender address** – `send_email` relies on `app.config['ADMINS'][0]` as the sender; if `ADMINS` is not defined in the config for the production environment, the email send will raise a `KeyError`.  

11. **Concurrency race conditions on follower updates** – While the digest job reads follower relationships, concurrent follow/unfollow actions could cause stale or missing posts in the digest unless the query is performed in a repeatable‑read transaction.  

12. **No test coverage for the new feature** – The repository’s `tests.py` does not include tests for scheduled email generation, so regressions (e.g., broken templates or query errors) could go unnoticed until production.
