1. The `entrypoint.sh` script always runs `python manage.py flush --no-input` before migrations, which will delete **all** data on every container start, causing catastrophic data loss in production.  

2. Running `python manage.py migrate` on every deploy can lock database tables; if the existing (old) container is still handling requests, those locks will block reads/writes and produce intermittent downtime or request failures.  

3. With Docker‑Compose there is no rolling‑update or health‑check mechanism, so a new `web` container may be started **before** the previous one has finished serving traffic, leading to a brief period where both containers are operating on the same database schema version and may encounter incompatibilities.  

4. The migration step is triggered unconditionally for **all** environments (including `docker-compose.prod.yml`), so a failed migration in a staging or CI run will automatically bring down the production service when the same image is promoted.  

5. No database backup or snapshot is performed prior to migrations; if a migration script contains a destructive operation (e.g., dropping a column), there is no automated way to roll back, increasing the risk of irreversible schema changes.  

6. The `depends_on` clause in `docker-compose.prod.yml` only guarantees container start order, not readiness; `nginx` may begin routing traffic to the `web` service before the migration has completed, causing 502/504 errors for users.  

7. Because the entrypoint runs migrations each time the container starts, scaling the service (e.g., multiple replicas) will cause **concurrent** migration attempts, resulting in race conditions and potential migration failures.  

8. The script uses a simple `nc` loop with no timeout to wait for PostgreSQL; if the database never becomes reachable, the container will hang indefinitely, preventing new deployments from completing.  

9. Static assets are mounted from a shared volume, but there is no `collectstatic` step in the entrypoint; new code that adds or modifies static files may not be served, breaking the UI after a zero‑downtime deploy.  

10. Environment variables for database connection (`SQL_HOST`, `SQL_PORT`, etc.) are read from `.env.prod` files that are not version‑controlled in the repo, making the migration step brittle and prone to failures when those files differ between environments.  

11. The `docker-compose.prod.yml` does not define any restart policy or graceful shutdown (`stop_grace_period`), so when the old container is stopped for the zero‑downtime swap, in‑flight requests can be terminated abruptly.  

12. There is no explicit versioning or tagging of migration scripts; adding a new migration that depends on a later code change could cause the old container to crash after the database schema has already been upgraded.
