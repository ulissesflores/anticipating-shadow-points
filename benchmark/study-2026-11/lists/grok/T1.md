Vou ler o código de usuários, itens e exclusão para apontar onde um soft delete de 30 dias quebraria de verdade.1. `DELETE /users/{user_id}` runs `delete(Item)` for that `owner_id` before `session.delete(user)`, and `DELETE /users/me` deletes only the user, which still removes items because `User.items` sets `cascade_delete=True` and migration `1a31ce608336` made `item.owner_id` `ON DELETE CASCADE` and `NOT NULL`. Soft-deleting through either call, or hard-purging the row after 30 days, destroys the items this change must keep, and the column cannot be nulled to detach them.

2. `User.email` is `unique=True`, and `crud.get_user_by_email` is the lookup for `POST /users/`, `POST /users/signup`, `PATCH /users/me`, `PATCH /users/{user_id}`, login, and password recovery. A hidden row keeps the address, so the same person cannot sign up again during the window, and rewriting the email to free the index makes a reset JWT (`sub` is the email, valid for `EMAIL_RESET_TOKEN_EXPIRE_HOURS` = 48) apply to whoever owns that address next.

3. `is_active` already blocks login, `get_current_user`, and `reset_password`, and the admin Edit User form toggles it on its own. Using `is_active=False` as the delete mark makes a manually deactivated account identical to a deleted one, and the existing `PATCH /users/{user_id}` (`UserUpdate` carries `is_active`, `password`, `email`, and `is_superuser`) turns the account back on with no 30-day check.

4. Access tokens last 8 days (`ACCESS_TOKEN_EXPIRE_MINUTES`), store only `sub` = user id, and sit in `localStorage`. `get_current_user` loads by id and only rejects `is_active=False`, and `authenticate` has no deletion check, so a hidden user keeps calling `/users/me` and `/items` and can obtain a fresh token until something on those paths reads a deletion timestamp.

5. `POST /password-recovery/{email}` sends a reset mail whenever `get_user_by_email` finds a row and never looks at `is_active`. `POST /reset-password/` only rejects an inactive user, so a hidden account can set a new password and log back in for the whole 30 days.

6. Nothing in this process expires rows: `prestart` migrates, and `init_db` only inserts `FIRST_SUPERUSER` when that email is absent. The 30-day limit has to be a `deleted_at` compared in UTC (same `DateTime(timezone=True)` as `created_at` from migration `fe56fa70289e`) on the restore handler, or hidden rows and their emails stay forever.

7. `GET /users/` counts and lists every `User` (`skip`/`limit` 100, ordered by `created_at`) with a separate count query, and the admin table (`columns.tsx`, `UserActionsMenu`) only offers Edit and Delete. Filtering deleted users out of that list removes the only screen an admin could restore from; leaving them in means the account is not hidden. `UserPublic` has no deletion field, and `frontend/src/client` will not grow a restore call until `scripts/generate-client.sh` is rerun.

8. `init_db` looks up `settings.FIRST_SUPERUSER` by email and skips creation when the row exists. Another superuser can hide that account (`DELETE /users/{user_id}` only blocks `user == current_user`), after which startup will not recreate it and login fails, so nobody left can restore accounts.

9. A superuser's `GET /items/` returns every item, and `PUT`/`DELETE /items/{id}` do not care that the owner is hidden. The items screen shows title and description, not the owner's email, so the kept items stay editable and deletable during the 30 days and cannot be tied back to the hidden account.

10. `test_delete_user_me` and `test_delete_user_super_user` assert the `User` row is `None`, and Playwright `admin.spec.ts` asserts the email row disappears after "The user was deleted successfully". Code that satisfies those tests still hard-deletes, and `DeleteUser.tsx` plus `DeleteConfirmation.tsx` tell the operator that items are permanently deleted and cannot be undone.

11. In development, `POST /private/users/` inserts a `User` with no email-exists check, and Playwright's `createUser` uses that route. A soft-deleted email hits the unique constraint as an unhandled integrity error instead of the 400 returned by `POST /users/signup`.
