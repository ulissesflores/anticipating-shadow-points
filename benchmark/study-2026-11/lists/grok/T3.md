Vou ler o código de autenticação deste repositório para apontar falhas concretas de ligar Google e senha pelo e-mail.O login por senha e o fluxo do Google estão em apps separados. Vou ler os dois e o modelo de usuário.1. Both Google callbacks identify the user from `id_token_decoded["email"]` after `jwt.decode(..., options={"verify_signature": False})`, and neither the raw nor the SDK flow checks `email_verified`, `aud` against `GOOGLE_OAUTH2_CLIENT_ID`, or `iss`. The `userinfo` payload is fetched and then ignored for identity, so an unverified or substituted email claim becomes the link to an existing `BaseUser`.

2. `UserCreateApi` is open: `DEFAULT_AUTHENTICATION_CLASSES` is empty, the view sets no permissions, and `user_create` never confirms the address. The emails app is only an outbox. Anyone who POSTs `/api/users/create/` with a victim's email owns that row, and a later Google sign-in that links on email enters the attacker's account while the attacker still has the password.

3. The reverse path is the same hole. `user_update` has an empty field list, so there is no way to add a password to a Google-created user. Changing `UserCreateApi` so that an existing email "links" by storing the posted password lets anyone who knows the address set that password.

4. `BaseUserManager.create_user` stores `normalize_email(email.lower())`, and `test_user_with_capitalized_email_cannot_be_created` treats the other casing as the same user via `ValidationError` from `full_clean`. The callbacks look up `user_list(filters={"email": user_email})` through `BaseUserFilter`, which is an exact, case-sensitive match, so a mixed-case Google email misses the row and a follow-up `user_create` lowercases it and raises instead of signing in. Inserting without `create_user` can store a second row, because the Postgres unique index is case-sensitive.

5. `BaseUser` has no Google `sub` or other provider id, and `email` is the username. A Google account that changes its address misses the old row and `user_create` inserts another user, or hits `unique` if that address is already taken. The password, `jwt_key`, `UserTwoFactorAuthData` one-to-one, `File.uploaded_by`, and group permissions stay on the old row, and there is no merge path.

6. `user_create` with no password calls `set_unusable_password()`, which `test_user_without_password_is_created_with_unusable_one` already locks in. `UserSessionLoginApi` and `UserJwtLoginApi` both use `authenticate`, so that user can never sign in with a password. Linking must not call `set_unusable_password` on a user who already has one, and `AUTH_PASSWORD_VALIDATORS` never run inside `user_create`, so a new "set password" path can store a password the validators would reject.

7. Password login goes through `authenticate`, so `ModelBackend` rejects `is_active=False`. Both Google callbacks call `login(request, user)` and never read `is_active` or `UserTwoFactorAuthData`. A deactivated account, including an `is_admin` user, gets a session that `UserMeApi` and the file APIs accept through `ApiAuthMixin`. The admin OTP check runs only inside `AdminSite`. Adding a second auth backend makes this `login()` call raise `ValueError`, because the queryset user has no `.backend`.

8. The Google callbacks return `id_token_decoded` and `user_info`. They do not return `{session, data}` or the JWT `{token}` and `JWT_AUTH_COOKIE` that `UserJwtLoginApi` sets. `ApiAuthMixin` accepts a session cookie, `Authorization: Session <key>`, or a `Bearer` token signed with that user's `jwt_key`. A client that only keeps the JWT stays logged out, and a token minted with any other secret fails `JSONWebTokenAuthentication`. `UserSessionLogoutApi` does not rotate `jwt_key`, and `auth_logout` does not clear the session, so one side stays signed in.

9. The live routes are `callback-raw` in `raw/apis.py` and `callback-sdk` in `sdk/apis.py`. `raw/views.py` and `sdk/views.py` repeat the same email lookup and `login()` but are not on the urlconf. Linking in only one of the four copies leaves the others matching or creating accounts under different rules. Both redirect views also share the single session key `google_oauth2_state`.

10. The callbacks do a non-locking `user_list` and would then create. A concurrent `POST /api/users/create/` for the same address can pass the same empty check. The loser gets `ValidationError` from `full_clean`, or `IntegrityError` if that check is skipped. The DRF handler turns the former into a 400 and the latter into a 500, and neither signs the winner in. `ATOMIC_REQUESTS` rolls the request back, so there is no retry onto the row that won.

11. Exact matching on the Google `email` string treats `jane.doe@gmail.com`, `janedoe@gmail.com`, and plus-aliases as different people. Google delivers one mailbox for those. The link then splits one person across two `BaseUser` rows, each with its own password and `jwt_key`.
