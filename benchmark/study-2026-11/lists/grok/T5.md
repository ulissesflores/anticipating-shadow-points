Vou ler o repositório para achar onde o deploy, as migrations e a subida do container realmente acontecem, e listar só os riscos concretos desse pedido.1. `app/entrypoint.sh` runs `python manage.py flush --no-input` before `migrate`. Reusing that script as the production boot path empties `hello_django_prod` on every container start. `app/entrypoint.prod.sh` today only waits for Postgres.

2. `nginx/nginx.conf` sets `upstream hello_django { server web:8000; }` and `proxy_pass http://hello_django` with no Docker DNS resolver. `docker-compose -f docker-compose.prod.yml up -d --build` gives the new `web` container a new IP while the already-running nginx keeps the old one, so port 1337 stays on 502 until the nginx container is recreated as well.

3. Production is a single `web` service with no healthcheck, and `depends_on` only waits until the container has been created. The documented `up -d --build` stops the old container before `entrypoint.prod.sh` finishes and before `gunicorn hello_django.wsgi:application --bind 0.0.0.0:8000` is listening. A `deploy.update_config` block in this Compose file is ignored outside Swarm.

4. The entrypoint reaches `exec "$@"` only after the shell script returns, and the database wait is an unbounded `nc -z $SQL_HOST $SQL_PORT` that never checks that `SQL_USER` from `.env.prod` can log in. A `migrate` added there holds the new container off port 8000 for the whole migration, and a Postgres that accepts TCP but rejects the role leaves this container as the only upstream while gunicorn is still not running.

5. `entrypoint.prod.sh` has no `set -e`, so a failed `migrate` still starts gunicorn against the migrations that already committed. Each Django migration is one Postgres transaction, but migration N+1 can fail after N is committed, and the compose service sets no `image:` tag, so `--build` overwrites the previous web image and leaves nothing to start when the new code and the half-applied schema disagree.

6. Keeping the old container up means a second `web` replica, and both would run `migrate` on boot against `hello_django_prod`. Those two runs can deadlock on the same `CREATE` or `ALTER`, or both write `django_migrations` and then abort because the relation already exists, so neither replica reaches gunicorn.

7. Every container shares one database. `upload/migrations/` contains only `__init__.py`, and the production entrypoint has never applied migrations, so the first automated `migrate` builds the contrib auth, admin, and session tables under live `/admin/` traffic. A later migration that drops, renames, or adds a `NOT NULL` column is applied while the previous container is still serving the old models.

8. Nginx serves `/static/` and `/media/` from `static_volume` and `media_volume`, which outlive the web container, so a `collectstatic` in the same entrypoint as `migrate` rewrites or, with `--clear`, deletes files another container is still using. `image_upload` stores the upload on `media_volume` via `FileSystemStorage`, and with no `stop_grace_period` Docker’s 10s `SIGKILL` cuts gunicorn’s 30s graceful stop and leaves a partial file.

9. The only migrations that run are the files `Dockerfile.prod` copies in with `COPY . $APP_HOME`. `migrate` will not invent the missing `upload` migration, and a `makemigrations` in the entrypoint writes that file only in the container’s writable layer. The next recreate boots an image without it and hits `InconsistentMigrationHistory` against the rows already stored on `postgres_data`.

10. `db` is in the same compose project, with no healthcheck, and `POSTGRES_PASSWORD` from `.env.prod.db` is honored only when `postgres_data` is first created. Recreating `db` or changing that password leaves the old role password in the volume, `migrate` cannot authenticate, and the web entrypoint never reaches gunicorn. A deploy that uses `down -v` also deletes `postgres_data`, `static_volume`, and `media_volume`.

11. `settings.py` falls back to a sqlite file at `BASE_DIR / "db.sqlite3"` when `SQL_ENGINE` is unset, and both entrypoints run their database steps only when `DATABASE=postgres`. Dropping either variable from the env file migrates a sqlite file that disappears with the container, or skips `migrate` and boots gunicorn against an unmigrated `hello_django_prod`.
