Vou ler o código de retry do ky e onde POST/PATCH são tratados, para listar os riscos concretos desta mudança.1. `retry.methods` is checked in `#calculateRetryDelay` before the error type, so adding `post` and `patch` to `retryMethods` in `source/utils/normalize.ts` also retries the default status codes 408, 413, 429, 500, 502, 503, and 504. The test `not on POST` currently requires a 500 to be sent once, and a 500 on POST often means the server already committed the write.

2. Ky never sends an `Idempotency-Key`. `isRawNetworkError` only matches `TypeError` messages such as `Failed to fetch`, `fetch failed`, and `terminated`, which is the same signal when the socket dies before the POST is sent and after the server has already processed it, and the default `limit` of 2 means the body can go out three times.

3. PATCH is not idempotent, and this repo already retries PUT and DELETE while leaving POST and PATCH out of `retryMethods` on purpose. Replaying a JSON Patch `add` or any other non-idempotent PATCH duplicates the change, so treating PATCH like PUT is unsafe.

4. A stalled mobile connection hits the per-attempt `timeout` of 10000 ms and becomes a `TimeoutError`, which is not retried because `retryOnTimeout` defaults to false. A drop while `.json()` or `.text()` is reading is wrapped in `NetworkError` inside `#raceBodyRead` and thrown through `#throwProcessedError`, so it is also not retried. `totalTimeout` defaults to `false`, so turning those paths on would resend a POST the server may already have answered, with no overall deadline.

5. `isRawNetworkError` treats every Chrome `Failed to fetch` and every Undici `fetch failed` or `terminated` as retriable, including CORS, CSP, mixed-content, and blocker failures, plus Chromium streaming uploads over HTTP/1.1, which `source/types/options.ts` documents as a network error even on plain HTTP. Those retries cannot succeed. The `beforeRetry` escape of clearing `onUploadProgress` runs only after the method is allowed, and it does nothing for a stream POST that failed without a progress handler.

6. A throw inside `onUploadProgress` fails the upload stream and is documented as a `NetworkError` that is retried, with the callback running again. The sample call is `ky.post`, but the method check currently stops that, so once POST is retriable a buggy progress callback duplicates the upload instead of failing once.

7. A retry resends the clone taken in `#fetch` with `Request.clone()` and `tee()`, then `cancelBody()` cancels the upload that just failed. The test that a network error resends a complete POST stream only covers an explicit `methods: ['post']` list, and it reads the whole body before throwing. A drop while the tee source is still live can error the saved branch, so the next attempt throws a stream `TypeError` that is not a `NetworkError` and the original failure disappears. Large uploads are then held in memory and transmitted up to three times.

8. `fetch` follows redirects inside a single attempt. A POST the server already accepted, answered with 301, 302, or 303, or followed with 307 or 308 onto a hop that then failed, is reported as a network error on the original request, and the retry sends that POST and its body to the original URL again.

9. 408 is in the default `statusCodes`, and the readme says Chromium already retries 408 on keep-alive connections. POST is outside `methods` today, so it avoids that second replay. Adding it makes Ky and the browser both resend the POST. A 429 or 503 also uses retry-timing headers with `maxRetryAfter` of `Infinity`, so the cloned POST body can sit in memory for as long as `Retry-After` says.

10. Callers who pass `retry: 2` or `{limit: n}` do not pin `methods`. `normalizeRetryOptions` fills them from `defaultRetryOptions`, and `methods: undefined` is specified to reset to that same list. `replaceOption(3)` is tested as restoring the default where POST is not retried. All of those callers would start retrying POST and PATCH unless they pass an explicit methods array.

11. `shouldRetry` and `beforeRetry` never run for a failing POST today, because the method check happens first. A `shouldRetry` that returns `undefined` to keep the default logic would start allowing POST status-code retries, and a `beforeRetry` that returns a new `Request` (used as-is, and unable to change `retry.methods`) can drop the body or mint a fresh idempotency header on each attempt.
