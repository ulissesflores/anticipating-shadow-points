Vou ler o repositório para achar onde posts, follows e e-mail já existem, e listar só os riscos concretos desse digest semanal.1. `User.following_posts()` also returns the recipient's own posts: the filter is `Follower.id == self.id OR Author.id == self.id`, and `test_follow_posts` expects that (John receives his own post; David, who follows nobody, still receives his). Dropping the `group_by(Post)` that collapses that self-join repeats each of those posts once per follower.

2. Nothing here fires weekly. The installed `rq` is only a consumer (`Procfile` worker and `deployment/supervisor/microblog-tasks.conf` with `numprocs=1`), and `app/cli.py` only implements `translate`. Starting a scheduler inside `create_app()` runs it once per Gunicorn worker and again in the worker process, because `app/tasks.py` calls `create_app()` at import, so the same week is mailed more than once.

3. `User` has no digest cursor. `last_seen` is overwritten on every authenticated request in `before_request`, and `last_message_read_time` tracks private messages. A rolling seven-day cutoff resends posts when the job overlaps or is retried, and skips posts when the single worker is down longer than the window. `followers` stores only the current edge, so a Friday follow includes that author's whole week and an unfollow before the job drops posts written while the follow existed.

4. `Post.timestamp` is a timezone-naive `DateTime` filled with aware `datetime.now(timezone.utc)`. Comparing those values, once read back from Postgres or SQLite, with an aware cutoff in the worker raises or puts boundary posts in the wrong week. No user timezone is stored, so the week boundary is only the server clock.

5. A worker cannot render mail the way password reset does. `get_locale()` reads `request.accept_languages`, and `User` has no locale column, so `_()` has neither a request nor a language (`LANGUAGES` is only `en` and `es`). `url_for(..., _external=True)` needs `SERVER_NAME`, an optional env var that is empty outside a request. Running each body through `app.translate.translate` calls Microsoft once per post, calls `_()` itself, and when `MS_TRANSLATOR_KEY` is missing or `post.language` is `''` (the `LangDetectException` path) returns the error sentence as the post text.

6. `send_email` defaults to a detached thread; only `export_posts` passes `sync=True`. An async send from an RQ job returns before SMTP finishes and dies with the job. A synchronous send for every user occupies the only worker, queued behind `export_posts`, which sleeps five seconds per post. RQ's default job timeout is 180 seconds, so a long digest is killed mid-loop. The sender is `ADMINS[0]`, hardcoded to `your-email@example.com`, and `MAIL_SERVER` is optional, so the message raises or is rejected.

7. `Task.user_id` is required, and `launch_task` always enqueues `app.tasks.{name}` with that user id. The only dedupe is `get_task_in_progress`. `export_posts` sets progress to 100 in both `except` and `finally`, so a failed run is stored as complete and is not retried. With no per-recipient send record, a retry after a partial SMTP failure mails a second copy to everyone already sent.

8. Posts are unlimited apart from `Length(max=140)`, while the home page stops at `POSTS_PER_PAGE` (25). Paginating the digest the same way drops the rest. Loading every followed post in the worker's long-lived session never calls `db.session.remove()`, so the identity map grows for the life of the process. The default database is SQLite, and every page view commits `last_seen`, so a long digest write lock stalls the site.

9. Addresses are never confirmed, and there is no opt-out. `POST /api/users` is unauthenticated, `PUT /api/users/<id>` can replace `email` with no verification, and the profile form does not edit email. The digest would send post bodies, which the app only shows behind `login_required`, to whatever inbox was typed. `Message` has the same body, timestamp, and author shape as `Post`, so a sweep of "activity from people I follow" would put private messages in the mail.
